# #87958: ED-209 and other patrol bots do not patrol on Tramstation

| | |
|---|---|
| Issues | [#87958](https://github.com/tgstation/tgstation/issues/87958): verified, fixed |
| Status | Fixed on a branch (map-only change); the beacon layout is a mapping choice for maintainers |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/87958 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Tramstation has almost no patrol navigation beacons. The upper station level has none, and the lower level has one whose `next_patrol` points at a beacon that does not exist. Patrol-mode bots look for a beacon on their own z-level, find none, and stand still. The fix adds a 10-beacon patrol loop on the upper level (central tram dock, bar, kitchen, theater, lounge) and a 5-beacon loop in the lower-left maintenance corridor that closes on the existing beacon. With them, an ED-209 and other bots patrolled on both levels in game.

## The bug

On Tramstation an ED-209 (or any other patrolling bot) that is set to patrol does not move, which the issue reports as the robot turning patrol off at once. A comment on the issue says only the lower "tramhole" has patrol beacons and the first floor has none, and a later comment says there are no navigation routes on the top level.

## Reproduction

1. Load Tramstation on the test server and start a round (the map has two station levels, game z2 lower and z3 upper).
2. As an observer, using the Lua editor, spawn `/mob/living/basic/bot/secbot/ed209` in the Central Tram Dock on z3 (the test used 125,123). A secbot named "Commander Beep O'sky" was already on z3 and was observed too.
3. Read `bot_mode_flags` and the beacon lists. The ED-209 had `bot_mode_flags` 16777207, so the autopatrol bit was set, and `GLOB.navbeacons["3"]` held no patrol beacons. Over repeated checks the ED-209 and Commander Beep O'sky stayed on their tile and the ED-209's beacon target (`BB_BEACON_TARGET`) was nil.

The ED-209 was spawned by the Lua editor rather than built by hand. In this master the patrol flag is not switched off by the bot, so "turning itself off" is not what happens: the flag stays set, the bot just has nothing to walk to.

## Cause

Patrol behavior is the `bot_patrol.bt.json` behavior tree, whose first step is `find_first_beacon_target` (`code/datums/ai/bots/bot_subtrees.dm:142`). It scans only `GLOB.navbeacons["[bot_pawn.z]"]`, the beacons on the bot's own z-level (`bot_subtrees.dm:150`). When that list is empty it returns `AI_BEHAVIOR_DELAY | AI_BEHAVIOR_FAILED` (`bot_subtrees.dm:159-161`) and the bot idles.

In `_maps/map_files/tramstation/tramstation.dmm` the only patrol navbeacon in the whole map is "TramLower16" (line 12877, game z2), with `codes_txt = "patrol;next_patrol=TramLower1"`. No beacon named "TramLower1" exists, so even that one is a dead end. The upper level (z3) has only delivery beacons (Library, Chapel, Security, Medical, Kitchen, Bar and so on), none with patrol codes.

## Fix

One commit, "Fix issue 87958: add patrol navigation beacons to Tramstation", edits only `tramstation.dmm` (152 lines added, 15 removed; the removed lines are the 15 tile references that now use new dictionary keys).

- Upper level: ten beacons, TramTop1 to TramTop10, each with `codes_txt = "patrol;next_patrol=<next>"`, and TramTop10 pointing back to TramTop1 so the route loops. The route runs around the central tram dock, bar, kitchen, theater and lounge.
- Lower level: five beacons, TramLower1 to TramLower5 in the lower-left maintenance corridor, with TramLower5 pointing at the existing TramLower16. This also fills in the dangling link, though TramLower16 itself still points at "TramLower1", which now exists and closes the loop.
- Each beacon was placed by adding a new dictionary key that copies the existing tile's contents plus the beacon, then pointing the grid cell at it. Where the intended tile held dense objects, the nearest open floor tile was used. The file was kept in TGM format.

Beacons were kept within a path-length limit of the pathfinder (the bot's JPS pathing used a maximum length of 25 steps), by keeping hops short. The placement avoids the tram lane. The other approach discussed in the issue, routing through maintenance, was not attempted, and the commenters noted the bolted airlocks would complicate it.

## Verification

- Before editing the map, ten test beacons (TramTop1 to TramTop10) were created on z3 with the Lua editor. The ED-209 and Commander Beep O'sky then moved between samples (for example 126,125, then 132,137, then 126,126, then 126,125), consistent with completing the loop.
- After the map edit and a rebuild, a new round was started on Tramstation. The beacon lists held 10 patrol-capable beacons on z3 and 6 on z2. A freshly spawned ED-209 moved from the dock (125,123) to 126,125, then to 136,132, then back to 126,125 over about a minute. The lower-level T.R.A.M Unit bot moved across 63,118, 76,119 and 73,118. Commander Beep O'sky moved only a few tiles (126,125 to 127,128) over the same period.
- The runtime log of that round contained no runtime errors.

Not checked: that the bots complete the whole loop repeatedly over a long time, behavior at the 25-step JPS limit on every hop, patrol while the tram is moving, and how the new beacons interact with the delivery beacons. Whether the bots path sensibly through all areas the loop touches was only checked by sampled positions.

## Notes

- Coverage is partial: the tram lane and the far east and far west areas have no beacons, because reaching them crosses the tram or bolted airlocks. The Medical, Science and QM plazas also need crossing the tram lane, so they are not covered.
- Beacon placement is a mapping choice. Maintainers may want a different route or more beacons, and may prefer to edit the map with the project's map tooling rather than by script.
- The issue text says patrol turns itself off. On this master the cause is the missing beacons, not a toggle in the bot code.
