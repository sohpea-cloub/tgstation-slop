## Summary

The report says the Nanotrasen Science Hub PDA app (the research app that scientists and heads get at roundstart) bluescreens the first time it is opened in a shift, and works after the PDA is closed and reopened. On master the first open sent complete, consistent data and produced no runtimes. The frontend also has code for the race that fits the report (dynamic data arriving before static data). The reporter's build very likely predates the techweb UI rework (PRs 98270 and 97223), so the crash was probably in the older code. That was not checked against the old code, and no real-client check was done.

## The bug

As reported: load in as a head or scientist, open the research app, and the UI bluescreens. Closing and reopening the PDA fixes it for the rest of the shift. Only the first open is affected. A commenter confirmed it and said it was the research app.

## Reproduction

Not reproduced. What was tried on the test server, at the first open of the app in the round:

1. Started the round, then used the Lua editor to spawn a human, give it the scientist outfit and possess it.
2. Took the PDA from the belt and opened it to the main NtOS screen. Put an ID in the PDA (using Lua: moved the ID into the PDA and set `stored_id`).
3. Ran the `experi_track` program (Nanotrasen Science Hub) with the `PC_runprogram` UI action. This was the first open of the app in the round.
4. Looked at the data the server sent for the opened `NtosTechweb` window, and at the round's `runtime.log`.

Observed: the first message contained, together, `techweb_catalogue` (url and version 1), `experiment_metadata` (8 keys), `stored_research`, `nodes` (id, tier and flag triples), `experiments` (8 entries), `points`, `points_last_tick`, `sec_protocols` and `locked`. The catalogue asset JSON (about 140 KB) was sent in the same step. `runtime.log` had no runtimes, only the known empty "uncaught runtime error:" lines.

This tooling cannot run the tgui JavaScript, so the actual window rendering was not seen.

## Cause

No defect was found on master. Relevant code:

- `code/modules/modular_computers/file_system/programs/techweb.dm` builds `ui_data`, `ui_static_data` and `update_static_data_if_outdated`. The static-key bookkeeping (`sent_static_keys`) was consistent on a first open.
- In `code/modules/tgui/tgui.dm`, `get_payload` (around lines 263-296) computes `ui_data` before static data, so a client can receive dynamic data without static data.
- `tgui/packages/tgui/interfaces/Techweb/Data.tsx:17-22` shows a loading screen until both `techweb_catalogue` and `nodes` exist, with the comment that NtOS can send data before static data the first time the app is opened. `Techweb/helpers.ts` (`joinResearch`) skips experiments whose description is missing or mismatched, `TechNode.tsx` falls back to `LockedExperiment` for an unknown experiment, and `common/catalogue.ts` retries the catalogue fetch with backoff.
- Switching apps inside an already open PDA window goes through `update_tablet_open_uis` in `computer_ui.dm`, which uses `send_full_update`. That call is gated by a 1 second cooldown, so a `ui_data`-only update can reach the client first. This is the case the frontend now handles.

Because the rework (PR 98270, which moved node and design data into a cached JSON asset and made experiment descriptions static data) changed how this data is sent, the bluescreen in the report was probably in the previous `ui_data`/frontend code. This is an inference: the old code was not run or read.

## Fix

None. No commit was made.

## Verification

A frontend test was written as a throwaway (not committed) and run with bun. It rendered `TechwebStart` with a synthetic catalogue in two cases: (1) static data and data together renders the full viewport; (2) data first and static data later shows "Please wait..." and then the full viewport. Both passed. So the first-open race that fits the report is handled in this tree.

Not checked: a real Dream Seeker client opening the app (the only definitive check), the behavior of the pre-rework code, and opening the app as a head rather than a scientist.
