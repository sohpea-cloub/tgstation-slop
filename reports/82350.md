# #82350: Over-long adminhelps and admin PMs are silently truncated

| | |
|---|---|
| Issues | [#82350](https://github.com/tgstation/tgstation/issues/82350): verified (adminhelp path reproduced and fixed; admin PM path patched but not run) |
| Status | Fixed on the fix branch |
| Fix branch | [fix/82350](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/82350) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Adminhelps and admin PMs longer than `MAX_MESSAGE_LEN` (1024 characters) are cut off with `copytext_char` and nothing tells the sender, so the tail of a long message is lost. The fix checks the length before sending. An over-long message is refused with an error that shows its length and the limit and echoes the full text back, so the player can shorten it without retyping. The Adminhelp tgui window also stays open with the text intact.

## The bug

A player writes a long adminhelp and sends it. The admins receive only the first 1024 characters. The window gives no limit indicator and no warning, and the sender sees nothing wrong. The issue reporter had to rewrite the missing part.

## Reproduction

1. Start a round on master and open the Adminhelp window from the `adminhelp` verb. The test was done as a localhost guest, who is an admin.
2. Submit an ahelp with a message of 1329 characters (the word "word" repeated).
3. Observed: the chat showed `PM to-Admins: word word ... wor`. The message ended mid-word at 1024 characters, the window closed, and there was no warning.

This was reproduced through the normal ahelp action, not by calling procs directly.

## Cause

The length limit is applied by cutting the string, with no check or message:

- `code/modules/admin/verbs/adminhelp.dm:214`, in `/datum/admin_help/New`: `sanitize(copytext_char(msg_raw, 1, MAX_MESSAGE_LEN))`
- `code/modules/admin/verbs/adminhelp.dm:403`, `MessageNoRecipient`, the same pattern
- `code/modules/admin/verbs/adminhelp.dm:788`, in `perform_adminhelp` (the urgent-ahelp path)
- `code/modules/admin/verbs/adminpm.dm:579`, in `adminpm_filter_text`, for senders without server/debug rights (and for messages to the external PM user)
- `code/modules/admin/verbs/adminpm.dm:688` also truncates, in a different path that was not examined further.

`MAX_MESSAGE_LEN` is 1024 (`code/__DEFINES/say.dm:126`). The Adminhelp tgui interface (`Adminhelp.tsx`) has no limit or counter. `ui_act` in `/datum/admin_help_ui_handler` calls `perform_adminhelp` at `adminhelp.dm:759` and then closes the window.

## Fix

One commit, "Fix issue 82350: refuse over-long adminhelps and admin PMs with an error instead of silently truncating them":

- In `/datum/admin_help_ui_handler/ui_act` (`adminhelp.dm`), before `perform_adminhelp`, the length of the message is checked with `length_char`. If it is over `MAX_MESSAGE_LEN`, the sender gets a danger-styled chat message ("Your adminhelp is N characters long, which exceeds the maximum of 1024, so it was not sent. Please shorten it and try again. Your message was: ...") with the sanitized text, and the proc returns before `ui.close()`, so the window stays open with the text in it.
- In `adminpm_filter_text` (`adminpm.dm`), the same check was added at the start of the branch for non-high-rank senders. It prints an "Error: Admin-PM-Filter" line with the length, the limit and the message, and returns.

The check was put in front of the existing truncation rather than raising the limit, because the limit is shared with other message types. The idea follows upstream PR #82837, which does the check in `/datum/admin_help/New`. That PR was closed, not merged, so master still had the bug. The tgui interface was not changed, so there is no live character counter.

## Verification

After rebuilding, on the test server:

- The same 1329-character ahelp was refused with the new message ("...1329 characters long, which exceeds the maximum of 1024, so it was not sent...") and the full text echoed in the chat.
- A short ahelp ("short ok message") still sent and closed the window normally.

Not checked:

- The admin PM path. The test account is a high-rank admin, which skips the patched branch, so the new PM message was never shown.
- The urgent-ahelp path at `adminhelp.dm:788`, the `MessageNoRecipient` path and the `adminpm.dm:688` path were not changed and not tested.
- Reading the code, the fallback path used when tgui is unavailable (`adminhelp.dm:802`) calls `perform_adminhelp` directly and therefore does not go through the new check, so it would still truncate silently. This was not exercised.

## Notes

- Upstream PR #82837 attempted the same fix and was closed without merging.
- A live counter or a limit notice in the Adminhelp interface would address the "hidden limit" part of the title more directly. It was not done here.
