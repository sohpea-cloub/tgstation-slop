## Summary

When several hot-mic intercoms (`broadcasting = TRUE`, `listening = FALSE`) hear the same line, the telecomms broadcaster correctly drops the repeated signals as duplicates, but it dropped them before marking them as handled. The sending radio's 2-second backup check then saw an "unprocessed" signal and rebroadcast it as an ordinary radio message, so one spoken line appeared several times in chat and in the telecomms log. The fix marks the signal done before the duplicate check. A second change stops `broadcast()` from composing a message with an already-deleted virtualspeaker, which is the source of the `get_language_holder()` runtime in the report; that part was found by reading the code and was not reproduced.

## The bug

The reporter saw, on a live round: runtimes from `get_language_holder()` called on a QDELing `/atom/movable/virtualspeaker` (followed by `Cannot execute null.has language()`), the telecomms log filled with repeats of everything said, and one air alarm in the AI chamber repeating its message dozens of times (about 26 per alarm). Stripping telecomms down to one set of machines removed some of the repetition, but not the air alarm's. Commenters reported that unscrewing and reattaching an intercom next to the AI seemed to stop it, and a 2024 comment reproduced it by mapping in a hot-mic intercom on a custom frequency, which sent each message 4 times; speaking into it manually with `:i` did not repeat.

## Reproduction

On Meta station, using admin tools on the test server:

1. As an observer, used the Lua editor to spawn a human ("Tester") in the AI antechamber at 215,139,2. Three mapped intercoms there are hot mics on AI Private (1447): at 215,140, 215,138 and 217,141, each with `broadcasting = 1` and `listening = 0`.
2. Made the human say "mapped test".
3. Read `telecomms.log` and the chat.

Before the fix: `telecomms.log` had 3 "Mapped test" lines (one at +0 s, two at +2.0 s). Chat showed "[AI Private] ... Mapped test" once and "[144.7] ... Mapped test" twice (the repeats arrived as ordinary radio messages on the common frequency). A newscaster line also showed up both as [AI Private] and as [144.7]. A single, non-mapped hot-mic intercom produced one line, as expected.

The runtime half was not reproduced. An attempt to build the needed signal and lists from Lua failed on unrelated null-list runtimes.

## Cause

Two separate defects.

1. **Duplicates dropped without being marked done** (`code/game/machinery/telecomms/machines/broadcaster.dm:30-36`). The broadcaster suppresses spam with a one-second `GLOB.recent_messages` check, but returned before calling `signal.mark_done()`:

   ```dm
   var/signal_message = "[signal.frequency]:[signal.data["message"]]:[signal.data["name"]]"
   if(signal_message in GLOB.recent_messages)
       return

   // Prevents massive radio spam
   signal.mark_done()
   ```

   The sending radio schedules `backup_transmission()` two seconds after transmitting (`code/game/objects/items/devices/radio/radio.dm:389-393`). If `data["done"]` is still unset, the radio assumes telecomms failed and broadcasts the message directly as a mundane radio message. So with N hot-mic intercoms hearing one line, the first signal went through telecomms, and the other N-1 were dropped by the dedup check and then re-sent by their radios' backup. Every extra hot-mic radio hearing the same line, and any identical message inside the one-second window, was echoed this way. Each hot-mic intercom retransmitting what it hears is by design and compounds it. The separate duplicate-hearing guard in `atoms_movable.dm` (around line 1047) is not involved.

2. **Late copy of a signal uses a deleted virtualspeaker** (`code/game/machinery/telecomms/broadcasting.dm`, `broadcast()` ending in `QDEL_IN(virt, 5 SECONDS)` at line 230). The virtualspeaker is shared by every copy of a vocal signal, and the first broadcast schedules it for deletion after 5 seconds. A copy that arrives later (the broadcaster delays by traffic, and there may be several broadcasters) calls `compose_message` on a deleting virtualspeaker, which reaches `get_language_holder()` (`code/game/atoms_movable.dm:1460`) and produces the runtime in the report. This was inferred from the code and the stack trace, not observed.

## Fix

One commit, "Fix issue 77437: telecomms rebroadcasting duplicate and late virtualspeaker messages":

- `broadcaster.dm`: `signal.mark_done()` now runs before the `recent_messages` check, so a dropped duplicate still counts as handled and its radio's `backup_transmission()` does not resend it.
- `broadcasting.dm`: `broadcast()` returns early when `QDELETED(virt)`, so no message is composed with a virtualspeaker that is already being deleted.

## Verification

After rebuilding, the same test (three mapped hot-mic intercoms, "mapped test"): `telecomms.log` had 1 line; chat showed "[AI Private] ... says, "Mapped test"" once with no [144.7] duplicates; the runtime log had 0 runtimes.

Not verified: the `QDELETED(virt)` guard (the runtime was never reproduced, so it is hardening based on the code), the reporter's air alarm case specifically, the 2024 custom-frequency intercom map example, and behaviour under real server load.

## Notes

- The air alarm's ~26 repeats are probably the same mechanism: an alarm's `say()` heard by many hot-mic intercoms gives many transmissions. The fix collapses these to one per second, but this was not tested with an air alarm.
- The "unscrew and reattach the intercom fixes it" comment may be a separate, older hearing duplication that is already guarded; that was not investigated.
- Each hot-mic intercom still retransmits what it hears; that design was left alone.
- With the first fix, the dedup check still silences identical messages in the one-second window, as before; only the follow-up rebroadcast is removed.
