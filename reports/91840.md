## Summary

Pressing a bot's "Personality" button starts a timed ghost poll, but in one narrow case a ghost could click the bot during the poll and take it, bypassing the poll. This happens when the personality is turned on, off and on again within the poll: the bot ends up with a `ghost_direct_control` component that never started a poll and so thinks nobody is waiting. The fix makes the component also ask the polling subsystem whether a poll is running for its bot. Separately, repair bots built girders beside space-side windows because the breach check ignored a window that already seals the tile; the check now skips windows that face the tile. The Beepsky-in-a-rolling-chair report is a design question and was not changed.

The fix branch also contains a commit for a different issue (#82859, bots with personality disabled stayed in the spawners menu) that the #91840 repro needed. See Notes.

## #91840: Bot ghost poll can be circumvented by clicking the bot

### The bug

When a bot's personality is enabled, ghosts get a poll like any other midround role. The reporter was able to click the bot during the poll and take it, skipping the roll. They could not reproduce it with a second medbot, and the first instance was an "oppenheimer" bot, so the trigger was unclear. A single enable is correct: clicking during the poll gives "Ghost candidate selection currently in progress!".

### Reproduction

On master, with the Lua editor and an observer ghost:

1. Spawn a medbot (`/mob/living/basic/bot/medbot`).
2. In one script call `enable_possession(nil, false)`, then `disable_possession(nil)`, then `enable_possession(nil, false)`. This stands in for toggling the personality button on, off, on within the 10 second poll.
3. As a ghost, click the bot while the "Looking for candidates" poll alert is still showing.
4. Observed: a "Become the Medibot?" confirmation opened during the live poll. The same click after one plain enable gave "Ghost candidate selection currently in progress!".

This used proc calls instead of the in-game button. The fix described below was tested against the same sequence.

### Cause

`enable_possession` (`code/modules/mob/living/basic/bots/_bots.dm:229`) adds a `ghost_direct_control` component, with `poll_candidates` set only when `offer_ghosts_cooldown` has finished, and then starts a 30 second cooldown. `disable_possession` (`_bots.dm:251`) does not remove the component. So on the second enable:

- the cooldown has not finished, so the new component is created with `poll_candidates = FALSE` and never polls, and its `awaiting_ghosts` stays FALSE (the component is also a replacement for the old one);
- the poll started by the first component is still running (`SSpolling`'s `currently_polling_targets` list, a static local in `poll_ghosts_for_target`, `code/controllers/subsystem/polling.dm:253`, so a second poll for the same target is refused anyway).

`on_ghost_clicked` (`code/datums/components/ghost_direct_control.dm:108`) only checked its own `awaiting_ghosts`, so it let the ghost through to `attempt_possession` while a poll was live.

### Fix

Commit "Fix issue 91840: ghosts can no longer click a bot to skip its running ghost poll":

- `currently_polling_targets` moves from a static variable inside `poll_ghosts_for_target` to a variable on `SSpolling`, and a new proc `is_target_being_polled(checked_target)` reports whether a poll is running for a target.
- `on_ghost_clicked` also refuses with "Ghost candidate selection currently in progress!" when `SSpolling.is_target_being_polled(our_mob)`, and `on_examined` no longer shows "You could take control of this mob by clicking on it" in that case.

Putting the "poll running for this target" state on the subsystem fixes it for any component instance, rather than trying to copy `awaiting_ghosts` between instances.

### Verification

On the test server after rebuilding, with the same on/off/on sequence: the click gave "Ghost candidate selection currently in progress!" and no confirmation opened. After the 10 second poll ended, clicking opened the normal "Become the Medibot?" prompt.

Not checked: pressing the real Personality button through the UI, other bot types, polls started by other users of `ghost_direct_control`, and any behaviour around `on_examined` beyond the code change.

### Notes

- The first attempt at this issue was to see whether the earlier #82859 change alone (removing the component in `disable_possession`) covered it. It does not: with that change alone the same sequence still let the ghost in, because the second enable still creates a component that did not poll. The branch therefore contains the #82859 commit ("Fix issue 82859: bots with personality disabled no longer stay in the spawners menu") first, then the #91840 commit. They are independent in code (`_bots.dm` versus `polling.dm` and `ghost_direct_control.dm`); the #91840 commit applies without it, but the #82859 fix is the cleaner state for the repro. That commit has not been checked against its own issue in this unit.

## #92258: Repair bots dislike space-sided directional windows

### The bug

Repair bots treated tiles next to space-side reinforced windows as hull breaches and built girders over them. The reporter listed #90144 and #88262 as cases seen in rounds.

### Reproduction

Not reproduced with a live repair bot. A setup was prepared (iron floor tiles whose south neighbours are space, reinforced windows facing north placed on those space tiles, a repair bot with all its flags set) but the bot did not act within about two minutes, and bots search only every 5 seconds. The behaviour was therefore checked by calling the targeting check directly (see Verification). Whether the picture in the issue shows windows on the space tile or on the floor tile is unknown: a window on the floor tile makes the tile blocked (`is_blocked_turf`), so the bot already skips it; this was not checked.

### Cause

`valid_wall_target`'s `valid_target` (`code/modules/mob/living/basic/bots/repairbot/repairbot_ai.dm:238`) treats any open turf with an adjacent `isspaceturf` in an `/area/space` as a breach:

```dm
for(var/turf/possible_spaced_turf as anything in adjacent_turfs)
	if(isspaceturf(possible_spaced_turf) && istype(get_area(possible_spaced_turf), /area/space))
		return TRUE
```

A window standing on that space turf and facing the tile already seals that side, but the check does not look at the space turf's contents.

### Fix

Commit "Fix issue 92258: repair bots no longer girder tiles beside a window facing away from space". The loop now skips a space neighbour that holds a `/obj/structure/window` that is `fulltile` or whose `dir` equals `get_dir(space_turf, tile)`. Any other window orientation, or no window, still counts as a breach. (The commit subject says "facing away from space"; the code and its comment treat a window on the void turf facing the tile as the sealing case.)

### Verification

Calling `valid_target` on a `valid_wall_target` node, for a solar panel tile with two space neighbours: with no windows the check returned a breach (1); with windows facing the tile, 0; with windows turned away, 1; with the windows removed, 1. Not checked: a live repair bot over time, fulltile windows, and the exact layout in the issue's picture.

## #81975: Beepsky keeps roaming while buckled to a rolling chair

### Result: reproduced as a design question, no change

The report is that a secbot buckled to an office chair rolls around the station in it. The comment on the issue says "feature". Reading the code: a buckled mob that moves moves the chair (`living.dm` around line 1049), and the bot's AI has no check for being buckled to an object; only its escape-captivity and pacifist subtrees run first. In the test, a secbot buckled to an office chair did not move in about two minutes, but that setup had no navigation beacons for patrolling, so it does not say either way. Whether bots should refuse to move while buckled to a chair is a maintainer decision. No change was made and no branch commit exists for it.
