## Summary

`/obj/item/organ/cyberimp/brain/connector` calls `owner.get_organ_by_type(ORGAN_SLOT_BRAIN)` in two places. `get_organ_by_type` takes a typepath, and `ORGAN_SLOT_BRAIN` is the string `"brain"`, so the lookup always returns null. As a result an EMP never damages the owner's brain or ejects a skillchip, and the "failing implant" branch of its action never pulls the brain. The fix passes `/obj/item/organ/brain`, and also guards the `skillchips[1]` access that the fix makes reachable.

## The bug

The issue (found by Typemaker 2) points at two lines in `augments_internal.dm` and says a string is passed where a typepath is expected. In game this means the connector's EMP penalty ("you either lose a chip or a bit of your brain") never applies. The player sees the "Something falls to the ground from behind ..." message, but nothing falls and the brain is untouched. Likewise, using the implant while it is failing was meant to pull the brain out of the implant; it does nothing.

## Reproduction

On master, using admin tools:

1. Using the Lua editor, spawn a human and insert an `/obj/item/organ/cyberimp/brain/connector` into them.
2. Call `emp_act(2)` on the implant (this calls the proc directly rather than detonating a real EMP).
3. Read the human's brain `damage` and `maxHealth`.

Observed: the "Something falls to the ground from behind ... head" message was shown, but brain damage stayed 0 and `maxHealth` stayed 200.

The `ORGAN_FAILING` branch of `ui_action_click` was not exercised in game.

## Cause

`code/modules/surgery/organs/helpers.dm:7` defines `get_organ_by_type(typepath)`, which looks an organ up by its type. Two callers in `code/modules/surgery/organs/internal/cyberimp/augments_internal.dm` pass a slot string instead:

- Line 265, in `ui_action_click()`: `remove_brain(owner.get_organ_by_type(ORGAN_SLOT_BRAIN))`
- Line 322, in `emp_act()`: `owner.get_organ_by_type(ORGAN_SLOT_BRAIN)`

`ORGAN_SLOT_BRAIN` is `"brain"` (`code/__DEFINES/DNA.dm:90`), which matches no organ type, so both return null. In `emp_act` the null `chippy_brain` makes `skillchip` null (`chippy_brain?.skillchips[1]`), so `remove_brain(null, ...)` runs, and `remove_brain` plays its sound and returns early on a null brain (`if(!chippy_brain) return`). In `ui_action_click` the `remove_brain(null)` call returns nothing, so the "You take ... out of the implant" message never appears. Elsewhere in the same file (line 277 and line 424) the lookup correctly uses `/obj/item/organ/brain`.

## Fix

One commit, "Fix issue 97913: connector implant looked up the brain by slot string instead of typepath":

- Both calls now pass `/obj/item/organ/brain`.
- `chippy_brain?.skillchips[1]` became `LAZYACCESS(chippy_brain?.skillchips, 1)`. Once the brain is found, `skillchips` is a plain list that is null or empty when the brain has no chips, and indexing it with `[1]` would raise a "bad index" runtime. `LAZYACCESS` returns null in that case, so the code falls through to `remove_brain`.

## Verification

On a build with the fix, using the Lua editor and calling `emp_act(2)` on the implant:

- Fresh human, no skillchips: brain damage 20, brain `maxHealth` 185 (one loop, `EMP_LIGHT` handling at the severity used), versus 0 damage and 200 before the fix.
- Second human with one skillchip implanted (`implant_skillchip`): the chip count went from 1 to 0, the chip ended up on the floor, and the brain took no damage.
- No runtimes appeared in the runtime log.

Not checked: the `ORGAN_FAILING` branch of `ui_action_click` (it needs a `do_after`; it is the same one-token change as the EMP path), a real EMP source rather than a direct `emp_act` call, and the higher-severity case with two loops.

## Notes

- Brain damage and maximum health loss now actually happen when a brain connector is hit by an EMP, which is a behavior change players will notice but is what the code was written to do.
- The reported brain values (20 damage, 185 max health) are for the single-loop case used in the test.
