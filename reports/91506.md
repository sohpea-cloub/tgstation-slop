## Summary

`sanitize_name()` HTML-encodes its result, but most of its callers hand it text that `tgui_input_text()` has already encoded. The second pass turned an apostrophe into `&amp;#39` with the semicolon stripped by the name filter, which is what players saw as `&#39`. Three circuit components had the same bug in a different form: they asked `tgui_input_text()` for encoded text and passed it to `say()`, which encodes again. The fix makes `sanitize_name()` decode its input first and asks for raw text in the three circuit components. Names that are encoded only once (chem master containers, airlock names) were deliberately left alone, since that is how the codebase stores player text.

## The bug

Players typing an apostrophe (or `&`, `"`, `<`, `>`) into a naming prompt sometimes got the HTML entity back instead of the character:

- #96192: a ghost taking over a cleanbot and giving it a name with an apostrophe got a name showing `&#39` in place of the apostrophe.
- #75648: a circuit that takes typed text and makes something speak it (a BCI or a keyboard shell feeding a Speech component) spoke `It&#39;s` instead of `It's`.
- #91506: the general complaint, with examples that included chem patch names ("chem's patch" becoming `chem&#39;s patch`). The reporter lists `' " & < >` as the characters affected and says it applies to "anything that can be player named".
- #34366: an old report (2018) that an airlock named "Captain's Quarters" shows `Captain&#39;s Quarters` on mouseover.

## Reproduction

All steps are on master `87b93338` with admin tools.

### Bot rename (#96192, and the same path as #91506)

1. Using the Lua editor, spawn a cleanbot and give it to the admin's client (`PossessByPlayer`).
2. Using SDQL2, run `CALL rename(src) ON /mob/living/basic/bot/cleanbot`. The other clientless bots in the round each raise an "Invalid name" alert for the admin, which have to be dismissed; the prompt for the possessed cleanbot comes up after them.
3. In the "Name change" text prompt, submit `O'Clean`.
4. The bot's `name` and `real_name` ended up as `O&#39Clean` (the SDQL result window showed it this way): the apostrophe became an entity, and the semicolon was gone.

This was done by calling the bot's `rename()` proc through SDQL2 rather than through the bot's own UI button, which calls the same proc (`code/modules/mob/living/basic/bots/_bots.dm:677`).

### Circuit keyboard shell (#75648)

1. Using the Lua editor, spawn a keyboard shell, attach an integrated circuit with an infinite-charge cell to it, add a Speech component, and wire the keyboard's output to the Speech component's message and its signal to the Speech component's trigger.
2. Use the keyboard shell in hand and submit `It's a test`.
3. Chat showed `Keyboard Shell says, "It&#39;s a test"`. For comparison, calling `say("It's plain")` on the shell directly printed `It's plain`.

The thought listener and the admin input request components were not exercised in game; they share the same code pattern (see Cause).

### Airlock and chem master (#34366, #91506)

These were read in code but not run in game (see Cause and Notes).

## Cause

### Names (`sanitize_name`)

`tgui_input_text()` encodes what the player types by default (`code/modules/tgui_input/text.dm`, `encode = TRUE`; the submitted entry goes through `html_encode()`). `sanitize_name()` (`code/__HELPERS/text.dm:25-35`) then runs the name through `reject_bad_name()` and returns `sanitize(result)`, which calls `html_encode()` a second time. In between, `reject_bad_name()` drops characters that are not in its allowed set, and `;` is not in it, so `&#39;` loses its semicolon. The second encode then turns the `&` into `&amp;`, giving `&amp;#39` in the stored name, which displays as `&#39`.

Many callers feed `sanitize_name()` the output of `tgui_input_text()`: bot renames (`_bots.dm:279`), pet, guardian and spirit naming prompts, the magic mirror's Change Name (`code/game/objects/structures/mirror.dm:189`), the wizard rename (`wizard.dm:228`), cyborg rename upgrades, xenobiology renaming, and others. Roughly 25 call sites follow this pattern, by the testers' count. A few other callers pass raw tgui parameters instead (the aquarium, minebot and virtual pet naming read `params["chosen_name"]`); for those, decoding first changes nothing unless the player typed an entity by hand.

### Circuits

`code/modules/wiremod/shell/keyboard.dm:53`, `code/modules/wiremod/components/bci/thought_listener.dm:59` and `code/modules/wiremod/components/admin/input_request.dm:62` call `tgui_input_text()` with the default `encode = TRUE`. The resulting string becomes a circuit port value, and a Speech component hands it to `say()` (`code/modules/wiremod/components/action/speech.dm:37`), which encodes again.

### Names that are encoded once

- Airlocks and windoors: the name comes from the electronics' `passed_name`, which is the raw tgui parameter (`code/game/machinery/doors/airlock_electronics.dm:106-108`). `door_assembly.dm:369` and `windoor_assembly.dm:380` run `sanitize(electronics.passed_name)` once. The result `Captain&#39;s Quarters` is encoded exactly once, which is the codebase's convention: names are stored HTML-encoded and render correctly in chat and examine text. The entity is visible only where the raw `name` is shown without HTML rendering, such as the status-bar mouseover the old report mentions.
- Chem master containers (what #91506 shows as a patch name): `chem_master.dm:523` takes `tgui_input_text()` output (encoded once) and assigns it to `item.name`. The plumbing pill press does `html_encode(params["name"])` (`pill_press.dm:143`), also once. These match the airlock case.

## Fix

One commit, "Fix issue 91506: stop double HTML-encoding player-entered names and circuit text":

- `sanitize_name()` now begins with `target = html_decode(target)`, with a comment explaining why. Already-encoded input is decoded, filtered as plain text by `is_ic_filtered()` and `reject_bad_name()`, and encoded once at the end. Input that was never encoded passes through unchanged. Fixing it here covers every caller at once, rather than editing about 25 call sites.
- The three circuit calls (`keyboard.dm`, `thought_listener.dm`, `input_request.dm`) now pass `encode = FALSE` to `tgui_input_text()`, so circuits receive raw text and `say()` does the encoding. Circuit values stay raw until output, which is also what other string components expect.

The fix does not touch single-encoded names (chem master, pill press, airlock and windoor assemblies). Removing their encoding would let raw player text, including HTML, into the item's `name`, and so into examine text and other places that render names as HTML.

## Verification

On a rebuilt test server:

- Keyboard shell with Speech component: `It's a test` came out as `Keyboard Shell says, "It's a test"` in chat, and the floating text read `It's a test`.
- Cleanbot rename via SDQL2 with `O'Clean`: the bot's `name` was `O&#39;Clean` (11 characters, semicolon kept, so encoded once), `real_name` the same, and it rendered as `O'Clean` in chat.
- Injection checks on `sanitize_name()` called directly: `<b>Bob</b>` returned `BBobb` (angle brackets and slash stripped); `&lt;b&gt;Bob` returned `BBob` (decoded, then filtered the same way); `A &amp; B` was rejected as an invalid name (also the case before the fix); `Plain Name` was unchanged.

Not checked:

- The thought listener and input request components were not run, only changed the same way as the keyboard.
- The other `sanitize_name()` callers (pets, guardians, mirror Change Name, and so on) were not run; they are covered by the one change in the shared helper.
- Callers that run `sanitize()` or `html_encode()` on `tgui_input_text()` output directly, without `sanitize_name()`, were not audited and may still double-encode.
- Players whose client has tgui input turned off take a different branch in `tgui_input_text()` (`stripped_input()`); that path was not tested.
- The chem master and airlock cases were not run in game, and the reporter's screenshots were not available, so whether every example in #91506 is covered is unknown.

## Notes

- **Remaining visible entity.** With the single-encoding convention, a patch named "chem's patch" is stored as `chem&#39;s patch`. Chat and examine render it correctly; anything that shows the raw `name` string without HTML rendering (tgui windows, tooltips, the status bar) still shows the entity. A fix there is a broader decision about where to decode for display, not a one-line change, which is why it was left.
- **#34366** is closed as not a double encode: the airlock name is encoded once, as intended. The status-bar part of the old report depends on how the client shows raw names, which the game cannot change.
- **Decoding trade-off.** `sanitize_name()` now treats a name containing a literal entity such as `&amp;` as the character it stands for. The final output is still encoded and the name filter still runs, so this does not open an injection path; the injection checks above are the evidence.
- **Related earlier report.** #75648 links an older issue, #68274, as related; it was not examined.
