## Summary

A client's parallax background can be left running an endless "travelling" animation after the player's mob changes while the arrivals shuttle is in transit. When `set_parallax_movedir()` is told to stop (direction `NONE`) on its "skip windups" path, it starts a new looping motion-blur animation instead of ending the old one. The direction variable then reads `NONE`, so later updates return early and never stop the loop. The fix cancels the animation on that path. The server-side state was confirmed correct in the broken case, and the buggy code path was seen being reached. The animation itself runs on the client and could not be observed, so the visual result was not verified.

## The bug

The reporter latejoined on Metastation and the stars kept scrolling as if the shuttle were still moving after it had docked. They saw it every time they respawned and latejoined, except when the arrivals shuttle was already docked at the station. Reconnecting fixed it.

## Reproduction

The triggering steps below came from reading the code and were then walked through on the test server. The stuck animation is drawn by the player's client, and the admin tools used cannot show it, so the symptom itself was not seen.

1. Start a round on the test server and latejoin as any job, so the character rides the arrivals shuttle.
2. Use the admin "AGhost" verb to leave the body. About ten seconds later the shuttle departs and the ghost, which stays in the shuttle area, is at the transit z-level (z12 in the test).
3. Use the "Respawn" verb (answering Yes to the admin-override prompt) so the player returns to the lobby (z1).
4. Latejoin again onto the arrivals shuttle once it has docked.

Observations from the test server, taken with a temporary `log_world` line in `set_parallax_movedir()` (removed afterward). This logging was on the same build that contained the fix, so it shows which path was reached but not the animation:

```
new=8 old=0 skip=1 z=12   latejoin into the shuttle in transit (WEST)
new=0 old=8 skip=0 z=12   the shuttle docks: normal stop, handled by the windup path
new=8 old=0 skip=0 z=12   the shuttle departs again
new=0 old=8 skip=1 z=1    ghost in transit -> Respawn -> lobby: the skip-windups stop
```

The last line is the problem case: a stop requested with `skip_windups` set while the old direction was non-zero. On unfixed master this goes through `update_parallax_motionblur()`, which starts a looping animation, per the code reading below. In an earlier round on unmodified master, after respawning and latejoining onto the docked shuttle, the server-side values for the client's parallax were consistent (`parallax_movedir` 0 on both the area and the client's parallax object), which agrees with the defect being only in the client-side animation.

## Cause

`code/_onclick/hud/parallax/parallax.dm:59-100`, `set_parallax_movedir()`:

```dm
if(skip_windups)
	update_parallax_motionblur(layer, new_parallax_movedir, new_transform)
	continue
```

(`:85-87`). `update_parallax_motionblur()` (`:102-112`) runs

```dm
animate(layer, transform = new_transform, time = 0, loop = -1, flags = ANIMATION_END_NOW)
animate(transform = matrix(), time = scaled_time)
```

which is an endless loop. That is right when a direction is being started, but this branch is also taken when `new_parallax_movedir == NONE`. In that case `new_transform` is still computed from the old direction (`animation_dir = new_parallax_movedir || parallax_movedir`, `:63`), so a stop starts a looping animation in the old direction.

`skip_windups` is passed as `quickstart_parallax` from `update_parallax()` (`:123-128`) and is TRUE on the first update or whenever the perspective's z-level differs from the stored `current_turf`. The parallax object is created once per client and survives mob changes, so it keeps the old direction while the player is a ghost riding the shuttle (direction WEST, `8`). A respawn moves the perspective to the lobby on another z-level and calls `set_parallax_movedir(NONE, TRUE)`. That starts the endless animation and sets `parallax_movedir = NONE` (`:99`).

When the player later latejoins onto the docked shuttle, the area's direction is also `NONE`, so `set_parallax_movedir()` returns at `:60-61` (`new_parallax_movedir == parallax_movedir`) and nothing ever stops the loop. This matches the report that the problem appears when the shuttle was in transit and not when it was already docked, and that reconnecting (which creates a fresh parallax object) clears it.

## Fix

One commit, "Fix issue 50676: stopping parallax without windup started a looping animation", adds a stop case to the `skip_windups` branch in `parallax.dm`:

```dm
if(skip_windups)
	if(new_parallax_movedir == NONE)
		// Stopping with no windup: cancel whatever looping animation is running instead of starting a new one
		layer.transform = matrix()
		animate(layer, transform = matrix(), time = 0)
		continue
	update_parallax_motionblur(layer, new_parallax_movedir, new_transform)
	continue
```

Instead of starting a loop, the layer's transform is reset to identity and a zero-time `animate()` on the layer replaces any queued looping animation. Starting a direction with `skip_windups` still uses `update_parallax_motionblur()` as before, and the normal (non-skip) stop path is unchanged. No alternative, such as resetting the parallax object on a mob change, was tried.

## Verification

- After the change the DM build compiled, and the stop-with-skip path (`new=0 old=8 skip=1`) ran once in game on respawn, with no runtime error attributable to it.
- Not checked: whether the stars visibly stop. That needs a real game client, and the tools used here only see server-side values. The intended final check is: ghost on the shuttle in transit, Respawn, wait for the shuttle to dock, latejoin, and confirm the background is still. A pre-fix baseline of the client animation was not seen either.
- Also not checked: whether the zero-time `animate()` cancels a running `loop = -1` animation in BYOND exactly as intended. This rests on how `animate()` replaces earlier animations on an object, and it is the main thing the client check would confirm.
