# #75861: ID trims of jobs removed by the map config get no access

| | |
|---|---|
| Issues | [#75861](https://github.com/tgstation/tgstation/issues/75861): verified (reported runtime already guarded on master; a related defect in the guard was reproduced and fixed) |
| Status | Fixed |
| Fix branch | [fix/75861](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/75861) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary
The issue reported a `Cannot read null.title` runtime in `/datum/id_trim/job/New()` when a map removes a job (both position counts set to 0 in `job_changes`). On master that runtime no longer occurs, because `New()` returns early when the job lookup gives null. That early return skips `refresh_trim_access()`, so the trim of a removed job ends up with empty `access`. The fix calls `refresh_trim_access()` before the early return.

## The bug
Removing a job through the map config means it is not in the job lookup lists, so `SSjob.get_job_type()` returns null for it. The original report was the runtime from the null job. With the guard that now exists, there is no runtime, but the trim of that job is left with no access, so any ID that uses the trim (for example mapped ID cards, or the ID console using it) gets none of the job's access.

## Reproduction
Map job changes are only applied when a real map config is loaded; with the default synthetic config `job_changes` is empty, so this needs a map config in place.

1. Added `"Chaplain": {"spawn_positions": 0, "total_positions": 0}` to `job_changes` in the MetaStation map JSON (a temporary edit) and used that file as the next-map config, then restarted the test server.
2. With the Lua editor, confirmed `SSjob.get_job_type(/datum/job/chaplain)` returned nil (the job is removed by `map_check` in `code/modules/jobs/job_types/_job.dm`).
3. Checked the runtime log: no runtime at boot (0 "runtime error" entries). The `null.title` runtime from the issue does not occur.
4. Read the chaplain trim: `trim.job` was nil, `access` had 0 entries, `minimal_access` had 6. For comparison the cook trim had 6 and 6.

## Cause
`/datum/id_trim/job/New()` (`code/datums/id_trim/jobs.dm:26-31`):

```
if(ispath(job))
	job = SSjob.get_job_type(job)
	if (isnull(job))
		// Not a valid job. Maybe removed by the map.
		return
```

The guard stops the null dereference at `job.title` later in `New()`, but it also skips `refresh_trim_access()`. That proc fills `access` from `minimal_access` and `extra_access`, and every other path in `New()` ends by calling it. A removed-job trim therefore keeps its `minimal_access` but never gets `access`.

## Fix
One commit, "Fix issue 75861: ID trims of jobs removed by the map config get no access". In the null-job branch of `/datum/id_trim/job/New()` it calls `refresh_trim_access()` before returning, with a comment that the trim is still usable (for example by mapped ID cards) and just has no job to take map access changes from. The early return is kept, so map access changes (`additional_access` and so on), which are keyed by job title, are still not applied to a trim without a job.

## Verification
After the change, with the same setup (Chaplain removed through `job_changes`), the chaplain trim had 6 entries in `access` while `get_job_type` still returned nil, and no runtime appeared. The temporary map JSON edit and next-map file were reverted afterwards.

Not checked: using such an ID in a round (opening doors with a mapped card of a removed job), and other removed jobs. Only the trim's access list was read; no player ID was used.

## Notes
- Other code that reads `trim.job` handles nil: the ID access subsystem assigns `job_trim.job` to the account job (`code/controllers/subsystem/networks/id_access.dm:509`) and the RETA system checks `!trim.job` (`code/modules/reta/reta_system.dm:141`). These two sites were read, not exercised.
- The upstream guard that fixed the reported runtime was not identified in the shallow history.
- Whether a removed job's trim should hold access at all is a design question; the fix keeps the previous behavior for non-removed jobs and restores consistency for removed ones.
