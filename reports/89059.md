## Summary

**#89059:** Dried products stay inside the drying rack instead of being ejected. This is explicit code (`AllowDrop()` on the drying smartfridge returns TRUE "to allow drying results to stay inside"), not an accidental regression, and it applies equally to the food dehydrator. No change was made; ejecting would be a design decision.

**#38769:** A glowshroom attached to a mineral rock wall was drawn behind the rock (layer 2.08 against the rock's 4.3), so it was invisible. The fix raises the shroom's layer to `ON_EDGED_TURF_LAYER` (4.35) when the turf it is attached to is a `/turf/closed/mineral`.

## #89059: Drying Racks no longer eject dried plants

### The bug

The reporter says that since the smartfridge UI rework (#85063, which they were not sure was the cause) a drying rack keeps dried plants inside itself, with no feedback that anything happened. Before, dried items were ejected as they finished, and players put a table under the rack to catch them. The reporter notes they like the new behaviour for storage. Another commenter doubted the rack ever ejected; the reporter said it did with the old UI. A maintainer commented that the rack should ideally be redone from scratch because it is a subtype of the smartfridge. The thread does not settle whether the old behaviour is wanted back.

### Reproduction

1. On the test server, using the Lua editor, spawn a `/obj/machinery/smartfridge/drying/rack` on a free tile.
2. Load a `/obj/item/food/grown/grapes` into it with the rack's `load` proc.
3. Call `toggle_drying(FALSE)` on the rack. This was done by calling the procs directly rather than clicking through the rack's UI.
4. Run the SDQL2 query `SELECT /obj/machinery/smartfridge/drying/rack WHERE drying == 1 MAP [contents, loc]`.

Observed: the rack's contents included the dried product (homemade raisins) and `loc` of the product was the rack itself. Nothing was ejected onto the floor. So the reported symptom reproduces.

### Cause

- `code/modules/food_and_drinks/machinery/smartfridge.dm:473`:
  ```dm
  /obj/machinery/smartfridge/drying/AllowDrop()
  	return TRUE // Allow drying results to stay inside
  ```
  With `AllowDrop()` true, `drop_location()` (`code/game/atom/_atom.dm:616`) returns the machine itself rather than its turf.
- The `dryable` element creates the result with `new dry_result(source.loc)` (`code/datums/elements/dryable.dm`, the `finish_drying` code around lines 50 and 56). `source.loc` is the rack, so the dried item is created inside it.
- The rack's `process()` skips items with `TRAIT_DRIED` (`smartfridge.dm:531` accepts only `TRAIT_DRYABLE` items without `TRAIT_DRIED`), so the dried items are not touched again.
- The same applies to the powered food dehydrator, which is the same subtype.
- A stale comment at `smartfridge.dm:494` still mentions "drying pop-out".

### Fix

None. Making the rack eject again would be a design choice that also changes the dehydrator. One option, not implemented: in `dryable` use `source.drop_location()` for the rack subtype only. `AllowDrop()` was added on purpose, so a maintainer should decide first.

### Verification

Reproduced as above. No fix, so nothing to verify. The player-facing UI path was not exercised.

## #38769: Glowshrooms become invisible when attaching to mineable rock

### The bug

The issue has no body; a commenter guessed a layering problem. A glowshroom that spreads onto a wall-mounted position on mineral rock (asteroid or lavaland rock) cannot be seen.

### Reproduction

1. Using the Lua editor, create a `/turf/closed/mineral/random` directly north of a floor tile.
2. Spawn a `/obj/structure/glowshroom` on the floor tile so that it attaches to the rock (`pixel_y` 32, dir NORTH).
3. Render the area: only the floor shrooms were visible and the rock tile showed nothing. The shroom's layer was 2.08.

### Cause

`code/game/objects/effects/glowshroom.dm:12` sets `layer = ABOVE_NORMAL_TURF_LAYER` (2.08) on the game plane. Mineral turfs are on `GAME_PLANE` at `EDGED_TURF_LAYER` (4.3) (`code/game/turfs/closed/minerals.dm:19-20`, `code/__DEFINES/layers.dm:267`) because they are larger than 32x32. The shroom is offset 32px onto the rock tile and so is covered by it. Ordinary walls are on `WALL_PLANE`, below the game plane, so shrooms on them were fine.

### Fix

Commit "Fix issue 38769: glowshrooms attached to mineral rock are drawn behind it". In the `!floor` branch of `Initialize` (`glowshroom.dm`, after the `icon_state` is picked) it adds:

```dm
if(istype(get_step(src, dir), /turf/closed/mineral))
	layer = ON_EDGED_TURF_LAYER
```

`ON_EDGED_TURF_LAYER` is 4.35, just above the rock. Only mineral walls are affected; floor shrooms and shrooms on other walls keep 2.08.

### Verification

After rebuilding, a wall-mounted shroom on mineral rock reported layer 4.35 and floor shrooms stayed at 2.08. A render showed the shroom's light and sprite on the rock tile where nothing had been drawn before. This was a low-resolution render only; a look through a real client was not done.

Not checked: what the layer is after the rock is mined (the shroom may keep the raised layer if it survives).

### Notes

- The raised layer is set only at Initialize, so it is not updated if the adjacent rock is later replaced.
