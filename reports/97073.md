# #97073: MULEbot cannot be turned back on from its UI after a cell swap or drain, and its battery HUD goes stale

## Summary

A MULEbot turns itself off when its cell is removed or runs flat, and the power button in its UI is supposed to turn it back on. The button (`Mule.tsx`) sends the action `on`, but the bot's `ui_act` only handles `power`, so the click does nothing and the bot stays off. The fix changes the button to send `power`, and also fixes the Auto-Return checkbox, which sent a misspelled action. Separately, the bot's diagnostic battery HUD never refreshed after an inducer recharge or after a cell was put back in; the second commit refreshes it in both cases.

## The bug

- #97073: once a MULEbot's cell is removed (or drained), the bot turns off. Putting a charged cell back, even the same one, does not bring it back, and the UI power button has no effect. The reporter had to put down a sentient MULEbot because of it. A commenter said cutting and mending the charge wire after inserting a new cell got a bot working again.
- #95164: recharging a MULEbot with an inducer does not update its diagnostic battery HUD. The issue text only says "same as #93951", so this write-up treats the symptom as the stale diagnostic battery HUD.

## Reproduction

All on master with admin tools (Lua editor, plus possessing a human to use the UI).

### #97073

1. Spawn a MULEbot and unlock it.
2. Move its cell out of the bot and back in (`forceMove`).
3. After the cell was removed, `bot_mode_flags` was `16777198`: the `BOT_MODE_ON` bit was cleared, which is `turn_off()` being called from `Exited()`.
4. After the cell went back in, `has_power()` returned 1 but the bot was still off.
5. As a human possessed by the admin, open the bot's Mule UI and send the UI actions directly. Sending `on`, which is what the shipped button sends, changed no data. Sending `power` changed `powerStatus` from 0 to 1 and the bot's light underlay came back.

The tgui button itself was not clicked: the test client cannot run tgui JavaScript, so the UI actions were sent by hand. What this shows is that the server ignores `on` and accepts `power`; that the button sends `on` was established by reading `Mule.tsx`.

### #95164

No before-fix reading was captured. With the drained cell recharged by a real inducer click, the pre-fix behaviour is known only from reading the code (below). After the fix, see Verification.

## Cause

### #97073

`tgui/packages/tgui/interfaces/Mule.tsx:176` (master):

```tsx
onClick={() => act('on')}
```

The MULEbot's `ui_act` (`code/modules/mob/living/basic/bots/mulebot/mulebot_control.dm:36`) passes unhandled actions to the parent bot's `ui_act`, where the power toggle is `if("power")` at `code/modules/mob/living/basic/bots/_bots.dm:632`. Nothing handles `on`, so the button is dead. Because the bot also turns off whenever the cell leaves (`mulebot_delivery.dm`, `Exited()` calls `turn_off()`), the UI button is the only way back on, and it never works.

The same file has a second mismatch: the Auto-Return checkbox (`Mule.tsx:121`) sent `autored`, while the server handles `autoret` (`mulebot_control.dm:79`).

The commenter's wire workaround appears unrelated to the power state. The investigation concluded it only re-runs the bot AI's check for whether it can run.

### #95164

- `inducer.dm:208` (`interact_with_atom`) only calls `update_appearance()` on the target. The MULEbot never refreshed its `DIAG_BATT_HUD` from `update_appearance()`, so charge added by an inducer was never reflected.
- `Exited()` in `mulebot_delivery.dm` calls `set_cell_hud()`, which sets `hudnobatt` when there is no power. `Entered()` in the same file calls `assign_cell(arrived)` but never `set_cell_hud()`, so the HUD stayed on `hudnobatt` after the cell was put back.

## Fix

Two commits.

1. **Fix issue 97073: MULEbot UI power button sends the wrong action.** In `Mule.tsx` the power button now calls `act('power')` and the Auto-Return checkbox calls `act('autoret')`. Changing the client to match the server was the smaller change, since `power` is the action every other bot UI uses and `_bots.dm` already handles it.
2. **Fix issue 95164: MULEbot charge HUD not updated on recharge or cell swap.** `mulebot.dm` gets an `update_appearance()` override that calls `set_cell_hud()` after the parent, so anything that charges the cell and refreshes the bot's appearance (inducers included) updates the HUD. `mulebot_delivery.dm` `Entered()` now calls `set_cell_hud()` after `assign_cell()`.

## Verification

Checked in game (after rebuilding with the fix):

- Cell out of the MULEbot: `hud_list['10']` (the diagnostic battery HUD) showed `hudnobatt`. Cell back in: `hudbattmax`.
- Draining the cell and recharging it with an inducer by a real click: the HUD went from `hudnobatt` to `hudbattmax`.
- No MULEbot-related runtimes appeared in the runtime log.

Not checked:

- The tgui change was not run. Only the server side was exercised (action `power` works, `on` does not). The `Mule.tsx` edit was confirmed by reading the source and by finding `power` and `autoret` in the built tgui bundle. During the test the client's reported action list for the Mule window still showed `on`/`autored`, which the testers attributed to a stale asset cache; this was not resolved.
- Clicking the real power button and Auto-Return checkbox in a tgui-capable client.
- The reporter's exact situation (a sentient MULEbot) and a bot that ran flat through use rather than by a manual cell removal.
- The pre-fix HUD state after an inducer recharge.

## Notes

- The commenter's cut-and-mend workaround is not explained by this fix beyond the observation above.
- #95164 refers to #93951 for its steps, which was not examined.
- Hooking `update_appearance()` makes the HUD refresh on every appearance update of the bot. It is cheap, but a maintainer might prefer a narrower hook if one is added for cell charge changes.
