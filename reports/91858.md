# #91858: Bluespace launchpad on a shuttle in transit can target turfs outside the shuttle's transit reservation

| | |
|---|---|
| Issues | [#91858](https://github.com/tgstation/tgstation/issues/91858): verified, fixed |
| Status | Fixed on the branch, verified in game (refusal checked; see Verification for limits) |
| Fix branch | [fix/91858](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/91858) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

A bluespace launchpad on a shuttle that is in transit can be aimed far enough to reach turfs of the shared reserved z level that do not belong to the shuttle's own transit reservation. The pad's teleport goes through a reservation check that is meant to stop exactly this, but the check compares the landing turf with itself, so it always passes. The fix makes `teleport_checks()` refuse a target when the pad is on a reserved level and the target turf is missing or in a different reservation than the pad.

## The bug

Shuttles in transit, whiteship and other reserved-space shuttles, and special places such as the bitrunning domain all live on one shared reserved z level, each in its own turf reservation, with empty space between them. The issue reporter described using a launchpad with enough range on a shuttle in transit: items and people were thrown past the edge of the transit area into the space between reservations. Someone without protection can get stuck there and die. Because the level also contains other shuttles' hyperspace and special areas, the reporter noted that the same kind of jump could land someone in places they should not reach (they mention taking a bitrunning avatar to the station this way, by other means, with a fix already up for that specific case).

## Reproduction

Reproduced with admin tools on master. The pad's teleport was triggered with SDQL2 rather than through the launchpad console, so the player-facing console and remote were not exercised.

1. Using the Lua editor, set the mining shuttle's `callTime` to 6000 and `ignitionTime` to 20, then move it with `SSshuttle:moveShuttle("mining", "mining_home", 1)`. After a few seconds the shuttle was in transit (mode `called`) on z 12, which has the reserved-level trait. Its location was in a `/datum/turf_reservation/transit` reservation.
2. On a turf of the shuttle (147,41,12, an iron floor in `/area/shuttle/mining`), spawned a `/obj/machinery/launchpad` and set `range = 100`, `x_offset = 30`, `y_offset = 0`. Next to it, spawned a crowbar to be teleported.
3. Checked the target turf, 30 tiles east (177,41,12): it was `/turf/open/space/basic` in `/area/space`, and `SSmapping.get_reservation_from_turf()` returned nil for it, so it is outside the transit reservation.
4. Using SDQL2, ran `CALL doteleport(null, 1) ON /obj/machinery/launchpad WHERE z == 12` (sending).
5. Selected the crowbar's position with SDQL2 (`SELECT /obj/item/crowbar WHERE z == 12 MAP [x, y, z, loc.type]`).

Evidence: the crowbar ended up at 177,41,12 on `/turf/open/space/basic`, outside the transit reservation. (The admin log lines for both queries were present; the exact result string of the select is not preserved in the notes beyond this position and turf type.)

## Cause

`/obj/machinery/launchpad/proc/doteleport` calls

```
do_teleport(ROI, dest, no_effects = !first, channel = TELEPORT_CHANNEL_BLUESPACE)
```

(`code/game/machinery/launch_pad.dm:268`) with a turf as destination and no precision. `do_teleport` then asks `check_teleport_valid(teleatom, destturf, channel, original_destination = destination)` (`code/datums/helper_datums/teleport.dm:71`).

That proc has a guard meant to stop imprecise teleports from landing outside the destination's reservation (`code/datums/helper_datums/teleport.dm:263-266`):

```
if(is_reserved_level(destination_turf.z) && istype(original_destination) \
    && SSmapping.get_reservation_from_turf(destination_turf) != SSmapping.get_reservation_from_turf(get_turf(original_destination)))
    return FALSE
```

For a launchpad, `destination` and `original_destination` are the same turf, so the two reservation lookups are always equal and the guard never fires. The guard only helps teleporters that pick a random turf near a requested one. Nothing else in the launchpad code validated the target against the pad's own reservation: `teleport_checks()` (`code/game/machinery/launch_pad.dm:160-171`) only checked power/availability, busy state and centcom/supply/transport areas.

## Fix

One commit, "Fix issue 91858: launchpads in reserved space can no longer target outside their own reservation", changes only `code/game/machinery/launch_pad.dm`. At the end of `teleport_checks()` it adds:

```
var/turf/our_turf = get_turf(src)
if(is_reserved_level(our_turf.z))
    var/turf/target = locate(x + x_offset, y + y_offset, z)
    if(isnull(target) || SSmapping.get_reservation_from_turf(target) != SSmapping.get_reservation_from_turf(our_turf))
        return "ERROR: Launchpad not operative. Target is outside the local bluespace stability field."
```

So a pad standing on a reserved z level refuses any target that does not exist or is in a different reservation than the pad. This applies to sending and pulling, and to every caller of `teleport_checks()`: the launchpad control computer and the launchpad remote (`code/game/machinery/launch_pad.dm:383`) and the circuit component (`:509`).

The check was put in `teleport_checks()` rather than in the shared `check_teleport_valid()`, because the shared proc cannot know the intended target for a launchpad (it receives the destination as both values) and changing its semantics would affect all teleporters. Making the pad pass a precision value was not tried.

## Verification

After rebuilding, on a fresh round, the mining shuttle was again sent into transit (z 12) and a launchpad with `range = 100` was placed on it. Calling `teleport_checks()` through the Lua editor returned:

- `x_offset = 30` (target outside the reservation): `"ERROR: Launchpad not operative. Target is outside the local bluespace stability field."`
- `x_offset = 1` (target inside it): `nil`, meaning the teleport is allowed.

No runtimes were seen.

Not checked: the actual teleport after the fix (the refusal was checked by calling `teleport_checks()` directly, not by pressing the button on the console or remote), the pull direction, the circuit component, a pad on the escape shuttle or whiteship, or pads on non-reserved z levels (these skip the new check by construction).

## Notes

- Only launchpads were fixed. Other teleporters that call `do_teleport` with a turf destination and no precision share the same blind spot in the reservation guard; they were not audited.
- Besides the launchpad, the issue's comment about reaching the bitrunning domain involves other teleport methods. Those are partly covered by the existing reservation guard at `teleport.dm:263`; this was not tested.
- The error text is new. A pad in a reservation that legitimately holds a target inside the same reservation (for example, a pad aimed at another part of the same shuttle) still works, as the `x_offset = 1` check showed.
- A broader alternative, as suggested in the issue thread, is a no-teleport flag on the transit area; it was not tried, and the thread notes it could conflict with the escape shuttle's hyperspace.
