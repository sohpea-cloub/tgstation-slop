# #97400: Bileworm devour behavior tree gate does not match what Devour accepts

| | |
|---|---|

| Status | Fix committed; the cause of the mismatch is from reading the code; the fix was only compiled and started on the test server |

## Summary

The issue says the bileworm's devour branch compares the target's stat against a removed `UNCONSCIOUS` define, and that even with that fixed the `mob_stat_at_least` decorator never re-evaluates. On master `87b93338` the first part no longer applies: `bileworm.bt.json` already uses `"min_stat": "SOFT_CRIT"`, and spawning a bileworm produces no runtime. What is still wrong is that the gate lets soft-crit targets through while the Devour ability itself only accepts targets with the knocked-out trait, which soft crit does not have, so a soft-crit target is refused and the worm throws its execution target away. The fix raises the gate to `HARD_CRIT`. A hard-crit target was devoured normally on unmodified master once the execution target was set by hand. Whether the worm reaches the devour branch by itself during a real fight was not observed.

## The bug

The reporter's expectation is that a bileworm that has beaten a player into a critical state burrows to them and eats them. They saw a runtime when a bileworm was spawned, and after changing `UNCONSCIOUS` to `HARD_CRIT` locally saw the worm "continue its same behaviour" while being beaten up, which they took to mean that `mob_stat_at_least` checks the stat only once, on creation.

On master:

- No runtime appeared when spawning a bileworm (the round's runtime log was clean), and `code/modules/mob/living/basic/lavaland/bileworm/bileworm.bt.json` has no reference to `UNCONSCIOUS`. The tree was evidently updated after the report. The earliest commit in the available (shallow) history that contains the `SOFT_CRIT` line is dated 2026-10-06; I could not tell which change introduced it.
- The remaining defect, described below, shows up as soft-crit targets never being eaten and the worm losing its target.

## Reproduction

All steps used the Lua editor and, for state changes, admin tools on the test server. The mobs were spawned on a Lavaland turf, because Devour only works from and to `/turf/open/misc`.

### Hard crit (works on unmodified master)

1. Start a round, observe, and open the Lua editor. Spawn a `/mob/living/basic/mining/bileworm` and a human on Lavaland (the Labor Camp level).
2. Let the human go into hard crit (stat 2) by suffocation (no air there); this keeps the human in hard crit without further input. The human was kept alive by periodically healing oxygen damage from Lua.
3. Check that the human has the knocked-out trait: it did (`_status_traits['knockedout']` was present at stat 2).
4. With the worm's AI on and the human as its current target, set the worm's `BB_basic_execution_target` blackboard key to the human from Lua.
5. Observed: about eight seconds later the chat showed "You are consumed by the bileworm!" So the devour branch, `mob_stat_at_least` and the `and_clear_target` behavior worked for a hard-crit target.

### What was not reproduced

- The worm never set `BB_basic_execution_target` by itself in the few minutes it was watched; that key is set only at the end of an `and_plan_execute` action (`code/datums/ai/basic_mobs/basic_ai_behaviors/targeted_mob_ability.dm:45-47`), that is after the worm resurfaces or spews bile at its current target. Why that did not happen during the observation window is unexplained. This is why the target was set by hand in step 4 and why the reporter's exact scenario (worm beats a player down, then devours) was not played through.
- The soft-crit refusal ("No way you're eating that while it's still kicking!") was not seen in game. An attempt to hold a human at soft crit failed because the test human dropped into hard crit from suffocation before Devour was off cooldown. The mismatch is established by reading the code (next section).
- The claim that the decorator only evaluates the stat once was not tested. Specifically, whether a stat change while the worm is already working through a lower-priority plan aborts that plan was not exercised.

## Cause

The devour branch in `bileworm.bt.json` (lines 20-45) is an `ability_available` decorator on `BB_BILEWORM_DEVOUR`, wrapping a `mob_stat_at_least` decorator on `BB_BASIC_MOB_EXECUTION_TARGET`, wrapping the `targeted_mob_ability/and_clear_target` leaf:

```json
"decorator": "/datum/bt_node/decorator/mob_stat_at_least",
"vars": {
	"observer_abort": "BT_ABORT_LOWER_PRIORITY",
	"invert": false,
	"key": "BB_BASIC_MOB_EXECUTION_TARGET",
	"min_stat": "SOFT_CRIT"
},
```

`SOFT_CRIT` is 1 (`code/__DEFINES/stat.dm`: `STABLE` 0, `SOFT_CRIT` 1, `HARD_CRIT` 2, `DEAD` 3), so the gate passes for any target in soft crit, hard crit or dead.

The ability it then triggers, `/datum/action/cooldown/mob_cooldown/devour/Activate()` (`code/modules/mob/living/basic/lavaland/bileworm/bileworm_actions.dm:270-281`), starts with:

```dm
if(!IS_UNCONSCIOUS(living_target))
	to_chat(owner, span_warning("No way you're eating that while it's still kicking! It should at least be unconscious first."))
	return
```

`IS_UNCONSCIOUS()` is `HAS_TRAIT(mob, TRAIT_KNOCKEDOUT)` (`code/__DEFINES/mobs.dm:1122`). In `code/modules/mob/living/living.dm` (around lines 2535-2565) soft crit adds `TRAIT_FLOORED`, `TRAIT_HANDS_BLOCKED`, `TRAIT_INCAPACITATED` and `TRAIT_FORCE_WHISPER`, and only hard crit (and death) add `TRAIT_KNOCKEDOUT`. So a soft-crit target passes the tree's gate but fails `Activate()`. Because the leaf is `and_clear_target` (`targeted_mob_ability.dm:49-53`), `finish_action()` clears `BB_BASIC_MOB_EXECUTION_TARGET` regardless of the outcome, and the worm forgets the target.

## Fix

One commit on `fix/97400`: **"Fix issue 97400: bileworm devour BT gate requires hard crit, matching Activate's knocked-out check"**.

- `bileworm.bt.json`: `"min_stat": "SOFT_CRIT"` becomes `"min_stat": "HARD_CRIT"`.
- `build/behavior_trees/.../bileworm.bt.compiled.json`: the compiled tree, which is tracked in the repository, with `min_stat` 2 instead of 1 (one-line change).

This makes the gate as strict as `Activate()`, so the worm does not spend its execution target on a refusal. Because the decorator uses `BT_ABORT_LOWER_PRIORITY` and listens for `COMSIG_MOB_STATCHANGE` on the target (`code/datums/ai/generic_decorators/mob_stat_at_least.dm`), the devour branch should be picked up once the target's stat later reaches hard crit; I did not test that.

Alternative: change `Activate()` to accept `IS_UNCONSCIOUS_OR_CRIT()` so that soft-crit targets can be eaten. That changes the ability (its description says the target "must be unconscious") rather than the AI, so it was not done.

## Verification

- The bileworm tree was rebuilt (0 errors, 0 warnings), the compiled JSON in the working tree showed `min_stat` 2, and the server started with the change.
- Not checked in game after the fix: no worm was spawned on the fixed build, so there was no hard-crit or soft-crit devour test with the new gate, and no check that a soft-crit target is left alone.
- Hard-crit devour had been observed before the fix (see Reproduction), so the change is expected to keep that behavior, but that was not re-run.
- Not checked at any point: the full natural sequence (worm resurfaces, spews bile, sets its execution target, target drops into crit, worm devours), and the decorator re-evaluating on a stat change.

## Notes

- The reporter's second claim (the decorator "never updates") is neither confirmed nor refuted. What was seen is consistent with the decorator working when the target is already in hard crit at the time the key is set.
- Open question for maintainers: whether soft-crit targets should be edible. The gate and `Activate()` should agree either way; this fix picks the stricter reading to match the ability's text.
- The reproduction needed the execution target set manually, so the unexplained absence of an automatic execution target in a few minutes of watching might be a separate problem or a setup artifact (for example the worm's AI turning itself off when no player is nearby; it had to be switched on from Lua during testing). It was not investigated further.
- During testing, the server crashed once in the Lua editor (`lua_state.dm:97`, `load_script`) on a script that called `death()` on many mobs from Lua and passed a Lua table to `add_traits`. It was not investigated; it is mentioned only in case it is a known Lua-wrapper issue.
