# #67229: Randomizing a character for an antagonist overwrites the player's saved character

| | |
|---|---|
| Issues | [#67229](https://github.com/tgstation/tgstation/issues/67229): verified, fixed. [#85636](https://github.com/tgstation/tgstation/issues/85636): duplicate of #67229, fixed by the same change. [#62011](https://github.com/tgstation/tgstation/issues/62011): same cause, verified, fixed by the same change (the original 2021 trigger could not be reproduced on current code, see below) |
| Status | Fixed; checked in game on the test server |
| Fix branch | [fix/67229](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/67229) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The "random name / random body" preferences, when set to "only when antagonist" (or "always"), randomize the character by calling `write_preference`. That writes the random values into the player's real preferences and savefile, and nothing puts the originals back, so the random name and body are kept for every later round. The fix makes `apply_character_randomization_prefs` return the values it replaced and restores them as soon as the character has been applied to the mob (or the ghost appearance has been read). It also restores the species-randomization toggle that humans-only jobs switch off. The antagonist still spawns with a random character; the saved character is untouched. A unit test covers it.

## The bug

A player with "random name" and "random body" set to antagonist-only gets a random character when they roll an antagonist role. The reports describe what happens next: in the following rounds the player keeps the random name (#67229, #85636), and their saved slot looks like the random roll. A comment on #67229 adds that other randomized things (species, body) are affected too, and #62011 describes a saved slot being replaced by a completely random character after accepting a CentCom intern ghost poll. A comment on #85636 says this was thought to be intended; the code shows nothing that restores the character, so it is a bug.

What is happening: the randomized values become the player's actual preference values, and the next time preferences are saved (closing the character setup, or any `save_character` / `save_preferences` call) they are written to disk.

## Reproduction

All steps were done on the test server with admin tools. The roundstart flow itself was not run (it needs the player's mind to be in `GLOB.pre_setup_antags`, and the test character was an observer with no mind); instead the Lua editor was used to call `safe_transfer_prefs_to(mob, TRUE, TRUE)`, which is exactly what `code/modules/jobs/job_types/_job.dm:586` calls for a roundstart antagonist.

1. Start the test server, start the round, and observe. Open the Lua editor.
2. In Lua, take the observer's client prefs and note the saved `real_name` ("Donald Carr") and `hair_color` (`#412922`).
3. Set `random_name` and `random_body` to antagonist-only (`1`, `RANDOM_ANTAG_ONLY`) with `write_preference`.
4. Spawn a human and call `prefs:safe_transfer_prefs_to(human, TRUE, TRUE)`.
5. Read the prefs again, then call `save_character()` and `save_preferences()`, and look at the player's `preferences.json`.

Observed on master:

- The spawned human was "Jalen Mcmullen", and the prefs' `real_name` had changed from "Donald Carr" to "Jalen Mcmullen" as well.
- `hair_color` had changed from `#412922` to `#fff2d6`.
- After saving, `preferences.json` on disk contained `"real_name": "Jalen Mcmullen"`.
- In the next round on the same server, the observer/body of that player was named "Jalen Mcmullen".

Whether the "random name only" setting works on its own is a separate question, see Notes.

## Cause

`apply_character_randomization_prefs` (`code/modules/mob/dead/new_player/preferences_setup.dm:14`) loops over the preferences and, for each one that `should_randomize` selects, does

```dm
write_preference(preference, preference.create_random_value(src))
```

(line 25). `write_preference` (`code/modules/client/preferences/_preference.dm:288`) writes the value into the savefile tree and into `value_cache`, so it replaces the player's real preference. This is the right call for the "Randomize" buttons in the character setup, but it is wrong for a temporary randomization.

The callers treat the call as temporary. `safe_transfer_prefs_to` (`code/modules/client/preferences.dm:514`) runs the randomization and then applies the preferences to the mob; it never restores anything. It is used by roundstart antagonists (`_job.dm:586`), ERT and the CentCom intern (`code/modules/admin/verbs/ert.dm:174,231`, the path from #62011), antagonist spawners and nuclear operatives (`code/modules/antagonists/_common/antag_spawner.dm`, `nukeop/datums/operative_team.dm:198`), and others. `set_ghost_appearance` (`code/modules/mob/dead/observer/observer.dm:833`) calls `apply_character_randomization_prefs()` too, for players whose prefs say "always random". The next save, such as closing the character setup, persists the randomized values.

A second, related problem is at `code/modules/jobs/job_types/_job.dm:585`: for jobs that require a human, `player_client.prefs.randomise["species"] = FALSE` is set so the species is not randomized for that spawn, but is never put back. Because `randomise` is saved with the character, the player's own species randomization setting was turned off permanently.

For #62011: the ERT/intern path is `safe_transfer_prefs_to(..., is_antag = TRUE)`. On current code it only randomizes when the player has `random_body` set to something other than disabled, and then it wrote the result over the slot, same as above. The default value of `random_body` is disabled, which returns early, so the exact situation in the 2021 report (no random preference set) does not reproduce on current master; it may have been caused by different code at the time.

## Fix

One commit on the fix branch: "Fix issue 67229: randomizing a character for an antagonist no longer overwrites the saved character".

- `apply_character_randomization_prefs` now builds and returns an associative list of preference type to the value the preference had before it was randomized (an empty list if nothing was randomized).
- A new proc `restore_character_randomization(original_values)` writes those values back, in the order they were stored. That order is the priority order of the preferences, so the species is restored before the things that depend on it.
- `safe_transfer_prefs_to` keeps the returned list, applies the preferences to the mob, then restores.
- `set_ghost_appearance` does the same: randomize, read the appearance values, restore.
- `_job.dm` remembers the original `randomise["species"]` and puts it back (or removes the key if it did not exist) after the transfer when it had been forced off for a humans-only job.
- Unit test `preferences_randomization_not_persisted` (`code/modules/unit_tests/preferences.dm`): sets a name, sets random name/body to antagonist-only, checks that a non-antagonist transfer keeps the name, that an antagonist transfer changes the mob's name, and that the saved name, hair color and species are unchanged afterwards.

The approach was chosen to keep every caller unchanged and the diff small. The alternative suggested in a comment on #62011, a separate temporary preferences datum whose savefile code does nothing, would be a larger change touching how preferences are created and read. The restore approach still mutates the real preferences for the duration of the call.

## Verification

On the test server after rebuilding with the fix:

- With saved name "Baseline Bob", hair `#fff2d6`, and random name/body at antagonist-only: a spawn with `is_antag = TRUE` produced a human named "Esther Stroh" with hair `#41250c` (randomization still works). A spawn with `is_antag = FALSE` was named "Baseline Bob".
- Afterwards the prefs still read `real_name` "Baseline Bob", `hair_color` `#fff2d6`, and species human. After saving, `preferences.json` was byte-identical (checked with `diff`) to a copy taken before the test.
- Ghost path: with `random_body` set to always and hair color randomization enabled, `set_ghost_appearance` gave the ghost hair `#a87f5c` while the stored preference stayed `#fff2d6`.
- No runtimes in the round's runtime log.
- The unit test was added and the `dm-test` build was reported as passing ("Success!").

Not checked: the full roundstart antagonist assignment flow (only the transfer proc it calls was exercised), the other `safe_transfer_prefs_to` callers individually (ERT, intern poll, nuclear operatives, antagonist spawners) beyond the shared proc, the `_job.dm` species restore in a real job spawn, and the real character setup UI after the fix.

## Notes

- Hardcore random (mentioned in a comment on #67229) has the same kind of problem on a different path: `select_hardcore_quirks` (`preferences_setup.dm`, called from `code/controllers/subsystem/ticker.dm:531`) replaces `prefs.all_quirks` with a random list, and `save_character` writes `all_quirks`. This was not touched and is a candidate for a follow-up.
- Possible separate bug, not verified in game and not changed: `apply_character_randomization_prefs` returns early when `random_body` is disabled, so "random name when antagonist" on its own, with random body disabled, would never randomize the name.
- Because the fix restores after the fact, a runtime inside `apply_prefs_to` between randomize and restore would still leave the randomized values in place until the next preference change.
