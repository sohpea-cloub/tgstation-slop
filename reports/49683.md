## Summary

Three table-related issues were worked together. #49683 (non-metal sheets making a metal table on a metal frame) no longer happens on master: every sheet with a material gives a greyscale table of that material, and sheets without a material give no table. #97181 was reproduced: a mob with `incorporeal_move` set shattered glass tables by walking over them; `check_break` now returns early for such mobs. #85602 was a map data problem: machines with a tabletop offset had map-edited `pixel_y` values that now stack on top of the new `pixel_z` offset; about 200 of those edits were removed across 59 map files.

## #49683: non-metal sheets on a metal table frame

### The bug

The issue (2020) reported that using reinforced glass, cardboard, wood, sandstone or bone on a metal table frame produced an ordinary metal table. A 2023 comment said most were fixed but some sheet types still produced a white table with the description "A square piece of nothing on four legs", and that some carpets had no table variant of their own.

### Reproduction

Not reproduced on master. Using the Lua editor on the test server, `get_table_type()` and `material_type` were read from spawned stacks:

- cardboard, wood, sandstone, bone, gold, plastic, paper frames, uranium and hot ice returned `/obj/structure/table/greyscale`, with the stack's own material as the table material;
- reinforced glass returned `/obj/structure/table/reinforced/rglass`, glass returned `/obj/structure/table/glass`, iron returned `/obj/structure/table`, carpet returned `/obj/structure/table/wood/fancy`;
- cloth, leather and rods (stacks with no material and no greyscale table) returned null, so no table.

### Cause (of the old behaviour) and why it is already fixed

`code/game/objects/items/stacks/stack.dm:262` (`/obj/item/stack/proc/get_table_type()`) returns null for a stack whose `table_type` is `/obj/structure/table/greyscale` but whose `material_type` is null ("This table type breaks without a material type"). `/obj/item/stack/sheet` sets `table_type = /obj/structure/table/greyscale` (`code/game/objects/items/stacks/sheets/sheets.dm:17`), so material sheets get a greyscale table. The frame calls this through `/obj/structure/table_frame/proc/get_table_type` (`code/game/objects/structures/table_frames.dm:94`), and `item_interaction` (line 54) returns without doing anything when the result is null (lines 58-59). The screentip at line 38 uses the same check. So nothing generic or metal is produced any more, and the "table out of nothing" complaint from the 2023 comment is covered by the null check.

### Fix

None; no code change.

### Verification

Only the proc results above were checked. A table was not built through a real frame in game (the `do_after` in `item_interaction` was not exercised); `get_table_type` is what the frame calls.

### Notes

The missing sprites for some carpet variants noted in the issue are an art question, not a code defect.

## #97181: incorporeal mobs shatter glass tables

### The bug

With `incorporeal_move` set to 1 through View Variables (as an admin or ghost-like mob), floating over a glass table shattered it and hurt the mob with the shards. The issue comments agree that intangible mobs should not break tables.

### Reproduction

1. On the Meta Station map, using the Lua editor, spawn two humans and pick two glass tables (the test used two adjacent ones).
2. Set `incorporeal_move = 1` on one human and move it onto one table with `forceMove`; move the other (normal) human onto the second table the same way.
3. Observed on master: "The glass table breaks!" appeared twice, both tables broke and both humans were hit by shards.

This was reproduced by moving mobs with `forceMove` from a script, not by a player walking.

### Cause

`/obj/structure/table/glass/proc/check_break` (`code/game/objects/structures/tables_racks.dm:569`) only skips the break when the mob has no gravity, is small, or has a movement type in `MOVETYPES_NOT_TOUCHING_GROUND`:

```dm
if(M.has_gravity() && M.mob_size > MOB_SIZE_SMALL && !(M.movement_type & MOVETYPES_NOT_TOUCHING_GROUND))
	table_shatter(M)
```

`incorporeal_move` (`code/modules/mob/living/living_defines.dm:99`) is a separate variable and does not set `movement_type`, so an incorporeal mob counts as a heavy mob on the ground.

### Fix

Commit "Fix issue 97181: incorporeal mobs no longer shatter glass tables" adds an early return to `check_break`:

```dm
if(M.incorporeal_move) // intangible mobs don't touch the table
	return FALSE
```

### Verification

After rebuilding, the same script was run again. Only the normal human's table broke ("The glass table breaks!" once, that human hit by the shards); the table under the incorporeal human survived.

Not checked: other table types, thrown or flying incorporeal mobs, and walking onto the table with real movement input rather than `forceMove`.

### Notes

The issue also mentions that an incorporeal mob falls through open space. That was not changed; the reporter said it may be intended.

## #85602: tabletop offset applied twice

### The bug

Machines that sit on tables (microwaves, grinders, processors, coffee makers and others) are raised by `anchored_tabletop_offset`. Many map files also carry a hand-edited `pixel_y` on those machines to raise them. Since #85372 the offset is applied to `pixel_z`, so the two now add up and the machine floats too high. The issue asks for a map lint forbidding `pixel_y` on such machines when they share a tile with a table.

### Reproduction

A scan of the map files found about 200 map entries of this kind: microwave (65 entries), reagent grinder (73), food processor, coffee maker, drinks dispenser, fax, mini fridge, library console and others, each on a tile that also holds a table. The visible double offset was not checked in game before the fix.

### Cause

`/obj/proc/check_on_table` (`code/game/objects/objs.dm:323`) sets `pixel_z = anchored_tabletop_offset` when the object is anchored on a tile with a table (called from `Initialize` at line 65 and from `set_anchored`). Before #85372 the offset was written to `pixel_y`, which overwrote the mapped `pixel_y`. Now `pixel_z` is used, so the mapped `pixel_y` survives and is added.

### Fix

Commit "Fix issue 85602: remove map pixel_y edits from machines that get a tabletop offset" removed the `pixel_y` variable (and only that variable; `pixel_x`, `dir`, `desc` and so on were kept) from these types when the same tile also held an `/obj/structure/table`: tipjar, mini fridge, secure safe (caps spare), bedsheet bin, small vatgrower, reagent grinder, library console, drinks chem dispenser, fax, gibber, microwave, coffee maker and food processor. This was done with a one-off script: 199 entries in 59 `.dmm` files (the whole branch diff is 186 insertions and 477 deletions, including the small #97181 change). It restores the effective pre-#85372 positions, since `pixel_y` was overwritten before. A tile containing a table frame also counted as a table in the script; the effect of that was judged negligible.

### Verification

The tree rebuilt (the edited maps compile), the server booted and a round ran. With SDQL2, `SELECT /obj/machinery/microwave WHERE pixel_y != 0` returned 0 of 23 microwaves on the round's map.

Not checked: before/after screenshots or offsets in game, and maps other than the one the test round used.

### Notes

- The map lint the issue asks for was not written, so new map edits can reintroduce the problem.
- The diff is large (59 map files) and touches many unrelated maps, so a maintainer may prefer to land it separately from the #97181 change.
- `pixel_y` edits on a machine on a rack or not anchored were not touched beyond the same-tile table rule.
