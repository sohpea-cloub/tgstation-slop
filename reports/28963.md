## Summary

The 2017 report said that a large grenade casing holding one beaker of plasma and two grey slime extracts produced one slime and one leftover extract, because the beaker's contents were not shared out between the extracts. This does not happen on current master. A large casing now refuses a third container, extracts included, so the "beaker plus several cores" setup cannot be built by hand. When the setup was forced with the Lua editor, the beaker's plasma was split between both extracts by free volume and each one produced a slime. No fix was written because none is needed.

## The bug

As originally reported (2017): put a beaker of plasma in a large grenade casing together with two grey slime extracts and set it off. The reporter expected two baby slimes and got one slime and one unused extract. Comments in the thread added that:

- slime extracts could be added to a large grenade without limit once the two beakers were in (the casing limits containers to two, but extracts were not being counted),
- an extract with several uses only reacts once per detonation, and
- one comment from 2023 says the described behaviour was no longer reproducible, probably because of #63393.

## Reproduction

I could not reproduce it. The checks run on master, using admin tools to spawn the parts:

1. Started a round and joined as a Scientist. Using the Lua editor, spawned a large grenade casing (`/obj/item/grenade/chem_grenade/large`), a beaker holding 10u plasma, two grey slime extracts (`/obj/item/slime_extract/grey`), a cable coil and a screwdriver on the same tile.
2. Built the grenade by hand, using each item on the casing in turn:
   - cable coil: "You rig the large grenade assembly."
   - beaker: "You add the beaker to the large grenade assembly."
   - first grey extract: "You add the grey slime extract to the large grenade assembly."
   - second grey extract: refused with "The unsecured large grenade can not hold more containers!"
3. Dropped the refused extract, locked the casing with the screwdriver ("You lock the large grenade assembly") and primed it. The grenade was primed by hand ("You prime the large grenade! 5 seconds!") and detonated when the timer ran out; no igniter assembly was attached. Result: "The solution begins to bubble", "Infused with plasma, the core begins to quiver and grow, and a new baby slime emerges from it!", one new baby slime (the living slime count went from 3 to 4), the used extract was gone, and the beaker was empty (0u). The only extract left on the tile was the second one that had been refused.
4. Since the hand-built setup can't hold the beaker plus two extracts, I forced it to test the splitting logic. Using the Lua editor I created a second large casing and put a 10u plasma beaker and two grey extracts directly inside it. I then added all three objects to the casing's `beakers` list, set `stage` to 3 (ready) and called `detonate()`. Before the forced detonation the contents were beaker 10/50u, extract 0/100u, extract 0/100u. Afterwards the living slime count went from 3 to 5, two of the slimes stood next to the grenade, the chat showed the "solution begins to bubble" and "new baby slime emerges" messages three times in total across both detonations, both extracts were consumed and the beaker was empty (0u).

The forced run called `detonate()` directly rather than priming the grenade, because the setup cannot be assembled by a player. One Lua error occurred during the test (a call to a nonexistent `add` method on a DM list); it was a mistake in my script, not a game runtime, and the runtime log showed no other errors involving grenades or slimes.

Not tested: extracts with more than one use, other extract types, and larger or uneven volumes.

## Cause

There is no active defect for the reported symptom. The relevant code on master:

- `code/game/objects/items/grenades/chem_grenade.dm:13`: `var/list/obj/item/beakers = list()` is an untyped item list. Extracts are accepted into it, so they count toward the container limit. (The 2023 comment blamed a `/obj/item/reagent_containers/cup`-typed list that excluded cores; that is no longer the case.)
- `chem_grenade.dm:213`: `if (length(beakers) == 2)` refuses a third container with "can not hold more containers!". The large casing allows `/obj/item/slime_extract` as a container (`:296`), so an extract takes up one of the two slots. A beaker plus two extracts, or any number of extracts beyond the second slot, can't be built.
- `chem_grenade.dm:303-351`, `/obj/item/grenade/chem_grenade/large/detonate()`: this is the splitting the issue asked for. It sums the reagents in the non-extract containers (`beaker_total_volume`) and the free space in all extracts that still have uses (`available_extract_volume`). It pours the beakers' contents into a temporary holder, then gives each extract a share of `beaker_total_volume * (available_volume / available_extract_volume)` and calls `handle_reactions()` on that extract. If an extract is destroyed by its reaction it is dropped from `beakers`.
- `code/modules/reagents/chemistry/recipes/slime_extracts.dm:28-35`: the grey slime reaction needs 1u plasma in a grey extract and spawns a baby slime. When the extract has no uses left it deletes itself (`delete_extract`, `:22-25`).

With one 10u beaker and two empty grey extracts (100u capacity each), each extract gets 5u plasma, enough for one slime each. This matches the forced test result.

## Fix

None. Nothing was changed.

## Verification

Nothing to verify after a fix. What was observed on unmodified master is described under Reproduction. Not checked:

- a three-way split (beaker plus several extracts) via a real player-built grenade, which is impossible with the container limit;
- the remaining remark from the thread that multi-use extracts only react once per detonation. By reading the code (`chem_grenade.dm:346`) each extract has `handle_reactions()` called once per detonation, so an extract with several uses would still spend only one use, but this was not tested in game.

## Notes

- This looks like #63393 (named in the issue's last comment as the likely fix) or a later change. I did not check the history to confirm which change fixed it.
- The issue could probably be closed. The one open design point from the thread, multi-use extracts reacting once per detonation, is a separate behaviour and not a reagent-splitting bug.
- The 2017 discussion also proposed letting slime cores bypass the two-container limit as a feature (boobytrapped grenades, mass reactions). Master now enforces the limit, so that use is no longer possible.
