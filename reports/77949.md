## Summary

The meat hook (`/obj/item/gun/magic/hook`) carries the `NOBLUDGEON` item flag, which makes the generic melee code return before doing anything. When the hook cannot fire (here: its charge is spent), a combat-mode click on an adjacent mob is handed to the melee code, which then does nothing, despite the hook's `force = 18`. The fix removes `NOBLUDGEON` from the hook. #91942 (an ID card destroyed with a burned PDA) did not happen on master: the card is dropped on the floor.

## #77949: meat hook does no melee damage

### The bug

The issue says the hook cannot attack people at point-blank range even though it has high brute force and can be sharpened. In practice a player with an empty (recharging) hook in combat mode clicks an adjacent person and nothing happens: no attack message, no damage.

### Reproduction

On master, using the Lua editor as an admin observer:

1. Spawn two humans next to each other, A and B.
2. Give A a `/obj/item/gun/magic/hook`, turn on A's combat mode, and set the hook's `charges` to 0 so it cannot fire.
3. Make A click B (`A:ClickOn(B)`).

Observed: B's brute damage stayed at 0 and no attack message appeared.

The click was issued from admin tools on the spawned humans rather than by a player at a keyboard.

### Cause

`code/modules/projectiles/guns/special/meat_hook.dm:17` sets `item_flags = NEEDS_PERMIT | NOBLUDGEON`. `NOBLUDGEON` makes both `/obj/item/proc/attack` and `/obj/item/proc/attack_atom` return early (`code/_onclick/item_attack.dm:234` and `:286`):

```dm
if(item_flags & NOBLUDGEON)
	return FALSE
```

In `gun.dm` an unfireable gun in combat mode returns `ITEM_INTERACT_SKIP_TO_ATTACK` (for example `return user.combat_mode ? ITEM_INTERACT_SKIP_TO_ATTACK : ITEM_INTERACT_BLOCKING` at `code/modules/projectiles/gun.dm:422`), which hands the click to the melee code. For the hook that code then bails out on `NOBLUDGEON`, so the click is swallowed.

### Fix

One commit, "Fix issue 77949: meat hook can melee when it can't fire", changes the hook's flags to `item_flags = NEEDS_PERMIT`. The hook then behaves like other guns: a loaded hook still fires point blank at an adjacent mob, and an unloaded one bashes in combat mode. The flag is the whole cause, so no other change was needed.

### Verification

On the test server with the fix, repeating the reproduction (hook with 0 charges, combat mode, A clicks adjacent B) produced the message "X attacks Y in the chest with the meat hook!", a hit sound and damage. A loaded hook clicked on an adjacent mob still produced "fires the meat hook point blank" and snagged the target, as before the change.

Not checked: the exact damage value against armor, a player actually clicking in combat (the click was issued via admin tools), and other firing paths such as the hook fired at range.

### Notes

- Side effect to review: the flag also blocked bashing objects, so a loaded hook clicked on a non-mob adjacent target now bashes it with force 18 instead of doing nothing. This is how most guns behave, but a maintainer may want to keep the hook from bashing objects, which would need a different approach than dropping the flag.
- The issue also mentions sharpening; that was not tested.

## #91942: ID card inside a burned PDA

### The report

An ID card stored in a PDA is said to be destroyed when the PDA burns on a bonfire, while a lone ID card is fire-immune.

### Attempt to reproduce

On master, using the Lua editor: a PDA with an ID card named TESTID inserted was put on a lit bonfire and left for 20 seconds until "The pda breaks apart!"; separately, a PDA with an ID card was burned by calling its `burn()` directly. In both cases the ID card was left on the turf, along with the PDA's power cell.

### Cause of the observed (correct) behavior

Destroying a burned PDA goes through `deconstruct`, and `atom_deconstruct` (`code/modules/modular_computers/computers/item/computer.dm:1036`) moves the stored ID, alternate stored ID and inserted disk to the drop location. `Exited()` (`computer.dm:540-555`) clears the corresponding variables, so the `QDEL_NULL(stored_id)` in `Destroy()` (`computer.dm:202`) finds nothing to delete.

### Verdict

Not reproduced; no fix. It is likely already fixed since the 2025 report, but the version that changed this was not identified.

Not checked: acid melting (it takes the same deconstruct path, but was not run). Related but outside this issue: the PDA's inserted pen is still deleted together with the PDA (`code/modules/modular_computers/computers/item/pda.dm:66`, `QDEL_NULL(inserted_item)`). No runtimes appeared in these tests.
