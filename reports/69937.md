# #69937: Loading a saved BCI circuit leaves the shell's default circuit and a stale action button behind

| | |
|---|---|
| Issues | [#69937](https://github.com/tgstation/tgstation/issues/69937): verified (duplicate stale action reproduced; the click runtime was not) |
| Status | Fixed on a branch; fix verified in game |
| Fix branch | [fix/69937](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/69937) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Loading a saved circuit that belongs to a shell such as a brain-computer interface (BCI) built the shell with its default circuit and then attached the loaded circuit on top, without removing the default one. The default circuit stayed registered with the shell and kept its granted action button, so the implanted user got a duplicate "Action" button that did not go away when the circuit was removed. The fix removes and deletes the shell's existing circuit in `on_load` before attaching the loaded one. The runtime the reporter saw when clicking the buttons was not reproduced.

## The bug

The reporter built a circuit with an action button in a BCI shell, saved it, loaded it with the Load Circuit verb, put the new BCI in an implanter and implanted it. The user got extra "funny buttons", clicking them produced runtimes (screenshot only), and the buttons remained even after the circuit was removed from the human.

What actually happens: the loaded BCI has two circuits' worth of state. The BCI's own default circuit (which contains an Equipment Action component) is never detached, so its action button stays granted. Because the shell then points at the loaded circuit, `remove_circuit()` never touches the old one.

## Reproduction

Reproduced on master through the Lua editor, using the same code path as the Load Circuit verb (the verb itself and the implanter were not used). The click runtime from the report did not occur.

1. Spawned a BCI (`/obj/item/organ/cyberimp/bci`) and took the circuit attached to its shell component.
2. Called `convert_to_json()` on that circuit, created an `/obj/item/integrated_circuit/loaded` and called `load_circuit_data(json)` on it. This creates a second BCI as the external object and fires `COMSIG_MOVABLE_CIRCUIT_LOADED` on it.
3. Spawned a human and inserted the new BCI (`Insert`).
4. Listed the BCI's actions and the human's actions, called `Activate()` on the "Action" buttons, then called `Remove()` and listed the actions again.

Observed on master:

- Before insertion the loaded BCI's shell reported the loaded circuit as its `attached_circuit`.
- After insertion the BCI had 3 actions and the human had 3 buttons: "Action", "Action", "Check BCI Charge".
- After `Remove`, the BCI still had 3 actions (the human had 0), so the actions were stale.
- Activating the "Action" buttons produced no new runtime in `runtime.log`. The only runtimes in the log were unrelated tgui asset errors from the admin's own client.

## Cause

The BCI creates a default circuit containing an Equipment Action component and passes it to the shell as `starting_circuit` (`code/modules/wiremod/shell/brain_computer_interface.dm:15-20`). When a saved circuit is loaded, `/datum/component/shell/proc/on_load` (`code/datums/components/shell.dm:77`) merges the unremovable components into the loaded list and finishes with `attach_circuit(circuit)` (line 90). It never removes the shell's current `attached_circuit`.

The default circuit therefore stays registered with the shell, and its `equipment_action` keeps the `datum/action` it granted. `attach_circuit` then overwrites `attached_circuit`, so a later `remove_circuit()` operates only on the loaded circuit and the old one is never unregistered.

## Fix

One commit, "Fix issue 69937: remove a shell's default circuit when a saved circuit is loaded into it", changes `on_load` in `code/datums/components/shell.dm`. At the top of the proc, if the shell has an `attached_circuit` that is not the circuit being loaded, it stores it, calls `remove_circuit()` (which unregisters it and its action components properly) and `qdel`s it, and then proceeds as before:

```dm
if(attached_circuit && attached_circuit != circuit)
	var/obj/item/integrated_circuit/old_circuit = attached_circuit
	remove_circuit()
	qdel(old_circuit)
```

Using `remove_circuit()` rather than only deleting the circuit means the normal detach path runs, so the old circuit's action components are unregistered and their actions are removed.

## Verification

Rebuilt and ran the same Lua sequence as in the reproduction:

- After insertion the BCI had 2 actions and the human had 2 buttons: "Action" and "Check BCI Charge". `attached_circuit` was the loaded circuit.
- After activating the "Action" button, `Remove()` and `remove_circuit()`, the BCI had 0 actions.
- No new runtimes appeared in `runtime.log` apart from unrelated tgui asset errors.

Not checked: the actual Load Circuit verb and a player using the implanter, a circuit that is saved and loaded across rounds, other shells that load circuits through `on_load`, and the runtime from the report.

## Notes

- The reported click runtime is uncertain. It is shown only in a screenshot, and the duplicate, stale action was the only symptom reproduced. It likely came from the stale action/circuit combination, but that was not confirmed.
- The fix applies to any shell with a starting circuit, not only BCIs; it changes `on_load` for all of them. A maintainer may want to confirm that no shell relies on keeping its starting circuit after a load.
- `qdel`ing the old circuit immediately after `remove_circuit()` assumes nothing else holds a reference that needs it; none was found during testing.
