## Summary

The 2024 report says that loading the "Ninja Holding" lazy template with the admin verb "Load/Jump Lazy Template" produced about 1700 runtimes (a screenshot shows 500), with maintainer comments pointing at reads of a `run_later` variable. On current master, loading the same template once produced no runtimes at all in the runtime log. The most likely original cause, found by reading the code, is a closed turf sitting in a turf's atmos adjacency list while the active-turf processing reads `run_later` on it. Whether that can still happen on master was not shown, so nothing was changed.

## The bug

As reported (client 515.1637, tested locally with "breakpoint on runtimes" enabled): the reporter loaded the ninja holding facility from the admin verb and the runtime log filled with errors straight away. The thread names the variable `run_later`; a maintainer says reads of `run_later` have been seen on live servers, and the reporter confirms the runtimes happened when the template was loaded, not independently of it. The exact runtime text is only in the screenshot, not in the issue body, so it is assumed here to be the `run_later` error the maintainer describes.

## Reproduction

I could not reproduce it. On master, using admin tools:

1. Started a round (Start Now) and observed.
2. Ran "Load/Jump Lazy Template", chose "Ninja Holding", and answered "Yes" to "Jump to template after loading?".
3. The template loaded after about 18 seconds and the admin was moved to the bottom left of the reservation. The log recorded `has loaded lazy template 'LT_NINJAHOLDING'`.
4. Waited about 3 more minutes and read the round's `runtime.log`.

Result: no `run_later` runtime, and no runtime error from the load at all. The only runtime errors in the log afterwards were 51 "bad proc" errors caused by the Lua code used afterwards to inspect the map (a `locate` call used incorrectly), not by the template load. Checking `SSair.active_turfs` with the Lua editor showed 197 turfs, all of them `/turf/open`.

Only the ninja facility was tried, only once, with the verb's "jump" option. Other templates, loading again, or loading while atmos was busy were not tried.

## Cause

Not observed. Reading master, the `run_later` reads that match the reports are in `/turf/open/process_cell()`, `code/modules/atmospherics/environmental/LINDA_turf_tile.dm:283`:

```dm
for(var/turf/open/enemy_tile as anything in adjacent_turfs)
	...
	if(enemy_tile.run_later)
		LAZYADD(share_end, enemy_tile)
```

`run_later` is declared on open turfs (`LINDA_turf_tile.dm:48`) and set for space turfs (`code/game/turfs/open/space/space.dm:61`). The loop is typed `turf/open`, so if a closed turf (which has no `run_later`) is in `atmos_adjacent_turfs`, reading `run_later` on it gives an "undefined var" runtime, once per processed cell that has such a neighbor. A map load replaces many turfs, so closed turfs can end up in adjacency lists during loading for a short time, which would explain a burst of runtimes that depends on timing. The same loop has a unit-test-only check (`stack_trace("closed turf inside of adjacent turfs")`, lines 275-279) that shows the code already treats this as an invalid state.

This matches the live-server report in #89649. An upstream PR (#96366) adds an `isopenturf()` guard in `process_cell` and `process_active_turfs`; it was closed without being merged.

## Fix

None. The problem did not occur, so there was no failing case to fix against, and the underlying race is shared with #89649.

## Verification

Nothing to verify beyond the negative result under Reproduction. Not checked: other lazy templates, repeated loads, loading with atmos under load, or the exact build the reporter used (515.1637 and a 2024 master).

## Notes

- Possible explanations for the difference: the race is timing dependent and did not hit on this run, or it was fixed or hidden by later atmos changes. The inputs do not distinguish these.
- If someone wants to retry: load "Ninja Holding" several times, load other templates, and load while the air subsystem is busy, then search the runtime log for `run_later`.
- Related: #89649 (same likely cause on live servers), and the closed PR #96366.
