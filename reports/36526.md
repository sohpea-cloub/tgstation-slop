## Summary

An AI can track, and jump its camera eye to, any mob that any camera can see, regardless of the camera's network. That includes the Syndicate cameras on the caravan ambush shuttle, which are on the `caravansyndicate1` network and not on the station's `ss13` network. The cause is that `/mob/living/proc/can_track` ends with a network-agnostic "is any camera seeing this?" check. The fix adds a network-aware visibility check to the cameras subsystem and uses it in `can_track` when the tracker is an AI.

## The bug

The issue (2018, still open with comments up to 2025) says that an AI can use "track with camera" and pick a Syndicate salvage pilot, leader or worker from the caravan ambush ruin (`caravanambush.dmm`), and so reach the ambush cameras. Comments note that `can_track` and `near_camera` would have to be reworked, that the problem is still present in 2023 and 2025, and that one option is to restrict AIs to station and lavaland cameras. A related network-jumping exploit had been fixed separately in `ai.dm`.

In game, the AI's tracking list contains mobs that only a camera on a foreign network can see, and selecting one moves the AI's eye to that location.

## Reproduction

Reproduced on master `87b93338`. The upstream PR #77776, which was merged, had not fixed it. A real caravan ambush ruin was not loaded; a synthetic camera on the same network was used instead.

1. Started a round on the test server and observed.
2. In the Lua editor, spawned a camera at (100, 100, z4) and set its `network` to `{"caravansyndicate1"}`. Spawned a human named "Caravan Victim" next to it (101, 100, z4).
3. In the same script, spawned a human at a station location (60, 60, z2) and turned it into an AI with `AIize()`. The AI's network was `ss13`.
4. Called `can_track(ai)` on "Caravan Victim".

Result: `Caravan Victim z4 track=1`. The AI could track a mob that only a `caravansyndicate1` camera could see.

## Cause

`/mob/living/proc/can_track` (`code/modules/mob/living/living.dm:1332`) rejects cloaked mobs, mobs inside containers, mobs on centcom or away levels, and mobs on the Syndicate base, and then finishes with:

```dm
// Now, are they viewable by a camera? (This is last because it's the most intensive check)
if(!SScameras.is_visible_by_cameras(src))
	return FALSE
return TRUE
```

`SScameras.is_visible_by_cameras` (`code/controllers/subsystem/cameras.dm:~233`) asks `turf_visible_by_cameras`, which reads the camera chunk's `visibleTurfs`. A chunk aggregates every camera that can see into it, whatever its network, so the answer is "some camera can see this turf", not "a camera this AI can use can see it".

`find_trackable_mobs` and the track action in `code/game/machinery/camera/trackable.dm` (line 49) rely on `can_track`, and `on_track_target` (`code/modules/mob/living/silicon/ai/ai.dm:369`) then moves the AI's eye to the target's turf.

The `is_away_level` check at `living.dm:1345` does not help here: the caravan shuttle docks in space, which is not an away level. The caravan cameras are `xray` cameras on network `caravansyndicate1` (`_maps/shuttles/ruin/ruin_syndicate_fighter_shiv.dmm:51-53`).

## Fix

One commit, "Fix issue 36526: AIs can track mobs seen only by cameras outside their network", touching two files.

- `code/controllers/subsystem/cameras.dm`: new `is_visible_by_camera_networks(atom/target, list/networks)`. It first returns FALSE if no camera at all sees the turf (cheap early out, using the existing `turf_visible_by_cameras`). It then walks the cameras of the turf's chunk, across the chunk's z range (`lower_z` to `upper_z`), and returns TRUE only for a camera that is on at least one of the given networks, passes `can_use()`, is within `view_range` when on the same z level, and whose `can_see()` list contains the turf.
- `code/modules/mob/living/living.dm`: in `can_track`, when the tracker is an AI the final check is `SScameras.is_visible_by_camera_networks(src, tracking_ai.network)`. Other trackers keep the old check.

The alternative suggested in the issue comments, limiting AIs to station and lavaland z-levels, was not taken; the network check is what the cameras are already designed around, and it does not special-case any level.

## Verification

After rebuilding, the test server was started with the same kind of setup plus controls, and `can_track(ai)` was called on each mob (AI network `ss13`):

| Mob | Location | Cameras seeing it | Result |
|---|---|---|---|
| Caravan Victim | z4 | camera on `caravansyndicate1` | `track=0` (was 1 before the fix) |
| SS13 Cam Guy | z4 | camera on the default network | `track=1` |
| Station Cam Guy | z2, at a station camera | station camera | `track=1` |
| No Cam Guy | z4 (160, 160) | none | `track=0` |

The runtime log was checked for entries from `cameras.dm` and `living.dm` and had none.

Not checked:
- An actual caravan ambush ruin load; a plain camera set to the caravan network was used (the ruin's cameras are xray cameras).
- The AI's "Jump to Network" verb with a changed network (it sets the same `network` variable that the fix reads), and the in-game "track with camera" UI itself; only `can_track` and the tracking list were called from Lua.
- A camera that is disabled or out of range (the code handles both, but no test covered them).

## Notes

- Cyborgs with a camera have a separate path (`silicon.dm`, around line 360); this was left unchanged.
- `is_visible_by_camera_networks` walks a chunk's cameras and calls `can_see()` for each, which is more expensive than the chunk lookup used before. `can_track` is called for every living mob when the tracking list is built, but the early out skips mobs not seen by any camera, and only AIs take the new path.
- Mobs that can no longer be tracked because their only camera is on a foreign network also drop out of the tracking list, not only out of the final tracking step.
