## Summary

The instrument volume complaint in #91554 (notes played at full volume regardless of the volume slider) no longer happens on this master: both the song's own volume setting and the listener's instrument-volume preference scale the volume of every note that is sent. The testers' notes identify the upstream change that fixed it as PR #97884, "Fixes instrument volume slider pref not being applied correctly", merged 2026-09-22 (the PR itself was not read, and this checkout has no history that includes it). The other three issues in the group are old reports about decimal sustain input (#64992, #65320) and loud headphone music for ghosts (#81416). None reproduced as bugs. One small display problem turned up on the way: the instrument editor's linear sustain slider shows a maximum of 50 "seconds" while the real maximum is 5 seconds.

## The bug

- **#91554**: a player heard instrument notes at full volume even with the volume turned down. The issue does not say which slider it means (the instrument's own volume in the editor, or the listener's instrument-volume preference), and the report mentions a test merge ("Dynamic Rework") that is not in the tested tree.
- **#64992 / #65320**: typing a decimal such as `0.5` into the linear sustain box of an instrument (and, per #65320, of the pAI music synthesizer) gave 5 seconds, as if the decimal point were dropped. Both are from 2022.
- **#81416**: headphone music sounded extremely loud and "crunchy" to ghosts standing next to the wearer, and was audible from a tile away.

## Reproduction

### #91554 (does not reproduce)

1. On the test server, as an observer, using the Lua editor, spawn `/obj/item/instrument/piano_synth/headphones` on the observer's tile.
2. Parse a short song with the instrument's song datum (`ParseSong`, 60 BPM, a run of notes), set it to repeat, and start it playing. The observer was the only listener.
3. Read the volume of the sounds the server sent to the observer with the instrument preference at 100:
   - song volume 75 gave sounds at 75%
   - song volume 10 gave sounds at 10%
   (the piano's `volume_multiplier` is 1, `code/modules/instruments/instrument_data/hardcoded.dm:8`)
4. Set the observer's instrument-volume preference to 20 (`write_preference` on `/datum/preference/numeric/volume/sound_instruments`) with song volume 75: notes were sent at 15%, which is 75 x 0.20.

So both sliders change the volume that is sent. The only runtimes were from the tester's own early script errors (calling `playkey_synth` directly before the sound samples were compiled).

### #65320 (pAI synthesizer; does not reproduce)

1. Using the Lua editor, spawn a pAI, buy the Music Synthesizer software, take control of it, and open Software Interface and Music Synthesizer. This is the common instrument editor UI.
2. In Linear sustain mode, send the `edit_sustain_mode` action with amounts `0.5`, `1.5`, `0.3` and `0.2`. All were kept: `sustain_linear_duration` was 5, 15, 3 and 2 deciseconds. In Exponential mode `1.25` was kept. No runtimes.

The values were sent as UI actions, not typed into the number box in a real client, so the client-side typing path was not exercised.

### #64992 and #81416

- #64992: not run in game. Judged by reading the code, as for #65320 (see Cause).
- #81416: the setup is the one used for #91554 above. The observer next to the headphones got one sound per note (no duplicates), at song volume x instrument multiplier x the observer's instrument preference. No separate loudness bug showed up.

## Cause

### #91554 (historical)

The testers' notes describe the old behaviour as the instrument-volume preference being effectively all or nothing in `code/modules/instruments/songs/play_synthesized.dm`, and attribute the fix to PR #97884. On master this file now applies the preference in both places that set a note's volume:

- `playkey_synth()` (`play_synthesized.dm:66-69`) reads the listener's `sound_instruments` preference, skips listeners at 0, and passes `volume * (pref_volume/100)` to `playsound_local()`.
- `process_decay()` (`play_synthesized.dm:134-135`) multiplies the per-channel volume updates sent while a note decays by `pref_volume / 100` as well.

The old code was not run, so how it failed is not confirmed here.

### #64992 / #65320

The old problem came from BYOND's `input()` rounding the number. Instruments now use a tgui `InstrumentEditor` for everyone, and pAIs get the same editor (`code/modules/instruments/songs/editor.dm`). `edit_sustain_mode` passes `params["amount"]` straight to `set_linear_falloff_duration()` (`editor.dm:185-193`), which only rounds to the world tick length (`_song.dm:399-401`: `round(duration * 10, world.tick_lag)`). The testers' notes also say the number box in the tgui front end parses typed values as floats and only snaps to whole steps when dragged (`InstrumentEditor.tsx`); that file was not re-read for this write-up.

### #81416

Headphones set `instrument_range = 1` (`code/modules/instruments/piano_synth.dm:40`), so anyone within one tile, ghosts included, is a listener. Each listener gets a single sound per note, and the volume is the song's volume times the instrument's multiplier times that listener's own instrument preference. A ghost with the preference at 100 hears the same volume as the wearer, by design. The testers' notes say the loud-ghost report predates PR #97884 (the preference slider was all-or-nothing then), so it probably came from the same defect.

### Side finding: linear sustain maximum shown in the wrong unit

`INSTRUMENT_MAX_TOTAL_SUSTAIN` is `5 SECONDS`, which is 50 deciseconds (`code/__DEFINES/instruments.dm:12`). The editor sends it as the slider maximum in Linear mode (`editor.dm:27`) under the label "Linear Sustain Duration (in seconds)" (`editor.dm:24`), so the slider offers up to 50 "seconds". `set_linear_falloff_duration()` clamps to that same constant after multiplying by 10, so the real limit is 5 seconds. Entering more than 5 is silently clamped. This was noted in the pAI test and not fixed.

## Fix

None. No commits were made for this group.

## Verification

Checked in game: the volume sent for song volume 75 and 10 (75% and 10%), and for a preference of 20 (15%); and that a pAI's synthesizer keeps decimal linear sustain values sent as UI actions.

Not checked:

- Whether the decaying-note volume update (`process_decay()`'s `set_sound_channel_volume()`) reaches a real client at the right level. The test client lists only newly started sounds, so a check with a real BYOND client is needed.
- Typing a decimal into the sustain number box in a real client.
- #64992 was not run at all, and #81416 was not run with a real headphone wearer and a second listener.
- The issue mentions other decimal inputs (reflector angle, pen head rotation); those were not looked at.

## Notes

- If anyone can still reproduce #91554 on a current build, the report needs to say which slider was used and whether the listener or the player moved it.
- The linear sustain label problem (a maximum of 50 shown for a 5 second cap) could be fixed by sending `INSTRUMENT_MAX_TOTAL_SUSTAIN / 10` as the maximum in `editor.dm:27`.
- #65320 was already closed upstream in 2022 as a duplicate of #64992, and a linked PR #65008 is the one that moved the sustain boxes to tgui (per the issue thread and the testers' notes).
