# #91318: Navigate menu mislabels and cannot route to destinations two or more z-levels away

| | |
|---|---|
| Issues | [#91318](https://github.com/tgstation/tgstation/issues/91318): verified, fixed |
| Status | Fixed and checked in game on a multi-z test map |
| Fix branch | [fix/91318](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/91318) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The Navigate verb uses `get_dir_multiz()` to label destinations "(Above)" or "(Below)" and to decide whether to look for stairs or ladders going up or down. `get_dir_multiz()` only recognises levels exactly one above or below, so for a destination two or more levels away it returns a plain horizontal direction. Such destinations were always labelled "(Below)", and choosing one failed with "can't find ladder or staircase going there!". The fix compares z-levels directly and also hides destinations on levels that are not part of the connected stack.

## The bug

On a map with a stack of three or more connected z-levels, Navigate showed destinations on levels above you as "(Below)" when they were two or more levels up. Selecting one produced the balloon text "can't find ladder or staircase going there!" and no path. Destinations on unrelated levels (for example a separate space level) were also listed.

## Reproduction

1. On the test server, use the MultiZ Debug map (z-levels 2, 3 and 4 are a connected stack, z1 is an unconnected space level).
2. In the Lua editor, create `/obj/effect/landmark/navigate_destination` landmarks at (128,129,4), (130,129,3), (131,129,2) and (127,129,1). They register in `GLOB.navigate_destinations` on creation.
3. Spawn a human with air and without damage (traits `no_breath` and `godmode` were used) at (126,129,2), and take control of it.
4. Use the Navigate verb.

Observed on master: the list contained "Engineering Storage (Below)", "Service Hallway (Above)" and "Space (Below)". "Space" is the z1 landmark, which is not connected to the stack. Choosing "Engineering Storage (Below)" gave "can't find ladder or staircase going there!". Which landmark carried the name "Engineering Storage" was not checked by z-level, but the destination two levels up is the one that should have been labelled Above.

## Cause

`create_navigation()` in `code/modules/mob/living/navigation.dm:36` builds the label with `get_dir_multiz(src, destination) & UP`. `create_navigation_line()` (line 68) uses `get_dir_multiz(src, navigate_target) & (UP|DOWN)` as the direction for `find_nearest_stair_or_ladder()`. `get_dir_multiz()` (`code/modules/mapping/space_management/multiz_helpers.dm:11`) only returns UP or DOWN if the other turf's z is exactly the level above or below; for any bigger gap it falls back to plain `get_dir`. The result for a destination two or more levels up has no UP bit, so the label becomes "(Below)" and `nav_dir` is 0. With a direction of 0, `find_nearest_stair_or_ladder()` finds nothing, which is the error message.

The code at line 35 only checks `is_multi_z_level(z)` and `destination.z != z`, so destinations on levels outside the connected stack were also added.

## Fix

One commit, "Fix issue 91318: navigate menu above/below hints with more than two z levels", changes `code/modules/mob/living/navigation.dm`:

- In `create_navigation()`, a destination whose z is not in `SSmapping.get_connected_levels(z)` is skipped. For the rest the label is "(Above)" if `destination.z > z` and "(Below)" otherwise.
- In `create_navigation_line()`, `nav_dir` is `UP` if `navigate_target.z > z`, else `DOWN`.

Connected levels are consecutive, so comparing z numbers is enough and no multi-step helper was needed. Hiding unconnected levels is an addition that goes beyond the issue text; without it the "Above/Below" label would be wrong for those levels too.

## Verification

After rebuilding and restarting the test server with the same map and landmarks, with the same human at (126,129,2):

- The list contained "Central Primary Hallway", "Engineering Storage (Above)", "Nearest Way Up" and "Service Hallway (Above)". There was no z1 "Space" entry.
- Submitting "Engineering Storage (Above)" gave the balloon text "navigation path created" and path images appeared on the floor starting at (126,129) toward (125,128). This is the destination that failed before.

Not checked: a "(Below)" destination from an upper level (the code path is symmetrical but was not run); that "Engineering Storage" is the z4 landmark (inferred, not looked up by z); following the whole path to the stairs; maps with the real station stack rather than the debug map.

## Notes

- The issue text pointed at the single `get_dir_multiz` call; there were two uses in this file (label and `nav_dir`) and both were changed.
- `get_dir_multiz` itself was not changed; other callers may still assume its adjacent-level behaviour.
- The destinations "Nearest Way Up" and "Nearest Way Down" are unaffected.
