## Summary

The report says a malfunctioning AI that was carded and then put into an AI system integrity restorer lost its hidden law 0 and was left with plain Asimov. On current master this does not happen. Law 0 survived carding, the restorer (insert, repair, revive from dead, UI law list), a law rack update and a law rack unlink, because malf law 0 is stored as a protected zeroth law that non-forced law operations ignore. The report dates from 2022, before law racks and `protected_zeroth`, so the cause was probably in code that has since been replaced. No fix was written.

## The bug

As reported (round 190066, client 514.1585, with a supermatter testmerge): a scientist who had late-joined as an AI rolled malf AI. Security carded the AI and, seeing no laws on the card, built an integrity restorer to read them. Before carding, the AI's laws (via the admin "check AI laws" option) were Asimov plus the hidden malf law 0. After the restorer, the AI had only Asimov. The shift-end report listed the AI as a malf antagonist but showed 0 law changes for it. The reporter could not reproduce it in a later round.

## Reproduction

Not reproduced. The test was done on a private server with the Lua editor; the round was started and the tester observed.

1. Spawned a human with a mind, then created an AI from it with `SS13.new('/mob/living/silicon/ai', loc, human, nil, nil, true)` (force mind move). It linked itself to a core law rack.
2. Gave the AI a malf-style law 0 by hand, with the same calls `add_law_zero()` makes (`set_zeroth_law(text, borg_text, TRUE)`, `protected_zeroth = TRUE`, `try_sync_laws()`). The real `add_law_zero()` could not be used: from an admin proc call, `strings()` returns early (`code/__HELPERS/_string_lists.dm:23`), so `malfunction_flavor` is null and `malf_ai.dm:148` (`malfunction_flavor["zeroth_law"]`) throws "bad index". This is an artifact of calling it from Lua, not a game bug. An attempt to add the real malf antagonist datum hit that same runtime.
3. Carded the AI with `/obj/item/aicard` (`capture_ai`), then moved it into a `/obj/machinery/computer/aifixer` with `transfer_ai(AI_TRANS_FROM_CARD, ...)`. Both transfer messages appeared in chat.
4. In the restorer: applied 60 brute damage, set the restorer to restoring and ran its `process()` eight times (health went from 40 to 80). Then killed the AI, applied 100 brute damage and ran `process()` 40 times to revive it (revival happens at health >= 0).
5. After every step, `laws.zeroth` was still the test law, `protected_zeroth` was 1, there were 3 inherent laws, and the AI was still linked to its rack. The restorer's UI data (`ui_data`) listed 4 laws: law 0 plus the 3 inherent ones.
6. Called the rack's `update_lawset()` and `unlink_silicon(ai)`: law 0 stayed. Unlinking wiped the inherent, supplied and hacked laws (0 inherent afterwards) but not the protected law 0. Re-linking was refused while the AI was carded or in the restorer, which is by design (`can_link_to`, `control_disabled`).

Evidence of this kind is only as good as the hand-set law 0. Paths not exercised: the real `add_law_zero()`, and the midround malf ruleset.

## Cause

There is no defect to point at on master; the code protects law 0:

- `set_zeroth_law` (`code/datums/ai_laws/ai_laws.dm:198`) returns without changing anything when `zeroth && !force && protected_zeroth`.
- `clear_zeroth_law` (`ai_laws.dm:212`) returns FALSE without changing anything when `!force && protected_zeroth`.
- `add_law_zero()` (`code/modules/antagonists/malf_ai/malf_ai.dm:142`) sets law 0 with `force = TRUE` and then sets `protected_zeroth = TRUE` (lines 152-153).
- The law rack only uses the non-forced setters: `apply_lawset` calls `set_zeroth_law(combined_lawset.zeroth, ...)` (`code/game/machinery/ai_core/law.dm:998`) and `unlink_silicon` calls `set_zeroth_law(null, null)` (`law.dm:913`). Both are ignored for a protected law 0.
- `aifixer.dm` and `aicard.dm` do not touch laws; both UIs pass `include_zeroth = TRUE` when listing them (`code/game/machinery/computer/aifixer.dm:46`, `code/game/objects/items/devices/aicard.dm:157`).
- The only forced clears are in `malf_ai.dm:53` (antagonist removal), the admin law panel (`code/modules/admin/verbs/lawpanel.dm:126`) and `code/modules/mob/living/silicon/robot/robot.dm:1005`.

## Notes

- Possible explanations for the original report cannot be told apart from it: the antagonist datum was removed from the mob, an admin action, the supermatter testmerge, or older code that the law rack and protected zeroth law replaced. "0 law changes" at shift end fits law 0 never having been applied or recorded, rather than being lost.
- Untested possibility: the AI rolled malf while SSD with a mind that was later moved, or a midround malf where `add_antag_datum` ran while the mind sat in a different mob. Nothing in the code suggests law loss in either case.
- Suggested outcome: close as not reproducible on current master.
