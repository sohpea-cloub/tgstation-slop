# #45997: visible_message from an item held in a hand is not shown to bystanders

| | |
|---|---|

| Status | Fixed on the branch below |

| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

`/atom/proc/visible_message()` treats any atom whose `loc` is not a turf as being "inside something", so an item in a mob's hand gives the full message only to the holder and the (usually empty) blind message to everyone else. People watching the holder therefore see nothing. The fix excludes items in the holder's hands from that case, so they follow the normal visibility rules for everyone who can see the holder.

## The bug

The issue is a short report: `visible_message` "does not work for inhand items". In the comments the reporter said it "definitely does not show to the holder" and believed it did not show to people around either. On master, testing showed that the holder does see the message; it is the bystanders who do not. Most `visible_message` calls from items pass no blind message, so bystanders get nothing at all.

## Reproduction

1. On the test server, using the Lua editor, spawn two humans, A and B, standing next to each other, and give A a crowbar in hand.
2. Take control of B (possess it) so B's chat is visible.
3. In the Lua editor, call `visible_message("TESTMSG-held", "TESTSELF", "TESTBLIND")` on the crowbar. Also call it with no blind message.
4. Observed on master: B saw only `TESTBLIND` (the blind message) for the first call and nothing for the call without a blind message. For comparison, the same call with the crowbar on the floor showed the normal message to B.
5. Take control of A, the holder, and repeat. A saw the normal messages (`TESTMSG-holder` and a variant without blind message). So the holder part of the issue was not reproduced; the bystander part was.

The messages were generated by calling the proc directly on the item, not by a player action that produces one.

## Cause

In `/atom/proc/visible_message()` (`code/modules/mob/mob.dm:280-322`), for each hearing mob:

```dm
else if(T != loc && T != src) //if src is inside something and not a turf.
    if(hearing_mob != loc) // Only give the blind message to hearers that aren't the location
        msg = blind_message
        msg_type = MSG_AUDIBLE
else if(!HAS_TRAIT(hearing_mob, TRAIT_HEAR_THROUGH_DARKNESS) && ...
```

(lines 309-315). `T` is the turf of the item, so an item in a hand has `loc` equal to the holding mob, which is neither `T` nor the item. The branch is meant for items in containers. Only the mob that is `loc` (the holder) keeps the full message; everyone else gets `blind_message`, which is null in most calls, and `if(!msg) continue` (line 316) skips them. The branch also skips the darkness check that applies to visible atoms.

## Fix

One commit, "Fix issue 45997: visible_message from a held item is shown to everyone who sees the holder". The condition at line 309 became:

```dm
else if(T != loc && T != src && !(ismob(loc) && loc:is_holding(src)))
```

Items the holder is holding in their hands now fall through to the normal check, so they are shown to every mob that can see the holder, and are subject to the usual darkness rule. Items in pockets, bags or other containers still count as "inside something", since `is_holding` is false for them. The change is in the core proc rather than in individual callers because the problem affects every item's `visible_message`.

## Verification

After rebuilding, with A holding the item and B possessed: B saw `TESTMSG-held` and the no-blind-message variant. The runtime log showed only runtimes caused by the test itself (admin proc-call without a ckey), none from the change.

Not checked in game: that a pocketed or bagged item keeps the old behaviour. An attempt to test a pocketed item in the Lua editor errored out on a destroyed callback and was not repeated; the claim rests on reading the code. Also not tested: the darkness case, and which real `visible_message` callers in the game are now more visible.

## Notes

- The change widens who sees `visible_message` calls made by held items. That is what the issue asks for, but it affects every such call, and a maintainer should check that no caller relied on bystanders not seeing the message.
- Upstream PR #45979 fixed only the Head of Personnel ticket case of this problem; it did not change the shared proc.
