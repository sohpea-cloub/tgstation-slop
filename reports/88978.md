## Summary

When an admin writes a ticket reference such as `#2` in asay, the message is first turned into a clickable ticket link whose text contains the ticket's initiator name. `ASay` then runs `keywords_lookup()` over the whole message, including that generated link markup. If a word of the initiator's name matches a mob name or ckey, `keywords_lookup()` inserts its own `(?|F)` anchors into the middle of the ticket link and breaks it. The fix runs `keywords_lookup()` on the plain text before the links are generated, and makes `keywords_lookup()` leave words starting with `@` or `#` alone.

## The bug

Admins saw `#N` references and `@0x...` datum references in asay lose their links and render as a garbled message (the reports' screenshots). The failure was intermittent: it worked for most messages and failed for others, which is why the original reporter and another developer could not reproduce it a day later, and why the 2022 report (#68641) said a freshly started debug server did not show it.

What is actually happening: a ticket link is generated as `#N (State | initiator_key/(Name))`, and the text includes spaces. Whether it breaks depends on the initiator's name. A name with no word matching a mob name or ckey leaves the link intact. A multi-word name (or a word in the name that equals a mob's name word or ckey) gets keyword anchors injected into it.

## Reproduction

Reproduced on master with admin tools, using a ticket whose initiator has a multi-word name. The ticket was created from the Lua editor rather than through the normal ahelp panel.

1. Started a round, joined as an observer, and opened the Lua editor.
2. Using the Lua editor, renamed the observer mob to "Bob Smith Jones" (`name` and `real_name`) and created a ticket with `SS13.new('/datum/admin_help', 'second', client, false)`. The ticket's `initiator_key_name` became `key/(Bob Smith Jones)` (the player key plus the mob name).
3. Ran the ASay verb with `see #2 and @0x<ref of the first ticket> ok`.
4. Observed in the admin chat:

   ```
   see #2 (Active | key/(Bob Smith(?|F) Jones)) and @0x210371df ok
   ```

   The ticket link text stopped at `key/(Bob Smith(?`. The `(?|F)` buttons that `keywords_lookup()` adds after a name match appeared inside the ticket's `<A>`, so the chat showed the link cut short, with the rest of the ticket text and a stray `F)` outside it.
5. As a control, an earlier ASay `look at #1 and @mob_2899 please` with a mob named "Nena Eliza" (no word matching the ticket text) produced `#1 (Active | key/(Nena Eliza))` with a working link. This matches the intermittent behaviour in the reports. In that message `@mob_2899` stayed plain text; `@mob_N` tags are not linkable by this code (it looks datums up by memory address) and the fix leaves that unchanged.

The datum-reference case from the #88978 screenshot (`@0xd03ccb1` shown as a mangled message) could not be reproduced on unmodified master. Only the ticket case failed. The reporter said later that they could not reproduce it either.

## Cause

`ASay` in `code/modules/admin/verbs/adminsay.dm` (lines 7-21 at master) processed the message in this order:

1. `check_asay_links(message)` (`code/modules/admin/verbs/adminhelp.dm:1074`) replaced `@ckey`, `@0x...` and `#N` words with HTML. For tickets it produces `<u><A href='...ahelp=...;ahelp_action=ticket'>#N (State | initiator_key_name)</A></u>` (adminhelp.dm around 1115-1130).
2. `log_talk(...)` logged the result.
3. `message = keywords_lookup(message)` (adminsay.dm:21) ran on the HTML-laden message.

`keywords_lookup()` (`adminhelp.dm:962`) splits its input on spaces and, for every word whose `ckey()` matches a mob's ckey, surname or forename, appends `<font ...>(<A ...>?</A>|<A ...>F</A>)</font>` right after the word (adminhelp.dm:1001 onwards, the loop over `msglist`). Because the generated ticket link contains spaces and the initiator's name, a word such as "Smith" in `key/(Bob Smith Jones)` matched a mob. The helper then wrote its anchors in the middle of the ticket `<A>` element, and browsers do not nest anchors, so the ticket link was cut at that point. `keywords_lookup()` was designed for plain text; asay fed it text containing markup.

Datum links and admin pings (`<u>@name</u>`) are single words without spaces, so by reading the code they are much less likely to be hit this way; no datum failure was seen in testing. #68641 is the same defect: ticket link markup rewritten by `keywords_lookup()`, shown as broken links.

## Fix

One commit on `fix/88978`, "Fix issue 88978: asay ticket and datum links no longer broken by keyword lookup":

- `adminsay.dm`: `keywords_lookup(message)` now runs first, on the plain text, and `check_asay_links()` runs afterwards on its output. The original text is kept in `logged_message` and passed to `log_talk()`, so the asay log still gets the plain message (before, the log received the version with link HTML for tickets and datums).
- `adminhelp.dm` (`keywords_lookup`): words whose first character is `@` or `#` are skipped. This is needed by the reordering. Without it, a ping such as `@adminckey` would match that ckey, get `<font ...>(?|F)</font>` glued directly after it with no space, and `check_asay_links()` would then see the word `@adminckey<font` and fail to ping or link it. Ticket words like `#2` would not match a mob but are skipped for the same reason.

Running the plain-text pass first avoids having to make `keywords_lookup()` parse or skip HTML; no other approach was tried.

## Verification

After rebuilding, on a fresh round with the same setup (mob renamed "Bob Smith Jones", a ticket created from the Lua editor):

- ASay `see #1 and @adminckey and Smith ok` produced `see #1 (Active | key/(Bob Smith Jones)) and @adminckey and Smith(?|F) ok`. The ticket link stayed whole (its `href` carried the `ahelp=...;ahelp_action=ticket` target), the ping sound for `@adminckey` played, and the plain word "Smith" still received its `(?|F)` buttons.
- ASay `datum @0x21049f72 and #1 done` produced working links for both the datum (`Vars=` to the View Variables target) and the ticket.
- The round's runtime log had no runtimes after the fix.

Not checked:
- The datum-reference symptom from the original screenshot, because it never reproduced on unmodified master, so there is no before/after for it.
- Messages with several tickets or datums at once, and tickets whose initiator name matches several mobs.
- A real adminhelp from a connected player; tickets were created from the Lua editor.
- The other callers of `keywords_lookup()` (the ahelp message, the namecheck world topic and the chat command) were not exercised. The change in `keywords_lookup()` only affects words beginning with `@` or `#`, which in those callers are no longer matched against mob names.

## Notes

- Behaviour change in the asay log: `log_talk()` now records the original text rather than the text with link HTML. This seems more useful, but a maintainer may want to confirm nothing parses the old format.
- Word-based matching in `keywords_lookup()` is also why the bug is intermittent: it only shows when a word in the ticket's initiator name equals a name word or ckey of some existing mob.
- #68641's observation that a debug server did not show the problem fits this: a test server rarely has a ticket whose initiator name collides with another mob's name word.
