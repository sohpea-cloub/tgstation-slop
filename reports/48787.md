| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The issue (opened 2020) reports that holoparasites cannot control their momentum in zero gravity, unlike guardians. On current master the complaint no longer holds: guardians get the `simple_flying` element, which gives them `TRAIT_MOVE_FLYING`, and `Process_Spacemove()` returns TRUE for flying mobs. In a no-gravity area a spawned guardian was able to "move in space", while a lone human was not. No fix was committed. A separate, unrelated bug was found in the gravitokinetic guardian's `set_summoner()` (an inverted check); it is described under Notes.

## The bug

As reported, a holoparasite in a no-gravity area drifted like a normal crewmember and could not stop or steer, even though it is a floating spirit. Guardians could fly through space with full control. The issue's comments add two related points: the Gravity holoparasite is hurt by its own heavy gravity with no visual indication, and a suggested fix (from a 2022 comment) was to give holoparasites `TRAIT_SPACEWALK` and to let the gravity holoparasite and its user negate gravity effects with `TRAIT_NEGATES_GRAVITY`.

## Reproduction

The zero-gravity part could not be reproduced. The check was made by calling procs through admin tools, not by steering a guardian with the movement keys, so "does not drift" is inferred from the return value of `Process_Spacemove()`, which is what the movement code consults (`code/modules/mob/mob_movement.dm:94`).

1. On the test server, using the Lua editor, set the NO_GRAVITY area flag (16384) on the area of an observer's tile.
2. Spawn a `/mob/living/basic/guardian/standard` and a `/mob/living/carbon/human` on that tile.
3. Call `has_gravity()`, `movement_type` and `Process_Spacemove(1)` on each.
4. Repeat for a `/mob/living/basic/guardian/gravitokinetic` and a human on separate tiles away from the first pair.

Observed:

| Mob | `has_gravity()` | `movement_type` | `Process_Spacemove(1)` |
|---|---|---|---|
| Standard guardian | 0 | 11 (includes FLYING) | 1 |
| Gravitokinetic guardian | 1 (its own `forced_gravity` element) | 3 (FLYING) | 1 |
| Human, alone on its tile (control) | 0 | not recorded | 0 |

The first human reading on the shared tile was 1 because the adjacent guardian counted as something to push off. The result from the human alone on its tile is the valid control. A second check on a tile that was not in the no-gravity area gave a guardian `has_gravity()` of 1 and `Process_Spacemove(1)` of 1, as expected for normal gravity.

## Cause

Why the old bug is gone:

- `code/modules/mob/living/basic/guardian/guardian.dm:99` calls `AddElement(/datum/element/simple_flying)` in the guardian's `Initialize()`.
- `code/datums/elements/simple_flying.dm` adds `TRAIT_MOVE_FLYING` while the mob's stat is `STABLE` and removes it otherwise.
- `/mob/Process_Spacemove()` (`code/modules/mob/mob_movement.dm:264`) returns TRUE for flying movement types:

```dm
if(movement_type & FLYING || HAS_TRAIT(src, TRAIT_FREE_FLOAT_MOVEMENT))
	return TRUE
```

(line 272). A flying guardian is therefore never treated as drifting in zero gravity. The 2022 comment's code links point to the older `simple_animal` guardian; the guardian type is now `/mob/living/basic/guardian`, which already has this element.

## Fix

None. No commit was made; the zero-gravity behavior the issue asks for is already present.

## Verification

Only the proc-level readings in the table above were taken. Not checked: moving a guardian in zero gravity by actual input, a Gravity holoparasite's user (see Notes), and whether guardians that are not at `STABLE` stat (for example while the guardian is in a worse state) lose flight, which the element does by design.

## Notes

- **Inverted check in the gravitokinetic guardian.** `code/modules/mob/living/basic/guardian/guardian_types/gravitokinetic.dm:30-34`:

  ```dm
  /mob/living/basic/guardian/gravitokinetic/set_summoner(mob/living/to_who, different_person)
  	. = ..()
  	if (!QDELETED(src))
  		return
  	to_who.AddElement(/datum/element/forced_gravity, 1)
  ```

  The check returns for every live guardian, so the `forced_gravity` element is only added to the summoner if the guardian is already deleted. `cut_summoner()` (line 36) removes that element from the summoner, so the add and remove sides do not match. The intended condition is probably `if (QDELETED(src))`. This was not tested in game and no fix was written. It is unrelated to the zero-gravity complaint and, if corrected, would change gameplay (the summoner would start being affected by the guardian's gravity).
- **Guardian hurt by its own heavy gravity.** The gravitokinetic type's description says "you are not immune to your own such effects" (`gravitokinetic.dm:9`), so the comment about a gravity holoparasite being hurt by its own gravity describes documented behavior rather than a bug. The lack of any visual indicator was not looked into.
- The issue's suggested `TRAIT_SPACEWALK` is not needed for the zero-gravity case, because `TRAIT_MOVE_FLYING` already satisfies `Process_Spacemove()`.
- The issue can reasonably be closed as already fixed, with the gravitokinetic `set_summoner()` check filed separately if desired.
