## Summary

The 2018 report says the landed auxiliary mining base cannot be destroyed by a singularity. On current master it can: with the base landed on Lavaland and a singularity placed inside it, the plating was consumed and replaced by lava. The base is built from ordinary plating with no singularity immunity, so no code change was made. Only the default base on Lavaland was tested; the Icebox site, the small base variant and the station dock were not.

## The bug

The issue (opened 2018-09-26, one screenshot, round 94501) says that the aux base area stayed intact while a singularity was eating the surrounding terrain. The screenshot could not be viewed while preparing this write-up, so what it showed is unknown beyond the issue text.

The comments say:

- The first reply expected the base's baseturf to be space after launch.
- The second reply (SpaceManiac) said this had changed: after launch the base now becomes plating instead of space, and that the bay on the maps could be changed from plating to space if desired. It asked whether other shuttles were singulo-immune.
- The third reply said it was only the aux base.

## Reproduction

This was an attempt to reproduce on master, and it did not show the reported behaviour. Admin tools used: the Lua editor and SDQL2/proc calls through Lua.

1. Start a round on the default map (the observer was enough) and open the Lua editor.
2. In Lua, find the `/obj/machinery/computer/auxiliary_base` console and set its landing zone to a basalt turf on Lavaland (z3, 130,130). `set_landing_zone()` accepted it (the game announced "Auxiliary base landing zone coordinates locked in for Lavaland Wastes").
3. Launch the base with `SSshuttle.moveShuttle("colony_drop", <the landing zone dock id>, TRUE)`. The shuttle passed through transit and landed: mode idle, z3, 130,130. The shuttle area (`/area/shuttle/auxiliary_base`, 9 wide by 11 high) was all `/turf/open/floor/plating` except one wall.
4. Spawn `/obj/singularity` at 130,128,3, inside the base. Within about 20 seconds the turf at that position had become `/turf/open/lava/smooth/lava_land_surface` (its `baseturfs` were the same type), still inside the aux base area.
5. Move the singularity to 130,131 and set its energy to 3000 (stage size 9). About 15 seconds later every aux base turf in rows 126 to 133 across the 9-wide area was lava. In the top row of the base, one plating tile remained and the other tiles had become basalt instead of lava (these were not studied further). Before this step, the grid printed from Lua showed only plating (and the one wall) in the base area; afterwards it showed lava.

The landing and the singularity placement were done with admin tools and procs rather than by a player operating the console and a real singularity, so the launch itself was not exercised through the console UI.

## Cause

There is no defect on current master:

- `/turf/singularity_act()` (`code/game/turfs/turf.dm:554`) calls `ScrapeAway(flags = CHANGETURF_INHERIT_AIR)` for ordinary turfs, which includes plating.
- The aux base shuttle maps (`_maps/shuttles/aux_base/aux_base_default.dmm`, `aux_base_small.dmm`) use `/turf/open/floor/plating`, `/turf/closed/wall` and the `/area/shuttle/auxiliary_base` area. They contain no indestructible turfs.
- No code excludes the base: neither `code/datums/components/singularity.dm` nor `code/modules/mining/aux_base.dm` has any special case for it.
- Because the base is placed over the landing site, scraping the plating exposes the site's own turf (basalt, then lava on Lavaland), as seen above.

This matches the comment in the issue that the base now becomes plating, which is destructible. The 2018 behaviour may have come from a stale shuttle turf or baseturf setup that has since changed; that is a guess, since the original case could not be examined.
