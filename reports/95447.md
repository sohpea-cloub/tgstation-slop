## Summary

A player inside an MMI, posibrain or AI card keeps looking through whoever last carried the item after it is dropped, until something moves the item itself. The occupant's client eye is the item both before pickup and after the drop, so the eye variable never changes and the client is never told to re-resolve it. The fix registers a move handler on the brain processor (MMI and posibrain) and on the AI card. One tick after a move it points the occupant's eye at the holder while the item is in a mob's hands, and back at the item when it is not. The on-screen symptom could not be seen in the test setup, so the fix is confirmed only through the server-side eye values, not in a real client.

## The bug

As reported in all three issues: someone picks up an MMI (or posibrain, or a carded AI) with a player inside, then drops it and walks away. The player inside keeps seeing the area around the person who dropped them, following that person, instead of the item lying on the floor. The workaround is to move the item (drag it or throw it). #95447 says this used to look "a lot more janky" and was partly fixed by an earlier PR. #90582 and #92096 describe the same for MMIs, posibrains and AI cards. A commenter on #95447 reported that the client's `eye` variable is already correct (the MMI) while the client keeps displaying the previous holder until the eye atom itself moves.

## Reproduction

The visual bug could not be reproduced on the test server. The tool used to play the game reads the eye the server sends and showed the correct view, so the staleness appears to be client-side rendering (the real Dream Seeker), not visible through the protocol the test client used. What was done and observed:

1. With the Lua editor, spawned a human to act as the carrier and an MMI whose brainmob was possessed by the tester's client. Separately, spawned a human, made it an AI (`AIize()`) and carded it.
2. Had the carrier pick up the item, carried it, dropped it, then teleported the carrier far away.
3. On unfixed master the tool showed the view centred on the dropped MMI or card (for example view centre 107,152 with the carrier at 100,144). So server-side state was already right in the one place the test could see.
4. Reading `client.eye` through the sequence showed it is the MMI/card object the whole time: the same atom before pickup, while held, and after the drop. This matches the commenter's description of the cause.

The on-screen staleness itself was therefore not reproduced; its existence rests on the three reports and the commenter's explanation.

## Cause

For a brainmob inside an MMI or a carded AI, `reset_perspective()` sets the client eye to the item holding it: when the mob is not on a turf, the default is `loc` (`code/modules/mob/mob.dm:507` onwards; the AI override at `code/modules/mob/living/silicon/ai/ai.dm:906` does the same with `client.set_eye(loc)`). That eye is the MMI or card, and it does not change when someone picks it up or drops it: the eye atom is the same before and after, so no new eye value is sent to the client. The client is left displaying the previous carrier until the eye atom moves by itself (for example dragged or thrown) or the eye is set again.

The AI card is a separate case in the code (`code/game/objects/items/devices/aicard.dm`), but the cause is the same.

## Fix

One commit, **Fix issue 95447: MMI and AI card clients keep looking at the mob that dropped them**.

- `obj/item/brain_processor` (`code/modules/mob/living/brain/processor/_processor.dm`, the base for MMIs and posibrains) and `obj/item/aicard` register `COMSIG_MOVABLE_MOVED` on themselves.
- When the item moves and its occupant has a client, a callback is queued with a zero-delay timer (unique, so repeated moves in a tick collapse into one). The refresh runs one tick later and checks the occupant is still inside the item.
- If the item is now in a mob's hands (`ismob(loc)`), the occupant's perspective is reset to that mob (`reset_perspective(loc)`), so the eye changes to the holder.
- Otherwise, if the client's eye is currently a mob, `reset_perspective()` sets it back to the item, again changing the eye value.

So the eye value now changes on every pickup and drop, which is what forces the client to look again.

Why the delay: the parallax code tracking the old eye is still handling the move when the signal fires. Resetting the perspective inside the signal double-registered the parallax's movement tracking and logged a `movable_moved overridden` runtime. Deferring by one tick avoids that.

Alternative tried and dropped: setting the eye to the item's turf (`reset_perspective(source.loc)`) on move, as an older closed upstream PR (#95974, written against the old MMI file) did. With a turf as the eye, parallax code throws because a turf has no `glide_size` (`code/_onclick/hud/parallax/parallax.dm:134`). Switching between the holder and the item avoids ever using a turf.

## Verification

On the test server with the fix built, tracking `client.eye` of the occupant through the Lua editor:

- MMI: start = MMI; held = carrier; carried = carrier; dropped = MMI; carrier teleported far = MMI; picked up again = carrier; dropped again = MMI.
- AI card: on floor = card; held = carrier; carried = carrier; dropped = card; carrier far away = card.
- Throwing and dragging the item also move it and so run the handler; by code reading it does nothing when the eye already has the right value. These were not separately exercised in game.
- The `runtime.log` for the final build had no new runtimes from this change (an earlier, discarded attempt that used a turf as the eye did produce parallax runtimes).

Not checked:

- Whether a real Dream Seeker client now shows the dropped item correctly. The test client could not show the problem before the fix, so this needs someone playing with the real client.
- pAI cards (a separate code path in `code/modules/pai`) were not changed or tested.
- A brain inside a mech, or an MMI installed in a cyborg: the handler acts only when the item is in a mob's hands or the occupant's eye is a mob, so these should be unaffected, but they were not tested in game.
- Posibrains were covered by the same code as MMIs and not tested separately.

## Notes

- If a real client shows the fix does not help, the server-side `reset_perspective()` logic is not the place to look, since it already set the right value before the fix; the problem would then be in how the client handles the eye atom (this is an inference, not tested).
- The change adds a signal handler and a timer for each MMI and each AI card for the whole round, but the handler returns immediately if the item has no occupant with a client.
- The only upstream attempt found was the closed PR #95974 mentioned above; no merged fix was found.
