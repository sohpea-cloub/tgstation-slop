## Summary

Photos taken with a camera showed short characters (spacer quirk, dwarfism) at normal height. Mob height is implemented with displacement map filters, and `getFlatIcon()`, which the camera uses to build photos, only composes icons and overlays and ignores filters. The fix makes `getFlatIcon()` emulate displacement map filters on the appearance they belong to. Other filter types are still ignored.

## The bug

The reporter photographed a character with the spacer quirk (short) and the photo showed them at normal height. The title asks whether this applies to all filters; for filters other than displacement maps, it still does (see Notes).

## Reproduction

1. On the test server, using the Lua editor, spawn humans and set each one's height with `set_mob_height()` (medium, shortest, dwarf, tallest, and some in between). Spacer heights are set through the same call.
2. Measure `getFlatIcon(human)` for each: the top opaque row, the bottom row and the number of opaque pixels. The sprite is 32 rows tall.
3. Take a real camera photo of a shortest-height human standing next to a medium-height one and read the photo's pixels.

Observed on master: the top opaque row of the flattened icon, by height setting, was 12 (medium) → 31, 10 → 30, 8 (shortest) → 29, 6 (dwarf) → 29, 14 → 32, 16 → 32, 18 (tallest) → 32. The dwarf's head was therefore only 2 rows below medium's, and its opaque pixel count was 310 against 320. These small differences come from the `pixel_z` offsets of some overlays; the displacement filters had no effect.

The camera photo on master was not compared before the fix; the baseline is the `getFlatIcon` numbers above.

## Cause

A human's height (spacer quirk, dwarfism and so on) is a displacement map filter on each whole-body overlay, using a mask from `icons/effects/cut.dmi` (`apply_height_filter()`, `code/modules/mob/living/carbon/human/human_update_icons.dm:806`, called at `:796` and `:938`), plus `pixel_z` offsets for upper and lower body overlays. Camera photos are built with `getFlatIcon()` (`code/modules/photography/camera/camera_image_capturing.dm:116` and `:122`; `code/__HELPERS/icons.dm:393`), which only composes icons, overlays and blends. The filters were never applied, so only the `pixel_z` part of the height showed.

## Fix

Commit "Fix issue 88650: photos ignore mob height (displacement map filters)", all in `code/__HELPERS/icons.dm`:

- A new `apply_displacement_filters(flat, filters_to_apply)` proc goes through an appearance's filters and, for each displacement filter that has a map icon, builds a new icon in which every pixel is taken from the source at an offset. The offset comes from the mask's red channel (horizontal) and green channel (vertical), scaled by the filter's `size`, with the filter's `x` and `y` shifting the mask. A channel value of 128 means no displacement. Green below 128 pulls pixels from above, so the image sinks (icon y runs bottom up).
- `getFlatIcon()` calls it in three places: on an appearance's own icon when it does not have `KEEP_TOGETHER` (the height code puts the filter on each child overlay), on the combined icon with its overlays when it does have `KEEP_TOGETHER`, and in the branch for appearances without overlays.
- Only `displace` filters are emulated. Alpha masks, blurs and the like are still ignored.

The cost is roughly 1,000 `GetPixel`/`DrawBox` operations per filtered overlay, paid only for appearances that have filters. This affects every `getFlatIcon()` user (photos, and previews made with it), which matches what the screen shows for them.

## Verification

After the rebuild, using the same measurement (top opaque row, medium 12 → dwarf 6): before 31 and 29, after 29 and 24; the dwarf's opaque pixel count went from 310 to 265 (medium 320 → 321). The full set after was `12:29, 10:28, 8:27, 6:24, 14:30, 16:31, 18:32`, with tall pixel counts of 329 to 353, monotonic with no obvious holes.

A real camera photo of a shortest-height human next to a medium one (96x96 picture read with `GetPixel`) had the short character's head starting at photo row 60-61 and the medium one's at row 63, about 3 pixels lower for the short one.

Not checked: how the photo or icon looks (it could not be rendered from the Lua editor; the numbers above are pixel measurements only); the photo before the fix; any other `getFlatIcon()` user; performance in a real round.

## Notes

- Uncertain: the direction and size convention of BYOND's displace filter was inferred from the masks in `cut.dmi` (a green value of 0 shrinks, 255 lengthens), and the measurements match that, but it was not compared with a real client's rendering. This is the main thing for a reviewer to check.
- Other filters (the title's "all filters?") are not emulated.
- `getFlatIcon()` is called in several places that were not examined; the added loop could be slow for many filtered overlays.
