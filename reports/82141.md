## Summary

The issue says saved pAI personalities are not saved and that loading takes many clicks. Saving and loading work on the server. The defect is in the candidacy window: its input fields copy the server's data once when the window opens, so after "Load" the fields keep their old (usually blank) contents. Pressing Save or Submit then sends those stale values, which overwrites the savefile and looks like "nothing was saved". The fix sends a load counter with the UI data and makes the window refresh its inputs whenever that counter changes.

## The bug

A player opens the pAI candidacy menu as an observer, fills in name, description and comments, and presses Save. Later they open the menu and press Load. Nothing appears in the fields, so they conclude the personality was never saved. One commenter on the issue reported needing to press Load twice to get the saved data to show.

## Reproduction

The server side was checked with admin tools; the UI symptom was not reproduced in a client.

1. In the Lua editor, create a human with a non-guest key (`tester`) and a `/datum/pai_candidate` for it.
2. Set a name, description and comments (Bob, desc, cmt), call `savefile_save`, then call `savefile_load` on a fresh candidate.
3. Both returned TRUE, and the fresh candidate had name Bob, description desc and comments cmt, read from the savefile `data/player_saves/t/tester/pai.sav`.

So persistence works for non-guest keys. For guest keys saving is refused on purpose ("You cannot save pAI information as a guest", `code/modules/pai/personality.dm`), which could be what some reporters hit.

The stale-field behaviour comes from reading the code. It was not seen in a client, because the test client used here does not run tgui's JavaScript.

## Cause

`PaiSubmit` (`tgui/packages/tgui/interfaces/PaiSubmit.tsx:26-31`) keeps the text boxes in React state:

```tsx
const { comments, description, name } = data;
const [input, setInput] = useState({ comments, description, name });
```

`useState` reads the server data only when the component first mounts. The "load" action (`code/controllers/subsystem/pai.dm:70`) loads the savefile into the candidate and calls `ui.send_full_update()`, so `data` does change, but nothing copies it into `input`, so the boxes still show what they showed before. Save and Submit use `input`, and the `save` and `submit` actions write the posted values to the candidate (`pai.dm` ui_act), so pressing Save after a Load saves the old values over the file, and Submit submits them. Pressing Load again cannot help, since the data it sends is identical.

The "double tap" comment on the issue is not explained by this reading; it may depend on client behaviour that was not examined.

## Fix

One commit, "Fix issue 82141: pAI candidacy window did not show loaded personality data":

- `code/modules/pai/candidate.dm`: new `load_revision` variable on `/datum/pai_candidate`, starting at 0.
- `code/modules/pai/personality.dm`: `savefile_load` increments it after reading the file.
- `code/controllers/subsystem/pai.dm`: `ui_static_data` includes `load_revision`.
- `PaiSubmit.tsx`: a `useEffect` keyed on `load_revision` copies `comments`, `description` and `name` from the server data into the input state.

A counter was used instead of keying the effect on the text values themselves because loading identical data must still overwrite what the player has typed since. Pressing Load with unchanged server data would otherwise do nothing.

## Verification

- The DM and tgui bundles built, and `bun run tsc` reported no errors.
- With Lua on the test server, `ui_static_data` returned `load_revision` 0, then 1, then 2 across repeated loads of identical data, with name Bob and comments cmt.

Not checked: the actual window behaviour. The input fields refreshing after Load was not seen in a real client, so it needs a check by someone running Dream Seeker or another real client. Also not checked: Save then Load through the UI, the guest case, and a savefile with an incompatible version.

## Notes

- Because `useEffect` also runs on first mount, the inputs are set once more with the same values when the window opens; this is harmless.
- `savefile_load` returns early (without incrementing) for guests, a missing file, or an incompatible version (which also deletes the file), so no refresh happens then.
- The issue is labelled "Needs Reproducing"; the part of it that can be reproduced is the UI refresh, which was not seen directly here.
