## Summary

The issue says that when a turf is replaced with `ChangeTurf`, signal handlers the new turf registers on itself in `Initialize` overwrite the handlers carried over from the old turf, because the two lists were merged with `LAZYOR`. On master `87b93338` this no longer happens: `ChangeTurf` now passes the old signal tables into the new turf's constructor, so `Initialize` adds to them instead of being merged afterwards. A test following the issue's steps kept both handlers.

## The bug

As filed (against an older commit): a handler registered on a turf for a signal such as `COMSIG_TURF_CHANGE` disappears after the turf is changed into a type that registers its own handler for the same signal in `Initialize` (the issue uses `/turf/open/water`, whose fishing setup does). The old handler is missing from `_listen_lookup`, and a second `ChangeTurf` does not fire it.

## Reproduction

The test followed the issue's "simple way", using the Lua editor on the test server:

1. On an iron floor turf, register a handler for `turf_change` with the Lua editor's `register_signal`.
2. Change the turf to `/turf/open/water` with `ChangeTurf` (called from a timer outside the Lua run).
3. Read `_listen_lookup['turf_change']` on the turf.

Observed on master: the turf was a `/turf/open/water` and `_listen_lookup['turf_change']` was a list of length 2, holding the Lua handler and water's own `COMSIG_TURF_CHANGE` handler. Nothing was overwritten. The Lua handler also fired for the first change. It reported an error, but that came from Lua resolving its reference to the turf to null in the middle of `ChangeTurf` and was a test artifact, not this bug.

Only one change was examined; the issue's step 4 (a second `ChangeTurf`) was not run separately.

## Cause

Cause of the issue as filed: the old `change_turf.dm` copied the old turf's `_listen_lookup` and `_signal_procs` and, after the new turf had run `Initialize`, merged them into the new turf's tables with `LAZYOR`. That does not deep-merge the two-level lookup (signal -> handlers), so an entry the new turf made for the same signal could replace the old one.

Master no longer does that:

- `code/game/turfs/change_turf.dm:108-112` copies the old tables and constructs the new turf with them: `new path(src, old_listen_lookup, old_signal_procs)`.
- `/turf/New` (`code/game/turfs/turf.dm:119-122`) assigns them to `_listen_lookup` and `_signal_procs` before calling the parent `New`, i.e. before `Initialize`. `RegisterSignal` in `Initialize` therefore adds to the existing tables with its normal merging logic.
- The old turf's own registrations are removed beforehand by `/turf/_clear_signal_refs` (`turf.dm:241`) during `Destroy`.

The agents' notes attribute this change to upstream PR #98038 (a fix for #91584). That attribution comes from the notes and was not re-checked against the PR itself.

## Fix

None. Nothing was changed.

## Verification

Only the reproduction above: both handlers were present after the change. Not checked: other signals or turf types besides `turf_change` and water; the old turf's own registrations being cleared correctly; the issue's proposed warning on a signal override.
