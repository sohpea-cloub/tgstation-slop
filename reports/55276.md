# #55276: datum/pipelines cause their contained atmos machinery to hard del

| | |
|---|---|
| Issues | [#55276](https://github.com/tgstation/tgstation/issues/55276): not reproduced directly; judged from the code to share its cause with [#55275](https://github.com/tgstation/tgstation/issues/55275) (see Notes) |
| Status | Unresolved for this issue on its own. No fix was committed for this unit. One unexplained GC failure of a vent pump was observed. |
| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 (MetaStation) |

## Summary

The issue reports that vent scrubbers (and other atmos components) attached to a `/datum/pipeline` fail garbage collection because the pipeline still holds a reference to them. Since the issue was filed, `nullify_node()` and `nullify_pipenet()` were reworked to remove a destroyed component from its pipeline's lists, and on master that path reads as correct. Deleting every vent and scrubber on the station left no hard deletes, but one vent pump that had been unwrenched after the pipe under it was rebuilt did fail GC with a reference count of 3. The reference that held it was not identified, so the bug is neither confirmed nor ruled out. No code was changed.

## The bug

As reported in the issue, a vent scrubber that was deleted stayed in memory. The reference finder on a reference-tracking build printed:

```
Found /obj/machinery/atmospherics/components/unary/vent_scrubber/on/layer2 [0x2009df5] in list World -> /datum/pipeline -> list.
```

The scrubber was therefore still sitting in one of a `/datum/pipeline`'s lists, and the garbage collector had to hard delete it. Players do not see this directly. It costs server time as a hard delete, and in the worst case it leaves a deleted machine reachable from a live pipeline. The last comment on the issue (2023-03-19) says the original cause was probably closed by #56202 but that the reporter was still seeing such hard deletes.

## Reproduction

The test server was a normal MetaStation round, with admin tools only. No reference-tracking build was used, so the only signal was the `unable to be GC'd` line the garbage subsystem prints when an object is still alive five minutes after `qdel`.

An earlier attempt used the Lua editor to `qdel`, deconstruct and rebuild the vents. It was discarded. The Lua state kept references to every object it touched, so almost everything it handled (vents, scrubbers, pipe fittings, manifolds, and two pipelines it had read) failed GC, which says nothing about the pipeline bug. Lua should not be used for this kind of test.

The second attempt avoided Lua:

1. Started a fresh round and joined as an Atmospheric Technician, so that real wrench clicks could be used.
2. With SDQL2, switched off four vents in Arrival Shuttle Hallway (`CALL set_on(0) ON /obj/machinery/atmospherics/components/unary WHERE ...` by z, x and y).
3. With a wrench, unwrenched and rebuilt (from the dropped fitting) the scrubber at 47,144 twice, and left it built.
4. Unwrenched the vent pump at 43,146 and rebuilt it from its fitting.
5. With SDQL2 (`CALL deconstruct(1) ON /obj/machinery/atmospherics/pipe WHERE ...`), took apart the supply manifold at 44,146 next to the vent, then rebuilt it with the wrench ("You fasten the air supply pipe fitting"). The vent's underlay showed as connected again.
6. Unwrenched the rebuilt vent a second time (about 10:09:03 server time) and left its fitting on the floor.
7. Ran `DELETE /obj/machinery/atmospherics/components/unary/vent_scrubber WHERE z == 2; DELETE /obj/machinery/atmospherics/components/unary/vent_pump WHERE z == 2` in SDQL2. The number of deleted objects was not seen, because the "SDQL query completed" line goes only to admin chat.
8. Waited more than five minutes and read the server log for `unable to be GC'd` lines.

Evidence:

- Exactly one GC failure was logged in the round, at 10:14:07:
  `GC: -- [0x202e3ef] | /obj/machinery/atmospherics/components/unary/vent_pump/on/layer4 was unable to be GC'd -- (ref count of 3)`
- No vent scrubber failed. No other vent pump failed. No atmos-related runtime appeared in `runtime.log`.
- The GC check happens 5 min 1 s after `qdel`, so the failing vent was deleted at about 10:09:06 or earlier, before the mass DELETE (which started at 10:09:19). Two vent pumps were deleted before then: the first one at 43,146 (unwrenched at 10:07:56, so it would have failed at about 10:12:57, and it was collected) and the rebuilt vent at the same tile (unwrenched about 10:09:03, matching the 10:14:07 failure). The failing object was therefore almost certainly the vent that had been built from a fitting onto a pipe that had been taken apart and rebuilt, then unwrenched.
- The log was read at 10:15:05, only about 45 seconds after the mass DELETE's own five-minute mark, so late failures from that delete could in principle have been missed.

This was reproduced by the player-style actions (wrench clicks) plus SDQL2 for the manifold and the bulk delete. The failure was seen once and was not repeated.

## Cause

Not determined. The code paths that should prevent the reported reference exist on master:

- `/obj/machinery/atmospherics/Destroy()` calls `nullify_node(i)` for every port (`code/modules/atmospherics/machinery/atmosmachinery.dm:109-111`).
- The components override (`code/modules/atmospherics/machinery/components/components_base.dm:143-147`) calls `nullify_pipenet(parents[i])`. `nullify_pipenet()` (`components_base.dm:174-198`) removes the machine from `reference.other_atmos_machines` (line 183) and from `reference.require_custom_reconcilation`, drops its gas mixtures from `other_airs`, clears its own `parents` entry, and deletes the pipeline if it has no members and no machines left.
- `/datum/pipeline/proc/merge()` (`code/modules/atmospherics/machinery/datum_pipeline.dm:170-188`) re-parents each component with `replace_pipenet()` and then empties the old pipeline's `members`, `other_atmos_machines` and `require_custom_reconcilation` before `qdel(parent_pipeline)`.
- `/datum/pipeline/Destroy()` (`datum_pipeline.dm:31-44`) calls `nullify_pipenet(src)` on each remaining component.

From this the straightforward case (delete a vent attached to a live pipeline) looks covered, and the bulk delete in the test agrees. The one failure involved a pipe that had been taken apart and rebuilt under the vent, so it ran through the pipeline destroy, rebuild and merge code, which is where a stale reference could remain. Reading the code did not find which reference.

Candidates that were considered but not tested:

- A leftover reference in a pipeline (the reported cause).
- The player's client having last clicked or hovered the vent, or the `do_after` progress bar created by the unwrench. The first vent that was unwrenched also had a progress bar and was collected, which argues against the progress bar alone.

## Fix

None. No change was made.

## Verification

Nothing to verify, since there was no fix. Not checked:

- Whether the one GC failure repeats. It was seen once.
- What held the vent. This needs a build with reference tracking (for example `-DREFERENCE_TRACKING_STANDARD`) and a repeat of steps 3 to 6, then reading the hard-delete log.
- The number of objects the mass DELETE removed.
- Other component types (heat exchangers, pumps, filters and so on). Only vent pumps and scrubbers were exercised.

## Notes

- The issue is grouped with #55275 ("datum/pipeline hard-deletes its contents") as having the same cause. A later review of the code, without a game test for this issue, concluded that the two share a root cause (a chain through a dead pipeline, described in #55275's write-up), and that the fix prepared for #55275 addresses it. That fix is part of #55275's unit, not this one, and its effect on the single vent pump failure seen here was not tested. Please treat that as a hypothesis, not a measured result.
- The original cause was addressed by #56202 (a re-PR of #55457, making component nodes nullify properly). The 2023 comment on the issue says hard deletes were still seen afterwards. The single failure above is consistent with that, but not enough to confirm it.
- Duplicate pipe pieces on one tile (mentioned by an early commenter) also break pipeline building; none were looked for here.
