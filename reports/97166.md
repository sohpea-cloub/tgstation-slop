# #97166: Chameleon projector disguises take the projector's plane instead of the scanned object's plane

## Summary

`/obj/item/chameleon/proc/make_copy()` saves the scanned object's appearance but then overwrites the plane with `initial(plane)`, which is the projector's own plane, offset for the z level the projector was on when it scanned. The disguise therefore renders on the wrong plane: always the wrong base plane, and on multi-z maps also the wrong z offset when the disguise is made on a different level than the scan. The fix stores the scanned object's unoffset plane and applies the z offset when the disguise is created. A second commit fixes #94719, where blood trails and footprints are built from `vis_contents`, which an appearance copy does not carry, so the disguise came out almost invisible.

## The bug

### #97166 and #91426: wrong plane

A disguise made with the chameleon projector is supposed to look like the scanned object. Instead it is drawn on the projector's plane. For ordinary floor decals the difference is visible: the decal's plane is lower than the projector's (on the single-level test map, -6 against -4), so the disguise is drawn above where the real decal would be.

On a multi-z map the baked-in plane is also offset for the z level of the projector at scan time. If the disguise is then created on another level, it sits on the plane stack of the level it was scanned on. #91426 describes that situation: scanning dried blood and activating the projector on a different elevation gave a disguise that was "blackened or completely unseeable". I did not look at rendered output for it (see Verification); the explanation is from the code and from the plane values below.

### #94719: near-invisibility from blood trails

Scanning a dried blood trail produced a disguise that was nearly invisible. The trail is a `/obj/effect/decal/cleanable/blood/trail_holder` whose visible pieces are separate objects in its `vis_contents`. `atom.appearance` does not include `vis_contents`, so the copy has the holder's own (almost empty) appearance and none of the pieces.

## Reproduction

All of this was done with the Lua editor on a private server, calling `make_copy()` and `toggle()` on the projector directly. The projector's normal use (click an object with it, then use it in hand) was not exercised through the UI; those two procs are what the click and the use-in-hand call.

### Plane (#97166)

1. Start a round on a single-level map (max plane offset 0) and open the Lua editor as an admin.
2. Spawn a human, a `/obj/item/chameleon` and a `/obj/effect/decal/cleanable/blood/splatter` on one turf.
3. Call `projector:make_copy(decal, human)`, then `projector:toggle(human)`, and read the plane of `projector.active_dummy`.
4. Observed on master: the disguise's plane was -4, the same as the projector's plane (-4), while the decal's plane was -6. The layer matched the decal (10018 on both).

### Multi-z (#91426)

The same sequence was run on master only on the single-level map above. The multi-z case was run after the fix (see Verification); no multi-z "before" measurement was taken. The cause in the next section accounts for it: the saved plane is computed with `SET_PLANE_EXPLICIT(..., src)`, so it is offset for the z level of the projector at scan time and nothing re-offsets it when the disguise is created.

### vis_contents (#94719)

1. Spawn a human, a chameleon projector and a `/obj/effect/decal/cleanable/blood/trail_holder` on one turf.
2. Call `add_dir_to_trail()` on the holder twice, once with SOUTH (2) and once with EAST (4), to give it two trail pieces.
3. Call `make_copy(holder, human)` and `toggle(human)`.
4. Observed on master: the holder had 2 objects in `vis_contents`; the disguise had 0 in `vis_contents` and 1 overlay (the holder's own).

## Cause

`code/game/objects/items/devices/chameleonproj.dm:70-77`:

```dm
/obj/item/chameleon/proc/make_copy(atom/target, mob/user)
	...
	var/obj/temp = new /obj()
	temp.appearance = target.appearance
	temp.layer = initial(target.layer) // scanning things in your inventory
	SET_PLANE_EXPLICIT(temp, initial(plane), src)
	saved_appearance = temp.appearance
```

The line above the last one is the defect. `initial(plane)` is evaluated on `src`, the projector, not on `target`, so the projector's plane is used. `SET_PLANE_EXPLICIT(temp, ..., src)` (`code/__HELPERS/_planes.dm`) then offsets that plane by the multi-z offset of the projector's turf. The `layer` line right before it correctly uses `initial(target.layer)`, so the plane line looks like a copy-paste slip where `target.` was left out.

On top of that, `/obj/effect/dummy/chameleon/activate()` (`chameleonproj.dm:126-127`) does `appearance = saved_appearance` and never adjusts the plane for the z level the dummy is created on. So even with the right base plane, a plane that had been offset at scan time would be wrong when the disguise is made on a different level. The offset has to be applied at activation, not at scan.

For #94719: the trail pieces are added with `vis_contents += new_trail` in `add_dir_to_trail()` (`code/game/objects/effects/decals/cleanable/blood.dm:451`). `target.appearance` does not include `vis_contents`, so `make_copy()` loses them.

## Fix

Two commits on `fix/97166`.

**"Fix issue 97166: Chameleon projector disguises use the scanned object's plane, offset for the z level they're made on"**

- In `make_copy()`, replaced `SET_PLANE_EXPLICIT(temp, initial(plane), src)` with `temp.plane = initial(target.plane)`, which stores the scanned object's own base plane with no offset.
- In `/obj/effect/dummy/chameleon/proc/activate()`, added `SET_PLANE_IMPLICIT(src, plane)` right after `appearance = saved_appearance`, which offsets the saved plane for the z level the dummy is created on.

Storing the unoffset plane and offsetting at activation avoids storing the plane per z level. It also matches the default `saved_appearance` set in `Initialize()` (`initial(butt.appearance)`), which is also an unoffset plane.

**"Fix issue 94719: Chameleon projector disguises keep the scanned object's vis_contents as overlays"**

- In `make_copy()`, each atom in the target's `vis_contents` is turned into a `mutable_appearance` with `plane = FLOAT_PLANE` and `layer = FLOAT_LAYER` and added to the temp object's overlays before the appearance is saved. The target is cast to `/atom/movable` for this because `vis_contents` is not defined on `/atom` (the first attempt failed to compile for that reason).

The alternative mentioned in the #94719 thread was a signal that lets objects add overlays to, or modify, the chameleon appearance. That was not tried; baking `vis_contents` into overlays in `make_copy()` is local to the projector and needs no changes to blood, footprints or other `vis_contents` users.

## Verification

Checked on a rebuilt test server running the fixed code:

- **Plane, multi-z.** On the MultiZ Debug map (max plane offset 2), a splatter was scanned on z2 and the projector activated on z2, z3 and z4 (a human on each). The projector's plane was -218 (offset for z2) and the scanned decal's plane was -220. The disguise planes were -220, -113 and -6 respectively, each equal to the plane of a fresh blood splatter spawned on the activation level. The disguise sat on the activation level (z2, z3, z4).
- **vis_contents.** With a trail holder having 2 trail pieces, the disguise had 3 overlays after the fix (1 before), with 0 `vis_contents`, as expected.

Not checked:

- Nothing was rendered or viewed with a client. #91426's "blackened or invisible" symptom and #94719's near-invisibility were not looked at before or after; the checks above are plane values and an overlay count.
- The baked trail overlays were not examined visually. In particular it is not known whether the transforms and directions of diagonal trail pieces (`add_dir_to_trail()` sets turns on them) come out right in the disguise.
- The multi-z "before" case, as noted above.
- The normal player flow (click with the projector, use in hand) through the UI.
- Moving a disguised user across z levels with the disguise active.
- Real dried-blood trails left by a damaged mob; a trail holder was built by hand.
- The existing unit tests and the other `vis_contents` users (footprints were not scanned).

## Notes

- `initial(target.plane)` reads the type's default, not the target's current plane. A target whose plane was changed at runtime is copied with its type default. This is the same convention the `layer` line already uses (and the reason for its comment about scanning things in the inventory), but it is a design choice a maintainer could weigh against copying the current plane with the offset removed.
- Copying `vis_contents` children as `FLOAT_PLANE` / `FLOAT_LAYER` overlays flattens them into the disguise at scan time; later changes to the original trail are not reflected, which is also true for the rest of the appearance.
- #91426 was classed as a duplicate of #97166 on the strength of the code path and the plane values above, not on a reproduction of its exact scenario (dried blood scanned on one elevation, projected on another).
- In #94719's thread, one comment questions whether it should be possible to disguise as a decal at all. The fix does not change what `can_copy()` allows.
