# #96407: `*faint` makes the player say a stray "Zzz..." after fainting

## Summary

Typing `*faint` in tgui-say printed "faints." followed by a spurious line in which the player "says" `Zzz...`. The emote puts the user to sleep while the submitted tgui-say entry is still considered open, so the sleep status effect's force-say speaks whatever is left in the box. The fix marks the say window as closed as soon as an entry is submitted.

## The bug

The issue reports a chat message like `Unknown command: -zzz...` after typing `*faint`, every time. On master the message observed was `<Name> says, "Zzz..."` directly after the emote line. If the box held other text, the force-say would append the sleep phrase to it (for example `x-Zzz...`), which gives the look of the message interrupting itself.

## Reproduction

1. On the test server, join as an Assistant.
2. Reproduce what the client does when a player types in tgui-say: send the say window the `open` message for channel Say, then an `entry` message with `*faint`. (The `say` command used directly bypasses tgui-say and only shows "faints.", so it does not show the bug.)
3. Evidence before the fix, in chat: `<Name> faints.` (emote) followed by `<Name> says, "Zzz..."`.

The tgui-say messages were sent by hand rather than by a player typing, so the real client was not used.

## Cause

`handle_entry` in `code/modules/tgui_input/say_modal/speech.dm` (the `type == "entry"` branch, about line 132) delegates the speech but leaves `window_open` TRUE until the client later sends its "close" message.

While the entry runs, `/datum/emote/living/faint` (`code/modules/mob/living/emote.dm`) calls `SetSleeping`. The sleeping status effect's `on_apply` runs `try_force_say()` (`code/datums/status_effects/debuffs/debuffs.dm:47`), which calls `human.force_say()` (`speech.dm`, around line 94). Its guard `IS_UNCONSCIOUS_OR_CRIT(src) || !client?.tgui_say?.window_open` does not stop it: the mob's `stat` has not updated yet and `window_open` is still TRUE. So the (empty) box is force-said with the status effect's alternate phrase "Zzz...".

## Fix

One commit, "Fix issue 96407: *faint no longer force-says over its own submitted entry". In `handle_entry`, for `type == "entry"`, it sets `window_open = FALSE` before `delegate_speech`, with a comment that the window is already on its way to closing. Anything the entry does, such as knocking the user out, therefore no longer force-says the box that was just submitted.

## Verification

After the fix, the same open and entry sequence produced only `<Name> faints.`, and the mob still fell asleep (the Asleep and Blind alerts appeared).

Not checked: other stun or sleep sources while text is being typed. That path is unchanged: `force_say` still works while the window is open and nothing has been submitted.

## Notes

The force-say chance and duration conditions in `try_force_say` (`debuffs.dm:51`) are random, so other emotes or commands that stun the user as part of a submitted entry would have been affected by the same stale `window_open` state; the fix covers them all because it is in the shared entry handler. This is inferred from the code and was not tested.
