| | |

| Status | Fixed; targeting checked in game, actual pull on a ball's movement not measured |

## Summary

The power beacon (`/obj/machinery/power/singularity_beacon`) only handled objects with the singularity component, which tesla energy balls do not have, and nothing anywhere assigned an energy ball's `target`, so the energy ball's movement toward a target was dead code. The fix keeps a global list of energy balls; an active beacon now sets itself as the `target` of every energy ball on its z-level and clears it on deactivation. The pull is weak by existing design (see Notes).

## The bug

A player wrenches a power beacon onto a powered wire, activates it, and lets a tesla loose. The beacon has no effect on the ball. The reporter tried up to nine beacons at once. Energy balls were attracted by the earlier "singularity beacon" because the tesla used to be a singularity subtype. Later changes moved the beacon to look for the singularity component, which the tesla never got.

## Reproduction

The bug was established from the code; no pre-fix run in game was done.

1. Grep the code for assignments to `energy_ball.target`: there are none. The beacon's `process()` iterates only `GLOB.singularities`, a list of singularity components, and energy balls are not on it.
2. (Setup used for the post-fix checks, same on master) With admin tools (Lua editor), spawn a `/obj/machinery/power/singularity_beacon` and set `energy_used` to 0 and `active` to 1 directly (a normal `Activate` needs 1500 W of surplus on a wired power network), then spawn an `/obj/energy_ball` 8 to 20 tiles away.

On master the ball's `target` therefore stays null.

## Cause

`code/game/machinery/syndicatebeacon.dm` `process()` (around lines 85-106) loops over `GLOB.singularities` and sets `singulo_component.target = src`; `Deactivate()` (line 33) clears it the same way. Nothing handles `/obj/energy_ball`:

```dm
for(var/datum/component/singularity/singulo_component as anything in GLOB.singularities)
	var/atom/singulo = singulo_component.parent
	if(singulo.z == z)
		singulo_component.target = src
```

`/obj/energy_ball` has a `target` var (`code/modules/power/tesla/energy_ball.dm:33`) that `move()` reads (lines 104-105: `if (target && prob(10)) move_dir = get_dir(src, target)`), but no code sets it. Energy balls are also not tracked in any global list, so the beacon had no way to find them.

## Fix

Commit "Fix issue 74069: power beacons now attract tesla energy balls":

- `code/_globalvars/lists/objects.dm`: new `GLOB.energy_balls`, typed to `/obj/energy_ball`.
- `code/modules/power/tesla/energy_ball.dm`: non-miniball energy balls add themselves in `Initialize` and are removed (and have `target` nulled) in `Destroy`. The `target` var is now typed `atom` and documented.
- `code/game/machinery/syndicatebeacon.dm`: in `process()` the beacon sets `ball.target = src` for energy balls on its z-level, on the same 8-second cooldown as for singularities, and announces the ball's distance and direction as it does for singularities. `Deactivate()` clears `target` on any ball targeting this beacon.

Orbiting mini-balls are not tracked, since only the main ball moves.

## Verification

In game on the test server, with the setup from Reproduction, after rebuilding:

- The ball's `target` became the beacon. The beacon said "The energy ball is now 18 standard lengths away to the southwest" and later reported 21, as the ball drifted.
- Calling `Deactivate()` on the beacon cleared the ball's `target`.
- A first test beacon was destroyed by the ball's zaps; its `Destroy` calls `Deactivate`, which also cleared the target.

Not checked: that the ball actually drifts toward the beacon over time (the movement code was not changed and no distance trend was measured); normal activation on a real powered wire (activation was forced by setting variables); more than one beacon or balls on other z-levels; mini-ball behaviour.

## Notes

- **The pull is weak.** `move()` steers toward the target only with `prob(10)` per step, otherwise it picks a random direction (plus some momentum toward shocked things). The beacon is a slight bias on a random walk. The probability was not tuned; a maintainer may want it higher if beacons are meant to be reliable.
- A comment on the issue says the singularity `target` var "doesn't work". That was not tested; `singularity.dm` around line 238 does read it.
- A 2025 comment notes the tesla engine is no longer in the game's standard setups, but tesla energy balls still exist and can be released.
