## Summary
Felinid code can pick "None" for the ears and tail, but a block in `/datum/species/human/felinid/on_species_gain` replaced "None" with the default cat parts every time a felinid was created without `pref_load`. The block was meant only for humans turned into felinids by purrbation. The fix moves it into `purrbation_apply`. #86128 (lizard snout bodyshape) and #91911 (slimeperson blood duplication) did not reproduce on master.

## #85108: felinid "None" ears / tail

### The bug
Felinids created with randomized features (for example `/mob/living/carbon/human/species/felinid`) should sometimes get no cat ears or no tail, since "None" is one of the randomizable accessories. In practice they always had cat ears and a tail.

### Reproduction
1. In a running round, open the Lua editor.
2. Spawn 40 `/mob/living/carbon/human/species/felinid` mobs.
3. For each, read `dna.features["ears"]` and `dna.features["tail_cat"]`, the ears organ type, and whether a tail organ exists.

Observed on master: 0 of 40 had "None" ears, 0 of 40 had "None" tail, and all 40 had the cat ears organ and a tail.

### Cause
`code/modules/mob/living/carbon/human/species_types/felinid.dm:27-32`:
```
/datum/species/human/felinid/on_species_gain(..., pref_load, ...)
	if(!pref_load) //Hah! They got forcefully purrbation'd. ...
		if(human_who_gained_species.dna.features[FEATURE_TAIL_CAT] == SPRITE_ACCESSORY_NONE)
			... = get_consistent_feature_entry(...)
		if(human_who_gained_species.dna.features[FEATURE_EARS] == SPRITE_ACCESSORY_NONE)
			... = get_consistent_feature_entry(...)
```
The comment says this is for forced purrbation, but the condition `!pref_load` is true for every `set_species` call that is not loading a preference, including the one that runs when a `species/felinid` mob is created. Feature randomization can pick "None" (any `natural_spawn` accessory is eligible), but this block then overwrote it with a default. The "None" ears check right after it (`felinid.dm:34-36`, which swaps in plain human ears) therefore never fired for these mobs.

### Fix
One commit, "Fix issue 85108: felinids can spawn with None ears and tail again". It deletes the `if(!pref_load)` block from `on_species_gain` and adds the same two checks to `purrbation_apply` (the `ishumanbasic` branch), just before `set_species(/datum/species/human/felinid)`. Purrbation, the only case that needs the forcing, behaves as before; every other path keeps whatever the features say.

### Verification
With the fix built on the test server:
- Spawning 40 `species/felinid` mobs gave 4 with "None" ears (those had the plain ears organ; the other 36 had cat ears) and 22 with "None" tail (18 had a tail).
- `purrbation_apply` on 10 humans whose ears and tail features were set to "None" turned all 10 into felinids, and their features were no longer "None".

Not checked: the real purrbation entry points (the mass purrbation secret, the toggle) were not exercised, only the proc called directly from Lua; visual appearance was not inspected.

### Notes
- The felinid ear and tail preferences set `can_randomize = FALSE` (`code/modules/client/preferences/species_features/felinid.dm`), so randomizing a character in character setup still never picks "None". That was left unchanged.
- A comment on the issue says the feature was not updated for the newer cat ear types; that was not investigated.

## #86128: organ bodyshapes not applied on spawn
Not reproduced. The issue says a lizard's `BODYSHAPE_SNOUTED` is only applied after an organ change. On master, with the Lua editor:
- a `/mob/living/carbon/human/species/lizard` had `bodyshape` 9 (`HUMANOID | SNOUTED`);
- a human given `set_species(lizard)` with `pref_load` true and with it false both had 9;
- three humans set to the lizard species through a preference datum and `apply_prefs_to` printed `bodyshape` 9 on the run where the preference was stored as `"lizard"`. (An earlier attempt wrote the species path rather than the serialized id, so the pref stayed human and gave bodyshape 1; that was a test error.)

The reporter may have seen a downstream or older behaviour. Real latejoin/roundstart spawn and the quickspawn path were not tested.

## #91911: slimepeople gain extra blood from their own jelly
Not reproduced. Using a syringe on both a slimeperson and a human, with godmode on:
- drawing 15u: blood 560 to 545, 15u in the syringe, for both species;
- injecting 15 x 1u back: blood 545 to 560, identical for the human.

Blood is conserved 1:1. Giving a slimeperson (blood 300, 30 brute damage) 30u of slime jelly by `trans_to` gave blood 309 and brute 15, with 8.3u still in the reagents. The blood rise (about 9) could come from ordinary regeneration, and was not isolated. The reported healing matches `/datum/reagent/toxin/slimejelly/on_mob_life` (`code/modules/reagents/chemistry/reagents/toxin_reagents.dm:329`), which heals any mob that metabolizes it; that looks like intended reagent behaviour rather than a slimeperson-only bug. The reporter's "inject x15, make body, repeat" loop (the body-split mechanic) was not run, and the issue says it was seen downstream, so downstream-only behaviour cannot be ruled out.
