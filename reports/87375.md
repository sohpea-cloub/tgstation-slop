# #87375: Pirate shuttle external airlocks have no access restriction

| | |
|---|---|
| Issues | [#87375](https://github.com/tgstation/tgstation/issues/87375): verified and fixed (the airlock access was checked; a pirate opening the door was not) |
| Status | Fixed on the branch, with open design and risk questions (see Notes) |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/87375 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The external airlocks of the pirate ships use `/obj/machinery/door/airlock/external/glass/ruin`, a subtype that is explicitly access-free, and no ship map gives them an access requirement, so anyone can walk in. The fix adds the Syndicate access mapping helper to those airlocks on six of the ships (20 airlocks). Pirate, syndicom and silverscale ID trims already carry Syndicate access. It has not been confirmed that every pirate crew's ID does, and the issue may describe an intentional design.

## The bug

Anyone can walk up to a pirate ship, bump the door and have it open. The reporter notes that this lets random players board and kill the pirates, and says it happened at least on the Deserter ship. A comment on the issue says pirates have their own IDs.

## Reproduction

On master `87b93338`, using admin tools:

1. Start a round and observe.
2. Jump to empty space on the same z-level and use the "Map Template - Place" verb to place the default pirate ship template (`pirate_default`).
3. Run an SDQL query on the placed airlocks: `SELECT /obj/machinery/door/airlock/external/glass/ruin WHERE z == 2 MAP [x, y, req_access, req_one_access]`.

Evidence: the four ship airlocks, at (27,24), (27,22), (33,24) and (33,22), had `req_access` and `req_one_access` both null. With no access requirement, a door opens for anyone.

This shows the missing restriction in the airlock data. No player was walked up to the door in game.

## Cause

`/obj/machinery/door/airlock/external/glass/ruin` is declared in `code/game/machinery/doors/airlock.dm`, under the heading "Access free external airlocks" (around lines 2349-2357), with no body. The pirate shuttle maps in `_maps/shuttles/pirate/*.dmm` use this type for their external airlocks and add no access to it. `ex_interdyne` sets `req_access = null` explicitly. The airlocks are therefore open to everyone by construction.

The IDs the crews spawn with do carry Syndicate access in the cases that were read. The `pirate` trim and the syndicom trims, which the outfits in `code/modules/antagonists/pirate/pirate_outfits.dm` use, have `ACCESS_SYNDICATE` (`code/datums/id_trim/ruins.dm:108`, `code/datums/id_trim/syndicate.dm`).

## Fix

One commit, **"Fix issue 87375: pirate ship external airlocks require Syndicate access"**. It adds `/obj/effect/mapping_helpers/airlock/access/all/syndicate/general` to every `external/glass/ruin` airlock in six ship maps:

| Ship map | Airlocks |
|---|---|
| `pirate_default` | 4 |
| `pirate_silverscale` | 4 |
| `pirate_ex_interdyne` | 2 |
| `pirate_irs` | 4 |
| `pirate_geode` | 4 |
| `pirate_grey` | 2 |

That is 20 airlocks. Map changes only; no code is touched.

Left unchanged:
- `pirate_siren` and `pirate_medieval`: the crews spawn with no ID (`id = null`), and the medieval ship has no airlocks.
- `pirate_dutchman`: its only door is an inner vault door.
- Interior doors on all ships: they are left as hatches and were not examined beyond the entrance.

Using Syndicate access reuses what pirate and syndicom IDs already have, rather than adding a new pirate-specific access.

## Verification

After the change (the map files are re-read when a template is placed, so no rebuild was needed), the default pirate template was placed again with the same verb and the same SDQL query. The four new airlocks, at (67,22), (67,24), (73,24) and (73,22), had `req_access` set to "syndicate".

Not checked:
- A pirate with a real ID opening the door, or a non-pirate being refused.
- The other five ships. Their change is the same line in the same kind of door, but it was not placed in game.
- Whether the `ex_interdyne` doors take the helper correctly: they set `req_access = null` explicitly in the map, and this was not tested.
- The Grey Tide crew's chameleon ID and the geode ship's black ID. Their trims come from the base pirate outfit, and it was not tested that those cards actually get `ACCESS_SYNDICATE`. If one does not, that crew cannot open its own doors.

## Notes

- Risk: a crew whose ID lacks Syndicate access (Grey Tide and the geode "lustrous" crew are the doubtful ones) would be locked out of its own ship's external doors. This should be checked before merging.
- Design question: the ships may have been left open on purpose (the inputs do not say). The only comment on the issue says pirates have their own IDs and gives no maintainer decision.
- No upstream pull request addressing this was found in the inputs.
