## Summary

When the traitor antagonist datum is removed, it deletes the first uplink it finds on the mob's body. A pen or PDA uplink that is not on the body (dropped, in a locker, held by someone else) keeps working, and so does an uplink that is not the first one found. The fix has the datum remove the uplink it was given, wherever it is, and makes `take_uplink()` also forget the uplink's location and code memories. #74896 (Take Uplink wiping the account number) does not happen on current master.

## #74892: Removing traitor does not remove the uplink

### The bug

An admin removed a player's traitor status and the player still had their uplink, a pen uplink. The reporter suggested checking whether this is specific to pen uplinks and noted that the implant uplink would be the easiest to test.

### Reproduction

All steps used the Lua editor on the test server.

1. Implant uplink (the default, for a human without a client): add the traitor datum, then remove it. `find_syndicate_uplink()` returned nil afterwards, so this case already worked.
2. Pen uplink: possess a human holding only a pen, which gives a pen uplink. Add the traitor datum, drop the pen on the floor, then remove the traitor datum.

Result on master for step 2: before removal the pen had a syndicate uplink, and after removal the pen still had it ("after_removal_pen_has=syndicate uplink"). The mind's uplink memory also stayed (one memory left).

The reporter's exact round (April 2023 code) was not checked. The dropped-pen case is the one that reproduced.

### Cause

`/datum/antagonist/traitor/on_removal()` (`code/modules/antagonists/traitor/datum_traitor.dm:90`) called `owner.take_uplink()`. That proc (`code/datums/mind/antag.dm:250`) is just `qdel(find_syndicate_uplink())`, and `find_syndicate_uplink()` (`antag.dm:226`) searches only `current.get_all_contents()` and returns the first uplink component it finds. An uplink on an item that is not part of the body is never seen. If the body holds more than one uplink, the one deleted may not be the traitor's own. The datum already keeps a weak reference to its uplink (`uplink_ref`, set at `datum_traitor.dm:59`), but removal did not use it.

### Fix

One commit: "Fix issue 74892: removing the traitor datum now removes its uplink wherever it is". It makes three changes:

- `take_uplink()` takes an optional uplink argument and falls back to `find_syndicate_uplink()` when none is given. It deletes that uplink and wipes both `/datum/memory/key/traitor_uplink` and `/datum/memory/key/traitor_uplink/implant`.
- `/datum/antagonist/traitor/on_removal()` calls `owner.take_uplink(uplink_ref?.resolve())`.
- The traitor panel's `takeuplink` handler in `code/datums/mind/_mind.dm` loses its own `wipe_memory_type(.../implant)` line, because `take_uplink()` now does it.

The memory wipe is by type, so unrelated memories stay.

### Verification

After rebuilding, with a pen on the floor and a traitor datum added, the sequence gave: before, the pen had a syndicate uplink and 2 memories; after removing the traitor datum, the pen had no uplink and 1 memory; after re-adding the datum, the pen had an uplink and 2 memories again; after the panel's Take Uplink, the pen had no uplink and 1 memory. The remaining memory was an unrelated account memory that was kept on purpose. The runtime log was not reported on for this unit.

Not checked: an uplink in a locker or on another mob, a PDA or implant uplink through the fixed path, a second uplink on the body, and the real traitor panel UI (the panel path was exercised by calling the procs from Lua).

## #74896: Take Uplink wipes every memory

### The report

Using Take Uplink in the traitor panel after removing someone's traitor status deleted everything from their memory, including their account number. The reporter said there was no selective memory deletion proc.

### Result: not reproduced

On master the panel's `takeuplink` handler (`code/datums/mind/_mind.dm`, near line 425) calls `take_uplink()` and then `wipe_memory_type(/datum/memory/key/traitor_uplink/implant)`, so it removes one memory type only. In the test above, an unrelated account memory survived `take_uplink()` (memories went from 2 to 1). A selective wipe-by-type proc exists, so the described behaviour was already fixed.

There was one leftover: only the implant variant of the uplink memory was wiped, so the plain uplink memory stayed. The commit for #74892 wipes both, as described above.

Not checked: other memory types after Take Uplink.
