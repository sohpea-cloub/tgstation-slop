## Summary

`/obj/item/toy/crayon/spraycan` is a subtype of `/obj/item/toy/crayon`, and two systems treat anything crayon-shaped as a writing tool. The PDA lists `/obj/item/toy/crayon` as something that goes in its pen slot, so using a spray can on a PDA tries to insert it and fails with the "too big!" balloon alert instead of painting (#84328). The crayon's writing-implement details also apply to spray cans, so the silent spray can, which carries the `tool_renaming` element, opens the rename prompt on a folder instead of painting it (#92105). The fix excludes spray cans from the PDA pen slot, stops them reporting as writing implements, and makes `tool_renaming` stay silent for tools that are not writing implements.

## The bug

### #84328

Using a spray can on a PDA does not paint it. The player sees the balloon alert "too big!" and the can stays in their hand. This happens in harm and help intent alike (as the reporter noted). The reporter's testmerge list included a tool-use ordering change, but the cause below is in master code.

### #92105

Using a spray can on a folder opens a rename prompt instead of painting the folder ("it just thinks you're trying to rename it, despite spraycans not being a writing tool").

## Reproduction

Everything was done on master with admin tools: the Lua editor to spawn a human, give the admin control of it, spawn the items, uncap the spray can, and call `melee_attack_chain(human, target)` (non-combat mode) to do the equivalent of clicking the target with the item in hand. The click itself was not simulated through the interface.

### #84328

1. Spawn a human, a spray can (`/obj/item/toy/crayon/spraycan`) and a PDA (`/obj/item/modular_computer/pda`). Uncap the can.
2. Use the spray can on the PDA.
3. Observed: the floating balloon text "too big!" appeared over the user, and the can stayed in the user's hand. No paint was applied.

### #92105

1. Spawn a human, a folder, a plain spray can, and a silent spray can (`/obj/item/toy/crayon/spraycan/mimecan`). Uncap the cans.
2. Use the plain spray can on the folder. Observed: "You coat the folder with spray paint." On this build the plain can already painted the folder, so the report as written did not reproduce for it. The issue is from July 2025 and may have been correct for an older version; this was not checked.
3. Use the silent spray can on the folder. Observed: a "Customization" list prompt (Rename / Reset) opened, i.e. the rename flow for the folder. This is the bug in #92105.

## Cause

Both symptoms come from spray cans inheriting crayon behaviour.

**PDA pen slot.** `code/modules/modular_computers/computers/item/pda.dm:51-55` defines the static `contained_item` list, which includes `/obj/item/pen`, `/obj/item/toy/crayon` and `/obj/item/flashlight/pen`. `item_interaction()` (line 152) starts with:

```dm
if(!is_type_in_list(tool, contained_item))
	return NONE
if(tool.w_class >= WEIGHT_CLASS_SMALL) // Anything equal to or larger than small won't work
	user.balloon_alert(user, "too big!")
	return ITEM_INTERACT_BLOCKING
```

`is_type_in_list` matches subtypes, so a spray can passes the first check. Spray cans are `WEIGHT_CLASS_SMALL` (crayons are tiny), so the second check blocks the interaction with "too big!" and the can never gets to paint the PDA. `add_context()` (line 135) uses the same check, so the screentip also offers "Insert" for a spray can.

**Folder rename.** `code/game/objects/items/crayons.dm:628` gives every crayon `get_writing_implement_details()`, which returns a writing mode, so spray cans count as writing utensils. In `Initialize` (line 218), crayons that cannot change colour get `/datum/element/tool_renaming`, with the comment "This makes sure that spraycans do not rename stuff instead of painting". The silent spray can sets `can_change_colour = FALSE`, so it gets the element. In `code/datums/elements/tool_renaming.dm:33-36`, `attempt_rename()` returns early unless the target has `UNIQUE_RENAME` (folders do, `code/modules/paperwork/folders.dm:9`) and `user.can_write(tool)` passes, and `can_write()` passes for a spray can because it is a writing utensil. The element then starts the rename flow and the rename flow wins over the spray can's own `interact_with_atom`.

(`can_write()` itself, `code/modules/mob/mob.dm:1330`, prints "You can't write with ..." when the tool is not a writing utensil, unless `silent_if_not_writing_tool` is set. That warning is relevant to the fix below.)

## Fix

Two commits.

**"Fix issue 84328: spraycans no longer get inserted into a PDA's pen slot"** (`pda.dm`). A new proc `can_insert_item(obj/item/tool)` returns FALSE for `/obj/item/toy/crayon/spraycan` and otherwise falls back to `is_type_in_list(tool, contained_item)`. `item_interaction()` and `add_context()` use it, so spray cans fall through (`NONE`) to the normal painting interaction and the screentip no longer offers "Insert". Ordinary crayons are unaffected. The list entry `/obj/item/toy/crayon` was left alone so that crayons and its other subtypes still fit.

**"Fix issue 92105: spraycans are not writing implements, so they paint folders instead of renaming them"** (`crayons.dm`, `tool_renaming.dm`).

- `/obj/item/toy/crayon/spraycan/get_writing_implement_details()` now returns `null`, so spray cans are not writing utensils. This is what the `tool_renaming` comment already assumed.
- `tool_renaming.dm` now calls `user.can_write(tool, silent_if_not_writing_tool = TRUE)`. Without this the element would, once spray cans stop being writing utensils, print "You can't write with the silent spraycan!" every time the can is used on a renameable object, before the click falls through to painting. This was observed during testing before the second change was added.

An alternative would have been to remove `tool_renaming` from the silent spray can only. Making spray cans not writing implements was chosen because it matches the existing comment and also handles the PDA and any other code that checks `IS_WRITING_UTENSIL` or `get_writing_implement_details()`. See Notes for the trade-off.

## Verification

Checked on the test server with the fix built, same method as the reproduction:

- Spray can on a PDA: "You coat the pda with spray paint." The PDA's `inserted_item` was still its original pen (nothing was swapped).
- Silent spray can on a folder: "You coat the folder with spray paint." with no "can't write" warning (this was the case after the final change; with only the first #92105 change the warning appeared).
- Pen on a folder: still opens the rename prompt (not a regression).
- Red crayon on a PDA: still swaps pens ("swapped pens"), so ordinary crayons keep fitting the pen slot.

Not checked: the PDA screentip text, other spray can subtypes (for example the slippery/lube can, bananium or other special cans), painting other renameable objects, using the can on paper, and any interface-level click (as opposed to the proc call).

## Notes

- Behaviour change: with `get_writing_implement_details()` returning `null`, spray cans can no longer be used as a writing implement through that path. Anything that wrote on paper with a spray can by way of the writing-implement code will now use the can's own painting interaction (`interact_with_atom`) instead. Whether anyone relied on writing on paper with a spray can was not investigated; a maintainer who wants to keep that should prefer removing `tool_renaming` from the silent spray can only and keep the PDA change.
- The plain spray can on a folder worked on master, so #92105's description only matches the silent spray can here. The "any click with a spraycan" wording in the issue was not reproduced for the plain can.
- Only the PDA's `contained_item` list was adjusted. Other places that accept `/obj/item/toy/crayon` by type (not checked) may have the same issue with spray cans.
