## Summary

#88713 said a table could be built on a tile it should not be allowed on by crafting the frame elsewhere and dragging it there. On master, finishing a table from a frame checks the tile for blocking objects both before and after the build delay, so the machine case from the report is refused. One related oddity remains: windows, windoors and railings do not block it. #97378 said a machine frame cannot be anchored on a table; it anchored without problems in testing, and the likely cause of the report is unproven.

## #88713: dragging the frame bypasses the tile checks

### The bug

The frame craft refuses a blocked tile (the craft has a density check), but a table frame itself is not dense and can be dragged anywhere. The reporter's video showed a table finished on a tile with a machine on it. Comments on the issue say the real problem is that edge objects block construction, and that it should be consistent either way.

### Reproduction

1. On the test server, using admin tools, spawn a vending machine and a table frame on the same tile.
2. As a human holding an iron sheet, click the frame.

Observed on master: floating text "Robust Softdrinks is in the way!" and no table was made. The issue's machine case is therefore not reproducible.

### Cause (why it works)

`table_frame/item_interaction()` (`code/game/objects/structures/table_frames.dm:66-82`) loops over every `/obj` on the frame's tile and refuses with "[object.name] is in the way!" if the object is dense without `IGNORE_DENSITY`, or has `BLOCKS_CONSTRUCTION`. It does this before the 2 second `do_after` and again after it, in case something was placed meanwhile. Objects with `PASSTABLE` are skipped. This check is also what matters for dragged frames, since the frame craft's own density check applies only where the frame is made. In the shallow clone the check appears under the commit message "PR #98038" (the exact upstream commit was not looked up).

### Remaining oddity (not the reported case)

A table can still be finished on a tile that has a window. Windows, windoors and railings have `IGNORE_DENSITY` and `BLOCKS_CONSTRUCTION_DIR`, which the table frame check does not consider, and the frame craft does not use the directional craft check either, so the frame and the table agree about edge objects. Issue comments say this is the only way to put windoors on tables, so nothing was changed. This is a design decision for maintainers.

### Fix

None.

### Verification

Only the vending machine case above was run in game. Other blockers (for example other dense machines, structures or `BLOCKS_CONSTRUCTION` objects) were read in code only.

## #97378: machine frames can't be anchored on tables

### The bug

Reporter steps: make a machine frame on a table, add wires, wrench it; it fails to anchor.

### Reproduction attempt

1. As a human with a wrench on the test server, spawn a table and then a machine frame (`/obj/structure/frame/machine`) on it.
2. Wrench the frame.

Observed: "You begin securing..." for about 4 seconds, then "You secure the machine frame." Unsecuring and securing again also worked. Wiring was not involved: the wrench check (`can_be_unfasten_wrench()` in `machine_frame.dm`, around line 265) only refuses when the circuit needs the frame anchored. (Wires were not added in the test.)

### Why it works

`default_unfasten_wrench()` (`code/game/objects/objs.dm:293`) refuses with "You fail to secure ..." when `is_blocked_turf(exclude_mobs, source_atom = src)` is true. A table is dense, but tables carry `datum/element/climb_walkable`, which gives a dense thing that enters or is created on the tile the `TRAIT_ON_CLIMBABLE` trait and a permit through `COMSIG_ATOM_TRIED_PASS`. In the Lua editor, `table:CanAllowThrough(frame)` was 0 but `table:CanPass(frame)` was 1, and `is_blocked_turf` returned 0.

### Likely reason for the report (unproven)

A dense frame that lacks `TRAIT_ON_CLIMBABLE` would be blocked. This could happen after a table is flipped and unflipped: `flip_table()` removes the element, which strips the trait from things on the tile, and `unflip_table()` adds the element back but not the trait (`code/game/objects/structures/tables_racks.dm`, roughly lines 100-140), or by any way a frame gets onto the tile without the signals that add the trait. A flipped table throws things off its tile, so the test frame was thrown away and this could not be shown cleanly. The reporter's exact steps (table type, how the frame got there) are needed.

### Fix

None.

### Verification

See the reproduction attempt. Not checked: a flipped and restored table, wired frames, and any table type other than the default.
