## Summary

#63258 (December 2021) reports that the simple_animal floorbot ignored untiled floor, tried to make arrests, and did not place custom (catwalk) tiles. That mob no longer exists on master: PR #86084 replaced it with the basic-mob repairbot, which has a different, behaviour-tree based AI. Only a spot check of the replacement was done: three repairbots loaded with catwalk or iron tiles re-tiled bare plating, filled a hole in space and laid catwalk after an explosion, and none attempted an arrest. The issue can be closed as obsolete. The check also showed a few repairbot limitations (see Notes) that are separate from this report.

## The bug

As reported, floorbots set to tile hull, place tiles, place custom tiles, patrol and repair damage were loaded with catwalk tiles and released. Some ignored bare floor, some tried to arrest people, and none worked on a bombed-out area. The reporter also recalled bots getting stuck on tiles that could not be reached (for example because a machine stood on top).

None of that applies to current master. The floorbot code is gone, and only `bot_announcement.dm` and `construction.dm` remain under `code/modules/mob/living/simple_animal/bot/`. The path-update script `tools/UpdatePaths/Scripts/86084_replace_floorbots.txt` maps `/mob/living/simple_animal/bot/floorbot` to `/mob/living/basic/bot/repairbot`. Cargo's emergency crate now contains repairbots (`code/modules/cargo/packs/emergency.dm:27`).

## Reproduction

The original report could not be reproduced because the mob it describes does not exist. The replacement was checked as follows, on a freshly started test server with an admin observing:

1. Using the Lua editor, spawned three `/mob/living/basic/bot/repairbot` in the Central Primary Hallway. The first held 60 catwalk tiles, the other two 60 iron floor tiles each; all three also held 50 iron sheets. All had the default flags (all five repair toggles on, including replace tiles) and were on with autopatrol.
2. Detonated `explosion(c, 0, 1, 2)` in the hallway, and in addition used `ScrapeAway()` on five floor tiles to leave bare plating, so the hallway had a mix of plating and holes to space.
3. Printed the area as a character map through the Lua editor at intervals and read each bot's tile count.

Observed:
- Within about five minutes all of the scraped-away plating had been re-tiled: the catwalk bot laid catwalk, the others laid iron floor. The hole to space in the hallway was floored over. Tile counts in the bots dropped accordingly (for example 60 to 57, 60 to 58).
- No bot attempted an arrest. A repairbot only saluted a passing security bot (Beepsky).
- After the work was done the bots stood idle with no target. The test did not show any bot stuck on an unreachable tile.

The server's runtime viewer showed a number of runtimes during the session; their text was not captured, and they were not tied to the repairbots. They may be from the Lua editor calls used to set up the test.

This was a spot check, not a full test of every repairbot behaviour.

## Cause

There is no defect to locate for the issue as filed: the code it was filed against was deleted and replaced. For reference, the relevant repairbot code on master:

- Tile replacement is a behaviour-tree search: `valid_plateless_turf` (`code/modules/mob/living/basic/bots/repairbot/repairbot_ai.dm:127-161`) looks for `/turf/open/floor/plating` when the replace-tiles flag is set and the bot carries a tile stack. It skips turfs with windows or grilles, plating the bot cannot see within 5 tiles, and anything in `/area/space` or `/area/station/maintenance`.
- Breach repair is the `breached` variant (`repairbot_ai.dm:163-175`), which needs the fix-breaches flag and a stack of `/obj/item/stack/tile/iron` specifically.
- The tiling itself is done by `stack_to_use.melee_attack_chain(src, target)` in `repairbot.dm` (around line 215).

## Fix

None. There was nothing to fix for this issue.

## Verification

Checked in game: the repairbot behaviours listed above (re-tiling plating with iron and catwalk tiles, flooring a space hole, no arrests).

Not checked: repairbots on the other maps or z-levels; long-term patrol over the whole station; emagged behaviour; broken or burnt tile repair beyond reading the code; the old floorbot (it cannot be spawned any more).

## Notes

These are side findings from the check, not part of #63258. They may be worth a separate issue:

- Broken and burnt tiles are not searched for. A burnt or broken open turf is welded only if it happens to become the bot's target (`repairbot.dm:170-173`), and the search in `repairbot_ai.dm:127-161` only looks for bare plating.
- Replacing an existing floor with a custom tile ("swap tiles", which the issue text mentions) is not implemented: the search filter is plating only (`repairbot_ai.dm:131-132`).
- A bot carrying only catwalk tiles never fixes space breaches, because the breach search requires iron tiles (`repairbot_ai.dm:166-172`).
- Plating in maintenance is deliberately skipped by the tile search (`repairbot_ai.dm:155-160`), the reverse of the old floorbot's "only good in maint" complaint.
- After the explosion, bots stayed idle for about two and a half minutes behind firedoors that had closed. Target search uses a radius of 5 (`code/datums/ai/bots/bot_subtrees.dm:11`). Patrol movement appears to use the `jps/bot` movement type with `maximum_length = 25` (`code/datums/ai/movement/ai_movement_jps.dm:54-57`), while the longer `travel_to_beacon` type (`AI_BOT_PATH_LENGTH`, line 67-68) was not found in use by the patrol tree. A closed firedoor blocked their path planning in this test. With the firedoors opened by an admin the bots resumed patrol. A direct path lookup from one bot to a beacon 4 tiles away returned no path with limits of 25, 60 and 120, so path planning around that spot may have another obstruction; this was not investigated further. These are suspicions from a short observation and were not confirmed as defects.

Related: #62880, #63016 and #62878 (earlier floorbot fixes mentioned in the issue thread), and PR #66451 (pathing through railings, suggested in the last comment).
