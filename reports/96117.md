# #96117: Security holobarriers in the Glacial Devourer bitrunning domain are invisible

| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The report says the two security holobarriers at the entrance of the Glacial Devourer (wendigo) bitrunning domain cannot be seen but still block players. On the test server the domain's mapped barriers had exactly the same appearance data as a barrier spawned on the station, and the station barrier is visible by design. No code or map defect was found. The cause is most likely on the client side or in the test merges active in the reporter's round, but this was not confirmed, because nothing was rendered visually.

## The bug

The issue (client 516.1662) shows a screenshot of the domain entrance and says there is a barrier on each side of it. Players get caught on barriers they cannot see and die. The reporter's round had two test merges: one reworking Heretic spells and rituals (#95796), and one that refactors the inventory UI to be "completely datum and vis_contents-based" (#95998). The issue has no comments.

## Reproduction

The invisibility was not reproduced. Only data was compared, not what a client draws.

1. On the test server, use the SDQL2 query tool to load the domain template `wendigo` (the Glacial Devourer). It contains two mapped `/obj/structure/holosign/barrier` objects, at 92,33 and 95,33 on the domain's z-level.
2. Read their variables with SDQL2. Both have `alpha` 0, `plane` -4, `layer` 2.9, `invisibility` 0 and `appearance_flags` 769. There is no plane offset on any z-level (`SSmapping.max_plane_offset` is 0), so `MUTATE_PLANE()` leaves the plane unchanged.
3. In the Lua editor, spawn a `/obj/structure/holosign/barrier` on the station (z 2) and another on the domain's z-level, and dump each together with its managed vis overlay.

Results: the barrier spawned on the station and the one spawned in the domain were identical. Parent: alpha 0, plane -4, layer 2.9. Vis overlay: plane -4, layer 4.1, alpha 255, invisibility 0, flags 837, icon state `holosign_sec`, direction 2, with one entry in the parent's `vis_contents`. The vis overlay cache (`SSvis_overlays.vis_overlay_cache`) held a single `holosign_sec` entry shared by all barriers, so the mapped barriers use the same overlay object as the spawned ones.

## Cause

No server-side cause was found.

An alpha of 0 on the parent is intended. `create_vis_overlay()` (`code/game/objects/structures/holosign.dm:71`) sets `alpha = 0` on the sign and draws the visible part as a vis overlay at `ABOVE_MOB_LAYER` with `KEEP_APART|RESET_ALPHA` (line 78), so the overlay is not affected by the parent's alpha. The comment there says "you see mobs under it, but you hit them like they are above it". The domain map places the barriers as plain `/obj/structure/holosign/barrier` objects (`_maps/virtual_domains/wendigo.dmm:127` and `:207`) with no overrides, so they go through the same code as every other barrier.

The visible part of a holosign therefore depends entirely on the client drawing a vis_contents child of an alpha-0 parent with `RESET_ALPHA`. If that fails to render, every holosign would be affected, not only these two. This points at the client or at the second test merge (#95998), which changes inventory UI to use vis_contents, rather than at the map. This is a hypothesis; it was not tested in a real client.

## Fix

None. No change to `holosign.dm`, `vis_overlays.dm` or the map is justified by the data. A possible workaround (a non-vis_contents overlay, or a small non-zero alpha on the parent) would change every holosign and was not tried.

## Verification

Checked: the equality of appearance data between the domain's mapped barriers and a station barrier (above).

Not checked: any visual rendering of the barriers, either by screenshot or in a real client. The tool used for rendering was considered unreliable for vis_contents, and the session ran out of calls. Not tried: a real quantum server load of the domain through the bitrunning machinery (the template was loaded directly); the two test merges named in the issue; client version 516.1662 specifically (the test server's BYOND build was used).

## Notes

- To settle this, someone should look at the domain in a real client at 516.1662 or newer, with and without the vis_contents inventory UI change, and also at a barrier made with a holosign projector on the station.
- The `vis_overlay_cache` entry is shared and the overlay is cleaned up by `SSvis_overlays` when unused. This was not seen to matter here, but a barrier whose managed vis overlay was removed would be invisible in exactly the way reported. The data from the two loaded barriers showed their overlays present.
