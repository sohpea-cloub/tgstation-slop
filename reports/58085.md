## Summary

The 2021 report says a tgui window closed by the player pops open again if someone else then uses the same machine (vending machine purchase, R&D research, ID inserted into the civilian bounty console, an AI using the communications console). On current master, closing a vending, R&D and bounty console UI and then updating those machines (including a real vend by another mob) did not reopen anything. The code has no path that reopens a closed UI for a bystander. The one thing not tested is the real client's own close button and window pooling, which is client-side JavaScript; the report most likely describes the older tgui implementation, since reworked.

## The bug

As reported: the player stands next to a Civilian Bounty Console, vending machine, or R&D console, opens its UI and closes it. When another person then uses the machine (inserts an ID, buys something, does research, or the AI uses the communications console), the player's window opens again by itself.

## Reproduction

Attempted on master with admin tools; the bug did not appear.

1. Started a test round and joined as an observer; opened the Lua editor.
2. Spawned a cola vending machine, an R&D console (`/obj/machinery/computer/rdconsole`) and a civilian bounty console (`/obj/machinery/computer/piratepad_control/civilian`), plus two humans nearby. Gave the admin's ckey to one human so it was controlled by a real client.
3. Opened each UI for that human by calling `ui_interact()` on the machine from Lua. The Vending, Techweb and CivCargoHoldTerminal tgui windows opened.
4. Closed the windows by sending the same messages the tgui client sends: `close` for the vending machine and the R&D console, `suspend` for the bounty console. Each window reported closed.
5. Triggered updates that the report describes, with the other human (no client) as the actor:
   - Vending: set `all_products_free` and called `vend()` with a real product record. The machine said "Thank you for shopping" and the vend sound played.
   - R&D and bounty: called `SStgui.update_uis()` and `update_static_data_for_all_viewers()` on each machine, and (R&D) changed `stored_research.research_points`.
6. Waited 4 seconds and listed the open tgui windows. Only the Lua editor was open; none of the closed windows had come back.

Limits: the "other person" actions were simulated (a direct `vend()` call; UI refresh calls) rather than a second player inserting an ID or starting an experiment. The AI and communications console case was not tried. The window closes were sent as tgui client messages, not by a real client pressing the X button.

## Cause

No defect was found. What the code does after a close:

- `code/modules/tgui/tgui.dm:366-369`: both the `suspend` and `close` messages from the client call `close()`. (The client's X button also runs the `uiclose` verb, `code/modules/tgui/external.dm:186`, which calls `SStgui.force_close_window()` at `code/controllers/subsystem/tgui.dm:148`.)
- `code/modules/tgui/tgui.dm:133-150`: `close()` sets `closing`, releases the window and calls `SStgui.on_close()`.
- `code/controllers/subsystem/tgui.dm:349-358`: `on_close()` removes the UI from the subsystem's lists and from `src_object.open_uis`.
- `code/controllers/subsystem/tgui.dm:218-230`: `update_uis()` only walks `src_object.open_uis`, so a closed UI is not touched. The periodic `process()` (`tgui.dm:306`) returns immediately when `closing` is set.
- The machines' `ui_interact()` procs (for example R&D at `code/modules/research/rdconsole.dm:193` and the vending machine in `code/modules/vending/vendor/ui_data.dm:9`) only run for the mob that interacted; a grep found no code that calls `ui_interact()` on nearby mobs when a machine's state changes. The old `updateUsrDialog()`/`updateDialog()` helpers, which did that for HTML-based UIs, no longer exist in the tree.

One path could in principle reopen a UI: `SStgui.try_update_ui()` (`code/controllers/subsystem/tgui.dm:169`) closes a UI whose status has dropped to `UI_CLOSE` or below and returns null, and callers then create a new `/datum/tgui`. But `open()` (`tgui.dm:85`) refuses when status is below `UI_UPDATE`, and that function already carries a `FIXME` about a related "paper bug". It does not apply to a UI the player closed.

## Fix

None; there is nothing to fix on master that this testing could find.

## Verification

Checked in game: vending, R&D and bounty UIs, closed with `close`/`suspend`, did not reopen after an update, a real vend, or a research-point change.

Not checked:

- The real BYOND client behavior (X button, pooled-window reuse, window ids reused by another UI). That logic runs in the client's JavaScript, which these tests did not run.
- A second human player using the machine; an ID inserted into the bounty console; an actual research experiment.
- The AI using the communications console.
- Other tgui machines.

## Notes

- The issue is from March 2021, has no comments, and is still open. It was written before the tgui rework that removed the HTML-dialog update path, so it likely no longer applies. If it does still happen, it would most likely be a client-side window pooling problem and would need a reproduction with a real client and the round's tgui log.
- Candidate for closing as obsolete unless someone can reproduce it on current master.
