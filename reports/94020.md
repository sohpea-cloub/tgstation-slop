## Summary

Using a crowbar or welding tool on an open, empty trophy display case never put it on display, because the case's `crowbar_act` and `welder_act` handle the click before `item_interaction` can insert the item. The fix makes those two procs step aside when the case is open, empty and unbroken. A second commit makes trophy cases refuse mob holders, which persistence cannot store (#78376). The general persistence limitation behind #70029 (only the typepath is saved) was not changed, as it needs a data-format change.

## The bug

**#94020.** Attempting to put a trophy into the Library's display case did nothing. The reporter's steps were: take a curator key, use it on the case to unlock historian mode, then use the wanted item on the case. The reporter did not say which item they used. On the test server, plain items such as a bike horn could be placed in an open empty case, but tools (a pocket crowbar, a welding tool) were attacked or used as tools instead of being displayed.

**#78376.** A mob (a mothroach in a holder) put into a trophy case came back in a later round as an invisible item named "Bugged mob".

**#70029.** Items put into a trophy case come back in a later round with their default icon (the reporter's screenshots show the wrong icon after the round change; a comment on the issue says the same).

## Reproduction

### #94020
1. Using admin tools, take control of a human in the Library, next to the four trophy display cases. Spawn a pocket crowbar (and a welding tool) and an ID with access.
2. Open a trophy case by using the ID on it. It is open and empty.
3. Use the pocket crowbar on the case.

Result on master: "You attack the trophy display case with the pocket crowbar"; nothing was inserted. The same flow with a bike horn gave "You put the bike horn on display". Tools are the failing class.

Not exactly the issue's steps: the steps in the issue (key first, case still closed) would never insert anything. The case must be ID-opened and empty first. If a holographic persistent trophy is in the case, an empty-hand click on the open case dumps it before anything new can be inserted. This was determined by reading the code and from the in-game flow above; the reporter's actual item is unknown.

### #78376 and #70029
Reproduced by reading the code only. The persistence round trip (saving, restarting, looking at the case next round) was not run.

## Cause

### #94020
`base_item_interaction` in `code/game/atom/atom_tool_acts.dm:12-15` calls `tool_act` first (when not in combat mode) and returns early if it returns anything. In `code/game/objects/structures/displaycase.dm`, `welder_act` (`:161`) and `crowbar_act` (`:181`) always return a value for those tools: `welder_act` reports "already in good condition" or repairs, and `crowbar_act` skips to attack on cases with `alert` set, otherwise opens or closes the case. The code that inserts a showpiece, `if(open && !showpiece) insert_showpiece(...)` in `item_interaction` (`:128-141`), is therefore never reached for a crowbar or welder.

### #78376
`save_trophy` in `code/controllers/subsystem/persistence/trophies.dm:118-121` stores only `showpiece.type` (`data.path`). On load, `set_up_trophy` (`displaycase.dm:378`) builds an `/obj/item/showpiece_dummy` from `initial()` of the name, description, icon and icon_state of that path. A mob holder's initial name is "Bugged mob" and it has no initial icon, so it comes back invisible and misnamed.

### #70029
The same mechanism: any item whose name, icon or icon_state differs from its initial values (dynamic icons) is shown with the initial ones.

## Fix

Two commits on [fix/94020](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/94020).

**"Fix issue 94020: put tools in an open empty trophy case instead of using them on it."** Adds `/obj/structure/displaycase/proc/accepts_showpiece_tool()`, returning `open && !showpiece && !broken`. `welder_act` and `crowbar_act` now return `NONE` first when it is true, so `item_interaction` runs and inserts the tool. Closed, occupied and broken cases behave as before.

Trade-off: a crowbar can no longer close an open, empty case (an ID still can).

**"Fix issue 78376: refuse mob holders in trophy display cases."** `/obj/structure/displaycase/trophy/insert_showpiece` now refuses `/obj/item/mob_holder` with "This doesn't belong in this kind of display." and returns TRUE. This is the simple option suggested by the reporter; the maintainer commenting on the issue noted that it would not help other items that don't survive the typepath-only format (a drink turning into an empty glass bottle, holochips with generated icons).

No commit for #70029. A real fix would store name, icon and icon_state in the trophy data, which changes the JSON format and needs a migration for existing saved trophies. That is a design decision for maintainers.

## Verification

On the rebuilt test server, with a possessed human in the Library:
- Open empty case, pocket crowbar: "You put the pocket crowbar on display." The case gained a crowbar overlay.
- A second open empty case, welding tool: "You put the welding tool on display."
- A real mothroach holder (made via `mob_try_pickup`) on an open case: "This doesn't belong in this kind of display." and the holder stayed in hand.
- Crowbar on a closed case: unchanged ("You pulverise the trophy display case with the pocket crowbar").

Runtimes in `runtime.log` (null `held_w_class`, `WrapAdminProcCall`) came from the Lua test setup (a bare `/obj/item/mob_holder` spawn and setting a ckey), not from the fix.

Not checked: broken-case and occupied-case behaviour in game (argued from the condition only); the persistence round trip, before or after; the reporter's actual steps with a curator key and historian mode; other display case types that use `crowbar_act`/`welder_act`, beyond the shared base proc.

## Notes

- Open question: whether a crowbar closing an empty open case matters. Players can still close with an ID.
- Usability: putting an item in a trophy case takes ID-open, clear any holographic trophy, insert, close, then a curator key to set the plaque. #78376 notes this is not documented anywhere.
- #78376 also mentions an unescaped apostrophe in persisted captions; this was not examined.
- #70029 and #78376 share one root cause, the typepath-only persistence format. Refusing mob holders removes the worst symptom only.
