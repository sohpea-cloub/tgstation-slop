# #96153: Mapped requests consoles lose announcement and ore-update abilities when deconstructed and rebuilt

| | |
|---|---|

| Status | Reproduced on master; fix written and checked in game |
| Fix branch | [fix/96153](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/96153) |

## Summary

Requests consoles that mapping helpers give the "can send announcements" or "receives ore updates" capability lose it when deconstructed, because deconstruction drops a plain wallframe that knows nothing about those settings. The fix gives the wallframe two matching variables, fills them in when the console is deconstructed, and applies them when the frame is attached, as `/obj/item/wallframe/flasher` does.

## The bug

The issue only says (title) that a head's requests console loses its announcement status after being deconstructed and placed back. In practice a head of staff's console that could make announcements, once taken down and rebuilt, no longer shows the announcement function. The same applies to the Quartermaster-style ore update setting.

## Reproduction

1. Start a round and use the Lua editor to take a mapped console with `can_send_announcements = 1` (the Captain's Desk console).
2. Call `deconstruct(true)` on it, spawn a `/obj/item/wallframe/requests_console`, and attach it to a wall with `interact_with_atom(wall, human)`.
3. Result on master: the new console had `can_send_announcements = 0`.

## Cause

Mapped consoles get their abilities from `/obj/effect/mapping_helpers/requests_console/announcement` and `.../ore_update` (`code/modules/mapping/mapping_helpers.dm:1397-1429`), which set the variables once at mapload. `/obj/machinery/requests_console/on_deconstruction` (`code/game/machinery/requests_console.dm:533`) did only:

```dm
new /obj/item/wallframe/requests_console(loc)
```

The frame has no record of the flags, so the console built from it (`auto_name`) starts with both `FALSE`.

## Fix

Commit "Fix issue 96153: requests consoles keep announcement and ore update abilities when rebuilt", all in `code/game/machinery/requests_console.dm`:

- `/obj/item/wallframe/requests_console` gets `can_send_announcements` and `receive_ore_updates` variables, both `FALSE` by default.
- `on_deconstruction` creates the frame and copies the console's two values onto it.
- A new `after_attach` override copies the values onto the console that is built.

This mirrors how the flasher wallframe carries its state. Consoles built from a fresh frame, with no flags, behave as before.

## Verification

On a test server with the fix built:

- Deconstructing the Quartermaster's Office console left a frame whose SDQL2-listed variables were `can_send_announcements = 1` and `receive_ore_updates = 1`.
- Attaching that frame (`interact_with_atom` returned success) produced a console with both values 1.
- A frame without flags (a plain console; Virology's was tried) still built a console with both 0.

Not checked: using the console's announcement UI after the rebuild, or deconstructing with a screwdriver and wrench by hand rather than the proc call. Only the announcement and ore-update flags were checked, not the other helper-set data.

## Notes

- Not changed: a rebuilt `auto_name` console takes its department name from the area it is placed in. A map-named console whose area name differs (for example "Captain's Desk" in an area named CentCom Administrative Office) therefore changes name on rebuild. The assistance, supplies and information lists are keyed by department, so they follow the area's name.
