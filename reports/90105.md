All three issues concern the data the orbit menu sends to ghosts (`code/modules/mob/dead/observer/orbit.dm`). The checks read that data directly with the Lua editor (the output of `ui_static_data` on the orbit menu datum) rather than looking at the interface, because the test setup could not render the tgui front end.

## Summary

The fix branch has two commits. The AI's camera eye was filed under "NPCs" because the eye has no mind; it is now classified by the AI that controls it (#52402). The two backseat mobs of a split personality passed the orbit menu's mind check and were listed next to the body (three entries in total); they are now excluded (#76990). #90105 (antagonists without an `antag_hud_name` send a null icon state, which used to render as the revolutionary icon) is not fixed here: the blob case was already fixed upstream, and the Orbit UI has since been rewritten so that a null icon state shows no icon.

## The bug

- **#90105:** an antagonist that appears in the orbit menu but has no `antag_hud_name` sent a null `icon_state`, and the old front end drew the first state of `antag_hud.dmi` next to the name, which is the revolutionary icon.
- **#52402:** for an AI, only the core was in the Alive section; the AI eye was listed under NPCs.
- **#76990:** a person with a split personality showed up as three people in the orbit menu.

## Reproduction

### #90105
1. With the Lua editor on the test server, give a mob antagonist datums that have no `antag_hud_name` and read the orbit menu's `ui_static_data`. Using `/datum/antagonist/ert` (Emergency Response Officer) gave an entry "Security Officer Zimmer | Emergency Response Officer | antag_hud.dmi | nil", i.e. the icon file is set and the icon state is null. The domain ghost actor and bitrunning glitch antagonists were identified in the code as having the same property.
2. Blob and infection already send `icon_state = "blob"` (`code/modules/antagonists/blob/blob_antag.dm:10`, from upstream PR #90103).
3. The visible effect was not reproduced. The current Orbit interface (`tgui/packages/tgui/interfaces/Orbit/OrbitItem.tsx`) defines `validIcon = !!icon_state && icon_state !== 'hudunknown'` (line 26) and only renders the job icon when valid (line 39), so a null state shows nothing. The Orbit UI rewrite (upstream PR #98038, 2026-10-06) is where the old behaviour went away. This was read from the code; no real client was used to confirm.

### #52402
1. Turn a human into an AI (`AIize`) and read the orbit menu data.
2. Observed on master: the entry "AI (AI Eye)" was in the NPC list. The eye has a null `mind`, which `ui_static_data` treats as an NPC (`orbit.dm:98`, `if(isnull(mob_poi.mind))`).

### #76990
1. Give a human the split personality brain trauma and set the state after a personality swap (body's mind is B, the stranger backseat's mind is B, the owner backseat's mind is A and carries the ckey). The swap code sets this up in `code/datums/brain_damage/split_personality.dm` (`switch_personalities`); the state was set directly with the Lua editor rather than waiting for a swap in play.
2. Read the orbit menu's `ui_static_data`. Observed on master: three entries ("alive: Splitty McSplit" plus two further entries labelled "(2)" and "(3)").

## Cause

- **#90105:** `get_antag_data` copies `antag.antag_hud_name` into `serialized["icon_state"]` (`orbit.dm:170`) with no fallback. Antagonists without one send null. Whether that shows a wrong icon is up to the front end.
- **#52402:** `ui_static_data` decides on `isnull(mob_poi.mind)` (`orbit.dm:98`). The AI eye mob never has a mind, so it goes to NPCs, and the name, job and antagonist data are never read from the AI behind it.
- **#76990:** `switch_personalities` assigns `mind` between the body and the backseat mobs directly (for example `new_backseat.mind = owner.mind`, `owner.mind = current_backseat.mind`). The backseat mobs therefore keep minds and pass `validate_mob_poi`'s `!mind && !ckey` check (`orbit.dm:300` onward), so they are listed as separate people.

## Fix

**"Fix issue 76990: split personality backseats no longer show up as extra people in the orbit menu"**
`validate_mob_poi` returns FALSE for `/mob/living/split_personality`. They are backseats of a body that is already orbitable.

**"Fix issue 52402: the AI eye is listed with the AI in the orbit menu, not under NPCs"**
Adds `/datum/orbit_menu/proc/get_mind_holder(mob)`, which returns the controlling AI for an AI's main eye (`ai.eyeobj == eye`) and the mob itself otherwise. `ui_static_data` uses it for the mind check, `client`, `name`, living data and antagonist data. A malf AI's eye would therefore go to the antagonists section. Multicamera picture-in-picture eyes, which are not the AI's main eye, are unchanged.

No commit for #90105.

## Verification

- #76990: after the fix and a rebuild the same setup produced one entry only.
- #52402: after the fix, with an AI that had a mind: "alive: AI name=AI job=AI icon_state=borg" and "alive: AI (AI Eye) name=AI job=AI icon_state=borg". The malf case was not tested; it follows from the code.
- No runtimes were noticed in the runtime log.
- Not checked: any visual output of the Orbit interface (no client), the Orbit UI behaviour for #90105, and the multicamera eyes.

## Notes

- The Alive and antagonist section counts now include both the AI core and its eye. The #52402 comment asked for the eye not to be counted twice in the alive total. That is not handled by this change.
- For #90105, a defensive default on the server side (a generic icon or skipping `icon_state`) was not added, since the new front end already guards against null.
- Related upstream: PR #90103 (blob HUD name) and PR #98038 (Orbit UI rewrite).
