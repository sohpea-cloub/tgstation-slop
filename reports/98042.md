## Summary

Several reports describe a player's action buttons vanishing, usually after dragging them around or resetting their positions. Two defects in the HUD code were found. First, `can_use()` on an action button treats a deleted button (one with no `linked_action`) as usable, so a drag-and-drop of such a button put it into one of the HUD's action groups. A dead button there fails garbage collection, and the null left in the group's list makes `refresh_actions()` runtime partway through, so the buttons after it keep a null `screen_loc` and are not drawn. Second, dropping a floating button onto the button palette hid the palette's "Show Buttons" toggle, so the action appeared to vanish. Three small commits fix these.

## The bug

What players report:

- #98042: action buttons were offset to the left. After resetting them a few times, and then once more with an oxygen tank equipped, every button except the internals one vanished.
- #75578: after taking off an EVA suit all of a miner's buttons were dragged on top of each other. A reset by shift-click then made them all vanish. They still occupied their slots (new actions made the bar grow) but were invisible. Only an admin respawn fixed it. Another player lost one button. A comment on the issue showed a hard delete of an action button that left a `null` entry in an action group list. A later runtime in the same issue was `Cannot read null.mymob` in `save_position` while a button was being dropped.
- #94921: moving the top-left buttons, picking up a hierophant club and alt-click resetting made the buttons disappear. A second player confirmed the loss.
- #89809: dragging a floating action into the button palette made it disappear.
- #93422: dropping a deleted action button runtimes with `Cannot read null.mymob` in `save_position`. A comment called it "kinda intended behavior".
- #65965 (2022): a giant spider lost its web action after a number of respawns, and cult spells after the fourth overlap the fourth button. A later comment found runtimes reading `current_offsets` and could not reproduce them.

## Reproduction

All steps were done as an admin on a test round as an Assistant, with the Lua editor to set things up and SDQL2 to call procs. The deleted-button cases were set up with admin tools rather than by a natural gameplay sequence.

### #93422 (reproduced on master)

1. Join as an Assistant, spawn an oxygen tank and a flashlight and put them in hand, so there are several listed action buttons.
2. In the Lua editor, `qdel` one of the buttons in `hud_used.listed_actions.actions`.
3. With SDQL2, simulate the client delivering the drop of the dead button: `CALL mouse_drop_dragged(null, null, null, null, null) ON /atom/movable/screen/movable/action_button WHERE gc_destroyed`. (This took about 18 seconds to run.)
4. The runtime log gained `Cannot read null.mymob` in `save_position` (`action_button.dm:150`), the text from the issue. The dead button was also found in `hud.floating_actions`. That list holds a strong reference, so the button fails GC and is hard deleted, as in the #75578 comments.

### #89809 (reproduced on master)

1. Join as an Assistant and spawn an oxygen tank and a flashlight (three listed actions).
2. Make one button float and drag it onto the "Show Buttons" palette button.
3. "Show Buttons" went from `invisibility 0` to `101` (hidden), and the action sat in the collapsed palette with a nil `screen_loc`. From the player's view it had disappeared.

### #98042, #75578, #94921 (not reproduced directly)

With clean state (no dead button in a group), resetting the positions by shift-click and by alt-click on the palette button worked correctly with three actions, both with floating and palette buttons mixed. The "all buttons vanish" state needs a deleted button in an action group, which would come from a hard delete. That was not triggered naturally. The analysis in Cause is a deduction from the code and from the null-entry evidence in the #75578 comments.

### #65965 (not reproduced)

The spider web button and the cult spell overflow were not tried in game (that needs a spider and a view change).

## Cause

### Dead buttons in a group (#93422, and by deduction #98042, #75578, #94921)

`/atom/movable/screen/movable/action_button/proc/can_use` (`code/_onclick/hud/screen_objects/action_button.dm:41`) ends with:

```dm
if(linked_action)
	if(linked_action.viewers[user.hud_used])
		return TRUE
	return FALSE

return TRUE
```

A button that has been `Destroy()`ed has no `linked_action`, so `can_use` returns `TRUE`. The Click and `mouse_drop_dragged` handlers (`action_button.dm:113`) trust it. A client that was in the middle of dragging a button when it was deleted still delivers the drop, which calls `hud.position_action` (`code/_onclick/hud/hud.dm:513`) or `position_action_relative` (`hud.dm:544`) with the dead button, and the dead button is inserted into `floating_actions` or into a group's `actions` list. `save_position` (`action_button.dm:149`) then reads `our_hud.mymob` on a button whose `our_hud` is gone, which is the #93422 runtime.

A dead button in a group fails to be garbage collected and is hard deleted. The group's `actions` list is left with a `null`. `/datum/action_group/proc/refresh_actions` (`code/_onclick/hud/action_group.dm:50`) walks that list and sets `button.screen_loc`, which runtimes on the null entry and ends the proc early. Every button after the null keeps a null `screen_loc` and is not drawn. After a reset, the internals button is the only one that survives, since it is inserted first (`SCRN_OBJ_INSERT_FIRST`, index 1). This matches #98042's description ("all of my action buttons (except o2) completely vanished"), #75578's invisible-but-present buttons (the group still counts them) and #94921. This chain, from null entry to vanishing buttons, was deduced from the code and the comments in #75578; the vanishing itself was not reproduced.

### Palette toggle hidden (#89809)

Dropping a floating button on the palette runs `position_action(button, SCRN_OBJ_IN_PALETTE)`. `position_action` first calls `hide_action` on the button's current location (`hud.dm:570`). For a floating button, `hide_action` removes it from `floating_actions` and calls `toggle_palette.update_state()` (`hud.dm:578`). At that moment the palette is still empty, so `update_state` (`action_button.dm:335`) sees no floating actions and calls `disable_landing`, which hides the toggle (invisibility 101). The button is then inserted into the palette group, but `/datum/action_group/palette/insert_action` (`action_group.dm:155`) never updated the toggle, and `update_state` only looked at `floating_actions`, never at the palette's contents.

### #65965

`view_audit_buttons` (`hud.dm:616`) loops over `floating_actions` and calls `screen_loc_to_offset(floating_button.screen_loc, our_view)`. That helper already returns `list(64, 64)` for a null `screen_loc` (`code/__HELPERS/screen_objs.dm:7`), so a null `screen_loc` itself does not cause a `current_offsets` runtime. A dead or null entry in `floating_actions` is a plausible source, but that was not confirmed.

## Fix

Three commits.

**"Fix issue 93422: ignore clicks and drops on deleted action buttons"**
- `can_use()` now returns `FALSE` when the button is `QDELETED`, has no `our_hud`, or has no `linked_action`. The `linked_action` branch is simplified accordingly.
- `save_position`, `load_position` and `dump_save` use `our_hud?.mymob` so they no longer runtime on a button that has lost its HUD.

**"Fix issue 98042: keep deleted action buttons out of the action groups"**
- `hud.dm`: `position_action` and `position_action_relative` return early if the button (or the `relative_to` button) is `QDELETED`, so a dead button can no longer enter `floating_actions` or a group.
- `action_group.dm`: `refresh_actions()` starts with `list_clear_nulls(actions)`, so a null that is already in the list does not stop the loop. This covers #75578 and #94921.

**"Fix issue 89809: keep the button palette toggle visible while it holds actions"**
- `button_palette.update_state()` now also activates the landing when the palette group has actions, not only when there are floating actions.
- The palette group's `insert_action` and `remove_action` call `palette.update_state()` after the change, so the toggle follows the palette's contents.

The `can_use` change is the narrowest fix for #93422 and also removes the way a dead button enters a group. The `QDELETED` guards in `hud.dm` cover callers that do not go through `can_use`. `list_clear_nulls` is a defensive repair for a list that already has a null in it. The #89809 report suggested swapping two lines in `hud.dm` (589 and 590 at the time of the report). The changes above were made instead because they also keep the toggle correct when buttons are removed from the palette.

## Verification

On the fixed build in game (as an Assistant, with an oxygen tank and a flashlight):

- #89809: a button floated with `position_action` and then dragged onto "Show Buttons" went into the palette (the palette held "Toggle Flashlight" with a nil `screen_loc`), the floating list was empty, and "Show Buttons" stayed visible (invisibility 0). Clicking it gave "Hide Buttons" and showed the button. Alt-clicking "Show Buttons" printed "Action button positions have been reset.", moved all buttons back to the list, and hid the toggle again once the palette was empty.
- #93422: the same set-up as the reproduction (a `qdel`ed listed button, then the SDQL2 `CALL mouse_drop_dragged(...)`) reported "1 objects executed on" and logged no `mymob` or `save_position` runtime. The dead button was absent from the listed, palette and floating groups.

Not checked:

- The "everything vanishes after a reset" state of #98042, #75578 and #94921 on master or on the fix. That state was never reproduced, so the fix for it rests on the analysis above. In particular, `list_clear_nulls` in `refresh_actions()` was not tested against a list that actually contained a null.
- A hard-deleted button in a group (the only observed case on master was the dead button entering `floating_actions` after a drop).
- The hierophant club, the EVA suit, test-merged mothperson arms or the combo meter that appear in the reports.
- #65965 (spider web button, cult spells after the fourth).
- Real client drag-and-drop of a button while it is deleted. The drop was simulated with SDQL2.

## Notes

- #65965 is listed as not reproduced. The `current_offsets` runtimes in its comments are consistent with a dead or null entry in `floating_actions`, which the second commit now prevents, but nothing was confirmed in game and the first half of the report (spider web after respawns) was not examined at all.
- #93422 had a comment that dropping a deleted button was intended behaviour. The runtime is fixed anyway; ignoring clicks and drops on a button that no longer exists is not a visible behaviour change.
