## Summary

When a circuit component with a "List Type" option (Index, Index Associative List, For Each, Associative List Pick) has its option chosen *after* a Variable Getter was wired to its list input, the input's value is wiped and never restored. A list variable is modified in place, so the getter never sends its value again and the input stays null. The fix makes an input port re-read the values of the output ports it is connected to after its datatype changes, and removes a dead duplicate `set_datatype` definition.

## The bug

#79671 reports that an associative list variable (the screenshot shows a Getter for a "locations" variable feeding an Index Associative List, type entity) does not work as an input to list components. The order in which the circuit is built matters: wiring the getter first and choosing the List Type afterwards leaves the list input empty, and the component outputs nothing. Choosing the type first and wiring afterwards works.

#76207 says the List Pick and Associative List Pick components "do not work". #78237 says a global string list, filled with List Add and read with a Variable Getter, comes out as `null` and a For Each over it does zero loops.

## Reproduction

All on the test server, using the Lua editor to build circuits (the circuit UI's add-variable action did not work when driven from Lua, so variables were created directly):

1. Spawn an integrated circuit, set it admin-only and on.
2. Create an associative list circuit variable `loc` (key type string, value type entity), set its value to an empty list, and register it in the circuit's variable lists.
3. Add a Variable Getter (name `loc`) and an Index Associative List component.
4. Connect the getter's output to the Index component's list port, then set the Index component's List Type option to `entity`.
5. Set the index key and trigger the component.

Observed before the fix: the Index component's list port value was `nil` and its output was `nil`. Swapping steps 4's order (option first, then connect) gave a working circuit. A control run with four List Add components and a Getter into Length (no List Type option involved) reported a length of 4, so list variables themselves work.

The Lua editor was used instead of the circuit UI, and values were read from the circuit's state log rather than from a player's view.

## Cause

`/datum/port/proc/set_datatype` ends by clearing the port's value (`src.value = null`, `code/modules/wiremod/core/port.dm:102`). An input port normally gets values only when a connected output sends one (`receive_value` on `COMSIG_PORT_SET_VALUE`), or once on `connect()` (`port.dm:192`).

The List Type handlers call `set_datatype` on the list input from `pre_input_received` (`code/modules/wiremod/components/list/index.dm:39` and `:69`, `foreach.dm:39`, `assoc_list_pick.dm:21`). If a getter was already connected, the datatype change nulls the freshly received list. Nothing re-reads the connected output, and the getter only sends when `circuit_variable.set_value` is called. List Add and Associative List Set change the list in place and do not call it, so no new send happens and the input remains null.

`port.dm` also contained two `/datum/port/input/set_datatype` definitions (`:107` and `:195`). The later one overrides the earlier, which made the first dead code.

## Fix

One commit, "Fix issue 79671: circuit input ports lose their value when their datatype changes", in `code/modules/wiremod/core/port.dm`:

- After the type check loop in the surviving `/datum/port/input/set_datatype`, if the new datatype does not have `DATATYPE_FLAG_AVOID_VALUE_UPDATE`, call `set_value(port.value)` for every connected output port. This mirrors what `connect()` already does and keeps signal-type ports from firing on a datatype change.
- Iterate over `connected_ports?.Copy()` in the type check loop, since `check_type` can disconnect incompatible ports and so change the list during iteration.
- Delete the dead first `set_datatype` definition.

The fix is in the port layer instead of the individual components, so it covers every component that changes an input's datatype after wiring, not only the four with a List Type option.

## Verification

Checked on the test server with Lua-built circuits, after the fix:

- Index Associative List: string associative list variable `loc` = `{here = "the floor"}`, Getter connected first, then List Type set to `string`, key `here`, triggered. The list port held a list and the output was `"the floor"`.
- For Each: string list variable `{"aaa", "bbb"}`, Getter connected first, then List Type `string`. Triggering Next Index twice produced element `aaa` (index 1) and then `bbb` (index 2).
- No new game runtimes appeared during the tests (only the known empty uncaught-runtime lines).

Not checked: entity-typed lists after the fix (same code path as the string case); the plain List Pick and the Associative List Pick being used by a real client through the list prompt; the original multi-component circuits from the three issues.

## Notes

- **#78237:** In the Length test the getter list had 4 elements. From the screenshots, the reporter's circuit is Getter, Length, Typecast (string), Concatenate. Typecast checks `istext(value)` (`code/modules/wiremod/components/utility/typecast.dm:47`), so casting a number to "string" yields null; that is intended (the To String component converts). The reporter's For Each doing 0 loops matches the #79671 order-of-wiring bug. Their circuit was not rebuilt exactly, so this is an inference.
- **#76207:** The base List Pick has no List Type option and its code reads fine; the associative List Pick shares the #79671 cause. A comment on the issue points at PR #72097, which may already have fixed the original "does not trigger" report. That could not be confirmed.
- Side finding, unrelated to the fix: in the test scripts, assigning an element by index from Lua to an empty DM list (`L[1] = 'x'`) crashed the server inside the Lua library (`libdreamluau.so`, "Crashing due to an illegal operation") twice. The workaround was to pass a pre-filled table to `set_value`.
