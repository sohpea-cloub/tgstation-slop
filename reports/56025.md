# #56025: VV-edited `verb_say` is ignored by humans (the tongue's `say_mod` wins)

| | |
|---|---|

| Status | verified, fix committed |
| Fix branch | [fix/56025](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/56025) |

## Summary

An admin who edits `verb_say` on a human with View Variables sees the change ignored: the character keeps using the verb from their tongue ("says" for most species, "meows" for felinids). `/mob/living/carbon/human/get_default_say_verb()` returns the tongue's `say_mod` before it ever looks at the mob's own `verb_say`, and every tongue has a non-empty `say_mod` ("says" by default). The fix makes a `verb_say` that differs from the type's initial value take precedence over the tongue's `say_mod`. Sign language (`temp_say_mod`) still takes precedence over both.

## The bug

The issue reporter changed several say-related variables on a felinid for a gimmick. Everything took effect except `verb_say`, which "reverted". It did not revert: the variable keeps the edited value, but it is never read when the human speaks. A comment on the issue points at #71635, which made the say verb depend on the tongue, and notes that the only way to change the verb now is to edit the tongue's `say_mod`.

## Reproduction

The variable was changed from the Lua editor, which sets the same variable View Variables sets. The reproduction does not depend on the Lua editor: the speech went through the normal `say` path, the same as if a player had spoken.

1. Start a round on the test server and open the Lua editor as an admin (as an observer, for example).
2. Spawn a human, make it a felinid with `set_species(/datum/species/human/felinid)`, and name it so it can be found in chat.
3. Set `verb_say = "zorps"` on it, as View Variables would. (A first attempt used "meows". That is a false positive, because the felinid tongue's `say_mod` is already "meows".)
4. Make the human say something, for example `h:say("hello again")`, and read the chat log.

Observed on master:

- `verb_say` read back as `"zorps"`, but `get_default_say_verb()` returned `"meows"`.
- The chat line was `Test Cat meows, "Hello again"`.

## Cause

`code/modules/mob/living/carbon/human/human_say.dm:24` overrides `get_default_say_verb()` for humans. After handling the tongueless case, it ends with:

```dm
return  tongue.temp_say_mod || tongue.say_mod || ..()
```
(`code/modules/mob/living/carbon/human/human_say.dm:30`)

`say_mod` is declared as `var/say_mod = "says"` (`code/modules/surgery/organs/internal/tongue/_tongue.dm:30`), so for any human with a tongue the `||` chain stops at `tongue.say_mod`. The `..()` at the end, which is the base implementation `return verb_say` (`code/game/say.dm:223`), is only reached if a tongue's `say_mod` is empty. The mob's own `verb_say` is therefore never used for humans with a tongue. The result of `get_default_say_verb()` is what the speech code uses: `code/game/say.dm:216` for the spoken message, and `code/game/say.dm:419` when a radio message copies the speaker's verb.

## Fix

One commit: "Fix issue 56025: VV-edited verb_say on humans is ignored in favour of the tongue's say_mod". It changes the last line of `get_default_say_verb()` into three steps:

1. If the tongue has a `temp_say_mod` (used for sign language), return it, as before.
2. Otherwise, if `verb_say != initial(verb_say)`, return the mob's `verb_say`.
3. Otherwise return `tongue.say_mod || ..()`, as before.

Comparing against `initial(verb_say)` keeps the tongue's verb as the default for unmodified mobs, so felinids still "meow" and other species keep their tongue verbs, while an explicit change (admin VV, for example) wins. The other option, reading `verb_say` first unconditionally, would have broken tongue-based verbs, because `verb_say` is "says" on every unmodified human.

## Verification

After the fix, the test server was rebuilt and four humans spoke in one round:

| Human | `verb_say` | Chat line |
|---|---|---|
| felinid, `verb_say = "zorps"` | changed | `zorps, "One"` |
| felinid, unmodified | default | `meows, "Two"` |
| human, `verb_say = "zorps"` | changed | `zorps, "Three"` |
| human, unmodified | default | `says, "Four"` |

The felinid with the changed verb also spoke a question ("what?") and the changed human an exclamation ("wow!"). They came out as "asks" and "exclaims", so the question and exclamation handling is unchanged.

Not checked in game:

- Sign language (`temp_say_mod`). It is handled first in the new code, so its behavior should be unchanged, but it was not tested.
- The unmodified human with a changed `verb_say` on unfixed master. The unfixed behavior was observed only on the felinid.
- Radio speech (`code/game/say.dm:419`) with a changed `verb_say`.

## Notes

- Only `verb_say` was affected. `verb_ask`, `verb_exclaim` and `verb_yell` are not overridden by tongues, so edits to them were never ignored.
- A `verb_say` that is deliberately set back to the type's initial value ("says") is indistinguishable from "unchanged" and falls back to the tongue's `say_mod`. Setting the tongue's `say_mod` still works as it did before.
- If a human subtype ever declares its own `verb_say` in its definition, `initial(verb_say)` would equal that value and the tongue would still win; no such human type was found or tested.
