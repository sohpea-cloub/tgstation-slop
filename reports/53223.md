## Summary

The 2020 report says filtered frequencies cannot be added to telecomms processors and servers. On current master, adding and removing a filtered frequency worked on both a telecomms server and a processor unit, and the game log recorded each change. The report was made against the old telecomms interface on client 513, and the interface has since been rewritten, so the bug was probably fixed along the way. The test sent the interface's actions directly instead of clicking the real tgui controls, so a problem in the browser-side number input cannot be ruled out.

## The bug

As reported: the "Filtered Frequencies" section of a telecomms machine's interface did not let a player add a frequency. The report gives no steps, error text or screenshots and says only that it was "tested to not work on processors and servers". Nobody commented on the issue.

## Reproduction

Not reproduced. What was done, using the Lua editor and the test server's admin tools:

1. Started the round, spawned a human next to the Science Server in the telecomms server room, gave it a multitool in its active hand, and took control of it.
2. Clicked the Science Server to open its Telecomms interface. The "Add Frequency" row is only shown while the user holds a multitool.
3. Sent the interface's `tempfreq` action with value 145.9, then the `freq` action. The machine's `frequencies` list went from 1 to 2 entries (1459 added).
4. Sent `tempfreq` with 146.10000000000002, which is the kind of value the interface's number input can produce from floating-point steps, then `freq`. The list gained 1461, so the value was rounded correctly.
5. Sent `delete` with value 1461. The entry was removed.
6. Repeated the add and remove on a processor unit in the same room: `tempfreq` 150.3 then `freq` took its list from 0 to 1 entries (1503), and `delete` took it back to 0.

Evidence:

- The game log contained "added frequency 1459 for Science Server", "added frequency 1461 for Science Server", "added frequency 1503 for the processor unit" and "removed frequency 1503 ...".
- The runtime log showed no runtimes from these actions.
- The interface received updated `frequencies` data after each action, so the list shown to the player would update.

Limits of the test: the tgui JavaScript was not run, so the interface's NumberInput and its buttons were not exercised, only the server-side actions behind them. The frequency was not checked for effect on actual radio traffic.

## Cause

No defect was found. The actions are handled in `/obj/machinery/telecomms/ui_act()` in `code/game/machinery/telecomms/machine_interactions.dm:76-133`, shared by all telecomms machines:

```dm
if("tempfreq")
	if(params["value"])
		tempfreq = text2num(params["value"]) * 10
if("freq")
	if(tempfreq in banned_frequencies)
		... // "Interference preventing filtering frequency" message
	else
		if(!(tempfreq in freq_listening))
			freq_listening.Add(tempfreq)
```

The data sent to the interface (`ui_data()`, `machine_interactions.dm:69-74`) lists `freq_listening` as `frequencies`, and the interface (`tgui/packages/tgui/interfaces/Telecomms.jsx:176-255`) shows the list and, when a multitool is held, an "Add Frequency" row with a number input that calls `tempfreq` and a "+" button that calls `freq`.

Behaviors that can look like "cannot add" but are by design or are limits of the interface:

- `ui_act()` returns early unless the user is a silicon or holds a multitool in the active hand (`machine_interactions.dm:82-84`), so actions without a multitool do nothing.
- Frequencies in `banned_frequencies` (Syndicate, CentCom and the four CTF frequencies, `machine_interactions.dm:9-16`) are refused with a message and a buzz sound.
- A frequency already in the list is ignored.
- A tgui window is view-only while the user is lying down or two or more tiles away, so actions sent from it then do nothing. This was noted during the test but not traced to its code.

Side finding: the row key in the filtered-frequencies table is `key={frequencies.i}` (`Telecomms.jsx:179`). `frequencies` is an array, so this is always `undefined`, which gives React's "each child in a list should have a unique key" warning. It has no effect on functionality.

## Fix

None. No commit was made.

## Verification

Server-side adding and removing of filtered frequencies was verified on master as described under Reproduction. Not checked: the browser-side interface in a real client (including the NumberInput control and its step and rounding behavior), real radio signals passing through a machine after a filtered frequency was added, and other telecomms machine types (hub, bus, relay, receiver) beyond the server and processor.

## Notes

- The likely explanation is that the Telecomms interface was rewritten after the 2020 report. The report is against client 513 and the old interface.
- If someone still sees the problem in a real client, the first things to check are whether a multitool is in the active hand, whether the window is in range, and whether the frequency is one of the banned ones.
- The `key={frequencies.i}` line could be changed to `key={entry}` to silence the React warning. It was not changed.
