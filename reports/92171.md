## Summary

#92171 reported that Fugitive Hunters never appear after fugitives are rolled. On current master they do, both when the emergency shuttle is called and when it is not (after a 10-minute countdown), which matches the already-merged fix in PR #92761. No code was changed. #93804 (round-end report says "Prank Call! ... no fugitives") and #93908 (forced Fugitives ruleset spawns nothing on Catwalk) are grouped with it as related, but they were not tested; they remain open questions.

## The bug

**#92171** (July 2025): "Any time fugitives rolls the hunters just never show up, might be a side effect of new dynamic?" The reporter's steps were to spawn in as a fugitive, wait, and see no hunters. The round was on Catwalk. A comment in September 2025 said it was supposedly fixed by #92761 ("Fugitive Hunters spawn again").

**#93804** (November 2025): after a round in which 4 fugitives were captured by 3 hunters, the round-end report listed the fugitives and the hunters and then showed "Prank Call! Bounty Fugitive Hunterss were called, yet there were no fugitives...?", so the hunters' win was not credited. The reporter says "hunters still broken".

**#93908** (November 2025): Fugitives rolled on a round, had sign-ups, and did not spawn. An admin trying to force the event twice (a random fugitive type and the Waldo type) saw nothing happen at all, not even a ghost poll. A commenter suspected the map (Catwalk) had no valid deploy spot.

## Reproduction

Only #92171 was exercised. Using admin tools on a running round on the test server:

1. Start a round and become an observer. Open the Dynamic Panel and run `execute_ruleset` on `/datum/dynamic_ruleset/midround/from_ghosts/fugitives`, choosing the "prisoner" fugitive backstory and the Spacepol hunter backstory.
2. First attempt: it failed with "Forced ruleset Fugitives, but preparation failed! Reason: Not enough eligible candidates. Have: 0, Need: 1". This was a setup problem and not the bug: the test account's role preferences (`prefs.be_special`) were empty, and `trim_candidates` (`code/controllers/subsystem/dynamic/_dynamic_ruleset.dm:275-290`) drops anyone whose preferences do not include the ruleset's role (`ROLE_FUGITIVE`). Using the Lua editor, "Fugitive" was added to the account's `be_special` list.
3. Ran the ruleset again with the same choices and signed up in the ghost poll. A fugitive was selected within about half a minute (the dynamic log recorded the forced selection) and spawned in maintenance.
4. **Shuttle path:** about 30 seconds after the fugitive was created, as an admin, called the emergency shuttle (Call Shuttle, "Yes"). Roughly one minute after the ruleset was executed a ghost poll "Do you wish to be considered for a group of Spacepol Fugitive Hunters?" appeared. After signing up, the player spawned a few seconds later on the Hunter Shuttle (z-level 11) with the message "Justice has arrived. I am a member of the Spacepol!".
5. **No-shuttle path** (the case the original bug was in): cancelled the shuttle (Cancel Shuttle), and ran the ruleset again with the Waldo fugitive and Russian hunter backstories, signing up as the fugitive. About 11 minutes after execution (1 minute plus the 10-minute countdown) the hunter poll for "Russian Fugitive Hunters" appeared. After signing up the player spawned in the "Russian Cargo Hauler" with the hunter's opening message.

So both timings work as the code describes.

Runtime log, with two observations that are not related to the missing hunters:
- `runtime error: Cannot read null.ambient_buzz` (in `refresh_looping_ambience`, `code/controllers/subsystem/ambience.dm:125`), once per fugitive spawn (twice in this session). It occurs when the new fugitive body, which is briefly in nullspace, gets its player attached through `prepare_for_role`. It appeared to be cosmetic.
- `WARNING: couldn't find shuttle with id: huntership` (`code/controllers/subsystem/shuttle.dm:318`), logged once. It comes from `/obj/item/pinpointer/shuttle/Initialize` (`code/game/objects/items/pinpointer.dm:223`), which looks up the hunter ship's docking port when the pinpointer is created, before the ship's port is registered. The pinpointer retries the lookup when it scans (`scan_for_target`), so it was treated as harmless.

## Cause

There is no live defect for #92171. The original problem, per the code history and triage, was that the delayed hunter-spawn timer was called with the wrong argument (`hunter_backstory` where `remaining_time` was expected), which made the callback runtime. On master (`code/controllers/subsystem/dynamic/dynamic_ruleset_midround.dm:940`):

```dm
addtimer(CALLBACK(src, PROC_REF(check_spawn_hunters), 10 MINUTES), 1 MINUTES)
```

and the callback (`dynamic_ruleset_midround.dm:979-984`) spawns hunters immediately if the countdown is 0 or the emergency shuttle is neither idle nor recalled, otherwise reschedules itself every minute with one minute less. That explains the two observed timings: the first check one minute after execution sees the called shuttle and spawns hunters; with the shuttle idle, the 10-minute counter runs down from the first check, giving the poll at about 11 minutes. `spawn_hunters()` (`:986`) then polls ghosts and loads the matching ship.

For #93804 and #93908 no cause was determined. Observations from reading the code at master only (not tested in game):
- The "Prank Call!" text is produced in `roundend_report()` of `/datum/team/fugitive_hunters` (`code/modules/antagonists/fugitive/hunters/hunter.dm:184-186`) when `get_result()` returns null, which happens when `assemble_fugitive_results()` (`hunter.dm:91-104`) finds no `/datum/antagonist/fugitive` datums in `GLOB.antagonists` (`hunter.dm:121-122`). The #93804 report showed fugitives listed in the same output, so which condition produced the null result is unclear.
- The fugitives ruleset's `can_be_selected()` (`dynamic_ruleset_midround.dm:865-866`) requires `find_maintenance_spawn(atmos_sensitive = TRUE, require_darkness = FALSE)` to return a spot, and the spawn location passed on execution comes from the same call (`:875-878`). This is a plausible area for a map-specific failure like the one suspected in #93908, but it was not checked on Catwalk.

## Verification

Nothing to verify, as nothing was changed. The checks described under Reproduction show hunters spawning on master via both paths. Not checked: the natural (non-admin) roll of the Fugitives ruleset, any map other than the test server's default map (the original reports were on Catwalk), more than a single fugitive and a single hunter, the round-end report, and the capture of fugitives with the bluespace capture machine.

## Notes

- Closing #92171 as fixed by #92761 looks justified, with the caveat that it was tested with the admin-forced ruleset on a different map from the reports.
- Admin pitfall that may explain part of #93908's "nothing happens": a forced Fugitives ruleset needs candidates who have the Fugitive role enabled in their preferences. In the test, with nobody opted in, the forced run produced a "preparation failed ... Not enough eligible candidates" message rather than a ghost poll. Whether the reporter hit this is unknown (they said there were sign-ups, which points elsewhere), so this is only a lead.
- #93804 (the round-end report) and #93908 (Catwalk) need their own investigation. A suggested start: force fugitives and hunters, capture the fugitives with the capture machine, and read the round-end report; and force the ruleset on Catwalk and see whether `find_maintenance_spawn` returns a turf.
