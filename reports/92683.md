# #92683: Omnitools in multitool mode runtime in multitool_act

| | |
|---|---|
| Issues | [#92683](https://github.com/tgstation/tgstation/issues/92683) - verified, fixed |
| Status | Reproduced on master; fix committed and checked in game |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/92683 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The debug omnitool (`/obj/item/debug/omnitool`) and the abductor "quizzandric interfacer" (`/obj/item/abductor/alien_omnitool`) change mode by setting `tool_behaviour` on themselves. In multitool mode they are still not `/obj/item/multitool`s, but about 57 `multitool_act()` procs declare their tool argument as `obj/item/multitool` and read multitool-only vars such as `buffer`, which causes a runtime. The fix gives both omnitools an internal, hidden real multitool and returns it from `get_proxy_attacker_for()` while the omnitool is in multitool mode, the same mechanism the cyborg omnitool already uses.

## The bug

Using either omnitool in multitool mode on a machine whose `multitool_act()` reads the tool's buffer (for example an R&D console) produces a runtime and the interaction does nothing. The issue reporter's steps: take an omnitool, try to save something to the buffer, and get runtimes. The same applies to any code that treats the held item as a multitool after checking only `tool_behaviour == TOOL_MULTITOOL`.

What is really happening is that the omnitool is passed straight into `multitool_act(mob/living/user, obj/item/multitool/tool)`. It has no `buffer` var, so reading `tool.buffer` fails. Nothing was missing from the multitool code itself; the omnitool never presents a real multitool to it.

## Reproduction

On master, using admin tools only:

1. In the Lua editor (as an observer or ghost on the test server), spawn a human (`/mob/living/carbon/human`), an R&D console (`/obj/machinery/computer/rdconsole`) and a debug omnitool (`/obj/item/debug/omnitool`).
2. Set the omnitool's `tool_behaviour` to `'multitool'`.
3. Call `omnitool:melee_attack_chain(human, console, {})`.
4. Read the round's `runtime.log`.

Observed: `runtime error: undefined variable /obj/item/debug/omnitool/var/buffer`, in proc `/obj/machinery/computer/rdconsole/multitool_act`, at `code/modules/research/rdconsole.dm,107`.

This was reproduced by calling `melee_attack_chain` directly from Lua with the mode set by writing `tool_behaviour`, not by a player clicking with the item in hand and choosing the mode from its menu. The abductor omnitool was not reproduced separately on unfixed master; its code has the same structure (see Cause).

## Cause

`melee_attack_chain` (`code/_onclick/item_attack.dm:26`) starts by asking the item for a proxy:

```dm
var/obj/item/source_atom = get_proxy_attacker_for(target, user)
if(source_atom != src)
	return source_atom.melee_attack_chain(user, target, modifiers, attack_modifiers)
```

The default `get_proxy_attacker_for()` (`code/game/objects/items.dm:2147`) returns `src`. Its doc comment describes exactly this use: an object that has different `tool_behaviour`s should return an internal reference of the matching tool to act for it. Only the cyborg omnitool does so (`code/game/objects/items/robot/items/tools.dm:218`).

`/obj/item/debug/omnitool` (`code/game/objects/items/debug_items.dm:35`) and `/obj/item/abductor/alien_omnitool` (`code/modules/antagonists/abductor/equipment/gear/abductor_items.dm:650`) do not override it. They only change their own `tool_behaviour`, so `multitool_act()` receives the omnitool itself. For example `/obj/machinery/computer/rdconsole/multitool_act` (`code/modules/research/rdconsole.dm:105`) does `tool.buffer` (line 107), and `/obj/machinery/rnd/multitool_act` (`code/modules/research/rdmachines.dm:112`) does the same.

A related caller is the R&D machine screentip code at `code/modules/research/rdmachines.dm:74`, which already calls `held_item.get_proxy_attacker_for(src, user)` and assigns the result to an `obj/item/multitool` variable before reading `tool.buffer`. On master this would receive the omnitool itself for these two items. That path was not tested.

## Fix

One commit, "Fix issue 92683: omnitools in multitool mode use an internal multitool as proxy". For both `/obj/item/debug/omnitool` and `/obj/item/abductor/alien_omnitool` it:

- adds a var `internal_multitool` (`/obj/item/multitool`);
- adds `get_proxy_attacker_for()`, which returns `src` unless `tool_behaviour == TOOL_MULTITOOL`; in multitool mode it lazily creates the internal multitool inside the omnitool (copying `toolspeed`, setting the `ABSTRACT` item flag and adding `TRAIT_NODROP`) and returns it;
- adds `Destroy()` that does `QDEL_NULL(internal_multitool)`.

The approach follows the maintainer comment on the issue (SyncIt21): code that changes `tool_behaviour` should hand out a correct internal tool as its proxy, as the cyborg omnitool does, rather than every `multitool_act()` being changed to accept non-multitools. The internal multitool is created only when first needed, and its buffer persists for as long as the omnitool exists.

The fix only covers multitool mode. Other typed tool acts were not found to matter, so no other modes were changed.

## Verification

On the rebuilt test server, for both the debug omnitool and the alien omnitool, using the Lua editor:

- With `tool_behaviour` unset, `get_proxy_attacker_for` returned the omnitool itself; after setting the mode to multitool, `melee_attack_chain` on an R&D console returned 1 and `runtime.log` showed no runtime.
- The internal multitool existed after that call. Its `buffer` was set to the first console's `stored_research`, the second console's `stored_research` was set to nil, and `melee_attack_chain` on the second console made it hold the same techweb as the first, so the buffer path works through the proxy.
- Switching the mode to the screwdriver made `get_proxy_attacker_for` return the omnitool itself again.

Not checked: a real player clicking with the omnitool, and choosing the mode from its in-hand menu or radial menu; setting the buffer through the normal multitool interaction (it was set directly from Lua); the R&D machine screentip at `rdmachines.dm:74`; other `multitool_act()` users beyond the R&D console; deleting an omnitool that has an internal multitool (the `Destroy()` cleanup was not exercised); the unit test suite.

## Notes

- Telecomms `get_multitool()` (`code/game/machinery/telecomms/machine_interactions.dm:357`) already calls `get_proxy_attacker_for()`, so it should work with the new override, but this was not tested.
- The internal multitool is `ABSTRACT` and `NODROP` so it cannot be seen or moved out of the omnitool; the code is duplicated in both omnitools, which a maintainer may want to share.
- The same 15 lines were added to each of two types. The alternative of loosening the `obj/item/multitool` argument type in the many `multitool_act()` procs would not help, because they read multitool-only vars such as `buffer`.
- Whether upstream has since fixed this was not checked.
