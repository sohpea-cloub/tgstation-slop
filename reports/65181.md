# #65181: Changing UI style drops client screen objects that are not part of the HUD

| | |
|---|---|
| Issues | [#65181](https://github.com/tgstation/tgstation/issues/65181): verified (symptom reproduced; fixed in part, see Notes) |
| Status | Fixed (partial: the HUD rework the issue asks for was not attempted) |
| Fix branch | [fix/65181](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/65181) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Changing the UI style rebuilds the HUD, and the rebuild calls `client.clear_screen()`. That removes every screen object on the client that has `clear_with_screen = TRUE` (the default) and that the HUD does not add back itself. Screen objects that belong to the client rather than to a HUD, such as the admin buildmode buttons, were silently dropped. The fix sets `clear_with_screen = FALSE` on the client-bound screen types. It does not rework how HUDs track screen objects, which the issue asks for.

## The bug

The issue (opened in 2022) says that not all screen objects are managed by the HUD, so changing UI style makes some of them disappear. It asks for HUD object management to be reworked, separate from the `screen` var on clients, so that observing also works.

Master already has a HUD with `screen_objects` and groups, so most of that has been done. What remains is that a UI style change still wipes any screen object that was added to `client.screen` outside the HUD. An admin in buildmode loses the four buildmode buttons, for example.

## Reproduction

Reproduced on master `87b93338`, partly by calling the preference apply proc directly (see step 4).

1. Start the round (`Start-Now`) and join as an Assistant.
2. As an admin, run `Toggle-Build-Mode-Self`. Four buildmode buttons appeared on the client screen (Toggle Mode, Buildmode Help, Change Dir, Quit Buildmode).
3. Note the client's screen contents: 36 screen objects were listed including those buttons.
4. In the Lua editor, set the `ui_style` preference to `Plasmafire` and call the preference's `apply_to_client` for the client. The test guest's `update_preference` returned false, so the apply path was called directly rather than through the player's preference menu. It leads into the same `update_ui_style` call chain.
5. Check the client screen again: the four buildmode buttons were gone. The HUD objects had been rebuilt with the new style.

## Cause

`update_ui_style()` (`code/_onclick/hud/hud.dm:425`) ends with `build_hand_slots(update_hud = TRUE)` (`hud.dm:436`), which calls `show_hud()` (`hud.dm:295`). `show_hud()` calls `screenmob.client.clear_screen()` (`hud.dm:306`):

```dm
/client/proc/clear_screen()
	for (var/object in screen)
		if (istype(object, /atom/movable/screen))
			var/atom/movable/screen/screen_object = object
			if (!screen_object.clear_with_screen)
				continue
		screen -= object
```

(`code/modules/client/client_procs.dm:1262`.) Only objects with `clear_with_screen = FALSE` survive. The HUD re-adds its own objects afterwards, but nothing re-adds screens that were put on the client by other code. Those screen types had the default `clear_with_screen = TRUE`.

## Fix

One commit, "Fix issue 65181: client-bound screen objects survive HUD refreshes". It sets `clear_with_screen = FALSE` on these client-bound screen types:

- buildmode buttons (`code/modules/buildmode/buttons.dm`)
- admin popup (`code/datums/components/admin_popup.dm`)
- cinematic (`code/datums/cinematics/_cinematic.dm`)
- credits (`code/_onclick/hud/screen_objects/credits.dm`)
- tutorial skip and tutorial instruction (`code/modules/tutorials/tutorial_skip.dm`, `tutorial_instruction.dm`)
- fishing minigame (`code/modules/fishing/fishing_minigame.dm`)

The existing opt-out flag was used because it is the mechanism `clear_screen()` already honours, and each of these objects is removed by its owner or when it is deleted.

## Verification

- Buildmode, in game: repeating the reproduction with the fix, the screen listed 40 objects (36 before the change, plus the buttons) and the four buildmode buttons were still present. The HUD was recoloured to the new style, and no new runtimes appeared.
- Not checked in game: admin popup, cinematic, credits, tutorial skip/instruction and fishing minigame. These were checked only by reading the code.
- The preference menu path was not exercised, only the apply call (see Reproduction step 4).

## Notes

- This is per-object hooking, which is what the issue asks not to do ("do NOT just make the existing problems go away by hooking them in"). The full rework, including observing support, was not attempted. A maintainer may prefer to close the issue as already addressed by the existing HUD refactor, or to take only the buildmode part.
- Other code that adds to `client.screen` was left alone: the Mafia popup, picture-in-picture, a hallucinated item and the robot module view used when observing. Whether they are affected by a style change was not checked.
- The tutorial and fishing changes carry no explanatory comment in the diff; the others do.
