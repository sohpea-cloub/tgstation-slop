|---|---|

## Summary

The 2018 report says that turning "ambient sounds" off only stopped the sound already playing, and new ambience kept coming until the player toggled it on and off again. On current master the toggle has become a volume preference (`sound_ambience_volume`, 0 to 100). Setting it to 0 removed the client from the ambience subsystem and no new ambience was sent, and setting it back to 100 resumed it. The reported behaviour did not occur, so no fix was made.

## The bug

As reported: after switching ambience off in the preferences, ambient sounds from areas continued to play. Only the sound that was already playing stopped. Switching the option on and then off again was needed to stop new sounds.

## Reproduction

The original on/off toggle is not in master, so the report could not be followed literally. The nearest equivalent was tested: setting the ambience volume preference to 0 and watching for new ambience.

1. On a test round, observing as a ghost, opened the Lua editor.
2. Baseline with the preference at 100: the ghost received an ambience sound (`sound/ambience/general/ambigen10.ogg`, volume 27%, on the ambience channel) within a few seconds.
3. Set `sound_ambience_volume` to 0 from Lua with `prefs:write_preference(...)` followed by `apply_to_client_updated(client, 0)`. (`prefs:update_preference(...)` returned FALSE because the preferences window was not open, so `is_accessible` failed; that is a property of the test setup, not of the code being tested.)
4. Result: the stored value was 0, and the number of clients in `SSambience.ambience_listening_clients` went from 1 to 0.
5. Teleported to another area (the Bar, through the Jump To Area verb) and waited 40 seconds: no ambience sound was sent.
6. Set the preference back to 100 and waited 20 seconds: an ambience sound (`ambigen11.ogg`, 27%) arrived.

So nothing turned the ambience back on by itself.

## Cause

The reported behaviour is gone because of how current code handles the preference:

- `/datum/preference/numeric/volume/sound_ambience_volume` (`code/modules/client/preferences/sounds.dm:10-16`) applies the value with `client.update_ambience_pref(value)`.
- `/client/proc/update_ambience_pref` (`code/modules/client/client_procs.dm:1195-1202`) adds the client to `SSambience.ambience_listening_clients` for a non-zero value and calls `SSambience.remove_ambience_client(src)` for 0.
- `remove_ambience_client` (`code/controllers/subsystem/ambience.dm:74-77`) removes the client from the listening list, from `client_old_areas`, and from the running `currentrun` list, so a client removed in the middle of a subsystem pass is not served by it.
- The only place that adds the client again is `update_ambience_pref` itself: at login (`client_procs.dm:583`, which reads the saved preference) and when the preference changes. The subsystem sends area ambience only through `area/proc/play_ambience`, which is called from `SSambience.fire` (`ambience.dm:49`) and, in the same subsystem, overridden for maintenance (`ambience.dm:95`). `play_ambience` also scales the volume by the preference (`ambience.dm:64`). The other `play_ambience` in the code base belongs to the hypertorus fusion core and is a separate proc.

## Fix

None. The reported behaviour does not occur on master.

## Verification

Not applicable (no change). The checks above were run on unmodified master. The reproduction used a ghost observer and set the preference through Lua, not through the preferences window.

Not checked: toggling the preference through the actual preferences UI, a player who is a living mob rather than a ghost, forced area ambience (`forced_ambience` areas), and ship or looping ambience, which have separate preferences (`sound_ship_ambience_volume`).

## Notes

- Minor, not what was reported: setting the volume to 0 stops new ambience, but an ambience sound that is already playing is not cut off. This was seen in the code (nothing stops the channel in `update_ambience_pref`), not tested as a separate case.
- It is not known how or when the old toggle was replaced by the volume preference; only the current code was examined.
