# #70065: Restraints can never be removed while buckled (bear traps, handcuffs in a wheelchair)

| | |
|---|---|
| Issues | [#70065](https://github.com/tgstation/tgstation/issues/70065): verified, fixed on the branch; [#64522](https://github.com/tgstation/tgstation/issues/64522): duplicate of #70065 (same cause), verified fixed by the same commit |
| Status | Reproduced on master and fixed (1 commit) |
| Fix branch | [fix/70065](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/70065) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

A mob buckled to a wheelchair can start removing a bear trap or handcuffs, sit through the whole progress bar, and still end up restrained with no message. `clear_cuffs()` (and the human override of it) refuses to do anything while the mob is buckled, after the `do_after` has already finished. The fix removes the `buckled` condition from both procs.

## The bug

Players in a wheelchair (most noticeably paraplegic characters, who spawn buckled to one) who stepped on a bear trap, or who were handcuffed, could click the restraint alert and watch the progress bar fill, but the restraint was never removed. Nothing was printed at the end. They could only get out by unbuckling first. #70065 reports this for bear traps on any chair or wheelchair; #64522 reports it for handcuffs and paraplegics (and a commenter had seen the bar fill without the unbuckle succeeding either).

Only wheelchairs actually reach the broken code. On an office chair, a buckled mob loses `MOBILITY_MOVE` (observed value 510 for the mobility flags), so clicking the restraint alert does nothing, and the Resist button only unbuckles the mob. Wheelchair riders keep `MOBILITY_MOVE` (the wheelchair gives `TRAIT_NO_IMMOBILIZE`), so they get through to the restraint removal.

## Reproduction

On master `87b93338`, using the Lua editor to set the scene and the real alert click to resist:

1. Spawn a human and buckle it to `/obj/vehicle/ridden/wheelchair`.
2. Equip a `/obj/item/restraints/legcuffs/beartrap` into the legcuff slot (`ITEM_SLOT_LEGCUFFED`, 131072) and set its `breakouttime` to 30 (3 seconds) to keep the test short. Possess the human.
3. Click the "Legcuffed" alert on the HUD (this calls `resist_restraints()`).

Observed on master: "You attempt to remove the bear trap..." appeared, the progress bar ran for its 3 seconds, and then nothing: no "manages to remove" message. Reading the state back with Lua showed `legcuffed` still set to the bear trap and the human still buckled to the wheelchair.

The same was done with handcuffs (`set_handcuffed` plus `update_handcuffed`, then the "Handcuffed" alert) with the same result. With a default `breakouttime`, the bear trap's attempt message said it would take about 30 seconds. With an office chair instead of a wheelchair, clicking the alert did nothing, as described above.

## Cause

Resisting from the alert goes `atom/movable/screen/alert/restrained/Click()` (`code/_onclick/hud/screen_objects/alert.dm:1140`, which requires `MOBILITY_MOVE`) to `resist_restraints()` (`code/modules/mob/living/carbon/carbon.dm:181`) to `cuff_resist()` (`carbon.dm:207`). After the `do_after` completes, `cuff_resist()` returns `clear_cuffs(cuffs, cuff_break)`, and `clear_cuffs()` starts with:

```dm
/mob/living/carbon/proc/clear_cuffs(obj/item/I, cuff_break)
	if(!I.loc || buckled)
		return FALSE
```

(`carbon.dm:243-245`). The human override repeats the same check (`code/modules/mob/living/carbon/human/human.dm:659-663`). So the delay is paid in full and then the removal is refused, silently. The `buckled` condition made the restraints impossible to remove while buckled; since a mob that is buckled to anything but a wheelchair cannot reach this code at all, the check only ever bit wheelchair users.

The Resist button/verb does not help here: `execute_resist()` (`code/modules/mob/living/living.dm:1150`) checks `buckled` first and calls `resist_buckle()`, so the alert is the way to get to `cuff_resist()` while buckled.

## Fix

One commit: "Fix issue 70065: allow removing bear traps and cuffs while buckled". It changes `if(!I.loc || buckled)` to `if(!I.loc)` in `/mob/living/carbon/clear_cuffs()` and in `/mob/living/carbon/human/clear_cuffs()`. The `I in get_all_attached_restraints()` check that follows is untouched, so only restraints the mob actually wears can be removed. The same change fixes both issues, since handcuffs and legcuffs share the code path.

The alternative of making a buckled mob unbuckle first, or of blocking the attempt before the progress bar starts, was not taken: that would require changing the alert and resist flow, and the reports ask for the restraint to come off when the bar completes.

## Verification

On the rebuilt test server, in a wheelchair, with the restraint's `breakouttime` set to 30:

- Bear trap: clicking the "Legcuffed" alert, the bar ran, then "You successfully remove the bear trap." appeared, the alert went away and the item dropped.
- Handcuffs: clicking the "Handcuffed" alert gave "You successfully remove the handcuffs." with the same outcome.
- The runtime log was clean.

Not checked: the unit test suite was not run; the default (unreduced) breakout times were not waited out; nothing other than humans (for example aliens, which have their own `cuff_resist`) was tried; and removal while buckled to something other than a wheelchair, which cannot reach this code through the alert.

## Notes

- Via the Resist button with a buckled mob, the player still gets two steps (`resist_buckle()` to unbuckle first, then the restraint). That behavior is unchanged. #64522's reporter wondered whether doubling the time was intended; this fix does not touch that and only makes the alert path work.
- If the `buckled` check was originally meant to stop restraint removal for some other buckle type (for example a mob buckled to a bed or a chair with restraints), it is not reachable through the alert as tested: those mobs lose `MOBILITY_MOVE`. Other callers of `clear_cuffs()` were not audited.
- The comment on #70065 notes the bear trap behavior is inherited from the leg cuff code; both live in the shared `clear_cuffs()`.
