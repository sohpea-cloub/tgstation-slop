# #44927: Creating a new area with blueprints inside the Free Golem Ship cuts off its power

| | |
|---|---|
| Issues | [#44927](https://github.com/tgstation/tgstation/issues/44927): verified (through the "new area" path, not through renaming) |
| Status | Fixed on the branch below |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/44927 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Redefining a room inside an always-powered ruin area (the issue's example is the Free Golem Ship) with "New Area" moves its turfs into a fresh default `/area`, which needs an APC, so the room loses power. The area-expansion code already skipped such areas in the list of areas that can be expanded, but did not stop the "New Area" option from taking their turfs. The fix makes `create_area()` refuse, with a message to the user, when the room contains any area that does not require power. Renaming an area with "Change area name" does not remove power and was not changed.

## The bug

The issue title says the golem ship loses power when its area is renamed via blueprints. In the comments, other testers found that "Change area name" did not remove any power. Only the "Create or modify an existing area" option did: choosing "New Area" there created a new area over the ship's existing area and removed the ship's power. The last commenter noted that this path ignores existing areas, bypassing the restriction. The same applies to other ruin areas that have no APC and rely on `requires_power = FALSE`.

## Reproduction

1. On the test server, place the Free Golem Ship ruin somewhere (for example in space) using the admin "Map Template - Place" verb and the template "Lava-Ruin Free Golem Ship", centered on a chosen turf.
2. Stand inside the ship and look at the area of the turf (with View Variables). Before the change it was `/area/ruin/powered/golem_ship` with `requires_power` 0 and `power_equip` 1.
3. Use the admin verb "Create Or Modify Area". It calls the same `create_area()` proc the blueprints and the HUD "edit area" button use. The list offered only "New Area". Choose it and enter a name (the test used "Golem Test").
4. The game reported "You have created a new area, named Golem Test." Looking at the turf again, the area was a plain `/area` named "Golem Test" with `requires_power` 1, `power_equip` 0 and `power_light` 0. Lighting objects appeared on the ship's objects and the lights went dark.

Only the admin verb was used, not the blueprint item itself. All three entry points (`code/game/objects/items/blueprints.dm:123`, `code/modules/admin/admin.dm:112`, `code/_onclick/hud/screen_objects/screen_objects.dm:166`) call `create_area()`, so the behaviour is shared.

## Cause

`create_area()` is in `code/__HELPERS/areas.dm:108`. It builds the list of choices, starting with `"New Area"` (line 132), and then walks the turfs of the detected room to add existing areas that may be expanded into. In that loop (line 138):

```dm
if(!place.requires_power || (place.area_flags & NOTELEPORT) || (place.area_flags & HIDDEN_AREA))
    continue // No expanding powerless rooms etc
```

The `continue` only keeps those areas out of the choice list. It does not stop the proc: if the player picks "New Area", `set_turfs_to_area()` moves every turf of the room into the new area. For areas such as `/area/ruin/powered/golem_ship` (the `/area/ruin/powered` base type sets `requires_power = FALSE` in `code/game/area/areas/ruins/_ruins.dm`) there is no APC to power the new area, and the old always-on power is gone.

## Fix

One commit, "Fix issue 44927: blueprints can no longer carve a new area out of an always-powered area". In the loop of `create_area()`, the single combined condition was split:

- If a turf's area does not require power, `create_area()` tells the user "This structure is part of an area that doesn't need an APC (<area name>) and can't be redefined." and returns, before any choice is offered.
- The `NOTELEPORT` and `HIDDEN_AREA` flags keep the old behaviour (the area is just skipped as an expansion choice).
- Blacklisted areas (`/area/space`, station asteroid areas) are still skipped first.

The proc refuses outright because the failure is the new area replacing the always-powered one. No alternative approach was tried.

## Verification

After the fix, the same steps (golem ship placed, "Create Or Modify Area") gave the chat message above, and no choice dialog and no change: the turf's area stayed `golem_ship` with `requires_power` 0 and `power_equip` 1.

Not checked: normal area creation in an ordinary station room (that path is unchanged by the fix but was not re-run), and the blueprint item and HUD button themselves (they use the same proc). Other ruin areas were not tested individually.

## Notes

- The fix refuses any room that includes even one turf of a `requires_power = FALSE` area, not only rooms that are mostly such an area. This also forbids a "New Area" that would take only part of a powerless area; whether that is acceptable is a design choice.
- The issue's title mentions renaming. "Change area name" (`edit_area()` in `code/game/objects/items/blueprints.dm`, using `rename_area()`) was tested by commenters on the issue as not affecting power, and was not changed.
- A comment on the issue suggests instead removing the always-powered flag from such ruins and giving them APCs and generators. That was not explored here.
