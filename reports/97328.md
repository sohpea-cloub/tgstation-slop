# #97328: Move() without a direction calls setDir(null)

| | |
|---|---|
| Issues | [#97328](https://github.com/tgstation/tgstation/issues/97328): verified, fixed |
| Status | Fixed (core movement change, needs careful review) |
| Fix branch | [fix/97328](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/97328) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

`/atom/movable` has two `Move()` overrides. The first replaces a missing direction with `get_dir()`, but only in its own local variable, so the second override still sees `null` and calls `setDir(null)` and sets `last_move = null`. Anything that moves with `Move(turf)` and no direction (the leash component, for one) therefore sends a null direction through `COMSIG_ATOM_DIR_CHANGE`, which is what causes the Virtual Pet runtime in the issue. The fix makes the second override derive the direction from the move and skip `setDir()` when there is none, and guards the Virtual Pet hat code against a missing offsets list.

## The bug

Calls like `Move(turf)` without a direction argument end up running `setDir(null)`. The issue notes that most code does not expect a null direction, so it mostly misbehaves silently. One visible case is a runtime in the Virtual Pet app's hat handling, reported with a pet wearing a hat on a leash. The issue also mentions a second runtime in the same proc, caused by `offsets_list` not being checked before use.

## Reproduction

The Virtual Pet app plus leash reproduction from the issue was not run. Instead, the underlying call was reproduced directly:

1. Using the Lua editor on the test server, spawn a `/mob/living/basic/cockroach`.
2. Register a handler for the `atom_dir_change` signal on it that logs the old and new dir.
3. Call `Move(turf)` on the cockroach with no direction (the call `code/datums/components/leash.dm:153` makes), then `Move(turf, 1)`, then `Move(turf)` again.

Observed on master: the log read `old=2 new=4; old=4 new=nil; old=4 new=1`. The second entry is the bug: a dir change to `nil`. This was a direct call of the proc, not the player scenario from the issue.

## Cause

Both overrides are in `code/game/atoms_movable.dm`. The first, at line 697, has `if(!direction) direction = get_dir(src, newloc)` (lines 705-706), but this changes only its local `direction`. The second, at line 775, takes `direct` straight from the caller. At the end it does `last_move = direct` (line 879) and `setDir(direct)` (line 882). With no direction given, both use `null`, so `last_move` becomes `null` and `setDir(null)` runs and signals listeners.

In `code/modules/modular_computers/file_system/programs/virtual_pet.dm:203`, `set_hat_offsets()` takes the new dir from that signal. With a null dir, `offsets_list` presumably ends up null (the exact lookup was not traced), and the next lines (205-206) index it and runtime.

## Fix

One commit, "Fix issue 97328: Move() without a direction no longer sets dir to null":

- In the second `Move()`, after the move and before `last_move` is set, `if(!direct) direct = get_dir(oldloc, newloc)`. `setDir()` is now called only when `direct` is non-zero. The original (null) argument is still what is passed to the parent proc and to the diagonal-movement logic, so the multi-tile handling the issue worried about is unchanged. This avoids the issue's problem with options 1 and 2, where multi-tile non-diagonal `Move()` calls stopped working.
- In `virtual_pet.dm`, `set_hat_offsets()` returns early when `offsets_list` is null (the second runtime the issue mentions).

## Verification

After rebuilding, the same Lua test logged `old=2 new=4; old=4 new=1; old=1 new=2`: no `nil`, and `dir` and `last_move` were real directions (4 after the first directionless move east). No new runtimes appeared in the runtime log. The Virtual Pet change compiled with 0 errors.

Not checked: the actual Virtual Pet plus leash scenario, other callers of directionless `Move()`, diagonal and multi-tile moves in play, and performance.

## Notes

- This changes the hot path of all movable movement. In particular `last_move` is now set to a real direction for directionless moves, where it was previously null; code that relied on `last_move` being null in that case would behave differently. It deserves careful review.
- `get_dir(oldloc, newloc)` returns 0 for same-turf moves, which is why `setDir()` is skipped for a zero direction.
- Other `COMSIG_ATOM_DIR_CHANGE` listeners were not audited.
