## Summary

The two issues are unrelated bugs that were worked together. The F.R.A.M.E. cartridge's fake uplink never received any primary objectives, so its tab was empty and gave the trick away. The fix gives it a believable set. An implanted uplink could never refund anything, because refunds only run when an item is used on the uplink's parent and an implant cannot be clicked. The fix lets the host refund by clicking themselves with the item while the uplink is open.

## #74750: F.R.A.M.E. fake uplink shows no objectives

### The bug

After a player bought a F.R.A.M.E. cartridge and infected a PDA, the PDA's uplink listed no objectives, unlike a real uplink. Comments on the issue say one player used it to frame someone as a lawyer and was caught at once because the uplink showed no objectives. A commenter guessed that the earlier objectives rework (#71349) did not account for F.R.A.M.E. uplinks.

### Reproduction

1. On the test server, as an observer with the Lua editor, create a human with a mind and two PDAs.
2. Call `send_virus(pda1, pda2, human)` on a `/obj/item/disk/computer/virus/frame`.
3. Call `ui_data(human)` on the uplink component that was added to the target PDA and read `primary_objectives`.

Result on master: `primary_objectives` was nil. The tgui uplink interface hides the objectives tab in that case.

This calls the virus disk's proc directly. It does not use the PDA messaging UI.

### Cause

In `send_virus()` of the F.R.A.M.E. disk (`code/modules/modular_computers/computers/item/disks/virus_disk.dm:124`) a new uplink component is added to the target PDA (line 147) and its handler's `owner` is set, but its `primary_objectives` is never set. The uplink's `ui_data` only sends `primary_objectives` when the handler has them (`code/datums/components/uplink.dm:170-180`), and the interface hides the objectives tab when the data is absent (`tgui/packages/tgui/interfaces/Uplink/index.tsx:232` and `:283`).

### Fix

Commit: "Fix issue 74750: F.R.A.M.E. fake uplinks show believable objectives". It adds `forge_fake_objectives(target_mind)` to the F.R.A.M.E. disk. It builds a list with either an assassinate objective (50%) or a steal objective (50%), whose target is picked with `find_target()`, plus an escape objective. `send_virus()` assigns this list to the new uplink's `primary_objectives`. It is only done when the fake uplink is first created; an uplink that already exists on the PDA is left alone.

### Verification

After the fix the same script gave, for `primary_objectives`: "DIRECTIVE ALPHA: Steal the nuclear authentication disk." and "DIRECTIVE BRAVO: Escape on the shuttle or an escape pod alive and without being in custody." Only the steal variant came up in the run; the assassinate variant was not observed.

Not checked: the objectives tab in the tgui window (no tgui code changed, and it was not opened), the PDA message flow, or the second infection of an already-infected PDA.

## #76595: Implanted uplink cannot refund items

### The bug

A traitor whose uplink is an implant bought a holoparasite, got no ghost for it, and could not refund it.

### Reproduction

1. On the test server, as an observer with the Lua editor, create a human and implant a `/obj/item/implant/uplink` (30 TC) in them. Unlock the uplink so it is active.
2. Buy the holoparasite injector (`/datum/uplink_item/dangerous/guardian`) from it. TC went from 30 to 12.
3. Call `melee_attack_chain(human, human)` on the item. This is what a self-click runs.

Result on master: TC stayed at 12 and the item was kept. The recorded TC figures were 30 before the purchase and 12 after it; the refund attempt did not change them.

This did not use a real click. A self-click was simulated with the attack chain proc.

### Cause

Refunds are triggered through `COMSIG_ATOM_ATTACKBY` on the uplink's parent (`code/datums/components/uplink.dm:54` registers it, `OnAttackBy` at `:114` handles it). With an implant the parent is the implant inside the host's body, which cannot be clicked, so the signal never fires.

A second obstacle came up while fixing it: `COMSIG_IMPLANT_IMPLANTED` (sent at `code/game/objects/items/implants/implant.dm:115`) fires inside the parent `implant()` call, before `/obj/item/implant/uplink/implant()` adds the uplink component (`code/game/objects/items/implants/implantuplink.dm:22`). The component's `Initialize` therefore cannot register for that signal.

### Fix

Commit: "Fix issue 76595: allow refunding items with an implanted uplink".

- In `uplink.dm`, an implant uplink now registers for `COMSIG_IMPLANT_IMPLANTED` and `COMSIG_IMPLANT_REMOVED` (alongside its existing implant signals). New `implant_implanted` registers `COMSIG_ATOM_ATTACKBY` on the host mob; `implant_removed` unregisters it.
- New `host_attackby` runs when the host attacks themselves with an item. It does nothing unless the user is the host, the uplink is active, and the item is an `/obj/item` that is not an implant. Otherwise it sends `COMSIG_ITEM_ATTEMPT_TC_REIMBURSE` to the item, the same signal normal uplinks use, and returns `COMPONENT_NO_AFTERATTACK` if the item was consumed (deleted).
- In `implantuplink.dm`, `implant()` calls `new_uplink.implant_implanted(...)` right after adding the component, to cover the signal that was sent too early.

The alternative of making the implant clickable was not explored.

### Verification

With the same setup after the fix, `melee_attack_chain(human, human)` returned the TC to 30 and the injector was deleted (with sparks). The runtime log showed no runtimes.

Not checked: a real click by a possessed player (a simulated attack chain was used), the case where the implant is removed or the host changes, other refundable items, and the guardian injector being used without ghosts. Refunding requires the uplink to be open, as it does for other uplinks.
