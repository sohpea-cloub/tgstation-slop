## Summary

An AI multicamera (picture-in-picture) window that shows a camera on a lower z-level of a multi-z map is drawn as a plain black rectangle. Only windows on the same plane offset as the multicamera room, which on IceBox means the top level of the station stack, show anything. The multicamera room has nothing on the planes of the lower levels, and the light mask and lighting plates of those levels paint opaque black over everything the windows pull in from below. The fix hides those plates while the AI's plane master group is looking through the multicamera room, and shows them again afterwards. Lower levels therefore appear fullbright inside multicamera windows.

## The bug

Reports:

- #97531: adding a multicamera window for a camera on a different z than the AI core "breaks"; the window shows nothing.
- #77205 (2023): cameras were created while the AI was in its core, then moved. A new multiview made for the lower floor still displayed a blank screen. The screenshot in the issue shows a black window.

The server-side state of such a window is correct (see Reproduction). The window simply renders black, so this is a client rendering problem, not a camera or visibility problem.

## Reproduction

Everything below was done on a test server running master. The map was set to IceBox, whose station is a stack of three z-levels: z2, z3 and z4. z4 is the top level and has plane offset 0, z3 has offset 1, z2 has offset 2. z1 is CentCom, where the multicamera room is; it also has offset 0.

1. Start the round and join as an observer. With the Lua editor, create a human, call `AIize()` on it, and possess the resulting AI (`PossessByPlayer`).
2. On the AI, call `toggle_multicam()`.
3. Call `drop_new_multicam()` three times. After each call, point the new window at a turf with `set_view_center()`, and set each window's `screen_loc` so the three do not overlap. The three turfs were:
   - z2: 77,105
   - z3: 50,102
   - z4: 82,140
   (Lua's `locate` was not callable; `dm.global_procs._locate` was used instead.) This reproduces the situation through procs rather than by clicking in the UI to add each window, but the windows are the real multicamera windows and it is the same code the player's action runs.
4. Look at the rendered screen.

Observed on master: the z4 window shows its content. The z2 and z3 windows are plain black. Server-side values for the black windows were normal: `viewing_turfs` held 9 turfs, the window's AI eye was on the correct z, it saw one camera chunk, and no runtime errors were logged.

Narrowing it down:

- Hiding the camera static images made no difference.
- Setting the lighting plane alpha to 0 made no difference.
- Changing the plane scale transform only changed the size of the black rectangle.
- Hiding the plane master "Light Mask #0" made the z3 window show its content. Also hiding "Light Mask #1" made the z2 window show.
- After that the z2 window was still black; the group's "Lighting plate #1" backdrop was covering it. The z2 turf was really lit (lumcount about 0.88), so this was not a lighting-value problem. Hiding the lighting plate showed it.
- With all of those hidden, all three windows showed their content.

The #77205 steps (cameras moved to a lower floor, a new multiview created there) were not run separately. They describe the same situation: a window on a lower floor of a multi-z map.

## Cause

The windows show other places by adding turfs to the window's `vis_contents` (`code/_onclick/hud/screen_objects/picture_in_picture.dm:154-162`, `refresh_view()`). Those turfs keep their own planes, which are offset per z-level.

The AI looks through the multicamera room while multicam is on (`reset_perspective(GLOB.ai_camera_room_landmark)`, `code/modules/mob/living/silicon/ai/multicam.dm:250`). The room is on z1 (offset 0), and its floor is deliberately put on the maximum-offset plane (`/turf/open/ai_visible`, `multicam.dm:86-100`). So in the window area there is nothing on any of the lower-offset planes.

Two plate types in `code/_onclick/hud/rendering/render_plate.dm` assume something is always drawn there:

- `light_mask` (`render_plate.dm:355-395`): its own documentation says "Any part of this plane that is transparent will be black below it on the game rendering plate". It is built from copies of the space, floor and wall planes of its offset. In the multicamera room, those planes are empty at the lower offsets, so the mask is transparent everywhere and blacks out the game plate below it, including the content of the windows.
- `lighting` (`render_plate.dm:266-324`): it adds a black backdrop (`lighting_backdrop_lit/unlit` fullscreens) that is only cancelled by light sources on the matching offset. The multicamera room lights nothing on the lower offsets, so the backdrop stays opaque over the windows.

A window on the same offset as the room (z4 on IceBox) works because its floors are on the planes the room's plates already cover.

Separately, `light_mask/hide_from` (`render_plate.dm:380-385`) calls `emissive.remove_filter("lighting_mask")` without checking that the emissive plane exists. The fix touches that function, so it was made null-safe.

## Fix

One commit, "Fix issue 97531: AI multicam windows blank for cameras on other z-levels", in `render_plate.dm` and `plane_masters/_plane_master.dm`:

- A new `plane_master/proc/update_multicam_hidden(applies)` in `_plane_master.dm`. If `applies` is true and the group's perspective is an `/obj/effect/landmark/ai_multicam_room`, it calls `hide_plane()` (if not already hidden). Otherwise, if the plane was force-hidden, it calls `unhide_plane()`.
- `light_mask` (every offset) and `lighting` (offset above 0 only) planes now listen to the group's `COMSIG_PLANE_GROUP_PERSPECTIVE_CHANGED`, and call `update_multicam_hidden()` from the signal handler and when they are given a home group. The lighting plate for offset 0 is left alone, so the AI's own offset keeps its normal lighting.
- `light_mask/hide_from` uses `emissive?.remove_filter(...)`.

The pattern copies how the camera static plane already hides and shows itself on perspective changes (`plane_master_subtypes.dm`, the `camera_static` plane). Alternatives such as putting something on every lower-offset plane inside the multicamera room, or giving each window its own lighting, were not tried; hiding the plates is the smallest change and the multicamera room is already a fullbright area.

## Verification

After the fix, on the same IceBox setup and with the same three windows, a render showed content in all three windows (z2, z3 and z4) without any manual plane hiding.

Plane state read back with the Lua editor:

- While multicam was on, Light Mask #0, #1 and #2 and Lighting plate #1 and #2 had `force_hidden` set; Lighting plate #0 did not.
- After `toggle_multicam()` turned multicam off and the AI eye returned to the core, all six planes had `force_hidden` cleared and the perspective was the AI eye again.
- No new runtimes appeared in the round's runtime log other than the usual noise from admin-proc-call wrapping of the Lua editor.

Not checked:

- A real Dream Seeker client. The render used for all before/after checks comes from a test client that emulates plane masters and their relays. It showed the black windows on master, which matches the reports, but whether the real client matches in every detail is unconfirmed.
- The exact steps in #77205 (cameras moved from the core, then a multiview created) and the player-facing "add camera" button, as opposed to calling `drop_new_multicam()` directly.
- Other maps (for example a different layout of z-levels), more than three levels, and AIs with a lighting cutoff or night-vision setting.
- Interaction with other uses of these plates, such as the main game view after leaving multicam mid-round beyond the toggle test above.

Note on method: the test client's session dropped every 10 to 60 seconds while rendering, and each reconnect re-logged the AI and ended multicam, so setup and rendering were done in short bursts.

## Notes

- Trade-off: while multicam is on, lower z-levels are shown fullbright (no lighting, no light mask) in the windows. Same-level content in the multicam room was already fullbright. If a maintainer wants lit lower levels in the windows, the approach would have to change, for example by rendering each window through its own set of plates.
- The fix hides the light mask on all offsets, not only the lower ones. This was a deliberate choice since the room has no use for a light mask, but it was not tested with offset 0 alone.
- #77205 was filed in 2023 against client 514 and is the same symptom, so it is considered a duplicate of #97531.
- No upstream PR that already fixes this was found in the inputs.
