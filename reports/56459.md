# #56459: Hourglass sprite reverts to the unflipped frame when it is not in a hand

| | |
|---|---|
| Issues | [#56459](https://github.com/tgstation/tgstation/issues/56459): verified (reproduced on master) and fixed |
| Status | Fixed on the fix branch; the fix was checked in game, with the limits listed under Verification |
| Fix branch | [fix/56459](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/56459) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The hourglass shows the running sand level only through an `animate()` call on `icon_state`. A client loses that animation when the item leaves and re-enters its view, for example when it is picked up and dropped, and then draws the last animation value, `hourglass_7`. That frame has all the sand at the bottom and looks like an unflipped hourglass. The fix drops the animation. `update_icon_state()` now computes the `hourglass_N` frame from the time left, and a looping timer refreshes it.

## The bug

A player flips an hourglass (using it in hand) and sets it down. The hourglass on the floor looks unflipped, with the sand at the bottom, even though the countdown is still running. The player has to hold it to see how much time is left. The issue reporter says this makes it hard to track time and easy to cheat at a board game by lying about the sand.

The animation does start when the hourglass is flipped. Its final frame is what remains once the client no longer has the animation. The issue's first comment (from 2024) says the same: the animation plays, but the frame from `flick("hourglass_flip", src)` does not stay when the item is dropped, and the admin subtype works as intended. The admin subtype is never held, which fits the cause below.

## Reproduction

The flip and the drop were done by calling procs from the Lua editor, not through the normal player actions (using the item in hand, then dropping it). The result matched what the issue describes, but the real in-hand flip and drop were not exercised.

1. Join the test server as an observer with admin tools and open the Lua editor.
2. Spawn a human and an `/obj/item/hourglass` (default `time` of 1 minute).
3. Put the hourglass in the human's hands and call `attack_self` on it with the human as the user. This is the in-hand flip, which calls `toggle()`. The chat message was "You flip the the hourglass."
4. Immediately call `dropItemToGround` on the hourglass from the human.
5. Inspect the dropped hourglass with View Variables and render it as a client would draw it.

Observed on master, about 3 seconds after the flip, on a 60-second timer:

- The `icon_state` of the dropped hourglass was `hourglass_7`, the last of the 7 sand frames. `timing_id` was still set (the timer was running).
- The client had no `animate()` entry for it, and the render showed the sand all at the bottom.

Control: a second hourglass was spawned on the floor and flipped there with `toggle()`, never held. A render 7430 ms after the flip showed an `animate()` entry of 7 steps over about 60,000 ms, at `hourglass_1` (sand mostly at the top). So the animation runs for an item that stays in view, and it is lost for the item that was in a hand.

## Cause

`code/game/objects/items/hourglass.dm` sets the sand level with a client-side animation and nothing else.

- `start()` (line 36) calls `timing_animation()` (lines 42-46):
  ```dm
  animate(src, time = step_time, icon_state = "hourglass_1")
  for(var/i in 2 to HOURGLASS_STATES)
  	animate(time = step_time, icon_state = "hourglass_[i]")
  ```
  This is one `animate()` chain with 7 steps of `time / 7` each. It ends on `hourglass_7`.
- `update_icon_state()` (line 32-34) only ever picks `hourglass_active` or `hourglass_idle`. Nothing calls it while the hourglass is timing, so the server-side `icon_state` is never the current sand frame.
- `toggle()` (line 23-30) additionally plays `flick("hourglass_flip", src)`, which is also client-side and temporary.

The animation lives only on the clients that were looking at the item when it started. When the item goes into a hand (or out of a client's view) and comes back, for example on pickup and drop, or for a player who comes into view late, the client has no animation for it. It draws the item's actual `icon_state`, and the animation's final value `hourglass_7` is what the client shows afterwards.

The test inspection matched this. The dropped item's `icon_state` was `hourglass_7` and no `animate()` entry was present for it. The exact engine step that discards the animation was not traced; the explanation (the client drops the animation when the item leaves and re-enters its view) is inferred from the missing `animate()` entry and the `icon_state` left behind.

## Fix

One commit, "Fix issue 56459: hourglass sand sprite reverts when dropped", changing only `code/game/objects/items/hourglass.dm`:

- `update_icon_state()` returns `hourglass_idle` when the hourglass is not timing. While timing, it works out the frame from the time left:
  ```dm
  var/step_time = time / HOURGLASS_STATES
  var/step = clamp(HOURGLASS_STATES - ceil((finish_time - world.time) / step_time) + 1, 1, HOURGLASS_STATES)
  icon_state = "hourglass_[step]"
  ```
  The frame is `hourglass_1` at the start and `hourglass_7` in the last seventh of the time.
- A new var `step_timer_id` holds a looping timer (`TIMER_STOPPABLE | TIMER_LOOP`) that calls `update_appearance()` every `time / HOURGLASS_STATES`. `start()` creates it and calls `update_appearance()` once so the first frame is set at once.
- `stop()` and `Destroy()` delete the timer, so no timer outlives the hourglass or runs while it is idle.
- `timing_animation()` and the `animate(src)` reset in `stop()` were removed. `hourglass_active` is no longer used by this code.

The reasoning is that the state a client falls back to is the real `icon_state`, so a server-side value that tracks the time left stays correct for any viewer. No alternatives were recorded as considered.

## Verification

On the test server after rebuilding with the fix:

1. A human and an hourglass were spawned. The hourglass `time` was set to 300 (30 seconds) and the hourglass was put in hand and flipped with `attack_self`.
2. The hourglass was dropped with `dropItemToGround`.
3. A render of the dropped item showed `hourglass_2`. An inspection a few seconds later showed `hourglass_3`. After the timer finished (the "stops" message was seen) the inspection showed `hourglass_idle`.
4. The runtime log of that round had no hourglass runtimes.

Not checked:

- The flip and drop were done through proc calls, not by a player using and dropping the item.
- The in-hand sprite and the inventory slot sprite were not looked at. Held items use their inhand states rather than `icon_state`, so the fix should not change them, but this was not confirmed. The inventory slot icon follows the `icon_state` var, which now changes with time; this was not inspected.
- Only a 30-second timer was tested end to end, not the default 1 minute, and not every intermediate frame.
- The admin subtype (`/obj/item/hourglass/admin`) was not tested with the change, nor was stopping the hourglass by hand (`toggle()` while it runs), nor deleting a running hourglass. The code paths for these go through the changed `stop()` and `Destroy()`.
- The frame timing was not compared against the sprite's frame durations by eye.

## Notes

- The sand level now changes in 7 discrete steps, one per `time / 7`. The old `animate()` also stepped through the 7 `hourglass_N` states, but each of those states has its own looping frames in the icon file; how the new version looks next to the old one was not compared.
- Each step is a normal `update_appearance()` call on the item, which is a small recurring cost per running hourglass (7 calls per run).
- `hourglass_active` is still in the icon file but no longer used by the code. The formula reads `time` at each update, so changing `time` on a running hourglass would shift the displayed frame; nothing in the code does that, and the test only set `time` before flipping.
- `flick("hourglass_flip", src)` in `toggle()` was left as is. It is a short animation and the fix does not depend on it.
- No related upstream fix was found in the inputs.
