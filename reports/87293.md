# #87293: Slimeperson split clones share their gene lists with the original

| | |
|---|---|
| Issues | [#87293](https://github.com/tgstation/tgstation/issues/87293): verified (shared-list cause reproduced on master) and fixed |
| Status | Fixed on the branch; checked in game with the Lua editor, not through the DNA console UI |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/87293 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

`copy_dna()` assigned the source DNA's `mutation_index` and `default_mutation_genes` lists to the copy by reference. A slimeperson's split body therefore shared both lists with the original. Scrambling or editing the clone's genes rewrote the original's genes as well, which is what lets the reported loop of "fix a sequence, print an activator, scramble, repeat" produce unlimited activators. The fix copies both lists, and replaces a reference comparison in `is_same_as()` that only worked because of the sharing.

## The bug

The issue describes this loop: split as a slimeperson, put the clone in the DNA scanner, fix a sequence, print an activator, inject it into the original, scramble the clone's DNA, repeat. Each scramble gives new sequences to fix, and the original's genes change along with the clone's, so the player can keep activating mutations. The cause is that the two bodies do not have independent gene data.

## Reproduction

On master `87b93338`, using admin tools. The steps below reproduce the cause (shared lists), not the full console loop.

1. Start a round and open the Lua editor.
2. Spawn a `/mob/living/carbon/human`, set its species to `/datum/species/jelly/slime`, and give it a mind (`mind_initialize()`).
3. Run the species' `slime_split` action's `make_dupe()` to create the split body. Find the new body in the species' `bodies` list.
4. Compare `mutation_index` of the two DNAs.
5. Call `generate_dna_blocks()` on the clone's DNA, which is what the console's scramble does, and read block 1 of the original's `mutation_index` before and after.

Evidence:
- `h.dna.mutation_index == clone.dna.mutation_index` was true, meaning the same list object.
- Before the scramble the original's block 1 was `/datum/mutation/olfaction`. After scrambling only the clone, it was `/datum/mutation/stoner`.

Not done: the actual DNA scanner and console flow, including printing and injecting activators. The shared list was shown directly instead.

## Cause

`make_dupe()` in `code/modules/mob/living/carbon/human/species_types/jellypeople.dm:349` calls `H.dna.copy_dna(spare.dna, COPY_DNA_SE|COPY_DNA_SPECIES|COPY_DNA_MUTATIONS)`. In `copy_dna()` (`code/datums/dna/dna.dm:83`), the `COPY_DNA_SE` branch does:

```dm
new_dna.mutation_index = mutation_index                          // :90
new_dna.default_mutation_genes = default_mutation_genes          // :91
```

That is a reference assignment, so both DNAs point at the same two lists. `generate_dna_blocks()` then modifies them in place (`mutation_index.Cut()` at `dna.dm:213`, followed by regeneration), so a scramble on either body is a scramble on both. Editing sequences from the console changes the same shared lists.

Other code in the same file already copies these lists: `dna.dm:459-463` uses `.Copy()` for `mutation_index` and `default_mutation_genes` in a different proc.

`copy_dna()` is used by every path that duplicates DNA (the report names slime split, cloning and changelings), so the sharing was not limited to slimepeople. Only the slime split was exercised.

A second line depended on the sharing. `is_same_as()` (`dna.dm:286`) compares `mutation_index == target_dna.mutation_index` (`:289`). For lists in DM this is reference equality, so it returned true only because the lists were shared. After the fix this comparison would always be false.

## Fix

One commit, **"Fix issue 87293: copy_dna no longer shares gene lists between the copy and the original"**, changing `code/datums/dna/dna.dm`:

- `copy_dna()` now assigns `mutation_index.Copy()` and `default_mutation_genes.Copy()`.
- A new proc `same_mutation_index(target_dna)` compares the two lists by value: equal length, and the same value for every key. It does not depend on the order of the entries.
- `is_same_as()` calls `same_mutation_index()` instead of `==`, so comparisons of copied DNA (for example the changeling profile duplicate check) keep working.

The alternative of copying the lists only in the slime split was not taken, because the shared-reference behaviour is in the common helper.

## Verification

After rebuilding, on the test server with the Lua editor, the same split and scramble as above:

- The two `mutation_index` lists were no longer the same object (comparison false).
- `is_same_as()` returned true immediately after the copy.
- After scrambling the clone, the original's block 1 was unchanged (`/datum/mutation/clever`), while the clone's block 1 was `/datum/mutation/clever` and its block 5 `/datum/mutation/adaptation/heat`. Reading from the log, the scramble produced different sequences in the clone only.
- `is_same_as()` returned false after the scramble, as expected for different genes.

Not checked:
- The DNA console and scanner flow (fixing sequences, printing and injecting activators, the scramble button and its cooldown).
- Other users of `copy_dna()` (cloning, changeling transformation and profiles, and others). The new comparison was exercised only on the slime split.
- A full runtime log review beyond the test run.

## Notes

- `copy_dna()` has many callers. A review should look for any caller that relied on the lists staying linked, though none was found.
- `same_mutation_index()` is order-independent because `mutation_index` is an associative list keyed by mutation type. If the project prefers a shared helper for associative list comparison, it could replace it. A search found none under the names tried.
- The fix is cheap: two list copies when DNA is copied with `COPY_DNA_SE`.
- No upstream pull request addressing this was found in the inputs.
