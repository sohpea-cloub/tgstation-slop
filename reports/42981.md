## Summary

The issue (2019) says that a ghost who observes a player opening a safe, and then stops observing, keeps getting the safe window popped open whenever the player turns the dial. In the current code an observer cannot receive another player's tgui window: each `/datum/tgui` is created for one user and opens a window for that user's client only, and observing only changes the ghost's eye and HUD. The test server only had one client, so the real two-player scenario could not be run. The conclusion rests on reading the code plus a partial in-game check. No fix was written.

## The bug

As reported: a ghost observes a player who is opening the vault safe, then leaves observe mode. Afterwards the safe window opens on the ghost's screen again, and keeps reopening each time the player turns the dial left or right (closing it does not help). A comment on the issue describes a similar case with a backpack: a former observer gets the backpack's storage window opened later when the owner puts something in it. A third comment asks for observers to see extra information (changeling abilities, security gas masks). That is a feature request, not part of this report.

## Reproduction

Not reproduced. A faithful test needs two real clients: one player using a safe and a ghost observing them. The test server had a single client, so this was approximated with admin tools:

1. With the Lua editor, spawned a human and a safe, made the test client possess the human, and called `ui_interact` on the safe for that human.
2. Ghosted the human's body and, as the resulting ghost, called `do_observe` on the human. Called `ui_interact` for the human on the safe again, then ended observing with `reset_perspective(null)`.
3. Looked at the safe's `open_uis` and at the client's tgui windows. `open_uis` was nil (reading its length in the Lua editor raised "attempt to get length of a nil value"), no Safe interface window was open, and the only extra window was a bare pooled one that had received just asset mappings.

This check is weak. The "player" and the observer were the same client, and the human's UI was opened before ghosting. It shows that no UI was attached to the safe or the observer in this setup. It does not show that the real two-player case is fine. A proper test with two clients is still needed to settle it empirically.

## Cause

Not applicable, because the behaviour was not found. These are the code facts behind the conclusion (all at master):

- A `/datum/tgui` is tied to one user. `/datum/tgui/New` stores `src.user = user` (`code/modules/tgui/tgui.dm:62`). `open()` returns early without `user.client` (`tgui.dm:86`) and takes a pooled window for that same user (`tgui.dm:93`).
- `SStgui.get_open_ui` matches on `ui.user == user` (`code/controllers/subsystem/tgui.dm:203-206`). `update_uis` loops over the `open_uis` of the source object and processes each UI, but each of those UIs belongs to the user it was created for (`tgui.dm:218-228` in the subsystem file).
- `/obj/structure/safe/ui_interact` only creates or updates a UI for the mob it is called with (`code/game/objects/structures/safe.dm:172-176`).
- Observing does not touch tgui. `do_observe` sets the client's eye and perspective, registers a z-change signal, and shows the target's HUD to the observer through `mob_eye.observers` (`code/modules/mob/dead/observer/observer.dm:890-916`). `cleanup_observe` undoes that (`observer.dm:878-888`). Neither calls `ui_interact` or reads `tgui_open_uis`. `code/modules/tgui` mentions observers only for UI status checks (`states.dm:25`, `status_composers.dm:30`, `states/observer.dm`) and a flag sent to the interface (`tgui.dm:286`).

## Notes

- The report is from 2019 and describes the old NanoUI/tgui arrangement. The tgui code today has no mechanism that mirrors one player's window to an observer. The most plausible reading is that the original bug was removed when tgui was rewritten. I could not confirm this.
- The backpack comment appears to involve a different mechanism: the HUD and the storage screen shown to observers (`code/_onclick/hud/hud.dm:382-398`, `code/modules/mob/inventory.dm:498`), not tgui. It was not investigated further and should be a separate report if it still happens.
- `SStgui.on_transfer` (`code/controllers/subsystem/tgui.dm:382`) does change a UI's owner. It is called when a player's own body turns into a ghost (`code/modules/mob/dead/observer/observer.dm:282`) or when a mind moves between bodies (line 377). It moves the player's own windows to their new mob. It is not triggered by observing.
- Suggested handling: close as no longer reproducible, unless someone with two clients can still show the safe window reopening.
