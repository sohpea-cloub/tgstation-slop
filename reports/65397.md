## Summary

`*flap` and `*aflap` had no check that the user has wings, so wingless humans and cyborgs printed "flaps their wings." anyway. The only usability requirement on them was "needs hands", which every human passes. The fix makes both emotes require a wings organ in the external wings slot. A second commit addresses #86476: emotes that need hands were listed by `*help` (and usable) for positronic brains, because the hands check was skipped for `*help` and brain mobs inherited two default hands. Brains now have zero default hands, and the hands requirement is enforced for any living mob with zero default hands.

## The bug

### #65397

A player with no wings (a plain human, or a cyborg) types `*flap` or `*aflap` and gets "You flap your wings" style output, with the message shown to everyone nearby. Nothing else happens, since there are no wings to animate, but the message is still printed.

### #86476

A ghost that haunts a positronic cube and types `*help` sees a list of emotes that includes ones needing hands (the reporter tried to spin and could not). The list claimed emotes were available that the cube could never sensibly use. The investigation found it is worse than the list alone: the hand emotes were also runnable by brain mobs, because the only hands check is the `TRAIT_HANDS_BLOCKED` trait, which brains do not have.

## Reproduction

Both were checked on master with the Lua editor as an observer, by calling each emote's `can_run_emote(mob, FALSE, TRUE)` on spawned mobs and by calling `emote()` on a human. The `*help` text itself was not read from a possessed brain; `*help` filters with `can_run_emote(status_check = FALSE)`, which is the call that was made.

1. Spawn a human, a human with a wings organ inserted (a moth human), a cyborg, and a `/mob/living/brain`.
2. For each, call `can_run_emote` for `flap`, `aflap`, `spin`, `wave` and `dap` (looked up in `GLOB.emote_list`).
3. Call `emote("flap")` on the wingless human.

Results on master (1 = allowed; the moth human was not measured before the fix):

| Emote | human | cyborg | brain |
|---|---|---|---|
| flap | 1 | 1 | 0 |
| aflap | 1 | 1 | 0 |
| spin | 1 | 1 | 1 |
| wave | 1 | 1 | 1 |
| dap | 1 | 0 | 0 |

The wingless human's `*flap` printed "flaps her wings." on the server. The brain's `spin` and `wave` were allowed (1), which is the #86476 symptom. The agents' notes are inconsistent about `wave` on the brain (the raw numbers say 1, a parenthetical says 0), so that cell is uncertain. `flap` and `aflap` were already 0 for a brain on master; the cause of that was not investigated.

## Cause

### #65397

`/datum/emote/living/flap` (`code/modules/mob/living/emote.dm:158`) sets only `can_use_flags = EMOTE_CANUSE_REQUIRE_HANDS`, and `/datum/emote/living/flap/aflap` inherits that. Wings are never checked in `can_run_emote`. `run_emote` (`code/modules/mob/living/emote.dm:165`) fetches the wings organ and simply returns early if there is none, but by then the parent `run_emote` has already printed the message:

```
var/obj/item/organ/wings/wings = human_user.get_organ_slot(ORGAN_SLOT_EXTERNAL_WINGS)
// play a flapping noise if the wing has this implemented
if(!istype(wings))
	return
```

### #86476

Two things combine:

- `can_run_emote` in `code/datums/emotes.dm:383` performs the hands check (`HAS_TRAIT(user, TRAIT_HANDS_BLOCKED) && (can_use_flags & EMOTE_CANUSE_REQUIRE_HANDS)`, line 395) only inside the `if(status_check && ...)` block. `*help` calls it with `status_check = FALSE`, so the check never applies to the listing.
- `/mob/living/brain` (`code/modules/mob/living/brain/brain.dm`) inherits `default_num_hands = 2` from `/mob/living` (`code/modules/mob/living/living_defines.dm:136`), and has no `TRAIT_HANDS_BLOCKED`, so even with `status_check = TRUE` the emotes pass.

## Fix

Commit "Fix issue 65397: *flap and *aflap require a wings organ" overrides `can_run_emote` on `/datum/emote/living/flap`. It returns FALSE unless `user.get_organ_slot(ORGAN_SLOT_EXTERNAL_WINGS)` is an `/obj/item/organ/wings`, then defers to the parent. Because `aflap` is a subtype, it is covered too. Making the check part of `can_run_emote` also removes the emote from `*help` and from the emote menu for wingless mobs.

Commit "Fix issue 86476: emotes that need hands are not available to handless brains" does two things:

- In `can_run_emote`, before the `status_check` block, an emote with `EMOTE_CANUSE_REQUIRE_HANDS` now returns FALSE for any living user whose `default_num_hands` is 0, regardless of `status_check`. This is what makes `*help` honest.
- `/mob/living/brain` sets `default_num_hands = 0`.

An alternative would be to move the whole `TRAIT_HANDS_BLOCKED` check outside the `status_check` block. The inputs do not record whether this was considered; the chosen check is narrower, since it only affects mobs that never have hands and leaves the temporary `TRAIT_HANDS_BLOCKED` behavior of `*help` unchanged.

## Verification

After the fix, on the test server, using the same calls as above:

- `flap` and `aflap`: human 0, moth human 1, cyborg 0, brain 0.
- `spin`: human 1, moth human 1, cyborg 1, brain 0. `wave` on the brain: 0.
- `emote("flap")` on the wingless human returned 0 and printed nothing. On the moth human it returned 1 and printed "flaps her wings." with the moth flutter sound.
- No new runtimes in the runtime log.

Not checked: the `*help` text in an actually possessed positronic cube (only the `can_run_emote` call it makes); typing `*flap` from a real player client; any wing species other than the moth human; the wing-open/close animation after the change.

## Notes

- Side effect: alien larvae already set `default_num_hands = 0` (`code/modules/mob/living/carbon/alien/larva/larva.dm:20`), so they also lose hand-requiring emotes. That is consistent with the intent but is a behavior change.
- Non-carbon mobs can no longer `*flap`. None of them could have a wings organ, so nothing real is lost.
- The `*flap` emote still carries `EMOTE_CANUSE_REQUIRE_HANDS`, which is unrelated to wings; it was left alone.
- The #86476 comment asks why spinning needs hands at all. That is a design question and was not changed; the fix only makes the existing flag consistent.
- Upstream: #50187 was an earlier report closed as "not a bug". Earlier PRs for #65397 were closed, not merged.
