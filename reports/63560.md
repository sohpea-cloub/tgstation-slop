## Summary

Both issues say that making several different announcements from the communications console earns the player an "identical messages" auto-mute, as if the announcements were the same phrase. On master, five distinct priority announcements in a row from a non-admin player produced no warning, no mute and no "..." replacement. The code explains why: the identical-message check compares each message with the previous one and resets its counter when they differ, and the console's 30 second announcement cooldown keeps announcements far below the separate rate limiter. No fix was made. The original reports probably came from older console code or from other speech by the same player being counted.

## The bug

Reported behaviour:

- #63560 (December 2021): "Use the Priority Announcement feature on the command consoles repeatedly. Whether you make different announcements or not doesn't matter." The player ends up with an unexpected IC mute, "because apparently they're all treated as the same phrase to the auto-ic spam filter".
- #50132 (March 2020): an AI, with telecomms destroyed, made many different comms-console announcements, got the "approaching the spam limit for identical spoken phrases" warning, was eventually muted, and all later announcements turned into "...". The reporter was unsure whether it was intended.

## Reproduction

The behaviour could not be reproduced. What was done, with admin tools on the test server:

1. The auto-mute is off by default (`#AUTOMUTE_ON` is commented out in `config/config.txt:276`). It was enabled in the test server's config and the server was restarted. A first attempt through the in-game Reload Configuration verb did not apply the setting.
2. To confirm that the check was live, a non-admin player said "spam" six times and received "You are nearing the auto-ban limit for identical messages". The check is skipped for admins (`!holder`), so the tester used the Deadmin verb to drop admin rights. The Lua editor could not do this itself, since calling `datum/admins/deactivate` from Lua is blocked as a permission elevation.
3. A human was spawned at the bridge holding a captain's spare ID, and the test player was moved into it. Because of the 30 second announcement cooldown, a Lua timer loop zeroed `GLOB.communications_controller`'s `silicon_message_cooldown` and `nonsilicon_message_cooldown` every second, so that announcements could be sent quickly. This makes the test harsher than real play.
4. At the bridge communications console the player clicked it with the ID, toggled authentication, then used Make Priority Announcement five times with different texts ("alpha one", "bravo two", "charlie three", "delta four", "echo five"), over about 40 seconds. An earlier run on the first boot of the server made two more.

Observed: every announcement went out with its own text. There was no spam warning, no mute, and no "..." substitution.

## Cause

There is no defect on master matching the reports. The relevant flow:

- `make_announcement` in `code/game/machinery/computer/communications.dm:778` first checks the cooldown (`can_announce`, `code/datums/communications.dm:34`), asks for the text, then calls `user.try_speak(input)` exactly once (line 786). If that fails (for example because the player is already IC-muted), it replaces the text with `"..."` (line 792) and the announcement goes out as an awkward silence.
- `try_speak` (`code/modules/mob/mob_say.dm`, around line 81) calls `client.handle_spam_prevention(message, MUTE_IC)`.
- `handle_spam_prevention` (`code/modules/client/client_procs.dm:194`) has two checks. The rate limiter (lines 207-215) counts messages in a 5 second window and only acts at `SPAM_TRIGGER_AUTOMUTE` (10) messages. The identical-message check (lines 218-236) runs only when `AUTOMUTE_ON` is set and the player is not an admin, and only increments its counter when `last_message == message`. A different text takes the `else` branch, which stores the new message and sets `last_message_count = 0`. Distinct announcements therefore cannot build up an "identical" count.
- The announcement cooldowns are 30 seconds (`COMMUNICATION_COOLDOWN` and `COMMUNICATION_COOLDOWN_AI`, `code/datums/communications.dm:1-2`), so even normal announcement spam stays well under the rate limiter.

An announcement can look like spam to this filter only if its text is identical to the player's previous `try_speak` message (the same text repeated, or repeated "..."), or if the player was already muted. The second case matches the "all my announcements became ..." symptom in #50132: that is a consequence of an earlier mute, not its cause.

Other speech by the same player also passes through `last_message`, so an announcement that repeats the player's last spoken line would count as identical. Whether this explains the original reports is a guess; no pull request mentioning either issue number was found.

## Fix

None.

## Verification

Checked in game, as a non-admin player with `AUTOMUTE_ON` active: five distinct priority announcements, with the cooldown bypassed, produced no warning or mute. The same player received the identical-message warning when saying the same word six times, so the filter was working.

Not checked:
- The AI mob. It goes through the same `try_speak` path (the AI-specific differences are the cooldown variable and `minor_announce`, and `try_speak` has a separate silent-AI config check), but it was not run, so #50132 is an inference from the shared code path.
- Repeating the identical announcement text, which should warn and eventually mute by design.
- The behaviour of the real tgui text input in a normal client; the test submitted the input through the tgui interface by admin tooling rather than a browser.

## Notes

- The two issues look like the same report across a gap of two years. Both can be closed as not reproducible on current code, unless someone can supply a sequence that actually repeats the same message text.
- Repeating the same announcement text is treated as spam by design, and it is the likeliest way a player could reach the warning in practice.
- With `AUTOMUTE_ON` disabled (the default in `config/config.txt`), the identical-message check never fires at all; only servers that enable it are affected.
