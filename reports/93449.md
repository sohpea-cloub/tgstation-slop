## Summary
**#93449.** Copying a MODlink frequency from a scryer to a suit with a multitool worked in every flow tried. The multitool code did give misleading or no feedback: it said "frequency set" before the Copy/Imprint choice, and was completely silent when neither the multitool buffer nor the device had a frequency. A shared helper now reports only the action taken and says "no frequency!" when there is nothing to copy. **#77883.** The hologram at the far end of a MODlink call spoke as "holocall (id)"; it now speaks with the mirrored user's voice.

## The bug
### #93449
The report says linking a modsuit to a scryer with a multitool fails with no error from either device. It adds that it may never have worked.

### #77883
When answering a MODlink call, the speaker appears in chat as the MODlink ID rather than by name.

## Reproduction
### #93449
1. On the test server, using admin tools, spawn a human, an engineering MOD suit worn on the back, a link scryer and a multitool.
2. Right-click the scryer with the multitool, then right-click the suit. This was done with real right-clicks on the worn suit and by calling the attack chain with a right-click from the Lua editor. The scryer's frequency was copied to the multitool buffer ("frequency copied"). Right-clicking a suit with no frequency then set it.
3. With a scryer on frequency CHRL copied to the buffer, right-clicking a suit on frequency NT opened the "MODlink Frequency" Copy/Imprint alert; Imprint set the suit to CHRL (checked in `GLOB.mod_link_ids`). This worked with the panel closed and not in combat mode.

The defects were found by reading the code and confirmed by return values:
- The balloon "frequency set" and a success result fired as soon as the buffer held a MODlink, before Copy or Imprint was chosen, so choosing Copy still said "frequency set".
- If the buffer was empty and the device had no frequency (suits and scryers built at a lathe have a null frequency), the proc returned `NONE` with no balloon. This silent failure matches the report.

### #77883
1. Using the Lua editor, create a call with `new /datum/mod_link_call(suit.mod_link, scryer.mod_link)`.
2. Have the suit's wearer say "Hello from the suit".
3. The receiver's chat showed `The holocall (619) says, "Hello from the suit"`.

## Cause
### #93449
Both `/obj/item/mod/control/multitool_act_secondary` (`code/modules/mod/mod_link.dm:78`) and `/obj/item/clothing/neck/link_scryer/multitool_act_secondary` (line 236) held the same copy-pasted logic: it set the "frequency set" balloon and success whenever the buffer was a MODlink, and had no branch for "nothing to copy and nothing to set".

Also noticed and not changed: in `code/modules/mod/mod_control.dm` (`tool_act`, line 304) an open panel sends a multitool to the wires UI before `multitool_act_secondary`, and in combat mode `tool_act` is skipped. These could make the multitool seem to do nothing, but were not tested as a cause of the report.

### #77883
`make_link_visual_generic` (`code/modules/mod/mod_link.dm:1`) makes a plain `/obj/effect/overlay` named "holocall (id)" (lines 3-4). The suit's and scryer's `Hear()` make that hologram `say()` what it hears, and a plain atom's `get_voice()` returns `"[src]"` (`code/game/say.dm:383`), hence "The holocall (id)".

## Fix
**"Fix issue 93449: MODlink multitool copy/imprint gives honest feedback."** A shared proc, `mod_link_multitool_act`, replaces the duplicated code in both `multitool_act_secondary` procs. It balloons "frequency copied" or "frequency set" only for the action taken, returns "no frequency!" with a blocking result when there is nothing to copy, and keeps the Copy/Imprint alert when both the buffer and the device have frequencies. Setting a frequency on a device with none now says "frequency set" (it was previously silent).

**"Fix issue 77883: MODlink hologram speaks with the user's voice."** A new `/obj/effect/overlay/modlink_hologram` holds the `mod_link` (cleared in `Destroy`) and overrides `get_voice(add_id_name)` to return the mirrored user's `get_voice(add_id_name)`, falling back to the default. `make_link_visual_generic` creates this type. Reusing the user's own `get_voice` keeps behaviour such as "Unknown" for a masked wearer. The hologram's name stays "holocall (id)".

## Verification
- #93449, using the real procs from Lua: a blank scryer returned the blocked result and left the buffer empty; a scryer on CHRL returned success and filled the buffer with its link; applying that buffer to a blank device set the frequency to CHRL.
- #77883, after rebuilding: the same call with the wearer ("Testa Suitwearer") saying hello gave the receiver `Testa Suitwearer says, "Hello from the suit"`. The runtime log showed no `mod_link` runtimes.
- Not checked: the balloon texts themselves (they did not show for items on the floor; only return values were checked), the Copy/Imprint alert after the refactor, masked wearers for #77883, and whether the reporter's lathe-built suit scenario is what they hit.

## Notes
- The #93449 change is a UX change, not proof of the reporter's failure. If the reporter's suit had a null frequency and the scryer had none, the new "no frequency!" message would now explain it. The panel-open and combat-mode paths remain as possible causes.
- The reporter also suggested scryers be a module or built into the suit; that is a design request and was not addressed.
