## Summary

Alt-clicking a paper folds it into a paper plane. If a second alt-click lands on the paper while it is already inside its plane, `make_plane()` folds it again, and the original plane is deleted together with the new plane and the paper. The fix makes `click_alt()` and `make_plane()` refuse to fold a paper whose location is a paper plane. The second issue is separate: any text written with white ink (the invisible ink pen) switched the paper to its "written" icon, so the page looked written on. The fix only switches the icon when some text, or the paper itself, is not white.

## #78676: paper vanishes when alt-click is spammed

### The bug

Players reported that spamming alt-click on a paper (or a pile of papers) folds it into a paper plane and then leaves nothing: no plane and no paper. One commenter could not reproduce it. Another (a maintainer) said they wanted the behaviour kept as a harmless exploit but agreed it is a bug.

What happens is that a click can target the paper while it is already inside the plane it was just folded into (for example a lagging or repeated click). The check that a user may alt-click an item in their hands still passes for a paper inside a plane that the user is holding, so `click_alt()` runs on it a second time.

### Reproduction

The original report involved spamming the click. It was reproduced here by calling the procs the click uses, not by clicking quickly:

1. Start a round on the test server and open the Lua editor as an observer.
2. In a Lua state, spawn a human and a `/obj/item/paper`, and put the paper in the human's hands.
3. Call `make_plane(human)` on the paper. This is what a single alt-click does. The paper is now inside a paper plane held by the human.
4. Call `AltClickOn(paper)` on the human. This stands in for the extra click that targets the paper inside the plane.

Observed on master: the Lua call returned a "destructed callback or destructed userdata" error, and the runtime log showed `Cannot read null.stamp_cache` at `code/modules/paperwork/paperplane.dm:68` (`update_overlays`), raised from the `Initialize` of the second plane. The first plane had been deleted, and the paper had been deleted with it.

### Cause

`click_alt()` (`code/modules/paperwork/paper.dm:393`) always calls `make_plane()`, with no check on where the paper is. In `make_plane()` (`paper.dm:410`) the paper's `loc` is the first plane, so the new plane is created inside the first plane:

```dm
var/obj/item/paperplane/new_plane = new plane_type(loc, src)
```

The new plane's `Initialize` (`paperplane.dm:24`) then calls `paper_made_of.forceMove(src)`, which moves the paper out of the first plane. The first plane's `Exited()` (`paperplane.dm:40`) treats that as its internal paper leaving and deletes the plane:

```dm
/obj/item/paperplane/Exited(atom/movable/gone, direction)
	. = ..()
	if (internal_paper == gone)
		internal_paper = null
		if(!QDELETED(src))
			qdel(src)
```

Deleting the first plane deletes its contents, which include the new plane that was just created inside it, and that plane now holds the paper. Everything is gone.

### Fix

Commit "Fix issue 78676: don't fold a paper that is already inside a paper plane" (`code/modules/paperwork/paper.dm`):

- `click_alt()` returns `CLICK_ACTION_BLOCKING` when `loc` is a `/obj/item/paperplane`.
- `make_plane()` returns `null` in the same case, so any other caller is protected too.

### Verification

After the fix, the same script was run on the test server with two extra alt-clicks on the paper after it had been folded. The plane and the paper both still existed, the paper's location was still the plane, and no runtime was logged.

Not checked: real rapid clicking from a client, and the Syndicate paper plane path (`TRAIT_PAPER_MASTER`), which goes through the same guard in `click_alt()` but was not exercised.

## #73684: invisible ink changes the paper's icon

### The bug

The issue has two claims. (1) Writing on paper with an invisible ink pen still switches the paper's icon to the "written" one, so the paper looks written on even though the ink is invisible. (2) If the paper is coloured, the invisible ink is fully visible; the reporter was unsure whether this is intended.

### Reproduction

1. Start a round on the test server and open the Lua editor.
2. Spawn a `/obj/item/paper`, call `add_raw_text('hi', nil, '#FFFFFF', false, false)` on it (white ink, as the invisible pen writes), then `update_appearance()`.
3. Read its `icon_state`.

On master (from the code, not from a before-fix run): `update_icon_state()` (`paper.dm:321`) checked only `LAZYLEN(raw_text_inputs)`, so the icon state was `paper_words` regardless of ink colour.

### Cause

```dm
/obj/item/paper/update_icon_state()
	if(LAZYLEN(raw_text_inputs) && show_written_words)
		icon_state = "[initial(icon_state)]_words"
```

Any text input, of any colour, counts as written words.

### Fix

Commit "Fix issue 73684: invisible ink doesn't change the paper's icon". A new `has_visible_text()` proc returns TRUE only if the paper has text and either the paper's own colour is not white or at least one text input has a colour that is not white (a missing colour counts as visible). Comparison is case-insensitive against `COLOR_WHITE`. `update_icon_state()` now uses `show_written_words && has_visible_text()`.

Only the icon changes. The text is still readable by anyone who opens the paper.

The second claim was deliberately left alone. White ink on coloured paper still shows and still switches the icon, because the one comment on the issue asks that this keep working for mime crayons, white crayons and the mime stamp.

### Verification

On the test server after the fix, a paper with one text input gave these `icon_state` values:

| Ink colour | Paper colour | `icon_state` |
|---|---|---|
| `#FFFFFF` | default | `paper` |
| `#ffffff` | default | `paper` |
| `#000000` | default | `paper_words` |
| `#FFFFFF` | red | `paper_words` |
| nil | default | `paper_words` |

Not checked: the other users of `show_written_words` (mail, bodybags, airlock pinned paper) beyond reading the code, and a real invisible ink pen used by a player.

## Notes

- Both changes are in `code/modules/paperwork/paper.dm`.
- The #78676 guard also stops the paper being folded from inside any plane via other callers of `make_plane()`; the only caller found was `click_alt()`.
- Whether the maintainer's wish to keep the vanishing paper as a "funny exploit" still holds is for maintainers to decide; the guard removes it.
