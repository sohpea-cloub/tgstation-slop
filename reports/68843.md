## Summary

A wheelchair with a rider on a conveyor belt was moved twice per belt tick, so it skipped a tile each step and looked like it was teleporting. The rider (a mob) gets its own conveyor move loop, and moving a buckled mob moves the thing it is buckled to, so the chair was carried once by its own loop and once by the rider's. The fix makes a buckled mob skip its conveyor step. A second fix, for #97499, makes conveyor belt assemblies merge when one is clicked onto another: `/obj/item/stack/conveyor/item_interaction` returned `NONE` instead of calling the parent. #68886 (pulled objects turning the wrong way on a corner belt) did not reproduce.

## The bug

### #68843
A player in a wheelchair on a running conveyor was carried much faster than items on the same belt and appeared to jump from tile to tile. A commenter on the issue suspected all rideables were affected; the cause found here applies to anything a mob is buckled to that can be conveyed.

### #68886
The report says a locker pulled onto a west-to-south corner belt moved east instead of south.

### #97499
A belt assembly obtained by crowbarring a placed belt would not stack with belt assemblies already held. The report also says placed belts "do drop stack", which matches the stacks merging at creation time but not when clicked.

## Reproduction

### #68843
1. In the Lua editor, spawn 13 `/obj/machinery/conveyor/auto` belts in a row facing east (direction 4).
2. Spawn a `/obj/vehicle/ridden/wheelchair` on the first belt, spawn a human there and buckle them to the chair. Spawn a crate and a toolbox on the same start tile.
3. Log the x coordinates of the chair, rider, crate and toolbox every 0.2 s with `SS13.set_timeout`.

Observed on master: the crate and toolbox advanced one tile every 0.2 s. The chair and rider moved together but in jumps of two tiles every 0.4 s: x = 100, 100, 100, 100, 102, 102, 104, 104, 106, 106, 108, 108, 110 over 13 samples.

### #68886
1. Place a south-east auto belt (the west-to-south corner) with south-facing belts below it.
2. Spawn a closed locker on the corner and a human pulling it from the west.

The locker moved south, one tile, the same as an unpulled locker on the same belt. The pulled one started about two ticks later; that is a delay, not a direction error. An attempt to drag the locker onto the belt by moving the puller with a Lua `Move` call was unreliable, so the "pulled onto the belt" path was not properly exercised. The conclusion rests on a locker that was pulled while already standing on the belt; confidence is low to medium.

### #97499
Done by calling procs from the Lua editor, not by the player action. Two `/obj/item/stack/conveyor` stacks were created. `can_merge` returned TRUE, and stacks created on the same tile merged at creation (the "drop stack" behaviour in the report). Calling `item_interaction(user, other_stack)` on one stack with the other returned 0 (`NONE`) and nothing merged. A real crowbar-removed belt was not tried (the tool use takes about 4 seconds); it is the same stack type with the same `merge_type`, and `mats_per_unit` and `id` did not block `can_merge` in the tests.

## Cause

### #68843
In `code/datums/components/conveyor_movement.dm`, `/datum/component/convey` creates a move loop for any movable on a belt (`:19`). The loop's check, `should_move` (`:24`), skips the step for flying mobs, anchored things and things without gravity, but not for buckled mobs. When the chair is moved by its belt, the rider enters the next belt tile with it and gets its own convey loop. Moving a mob goes through `/mob/living/Move` (`code/modules/mob/living/living.dm:1048`):

```dm
if (buckled && buckled.loc != newloc) //not updating position
	if (!buckled.anchored)
		. = buckled.Move(newloc, direct, glide_size)
```

so the rider's loop calls `Move` on the chair. Per tick the chair moved once from its own loop and once from the rider's.

### #68886
No defect found. The 2022-era report did not reproduce on master; it was possibly fixed by the later rewrite of conveyor movement to move loops (not verified against history).

### #97499
`code/modules/recycling/conveyor.dm:679-680`:

```dm
/obj/item/stack/conveyor/item_interaction(mob/living/user, obj/item/tool, list/modifiers)
	if(!istype(tool, /obj/item/conveyor_switch_construct))
		return NONE
```

This override replaces `/obj/item/stack/item_interaction` (`code/game/objects/items/stacks/stack.dm:812`), which merges stacks when `can_merge` allows it. Returning `NONE` for every non-switch tool meant the parent's merge never ran.

## Fix

- **Fix issue 68843: buckled mobs no longer double-move their vehicle on conveyors.** `should_move` now returns `MOVELOOP_SKIP_STEP` when `moving_mob.buckled` is set. The buckled thing is conveyed by its own loop, so the rider needs none. This was preferred over special-casing wheelchairs because the same doubling applies to any conveyable buckled-to object.
- **Fix issue 97499: conveyor belt assemblies can be merged by clicking.** The early `return NONE` became `return ..()`, so non-switch tools fall through to the stack merge handling.

## Verification

- #68843: same setup after the fix, the chair and rider advanced one tile per sample (x = 100, 100, 100, 101, 102, 103, ... 111), matching the crate.
- #97499: same proc call after the fix returned 1 (`ITEM_INTERACT_SUCCESS`) and the target stack held 3 (1 + 2 merged).
- Not checked: a real player clicking a stack with a crowbar-removed belt; a human player in the chair, as opposed to a spawned human buckled by script; other buckled-to objects (beds, other vehicles); #68886 beyond the case above.

## Notes

- In one run, an empty wheelchair spawned on a belt tile did not move while one spawned on the next tile did. This was not investigated and is not explained by the fix.
- Whether the fix changes anything for unconscious or flying buckled mobs was not tested. They were already treated specially before the new check.
