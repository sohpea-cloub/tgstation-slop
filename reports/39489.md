# #39489: Examining turfs from inside a mech silently does nothing

## Summary

A human pilot inside a mech cannot examine turfs: nothing is printed, with no error. `/mob/proc/run_examinate` rejects turfs that are not in `view(client.view, src)`, but when `src` is inside a mech, `view()` centered on it returns only the mech's contents, so no turf is ever in the list. The fix centers that `view()` on the turf the client's eye is looking from, `get_turf(client?.eye || src)`, in `run_examinate` and in the "examine closer" topic link. After the fix, turfs near the mech can be examined from inside it, and turfs far outside the view are still rejected. #82726 (brains in a mech) did not reproduce: a brain pilot could already examine objects and turfs on the unfixed logic.

## The bug

### #39489

The issue reports that nothing happens when you examine something from inside a mech. Early comments say shift-click works. A later comment narrows it down: examining fails for turfs only, by right-click or shift-click, while objects work with shift-click.

On master, examining an object or a mob from inside a Durand worked. Examining a turf printed nothing, whether done by the Examine verb or by shift-click. The turf is silently dropped by an early return in `run_examinate`, so there is no feedback.

### #82726

The report says a "brain cube" (an MMI or positronic brain) placed in a mech cannot inspect anything. This did not reproduce for a positronic brain in a Durand (see Reproduction). The cause found for #39489 does not apply to it.

## Reproduction

### #39489 (reproduced)

On master, with admin tools (the Lua editor was used for the setup):

1. Pick a spot on a hallway and spawn, in a row on adjacent tiles: a human (the pilot), a Durand mech, a crowbar and a second human (named "Target Dude" for convenience). Give the pilot's body to your client (`ckey` set from the Lua editor), so you play as that human.
2. Make the pilot enter the Durand by calling `mob_try_enter(pilot)` on the mech. It runs a do_after of about 4 seconds, after which the chat shows "Pilot climbs into the Durand!" and the pilot's `loc` is the mech.
3. Examine the crowbar and the target human. Both print their normal examine text.
4. Examine a turf a few tiles away (the test used the floor at 110,145 with the mech at 108,144, so the turf was 2 tiles east and 1 north). The Examine verb was called on that turf. Nothing was printed in chat.
5. Check the cause from the Lua editor: `view(7, pilot)` returned 13 things (the mech's contents), the turf at 110,145 was not among them, and `pilot.sight` was 0 (no `SEE_TURFS`). The client's eye was the Durand and the pilot's `loc` was the Durand.

The early return prints nothing, which matches the silence. The right-click context menu itself was not used; the Examine verb was invoked on the turf directly, and shift-click was used on turfs after the fix (see Verification). Whether the pre-fix shift-click on a turf failed the same way was not tried separately, but both paths go through `run_examinate`.

### #82726 (not reproduced)

1. On the fixed build (so not an unfixed one, see below), spawn a positronic brain with a brain mob, assign its `ckey` to your client, and place it into the Durand. `mmi_moved_inside` itself returned `0` because the helper "user" the test passed in was not a valid user, so the steps it performs (`add_occupant`, `reset_perspective`, `remote_control`, `update_mouse_pointer`) were replicated by hand through the Lua editor. The brain mob ended up inside the Durand with the client's eye on it.
2. As the brain, shift-click the crowbar and several floor tiles. Each printed the normal examine text.
3. The brain mob's `sight` was `SEE_MOBS|SEE_OBJS|SEE_TURFS`. Because of that, the `!(sight & SEE_TURFS)` part of the check at `code/modules/mob/mob.dm:560` is false, and the `view()` test is never evaluated for it.

Not done: no unfixed copy was built to repeat step 2 on master, so the brain's pre-fix behavior was inferred from the code and from `sight`, not observed directly. A real MMI inserted by a player (rather than the hand-replicated steps) was also not tested.

## Cause

`code/modules/mob/mob.dm:560`, in `/mob/proc/run_examinate`:

```dm
if(isturf(examinify) && !(sight & SEE_TURFS) && !(examinify in view(client ? client.view : world.view, src)))
	// shift-click catcher may issue examinate() calls for out-of-sight turfs
	return
```

The check exists because the shift-click catcher can send `examinate()` calls for turfs the player cannot see. It skips the check for mobs with `SEE_TURFS` sight (meson vision, X-ray, ghosts, and so on) and otherwise requires the turf to be in `view()`.

In BYOND, `view(range, center)` with a center that is itself inside another atom (not on a turf) returns only what is inside that container, not the surrounding map. A pilot's `loc` is the mech, so the list holds the mech's contents and never a turf. Objects and mobs are not subject to this check (only turfs are), which is why the same pilot could still examine them.

The same pattern appears in `/mob/Topic` at `code/modules/mob/mob.dm:618`, which handles the "You can examine X closer..." link (shown when the player has the "remove double-click" preference on):

```dm
if(examined_atom in view(client ? client.view : world.view, src))
	run_examinate(examined_atom, force_examinate_more = TRUE)
```

Here the check is applied to every kind of atom, not only turfs (the in-code comment says it only early returns for turfs, which is out of date). A mech pilot who clicked that link for a nearby object would also have been rejected silently. This second case was not reproduced in game before the fix; it is inferred from the code.

A pilot's client eye is the mech (the `reset_perspective(src)` calls in `code/modules/vehicles/mecha/mecha_mob_interaction.dm`), so `get_turf(eye)` is the mech's turf.

## Fix

One commit, "Fix issue 39489: examining turfs from inside a mech", changing two lines in `code/modules/mob/mob.dm`:

- In `run_examinate`, the turf check now uses `view(client ? client.view : world.view, get_turf(client?.eye || src))`.
- In `/mob/Topic`, the `run_examinate` link check uses the same center.

The center is the turf of the client's eye, falling back to the mob when there is no client. Using the eye rather than `get_turf(src)` keeps the check consistent with what the player actually sees through other remote views (cameras and the like) and still handles the mech case, since the pilot's eye is the mech. `get_turf(src)` alone would also have fixed the mech case. The commit adds a short comment explaining why `view()` is not centered on the mob.

The sight rules (`SEE_TURFS` bypass, the blind check, the darkness check) were not changed.

## Verification

On a rebuilt server, with the same setup as in the reproduction (human pilot in a Durand, crowbar and a target human nearby):

- Objects and mobs were not re-tested after the fix. The Examine verb on the floor at 110,145 printed "That's a floor. There's a small crack on the edge of it."
- Shift-click on the floor at 109,146 and at 111,144 printed the same text.
- The Examine verb on a turf at x=125 (the mech was at x=108, well beyond the default view) printed nothing, so out-of-view turfs are still rejected.

Not checked:

- The right-click context menu. The test client could not open the BYOND context menu. The verb is declared with `GAME_VERB_CONTEXT(/mob, examinate, ...)` and its context argument is `in world`, so the menu list does not appear to depend on `view()`, but this was not exercised.
- The "examine closer" link (`/mob/Topic`) after the fix. It uses the same center, but nobody clicked it.
- Other kinds of pilots or remote viewers (AI, camera consoles, vehicles other than mechs) (mobs carrying `SEE_TURFS` sight skip the check anyway).
- The later darkness check in `run_examinate` (`get_dist(src, examine_turf) > 1` for unlit turfs) was not looked at for the in-mech case.
- No multi-occupant mech, and no pilot with the "remove double-click" preference on.

## Notes

- **Related issue #82726** (brain pilots). On the evidence here, a brain pilot is not affected by this bug, since its sight includes `SEE_TURFS` and the check is bypassed. The reporter's actual failure, if it still exists, was not found. Possible causes that were not investigated include a player-specific setup, a different sight state, or something else in the MMI mech path. If the reporter can still reproduce it, it needs its own look. The positronic brain used here was placed in the mech by hand; a real MMI insertion might behave differently.
- The `sight` value of the brain comes from the brain mob being `stat = DEAD` by default (`code/modules/mob/living/brain/brain.dm`) and the dead branch of `/mob/living/update_sight` (`code/modules/mob/living/living.dm:2037-2038`), which sets `SEE_TURFS|SEE_MOBS|SEE_OBJS` when the z-level does not forbid X-ray. This is my reading of the code and agrees with the observed value, but it was not traced in the running game.
- A similar pattern remains in `/datum/verb_arg_metadata/proc/get_view_targets` (`code/datums/verb_metadata.dm:117`), which builds the list of valid verb targets with `view(viewer.view, viewer.mob)`. For a mob inside a container this would give the same short list. It is used for verb arguments declared with `VERB_ARG_SOURCE_VIEW`, which includes the examine verb's argument, so a prompt or list of targets built from it could have the same problem. Whether that is reachable for the examine verb was not tested, and the code was left unchanged.
- A mech pilot's `sight` is 0, so any other code that relies on `view(..., src)` for a pilot will see the same short list. Only the examine paths were audited.
- Upstream PRs were not searched, so whether this is already fixed upstream is unknown.
