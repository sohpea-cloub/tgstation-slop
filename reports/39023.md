## Summary

Issue #39023 (opened 2018) reported hundreds of runtimes when a singularity was let loose: `undefined proc or verb /turf/open/floor/plating/dismantle wall()` from `/turf/closed/wall/r_wall/singularity_pull`, and a `Cannot read null.type` in `radiation.dm`. On current master neither runtime occurs. Two stage-5 singularities were left next to reinforced walls for about five minutes; reinforced walls were visibly being destroyed and the runtime log contained neither error. The reinforced-wall code path was restructured so that the dismantle runs once per pull, and the radiation code the second runtime pointed at was rewritten. The issue looks closable as already fixed.

## The bug

As reported (BYOND 512, 2018): spawn a singularity on a vanilla server and let it go loose. Every time it pulled a reinforced wall, the log filled with

```
Runtime in reinf_walls.dm,223: undefined proc or verb /turf/open/floor/plating/dismantle wall().
  proc name: singularity pull (/turf/closed/wall/r_wall/singularity_pull)
  src: the plating (126,79,2) (/turf/open/floor/plating)
  call stack: ... singularity pull(the supermatter-charged gravit... (/obj/singularity), 11) ...
```

and occasionally `Runtime in radiation.dm,19: Cannot read null.type`. The reporter added that it happened with supermatter-charged singularities and also with ordinary ones at stage 5, and guessed that the cause was the wall being replaced by plating underneath the running proc, so that the same reference (a turf reference follows the coordinates) now pointed at plating which has no `dismantle_wall()`.

## Reproduction

On master `87b93338` the original runtimes could not be reproduced.

1. Started the test server, started the round and observed.
2. Using the Lua editor, spawned an `/obj/singularity` on the admin's turf and called `expand(11)` on it. Its `current_size` became 9 (`STAGE_FIVE`).
3. Counted the station's `/turf/closed/wall/r_wall` turfs (via `GLOB.station_turfs`): 1628.
4. Spawned a second `/obj/singularity` on an open turf adjacent to one of the reinforced walls (the 400th in `station_turfs` order) and called `expand(11)` on it as well. (The first attempt at this failed with a `bad proc` runtime because `locate()` and `get_step()` cannot be called directly from the Lua editor; the SDQL wrappers `_locate()` and `_get_step()` worked.)
5. Let both singularities run for about five minutes, then recounted: 1625 reinforced walls and 2980 plating turfs. So reinforced walls were being dismantled and replaced by plating, which is the exact situation in which the original runtime fired. The chat also showed objects such as a status display, a security camera and a light fixture "falls apart".
6. Read the round's `runtime.log`.

Evidence: no line containing `dismantle`, `singularity_pull` or `Cannot read` appeared. The only runtimes in the log were:

- 7 `bad proc` runtimes from `WrapAdminProcCall`, caused by the Lua calls described in step 4 (and an earlier similar attempt that used `locate()`/`block()`), not by the game code.
- A handful of unrelated atmospherics runtimes (see Notes).

SDQL2 queries meant to list the reinforced walls near the first singularity failed with a parsing error and were not used further; the counts above come from Lua.

## Cause

The original defect is not present in this tree, so this part is an account of why the code now works rather than a live observation of the old failure. The repository checkout used for testing is shallow, so the old code was not re-read; the explanation of the 2018 failure below follows the reporter's guess and is consistent with how the code is shaped now.

At master:

- `code/game/turfs/closed/walls.dm:265-267`: `/turf/closed/wall/singularity_pull(atom/singularity, current_size)` calls `..()` and then `wall_singularity_pull(current_size)`.
- `code/game/turfs/closed/walls.dm:269-276`: `wall_singularity_pull()` dismantles the wall with 50% probability at stage 5 and above, and 30% at stage 4.
- `code/game/turfs/closed/wall/reinf_walls.dm:214-217`: `/turf/closed/wall/r_wall` no longer has its own `singularity_pull`; it only overrides `wall_singularity_pull()` (30% chance at stage 5 and above).

```dm
/turf/closed/wall/r_wall/wall_singularity_pull(current_size)
	if(current_size >= STAGE_FIVE)
		if(prob(30))
			dismantle_wall()
```

The singularity component calls `tile.singularity_pull(...)` once per tile per pass (`code/datums/components/singularity.dm:217`). So a reinforced wall gets exactly one `dismantle_wall()` attempt per pull, and nothing runs on `src` after `dismantle_wall()` has done `ChangeTurf` (`walls.dm:98-109`). In the old runtime the pull proc was `/turf/closed/wall/r_wall/singularity_pull` itself, with `src` already a plating turf. The most likely explanation is that the old reinforced-wall `singularity_pull` called `..()` (which already ran the wall pull and could dismantle the wall) and then dismantled again, so the second call ran on the same coordinates after the turf had become plating. That is the reporter's hypothesis; it was not confirmed against the old code here.

The `radiation.dm:19` `Cannot read null.type` runtime has no counterpart any more: radiation was rewritten (`code/__HELPERS/radiation.dm`, `radiation_pulse()`, and `code/controllers/subsystem/radiation.dm`). It did not recur in the test, but the test did not show what in the old code produced it.

## Fix

None. There is nothing to fix on master for the runtimes in this issue.

## Verification

Checked in game, on master with no changes: two stage-5 singularities ran for about five minutes next to reinforced walls, with walls being destroyed (1628 -> 1625 reinforced walls, 2980 plating), and no `dismantle_wall`/singularity/radiation runtimes were logged.

Not checked:

- A supermatter-charged singularity (the variant the reporter said it "seems to happen with") was not spawned. A supermatter delamination did happen on the test server during the run (see Notes), but that is not the same as a supermatter-charged singularity.
- Singularity stage 4 and below, and the narrower question of exactly which code produced `radiation.dm:19` in 2018.
- The test ran for a single round on one map; the wall removal rate was low (3 reinforced walls in five minutes), so the number of pulls on reinforced walls in the run is not known, only that some dismantles did happen. Because the old defect was a deterministic double call on every reinforced-wall pull that reached the dismantle branch, even a few dismantles would have been expected to produce it.

## Notes

- Suggested resolution: close #39023 as fixed by the later restructuring (`wall_singularity_pull()` override, single call). The specific PR that did it was not identified from the inputs.
- Unrelated side finding: while a supermatter was delaminating during the test, the runtime log held a few `Cannot execute null.reset_cooldowns()` and `Cannot modify null.dismantle_cooldown` runtimes (6 occurrences in total) from `/turf/open/process_cell` at `code/modules/atmospherics/environmental/LINDA_turf_tile.dm:353`, on a plating turf. Line 353 is the `LAST_SHARE_CHECK` macro (defined at `LINDA_turf_tile.dm:200-247`), which dereferences `our_excited_group` (`our_excited_group.reset_cooldowns()` / `.dismantle_cooldown = 0`). So the null value is most likely `our_excited_group` rather than the tile's air (the test notes guessed `enemy_tile.air`; the macro reading is from the source, not confirmed in game). When the turf was inspected afterwards its air and neighbours were normal. This is probably a transient of turfs being changed under atmos processing and is not the runtime from this issue; it was not investigated further.
- The Lua editor cannot call `locate()`, `get_step()` or `block()` directly (they log a `bad proc` runtime); use the SDQL wrappers `_locate()`, `_get_step()`, `_block()` from `code/modules/admin/verbs/SDQL2/SDQL_2_wrappers.dm`.
