## Summary

The report says that after a player is picked up inside a crate by a MODsuit hydraulic clamp and then gets out, their hearing stays attached to the place where they were released instead of following their mob. This could not be reproduced on master. Two runs through the clamp's real pickup and drop code left the hearing lists correct and hearing followed the mob. The exact scenario in the report also can no longer happen with default settings, because the clamp refuses crates that hold any mob larger than `MOB_SIZE_SMALL`.

## The bug

As reported in 2022: a player in a crate is carried by someone wearing a MODsuit with a clamp. When the player leaves the crate, they can hear things near the point where they got out but not near their own mob when they move away, "as if you were standing in place but you can move your mob freely". That points to a stale entry in `important_recursive_contents`, the per-atom list that tracks which hearing-sensitive mobs are inside a container. A comment in the thread suggested the same thing. The same kind of desync was fixed for sleepers in #62632. Later comments say the reporter's steps could not be reproduced by others, that "the obvious ripley clamp doesn't reproduce this issue", and that clamps were nerfed in #66170.

## Reproduction

The aim was to follow the report as closely as the current rules allow, using admin tools on the test server (MetaStation, Arrival Shuttle Hallway, round started). Two runs were done.

Setup (Lua editor):

1. Spawn a human carrier and equip it with an `/obj/item/mod/control/pre_equipped/standard`. Install an `/obj/item/mod/module/clamp` in it with `mod:install`, and activate the suit with `quick_activation()`.
2. Raise the clamp's `max_mob_size` to 4, so that it will accept a crate with a human in it (at the default it refuses, see Cause).
3. Put a closed `/obj/structure/closet/crate` on the tester's tile, with the tester's mob resting (not dense) inside it.
4. Call the clamp's `on_select_use` on the crate with the carrier adjacent, so the real pickup code runs, including the `do_after` delay and `forceMove` into the module. The crate was in the clamp's `stored_crates` afterwards.

Run 1, dropping with the clamp:

1. Carrier walked about ten tiles with the crate.
2. Clamp used on a free tile, which dropped the crate there.
3. The tester opened the crate, got out, and walked 14 tiles away.
4. Two NPC humans were spawned, one next to the tester and one next to the drop spot. Each said a line, and `get_hearers_in_view` was run on each speaker.

Run 2, dropping by deactivating the suit:

1. Same setup. The carrier's suit was deactivated, so `on_part_deactivation` dropped the crate at the carrier's location.
2. The tester resisted out of the crate, walked about ten tiles away, and the same two-NPC check was done.

Observed:

- While carried, the tester's mob, the crate, the clamp and the MOD control unit all listed the tester in their hearing-sensitive `important_recursive_contents`, and the carrier showed up as well. Nothing was missing.
- After leaving the crate in run 1, the tester's mob listed itself, the crate's list was empty, and the clamp and the MOD unit had no entries. The NPC next to the tester heard them (`get_hearers_in_view`: true, and the line appeared in chat). The NPC at the drop spot did not (false).
- Run 2 gave the same result: the tester's list contained only the tester, the crate's list was empty, the NPC next to the tester heard them, and the NPC at the drop spot did not.
- Pressing the resist key while still inside a crate that was being carried did nothing (see Cause).

Limits: the tester's mob was possessed through admin tools and put in the crate with `forceMove`, not by the normal action of climbing in. The hearing check used `get_hearers_in_view` plus the chat output, so it measured the server-side hearing lists, not a live client's experience.

## Cause

No defect was found. The relevant code paths were read and match what the runs showed:

- The clamp moves crates with plain `forceMove` into itself on pickup (`code/modules/mod/modules/modules_supply.dm:76`), out to the target tile on drop (line 94), and out when the suit deactivates (line 105).
- `forceMove` goes through `Entered()` and `Exited()` in `code/game/atoms_movable.dm` (around lines 1005-1040), which add and remove a mob's hearing entries on every container it passes through. This is the same machinery that #62632 fixed for sleepers, and it handled the clamp's `forceMove` correctly.
- `check_crate_pickup()` (`modules_supply.dm:108-117`) refuses any crate that contains a living mob with `mob_size` above `max_mob_size`, which defaults to `MOB_SIZE_SMALL` (line 46). A human in a crate is therefore refused at default settings (balloon alert "crate too heavy!"), so the reported case cannot occur. Only small mobs, or a clamp with a raised `max_mob_size`, can be carried.
- A crate being carried has `loc` set to the module. Resisting inside it calls `container_resist_act` (`code/game/objects/structures/crates_lockers/closets.dm:1088-1092`), which relays to the module through `relay_container_resist_act`. The clamp does nothing with that, so a carried player cannot get out until the crate is dropped.

## Fix

None. There was nothing to fix on master.

## Verification

Not applicable beyond the two runs above. Both runs found the hearing lists and actual hearing correct after leaving a clamp-carried crate.

Not tested:

- Small mobs (the case allowed at default settings) in a carried crate, and mobs with other sizes between small and 4.
- Cases that move the crate or the mob by other means while it is carried (a second clamp use, teleporting, deleting the carrier, a crate with several mobs).
- Big packages (`/obj/item/delivery/big`), which the clamp also accepts.
- Round-start code paths: the game was started with a start-now admin command and the tester joined late. The state of the world as of 2022 may have differed in ways the code reading cannot show.
- Other sources of the hearing desync that the last commenter asked about. The Ripley clamp was not tested here either.

## Notes

- The report can be closed as fixed or obsolete, most likely by the clamp size limit (#66170) and the earlier recursive-contents fixes. The runs here only show the current behaviour, not which change fixed it.
- Side finding about the test tooling, not the game: every `runCode` call in the Lua editor wrote an empty "uncaught runtime error: " line to `runtime.log`, and nothing else. It also appeared on a different issue and is probably unrelated to this one. It was not investigated.
