# #91446: Balancing a malfunctioning chameleon hat on an EVA helmet freezes its worn appearance

| Status | Fixed and checked in game (the look change was triggered through the Lua editor, not by a real EMP) |

## Summary

A chameleon hat balanced on a hat-stabilizing helmet (the EVA helmet) changes form, but the wearer's worn overlay is never redrawn, so it keeps showing the old form. `update_look()` only redraws the wearer when the chameleon item is held directly by a mob, and a balanced hat is held by the helmet. The fix adds a branch that redraws the holder item when it has a `hat_stabilizer` component.

## The bug

EMP'd or pre-broken chameleon gear changes form at random. When such a hat is balanced on an EVA helmet, the head overlay stays on whichever form the hat had when it was placed. It only updates after the wearer changes z-level, takes the helmet off and puts it back on, or removes the hat from the helmet. The hat itself has changed form (its item appearance is correct); only the worn overlay is stale.

## Reproduction

1. On master, using the Lua editor, spawn a human and equip an EVA helmet (`/obj/item/clothing/head/helmet/space/eva`) on the head slot.
2. Spawn a chameleon hat (`/obj/item/clothing/head/chameleon`), move it into the helmet, and call the helmet's `hat_stabilizer` component's `attach_hat(hat, null)`.
3. Call `update_look()` on the hat's chameleon action with the ushanka as the target. This is the proc that an EMP's `random_look()` ends up calling.
4. Inspect the human's overlays.

Observed: the overlays listed `[space]` and `[blacksoft]`, the stale cap look, although the hat was already the ushanka.

Caveat: the attach and the look change were made by calling procs from Lua, not by the player action (placing the hat on the helmet by hand and letting an EMP fire). The code path is the same as the one the EMP takes, but the full player flow was not run.

## Cause

`update_look()` in `code/modules/clothing/chameleon/_chameleon_action.dm:130` updates the item and then redraws only if the item is on a mob:

```dm
if(ismob(chameleon_item.loc))
	var/mob/wearer = chameleon_item.loc
	wearer.update_clothing(chameleon_item.slot_flags | ITEM_SLOT_HANDS)
	wearer.refresh_obscured()
```

A hat attached with the `hat_stabilizer` component has the helmet as its `loc`. The helmet draws the hat as part of its own worn overlay (`get_worn_overlays` in `code/datums/components/hat_stabilizer.dm:107`), so that overlay needs regenerating when the hat changes. Nothing did that, so the cached overlay stayed until something else forced a redraw (helmet re-equip, z-change, hat removal).

## Fix

One commit, "Fix issue 91446: redraw a hat-stabilizer holder when a chameleon hat on it changes look". It adds an `else if` branch to `update_look()`: if the chameleon item's `loc` is an item with a `hat_stabilizer` component, call `update_appearance()` and `update_slot_icon()` on that item. The helmet's worn overlay is rebuilt, and the wearer's sprite is refreshed. No alternatives are recorded in the inputs.

## Verification

After the fix, the same Lua steps gave overlays `[space]` and `[ushanka_gagdown]`, so the worn overlay followed the hat's new form.

Not checked: an actual EMP or the random form cycling over time, placing the hat on the helmet by hand, the other triggers listed in the issue (z-change etc.) as a regression check, and other hat-stabilizer holders besides the EVA helmet.

## Notes

- Not addressed: the holder's `flags_cover` is set when the hat is attached (`hat_stabilizer.dm:189`) and is not re-synced when the hat later changes to a form with different cover flags. This is existing behavior and outside this issue.
- The branch redraws the holder, not the wearer's obscured-flag state (`refresh_obscured()` is only called in the mob branch), which is consistent with the flags_cover point above.
