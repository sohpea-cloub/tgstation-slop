| | |

| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The 2022 report was a runtime ("`/obj/structure/disposalconstruct` destroy proc was called multiple times, likely due to a qdel loop in the Destroy logic") when an explosion hit a disposal pipe that still held its construction item. On master `87b93338` the loop cannot happen any more: the `handle_atom_del` hook that closed the loop is gone, and the pipe now reacts to its stored construct leaving through `Exited()`, clearing its reference before it deconstructs itself. Four ways of destroying a pipe with a stored construct (explosion damage on the construct, `qdel` on the construct, an explosion on the pipe tile, and `deconstruct`) produced no loop and no runtime.

## The bug

An explosion on a disposal pipe could produce the runtime above, with `Destroy()` of both the pipe and the stored `disposalconstruct` called repeatedly. The reporter attributed it to the `handle_atom_del` logic added in #54861 and linked two pieces of `code/modules/recycling/disposal/pipe.dm` of that time. Comments say it happened in at least one more round (203090), and a commenter wondered whether PRs that fixed mobs being deleted from deconstructed disposals had fixed it.

## What the old loop was

From the stack trace in the issue and the code: the explosion damages the stored `disposalconstruct`, which deconstructs (`qdel`). The `qdel` of the construct triggered the pipe's `handle_atom_del`, which called the pipe's `deconstruct()`, which `qdel`led the pipe. The pipe's `Destroy()` did `QDEL_NULL(stored)`, but `stored` still pointed at the construct that was already being deleted, so it `qdel`led it again, and each side kept re-entering the other.

## Reproduction attempt

On master, Lua editor on the test server, as an observer. Four disposal pipe tiles were made (two straight segments and two `/obj/structure/disposalpipe/broken`), each with a `/obj/structure/disposalconstruct` inside it as its stored construct. It was checked that `pipe.stored` was the construct and the construct's location was the pipe. Then:

1. `ex_act(2)` on the stored construct inside a segment pipe (the issue's path: `ex_act` -> `take_damage` -> `atom_destruction` -> `deconstruct`).
2. `qdel` of the stored construct inside a broken pipe.
3. `explosion(turf, 0, 1, 2)` on a segment pipe.
4. `deconstruct(FALSE)` on a broken pipe.

Results: the pipe and construct were destroyed in cases 1, 2 and 4. In case 3 the explosion is asynchronous, and the pipe was undamaged when checked immediately afterwards, so that case was not conclusively exercised. The round's runtime log contained no "qdel loop" or "destroy proc was called multiple times" lines; the only runtimes were from mistakes in the test script itself (calling `get_step` and `locate` from Lua, and an explosion on a null turf).

## Why it no longer happens

In `code/modules/recycling/disposal/pipe.dm` on master:

- `Destroy()` (lines 59-62) still does `QDEL_NULL(stored)`.
- `handle_atom_del` no longer exists anywhere in the code (a search for it finds nothing).
- `Exited()` (lines 80-87) is the replacement. When the stored construct leaves the pipe, it clears the reference first and only then deconstructs:

```dm
/obj/structure/disposalpipe/Exited(atom/movable/gone, direction)
	. = ..()
	if(gone != stored || QDELETED(src))
		return
	spawn_pipe = FALSE
	stored = null
	if(QDELETED(gone))
		deconstruct(FALSE) //pipe has broken.
```

Because `stored` is null by the time `deconstruct` runs, `Destroy()` has nothing left to re-delete, and the early return on `QDELETED(src)` stops re-entry. This is the same defect as the old one, closed by the order of operations. Which upstream change removed `handle_atom_del` was not looked up.

## Not checked

- The explosion on the pipe tile (case 3) was not confirmed to resolve, only that no loop or runtime appeared.
- No unit test was added; the test was manual only. No fix was needed, so there is no fix branch.
- Variants outside the four cases (a pipe holding a disposal holder with a mob inside, other pipe subtypes, chained explosions) were not tried.

## Notes

- The issue can probably be closed as fixed on current master. If a maintainer wants regression protection, a unit test that spawns a pipe with a stored construct and deletes each in turn would cover the cases above.
