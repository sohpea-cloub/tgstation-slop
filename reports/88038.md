## Summary

The E.X.P.E.R.I-MENTOR accepts any item, including the `/obj/item/mob_holder` made when a player picks up a pet. Experiments delete the loaded item, but deleting a mob holder only releases the animal, so the animal comes out again ("The corgi uncurls!") and can be picked up and loaded again. The fix makes the machine refuse mob holders with the message "no living subjects!".

## The bug

A player can pick up a small animal into its in-hand holder, put the holder in the Experimentor and run an experiment. The experiment's result happens and the machine reports the subject destroyed, but the animal survives and is released, so the same animal can feed the machine indefinitely. The issue's author notes this gives unlimited items when the experiment outcome is the irradiation clone.

## Reproduction

1. On the test server, using the Lua editor, spawn an experimentor and a corgi.
2. Create a `/obj/item/mob_holder` holding the corgi (created with the corgi as its held mob), move it into the machine and set the machine's `loaded_item` to it. This stands in for the player action of picking up the corgi and inserting it. The real insertion by hand was not performed.
3. Call `run_experiment('Poke')` on the machine.
4. Observed chat: "prods at the corgi", then "activates the crushing mechanism, the corgi is destroyed!", then "The corgi uncurls!". The holder was deleted, but the corgi was alive and could be picked up again.

## Cause

Two things combine:

- `/obj/item/mob_holder/Destroy()` (`code/modules/mob/living/inhand_holder.dm:31-35`) calls `release()` when the held mob is still inside, so deleting the holder frees the animal instead of killing it.
- `/obj/machinery/rnd/experimentor/item_interaction()` (`code/modules/research/experimentor/experimentor.dm:335`) accepts any item after the insertion-ready check and `transferItemToLoc`, setting `loaded_item`. The experiments then only remove the loaded item with `QDEL_NULL(loaded_item)`, which for a holder amounts to releasing the animal.

A related path was noted in `item_eject()` (`experimentor.dm:235`): it creates a copy with `new loaded_item.type(drop_atom)` for the irradiation clone, which for a holder would produce an empty holder. This was read in the code, not exercised.

## Fix

One commit, "Fix issue 88038: experimentor refuses held animals". In `item_interaction()`, after `is_insertion_ready()` and before `transferItemToLoc`, an `istype(weapon, /obj/item/mob_holder)` check shows the balloon alert "no living subjects!" and returns `ITEM_INTERACT_BLOCKING`. The holder stays in the player's hand.

Refusing was chosen over making the experiment kill the animal, which avoids a new gore path and keeps the change to one place. See Notes.

## Verification

After rebuilding the test server, `item_interaction()` was called with a human user:

- With the corgi's holder: it returned `ITEM_INTERACT_BLOCKING` (2), `loaded_item` stayed nil, the holder remained in the user's hand and the corgi stayed inside it.
- With a pocket crowbar: it returned `ITEM_INTERACT_SUCCESS` (1) and `loaded_item` was the crowbar.

Not checked: the real click-through by a player (including the balloon alert text appearing), other held creatures or other holder subtypes, and the full experiment run after the fix (the machine never receives a holder now).

## Notes

- The issue says the pet is "destroyed as intended". Maintainers may prefer that experiments kill the animal rather than refuse it. Refusal was chosen to avoid killing pets by accident.
- A comment on the issue asks whether the exploit matters, since paper can be put in the machine for items. This was not evaluated.
- Another comment says pet holders are "cursed", and refers to a wider set of problems with them that was not investigated.
