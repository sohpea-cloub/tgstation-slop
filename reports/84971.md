## Summary
Ghosts could open an instrument's UI and use its buttons (change the instrument id, add lines, import, start and stop playing). The tgui base `ui_act` returns TRUE for a UI that is not interactive for the user, but `/datum/song/ui_act` ignored that return value and ran its action switch anyway. The fix returns early when the parent returns TRUE. The chair-dragging half of #84971 is already fixed on master, and the ghost gas scan in #92201 worked when tested.

## The bug
#84971 reports two ghost interactions: dragging a chair onto the ghost, and using instruments. For instruments, a ghost near an instrument gets the song editor window. tgui marks it view-only for the ghost, so the buttons should do nothing. In fact, the actions were still accepted by the server.

## Reproduction
Instruments, on master:
1. Start a round and observe, so you are a ghost.
2. Using the Lua editor, spawn a `/obj/structure/musician/piano` two tiles from the ghost.
3. Click the piano. The InstrumentEditor window opens; tgui reports it as view-only (status 1, `UI_UPDATE`).
4. Send the UI actions `set_instrument_id` (id `ghostpoltergeist`) and `add_new_line` from that window.

Observed: the song's id changed from `""` to `"Ghostpoltergeist"`, and `add_new_line` opened a TextInputModal prompt for the ghost. The actions were sent as tgui actions to the window, not by pressing the buttons with the mouse, since the buttons are inert in a view-only window.

Chairs: not re-tested in game; see Notes.

#92201: the gas scan was toggled with the "Toggle Gas Scan" verb, then a floor turf was clicked as a ghost. Chat showed "Results of analysis of the floor" with moles 104 (O2 22, N2 82), 101.34 kPa, 20 °C. The scan worked.

## Cause
`code/modules/tgui/external.dm:103-104`: the base `/datum/proc/ui_act` returns TRUE when `ui.status != UI_INTERACTIVE`, meaning "bail, nothing to handle".

`code/modules/tgui/states.dm:25-34`: ghosts get at least `UI_UPDATE` when within view range of the object, so for a regular ghost the UI is open but not interactive.

`code/modules/instruments/songs/editor.dm:66-68`:
```
/datum/song/ui_act(action, list/params, datum/tgui/ui, datum/ui_state/state)
	. = ..()
	var/mob/user = ui.user
```
The return value of `..()` was stored in `.` but never checked, so the `switch(action)` below it ran for any user whose UI status was not interactive.

## Fix
One commit, "Fix issue 84971: ghosts can edit and play instruments through view-only song UIs", adds to `/datum/song/ui_act`, right after `. = ..()`:
```
if(.) // not interactive for this user (ghosts only get to watch)
	return
```
This makes the song follow the same convention as the base proc instead of special-casing ghosts, so it also covers any other non-interactive status (for example a user too far away).

## Verification
On the test server with the fix built:
- As a ghost, with the same piano two tiles away, `set_instrument_id` and `add_new_line` had no effect: no data change and no prompt.
- After taking over a human standing next to the piano, `set_instrument_id` (id `livingok`) still worked (`""` to `"Livingok"`).

Not checked: the other song actions (import, play/stop, delete line) after the fix, which go through the same early return but were not each exercised; chair dragging; other `ui_act` procs.
