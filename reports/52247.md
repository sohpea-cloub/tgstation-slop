# #52247: Planted C4 is sent to nullspace, so a voice analyzer attached to it never hears

| | |
|---|---|
| Issues | [#52247](https://github.com/tgstation/tgstation/issues/52247): verified and fixed |
| Status | Fixed |
| Fix branch | [fix/52247](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/52247) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

When C4 is planted, `plant_c4()` moves it to nullspace. A voice analyzer (or any assembly) wired to the C4 is inside the C4, so it has no turf and is in nobody's hearing range; speech never reaches it and it never triggers the charge. The fix moves the C4 into the target it is stuck to and hides it with abstract invisibility instead, so the attached assembly sits at the target's location and can hear.

## The bug

A player attached voice analyzers to C4 charges, planted them, and spoke the activation phrase. Nothing happened. A commenter on the issue worked out why: C4 is sent to nullspace when it is attached to something, so the analyzer inside it does not hear speech. Other commenters who could not reproduce it had probably used the analyzer in a different way (for example on a door, or attached to a signaler).

## Reproduction

Reproduced with the Lua editor on a test server, calling `plant_c4()` directly rather than going through the three-second planting action.

1. Spawn a human (the planter), a closet, a C4 with `det_time` set to 600 (a long fuse) and a voice analyzer that has "boom" recorded and is not currently listening.
2. Attach the analyzer to the C4 with `c4.wires:attach_assembly(c4.wires.wires[1], analyzer)`.
3. Call `c4:plant_c4(closet, user)`.
4. Spawn a fresh human on the same tile and have it say "boom".

Observed on master, in two clean runs (speaker on the same tile as the target, and with the target moved elsewhere): the speech was logged and no explosion followed. In one earlier run the charge did explode after about 2 seconds; this was thought to come from a stale spatial-grid cell left by the nullspaced charge, and was not reliable.

## Cause

`/obj/item/grenade/c4/proc/plant_c4()` in `code/game/objects/items/grenades/plastic.dm` ends its planting with `moveToNullspace() //Yep` (`:140`), after setting `target` and before adding the overlay to the target. The C4 then has no `loc`.

`/datum/wires/proc/attach_assembly()` (`code/datums/wires/_wires.dm:217`) does `assembly.forceMove(holder)`, so an attached voice analyzer lives in the C4's contents. The voice analyzer is hearing-sensitive (`become_hearing_sensitive()` in `code/modules/assembly/voice.dm:30`) and receives speech through `Hear()` only if it is among the hearers of the speaker's location. With the C4 in nullspace, the analyzer is in no turf's contents tree and hears nothing. `detonate()` itself does not need a location for the C4: it explodes at `get_turf(target)` (`plastic.dm:80-83`), which is why a timer or a plain wire pulse worked regardless.

## Fix

One commit, "Fix issue 52247: keep planted C4 inside its target so attached voice analyzers can hear". In `plant_c4()`, `moveToNullspace()` is replaced with:

```
forceMove(target)
SetInvisibility(INVISIBILITY_ABSTRACT, id = type)
```

The charge now sits in the target's contents, so assemblies wired to it have a location (and travel with the target). `INVISIBILITY_ABSTRACT` keeps the C4 from being seen as a separate object on the target's turf, as it already was in nullspace; the planted look comes from the overlay added to the target.

## Verification

On the fixed build, using the same Lua steps:

- Closet target: "boom" said at 19:28:02 and the charge exploded at 19:28:03.9, destroying the closet.
- Floor turf target: the analyzer heard the phrase and the charge exploded.
- Human target moved with `forceMove` to another room: the phrase said there set off the charge at the target's new location, so it travels with its target.
- The only new runtime in the log was an unrelated "power cable taking damage while having <= 0 integrity" from the blast.

Not tested: a wall target (the turf case was covered by the floor test), a thrown-item target, a mob wearing the planted C4 through a real planting action by a player, other assemblies (proximity sensors and so on), and the effect of the charge being in the target's contents on explosions that do not originate from the charge itself.

## Notes

- Side effects to review: the C4 is now in `target.contents` instead of nullspace. When the blast calls `EX_ACT` on the target, it could also be applied to the contents, and the target's contents can now be seen by code that iterates them (for example a closet's `contents`, or a mob's `contents`). `detonate()` still ends with `qdel(src)`, and the tests that were run showed normal behaviour, but that is the main risk of this approach.
- When the target is a mob or item, the C4 is now carried inside it, which may interact with inventory code (dropping, stripping) or with the target being qdeleted before the timer ends; none of that was tested. `Destroy()` sets `target = null`, but a target being destroyed does not itself clear the C4's reference.
- Another approach would be to leave the C4 in nullspace and relay speech to its assemblies some other way; this was not tried.
