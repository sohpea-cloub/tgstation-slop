| | |

| Status | Fix committed and checked on the test server |
| Fix branch | [fix/32799](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/32799) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Walls that list airlocks in their `canSmoothWith` (titanium, plastitanium, syndicate, false and tram walls) only join up with an airlock if the airlock was already there when the wall smoothed. An airlock built next to an existing wall never tells the wall to re-smooth, and neither does removing one. The cause is that airlocks have a smoothing group but are machinery without `USES_SMOOTHING`, so the generic "queue my neighbours" code never runs for them. The fix makes the airlock queue its neighbours in `Initialize()` (when not loading the map) and in `Destroy()`.

#93071 (walls losing their connected sprites after an RCD wall is built on a conveyor tile) could not be reproduced on master and is not fixed by this change.

## The bug

### #32799

If a wall can smooth with certain objects (the issue gives titanium and plastitanium with airlocks), it does not smooth with them when the wall is built first and the object second. When the object comes first and the wall second, the wall smooths normally. A 2023 comment on the issue says airlocks are still affected, while windows of the same material (titanium wall and titanium window) update correctly.

What happens is that the wall's `smoothing_junction` is computed once, when the wall smooths, and nothing recomputes it when a matching neighbour appears later.

### #93071

The report shows wall sprites with broken connections after a player used an RCD to build a wall on a floor tile that holds a conveyor belt. The reporter's round had several test merges active, including "Smooth Movement 5.3" and a change to camera handling. See the Reproduction section for what was tried.

## Reproduction

### #32799

On the test server (any map; the walls were placed in the Central Primary Hallway), using the Lua editor as an observer:

1. Turn a floor turf into a titanium wall with `ChangeTurf('/turf/closed/wall/mineral/titanium')`.
2. Create an `/obj/machinery/door/airlock` on the tile directly east of the wall.
3. After the icon smoothing subsystem had had time to run (the value was read after a wait in the Lua script), read `smoothing_junction` on the wall.

Observed on unmodified master: the junction was `0`, meaning no connection to the airlock. Calling `smooth_icon()` on the wall by hand then changed it to `4` (the east bit), which is the correct value. So the wall can smooth with the airlock; it is just never asked to.

This was reproduced by creating the objects with Lua rather than by building them as a player, and the check was on the junction value, not on a rendered picture.

### #93071

Using the Lua editor on the test server:

1. Turned the tiles at two positions with one tile between them into plain walls.
2. Created an `/obj/machinery/conveyor` on the tile between them.
3. Spawned a human and a fully loaded RCD (`/obj/item/construction/rcd/loaded`, wall mode) and called `interact_with_atom` on the conveyor tile with that human as the user. This went through the real RCD path (`rcd_act` on the floor, which calls `place_on_top(/turf/closed/wall)`) and the tile became a wall.
4. Read `smoothing_junction` on the three walls: `4`, `29`, `137`. Calling `smooth_icon()` on each of them afterwards gave the same three values, so none of them was stale.

A second check without the RCD (placing a wall on top of a floor tile with `place_on_top`, in a row of three walls at another spot) gave `4`, `12`, `8`, which are also correct.

Result: the RCD wall on a conveyor tile smoothed correctly. The only conveyor state tried was a freshly created conveyor with default settings.

## Cause

### #32799

`/obj/machinery/door/airlock` sets `smoothing_groups = SMOOTH_GROUP_AIRLOCK` (`code/game/machinery/doors/airlock.dm:87`) but sets no `smoothing_flags`, so `USES_SMOOTHING` is not set on it.

The code that tells neighbours to re-smooth when something appears or goes away lives in `/obj/structure`, and only runs for things that use smoothing (`code/game/objects/structures.dm:22-30`):

```dm
/obj/structure/Initialize(mapload)
	. = ..()
	if(smoothing_flags & USES_SMOOTHING)
		QUEUE_SMOOTH(src)
		QUEUE_SMOOTH_NEIGHBORS(src)

/obj/structure/Destroy(force)
	if(smoothing_flags & USES_SMOOTHING)
		QUEUE_SMOOTH_NEIGHBORS(src)
	return ..()
```

Airlocks are machinery, not structures, so they never run this code. Every wall whose `canSmoothWith` includes `SMOOTH_GROUP_AIRLOCK` is affected. In master these are the titanium and plastitanium walls in `code/game/turfs/closed/wall/mineral_walls.dm` (lines 279, 326, 368), the plastitanium reinforced wall (`code/game/turfs/closed/wall/reinf_walls.dm:249`), the indestructible plastitanium wall (`code/game/turfs/closed/indestructible.dm:135`), the titanium and plastitanium false walls (`code/game/objects/structures/false_walls.dm:374`, `:386`) and the tram walls (`code/modules/transport/tram/tram_structures.dm:249`, `:261`). The test only exercised a titanium wall.

Windows are structures, and `code/game/objects/structures/window.dm` queues neighbour smoothing itself when `USES_SMOOTHING` is set (lines 421-422), which is consistent with the report that windows of the same material update correctly.

### #93071

No cause was found. Nothing in `code/modules/recycling/conveyor.dm` touches smoothing.

## Fix

One commit, "Fix issue 32799: queue wall smoothing when an airlock is built or removed", changes `code/game/machinery/doors/airlock.dm` (4 added lines):

- In `/obj/machinery/door/airlock/Initialize(mapload)`, right after `. = ..()`, it calls `QUEUE_SMOOTH_NEIGHBORS(src)` when `mapload` is false. Mapload is skipped because the initial smoothing pass at round start already covers airlocks placed by the map.
- In `/obj/machinery/door/airlock/Destroy()`, it calls `QUEUE_SMOOTH_NEIGHBORS(src)` as the first line, so a wall re-smooths when the airlock it was joined to disappears.

The airlock itself is not queued to smooth, and `USES_SMOOTHING` is not set on it. Only its neighbours are told to update, which is what the wall needs. This is also what the first comment on the issue suggested (queue neighbour smoothing from the airlock's `Initialize()`).

## Verification

On a rebuilt test server with a fresh round, using the Lua editor:

1. Created a titanium wall, then an airlock to its east, as in the reproduction.
2. After the smoothing subsystem ran, the wall's `smoothing_junction` was `4` without any manual `smooth_icon()` call.
3. Destroyed the airlock. The wall's `smoothing_junction` went back to `0`.

No runtimes beyond the usual startup noise were seen.

Not checked:
- Anything rendered. The check was on `smoothing_junction`, not on the displayed icon.
- Wall types other than titanium (plastitanium, syndicate, false walls, tram walls).
- Airlock subtypes other than the base airlock, and airlocks built by a player with tools or an RCD rather than created from Lua.
- That mapload airlocks still smooth correctly at round start, and any effect on round-start time or smoothing-queue load. The latter was the concern raised in the 2017 comment on the issue.
- Windows (not touched, and the issue says they already work).
