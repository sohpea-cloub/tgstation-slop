## Summary

The silicon "State Laws" panel keeps its list of laws to state in `to_state`, but fills it with `assoc_to_values(laws.inherent)`. `inherent` maps law text to an "is this an ion law" boolean, so `to_state` ended up holding 0/1 values instead of law texts. Every check in the UI and in `state_laws()` is `law in to_state`, so no law was selected by default, and supplied, hacked and zeroth laws were never covered. The fix tracks the laws the user has *unchecked* instead of the ones they have checked, so everything is stated unless unchecked, including laws added later. The specific symptom in #91044 (a purple law whose toggle will not change from "No" to "Yes") could not be reproduced on current master: toggling a supplied law works.

## The bug

### #97535 and the rest of #91044

Opening the State Laws panel as a cyborg (#97535) or an AI showed every checkbox unchecked. A silicon who presses "State Laws" without touching anything says only "Current Active Laws:" and no laws. The "state laws" link in the chat's Show Laws message (see Cause) uses the same selection, so it also stated nothing by default. #91044's reporter, asked to state their laws, "couldn't actually state all of my laws" and saw the toggle for law 5 stay on "No". Other silicons had the same trouble.

### #91044's literal complaint and #67998

#91044 says that pressing the toggle for a supplied (purple) law does not switch it to "Yes". #67998 (2022) reports the same for borgs synced to an AI with supplied law modules, and a 2024 comment there blames a `lawcheck` list that is never cleared on law sync. Neither could be reproduced on master (see Reproduction): the `lawcheck` list and verb from 2022 no longer exist, and the toggle works. Both reports were probably made against older code or a test merge. The toggle problem and the default-selection problem look the same from the outside (nothing is "Yes" and you have to click every law yourself), which may be why they were reported together.

## Reproduction

All on the test server with admin tools and the Lua editor.

### Default selection (#97535, and the base of #91044)

1. Created an AI from a human (`AIize()`), gave its lawset two supplied laws ("Supplied one", "Supplied two") and one hacked law ("Hacked one"), and moved an admin's client into the AI.
2. Clicked the "State Laws" button on the AI's HUD. The State Laws panel opened.
3. Read the panel's data in the Lua editor window's state: `stated_laws` was `[0]`. A single boolean and no law text, so no checkbox was checked.
4. Sent the panel's `toggle_stated` action for "Supplied one": `stated_laws` became `[0, "Supplied one"]`, and the checkbox for "Supplied one" would become checked. This is the toggle working on a supplied law on master, which is what #91044 and #67998 say fails.

The same state was not read on a cyborg before the fix. The cyborg panel uses the same `/datum/state_laws_ui` code, and #97535 describes the same result.

### Not reproduced

- Toggling a supplied law (step 4 above) for an AI works. For a cyborg, toggling "Supplied two" off and on worked on the fixed build; it was not tried on unfixed master.
- Nothing like the 2022 `lawcheck` list from #67998 exists in the current code.

## Cause

In `code/datums/ai_laws/state_laws_ui.dm` at master:

```dm
VAR_PRIVATE/list/to_state                                  // line 6
...
/datum/state_laws_ui/proc/update_inherent_stated_laws(datum/ai_laws/laws)
	to_state = assoc_to_values(laws.inherent)              // line 18
```

`laws.inherent` is "Core Laws - Assoc list ... key = law text, value = is this an ion law" (`code/datums/ai_laws/ai_laws.dm`, around line 130). `assoc_to_values()` (`code/__HELPERS/_lists.dm:995`) returns the deduplicated *values*, so for any lawset without ion laws `to_state` is just `[0]`. The UI expects law texts:

- `ui_data()` sends `stated_laws = to_state` to the interface (`state_laws_ui.dm:62`), and `StateLawUi.tsx` draws each checkbox with `checked={stated_laws.includes(law.text)}`.
- `ui_act("toggle_stated")` adds or removes the law's text in `to_state` (`state_laws_ui.dm:72-79`).
- `state_laws()` says a law only if `law in to_state_cached` (`state_laws_ui.dm:105-127`), for the zeroth, hacked, core and supplied laws alike.

So nothing is selected at the start. Supplied, hacked and zeroth laws were never going to be selected by default anyway, since only `inherent` was ever read. The selection is reset by `ui_close()` (line 46), and by `ai.dm:38` and `pai.dm:203` through `update_inherent_stated_laws()`, so every reset repeated the problem.

The "Show Laws" chat link calls `statelaws()` (`code/modules/mob/living/silicon/silicon.dm:203-206`, `:231`), which calls `law_ui.state_laws()` and so used the same empty selection.

## Fix

One commit, **"Fix issues 97535, 91044: State Laws UI states every law by default"**:

- `to_state` is replaced by `not_to_state`, the list of law texts the user has unchecked (default empty).
- `ui_data()` computes `stated_laws` as every law in `get_laws_ui_data()` whose text is not in `not_to_state`. The interface file (`StateLawUi.tsx`) is unchanged.
- `toggle_stated` toggles membership in `not_to_state`. `state_laws()` now says a law unless it is in `not_to_state_cached` (still taking the cache at the start, so changing laws mid-statement behaves as before).
- `update_inherent_stated_laws(laws)` is renamed `reset_stated_laws()` and just empties `not_to_state`. Its three callers (`ui_close()`, `ai.dm`, `pai.dm`) were updated, and the constructor no longer needs to pre-fill anything.

Tracking the unchecked laws, rather than fixing the pre-fill (for example `to_state = assoc_to_keys(laws.inherent)`), was chosen so that laws which arrive later, such as supplied, hacked or zeroth laws added after the panel's last reset, are stated by default too. A pre-fill would have needed a refresh on every law change; with the inverse list there is nothing to keep in sync. A side effect is that the "Show Laws" chat link now states all laws by default.

## Verification

Checked in game as a cyborg on a build with the fix:

1. Created an AI with two supplied laws and a cyborg (`Robotize()`), connected the cyborg to the AI and ran `lawsync()`. The cyborg had its 10 core laws and the 2 supplied laws.
2. Moved the client into the cyborg and opened the State Laws panel (`checklaws()` from the Lua editor). `stated_laws` contained all 12 law texts, including "Supplied one" and "Supplied two".
3. Sent `toggle_stated` for "Supplied two". `stated_laws` dropped from 12 to 11.
4. Sent `state_laws`. The cyborg said "Current Active Laws:" and then laws 1 to 11, including "11. Supplied one", and left out "Supplied two". No runtimes.

Not checked:

- The AI's panel on the fixed build (the AI was created, but only the baseline was read for it before the fix and the cyborg after).
- pAIs, whose reset call in `pai.dm` was changed but not run.
- The "Show Laws" chat link and the forced `statelaws(force = TRUE)` path (the admin law panel uses it) after the fix.
- Hacked and zeroth laws after the fix (the AI was given a hacked law only for the baseline).
- A malf AI, and a cyborg re-synced to different laws while the panel is open.

## Notes

- Two laws with exactly the same text are toggled together, because the selection is keyed by law text. This was already the case before the change.
- The numbers shown for ion laws change on every `ui_data()` call (`ion_num()` is random each time), so they flicker in the panel. That is cosmetic and was already the case.
- Because the report in #91044 and #67998 (toggle stuck on "No") did not reproduce, if players still see it on a live server it may be tied to a test merge or a downstream change, or to the same default-selection bug in a different form. #91044 includes a screenshot that was not examined.
- #67998 is therefore not a duplicate of #91044 in the strict sense; only the part that remains in the current code (nothing is selected by default) is fixed by this branch.
