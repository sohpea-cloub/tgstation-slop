## Summary

The report said that the malfunction module picker, which uses the shared `GenericUplink` tgui component, kept showing modules after they were bought, and did not mark them as purchased when reopened. On master `87b93338` this no longer happens: bought modules disappear from the list immediately and stay gone when the menu is reopened. The investigation found that upstream PR #89079 ("Fixes malf ai screen", merged 2025-01-23) had already fixed it; I did not confirm that PR's contents beyond its title and date, which came from the search that started the investigation. No commit was made.

## The bug

As reported (August 2024, still seen in January 2025): in the malf AI module picker, purchased modules did not remove themselves or show as purchased after the menu was reopened. A comment suggested the abductor console, which also uses `GenericUplink`, could be affected, and another reported a `TypeError: Unable to get property 'length' of undefined or null reference` in the `AntagInfoMalf` interface.

## Reproduction

Attempted on master, as an admin:

1. Spawn a human, call `AIize(nil, false)` on it, then `add_malf_picker()` on the resulting AI, and set the picker's `processing_time` to 500. Possess the AI. (An AI created directly with `SS13.new('/mob/living/silicon/ai')` has null laws and breaks the status tab and verbs, with runtimes at `silicon.dm:372`, so it was not used.)
2. Click the "Malfunction Modules" button on the HUD. The module picker opened with 20 static modules.
3. Buy "Hostile Station Lockdown" through the interface.
4. Buy the upgrade "Enhanced Surveillance".

Observed: after step 3, `processingTime` went 500 to 470 and `static_data.modules` went from 20 to 19 entries (Hostile Station Lockdown removed). After step 4, `processingTime` was 440 and the modules dropped from 19 to 18 (Enhanced Surveillance removed). The purchased modules were removed live, and the notes say they stayed removed when the menu was reopened, since the same datum is reused and `possible_modules` persists. I did not separately reopen and re-read the data to confirm that last point, so it rests on the code reading. The abductor console and the generic uplink were not tested.

## Cause

Nothing to report on master. The relevant code is in `code/modules/antagonists/malf_ai/malf_ai_module_picker.dm`: `purchase_module()` (`:77`) removes bought upgrade and one-purchase modules with `possible_modules -= AM` (`:89`, `:103`) and calls `update_static_data(AI)` (`:94`, `:104`) so the interface gets the new list. On the tgui side, `MalfunctionModulePicker.tsx` maps the static modules into `GenericUplink` items. `AntagInfoMalf.tsx` no longer uses the module categories, only a type field, so the `length` TypeError in the comments has no obvious source in current code.

## Fix

None; no commit was made.

## Verification

Checked in game on master `87b93338` as a malf AI, as described above. Not checked: a client-side render of the picker (the interface data was read, not the screen); the abductor console and other `GenericUplink` users; the NTOS-screen TypeError, which was only checked by reading `AntagInfoMalf.tsx`.

## Notes

- A later upstream changelog entry (PR #98187) touches `AntagInfoMalf.tsx`, `MalfunctionModulePicker.tsx` and the `GenericUplink` component, which is consistent with the interface having changed since the report.
- The issue is probably closable as fixed by #89079.
