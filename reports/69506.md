## Summary
The issue (2022) said a deck of cards inside a box inside a backpack could not be mouse-dragged to the hand without removing the box first. On current master the drag works: both a drag onto a hand slot and a drag onto the player's own mob picked up the whole deck while the box stayed in the backpack. The deck now uses the `drag_pickup` element, and the per-deck mouse-drop code the issue linked no longer exists, so the bug appears to have been fixed incidentally.

## The bug
As reported: with a deck of cards in a box that is itself in a backpack, dragging the deck from the open box storage to your hand did nothing. Drawing single cards worked. The reporter clarified in the comments that it was the drag of the whole deck that failed. A commenter suggested the deck's drag handler needed a turf check.

## Reproduction
This was attempted and did not reproduce.

1. On the test server, started the round and observed. Using the Lua editor, spawned a human, equipped a backpack in the back slot, inserted a box into the backpack and a deck of cards (`/obj/item/toy/cards/deck`) into the box, then gave the admin's client control of that human.
2. Clicked the worn backpack (it opened, the box was listed), then opened the box's storage (the deck was listed).
3. Dragged the deck onto the "left hand" screen object. Result: the deck of cards appeared in the left hand. The box remained in the backpack.
4. Put the deck back into the box ("You put the deck of cards into the box."), then dragged it onto the player's own mob. Result: the deck was again in the left hand.

No runtimes occurred. Not tried: the backpack lying on the floor, or the box held in a bag on another mob. The issue only describes the worn-backpack case.

## Cause
Nothing is broken on master, so there is no defect to point at. Why the report no longer applies:

- The deck registers `AddElement(/datum/element/drag_pickup)` in its `Initialize` (`code/modules/cards/deck/deck.dm:34`). The per-deck `mouse_drop` that the issue's code link pointed to (deck.dm, 2022) is gone, and the cards code has no mouse-drop override left.
- `/datum/element/drag_pickup/proc/pick_up` (`code/datums/elements/drag_pickup.dm:19`) handles `COMSIG_MOUSEDROP_ONTO`. It checks `user.can_perform_action(source, FORBID_TELEKINESIS_REACH)`, which relies on the generic reachability logic (`IsReachableBy`, `code/_onclick/click.dm:217`). That logic passes for an item nested in storage inside worn gear. It then puts the item in hand when dropped on the user or on a hand slot.

I did not verify which upstream change removed the old handler.

## Fix
None. No commits.

## Verification
Checked in game as described under Reproduction: both drag targets (hand slot, own mob) worked with the box and deck two storage levels deep in a worn backpack. Not checked: a backpack on the floor, a bag on another mob, or other deck-like items.

## Notes
The issue can likely be closed as fixed upstream. A regression test would need to cover a drag from nested storage, which the existing reachability code appears to handle.
