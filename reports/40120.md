## Summary

The two issues are unrelated bugs that were examined together. #40120: `mob/proc/ClickOn` returned early for every click from a mob with `TRAIT_NO_TRANSFORM`, which the immortality talisman applies, so the person inside the talisman's "hole in reality" could not shift-click anything to examine it. A plain shift-click is now passed to `ShiftClickOn` in that state. #54575: human examine used an if/else-if chain in which any worn glasses (even a HUD monocle that does not cover the eyes) skipped the "eyes are glowing with an unnatural red aura" and "eyes are bloodshot" lines; those lines are now hidden only by glasses with `GLASSESCOVERSEYES`.

## #40120: Shift-click examine in the immortality talisman

### The bug

After using an immortality talisman the user is inside an `/obj/effect/immortality_talisman` ("hole in reality"). Shift+left-clicking the hole did nothing (no message). Right-clicking it and choosing "Examine" worked. In the 2018 thread the reporter tested it as an observer and found that only the person inside is affected; other players can shift-click it.

### Reproduction

On master on the test server, with a real player click (not a direct proc call):

1. Using the Lua editor, spawn a human (named "Testy" in the test) and an immortality talisman next to them. Give the human a client by assigning the player's ckey to it.
2. Pick up the talisman and activate it with its "Immortality" action button. The chat reports that the human vanishes and leaves a hole in reality, and a "hole in reality" object appears.
3. Shift+left-click the hole. Nothing was printed in chat and nothing happened.

### Cause

`/mob/proc/ClickOn` in `code/_onclick/click.dm:76`:

```dm
if(check_click_intercept(params,A) || HAS_TRAIT(src, TRAIT_NO_TRANSFORM))
	return
```

returned before any click type was looked at. The talisman's `vanish()` adds `TRAIT_GODMODE` and `TRAIT_NO_TRANSFORM` to the user (`code/modules/mining/lavaland/mining_loot/equipment.dm:205`) while the mob sits inside the effect, so every click, including shift-click examine, was discarded. Right-click "Examine" goes through a verb rather than `ClickOn`, so it still worked. The line numbers cited in the issue thread refer to older code; the trait check is now the cause.

### Fix

The commit "Fix issue 40120: allow shift-click examine while in a no-transform state (immortality talisman)" removes the `TRAIT_NO_TRANSFORM` test from the first `return`, and after the modifiers are parsed adds:

```dm
if(HAS_TRAIT(src, TRAIT_NO_TRANSFORM))
	// Mobs that can't act can still look around (e.g. someone inside an immortality talisman's effect)
	if(LAZYACCESS(modifiers, SHIFT_CLICK) && !LAZYACCESS(modifiers, MIDDLE_CLICK) && !LAZYACCESS(modifiers, CTRL_CLICK) && !LAZYACCESS(modifiers, ALT_CLICK))
		ShiftClickOn(A)
	return
```

Only a plain shift-click is allowed; every other click, and all other modifier combinations, are still dropped as before, and the click-intercept check still runs first. The other branches of `ClickOn` are not reached in this state, so nothing else a locked mob can do changes.

### Verification

After rebuilding the test server, the same steps (steps 1 to 3 above) produced in chat: "That's a hole in reality. It's shaped an awful lot like Testy. It is a indestructible object." The runtime log of the round had no runtimes.

Not checked: shift-click combined with control, alt or middle click while locked (still ignored by design); other sources of `TRAIT_NO_TRANSFORM`; and non-examine effects of shift-click (`ShiftClickOn` also sends `COMSIG_CLICK_SHIFT`).

### Notes

`TRAIT_NO_TRANSFORM` is also applied by other code: the round-start lock in the ticker, the end-of-round cinematics, falling into a chasm, transformation diseases, a cyborg upgrade, colossus possession, and the temporary-transformation procs. All of those mobs can now shift-click examine, which is probably wanted but was not tested individually. A maintainer may prefer a narrower fix, for example a different trait for the talisman, if allowing examine during, say, a cinematic is not desired.

## #54575: HUD glasses hide glowing and bloodshot eyes on examine

### The bug

The issue (filed for cult red eyes) says that wearing a medical, security or diagnostic HUD hides the "glowing red eyes" examine text, so cultists wearing one can only be spotted by their sprite. The reporter argued that a HUD only covers one eye, so the eyes should still be visible. A reply in the thread was lighthearted and did not dispute the behaviour.

### Reproduction

On master on the test server:

1. Using the Lua editor, spawn a human with the `unnatural_red_glowy_eyes` trait (the trait that cult red eyes use; the cult mechanic itself was not set up) and equip it with `/obj/item/clothing/glasses/hud/health`.
2. Examine the human as a ghost. The output included "He has a health scanner HUD covering his eyes." and no line about the eyes.

### Cause

`code/modules/mob/living/carbon/examine.dm:427-433`, in the human clothing examine code:

```dm
if(!(obscured_slots & HIDEEYES))
	if(glasses  && !HAS_TRAIT(glasses, TRAIT_EXAMINE_SKIP))
		. += "[t_He] [t_has] [glasses.examine_title(user)] covering [t_his] eyes."
	else if(HAS_TRAIT(src, TRAIT_UNNATURAL_RED_GLOWY_EYES))
		...
	else if(HAS_TRAIT(src, TRAIT_BLOODSHOT_EYES))
		...
```

Because it is an else-if chain, any worn glasses took the first branch and the red-eyes and bloodshot lines were never evaluated, regardless of whether the glasses cover the eyes. The HUD glasses define `flags_1 = null //doesn't protect eyes because it's a monocle, duh` (`code/modules/clothing/glasses/hud.dm:5`) and have no `GLASSESCOVERSEYES` cover flag, which is the flag other code uses to decide that glasses cover the eyes (for example `code/modules/mob/living/carbon/human/human_defense.dm:752`).

### Fix

The commit "Fix issue 54575: HUD glasses no longer hide glowing/bloodshot eyes on examine" splits the chain: the glasses line is printed as before, and the red-eyes and bloodshot lines are printed whenever there are no glasses, or the glasses do not have `GLASSESCOVERSEYES` in `flags_cover`:

```dm
if(!glasses || !(glasses.flags_cover & GLASSESCOVERSEYES))
	if(HAS_TRAIT(src, TRAIT_UNNATURAL_RED_GLOWY_EYES))
		...
	else if(HAS_TRAIT(src, TRAIT_BLOODSHOT_EYES))
		...
```

Sunglasses and other glasses with `GLASSESCOVERSEYES` therefore still hide the eyes, as before.

### Verification

On the rebuilt test server, examining the same human with the health HUD showed the HUD line plus "Her eyes are glowing with an unnatural red aura!". The runtime log had no runtimes.

Not checked: that sunglasses (or other glasses with `GLASSESCOVERSEYES`) still hide the eyes (this follows from the condition and from the `flags_cover` values in `code/modules/clothing/glasses/_glasses.dm`, but was not run); the bloodshot-eyes line; security and diagnostic HUDs (they share the same HUD parent type but were not tried); and real cult red eyes.

### Notes

The HUD's own line still reads "covering his eyes" even though the eyes are now also described; the wording was not changed. The reporter's side question about wearing two HUDs, one per eye, is a design suggestion and was not addressed.
