## Summary

Both issues describe using the MOD atrocinator module while carrying someone: separated bodies, lost local speech (#64703), and repeated falling sounds with a black screen (#76379). On master the module already unbuckles anyone carried by the wearer when it activates, and blocks anyone from being buckled onto an active wearer, so the reported symptoms did not occur in testing. One related defect remained: if the active wearer is the one being carried by someone else, `check_upstairs` hit a "this shouldn't happen" `stack_trace` on every move. The fix removes that `stack_trace` for a buckled wearer and just returns.

## The bug

The reports are vague (a fireman-carried or piggybacked body ending up on a different floor from the wearer, local speech lost afterwards, and in #76379 a looping falling sound and black screen). The module flips the wearer's gravity so they "fall" upward through open space. A carried mob is buckled to the carrier, so changing the carrier's gravity and z-level could in principle separate or loop them.

What was actually found on master is narrower: the module guards against carrying, but its guard against being carried was wrong. A wearer who is buckled to someone else (fireman carry, piggyback, or any buckle such as a chair) triggered a runtime on every move, although being carried is a legal state.

## Reproduction

The test used the `multiz_debug` map (z2 to z4). Everything was set up through the Lua editor, and the buckling was done by calling `buckle_mob` directly rather than through the player's piggyback or fireman-carry `do_after` actions.

Original scenario (wearer carries someone):

1. Spawned a human wearer in a standard MOD suit with an atrocinator module, and made the suit active. Made the turf above a position on z3 into openspace. Spawned a second human (the victim) and paralysed them.
2. Made the wearer fireman-carry the victim (`buckle_mob(victim, TRUE, TRUE, 16)`) and activated the module.
3. Observed the message "As X flips, Y flies off of his back!". The wearer moved up to z3, the victim dropped at z2, no runtime appeared, and when the wearer was made to speak the line appeared in the game say log. So bodies did not stay separated in an odd state and speech was not lost.

Residual defect (wearer is carried):

1. With the module active on the wearer, a second human (the carrier) was set up and the wearer was buckled onto the carrier.
2. The wearer then moved with the carrier. On every move the runtime log showed `Atrocinator user is buckled despite protections - this shouldn't happen!`, raised from `modules_maint.dm:375`.
3. Buckling a victim onto the active wearer was still refused (`buckle_mob` returned false).

## Cause

In `code/modules/mod/modules/modules_maint.dm` the module registers two protections when activated:

- `on_activation` (line ~333) unbuckles anyone riding the wearer (`unbuckle_all_mobs()`), with the message seen above.
- `on_someone_buckled` (line ~418, registered on `COMSIG_MOVABLE_PREBUCKLE`) refuses new riders on the wearer.

`check_upstairs` (the `COMSIG_MOVABLE_MOVED` handler) then contains two sanity checks:

```dm
// Prevent infinite loops when being fireman carried - Stack trace if it does
if(mod.wearer.buckled)
    stack_trace("Atrocinator user is buckled despite protections - this shouldn't happen!")
    return
```

The comment assumes the PREBUCKLE block covers this case, but it only blocks riders on the wearer (`wearer.buckled_mobs`). It does nothing for the wearer riding someone else (`wearer.buckled`), so a carried wearer is a normal state that hits the `stack_trace` on each move. The check for `buckled_mobs` just below it (`you shouldn't be carrying someone`) is correct, as that is the case the protections prevent.

## Fix

Commit "Fix issue 64703: no stack trace when an atrocinator wearer is carried" changes `check_upstairs` in `modules_maint.dm`: the `stack_trace` for `mod.wearer.buckled` is removed and the branch only returns, with a comment saying that a buckled wearer moves with whatever they are buckled to, and that only carrying is blocked. The early return was kept so a carried wearer is not pushed through the zFall logic on its own. The `buckled_mobs` check and its `stack_trace` are unchanged.

## Verification

After rebuilding, the carried-wearer scenario was repeated: the runtime log had no `Atrocinator user` entries (0 runtimes), and buckling a victim onto the wearer was still refused. The original scenario (wearer carries a victim, then activates) was checked on master as described above and behaved correctly.

Not checked:

- The real piggyback and fireman-carry `do_after` paths performed by players; buckling was done by direct proc call.
- The tram scenario in #64703.
- The #76379 symptoms (looping falling sound, black screen), which were not exercised.
- What happens when a wearer is unbuckled while over openspace: the code does not recheck falling until the next move. This was noted and left unchanged.

## Notes

- #76379 is treated as a duplicate of #64703; both describe carrying someone while using the atrocinator. The reported symptoms are believed to be fixed by the unbuckle-on-activation and PREBUCKLE guards already on master (the upstream change referenced in the testing notes was PR #74529, already present in the tested tree), but the testing did not reproduce the original reports on an older build, so this is inferred from code and a clean run on master rather than demonstrated.
- The fix only removes a spurious runtime; it does not change gameplay.
