# #81143: Ghost add-view-range, View Range and shift-scroll use a radius helper as an offset

| | |
|---|---|
| Issues | [#81143](https://github.com/tgstation/tgstation/issues/81143): verified, fixed (the "7 increases the view" part could not be reproduced) |
| Status | Fixed and checked on the test server |
| Fix branch | [fix/81143](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/81143) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The ghost view-range code (the hidden `add-view-range` verb, shift + mouse wheel, the View Range verb and the ghost menu setting) called `view_data.setTo()`, which treats its argument as a `world.view`-style radius and turns N into 2N+1 tiles. The ghost code wanted an offset in tiles per side, so every result was off and the cap could be exceeded. In addition, `add-view-range` set the offset to the typed number instead of adding to the current one, so shift-scroll jumped instead of stepping. The fix adds `setRadiusOffset()`/`getRadiusOffset()` to `view_data`, makes `add-view-range` relative and clamped to the ghost maximum, and removes the broken `rescale_view()`.

## The bug

The issue reports (as a BYOND member) that:

1. `add-view-range` can go up to 21 although the member maximum is 14.
2. The resulting offset does not match the number typed.
3. Choosing 7 in View Range while already at 7 increases the view.
4. Shift + scroll cannot reduce the view to 7, only to 8, and scrolling while at 7 increases it to 8.

What happens: the offset is computed with the wrong helper, and `add-view-range` does not add to the current value at all, so what the player sees is a view that jumps by unexpected amounts and passes the cap.

## Reproduction

The test server's ghost was a non-member (`unlock_content` 0), so the cap was 10 tiles of radius (default view 19x15, i.e. radius 9 wide).

1. Start a round, observe to become a ghost.
2. Open the Lua editor and, from the ghost's mob, call `add_view_range(n)` (the proc behind the hidden verb; this goes through the same code as typing `add-view-range n` and as shift-scroll, but the verb itself was only run once, with `add-view-range 3`) and read `client.view` after each call.
3. Observed on master, starting at 19x15:
   - `add_view_range(3)` -> 26x22 (width offset 7, not 6)
   - `add_view_range(20)` -> 32x28 (offset 13; the non-member cap should have allowed at most 3 extra tiles per side, i.e. 25x21)
   - `add_view_range(1)` -> 22x18 (the call set the offset instead of adding 1 to the previous one)
   - `add_view_range(-1)` -> back to 19x15
   - `add_view_range(0)` -> unchanged
4. The View Range verb (tgui list 7..10) was run after the fix only; see Verification.

Not reproduced: item 3, "choosing 7 while at 7 increases the view". On master, choosing 7 passes `7 - 7 = 0` to `setTo()`, which left the view at 19x15. The member cap of 14 was also not tested (the test ghost had no membership), but it goes through the same clamp code.

## Cause

- `code/datums/view.dm:82` `setTo(to_set)` converts its argument with `getviewsize()`, so N becomes 2N+1 added to width and height. It is a compatibility helper for callers that pass a `world.view`-style radius.
- `code/modules/mob/dead/observer/observer.dm:510` (View Range verb) does `client.view_size.setTo(clamp(new_view, 7, max_view) - 7)`, and `code/modules/mob/dead/observer/ghost_menu.dm:184` does `setTo(round(new_view, 1) - GHOST_MIN_VIEW_RANGE)`. Both want an offset in tiles per side, but `setTo` adds 2*offset+1 to the size.
- `code/modules/mob/dead/observer/observer.dm:676` (`add_view_range`) called `client.rescale_view(input, 0, ((max_view * 2) + 1) - 15)`. `rescale_view` (`code/modules/client/client_procs.dm:1018`) is `view_size.setTo(clamp(change, min, max), clamp(change, min, max))`: `setTo` takes one argument, so the second is ignored; the result is an absolute value (not added to the current one), and the clamp maximum is in size units while `setTo` takes a radius, so the cap does not hold.
- Shift-scroll (`code/_onclick/click.dm:518`) calls `add_view_range(+1/-1)`. Since that sets an absolute offset, scrolling from the default jumped to the `setTo(1)` size and "decreasing" produced a reset, which matches the 7/8 behavior in the report.
- In `ghost_menu.dm:182`, the early return was `if(max_view >= new_view && new_view < GHOST_MIN_VIEW_RANGE)`, so values above the maximum were not clamped and the condition mixed the cap with the minimum.

## Fix

One commit, "Fix issue 81143: ghost view range verbs, shift-scroll and ghost menu used a radius helper as an offset":

- `code/datums/view.dm`: adds `setRadiusOffset(radius_offset)` (calls `setBoth(2 * offset, 2 * offset)`, so 0 is the default and 1 is exactly one tile further per side) and `getRadiusOffset()` (`round(max(width, height) / 2)`).
- `observer.dm`: `add_view_range` now computes `clamp(getRadiusOffset() + input, 0, max_view - GHOST_MIN_VIEW_RANGE)` and applies it with `setRadiusOffset()`, so it is additive and capped. The View Range verb uses `setRadiusOffset(clamp(new_view, GHOST_MIN_VIEW_RANGE, max_view) - GHOST_MIN_VIEW_RANGE)`.
- `ghost_menu.dm`: `set_view` now only rejects values below the minimum, clamps to the maximum, and uses `setRadiusOffset()`.
- `client_procs.dm`: removes `rescale_view()` (its only caller was `add_view_range`).

The admin "Change View Range" verb (`code/modules/admin/verbs/admingame.dm:397`) still calls `setTo(x - 7)` and was left alone. Other `setTo()` callers (turret, farsight) were not touched.

## Verification

On the test server, as a ghost with no membership (cap 10, max offset 3), after rebuilding:

- `add_view_range` sequence from 19x15: +3 -> 25x21 (the cap); +1 -> 25x21; +20 -> 25x21; -1 -> 23x19; -30 -> 19x15; 0 -> 19x15; +1 -> 21x17; -1 -> 19x15.
- View Range verb: choosing 7 at the default left the view at 19x15; choosing 9 gave 23x19.

Not checked: the member cap of 14; the shift-scroll input itself (the proc it calls was used instead); the ghost menu's view setting; the verb typed with 20 in the command bar (called through Lua instead).

## Notes

- Shift-scroll now steps one tile per notch and can return to the default, so the "7 vs 8" symptom should be gone; this follows from the code change but was not tested with the real input.
- The admin "Change View Range" verb has the same `setTo()` radius semantics. It was left as is, since its values (up to 37) are written as `world.view`-style radii.
