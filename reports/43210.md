| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The 2019 report says that null entries appeared in the global mob lists (`mob_list`, `alive_mob_list`, `dead_mob_list`, `suicided_mob_list`, `player_list`), and quotes a `Login()` runtime (`Cannot read null.address`) as a possibly related symptom. On current master none of this could be reproduced: after about a dozen login, logout, possession, deletion and respawn scenarios run on a test server, none of the global mob lists contained a null, a deleted mob, or a duplicate entry, and the server never logged "Found a null in ...". The code paths named in the issue are guarded now (an early return in `mob/Login()` when the client is already gone, removal from every list in `mob/Destroy()`, and a periodic null-clearing safety net in `SSserver_maint`), so no change was made. The underlying causes the issue discussion mentions (hard deletes, BYOND skipping `Logout()`) were not ruled out; they are just not observable with the scenarios tried.

## The bug

As reported in 2019, global mob lists sometimes end up with null entries. That breaks any code that iterates those lists without a null check. The reporter also saw `Login()` run on a `/mob/dead/new_player` with no client and no location, runtiming on `client.address`, which "breaks a lot of shit, including generating preferences for new players". The only reply in the thread says a pull request (#43160, never merged) was the goal to run towards, and that BYOND bugs which skip `Logout()` are a further, separate cause. A 2021 comment just says "harddel pain".

What happens underneath is that a list holding a reference to a datum gets a null if that datum is hard-deleted (deleted by `del()` after failing to garbage collect, instead of through `qdel()`) while it is still in the list. A mob that is deleted without being removed from the lists, or one whose `Logout()` never ran, would leave such an entry or a stale player-list entry.

## Reproduction

This was a "check whether it still happens" test, and it did not reproduce. What was done, on a freshly started test server on master, with the round started from the lobby:

1. Opened the Lua editor and ran a scanner that, for each of `GLOB.player_list`, `mob_list`, `alive_mob_list`, `dead_mob_list`, `suicided_mob_list`, `keyloop_list`, `dead_player_list`, `alive_player_list` and `clients`, counted the entries that were null, the entries whose `gc_destroyed` was set (already deleted), and duplicates. It was also run on a half-second timer at first.
2. Baseline in the lobby, then observed (lobby "Observe") and used the "Start Now" admin verb. Scanned.
3. From the Lua editor, spawned eight mobs next to the admin: four humans, two monkeys, a corgi and a mouse. Scanned.
4. Used the "Give Direct Control" admin verb to put the connected player into one of the humans, then used "AGhost", then "Re-enter Corpse". Scanned.
5. From Lua, set the `ckey` of a second human to the player's key (taking control of it), then `qdel`'d that possessed mob, then `qdel`'d a further unpossessed one. After the deletion the client ended up in a ghost (as seen on the next reconnect). Scanned after each. Repeated with more unpossessed mobs (two humans, a monkey and the corgi) for a total of four deleted in one call.
6. Disconnected and reconnected the client twice while controlling a ghost. Scanned.
7. Used "Give Direct Control" to put the player into another human, disconnected the client while in it, and, from Lua, waited until the mob's `client` was null and then `qdel`'d that now clientless but still ckeyed body. Reconnected. Scanned.
8. Used the "Respawn" verb (confirming the admin override, since respawn was disabled) so the player returned to the lobby, then disconnected and reconnected twice in the lobby. Scanned.
9. Latejoined as Assistant, ran the "Suicide" verb, and from Lua `qdel`'d the resulting suicided corpse (the only entry in `suicided_mob_list`) and `gib()`'d a monkey. Scanned.
10. Searched the round's logs for "Found a null" and the runtime log for `Login` / `Logout` / `null.address` runtimes.

Evidence:

- After every step the scan reported `nulls=0`, `qdel=0` (no deleted mobs left in lists) and `dup=0` for every list. For example, with the round running and the eight spawned mobs, `mob_list` was 379 long, `alive_mob_list` 326, `dead_mob_list` 53, `suicided_mob_list` 0, `player_list` 1 and `clients` 1, all clean. After the suicide step the corpse was in `suicided_mob_list` (length 1, no null) and was gone from the list (length 0) after it was deleted.
- `player_list` always held exactly the connected player's current mob, and `dead_player_list` / `alive_player_list` followed the player between ghost and living bodies.
- The world log had zero "Found a null" lines, so the periodic safety net in `SSserver_maint` never had a null to clear during the roughly 13 minutes of the test.
- No `Login()`, `Logout()` or `null.address` runtimes were logged. The runtime log did contain about two dozen blank "uncaught runtime error:" lines, which were traced to the test itself: Lua calling procs after the mob it was running as had lost its client, which hits `CRASH("WrapAdminProcCall with no ckey ...")` in `code/modules/admin/callproc/callproc.dm:196-197`. Lua timers also stopped firing in that state, so the half-second scan loop only ran 17 times; later scans were run by hand after each step.
- An early scan reported many duplicates (for example 239 in `mob_list`). That was a bug in the first version of the scanner, not in the game; with the scanner fixed the duplicate count was 0 everywhere, including when re-run over the same lists.

Because the scenario is "admin tools drive the transitions" rather than real players on a lagging connection, this does not cover the case where a client drops in the middle of `Login()`, or a BYOND-side failure that skips `Logout()`.

## Cause

No defect was found on master; the code that the 2019 report and its discussion point at is now defended in several places:

- `code/modules/mob/login.dm:29-31`: `mob/Login()` starts with `if(!client) return FALSE`. The doc comment on lines 1-4 and the repeated `if(!client)` checks after each step that can sleep (lines 50, 55, 75) exist because a client can disconnect mid-`Login()`. The old runtime from the report (`client.address` on a null client) is therefore avoided; `lastKnownIP = client.address` at line 37 runs right after the guard and the `add_to_player_list()` call.
- `code/modules/mob/mob.dm:34-37`: `mob/Destroy()` calls `remove_from_mob_list()`, `remove_from_dead_mob_list()`, `remove_from_alive_mob_list()` and `remove_from_mob_suicide_list()`, so a normally deleted mob leaves every global list. `Destroy()` also calls `stack_trace` if a mob with a client (line 27-28) or a ckey without a client (line 29-30) is deleted, which makes that kind of deletion visible rather than silent.
- `code/modules/mob/logout.dm:1-6`: `mob/Logout()` calls `remove_from_player_list()`, which removes the mob from `player_list` and `keyloop_list` (`code/modules/mob/mob_lists.dm:59-68`). `add_to_player_list()` (`mob_lists.dm:47-56`) is only reached from `Login()` after the client check, using `|=` so a mob cannot be listed twice.
- `code/controllers/subsystem/server_maint.dm:28-35` and `:43-56`: `SSserver_maint` removes nulls from `player_list`, `mob_list`, `alive_mob_list`, `suicided_mob_list`, `dead_mob_list` and `keyloop_list`, one list per five fires, and writes "Found a null in <list>!" to the world log when it finds one. This hides any null left by a cause upstream of the lists, but the zero count in the test shows none was produced here.

## Fix

None. No commit was made, because there was nothing to fix in the scenarios tested.

## Verification

What was checked: the scenarios in "Reproduction", all on master `87b93338`, produced no nulls, no deleted entries, no duplicates, and no "Found a null" log lines.

What was not checked:

- More than one connected player at a time (only one client was used).
- A client disconnecting in the middle of `Login()` (the code guards for it, but it was not forced).
- BYOND failing to call `Logout()`, which the issue thread names as a cause.
- A long-running or busy round: the test lasted about 13 minutes on an almost empty station.
- Whether the safety net in `SSserver_maint` would have masked a transient null: scans were taken after each step, not continuously, once the Lua timer stopped firing. The zero "Found a null" count covers the whole run, however.

## Notes

- Hard deletes are still frequent for mobs, but they left no nulls behind in these lists. By the end of the run the garbage collector had logged 19 "was unable to be GC'd" lines. Per type, from the garbage subsystem's counters: `/mob/dead/new_player` 4 qdels with 4 failures and 3 hard deletes (reference counts 58 to 148), `/mob/dead/observer` 6 qdels with 4 failures and 4 hard deletes (reference counts 242 to 1512), `/mob/living/carbon/human` 5 qdels with 4 failures and 4 hard deletes, `/mob/living/basic/cockroach` 4/4/4, and single failures for a mouse, a monkey and a corgi. Some of these references are held by the Lua table the test used to keep the spawned mobs, so they overstate what players would see; the lobby `new_player` mobs and observers are not explained by that and belong to the separate hard-delete problem the triage label points at.
- Steps 5 and 7 deleted mobs while they had a client or a ckey, which is the case `mob/Destroy()` reports with `stack_trace`; the lists stayed clean regardless.
- #43160, the pull request the thread points at (making the player list update only at the end of login), was never merged. The relevant protection on master is the set of guards listed under "Cause".
- If a reproduction is still wanted, a better test than this one would be real players on a loaded server with clients that drop during login, or Lua code that forces a client disconnect between `add_to_player_list()` and the following lines of `Login()`.
