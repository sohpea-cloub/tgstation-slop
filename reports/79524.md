## Summary

The circuit Delay component was meant to restart its timer when triggered again, but every trigger queued a new, independent delayed signal because the timer's uniqueness check never matched. The fix deletes the previous timer explicitly before starting a new one. The same branch also removes the `table` type from the List Literal component's type options, because a large table made that component output nothing (#61983). #61946 could not be reproduced: master already keeps the removed BCI inside the chamber.

## #79524: Delay component queues several delayed pings

### The bug

A Delay component's description says "Timer gets reset when triggered again." In practice, triggering it several times within the delay period produced several pending delayed signals instead of one. If the Result output is wired back to the Trigger input, each queued signal starts its own self-sustaining loop, so the number of loops grows with every extra trigger. That is the runaway power drain and overheating described in the issue.

### Reproduction

All of this was done on the test server with the Lua editor, and the circuit was built in Lua, not by hand in a circuit printer. The triggers were fired by setting the Trigger input directly, not by a player pressing buttons.

1. Create an integrated circuit with `admin_only = true` and `on = true`, and add a `/obj/item/circuit_component/delay` to it.
2. Set the Delay input to 3 seconds and connect the Trigger input to the component's own Result output.
3. Set the Trigger input to a value, then set it again 1 second later and 2 seconds later with different values (101, 102, 103 in the run, after two earlier triggers with values 0 and 1).
4. Read the keys of `SStimer.hashes` that contain `set_output`.

Observed on master: five pending timers existed at once, with keys of the form `Result|||||||([ref])|||||||set_output|||||||0|||||||30|||||||<value>`, one for each of the values 0, 1, 101, 102 and 103. The wait field is 30 deciseconds, which is the 3 second delay. Triggers that carried the same value (the earlier triggers with value 1) did not add another key, which fits the cause below.

### Cause

`trigger_delay()` in `code/modules/wiremod/components/utility/delay.dm:33` created the timer like this:

```dm
timer_id = addtimer(CALLBACK(output, TYPE_PROC_REF(/datum/port/output, set_output), trigger.value), delay*10, TIMER_UNIQUE|TIMER_STOPPABLE|TIMER_OVERRIDE)
```

`TIMER_UNIQUE|TIMER_OVERRIDE` is supposed to replace any earlier timer with the same hash. The hash is built in `addtimer()` (`code/controllers/subsystem/timer.dm:633-639`) from the callback object, delegate, flags, wait and `callback.arguments`. The argument here is `trigger.value`. For a Signal port, the value is `COMPONENT_SIGNAL`, defined as `world.time / (1 SECONDS)` (`code/__DEFINES/wiremod.dm:72`), so it differs on every trigger. Every trigger therefore produced a different hash, `TIMER_OVERRIDE` never found a timer to replace, and `timer_id` was simply overwritten, losing the handle to the older timer. The older timers could no longer be stopped by Interrupt either.

### Fix

Commit "Fix issue 79524: circuit delay component no longer stacks overlapping delayed signals" changes `trigger_delay()` to:

- delete the timer stored in `timer_id` (if any) and clear `timer_id` at the start, for both the delayed and the immediate case;
- start the new timer with `TIMER_STOPPABLE` only, no longer relying on `TIMER_UNIQUE`/`TIMER_OVERRIDE`;
- call a new proc, `finish_delay(signal_value)`, when the delay ends. It clears `timer_id` and then calls `output.set_output(signal_value)`.

Clearing `timer_id` in `finish_delay` keeps a stale id from being passed to `deltimer` after the timer has fired. The alternative of keeping `TIMER_UNIQUE` and dropping the value from the callback arguments was not chosen, because the signal value still needs to reach the output.

### Verification

After rebuilding with the fix, a fresh circuit with a Delay of 3 seconds received triggers with values 200, 201, 202 and 203 at 0, 1, 2 and 3 seconds. The Result value was polled every 0.5 seconds. The only change seen was `nil` at 0.5 s and then 203 at 6.5 s, i.e. one output, from the last trigger, about 3 seconds after it. The earlier triggers produced no output.

Not checked: the self-looping circuit (Result wired to Trigger) after the fix, the Interrupt input, a delay at or below the 0.1 second minimum after the change, and power use of a real printed circuit. The earlier read of a single `timer_id` after three triggers on the fixed build agrees with the polling result but is not independent evidence.

### Notes

- In the same trigger, the old code cleared `timer_id` only in the "no delay" branch. The new code clears it in both branches, so a zero-delay trigger also cancels a pending delayed signal, as before.

## #61946: BCI implanter puts the BCI in internal storage and also drops it

Verdict: not reproduced; already fixed on master. No commit.

### The bug

The issue (2021) said that when the BCI manipulation chamber removes a patient's BCI it announces that the BCI went to internal storage, but the BCI was actually dropped on the floor. A comment adds that the BCI could be picked up, and that the chamber would then pull it back and implant it in the next occupant.

### Reproduction attempt

On the test server, using the Lua editor: spawn a `/obj/machinery/bci_implanter`, spawn a human and insert a `/obj/item/organ/cyberimp/bci` into them, then call `close_machine(human)` on the chamber. After about 3 seconds the chamber said "Occupant's previous brain-computer interface has been transferred to internal storage unit." At that point the BCI's location was the chamber and `bci_to_implant` was the BCI. Calling `open_machine()` released the occupant, and the BCI stayed in the chamber with `bci_to_implant` still pointing at it. This was done twice, on two builds, with the same result.

### Cause of the old behaviour, and why it no longer applies

`complete_process()` (`code/modules/wiremod/shell/brain_computer_interface.dm:380`) moves the removed organ into the chamber and sets `bci_to_implant`. Opening the machine calls `dump_inventory_contents()`, which would drop every content. Master overrides it at line 464:

```dm
/obj/machinery/bci_implanter/dump_inventory_contents(list/subset)
	// Prevents opening the machine dropping the BCI.
	// "dump_contents()" still drops the BCI.
	return ..(contents - bci_to_implant)
```

and `Exited()` (line 469) clears `bci_to_implant` when the BCI leaves. This is the behaviour the issue asked for. Which change introduced the override was not determined.

### Notes

Only the open-machine path was checked. The sentence "`dump_contents()` still drops the BCI" in the code comment means other ways of emptying the machine, such as deconstruction, were not tested here.

## #61983: List Literal cannot return a list of type table

### The bug

With the List Literal component set to the `table` type and a table connected to an index port, the Value output stayed `null`.

### Reproduction

In the Lua editor: create a circuit with a List Literal, call `list_options:set_input('table')`, set `entry_ports[1]` to a Lua table of N rows (`{a=i, b=i}` for row i), trigger the component and read the output list. The input value was changed on each trigger.

| Rows N | Output |
|---|---|
| 2, 50, 97, 98 | list of length 1 |
| 99, 120 | `null` |

So small tables worked, and the limit was just under 100 rows, which does not match "no table ever works" in the report but matches the commenter who observed nested lists failing. (A first run returned length 1 for every N including 99 and 120. It was discarded and repeated with a different trigger value on every step; the likely reason is that the unchanged trigger value did not run the component again, but this was not confirmed.)

### Cause

`input_received()` in `code/modules/wiremod/components/list/list_literal.dm:49` guards against runaway nesting:

```dm
if(islist(value) && get_list_count(value, max_list_count) >= max_list_count)
	visible_message("[src] begins to overheat!")
	return
```

`get_list_count()` (line 65) counts the list itself plus every list nested in it. A table is a list of rows, and each row is a list, so a table with 99 rows counts as 100 lists and trips the check (`max_list_count` is 100). The component prints the overheat message and returns before `set_output`, leaving the output `null`. A list of tables is a nest of lists, so this is expected rather than a miscount.

### Fix

Commit "Fix issue 61983: list literal circuit component no longer offers the table type, which always output null for large tables" changes `populate_options()` to offer `GLOB.wiremod_basic_types - PORT_TYPE_TABLE`. This follows the maintainer comment on the issue ("it shouldn't be able to select table in the first place"). Raising the limit or special-casing tables was not tried.

### Verification

After rebuilding, a new List Literal's possible options no longer contained `table`, and `list_options:set_input('table')` left the value at `any`. The large-table case was not run again after the change since it can no longer be selected.

### Notes

- Only List Literal loses the option. List Find, Filter, For Each and the NTNet/Wirenet/NFC components still use the full `GLOB.wiremod_basic_types` list, including `table`; whether they have a similar problem was not tested.
- A saved circuit that has a List Literal set to `table` will now fall back to the option's default type when loaded. This was not tested with an actual saved circuit.
