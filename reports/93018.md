## Summary

`write_map()` (used by the map-export admin verb and the Map Export buildmode) sized its header keys from `(maxx - minx) * (maxy - miny)`, which is one short on each axis and ignores depth. A 2x2 selection got zero-length keys, a one-wide selection computed `log(52, 0)` and returned null, and larger selections could have fewer possible keys than unique headers. The fix counts turfs inclusively on all three axes and always uses at least one key character. The issue's "froze the server for 10 minutes" on placement was not reproduced: the broken exports only produced runtimes, and the one slow load found (a 21x21 station-area export) was not traced to a cause.

## The bug

The reporter exported a pile of walls with the Map Export buildmode, uploaded the result as a map template, placed it, and the server stalled for about ten minutes. On master, the exporter has a clear defect in how it chooses the length of the key that labels each distinct turf/object/area combination in the `.dmm` header. For small selections the exported file is malformed (empty keys) or no file is produced at all.

## Reproduction

The export was driven by calling `write_map` directly from the Lua editor (not through the buildmode click path), then loading the text back with the `load_map` proc / `/datum/parsed_map`. The buildmode caller (`code/modules/buildmode/submodes/map_export.dm`, around line 85) calls `write_map` with the same arguments.

On a running round, on the station z-level:

1. Open the Lua editor and call `write_map(minx, miny, z, maxx, maxy, z, 16383)` (through `SS13.await(SS13.global_proc, 'write_map', ...)`, since the proc sleeps) for a 2x2 region of space turfs, e.g. (100,140)-(101,141).
2. The returned text had zero-length keys. Each header block began `"" = (` followed by `/obj/structure/lattice, /turf/open/space/basic, /area/space/nearstation)`.
3. Constructing a `/datum/parsed_map` from that text logged a runtime from `code/modules/mapping/reader.dm:226`: `Coords before model definition in DMM`. No freeze occurred.
4. Calling `write_map` for a region one turf wide or tall (1xN or Nx1) logged `runtime error: log(52,0) is not computable` and returned null.
5. Separately, a 21x21 station-area export, (90,100)-(110,120), produced 87,832 characters quickly (441 turfs need 2-character keys, and the old formula produced them). Loading it with `load_map(text, 10, 10, 2)` was still running after more than 3 minutes with DreamDaemon at about 56% CPU while the server stayed responsive; an 11x11 export loaded in under 30 seconds. This is the only slow load observed and it is not confirmed to be the reported freeze.

## Cause

`code/modules/admin/verbs/map_export.dm:210-212` computes the spans as differences:

```dm
var/width = maxx - minx
var/height = maxy - miny
var/depth = maxz - minz
```

so a selection that is N turfs wide has `width == N - 1`. Lines 224-225 then derive the key length from those spans:

```dm
var/turfs_needed = width * height
var/layers = FLOOR(log(GLOB.save_file_chars.len, turfs_needed) + 0.999,1)
```

`GLOB.save_file_chars` has 52 entries. Consequences:

- A 2x2 selection has `width == height == 1`, so `turfs_needed == 1`, `log(52, 1) == 0` and `layers == 0`. `calculate_tgm_header_index` (line 350, called at line 317) then returns an empty key for every header.
- A selection one turf wide or tall has a span of 0, so `turfs_needed == 0` and `log(52, 0)` is not computable. `write_map` returns null.
- The count is smaller than the real turf count `(width + 1) * (height + 1)`, so for some sizes the key space (52^layers) can be smaller than the number of unique headers. The index would then wrap and produce duplicate keys. This was reasoned from the code, not observed.
- Depth was ignored even for multi-z selections.

On the reader side, `code/modules/mapping/reader.dm:215-226` takes `key_len` from the first header key and crashes with `Coords before model definition in DMM` if it is zero when coordinates are encountered.

## Fix

One commit, "Fix issue 93018: map export key length ignored the inclusive turf count", changes `code/modules/admin/verbs/map_export.dm` only:

```dm
var/turfs_needed = (width + 1) * (height + 1) * (depth + 1)
var/layers = max(1, CEILING(log(GLOB.save_file_chars.len, turfs_needed), 1))
```

The turf count is now the inclusive volume of the selection, and `max(1, ...)` guarantees at least one key character (a single turf gives `log(52, 1) == 0`). `CEILING(log(...), 1)` replaces `FLOOR(log(...) + 0.999, 1)`, which was an approximation of the same thing. Counting depth makes the key space large enough for multi-z selections.

## Verification

After rebuilding and starting a new round on the test server, exports of 2x2, 1x5, 5x1 and 1x1 regions all produced text with the key `"a"`, loaded back through `load_map` to completion, and logged no runtime from `reader.dm` or `map_export.dm`.

Not checked:

- The reported freeze. Neither the original wall pile nor the buildmode placement path (`map_template.load` after upload and place) was tested; only bare `load_map` calls.
- Exports large enough to need two or more key characters were exercised only before the fix (the 21x21 export); they were not re-run after.
- Behavior with several z-levels selected.

## Notes

- The key-length defect cannot by itself explain a ten-minute stall: it produces runtimes, not loops. The reporter's selection (a pile of walls, likely thin or small) may have hit the 1xN or 2x2 case, but the issue does not say what size was exported, and the reporter was also running four test merges.
- Lead for whoever continues: the 21x21 load took more than 3 minutes while an 11x11 took under 30 seconds, suggesting load cost grows faster than area in the map loader or template load (`code/modules/mapping/reader.dm`, per-row/column loops, or atmos/lighting initialization). A line-profiler run during a 21x21 `load_map` would show where the time goes. It was not profiled, and it was not confirmed whether that load ever finished.
