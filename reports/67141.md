# #67141: Growing samples with both motile fungal hyphae and amphibian cells causes runtimes

| | |
|---|---|
| Issues | [#67141](https://github.com/tgstation/tgstation/issues/67141): verified, fixed |
| Status | Reproduced on master, fixed, checked in game |
| Fix branch | [fix/67141](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/67141) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

When a growing vat holds a sample with two or more cell lines (for example frog and walking mushroom) and no resampler is active, the first line to reach 100% growth deletes the vat's sample. `biological_sample/handle_growth()` keeps looping over its remaining cell lines anyway, so the next one runs `calculate_growth()` with a null sample and runtimes with `Cannot read null.micro_organisms`. The fix stops the loop as soon as the sample has been consumed.

## The bug

A sample containing both cell lines is put in a vat filled with protein. When growth completes, the vat reports the sample as gone and the log fills with runtimes. In the report, the same two runtimes appeared whether the growth failed or produced a walking mushroom or frogs.

## Reproduction

Reproduced with admin tools by constructing the sample directly, not by taking samples from ferns. Whether such a sample can occur naturally was not tested.

1. On a running round, open the Lua editor.
2. Spawn a `/obj/machinery/vatgrower` and anchor it. Add 100 units of protein to its reagents.
3. Create a `/datum/biological_sample` whose `micro_organisms` contain a `/datum/micro_organism/cell_line/frog` and a `/datum/micro_organism/cell_line/walking_mushroom`. Put it in a `/obj/item/petri_dish` (`sample` var) and call the vat's `deposit_sample()` with it. The resampler is off by default, and was off here.
4. Set `growth = 99` on both cell lines so they finish on the next vat process tick.
5. Wait a few seconds and read the round's `runtime.log`.

Observed before the fix: both "The random frog pops out of the growing vat!" and "The walking mushroom pops out of the growing vat!" appeared in chat, and `runtime.log` contained one runtime:

```
runtime error: Cannot read null.micro_organisms
 - proc name: calculate growth (/datum/micro_organism/cell_line/proc/calculate_growth)
 - source file: code/modules/research/xenobiology/vatgrowing/samples/_micro_organism.dm,72
 - src: Unknown fluids (/datum/micro_organism/cell_line/walking_mushroom)
```

It was called from `/datum/biological_sample: handle growth`.

## Cause

`/datum/biological_sample/proc/handle_growth()` (`code/modules/research/xenobiology/vatgrowing/samples/_sample.dm:34`) iterates every cell line in the sample and calls `organism.handle_growth(vat)` on each.

When a line reaches 100 growth, `finish_growing()` (`.../samples/_micro_organism.dm:79`) sends `COMSIG_SAMPLE_GROWTH_COMPLETED`. The vat handles it in `on_sample_growth_completed()` (`.../vatgrower.dm:166`):

```dm
if(resampler_active)
	...
	biological_sample.reset_sample()
else
	QDEL_NULL(biological_sample)
```

Without a resampler, `vat.biological_sample` becomes null in the middle of the loop. The next cell line then runs `handle_growth()` (`_micro_organism.dm:36`), which calls `calculate_growth(vat.reagents, vat.biological_sample)` (line 39) with null. `calculate_growth()` iterates `biological_sample.micro_organisms` to apply virus penalties (line 72), and that read fails. The two lines being at 99 growth in the same tick is what the reporter guessed ("both cell lines finishing at the same time"). Any order works as long as a second line is processed after the first has consumed the sample.

The issue shows a second runtime in `finish_growing` (`null.micro_organisms`, line 76 in the 2022 code). At master that proc only sends signals with `vat.biological_sample` as the target, and no second runtime was seen when reproducing. I did not trace what the 2022 code did there.

## Fix

One commit, "Fix issue 67141: stop growing a vat sample's remaining cell lines once one consumed it", changes `_sample.dm`. After each `organism.handle_growth(vat)` it breaks out of the loop if the sample was deleted or is no longer the vat's sample:

```dm
organism.handle_growth(vat)
//A cell line that finished growing may have consumed this sample (no resampler): the remaining lines have nothing left to grow in.
if(QDELETED(src) || vat.biological_sample != src)
	break
```

With the resampler on, the sample survives and `reset_sample()` zeroes the other lines' growth, so the loop continues as before.

## Verification

After rebuilding, the same setup was repeated in game (new round, same Lua steps, both lines at 99 growth). Chat showed only "The random frog pops out of the growing vat!", and the new round's `runtime.log` had no `micro_organisms` runtime (it had one before the fix).

Not checked: the resampler-on path, samples with viruses, a natural fern-derived sample, and three or more cell lines.

## Notes

- Behavior change: when two lines finish in the same tick, only the first one in list order produces its mob; the other is lost with the sample. Before the fix both mobs spawned (along with the runtime). If both should spawn, an alternative is to let the remaining lines finish without the sample, but that needs `calculate_growth()` to tolerate a null sample and wasn't tried.
- The "Found a null in simple_animals list!" line in the report was not investigated.
