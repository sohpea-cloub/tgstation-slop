# #87135: A borg's buckled rider blocks the thing the borg is pulling

## Summary

When a cyborg has a human buckled to it and is also pulling a dense object or mob, the pulled thing does not follow the borg. The rider is still standing on the tile the borg just left when the pulled thing tries to step onto it, so the rider's collision check refuses the move. The fix adds one rule to `/mob/living/CanAllowThrough`: a mob whose buckle target is the puller of the thing currently being moved by a pull lets that thing through.

## The bug

#87135 reports that a borg with a rider who tries to drag another human around "feels glitchy", as if collisions happen in the wrong order. #77190 reports the same thing for pulled solid objects: "pulling solid objects will be interrupted, as if you placed an invisible wall before moving", and notes that it does not happen on diagonal steps. In both cases the borg walks off and the pulled thing is left behind. When it is left more than a tile away, the pull is dropped.

## Reproduction

All steps are on master `87b93338`, on a private test server with admin tools. The setup was done through the Lua editor; the final movement was done by taking control of the borg and walking with ordinary movement input.

1. Start a round and open the Lua editor. Spawn a cyborg (`/mob/living/silicon/robot`) and a human (`/mob/living/carbon/human`) on one tile in an open hallway.
2. Buckle the human to the borg: `borg:buckle_mob(human, true, false)`.
3. Spawn a dense object, a water tank (`/obj/structure/reagent_dispensers/watertank`), on the tile behind the borg and make the borg pull it: `borg:start_pulling(tank)`.
4. Give the borg to a player (`borg.ckey = ...`) and walk it one tile east.

Observed on master:

- The borg moved from 110,144 to 111,144. The tank stayed at 109,144, two tiles behind. The borg's "stop pulling" HUD button was still shown after this step.
- Earlier runs on master, driving the borg with `Move()` from Lua, gave the same picture. With a rider, a pulled water tank and a pulled space heater stayed where they were and the pull was dropped (borg at 106, rider at 106, tank still at 104). The same tank pulled by a borg with no rider moved along normally (borg 106, tank 105).
- A control run of the same setup with the rider unbuckled and moved away let the tank follow, which points at the rider as the blocker.

Things that were not reproduced or not clear:

- In the direct `Move()` runs on master, a pulled standing human followed the borg even with a rider on it (borg 106, rider 106, pulled human 105). So the blocking was only seen with dense objects (water tank, space heater). Why the pulled human was not blocked in those runs was not investigated. The fix was nevertheless also tested with a pulled human (see Verification).
- A closed crate was inconclusive: it was not pulled with or without a rider in the one run on master.
- The diagonal case from #77190 was not tested in game; the explanation in Cause is from reading the code.

## Cause

Pulling is handled inside the puller's own `/atom/movable/Move`. After the puller has moved, it moves its pulled thing onto the tile the puller just left (`code/game/atoms_movable.dm:848-864`, which calls `pulling.move_from_pull(src, target_turf, glide_size)`; `move_from_pull` at `code/game/atoms_movable.dm:894-897` sets `moving_from_pull` to the puller for the duration of that `Move`).

Buckled mobs are moved later. `handle_buckled_mob_movement` is only called at the end of `Move` (`code/game/atoms_movable.dm:883`, defined at `:1476`). So at the moment the pulled object tries to enter the old tile, the rider is still standing there.

Entering that tile asks the rider's `CanAllowThrough` (`code/modules/mob/living/living_movement.dm:58-69`):

```dm
/mob/living/CanAllowThrough(atom/movable/mover, border_dir)
	. = ..()
	if(.)
		return
	if(mover.throwing)
		...
	if(buckled == mover)
		return TRUE
	if(ismob(mover) && (mover in buckled_mobs))
		return TRUE
	return !mover.density || body_position == LYING_DOWN
```

A dense mover that is not the rider's own buckle target or one of the rider's own riders is only let through if the rider is lying down. A standing rider is dense, so a dense pulled object is refused. The pull step fails, the pulled thing is left behind, and the next call to `check_pulling` drops the pull because the distance is now too large.

Diagonal moves do not hit this because then the pulled thing does not step onto the tile the borg left (the code around `atoms_movable.dm:857-864` only moves the pullee when the target turf differs, or for a diagonal first step). That is consistent with #77190's remark, but it was not tested.

## Fix

One commit on `fix/87135`: "Fix issue 87135: a borg's rider no longer blocks what the borg is pulling". It adds this to `/mob/living/CanAllowThrough`, before the final density check:

```dm
// Our puller's rider is still on the tile the puller just left (buckled mobs move after the pull step), so don't let it block what the puller drags.
if(mover.moving_from_pull && (src in mover.moving_from_pull.buckled_mobs))
	return TRUE
```

`moving_from_pull` is already set by `move_from_pull` for exactly the duration of the pull step, so the rule applies only to the thing being dragged, only while it is being dragged, and only for the riders of the mob that is dragging it. Everything else a rider collides with is unchanged. The commit message includes `Fixes #77190`.

Not tried: reordering the movement so that riders move before the pull step. That would change movement order for every buckled-mob case and is a much larger change than a targeted exemption.

## Verification

On a build with the fix, with a player controlling the borg that had a human rider:

- Pulled water tank: the borg stepped east from 118,144 to 119,144 and the tank came along to 118,144. The rider stayed buckled.
- Further single steps (east, then north, west and south) with the tank pulled and the rider buckled each brought the tank along; the tank ended one tile behind the borg each time.
- Pulled standing human: the borg stepped from 119 to 120 and the pulled human followed to 119,144, with the rider still buckled.
- `CanPass` called directly on the rider with `moving_from_pull` unset returned false for the water tank and true once it was set to the borg.
- With the fix temporarily removed and the game rebuilt, the first scenario failed again (borg moved, tank left behind), so the difference is due to the change. The fix was then restored and committed.
- No new runtimes appeared in the runtime log from the change.

Not checked: diagonal moves; riders on anything other than a borg (the rule covers any puller with riders, for example other ridden mobs or vehicles, but only the borg case was run); pulling across z-levels; whether the remaining "glitchy" visual feel the reporter describes (glide/animation of the rider and pulled thing) is fully gone, since only positions and pull state were observed.

## Notes

- The rule is generic: it covers any puller that has buckled mobs, not only borgs.
- A comment in #77190 suggests borgs might not be meant to pull and carry a rider at once. The fix assumes that doing both is allowed and just makes it work.
