# #69680: Bots stall for minutes when a patrol beacon is unreachable

| | |
|---|---|
| Issues | [#69680](https://github.com/tgstation/tgstation/issues/69680): the reported behaviour (bouncing between two beacons, causing lag) did not reproduce on master; a related patrol stall was found, fixed and verified instead |
| Status | Fixed (related stall) and checked in game on MetaStation |
| Fix branch | [fix/69680](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/69680) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The 2022 report describes a "simplebot" that cannot reach patrol point C, falls back to point A, walks to B again and repeats forever, flooding the pathfinder. The simplebot code no longer exists, and on master that A-B loop and the lag spikes did not happen. What did happen is that one unreachable beacon left a bot standing still for about 4 minutes, failing one beacon after another, because patrol movement used a 25-tile path limit while most beacons were further away. The fix lets patrol use the longer 60-tile movement type that was already defined, gives up at once when no path exists, and has the bot skip beacons it recently failed to reach.

## The bug

#69680 (Performance, Bug) was written against the old simplebot code. Its description:

- The bot pathfinds from patrol point B to patrol point C.
- It cannot reach C, so it re-calculates, finds no path, and returns to the previous point A.
- From A it continues the normal patrol back to B, and the cycle repeats.

The discussion called this a lag exploit (the reporter said they had consistent reproduction steps and did not post them). One comment proposed making path generation use a subsystem and, separately, preventing the loop in the first place. A later comment says pathfinding now runs on a subsystem, so the massive lag is gone, but the flawed AI behaviour the report describes is still worth fixing.

Today every bot is a `/mob/living/basic/bot` with a behaviour-tree AI. Patrol is `find_next_beacon_target`, falling back to `find_first_beacon_target`, followed by `move_to_target` and `arrive_at_beacon` (`code/datums/ai/bots/bot_subtrees.dm`).

## Reproduction

### The reported behaviour (not reproduced)

Using the Lua editor on MetaStation (round started, observer only):

1. List the station's navbeacons (`GLOB.navbeacons["2"]`, 33 of them). The chain used was `10-Aft-To-Central` (106,92), `10.1-Central-from-Aft` (106,115), `10.2-Aft-Port-Corner` (88,116), `11-Command-Port` (88,126) and onward.
2. Replace the eight floor tiles around (106,115) with `/turf/closed/wall/r_wall` using `ChangeTurf`, so beacon 10.1 cannot be reached.
3. Spawn a `/mob/living/basic/bot/secbot` at (106,94). Autopatrol is on by default. Set its `previous_beacon_target` blackboard key to beacon 10 so that 10.1 is its next target.
4. Register for `mob_ai_movement_started` / `mob_ai_movement_failed` on the bot and sample `SSpathfinder.cost` every few seconds.

Observed: no return to the previous beacon and no A-B oscillation. `SSpathfinder.cost` stayed around 0.5-5 ms on master in this setup, with an occasional spike (up to 74 ms noted); nothing like the lag the report describes.

### The related stall (reproduced on master)

In the same test the bot did not oscillate; it stopped. After failing 10.1 it stood at about (106,94) for roughly 4 minutes, starting and failing 25 beacon targets in a row (10.2, 11, 11.1, 12, 13.1, and on down the chain) until one of them was within about 25 path tiles. Each failed attempt took about 4 s. A Beepsky and a cleanbot on the station were also seen stuck the same way at (106,92). The same kind of stall (repair bots behind firedoors) was seen independently while looking at #63258; that issue was not part of this unit.

## Cause

Three things combine, all on master:

1. **Patrol uses a 25-tile path limit.** Bots move with `/datum/ai_movement/jps/bot` (`code/datums/ai/movement/ai_movement_jps.dm:54`), with `maximum_length = 25` and `max_pathing_attempts = 8`. JPS rejects a path longer than that outright. A subtype `/datum/ai_movement/jps/bot/travel_to_beacon` exists with `maximum_length = AI_BOT_PATH_LENGTH` (60), but nothing used it, so most next beacons, which are further than 25 tiles, were unreachable by definition.
2. **A failed beacon is never put on the ignore list.** `find_next_beacon_target` (`bot_subtrees.dm:172`) sets `BB_PREVIOUS_BEACON_TARGET` to the beacon it picks, which is why the report's A-B loop no longer happens (the chain moves on). But the key is only cleared when no next beacon exists, so the fallback `find_first_beacon_target` (nearest beacon) is never run again after one failure. The bot just takes the next beacon in the chain, fails it too, and so on. A failed beacon is not added to `BB_TEMPORARY_IGNORE_LIST`.
3. **Each failure takes about 10 search attempts.** `fail_movement()` only fires after the attempt limit, so a hopeless target costs several seconds of repeated searching. A long search that finds nothing is also the expensive case for the pathfinder.

A side finding: `fail_movement()` (`code/datums/ai/movement/_ai_movement.dm:42`) calls `stop_moving_towards()`, which forgets the target, before it sends `COMSIG_MOB_AI_MOVEMENT_FAILED` with `moving_controllers[controller]`, so the signal always carried a null target.

## Fix

Two commits.

**Fix issue 69680: bots no longer stall on an unreachable patrol beacon** changes `bot_subtrees.dm`, `bot_patrol.bt.json` (and its compiled JSON under `build/behavior_trees/`), `ai_movement_jps.dm`, `bot_ai.dm` and `medbot_ai.dm`:

- A new node `/datum/bt_node/ai_behavior/move_to_target/patrol_beacon` is used for the patrol move. Its `setup()` takes the movement type from a new `patrol_movement_type` var on the bot controller, which defaults to the existing, previously unused `/datum/ai_movement/jps/bot/travel_to_beacon` (60 tiles). Medbots use `/datum/ai_movement/jps/bot/medbot/travel_to_beacon` so they keep their stationary-mode behaviour.
- A new `fail_without_path` var on `jps/bot`, set to TRUE on both `travel_to_beacon` types. When the pathfinder returns an empty path (`COMSIG_MOVELOOP_JPS_FINISHED_PATHING`), the movement fails immediately rather than searching up to 10 times. A fixed beacon that cannot be reached will not become reachable on the next search. This was needed: with 60-tile paths but no early give-up, the first fixed build drove `SSpathfinder.cost` to 268-668 ms for the roughly 18 s one failure lasted, which is the kind of lag the issue complains about.
- When pathing to a beacon fails, the node calls `note_unreachable_target()` on it, which puts it on the temporary ignore list (`BB_UNREACHABLE_LIST_COOLDOWN`: 45 seconds by default in `bot_ai.dm:9`; some bot types, such as the secbot, override it with other values).
- `find_next_beacon_target` now walks down the chain past beacons that are on the ignore list or further than the patrol path length (via a new helper, `find_patrol_beacon`). If nothing down the chain will do, or after two failures in a row (counted on the node), it clears `previous_beacon_target`. `find_first_beacon_target` then picks the nearest beacon that is not ignored and within range.

The chain is tried first, and the nearest beacon only as a fallback, because going straight to the nearest beacon after one failure would bring back the report's A-B loop once the ignore entry expired.

**Fix issue 69680: send the failed target with COMSIG_MOB_AI_MOVEMENT_FAILED** reads `moving_controllers[controller]` before `stop_moving_towards()` clears it, so the signal carries the target. No listener uses the argument yet.

## Verification

In game on MetaStation, with the final build and the same set-up as the master test, but with r-walls around both beacon 10.1 (106,115) and beacon 10.2 (88,116), a test secbot at (106,94) with beacon 10 as its previous target, signals hooked on every bot except MULEbots, and `SSpathfinder.cost` sampled every 3 s:

- The bot started toward 10.1 and failed after one search, in 0.5 s (versus about 4 s per failure on master and about 18 s on the first fixed build). It then tried 10.2 and failed in 0.5 s.
- Since that was two failures in a row, it took the nearest beacon, then went 8.1, 9.1, 9.2, 9.3, 9.4, 10. Later it skipped the ignored 10.1 and 10.2 and went to 11-Command-Port, walking around the walls, then 11.1, 12, 13.1 and on. It kept moving the whole time.
- `SSpathfinder.cost` over 40 samples averaged 1.16 ms with a maximum of 7.1 ms (on master in this setup: 0.5-5 ms, with spikes up to 74 ms).
- Normal patrols were not broken: Beepsky completed its chain (1, 1.5, ... 6, 7, 7.5, 8, 8.1, 9.x) with no patrol failures, including the 6 to 7 link of 38 tiles that is now in range. A medibot patrolled the whole chain on its own movement type with no failures. A cleanbot's patrol worked; it failed 9.2-Escape-2 in 0.5 s in two separate rounds, so that looks like a deterministic no-path (probably door access, since Beepsky reaches it) rather than a false skip, and it moved on to 9.3.
- No runtimes from bots, pathing or AI movement. The only entries were the empty `uncaught runtime error:` lines from the Lua runs themselves.

Not checked: any map other than MetaStation (a link longer than 60 tiles is still skipped immediately, as before); a unit test (none was added or run); other bot types beyond secbot, medbot and cleanbot; the original reporter's exact steps, which were never posted.

## Notes

- **Behaviour change to weigh.** With `fail_without_path`, a beacon goes on the ignore list (45 s by default) after a single empty search. Previously a bot made 10 searches 0.5 s apart, which would have got past something blocking the way only briefly (a door opening, a person in a corridor). A temporary block now costs a skipped beacon rather than a short delay.
- The 25-tile `jps/bot` limit still applies to everything other than patrol (targets such as dirt, patients and suspects).
- Related issues listed in the discussion (#37642, #63258, #69395) were not examined. The only merged PR found that touches this area is #82874 ("jps mobs pathing forever"); an open PR #97312 rewrites pathfinding with a native A* and was not about patrol.
- The first commit changes the compiled behaviour-tree JSON as well as the source JSON, since the repository keeps both.
