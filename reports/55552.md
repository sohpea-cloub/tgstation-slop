# #55552: Explosive gondola pods destroy their own delivery

| | |
|---|---|
| Issues | [#55552](https://github.com/tgstation/tgstation/issues/55552): verified (the 2020 runtime itself no longer occurs; a related bug in the same code, the pod destroying its own cargo, was reproduced and fixed) |
| Status | Fixed on the fix branch; fix checked in game |
| Fix branch | [fix/55552](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/55552) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The issue reports a runtime when a gondola-styled supply pod with an explosion lands. The reported runtime did not appear on master, but the underlying problem is still there: the pod explodes on landing and then turns into a gondola mob on the same tile, the blast kills that gondola, and because the gondola deletes itself on death, the cargo inside is deleted with it. The fix makes the gondola pod mob ignore explosions while its linked pod is an explosive one.

## The bug

An admin sends a gondola-styled supply pod with a non-zero explosion. The pod lands, explodes, and a gondola appears. What the issue saw was a runtime from the pod's delayed "open" callback. On master there is no runtime, but the gondola does not survive a large blast and the delivery never arrives: the gondola dies within about half a second of the explosion, and the items it carried are gone with it.

## Reproduction

All on the test server, as an observer, using the Lua editor:

1. Created a `/obj/structure/closet/supplypod/centcompod` and set its style to `/datum/pod_style/gondola`.
2. Set `explosionSize` to `(3, 4, 5, 3)` (devastation, heavy, light, flame), `reversing = 0` and `bluespace = 0`, and put a crowbar inside.
3. Created an `/obj/effect/pod_landingzone` on a hallway turf with that pod.
4. Waited for the pod to land.

Observed on master:

- No runtime appeared in `runtime.log` or in the server output in any run.
- With a large explosion, the game log had an "Explosion ... Possible cause: the gondola" line and the attack log had `ATTACK: ... (gondola) died` within about 0.5 s of it. This happened in all three large-blast runs. The gondola was gone and the crowbar with it, even though the crowbar was set to be indestructible: it was deleted, not destroyed.
- With a small blast `(0, 0, 1, 2)`, the gondola survived (its health was 170 of 200, so it was damaged but alive).
- A bluespace pod simply deletes itself after opening, which is by design.

## Cause

`/obj/structure/closet/supplypod/proc/pre_open()` (`code/modules/cargo/supplypod.dm:321`) does the explosion first and then builds the gondola:

```dm
explosion(turf_underneath, boom[1], boom[2], boom[3], flame_range = boom[4], ... explosion_cause = src)
...
if (ispath(style, /datum/pod_style/gondola))
	var/mob/living/basic/pet/gondola/gondolapod/benis = new(turf_underneath, src)
	benis.contents |= contents
```

(`supplypod.dm:361` and `:370-376`.) The blast damages the gondola as a normal `/mob/living/basic` (`code/modules/mob/living/basic/basic_defense.dm:117`), which kills it at a large size. Gondolas are `DEL_ON_DEATH` (`code/modules/mob/living/basic/pets/gondolas/gondola.dm`), and `/mob/living/basic/pet/gondola/gondolapod/death()` also does `QDEL_NULL(linked_pod)` (`code/modules/mob/living/basic/pets/gondolas/gondolapod.dm:35`). So the cargo, which `pre_open()` had moved into the gondola's contents, is deleted with the mob. The pod itself is moved to nullspace right afterwards (`supplypod.dm:375`) and a delayed `open_pod` callback is registered on it (`:376`).

The issue's 2020 runtime came from that delayed callback running on a pod that had been deleted in the meantime (also noted in the issue's comments). On master the callback no longer errors: `/datum/callback/Invoke` returns early when its object is gone (`code/datums/callback.dm:104`). That explains the missing runtime, but I did not trace it further than reading that code; what was observed is simply that no runtime occurred.

The ordering (explosion before the gondola exists) was not changed by the fix; the cargo loss is the observable problem.

## Fix

One commit, "Fix issue 55552: explosive gondola pods no longer kill their own gondola". It adds an `ex_act()` override to `/mob/living/basic/pet/gondola/gondolapod` in `gondolapod.dm`:

```dm
/mob/living/basic/pet/gondola/gondolapod/ex_act(severity, target, origin)
	if(!QDELETED(linked_pod) && length(linked_pod.explosionSize) && (linked_pod.explosionSize[1] + linked_pod.explosionSize[2] + linked_pod.explosionSize[3]))
		return FALSE
	return ..()
```

The override ignores the explosion when the linked pod has a non-zero devastation, heavy or light range, which are the ranges that call `ex_act()`. The flame and flash ranges of the blast do not use `ex_act()`, so they are not part of the check. This follows the idea of an earlier, closed upstream PR (#60589) but is written for the current basic-mob gondola. Alternatives such as changing the order in `pre_open()` (explode before creating the mob) were not tried.

## Verification

On a build of the fix branch, the same large-blast launch was repeated: the gondola stayed alive (it showed the open overlay, `gondola_open`), and the crowbar was delivered to the tile at 108,144. The attack log had no gondola deaths and there were no runtimes.

Not checked: pods with only a small or only fire/flash explosion on the fix branch; cargo that is a living mob; a player-controlled gondola; other specialised pods; a non-explosive gondola pod after the change; a gondola killed by some other source while its pod is explosive.

## Notes

- The fix has a side effect worth weighing: while the linked pod has a non-zero devastation/heavy/light range, the gondola is immune to every explosion, not only its own pod's. A bomb set off later by someone else at that gondola, while it is still waiting to deliver, also does nothing. The same limitation applies to the earlier closed upstream PR.
- Because the check reads the pod's `explosionSize`, the base supply pod default `(0,0,2,3)` (`supplypod.dm:49`) also counts as explosive, so a gondola pod that keeps that default would also be covered; this was not tested.
- A more targeted option would be to make only the pod's own explosion not hurt the gondola (for example by creating the mob after the blast, or by tagging the blast's cause); that was not implemented or tested.
- The issue's comment that gondola pods "refuse to transport anything" was not investigated.
