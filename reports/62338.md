# #62338: An interrupted soulscythe charge leaves the scythe stuck in the charging state

| | |
|---|---|
| Issues | [#62338](https://github.com/tgstation/tgstation/issues/62338): verified (reproduced, then fixed) |
| Status | Fixed, with a one-commit fix on a branch |
| Fix branch | [fix/62338](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/62338) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

`/obj/item/soulscythe/proc/charge_target()` sets `charging = TRUE` before its 2-second `do_after()` and returns early when that `do_after()` is interrupted, without clearing the flag. Only `throw_impact()` ever clears it, so the scythe stays "charging" indefinitely. While the flag is set, the soul inside cannot move the scythe and cannot start another charge. The fix clears `charging` and resets the spin animation on the interrupt path. It also undoes the charge state if `throw_at()` refuses to start the throw.

## The bug

A player controlling a soulscythe (the soul inside it) can charge at a target with the secondary attack. The charge has a 2-second windup, after which the scythe is thrown at the target. If the windup is interrupted, the soul sees "interrupted!" and nothing else happens. The scythe is then stuck: movement input does nothing, and further charges are refused. The flag is only reset when the scythe next hits something after being thrown, so the scythe stays stuck until another mob throws it. The issue's title says the same.

## Reproduction

All steps were done on the test server as an admin, using the Lua editor and SDQL2. The charge was started by calling `charge_target()` directly instead of by the soul's secondary click, because the interrupt had to be timed exactly.

1. Open the Lua editor and create a state.
2. Spawn a scythe on the floor with `SS13.new('/obj/item/soulscythe', loc)`.
3. Call `scy:charge_target(scy)` from a timer. This prints "The soulscythe starts charging..." and starts the 2-second `do_after()`.
4. One second later, call `scy.soul:forceMove(<turf>)`. This moves the soul out of the scythe. The charge's `do_after()` is called with `IGNORE_TARGET_LOC_CHANGE` but without `IGNORE_USER_LOC_CHANGE`, so a change in the user's location interrupts it.
5. At 2.5 seconds, call `scy.soul:forceMove(scy)` to put the soul back inside the scythe.
6. Read `scy.charging`, `scy.throwforce` and the locations.

Observed on master: `scy.charging` was `1` well after the interruption, `scy.throwforce` was `17` (so no throw had happened), and the soul was back in the scythe lying on the floor. The flag stayed set, which matches the issue.

Two details of the setup:

- Paralysing the soul (SDQL2 `CALL Paralyze(100) ON /mob/living/basic/soulscythe`, or `Paralyze` from Lua) did not interrupt the charge. `do_after()` registers its incapacitation check on the signal for the trait being added (`code/datums/timed_actions.dm:77-78`), and the charge ran to the end and threw the scythe at the target. That is why the location change was used instead.
- A control charge with no interruption, started with `CALL charge_target(src) ON /obj/item/soulscythe`, ran normally: "The soulscythe charges at the soulscythe!". It did not hit the bug.

## Cause

In `code/game/objects/items/weaponry/melee/soulscythe.dm`, `charge_target()` (line 226) does the following:

```dm
if(charging || !use_blood(30))
	return
COOLDOWN_START(src, attack_cooldown, 5 SECONDS)
animate(src)
charging = TRUE
...
if(!do_after(soul, 2 SECONDS, target = src, timed_action_flags = IGNORE_TARGET_LOC_CHANGE))
	balloon_alert(soul, "interrupted!")
	return
```

When `do_after()` fails (lines 234-236), the proc returns with `charging` still `TRUE`. Its only reset is in `throw_impact()` (lines 124-130), which runs only after the scythe was actually thrown. Two checks then block the soul:

- `relaymove()` returns immediately while `charging` is set (line 111), so the soul cannot move the scythe.
- `charge_target()` returns immediately while `charging` is set (line 227), so it cannot charge again. The 5-second attack cooldown expires, but the flag still blocks the charge.

The `animate(src)` at line 230 also stops the idle spin animation. The interrupt path never restores it either, because `reset_spin()` is only called from `throw_impact()` and a few other places.

The soulscythe's soul mob was converted to a basic mob in upstream PR #91667. That PR is already in the tested build, but it did not touch this logic, and the bug was still present on master.

## Fix

One commit, "Fix issue 62338: soulscythe stays stuck charging when its charge is interrupted", changes `charge_target()` in two places:

- On an interrupted `do_after()`, it now sets `charging = FALSE` and calls `reset_spin()` before returning. This is the issue's suggested fix, plus restoring the spin animation that `animate(src)` had stopped.
- The call `throw_at(attacked_atom, 10, 3, soul, FALSE)` is now wrapped in `if(!throw_at(...))`. `throw_at()` can return `FALSE` without starting a throw, in which case `throw_impact()` would never run and the scythe would be stuck in the same way, with its `throwforce` doubled as well. In that case the code now sets `charging = FALSE`, halves `throwforce` again (`*= 0.5`, the same undo that `throw_impact()` does), and calls `reset_spin()`.

The `throw_at()` change goes beyond what the issue describes. It was added because the same stuck state was reachable through that early return.

## Verification

After the fix was built on the test server, the same Lua editor sequence was run again (charge, then `forceMove` of the soul at +1 second, then the soul put back at +2.5 seconds):

- Right after the interruption, `scy.charging` was `0`.
- A second scythe was charged at a turf 5 tiles east to check that a normal charge still worked. It printed "The soulscythe charges at the floor!" and moved 5 tiles. Afterwards its `charging` was `0` and its `throwforce` was `17` (not doubled).
- No runtimes were logged from the soulscythe code during these tests.

Not checked:

- The new `throw_at()` failure branch was not exercised. No case where `throw_at()` returns `FALSE` was constructed.
- A real player controlling the scythe was not used. The charge was started by calling the proc directly, and the interruption was a forced move of the soul.
- The result after the interrupt was checked through `charging` and `throwforce`. Movement with `relaymove()` and a second charge after an interruption were not exercised in game, and neither was the spin animation.
- Other interruption causes (for example the soul being incapacitated in a different way) were not tested.

## Notes

- The paralysis attempt above showed that `do_after()` for the soul only reacts to the incapacitated trait being added during the action, not to the soul already being paralysed. If the soul is already incapacitated when the charge starts, the check at the beginning is not what stops it. This was a side observation and was not investigated further.
- The fix only touches the charge path. The "resist" `do_after()` in the same file (line 163 area, `on_resist`) also returns on interruption; it does not use `charging`, so it was left alone.
