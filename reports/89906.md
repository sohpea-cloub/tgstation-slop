# #89906: Universal scanner can't be placed on tables or in backpacks

| | |
|---|---|
| Issues | [#89906](https://github.com/tgstation/tgstation/issues/89906) verified and fixed |
| Status | Fixed on the branch, verified in game |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/89906 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

While in export-scan or price-tag mode, the universal scanner treated every click on an object as a scan, including clicks on tables and backpacks, so it could not be put down or stored. The fix makes it ignore the click when the user is in combat mode, so the normal placement and storage handling runs, as with soap and similar items. The screentip was not changed.

## The bug

The issue asks that the scanner check combat mode "like soap and whatnot". On master, clicking a table or backpack with the scanner in hand only produced a scan message.

## Reproduction

1. On the test server, use the Lua editor to spawn a human (possessed), a table, a backpack and a universal scanner placed in the human's hand.
2. Click the table, then the backpack.
3. Observed: "Scanned the table, no export value." and "Scanned the backpack, no export value." The scanner was never placed or stored.

## Cause

`interact_with_atom` in `code/modules/cargo/universal_scanner.dm:62-71` returns `NONE` only for non-objects. For any object it returns `ITEM_INTERACT_SUCCESS` in `SCAN_EXPORTS` and `SCAN_PRICE_TAG` modes, with no combat mode check:

```
if(!isobj(interacting_with))
    return NONE
if(scanning_mode == SCAN_EXPORTS)
    export_scan(interacting_with, user)
    return ITEM_INTERACT_SUCCESS
```

Because the interaction is reported as handled, the click never falls through to table placement or storage insertion.

## Fix

One commit, "Fix issue 89906: universal scanner can be placed on tables and in bags in combat mode": after the `isobj` check, `if(user.combat_mode) return NONE`, with a comment explaining it. With combat mode on, the click falls through to the default behavior. With combat mode off, scanning is unchanged. Only `interact_with_atom` was changed.

## Verification

After rebuilding, on the test server:

- Combat mode off: clicking the table still scanned it (intended).
- Combat mode on: clicking the table moved the scanner onto the table tile; clicking a backpack on the floor gave "You put the universal scanner into the backpack."

Not checked: the sales-tagger mode, which does not use this code path, and the other scanner modes with combat mode on beyond export scan.

## Notes

- The screentip still reads "Scan for export value" while in combat mode, since the hint was not changed; a maintainer may want it to reflect the placement behavior.
- Combat mode is what other items (soap, for example) use for the same purpose, which is why it was chosen over alternatives.
