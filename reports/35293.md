## Summary

The 2018 report says a blind drop of the auxiliary mining base to coordinates (255, 49) left the base stuck in space in transit. The suspected cause was that the base's footprint overlapped the edge of the map. On current master, `set_landing_zone()` rejects any landing zone whose footprint includes a turf that does not exist, so a drop near the edge is refused before a shuttle is ever sent. A base sent to the closest accepted spot landed normally. No code was changed.

## The bug

As reported in 2018: the base was dropped to (255, 49) with the blind drop option on the auxiliary base console. It never arrived, and stayed in transit in space. The reporter and a commenter suspected that the 9x9 base footprint overlapped the edge of the map. A commenter pointed out that the code picking the landing turf needed to account for the base's size and `TRANSITIONEDGE`.

## Reproduction

The bug could not be reproduced. What was done on the test server, as an observer using the Lua editor:

1. Found the base: an `/obj/docking_port/mobile/auxiliary_base`, 9x9 with `dwidth` 4 and `dheight` 4, shuttle id `colony_drop`, on the station level at (47, 155). The mining level in this round was a Lavaland level.
2. Called `set_landing_zone(turf, null, FALSE)` on the station's `/obj/machinery/computer/auxiliary_base` console for the turf at y = 49 on the mining level, with x = 255, 254, 253, 252, 251, 250, 249, 5 and 2. (The blind drop option calls this same proc with a randomly chosen turf. It was not used through the console interface, and the issue's exact (255, 49) was among the turfs tried.) The return values did not come back through the Lua editor because the proc sleeps in `CHECK_TICK`, so the outcome was read from the landing zones created.
3. A landing zone was created only for x = 251, 250 and 249. The requests for x = 255, 254, 253, 252, 5 and 2 created nothing, meaning they were rejected. Chat showed the "landing zone coordinates locked in" announcement three times, one for each accepted zone.
4. Called `SSshuttle.moveShuttle("colony_drop", <the landing zone at 251,49>, 1)`, and waited 40 seconds. The base was docked at (251, 49) on the mining level, in `idle` mode with a timer of 0, in the area "Auxiliary Base". It was not stuck in transit.

The move was started with `moveShuttle` directly, not by pressing the launch button on the console. The console's launch action calls the same `moveShuttle`.

## Cause

This is why the old report no longer applies. `set_landing_zone()` in `code/modules/mining/aux_base.dm:206` computes the base's footprint and checks it before creating a landing zone:

```dm
var/list/colony_turfs = base_dock.return_ordered_turfs(T.x,T.y,T.z,base_dock.dir)
for(var/i in 1 to colony_turfs.len)
	CHECK_TICK
	var/turf/place = colony_turfs[i]
	if(!place)
		return BAD_COORDS
```

(lines 223-228). `return_ordered_turfs()` (`code/modules/shuttle/shuttle.dm:119`) uses `locate()` for each footprint tile, so a tile outside the map comes back as null, and the proc returns `BAD_COORDS`. With a 9x9 footprint centred on the chosen turf (`dwidth` 4), a drop at x = 252 or higher would need tiles at x >= 256, so it is refused. The observed results fit that (251 accepted, 252 refused), together with a symmetric refusal at x = 5 and x = 2 on the western edge. The blind drop option's "random" action in `ui_act()` (line 160) picks a turf and then calls the same `set_landing_zone()` (line 172), so it gets the same check and replies "Landing zone unsuitable. Please recalculate." The designator item reports `BAD_COORDS` as "Location is too close to the edge of the station's scanning range." (line 300). This matches the "take the size of the base into account" request in the issue's second comment.

The checks that come after (area, turf type) apply on top of this.

I did not find which change introduced the check. The repository clone is shallow, so the history was not searched.

## Fix

None. No code was changed and no branch was made.

## Verification

No fix was made, so this is only the check of current behaviour in the Reproduction section. In short: edge footprints are refused, and a base moved to the nearest accepted turf landed and went idle.

Not checked:
- The blind drop was not started through the console UI; `set_landing_zone()` was called directly on chosen turfs.
- The exact 2018 situation was not recreated, since that code is no longer present. It is not known what the original code did, and the exact map in the 2018 round (a different Lavaland layout) was not used.
- Other mining levels (for example an ice moon level) were not tried.
- Only one map size was seen. Whether the map's maximum x was 255 was inferred from the results above (x = 252 refused with a 4-tile half-width), not read directly.

## Notes

- **Landing zones inside the transition edge band still work.** `TRANSITIONEDGE` is 8 (`code/__DEFINES/maps.dm:47`). A base at x = 251 has a footprint of x = 247 to 255, which lies inside that 8-tile border, and it landed and went idle without trouble. Nothing in the code checks `TRANSITIONEDGE` for this, and nothing failed. A maintainer may still want the check if that band is considered unsafe for any reason, but no failure was seen.
- **The admin-only designator skips all checks by design.** The "omni-locational landing field designator" (`/obj/item/assault_pod/mining/unrestricted`, `no_restrictions` set, line 306) bypasses the whole footprint check, so using it at the map edge can still produce a bad dock. Its description says "Use with caution" and the variable comment calls it a badmin tool.
- **A similar symptom has a different cause.** Replacing a shuttle that is in transit through the shuttle manipulator can also leave the replacement stuck in space. That is a separate mechanism: `SSshuttle.action_load` deleting the transit dock. The auxiliary base is moved by the console with `moveShuttle` and the console's `colony_drop` port id matches the mobile port's id, so the two do not overlap.
- The issue appears safe to close as already fixed.
