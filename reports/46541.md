# #46541: Photo albums don't save/update if the round ends with no escape shuttle

| | |
|---|---|
| Issues | [#46541](https://github.com/tgstation/tgstation/issues/46541): not reproduced |
| Status | Not reproduced on current master; likely closable |
| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The 2019 report said a photo album did not pick up a new photo when the round ended without the escape shuttle (Nar'Sie was summoned and the round ended abnormally). On current master this does not happen. Albums are written to `data/photo_albums.json` every time a photo enters or leaves the album, so the round-end path is not involved. No code change was made.

## The bug

As reported, a player put a photo in their album, the round ended by a cult victory instead of the shuttle, and next round the album did not contain the new photo. A 2021 comment on the issue says "Still a thing. Also none of my new photos are saving currently." The second sentence describes a different failure, not one tied to how the round ends.

## Reproduction

This was not reproduced. It was tested on master with admin tools as follows:

1. Started a round on the test server and, with the Lua editor, spawned a human, a camera and a `/obj/item/storage/photo_album` with `persistence_id` set to a test value (`test_album_2`).
2. Had the human take a photo with `attempt_picture`, then inserted the resulting photo into the album with `atom_storage:attempt_insert`.
3. `data/photo_albums.json` immediately contained `{"test_album_2": ["L_20261024_T_05.47.15_1"]}`, while the round was still running.
4. Used Delay-Round-End, then End-Round. The round ended without the escape shuttle being used.
5. After the round had ended, spawned a new camera and a new album (`test_album_3`), took another photo and inserted it. Within about two seconds the file also contained `"test_album_3": ["L_20261024_T_05.47.15_2"]`.
6. No runtimes appeared in the runtime log.

The photos and albums were created and filled by Lua calls to procs (taking the picture and inserting it into the album's storage), not by a player clicking through the UI. The "round ends by Nar'Sie" case itself was not run; End-Round was used as the non-shuttle ending.

## Cause

There is no defect to point at on master. The original report predates the current design, in which albums persist on every change:

- `code/modules/photography/photos/album.dm:73-84`: `/datum/storage/photo_album` overrides `handle_enter` and `handle_exit`, and both call `save_everything()`, which does `SSpersistence.photo_albums_database.set_key(album.persistence_id, album.get_picture_id_list())`.
- `code/datums/json_database.dm:75-77` and `97-117`: `set_key` stores the value in the cache and calls `queue_save()`, which schedules `save()` with `addtimer(..., 0)`. `save()` backs up the old file, writes the new JSON, validates it and removes the backup.

Nothing in this path waits for round end, so the way the round ends does not matter. How the 2019 code worked was not checked, because the repository history available was shallow. The likely explanation is that the original code saved albums only from the round-end collection step, but that is unconfirmed.

What a photo needs in order to be saved is a picture id. The id is assigned only when the picture is logged to disk (`code/modules/photography/_pictures.dm:172-190`, `log_to_file`), and `log_to_file` returns early unless the `LOG_PICTURES` config flag is on. The camera only calls it if `PICTURE_LOGGING_CAMERA` is also on (`code/modules/photography/camera/camera.dm:384-385`). Both flags are enabled in the shipped config, and they were on on the test server. A server with either flag off would produce photos with no id, and those would not be restored after a restart. This might explain the 2021 comment that "none of my new photos are saving". It was not tested.

## Fix

None. No commit was made.

## Verification

Checked in game, as described under Reproduction: an album was written on insert mid-round, and a second album was written after End-Round with no shuttle, with no runtimes.

Not checked:

- The actual Nar'Sie-summoned round end, or any other cult or antagonist ending.
- Loading the saved albums in the following round. Only the contents of `data/photo_albums.json` were inspected.
- Behaviour with `LOG_PICTURES` or `PICTURE_LOGGING_CAMERA` disabled.
- A server crash or restart in the middle of a round.

## Notes

- `queue_save()` in `code/datums/json_database.dm:97-103` checks `save_queued`, but nothing ever sets it to `TRUE`. `save()` only sets it to `FALSE` (line 108). The result is that every `set_key` adds its own timer and the file is rewritten several times when several changes happen in the same tick. No data is lost. This is a harmless inefficiency, not related to the issue.
- Recommendation: close #46541 as fixed by the move to per-change saving. If the 2021 "no photos save" report is still seen, check the picture-logging config flags on that server first.
