## Summary

None of the three issues led to a code change. On master, a healed severe burn wound clears its limb's disabled state (#79309). The embedded-object jostle damage does skip "physiology armor" (inner armor), but no code in tgstation gives a mob melee inner armor, so there is no effect here (#94243). Sutures and welders do treat other people's wounds, but hot tools like a lit welder need the user to hold the patient in an aggressive grab, which is deliberate; nothing tells the player this (#95334).

## #79309: burn wound disabling never clears

### The bug

The issue text is only its title: if a burn wound heals while it is disabling a limb, the disablement never goes away. It gives no steps.

### Reproduction

Not reproduced. Using the Lua editor on a spawned human:

1. Spawned a human and added a `/datum/wound/burn/flesh/severe` to the right arm, then called `set_disabling(1)` on it. The arm's `bodypart_disabled` became 1. (A critical burn wound was not used: it dismembers the arm when applied.)
2. Set the wound's `flesh_damage` and `infection` to 0 and let the wound tick.
3. Observed: the human's `all_wounds` and the arm's `wounds` were null, and `bodypart_disabled` was 0. The disablement was cleared.

### Cause

No defect on master. The pieces that make it work:

- `remove_wound` calls `set_disabling(FALSE)` first (`code/datums/wounds/_wounds.dm:370`).
- The traits `TRAIT_PARALYSIS` and `TRAIT_DISABLED_BY_WOUND` are applied with a per-wound source (`REF(src)`). They are removed in `set_disabling` (`_wounds.dm:419-428`) and in `set_limb` (`_wounds.dm:306`).
- `code/datums/wounds/burns.dm:86-89` deletes the wound when `flesh_damage` is 0 or less and infection is low, and `Destroy` goes through `remove_wound`.

The bug was probably fixed by a later rewrite to per-wound trait sources. This was not checked against history.

### Fix

None.

### Verification

Only the Lua scenario above. Not checked: other wound types, wounds replaced by a worse wound while disabling, or the limb being re-disabled by another wound.

## #94243: embedded objects bypass physiology armor

### The bug

The reporter, who had not reproduced it, suspects that damage from an embedded object jostling skips armor, including "physiology armor" (on tgstation, the mob's `inner_armor`). Their motivation is a downstream bug (DarkPack13/SecondCity#397) in a modular status effect that works off physiology armor.

### Reproduction

Not reproduced in game; only the code was read.

### Cause

In `owner_moved()` in `code/datums/embedding.dm:391-397`, jostle damage is applied with `owner.apply_damage(damage = (1 - pain_stam_pct) * damage, damagetype = BRUTE, def_zone = owner_limb, wound_bonus = CANT_WOUND, ...)`, and `blocked` is left at 0, so no armor check is made. `damaging_removal_effect` (around `embedding.dm:363`) does the same.

"Physiology armor" in tgstation is `inner_armor`: `getarmor` includes it (`code/modules/mob/living/living_defense.dm:34`), with `add_inner_armor` and `remove_inner_armor` at `:42` and `:48`. The only user in tgstation is the roach organs, which give bomb, radiation and bio armor but no melee. So the jostle damage cannot be reduced by inner armor on tgstation today.

### Fix

None. A possible small fix was considered but not made: add `/mob/living/proc/get_inner_armor_value(type)` and pass its melee value as `blocked` in `owner_moved` and `damaging_removal_effect`. A test idea for it was to add a melee 100 inner armor datum with `add_inner_armor`, embed a shard, and call `owner_moved` with `jostle_chance` 100.

### Verification

None in game.

### Notes

The lean verdict is that this is intended, or downstream-only. Worn armor not applying to jostle damage is plausibly intended. A downstream codebase that adds melee inner armor would see the gap.

## #95334: ghetto tools can't treat others' wounds

### The bug

The reporter tried to treat a ruptured cavity on a doll (a standing human, not on a bed) with a suture and a mini welder. They say the suture "just heals the limb, not the wound", the welder did nothing, and normal cautery and self-treatment work.

### Reproduction

Reproduced as a usability problem, behaving as designed. On master, with admin tools:

1. Used Give Direct Control to play one human ("Doctor") next to another ("Patient"), and gave Patient a `/datum/wound/pierce/bleed/critical` ("Ruptured Cavity") on the chest. Doctor held a lit emergency welding tool in one hand and a suture in the other.
2. Applied the suture to Patient with no grab. It worked ("You apply the suture on Patient's chest", five applications until fully treated). Each application reduces `blood_flow` by 0.5 through `heal_carbon` (`code/game/objects/items/stacks/medical.dm:346-349`), and the wound is removed when `blood_flow` reaches 0 or less. So sutures reduce bleeding and heal brute damage rather than closing the wound in one step, which probably matches "just heals the limb".
3. Used the lit welder on Patient with no grab. Result: "You attack Patient in the chest with the emergency welding tool!" A burn wound was caused and the wound was not treated.
4. Upgraded to an aggressive grab (ctrl-click twice) and used the lit welder again. Result: "You begin cauterizing Patient's chest with the emergency welding tool..." The progress bar started (20% when the tester stopped). The do_after was not watched to completion and the drop in `blood_flow` was not confirmed.

### Cause

`item_can_treat()` (`code/datums/wounds/_wounds.dm:538-550`) lets a hot, non-cautery tool treat a wound only if the user is the victim or has the victim in an aggressive grab (`user.pulling == victim && user.grab_state >= GRAB_AGGRESSIVE`), checked through `check_grab_treatments` (`code/datums/wounds/pierce.dm:138-141`, `slash.dm:175-180`). The code comment says this is so a user does not try treating someone they are "eswording". Without the grab, the click falls through to a normal attack.

### Fix

None. A small usability change was sketched but not made: in the wound treatment code, when a hot tool is rejected only for lack of a grab and the user is not in combat mode, show a message ("grab them aggressively to treat with this") and block the interaction. The risk is blocking real attacks with hot weapons, which the existing comment is meant to avoid.

### Verification

The grabless and grabbed cases above were tested in game. No change was made, so nothing else was verified.

### Notes

The label "Tested/Reproduced" on the issue fits the grabless failure. The behavior is deliberate; the missing feedback is the actual gap.
