## Summary

Both issues say the bluespace locator ignores tracking implants and only shows teleporter beacons, whichever tab is selected. On master `87b93338` that no longer happens: upstream PR #93338, "Bluespace Locator Update" (merged 2025-10-07), removed the leftover beacon code and the beacon/implant tabs, and the locator now lists tracking implants and TRAC (.38) implants and leaves beacon implants out. No fix was written. Neither issue appears to have been closed when the PR merged, so both can be closed as fixed by #93338.

## The bug

As reported in #81456 (and confirmed in a comment by the implants rework author), the locator from the tracking implant box tracked beacon implants instead of tracking implants, and its UI showed only beacons regardless of the tab chosen. #86854 reports the same from the other side: tracker implants (including those from TRAC bullets) did not show up on the locator, and the interface did not let the user switch from teleport beacons to trackers. The cause was old code that dated from when tracking implants acted as teleport beacons.

## Reproduction

The reported behaviour did not reproduce. What was done on master to check the current behaviour:

1. On a test server, with the round started and the tester observing, use the Lua editor to spawn a human, "Holder A", holding a `/obj/item/locator`.
2. Spawn three more humans and implant each by calling the implant's `implant()` proc on them (the proc the implanter calls): "Tracked B" 5 tiles east with `/obj/item/implant/tracking`, "Trac38 C" 4 tiles south with `/obj/item/implant/tracking/c38` (the TRAC implant fired by .38 tracking bullets), and "Beacon D" with `/obj/item/implant/beacon`.
3. Call `ui_data()` on the locator. Result: `trackingrange` 35, and `trackimplants` contained Tracked B (east, 5) and Trac38 C (south, 4). Beacon D was not listed.
4. Give the player control of Holder A and press Z (use the item in hand). The `BluespaceLocator` tgui window opened, and its data was:

   `{"trackingrange":35,"trackimplants":[{"name":"Tracked B","direction":"east","distance":5},{"name":"Trac38 C","direction":"south","distance":4}]}`

5. The runtime log for the round contained no runtime errors.

Not tested: using a real implanter by hand, and firing a real TRAC bullet. Both go through the same `implant()` call, but that was established by reading the code, not in game.

## Cause

For the reported behaviour, the cause was in code that has since been removed. What the current code does:

- `/obj/item/locator/ui_data()` (`code/game/objects/items/teleportation.dm:35-66`) loops over `GLOB.tracked_implants` and keeps only `/obj/item/implant/tracking` (which includes the `/tracking/c38` subtype). Beacon implants are therefore excluded. It skips implants that are not inside a living mob, implants in mobs that have been dead longer than `lifespan_postmortem`, implants on another z level, and implants further than `tracking_range` (35, Chebyshev distance). The result is sent as `trackimplants` (name, direction, distance).
- An implant is added to `GLOB.tracked_implants` in `implant()` (`code/game/objects/items/implants/implant.dm:116`). The implanter (`code/game/objects/items/implants/implanter.dm:38`) and the TRAC bullet (`code/modules/projectiles/projectile/bullets/revolver.dm:108-109`) both call `implant()`.
- `BluespaceLocator.tsx` has no tgui actions any more; choosing a target is client-side state, so there is no server-side tab handling left that could fail.

## Fix

No commit was made. According to the PR description, #93338 changed `code/game/objects/items/teleportation.dm` and `tgui/packages/tgui/interfaces/BluespaceLocator.tsx`, removed the legacy teleport-beacon tracking code, and replaced the UI with a single list of tracked targets with a search box and a direction arrow. Its text says it makes the locator track tracking implants instead of beacon implants and cites #81456.

## Verification

Done on master with no changes: the checks listed under Reproduction (server-side `ui_data()` output for both tracker types and a beacon implant, and the actual tgui window data after opening the locator in the hand of a possessed human). Not checked: a hand-operated implanter, a fired TRAC bullet, a locator on a pad as mentioned in #86854's title, other z levels, dead targets, and the rendered appearance of the window.

## Notes

- Side finding, not part of either issue and not tested in game: the locator UI selects and keys targets by name (`BluespaceLocator.tsx`, `key={implant.name}` and `selectedImplantName`). Two tracked mobs with the same visible name, for example two masked "Unknown" people, would collide: React would warn about duplicate keys and the selection could jump between them.
- #86854 mentions "locator pads"; the checks covered the handheld locator only.
- Both issues can be closed as fixed by PR #93338.
