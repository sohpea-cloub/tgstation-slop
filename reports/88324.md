# #88324: Command report is lost when a station communications console has no power

| | |
|---|---|
| Issues | [#88324](https://github.com/tgstation/tgstation/issues/88324): verified, fixed |
| Status | fixed (the lost-report cause reproduced and fixed; whether the original behaviour was intended is a design question, see Notes) |
| Fix branch | [fix/88324](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/88324) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

`send_message` skipped any station communications console that was broken or unpowered, for both storing the message and printing the paper. A command report sent during a blackout (for example with "announce contents" off) therefore never reached those consoles' message lists, and was not delivered later when power came back. The fix always stores the report on station-level consoles and only prints the paper when the console is working. The GPS runtime quoted in the issue is unrelated and was fixed upstream by PR #88329.

## The bug

The reporter sent a Central Command report from the admin Command Report verb with "announce contents" off, so it was meant to appear only as paper on the communications consoles and in their message lists. The captain found nothing printed and nothing in the console's records. The reporter noted there was a blackout at the time, and that a similar report sent later in the round worked.

The runtime pasted in the issue (`imprint_gps` called without a `gps_tag` from the console's `toggleAuthentication` action) was thought by the reporter to be the cause. A commenter said it was unrelated, and a later comment says PR #88329 fixed it. This investigation agrees: that runtime comes from a different code path and does not affect command reports.

## Reproduction

The report was reproduced by calling the same proc the Command Report verb calls, not by using the verb's UI.

1. Start a round on master and observe. The station has two station-level communications consoles, in the Bridge and in the Captain's Quarters.
2. Using the Lua editor, set the Bridge console's `machine_stat` to `NOPOWER` (2), simulating a blackout for that console.
3. Call `print_command_report('Test blackout report', 'Classified Test', false)`. This is the call `code/modules/admin/verbs/commandreport.dm:163` makes when announce contents is off.
4. Read each console's `messages` list.

Observed on master:
- Bridge (`machine_stat` 2): 0 messages.
- Captain's Quarters (`machine_stat` 0): 1 message.

So the unpowered console never received the report and nothing queues it for later.

## Cause

`/datum/communciations_controller/proc/send_message` (`code/datums/communications.dm:58`) wraps both the storing and the printing in one condition:

```dm
for(var/obj/machinery/computer/communications/C in GLOB.shuttle_caller_list)
	if(!(C.machine_stat & (BROKEN|NOPOWER)) && is_station_level(C.z))
		... C.add_message(...)
		if(print)
			... new /obj/item/paper(C.loc) ...
```

(`code/datums/communications.dm:59-60`). A console that is broken or has no power is skipped entirely, so the message is neither added to its list nor printed. Nothing retries when power returns, which matches the report: the message was missing from the records, and a later report worked once power was back.

## Fix

One commit, "Fix issue 88324: store command reports on unpowered communications consoles", in `send_message`:

- Station-level consoles always call `add_message`, whatever their `machine_stat`.
- The paper is printed only when `print` is set and the console is not `BROKEN` or `NOPOWER`.

Non-station-level consoles are still skipped. The alternative of queueing the report and delivering it when power returns was not tried; storing it immediately is simpler and the console shows it as soon as it works.

## Verification

After rebuilding and starting a fresh round on the test server, the same steps were repeated:

- Bridge (`machine_stat` 2): 1 message. Captain's Quarters (`machine_stat` 0): 1 message.
- A paper named `paper - 'Classified Test'`, colour `#deebff`, was present at the powered console in the Captain's Quarters.
- The game log showed no runtimes ("Runtime in" count 0).

Not checked: the stored message was not viewed in the console's tgui, only in its `messages` list. A check that the unpowered console printed no paper was not done explicitly (an SDQL2 search for the paper failed with a parsing error and was not pursued). The real Command Report verb and the `BROKEN` state were not exercised, only `NOPOWER` through `print_command_report`.

## Notes

- Design call: a console without power not receiving a message could be considered intended. This write-up treats losing the report permanently as the bug, since the message list is the record the captain checks later. A maintainer may prefer a different policy.
- The same `send_message` is used by other callers of `print_command_report` (the roundstart report in `code/datums/communications.dm`, the intercept report in `code/controllers/subsystem/shuttle.dm`, and the personnel update in `code/controllers/subsystem/ticker.dm`), so they get the same behaviour.
- Related upstream: PR #88329 ("Fixes a board GPS imprintion runtime") fixed only the unrelated runtime in the issue and does not change this behaviour.
