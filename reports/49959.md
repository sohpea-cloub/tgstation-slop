## Summary

The 2020 report said that after being put into crit and recovering, every action button stayed dark red as if unavailable, until it was clicked. On master the buttons turned dark red in crit and returned to normal on recovery in every case tried. Action buttons now refresh themselves from stat and trait signals, (the 2020 code was not inspected, so it is assumed the report predates this), so no fix was written.

## The bug

As reported: a player with internals, a welding gas mask and a PDA (all with action buttons) was put into crit. After regaining consciousness the buttons were still dark red, the colour used for unavailable actions, even though they could be used. Clicking "Toggle welding mask" worked and reset that button to its normal look. A commenter said the problem had existed for a long time and would probably be hard to fix.

## Reproduction

Not reproduced. What was tried on the test server, using the Lua editor and admin tools:

1. Spawned a human, gave it a welding helmet (its action "Toggle welding helmet" has check flags for blocked hands, consciousness and incapacitation) and took control of it.
2. Read the button's colour on the player's screen and the action's `IsAvailable()` after each step.
3. Put the human into soft crit with oxygen damage (`adjust_oxy_loss(150)` then `update_stat`), then healed it. The button colour went plain, then `#800000` with alpha 128 (dark red), then plain with alpha 255.
4. Put the human into hard crit with brute damage (`adjust_brute_loss(170)`), then healed it: the same result in both directions.
5. Applied `Unconscious(30)` and `Unconscious(100)` and let them time out: the same result.
6. Called `death()` and then `revive(65535)`: the same result.
7. Granted items while in crit (a PDA with "Toggle Flashlight", and a welding mask) and then recovered: the buttons returned to their plain colour.

One reading right after `Unconscious(100)` showed stat 0 with the action unavailable. It was taken while the server was still starting up and lagging, in the middle of the transition, and the following reads were consistent and the button recovered.

## Cause (why it no longer happens)

When an action is granted, `/datum/action/proc/Grant` (`code/datums/actions/action.dm:105-120`) registers `update_status_on_signal` on signals chosen by the action's `check_flags`: `COMSIG_MOB_STATCHANGE` for `AB_CHECK_CONSCIOUS`, and the add/remove signals of the incapacitated, immobilized and hands-blocked traits, plus lying, phasing and open-turf checks. `update_status_on_signal` (line 428) calls `build_all_button_icons(UPDATE_BUTTON_STATUS)`, and `update_button_status` (line 340) recolours the button from `IsAvailable()`:

```dm
if(IsAvailable())
	current_button.color = rgb(255,255,255,255)
else
	current_button.color = transparent_when_unavailable ? rgb(128,0,0,128) : rgb(128,0,0)
```

`/mob/proc/set_stat` (`code/modules/mob/mob.dm:1566`) sends the stat-change signal. With this in place the button is recoloured on every relevant change. The old behaviour (buttons updated only when clicked) is consistent with the report, but the 2020 code was not inspected, so this is an explanation from reading current code.

## Fix

None; nothing to fix.

## Verification

Nothing was changed. The checks above are the verification that the current behaviour is correct.

Not tested: cases where the mob changes state while the client is disconnected or the HUD is recreated (reconnect), and other action types beyond the welding helmet, welding mask and PDA flashlight.

## Notes

If the bug is still seen on a live server, client reconnects and HUD recreation are the paths this test did not cover.
