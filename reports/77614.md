# #77614: Ice gets snowed in backwards

| | |
|---|---|
| Issues | [#77614](https://github.com/tgstation/tgstation/issues/77614): verified, fixed |
| Status | Fixed on a branch, checked in game by rendering the result |
| Fix branch | [fix/77614](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/77614) |

## Summary

Smoothed ice turfs (`/turf/open/misc/ice/smooth`) showed a snow rim between neighbouring ice tiles and none along the outer edge of an ice patch. The five sprite blocks in `icons/turf/floors/ice_turf.png` were in the reverse of the order the `bitmask/diagonal_32x32` icon-cutter template expects, so interior tiles drew the "snow all round" island sprite. The fix reorders the blocks in the PNG and regenerates the `.dmi`. No code changed.

## The bug

On the reporter's screenshot, every ice tile is outlined in snow, except on the sides that actually touch snow. The correct picture is solid ice inside a patch with a snow rim only on the outer boundary.

The smoothing logic itself was fine. Only the sprite chosen for each smoothing state was wrong.

## Reproduction

1. On the test server, on MetaStation, join as an observer ghost. Use the Toggle-Darkness verb, or the renders stay too dark to see.
2. Using the Lua editor, call `ChangeTurf` to build a test patch on z2, x30..49, y40..50: a field of `/turf/open/misc/asteroid/snow/icemoon`. Place `/turf/open/misc/ice/smooth` in these shapes:
   - a 3x3 block at x39..41, y42..44
   - a lone tile at 37,45
   - a strip and an L at x32..35, y42 and x32, y43
3. Check the smoothing states. They were correct: the centre of the 3x3 block was `ice_turf-255` and its edge tiles had states such as 38, 110 and 74.
4. Render the area. Grey snow lines ran between the ice tiles and none appeared along the outer boundary, which is the reverse of the issue's screenshot.

`/turf/open/misc/ice/icemoon` (the non-smoothing type, always `ice_turf-0`) never smooths, so it renders as a single block and does not show the bug. Only `ice/smooth` does.

## Cause

`/turf/open/misc/ice/smooth` uses `SMOOTH_BITMASK | SMOOTH_BORDER` with `base_icon_state = "ice_turf"` (`code/game/turfs/open/ice.dm:75-79`). Its `ice_turf.dmi` is generated at build time from `icons/turf/floors/ice_turf.png`, using the template named in `ice_turf.png.toml` (`bitmask/diagonal_32x32.toml`).

The template expects the PNG to hold five blocks in this order: convex (the island, snow on every side), vertical, horizontal, concave (full tile), flat (full tile). `snow_turf.png` and `ash.png` follow that order, with the island as block 0. `ice_turf.png` had the order reversed: block 0 was full ice and block 4 was the island. The `flat` sprite, used by interior tiles with all neighbours the same, therefore came out as the island, and the convex corners and edges came out plain.

## Fix

One commit, "Fix issue 77614: ice smoothing sprites were in reversed order", changes `icons/turf/floors/ice_turf.png` and the generated `icons/turf/floors/ice_turf.dmi`. The new PNG is the old blocks in the order [4, 2, 3, 1, 0], matching the template and `snow_turf.png`. The `.dmi` in the repository is regenerated from the PNG by the build.

Which of the two middle blocks is vertical and which is horizontal was decided by looking at the art. In the old order, block 2 had snow on the left and right, which was taken as vertical.

## Verification

After rebuilding and restarting the test server, the same patch was recreated and rendered at 4x over x32..40, y41..47:

- The 3x3 block and the strip were solid ice inside.
- A ragged snow rim appeared only on the outer boundary: top and bottom of the strip, its ends, and the corner of the L.
- The lone tile was rimmed on all sides.
- Straight edges were on the correct sides, so the vertical and horizontal blocks did not need swapping.

Not checked: this was a visual check of a few shapes on one map. Other ice maps or the real IceBox layout were not rendered, and the vertical/horizontal assignment was judged by eye.

## Notes

- The change is art-only, so no runtime checks applied.
- The `.dmi` diff in the commit is a binary regeneration. Maintainers may prefer to commit only the PNG and let CI or the build produce the `.dmi`, depending on how the repository handles generated icons.
