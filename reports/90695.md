# #90695: Equipping outerwear that squishes digitigrade legs does not squish the shoes

| | |
|---|---|
| Issues | [#90695](https://github.com/tgstation/tgstation/issues/90695): not reproduced |
| Status | Not reproduced on master; probably already fixed upstream |
| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The issue reports that when a digitigrade character wearing shoes puts on outerwear that squishes the legs, the legs change to the plain sprite but the shoes keep their digitigrade sprite. On master `87b93338` this did not happen: after the coat was equipped, the legs switched to the squished state and the shoe overlay switched to the plain (non-digitigrade) icon. No fix was written. The reporter's behaviour was probably fixed by the upstream change "State based digi and snout bodyshape" (PR 96030, merged 2026-05-09), which is already in the tested tree. That attribution rests on the code reading and the test result, not on a before/after comparison.

## The bug

As reported (April 2025): a player with digitigrade legs wears shoes, then puts on a coat that squishes the legs. The legs are drawn squished, but the shoes stay in their digitigrade shape and no longer line up with the legs.

## Reproduction

Not reproduced. The attempt, using admin tools on the test server:

1. Using the Lua editor, spawned a human, made them a lizard, set their `legs` feature to `Digitigrade Legs`, and replaced the body with the species' `replace_body`.
2. Equipped shoes into the feet slot, then equipped a squishing coat into the outer-clothing slot with `equip_to_slot_or_del`.
   - The coat has to cover the legs and have `supports_variations_flags` without any digitigrade bits. `/obj/item/clothing/suit/jacket/quartermaster` qualifies. Other suits such as `jacket/fancy`, the bio suit and waders do carry the digitigrade flags, so they do not squish at all.
3. Repeated with `sneakers/black`, `sneakers/red`, `jackboots`, `workboots`, `combat` boots and `winterboots`.

Observed, for every shoe type tried:

- The leg `limb_id` changed to the plain `lizard` id.
- The human's `bodyshape` changed from 13 to 9, so the digitigrade bit was cleared.
- The shoe overlay (`overlays_standing` at the shoes layer) was the plain icon. For sneakers that was the generated plain greyscale file rather than the generated digitigrade one. For jackboots it was `icons/mob/clothing/feet.dmi`.
- Equipping through `equip_to_appropriate_slot` gave the same result.

A caveat from the attempt: reading `bodyshape` in the same Lua chunk as the equip can still return the old value (13), so it has to be read in a later call.

All of this was done by calling equip procs from Lua. A player putting the coat on by hand was not tried.

## Cause

No defect found on master. The relevant flow, in `code/datums/components/digitigrade_limb.dm`:

- `equipped_item()` (line 60) checks `item_squishes_limb()` (line 95). For outer clothing, that returns true when the item covers the legs and lacks `DIGITIGRADE_VARIATIONS`. If so it adds the item's ref to `squashing_us` and calls `update_limb_id()`.
- `update_limb_id()` (line 119) sets `limb_id` to the squashed id and calls `remove_bodyshape(BODYSHAPE_DIGITIGRADE)`. That in turn calls `synchronize_bodyshapes()` on the owner (`code/modules/surgery/bodyparts/helpers.dm:277`).
- When the id changed, it then calls `update_slot_icon()` on every equipped item that has `DIGITIGRADE_VARIATIONS` (lines 137-140), so the shoes are redrawn with the plain icon.

Judging by the date and title, PR 96030 is the change that made digitigrade state follow the bodyshape and refresh equipped items this way. I did not run the pre-PR code, so I cannot confirm that it was the cause of the original report.
