# #52084: Reference tracker output looks like false positives, and a same-tick search skips references

| | |
|---|---|
| Issues | [#52084](https://github.com/tgstation/tgstation/issues/52084): fixed (the reported references are real; output made explicit, plus a separate search bug fixed) |
| Status | Fixed (debug tooling only). The reporter's "false positives" were not reproduced as false. |
| Fix branch | [fix/52084](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/52084) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The issue reports that the reference tracker (`find_references()`) lists datums that "should not be" holding a reference to the searched mob, such as `/datum/component/edible`, which "has nothing to do with this mob". On current master the references the tracker reported were all genuine: a component registers signals on the datum it is attached to, so it really does hold a reference to its parent, but the log line never said which datum the component belonged to. The fix makes the output name the component's parent. It also replaces `world.time` as the per-search "visited" marker with a unique counter, because a second search started in the same tick would silently skip everything the first search had visited.

## The bug

The reference tracker is a debugging tool that is compiled in with `REFERENCE_TRACKING`. It walks every global, datum and client and logs each place a reference to the searched datum is held. The reporter searched for references to their own human mob and got entries naming `/datum/component/edible` and `/datum/feedback_variable` as holders, and concluded the tracker was returning nonsense.

On master, the visible problem is that the log gives no context for a component. A line such as `/datum/component/edible [0x...] -> _signal_procs` gives no sign that the component is attached to the searched mob, and no sign that the mob matched as an associative key of `_signal_procs` rather than as a value. That reads exactly like a false positive.

There is also a separate defect, found by reading the code: the "already visited" marker for a search is `world.time`. Searches do not sleep, so two searches started in the same tick would collide (details under Cause). That defect was not seen in game.

## Reproduction

The tracker has to be compiled in, so this needs a build with `-DREFERENCE_TRACKING_STANDARD` (later also `-DFAST_REFERENCE_TRACKING` to shorten searches). There is no View Variables "Find References" entry any more, so the search was started by calling the proc directly.

1. Build master with `REFERENCE_TRACKING_STANDARD` and start a round.
2. Using SDQL2, run `CALL find_references() ON /mob/living/carbon/human`, and answer Yes to the "Find References" confirmation. (A query with a `WHERE name == "..."` clause on the playing character failed to parse in the first attempts, so the query targeted the first human instead.) The same proc was also called from the Lua editor.
3. Read the result in the round's `harddels.log`.

Observed on the searched monkey (the first `/mob/living/carbon/human`): 64 "Found" lines. Every one was a real reference, for example:

- global lists and `_listen_lookup`;
- `/datum/component/edible -> _signal_procs` (the monkey carried its own edible component, which registers signals on its parent, so the monkey is a genuine key in that list);
- `mood.mob_parent`, `dna.holder`, `reagents.my_atom`, `mood_event/fed.owner`;
- `turf.contents`;
- a banana's `loc` (the monkey was holding a banana).

The logged chain for the component read only `/datum/component/edible [0x..] -> _signal_procs`, with no parent shown. `/datum/feedback_variable` and the "owner var" lines from the issue's screenshot did not appear on current master, so those were not reproduced.

The same-tick bug was not reproduced in game. Searches triggered through the garbage collector's hard-lookup each ran in its own garbage subsystem fire (the second started 22 seconds after the first ended). An attempt to start two searches from one Lua timer never started the second one; the Lua task apparently died, and no runtime was logged. So this defect is established from the code only. In practice it needs two direct calls in one tick.

## Cause

Two separate things in `code/modules/admin/view_variables/reference_tracking.dm`.

1. Missing context for components. `/datum/proc/ref_search_details()` (`:274`) just returns `text_ref(src)`; only `/datum/callback` overrides it (`:277`). A component therefore appeared in the chain as a bare `/datum/component/edible [0x...]`. A component is attached to a `parent` and registers its signals on it (`RegisterSignal(parent, ...)` in `code/datums/components/food/edible.dm:81` onward), so the parent legitimately appears in the component's `parent` var and as a key of `_signal_procs`. Nothing in the output said so.

2. A non-unique search id. `_search_references()` starts with `var/starting_time = world.time` (`:79`), and every datum visited is stamped with it: `if(datum_container.last_find_references == search_time) return` / `datum_container.last_find_references = search_time` (`:153-156`). Searches run without sleeping (the per-level `CHECK_TICK` is skipped with `FIND_REF_NO_CHECK_TICK`), so a second search that starts in the same tick sees every datum the first search touched as already searched and silently misses references through them.

## Fix

One commit, "Fix issue 52084: reference tracker output explains components and uses unique search ids", changing only `reference_tracking.dm`:

- Adds `GLOBAL_VAR_INIT(reftracker_search_id, 0)` and sets `starting_time = ++GLOB.reftracker_search_id`, so each search gets its own id regardless of world time.
- Adds a `/datum/component/ref_search_details()` override that returns `"[text_ref(src)] (component of [parent.type] [text_ref(parent)])"` (or `null` when there is no parent). Chain entries for a component now say which datum it belongs to, which makes it clear that the component's `parent` var or `_signal_procs` registration is the real reference.

The existing `last_find_references` variable and its comparison stay as they were; only the value stamped into it changed.

## Verification

After rebuilding with the tracker enabled, a margherita pizza was spawned with the Lua editor and `CALL find_references() ON /obj/item/food/pizza/margherita` was run through SDQL2. The search completed with 22 "Found" lines and no runtimes. Component entries now read, for example:

- `Found /obj/item/food/pizza/margherita [0x20295e8] in list Datums -> /datum/component/edible [0x21045411] (component of /obj/item/food/pizza/margherita [0x20295e8]) -> _signal_procs (list).`
- an entry for `connect_loc_behalf` reading `(component of /datum/component/edible [..]) tracked var`.

Not checked: the same-tick fix itself, since the bug could not be triggered in game; a search on a human with the new output (the check was on a pizza, which also carries an edible component); and the unit-test build or `REFERENCE_TRACKING_DEBUG`.

## Notes

- This is debug-only code compiled out of normal builds, so there is no gameplay risk, but the change should be read by someone who uses the tracker.
- Issue #52084's `/datum/feedback_variable` and "owner var" holders could not be reproduced on master. The reporter first saw the problem in a port of the tracker to another codebase and then on tgstation at the time (2020), so those entries may have since been fixed or may have come from that older code; this is not established.
- Not changed: matches as an associative-list key are still logged identically to value matches (`in list X -> _signal_procs`); an "(as key)" marker would help. The clients search prints a benign "Curiosity: ... lead to an error" for `client.screen`, `images` and `verbs`.
- Search time: a search of all atoms took roughly 6 minutes without `FAST_REFERENCE_TRACKING` and roughly 1 minute with it.
