## Summary
The issue reported a Blood Brother whose objective was to stop a target from escaping, after that target had been borged. The objective was a "maroon" objective ("Prevent X from escaping alive"), not an assassination, so it was the right kind of objective. According to the comments, the target was later unborged, respawned as a podperson and boarded the shuttle, so the objective legitimately failed. On master the maroon objective follows the mind into the pod body, and a borged target counts as not alive. No code defect was found and no fix was written.

## The bug
The screenshot showed a Blood Brother with an objective to prevent a target from escaping, in a round where the target had been turned into a cyborg. The reporter first read it as a bad objective for a target that should already count as dead. A commenter then explained what had happened:

- A Brother killed the target and had them borged, apparently so they could be ordered to stay behind.
- Someone else unborged them.
- The preserved body was used for a pod-person respawn.
- That pod person ended up on the shuttle with the Brother, and the objective "never got updated after the pod-respawn".

The reporter agreed the title was wrong. The remaining question is whether a pod-person respawn leaves the objective pointing at a stale body.

## Reproduction
The pod-respawn path was tested. A full Blood Brother round was not played, and the borging and unborging steps were not tested as player actions.

1. In the Lua editor, spawn two humans with minds: A (the target, controlled by a player) and B (the brother).
2. Create a `/datum/objective/maroon` with owner B and target A's mind. Before anything else it gave `check_completion()` = 1, `considered_alive(target)` = 1 and the text "Prevent Davion Hirleman, the Unassigned Crewmember, from escaping alive."
3. Kill A (stat 3, DEAD).
4. Put a replicapod seed into a hydroponics tray with its `mind` set to A's mind and its `ckey` set to the player, then call `harvest(B)` on the seed. This is the same code that makes a podperson in normal play.
5. Check the objective. Observed results:
   - `objective.target.current` was a new `/mob/living/carbon/human` (stat 0), not the old body.
   - A's old mind variable on the old body was gone, and the old body stayed at stat 3.
   - `considered_alive(target)` = 1 and `check_completion()` = 1, because the podperson was not on CentCom.

A runtime appeared at `code/modules/hydroponics/grown/replicapod.dm:201` ("bad index") after the mind transfer. It was caused by the test, which passed empty Lua lists for the seed's `features`, and not by the game.

## Cause
There is no defect here. The following is why the objective behaves as it does:

- `code/modules/hydroponics/grown/replicapod.dm:193` calls `mind.transfer_to(podman)`. This moves the existing mind datum to the new body, and objectives store `target` as that mind, so they keep working. The closed PR #64169 targeted an older version of the replicapod code and no longer applies.
- `code/game/gamemodes/objective.dm:294` is `/datum/objective/maroon/check_completion()`. It returns TRUE when the target is missing, when `considered_alive(target)` is false, or when the target's current mob is on neither CentCom nor the Syndicate base. Otherwise it returns FALSE.
- `considered_alive()` (`code/__HELPERS/game.dm:39`) returns FALSE for a dead mob or one with `TRAIT_NEVER_CONSIDERED_ALIVE`. Silicons carry that trait (`code/modules/mob/living/silicon/silicon.dm:71`), so a borged target counts as not alive and the maroon objective is satisfied until they are human again.

With a pod person who then escaped on the shuttle, the objective returns FALSE (failed), which is correct. The only cosmetic point is that `explanation_text` is rebuilt only by `update_explanation_text()`, which reads `target.name` (the mind's name). It is not a bug.

## Fix
None. No commit was made.

## Verification
On master, the maroon objective was shown to follow the mind into a pod body (see Reproduction). The reasoning that a borged target counts as not alive comes from reading the code at the lines above. It was not tested by borging a target in game. Not tested: the shuttle-escape outcome for a podperson (inferred from `check_completion()`, where an off-CentCom podperson returns TRUE and an on-CentCom one returns FALSE), and the unborg step.
