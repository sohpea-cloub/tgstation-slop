## Summary

The 2023 report said the Botkeeper (Robotic Interface) PDA app showed a MULE carrying another MULE's cargo, or the item it had carried earlier. On current master the app's data is built per MULE and the interface matches each MULE by its own reference, so the symptom did not appear in any test. The report was most likely against the older MULE and UI code, and no code change was made.

## The bug

As reported, with two MULEs, putting something on one and opening the Botkeeper app showed the wrong cargo name on a MULE. It was the other MULE's load, or the previous item after an unload or a delivery. The reporter's screenshots showed "MULE #1" and "MULE #2" with mismatched cargo.

## Reproduction

I could not reproduce it. What was done on the test server:

1. Started the round and spawned a crew security PDA (it has the Robotic Interface app) with a captain's spare ID inserted, plus two MULEs and several crates.
2. Loaded a crate onto one MULE. Using the Lua editor, I called the app's `ui_data` proc directly and read `data["mules"]`. The loaded MULE reported `load = "crate"` and the other reported `nil`.
3. Loaded a "wooden crate" onto the second MULE while the first still held "crate". Each reported its own cargo.
4. Repeated with 13 MULEs at once. Only the loaded ones showed cargo, each with its own.
5. Unloaded a MULE with `unload(0)`: its `load` became `nil`. Moved a crate out of a MULE by other means: `load` became `nil`. Deleted a loaded crate: `load` became `nil`.

This checked the data the server sends to the UI, not the rendered interface. The tgui JavaScript did not run in the test, so the on-screen result was not observed.

## Cause

No defect was found. At master:

- `code/modules/modular_computers/file_system/programs/robocontrol.dm:46-62` rebuilds the MULE list on every `ui_data` call. Each entry carries `"mule_ref" = REF(basic_mulebot)` and `"load" = basic_mulebot.get_load_name()`.
- `get_load_name()` (`code/modules/mob/living/basic/bots/mulebot/mulebot_delivery.dm:84`) is `return load ? load.name : null`, so it reflects the current `load` variable.
- `tgui/packages/tgui/interfaces/NtosRoboControl.jsx:14-15,106` finds a robot's MULE entry with `mule.mule_ref === robot.bot_ref`, not by list position. Line 161 renders `mule.load || 'N/A'`.
- `load` is cleared on unload paths in `mulebot_delivery.dm` (around lines 33, 104 and 117).

Nothing pairs MULEs by index, and no cached value survives between calls. This suggests the 2023 behaviour came from the older implementation, which has since been refactored. I did not verify that against history, because the checkout is shallow.

## Fix

None. No commits were made.

## Verification

Verified, on the test server and through `ui_data` output only: the per-MULE load for two and for 13 MULEs, clearing after unload, after the crate left the MULE, and after the crate was deleted.

Not checked: the rendered tgui, a mob riding a MULE, and the paranormal MULE subtype (where `get_load_name()` exists specifically to hide ghost riders' names).

## Notes

- The issue is old (April 2023, reported on client version 514.1589 with several testmerges), and current master no longer matches its code. Closing it is reasonable, ideally after someone glances at the app in a real client.
- The UI's reference-based matching is what rules out the "another MULE's cargo" symptom. A stale-name symptom would need `load` to stay set after the cargo left, and the unload paths checked above clear it.
