## Summary

Three unrelated megafauna issues were examined together. A Hierophant killed by an explosion dropped its club in every test, and the club was only lost when a second explosion hit its tile, which is ordinary object behaviour, so #37952 was not reproduced. The watcher half of #68999 was not reproduced (its projectile uses the default speed), and the demonic frost miner's slow projectiles look like deliberately converted old delay values, so nothing was changed. For #95288, the Blood-Drunk Miner attacked anything in sight because its behaviour tree used sight-based target acquisition; the fix switches it to the retaliate list, so it only fights mobs that attacked it.

## #37952: Hierophant killed by an explosion does not leave its club

### The bug

The 2018 report says a Hierophant died to a gibtonite explosion, its body stayed in place, and no loot appeared. One commenter suggested that a further explosion after the death may have destroyed the dropped staff.

### Reproduction

All steps were done with admin tools on a test round, observing as a ghost, using the Lua editor and SDQL2. No gibtonite was used; the explosions were created directly by calling `explosion()`.

1. Spawned a Hierophant and reduced it to about 5 health (`adjust_brute_loss(2495)`). Setting `health` directly does not work, because `updatehealth` recomputes it from the brute loss; a first attempt that used `set_health(5)` was therefore invalid and was discarded.
2. Called `explosion(turf, 1, 3, 5)` centred on the Hierophant's tile.
3. Repeated with four Hierophants placed at distances 0 to 3 tiles from the explosion centre.
4. Searched the area with SDQL2 for Hierophant clubs.
5. As a control, killed a Hierophant with `adjust_brute_loss(5000)` instead of an explosion.

Result: every Hierophant killed by an explosion dropped a club, and every club survived (the blast threw them a few tiles). The control kill also dropped a club. The loss of the club was not reproduced.

Not tested: two explosions in quick succession, which is the scenario the code reading below predicts would destroy the club.

### Cause

No explosion-specific code path removes the loot.

- `/mob/living/simple_animal/hostile/megafauna/ex_act` (`code/modules/mob/living/simple_animal/hostile/megafauna/_megafauna.dm:171`) only subtracts health (250, 100 or 50 by severity). Death then goes through `hierophant/death()` (`.../megafauna/hierophant.dm:437`), which calls the parent `death()`, and that calls `drop_loot()` (`code/modules/mob/living/simple_animal/simple_animal.dm:357`) to create the club before the mob is deleted.
- The club is a normal object. `/obj/ex_act` (`code/game/objects/obj_defense.dm:10`) destroys it on a devastate explosion and damages it otherwise, unless it has `INDESTRUCTIBLE` or `BOMB_PROOF`. The club only has `LAVA_PROOF | FIRE_PROOF | ACID_PROOF` (`code/modules/mining/lavaland/mining_loot/megafauna/hierophant.dm:20`).
- Explosions collect the contents of a turf (`/turf/contents_explosion`, `code/game/turfs/turf.dm:579`) during the turf phase. A club created by a death during an explosion did not exist then, so the same explosion does not touch it. A later explosion on that tile does.

This matches the explanation in the issue's comments.

### Fix

None. Making the club explosion-proof would be a gameplay change that the issue does not ask for.

### Verification

Not applicable (no change). The tests above were run on unmodified master.

### Notes

- Side finding: `hierophant/death()` runs twice. It sets the stat to `DEAD`, then at `hierophant.dm:446` sets it back to `STABLE` (`set_stat(STABLE)`, commented "deathgasp won't run if dead"), which lets death trigger again. The attack log showed died / left crit / regained consciousness / died, and the death message and burst were printed twice. This is harmless for the loot (`drop_loot` empties `loot` after the first run) and was not investigated further.

## #68999: Watcher and demonic frost miner projectiles are too slow

### The bug

The reporter (2022) saw watcher bolts and all demonic frost miner (DFM) projectiles travelling "super slow".

### Reproduction

Using the Lua editor, created one projectile of each type (`/obj/projectile/temp/watcher`, `/obj/projectile/colossus/frost_orb`, `/obj/projectile/colossus/snowball`, `/obj/projectile/colossus/ice_blast`), fired them in one direction, read their `speed` variable and watched how far each moved in a couple of seconds.

- The watcher bolt crossed about 8 tiles within roughly 1 to 2 seconds. It is not slow.
- The frost orb moved about 2 tiles in the time the ice blast and the snowball moved about 6, so the orb is roughly 1 tile per second and the other two roughly 3 tiles per second. The measurements were coarse (a few observations of positions two seconds apart).

### Cause

- Projectile speed is higher-is-faster: each tick the projectile moves `elapsed_time * SSprojectiles.pixels_per_decisecond * speed` pixels (`code/modules/projectiles/projectile.dm:903`). The default is `speed = 1.25` (`projectile.dm:106`).
- The watcher bolt (`code/modules/mob/living/basic/lavaland/watcher/watcher_projectiles.dm`) does not override `speed`, so it uses 1.25.
- The DFM projectiles in `code/modules/mob/living/simple_animal/hostile/megafauna/demonic_frost_miner.dm` set `speed = 0.1` (frost orb, line 201), `0.33` (snowball, line 216) and `0.33` (ice blast, line 226). That is 4 to 12 times slower than the default. The values look like the old per-tile delays (10, 3 and 3 deciseconds) carried over when the projectile speed semantics were inverted. The DFM's own speed multipliers (for example the enraged 2x) already assume higher-is-faster.

### Fix

None. The slow DFM projectiles fit the encounter (slow, homing orbs and a snowball stream), and changing them is a balance decision. If maintainers want them faster, the change is to raise the three `speed` values. The watcher half of the report was not reproduced, and no cause for the reporter's observation was found.

### Verification

Not applicable (no change).

### Notes

- The watcher mob's own `speed = 3` (`watcher.dm:13`) is its movement delay, not a projectile speed.

## #95288: Blood-Drunk Miner is always aggroed

### The bug

A Blood-Drunk Miner attacks as soon as a player comes into its line of sight, instead of waiting to be attacked like other megafauna. The issue's comments say megafauna used to behave this way and that the AI refactor (PR #94728) may have changed it; they also note that lowering `BB_AGGRO_RANGE` to 0 does not help, because the target search uses a vision range as well.

### Reproduction

1. Started a round and observed as a ghost; opened the Lua editor.
2. Spawned a `/mob/living/basic/boss/blood_drunk_miner` six tiles from a human in an open hallway with clear line of sight, and waited about 12 seconds.
3. After the fix (see Verification): the miner stood still. It did not move or attack.

The behaviour before the fix was not re-run on the test server. The cause below comes from reading the code and from the issue's own reproduction steps.

### Cause

`blood_drunk_miner.bt.json` ran `/datum/bt_node/ai_behavior/acquire_target/update_combat_targets` (line 35 at master) as the secondary branch of its parallel node. That behaviour looks for any valid target within sight and the controller's `BB_AGGRO_RANGE` (18, `blood_drunk_ai.dm:12`), so the miner picks a target as soon as anyone is visible. The mob only had the `relay_attackers` element (`_blood_drunk_miner.dm:60`), which reports attackers but does not feed any target list. Nothing in its behaviour tree restricted targets to mobs that had attacked it.

### Fix

Commit "Fix issue 95288: Blood-drunk miners only fight those who attack them" changes three files:

- `blood_drunk_miner.bt.json` (and its compiled `.bt.compiled.json`): replaced `update_combat_targets` with `target_from_retaliate_list` (`code/datums/ai/generic_behaviors/target_retaliate.dm`) and set `vision_range` to 18. That behaviour's default vision range is 9; 18 keeps the miner's old reach, so a distant attacker (for example someone with a kinetic accelerator) still counts.
- `_blood_drunk_miner.dm`: `Initialize` now adds `/datum/element/ai_retaliate` instead of `/datum/element/relay_attackers`. The retaliate element adds `relay_attackers` itself and records each attacker in `BB_BASIC_MOB_RETALIATE_LIST`, which is the list the new behaviour reads.

The change is in the shared base type, so it applies to all subtypes (guidance, hunter, doom). The alternatives mentioned in the issue were lowering `BB_AGGRO_RANGE` (shown not to be enough) or building an enemy list like monkeys have; using the existing retaliate element does the latter with existing code.

### Verification

On a rebuilt test server, a miner was spawned six tiles east of a human in the open Central Primary Hallway (clear line of sight). For 12 seconds or more it neither moved nor attacked. A projectile fired with the human as its `firer` was then shot at the miner, and the miner immediately chased and attacked (chat: "The blood-drunk miner slashes at ... with her cleaving saw!", and it fired its kinetic accelerator). The round's runtime log showed no new runtimes, only the notice line for the SDQL2 query.

Not checked:
- The behaviour before the fix, in game.
- The guidance, hunter and doom subtypes individually (the change is in the shared base type and bt.json).
- Whether the miner gives up and returns to idle after an attacker leaves or dies.
- An attacker beyond the 18 tile range.

### Notes

- This is a behaviour change: miners that used to attack on sight now ignore passers-by, which makes the mining ruins easier. The issue's comments argue this is the intended design (players choose the difficulty, and rescues are easier). Maintainers should confirm they want that.
