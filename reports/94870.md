## Summary

Ore vent wave mobs are placed with `turf_peel(..., view_based = TRUE)`, which uses BYOND `view()`. Windows do not block `view()`, so with a ring of windows around the vent the mobs spawned outside the ring. The vent's `anti_cheese()` explosion, which fires only when no valid spawn turf exists, never ran. The fix gives `turf_peel()` an optional `reachable` flag that keeps only turfs a mob could walk to from the vent, and the spawner uses it. A sealed vent now falls back to the vent tile and triggers `anti_cheese()`. #93715 (mobs stop attacking when the miner leaves) is a separate likely cause, only read in code and not tested.

## #94870: window ring around the vent

### The bug

A miner surrounded an ore vent with plasma windows (all sides but one, scanned the vent, then pushed a window onto the last side) and walked away. The reporter doubts the vent can be lost this way. A comment from a maintainer explains the intended defense: `anti_cheese` spawns mobs on the vent itself when there are no visible turfs to spawn them on, but windows let turfs stay visible.

### Reproduction

On the test server, on the lavaland level, using the Lua editor and admin tools:

1. Possess a human with a mining scanner. Put reinforced plasma fulltile windows (`/obj/structure/window/reinforced/plasma/fulltile`) on all 8 tiles around an ore vent, and start the wave by calling the vent's `scan_and_confirm` from Lua and answering "Yes" in the prompt.
2. Watch the spawned mobs and the node drone.

Observed on master (first trial): the mobs (two bileworms and a legion) appeared outside the ring, 3-4 tiles from the vent. In that one trial the vent was still lost: the node drone's health went from about 300 to 110 to 22 and then it was gone, and the vent was reset to untapped. What damaged the node was not identified (ranged attacks from the mobs, or something else). So that trial placed the mobs outside the windows as predicted, but did not show the "unlosable" outcome. Trials with melee-only mobs were not run.

### Cause

`/datum/component/spawner/proc/select_turf` (`code/datums/components/spawner.dm:172`) picks the spawn turf with:

```dm
picked_spot = pick(turf_peel(spawn_distance, spawn_distance_exclude, spawner.loc, view_based = TRUE, reject_dense = TRUE))
```

`turf_peel` (`code/__HELPERS/spatial_info.dm:521`) with `view_based = TRUE` uses `circle_view_turfs()`, which iterates BYOND `view()`. Transparent windows do not block it, so turfs outside a window ring count. The fallback `COMSIG_SPAWNER_SPAWNED_DEFAULT` (sent at `spawner.dm:176`), which `ore_vent.dm` registers to `anti_cheese()` (`code/game/objects/structures/lavaland/vent_mining/ore_vent.dm:101`, proc at `:596`), only fires when the peel is empty and the spawn falls back to the vent tile. With the ring in place the peel is never empty.

### Fix

One commit, "Fix issue 94870: ore vent mobs no longer spawn past window rings":

- `code/__HELPERS/spatial_info.dm`: new `circle_reachable_turfs(center, radius)`, a breadth-first walk over the 8 directions from the center, stopped by dense turfs and by `LinkBlockedWithAccess` (so windows and closed doors count as walls), limited to the circle of that radius. `turf_peel()` gets a new argument `reachable = FALSE`. When set, it walks to twice the outer range, so a gap just outside the peel still counts, and drops peel turfs that were not reached.
- `code/datums/components/spawner.dm`: `select_turf()` passes `reachable = TRUE`.

The result: a sealed vent has an empty peel, falls back to the vent tile, and fires the existing `anti_cheese()` explosion. The design follows upstream PR 96756 (a flood fill added to `turf_peel`, closed without being merged and written for an older version of `turf_peel`); it was adapted to the current `view_based`/`reject_dense` signature rather than a mode argument.

### Verification

On the test server after the fix:

- Sealed vent: a small ore vent with 8 reinforced plasma fulltile windows around it, wave started. Chat showed "A creature emerges to assault the small ore vent." The mobs (a chasm lobstrosity and a brimdemon, plus the node drone) were at the vent's own tile and none outside the ring. All 8 windows were still standing but damaged to 947-982 of 1000 integrity, consistent with the `anti_cheese()` explosion.
- Open vent (regression): a medium ore vent with no windows. Mobs spawned at 3-4 tiles from the vent as before (two lobstrosities and a bileworm), and a goliath on the vent tile attacked the node. No new runtimes appeared.

Not checked: a partially walled vent (one gap), a wave that is actually lost or won with only melee mobs, and the cost of the extra flood fill on a wave with many spawns.

### Notes

- The `if(!picked_spot)` fallback after `pick()` in `select_turf()` is dead code, because `turf_peel()` always returns at least the center.
- The query tool broke on `&&` and `>=` in an SDQL2 query submitted through the UI; plain `==` or Lua worked. This is unrelated to the fix.

## #93715: mobs stop attacking the vent when the miner leaves

### The bug

As reported, running out of render distance during the wave makes the defending mobs stop attacking the vent, giving a free completed vent. A commenter guesses it is for performance.

### Reproduction

Not attempted in game.

### Likely cause (code reading only)

`get_active_ai_status()` in `code/datums/ai/_ai_controller.dm:482-497` returns `AI_STATUS_OFF` for a controller whose pawn is not in a station or shuttle area, has no nearby client, and lacks the `RUN_WHILE_UNWATCHED` trait. Lavaland mobs spawned by the vent fall in that case, so once no player is nearby their AI switches off while the wave timer continues.

### Suggested fix (not implemented or tested)

Give vent-spawned mobs `RUN_WHILE_UNWATCHED` (for example in `ore_vent.dm` where spawned mobs are set up, with `created.ai_controller.ai_traits |= RUN_WHILE_UNWATCHED` followed by `reset_ai_status()`), or `ALWAYS_HIGH_PRIORITY`. This should be reproduced first by starting a wave, walking away and watching mob positions. It would also affect AI load while a wave runs.
