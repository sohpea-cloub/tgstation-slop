| Status | #77877 fixed on the branch below; #86667 no fix (could not be reproduced) |

| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

When a slimeperson who has split off spare bodies holds a stabilized green extract and then loses it, the extract's removal code re-applies the owner's species even though it has not changed. That replaces the slime species datum, whose `bodies` list is the only link to the spare bodies, so the owner loses them (and the other bodies lose the owner). The fix restores the species on removal only when it differs from the stored original, so the same-species case keeps the datum and the link. #86667 (a CQC skillchip carried over to slimeperson clones) could not be reproduced: clones never received the martial art.

## #77877: stabilized green extract removes spare bodies

### The bug

The reporter made several copies of a slimeperson, picked up a stabilized green extract, and no longer had the extra bodies. The issue also complains more generally that the body link is fragile (it breaks on becoming human or another jelly species) and asks for bodies to be recoverable after a species change. Only the stabilized green case is a clear defect; the rest is a design question (see Notes).

### Reproduction

On master, using admin tools (the Lua editor on the test server):

1. Spawn a human, set its species to `/datum/species/jelly/slime`, and put a player in control of it.
2. Use the slime's Split Body action (`make_dupe()`) so the species' `bodies` list holds the spare bodies. The list held 3 entries in the run on master.
3. Apply `/datum/status_effect/stabilized/green` to the owner (this is what holding the extract does), then remove it.
4. Compare the `bodies` lists.

Observed before the fix: `bodies` had 3 entries before and during the effect. After removal the owner's species still had type `/datum/species/jelly/slime`, but its `bodies` list had 1 entry, and the other body's list had 2 (the owner was gone from it).

The effect was applied and removed by calling the status effect procs from the Lua editor, not by actually holding and dropping an extract in game. The result matches the reporter's description.

### Cause

On apply, `/datum/status_effect/stabilized/green` stores a copy of the owner's DNA, including species (`code/modules/research/xenobiology/crossbreeding/_status_effects.dm:821`), then randomizes the owner. On removal it copies the stored DNA back with `COPY_DNA_SPECIES`:

```dm
originalDNA.copy_dna(human.dna, COPY_DNA_SE|COPY_DNA_SPECIES|COPY_DNA_MUTATIONS)
```
(`_status_effects.dm:836`)

For a human target, `copy_dna` handles `COPY_DNA_SPECIES` by calling `set_species(species.type, ...)` (`code/datums/dna/dna.dm:97-98`), which always builds a new species datum, even when the type is unchanged. The old slime datum then runs `on_species_loss` (`code/modules/mob/living/carbon/human/species_types/jellypeople.dm:241-246`):

```dm
bodies -= C // This means that the other bodies maintain a link
// so if someone mindswapped into them, they'd still be shared.
bodies = null
```

The list is removed from the owner, and the new datum starts with a fresh list containing only the owner. The other bodies keep the old list, minus the owner. The link is gone in both directions.

### Fix

One commit, "Fix issue 77877: stabilized green extract no longer breaks the slimeperson body link", changes `on_remove` in `_status_effects.dm`. It builds the copy flags as `COPY_DNA_SE|COPY_DNA_MUTATIONS` and adds `COPY_DNA_SPECIES` only if `human.dna.species.type != originalDNA.species.type`. The effect still restores the species when it was really changed, but leaves the datum alone when it was not. This is the smallest change that stops the wipe. Making `set_species` skip same-type changes, or making `on_species_loss` preserve the list, would be broader and affect other callers; neither was tried.

### Verification

On the test server with the fix, in the same Lua setup: the `bodies` list had 2 entries before applying the effect, 2 during, and 2 after removal, and the owner's and the other body's lists were the same list object.

Not checked: holding and dropping a real extract in game; the case where the effect actually changes the species type (the restore path with `COPY_DNA_SPECIES` is unchanged but was not exercised); more than two bodies after the fix (the post-fix run had 2 entries).

### Notes

- The issue's wider requests are not addressed: that bodies should be recoverable after changing species and later returning to slimeperson, and that links break in other situations (becoming human, other jelly species). As the issue's commenter noted, the bodies are stored on the slime species datum and are wiped when the species changes, and it is unclear whether bodies should be tied to a DNA string. That is a design decision.
- Other code that calls `set_species` with the same slime type will have the same effect; this was not searched for.

## #86667: CQC chip skill survives in slimeperson clones

### The report

Slimeperson clones of someone with a Close Quarters Cooking chip (usually the cook) reportedly keep the martial art when the player transfers into them.

### Attempt to reproduce

On master, using the Lua editor: spawn a human, make it a slimeperson, implant a `/obj/item/skillchip/job/chef` chip and activate it, then split a body from the chipped body. The chipped body had one martial art; both clones had none. This also held after swapping back and forth between bodies (`swap_to_dupe`) and after a second split.

Martial arts are stored on the mob (its `martial_arts` list; see `code/datums/martial/_martial.dm`), not on the mind, and `make_dupe`, `swap_to_dupe` and the quirk transfer do not copy them. So a clone does not inherit the art, and a player moving into a clone does not take it along.

### Verdict

Not reproduced; no fix. Two explanations are consistent with the findings, neither tested: the 2024 report was made before a martial art refactor that changed this, or the player swapped back into the original chipped body, which keeps CQC because the chip is in that brain (expected behavior). The report was made on client 515 with a test merge, so a round-specific cause cannot be excluded.
