## Summary

The Ore Silo UI builds a search string for every log entry and assumes each entry's `noun` is a string and its `user_data` is a record with a name and assignment. Two server-side callers break that assumption: the module duplicator passes its materials list where the log noun belongs, and several machines that log without a user (smelters, conveyor-fed redemption machines) leave `user_data` null. Either one makes the tgui component throw and show the blue screen of death. The fix makes the module duplicator pass proper arguments, makes `/datum/ore_silo_log` always store a string noun and a user record, and makes `OreSilo.tsx` tolerate both anyway. #91694 was checked and the silo already enforces distance and consciousness through the default tgui state.

## The bug

Opening the Ore Silo UI crashes with a TGUI "fatal exception" screen (`TypeError: e.noun.toLowerCase is not a function` in #95816). After the crash, the reporter could not clear the error box even by refreshing TGUI. #94038 reports the same blue screen when opening the silo, with comments saying it happens "intermittently" and, for one commenter, always for an AI; a commenter traced it to `e.user_data.name.toLowerCase()` with a null `user_data`. #91694 is a separate report that the silo's UI ignores distance, consciousness and similar checks.

## Reproduction

On master `87b93338`, with the Lua editor as an admin observer on MetaStation. Machine actions were driven partly through procs and tgui actions rather than through hands-on construction. The crash itself was not reproduced in a rendered client: the UI data that the browser receives was read instead and shown to contain the offending values.

**#95816, non-string noun**

1. Spawn a `/obj/machinery/module_duplicator`. Connect its materials to the default silo (`GLOB.ore_silo_default`) by calling `materials._PrepareStorage(1)` on it, set the silo's `ID_required = 0`, and add iron to the silo.
2. Give the duplicator a fake design: `scanned_designs = {{name = "testcomp", materials = {[iron] = 1000}}}`.
3. Possess a human next to the duplicator, click the duplicator to open its UI, and send the tgui action `print` with `design_path = 1`.
4. Open the silo UI and read `data.logs`. The entry was:

   ```
   "machine_name": "module duplicator", "action": "testcomp", "amount": -1,
   "noun": { "iron": 1000 }, ...
   ```

   The `noun` is an object, not a string, so `log.noun.toLowerCase()` in `OreSilo.tsx` (line 269 on the tested tree) throws exactly the error in the report. The action is also the design's name, which should have been the verb.

**#94038, null user data**

1. In the Lua editor, call `silo.silo_log(silo, "processed", -1, "bar", {[iron] = 100}, nil)`, which is what a caller with no user does.
2. Call `silo.ui_data(user)` and look at that entry: `user_data` is null (it would be sent to the UI as JSON `null`), so `log.user_data.name.toLowerCase()` (`OreSilo.tsx:264`) would throw.

Not tested: an AI viewing the silo. The code does not make `ui_data()` depend on who is looking, so the "always for an AI" comment is probably just the AI being the person who most often opens the silo.

**#91694**

1. Open the silo UI as an adjacent human. Ejecting one sheet of iron worked (200000 to 199900).
2. Make the human unconscious. The window went to tgui status 0 (view only) and an eject did nothing.
3. Teleport the human about 20 tiles away: the silo window closed.

## Cause

- **Noun.** `code/modules/wiremod/core/component_printer.dm:432` calls
  `materials.use_materials(design["materials"], efficiency_coeff, 1, design["name"], design["materials"], user_data = user_data)`.
  The parameters of `/datum/remote_materials/proc/use_materials` (`code/datums/materials/material_container/remote_materials.dm:244`) are `(mats, coefficient, multiplier, action, name, user_data)`, so the design name went into `action` and the materials list went into `name`, which the silo logs as the `noun`. Other callers (`_production.dm`, `mech_fabricator.dm`) pass `"processed"` and `"[design.name]"`.
- **Null user data.** `/datum/ore_silo_log/New()` (`code/modules/mining/machine_silo.dm:579-587`) stores `noun` and `user_data` exactly as given, and `ui_data()` sends them straight to the UI (`machine_silo.dm:282-283`). Callers without a user, such as the smelter (`machine_processing.dm`: `materials.use_materials(alloy.materials, multiplier = amount)`) and the ore redemption machine (`machine_redemption.dm`, where `user_data` starts as null), pass nothing, so `user_data` is null.
- **UI.** `OreSilo.tsx:258-270` builds the search string with unguarded calls (`log.user_data.name.toLowerCase()`, `log.noun.toLowerCase()`, and so on), and lines 418 and 448 read `user_data.name`, `user_data.assignment` and spread `user_data`, all assuming both values always exist. One bad entry therefore breaks the whole component for everyone viewing the silo, and because the log is persistent for the round, the crash comes back on every open.

## Fix

One commit, "Fix issue 95816: ore silo logs always have a string noun and user data", with three parts:

- `component_printer.dm`: the call now passes `"processed"` as the action and `"[design["name"]]"` as the noun, like the other fabricators.
- `machine_silo.dm`: `/datum/ore_silo_log/New()` stores `noun = "[_noun]"` and `user_data = user_data || ID_DATA(null)`. `ID_DATA(null)` is the record the code already uses for an unknown user, with every field set to `id_read_failure`. The structured log line and the UI data now use the stored record.
- `OreSilo.tsx`: `user_data` is typed `UserData | null`; the search string uses optional chaining and `String(log.noun ?? '')`; `UserItem` takes `Partial<UserData>`; the log entry display and its spread of `user_data` tolerate null.

The server and UI changes overlap on purpose. Fixing only the server leaves the UI fragile to any future caller passing bad data; fixing only the UI would leave a log with a materials list for a noun and a null user in the structured log (the log line also reads `user_data["name"]`).

No change for #91694.

## Verification

After the fix, with the same duplicator print:

- The log entry has `action` `processed` and `noun` `"testcomp"` (a string).
- The null-user entry now carries a `user_data` alist (the `ID_DATA(null)` record, name `id_read_failure`) instead of null.
- No new runtime came from the silo or duplicator paths. One `bad index` runtime at `code/modules/wiremod/core/duplicator.dm:220` appeared, caused by the fake design having no component data, an artifact of the test setup.

Not checked:

- The `OreSilo.tsx` change was built with the tgui bundler without TypeScript errors for that file, but it was never run in a rendered client, so the actual blue screen and its absence were not observed.
- An AI user opening the silo, and the "box that cannot be dismissed after Refresh TGUI" from #95816's second screenshot.
- Which machine produced the non-string noun in the reporter's round is not known; the module duplicator is the only caller found passing a non-string name (the other component printer calls at lines 140 and 172 use `"[design.name]"`).

## Notes

- #91694 is closed as not reproduced because the silo has no `ui_state` override and so uses `default_state`, which already handles distance (`shared_living_ui_distance`), consciousness, AI line of sight and telekinesis range. A cyborg, AI or TK user acting within view or range is the intended behavior of that state for all machines (the ore redemption machine behaves the same). A real cyborg or TK run was not done.
- With `ID_DATA(null)` as the fallback, silo log entries from user-less machines show the name and assignment `id_read_failure` in the UI. That is the existing placeholder rather than a nicer label such as the machine's name; a maintainer may prefer something friendlier.
- One commenter on #94038 suggested `user_data ? user_data["name"] : "STATION"` in `machine_silo.dm`. The fix keeps a full record instead, so the UI and the ban buttons that send `user_data` back to the server get a complete structure.
- Starting Lua code before the server reported "Initializations complete" crashed the test server once; this is a test-workflow note, not part of the bug.
