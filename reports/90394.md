## Summary

The counterplay to a revenant-haunted item is to hit it with a bible or a null rod. That does not work when the haunted item is a storage item such as a backpack, box, toolbox or RPED: the click is consumed by the storage's "insert the held item" handling before the haunt component ever sees it. The fix makes the `haunted_item` component also react to `COMSIG_ATOM_ITEM_INTERACTION`, which is sent before the storage insertion, so holy items dispel the haunt first.

## The bug

All three issues report the same thing:

- #90394: hitting a haunted box or backpack with a bible makes the game "think you're trying to put the bible in the storage object", so the item is not purified. The reporter guessed it might only happen when the bible does not fit.
- #86939: haunted items that have storage, such as an RPED, cannot be dispelled with a bible. MrMelbert commented that it "just needs to be changed from attackby to item interaction comsig".
- #97943: hitting a haunted storage item with a bible prioritises insertion over dispelling.

The reporter's guess was close. Depending on the container, the bible is either inserted or refused as not fitting, and in both cases the haunt stays.

## Reproduction

With the round started and an admin observing, using the Lua editor:

1. Spawn a human and, for each of a backpack, box, RPED (`/obj/item/storage/part_replacer`) and toolbox, spawn the item and add the component `/datum/component/haunted_item` to it (`_AddComponent`). The item then has a haunted AI controller.
2. Spawn a `/obj/item/book/bible` and call `melee_attack_chain(human, item)` with it on each item. This goes through the normal attack chain used when a player clicks an item with the bible. The click was not made by a player in the client, but by this call.
3. Check whether the item still has its AI controller (the haunt) and where the bible ended up.

Observed on unfixed master:

- Backpack and toolbox: the chat showed "puts the bible into the backpack" (and toolbox). The haunt remained and the bible was inside.
- Box and RPED: the haunt remained as well. The bible was not inserted (it was rejected as not fitting), and nothing dispelled the haunt.

## Cause

Item clicks go through `atom/proc/base_item_interaction()` in `code/game/atom/atom_tool_acts.dm`. It first sends `COMSIG_ATOM_ITEM_INTERACTION` (`:28`), then runs the atom's `item_interaction` and the tool's `interact_with_atom`, and then, at `:53-59`, handles storage itself:

```dm
// We have to manually handle storage in item_interaction because storage is blocking in 99% of interactions ...
if(atom_storage)
	if(is_left_clicking)
		if(atom_storage.insert_on_attack)
			return atom_storage.item_interact_insert(user, tool)
```

`item_interact_insert` (`code/datums/storage/storage.dm:906`) calls `attempt_insert` and then always returns `ITEM_INTERACT_SUCCESS`, whether or not the item actually fits, so the click ends there. The old `attackby` path is only reached when `base_item_interaction` returns `NONE`.

`/datum/component/haunted_item` in `code/modules/antagonists/revenant/haunted_item.dm` only listened to `COMSIG_ATOM_ATTACKBY` (`:85`, handler `on_hit_by_holy_tool` at `:100`). For any item with `atom_storage` the click had already been consumed, so the dispel never ran.

The holy items that dispel a haunt by default are `/obj/item/nullrod`, `/obj/item/book/bible` and anything with `TRAIT_NULLROD_ITEM` (`:71-72`).

## Fix

One commit, `Fix issue 90394: holy items dispel haunted storage items instead of being inserted`, changing only `code/modules/antagonists/revenant/haunted_item.dm`:

- `RegisterWithParent()` also registers `COMSIG_ATOM_ITEM_INTERACTION` to a new `on_item_interacted_by_holy_tool()`. `UnregisterFromParent()` unregisters both signals.
- The body of the old `on_hit_by_holy_tool()` was moved into a shared `try_dispell(source, attacking_item, attacker)`, which does the type/trait check, shows the "dispells the ghostly energy" message, clears the haunt, and returns whether it dispelled. The old attackby handler calls it and keeps returning `COMPONENT_NO_AFTERATTACK` on success. The new handler returns `ITEM_INTERACT_SUCCESS` on success and `NONE` otherwise, so non-holy items fall through to the normal storage behaviour.
- The existing attackby handler was kept, so non-storage items and other paths into attackby behave as before.

This is the approach MrMelbert suggested in #86939 (use the item interaction signal). Because the signal is sent on the atom before the storage block, no change to storage code was needed.

## Verification

On a rebuilt server, with the same setup extended to a backpack, box, RPED, toolbox and crowbar, each hit with a bible, a null rod and a wrench:

- Bible and null rod on every one of these items: the chat showed "dispells the ghostly energy from the X!", the haunt was gone afterwards, and the holy item was not inserted into the storage item.
- Control with a wrench (not a holy item): on backpack, box and toolbox it was still inserted and did not dispel the haunt. The RPED rejected it as before.
- The crowbar (a non-storage haunted item) was dispelled by the bible and null rod as well.

Not checked:

- A real client click by a player. All hits were done by calling `melee_attack_chain` from the Lua editor.
- Right-click (secondary) interactions, which use `COMSIG_ATOM_ITEM_INTERACTION_SECONDARY` and are not covered by this change.
- Combat mode on versus off, and other holy items that dispel through `TRAIT_NULLROD_ITEM`.
- The runtime log was not inspected for this unit.

## Notes

- Other components that rely only on `COMSIG_ATOM_ATTACKBY` for items that can also be storage would have the same problem. None were searched for.
- #86939 and #97943 are marked as duplicates of #90394 because they describe the same cause. All three should be closable by one fix.
