## Summary

Wounds caused by shotgun pellet clouds were applied without a damage source, so autopsy reports listed them as "Unknown". `painless_wound_roll()` had no damage-source argument, and its final `check_wounding()` call also put `wound_clothing` into the `attack_direction` slot. In addition, when a wound was escalated through `replace_wound()`, the new wound inherited the old wound's source instead of the attack that caused the upgrade. The fix passes the pellet's name through and lets escalations record the new source.

## The bug

The reporter shot a human with buckshot, a hellfire laser and a .38 revolver, and got "Wound source: Unknown" in the autopsy for the wounds. Testing on master showed that single-projectile hits already record their source. Only the pellet-cloud path (buckshot) printed "Unknown". The reporter's remark that the puncture was missing from the report is expected: a healed wound is removed and is not reported.

## Reproduction

On master, using the Lua editor as an observer:

1. Spawn humans.
2. Hit one with a direct projectile through `victim:bullet_act(proj, zone)`, using a .38 bullet, a hellfire laser and a shotgun slug. These gave "Ruptured Cavity = .38 bullet" and "Third Degree Burns = hellfire laser", so the source was recorded.
3. Fire buckshot at a human with `fire_casing(victim, shooter, null, 0, true, 'chest', 0, gun)` on an `/obj/item/ammo_casing/shotgun/buckshot`. The result was the wound "Weeping Avulsion = Unknown".

This was done by calling the firing procs directly, not by a player shooting a gun.

## Cause

- `code/datums/components/pellet_cloud.dm:339` called `hit_part.painless_wound_roll(wounding_type, damage_dealt, w_bonus, bw_bonus, sharpness)` with no damage source.
- `painless_wound_roll()` (`code/modules/surgery/bodyparts/wounds.dm:2`) had no damage-source parameter. Its last line, `check_wounding(wounding_type, wounding_dmg, wound_bonus, exposed_wound_bonus, wound_clothing)` (`wounds.dm:35`), passed `wound_clothing` positionally into the `attack_direction` slot, so the clothing flag was never seen as such.
- When `check_wounding()` upgraded an existing wound, it called `replace_wound()` (`wounds.dm:129`), and `replace_wound()` (`code/datums/wounds/_wounds.dm:407`) always passed the old wound's `wound_source` on to the new wound. The upgrade therefore kept the first attack's source rather than the one that caused the escalation.

## Fix

One commit, "Fix issue 76781: record the damage source on wounds from pellet clouds and wound escalation":

- `painless_wound_roll()` takes a `damage_source` argument and passes it to `check_wounding()`, using named arguments (`damage_source =`, `wound_clothing =`) so `wound_clothing` no longer lands in the `attack_direction` slot. The `wound_clothing` parameter now defaults to TRUE.
- The pellet cloud passes `proj_name` (for buckshot, "buckshot pellet") as the damage source.
- `replace_wound()` takes a `new_wound_source` argument. If it is null the new wound keeps the old source (so demotions behave as before). `check_wounding()` passes its `damage_source` when it replaces a wound.

## Verification

After rebuilding, in the same setup:
- Buckshot gave "Open Laceration = buckshot pellet".
- A .38 gave "Ruptured Cavity = .38 bullet", and a shotgun slug gave "Compound Fracture = 12g shotgun slug".
- One runtime appeared during testing. It came from the Lua test script firing a slug at an already severed limb, not from the change.

Not checked:
- The `replace_wound()` upgrade path (two shots producing a higher-severity wound in the same series) was not exercised in game; it is a simple argument pass-through.
- The reporter's hairline fracture from buckshot specifically was not tested, though bone wounds go through the same pellet path.
- Autopsy reports were judged from the wound source value, not read through the surgery UI.

## Notes

- The `wound_clothing` default changed from unset (null) to TRUE, and it now reaches its real parameter. Before, pellet-cloud wounds never asked to damage clothing (the value went into `attack_direction`); now they do. A maintainer may want to confirm this is the intended behaviour; it was not tested.
