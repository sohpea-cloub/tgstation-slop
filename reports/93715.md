# #93715: Ore vent wave mobs stop attacking when no player is nearby

| | |
|---|---|
| Issues | [#93715](https://github.com/tgstation/tgstation/issues/93715): verified (reproduced on master) and fixed |
| Status | Fixed on the branch below; checked in game by starting the wave through the Lua editor, not through the player-facing scan/prompt path |
| Fix branch | [fix/93715](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/93715) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

When a player starts an ore vent defense wave and then walks away, the vent's defenders (goliaths, brimdemons, watchers, lobstrosities, and so on) never attack the node drone. The AI controller classifies them as off-station with no client nearby, and it turns their AI off unless they carry the `RUN_WHILE_UNWATCHED` trait. Lavaland wave mobs do not carry it. The fix sets `RUN_WHILE_UNWATCHED | ALWAYS_HIGH_PRIORITY` on mobs the spawner component creates in wave mode, so their AI keeps running with nobody around.

## The bug

The issue reporter described it like this: start the ore vent event, run out of render distance, and the vent finishes without the enemies attacking it. The result is free mining points and a completed vent. A commenter guessed the cause was performance-related. That guess matches the code, because the AI is switched off deliberately to save CPU.

What actually happens is that the wave mobs spawn and then sit idle. Their AI is off, so they never go for the node drone, and the wave timer runs out with the drone untouched.

## Reproduction

The steps below were run on master. The wave was started by calling the vent's proc directly, not through the in-game scan and confirmation prompt. See the note at the end of this section.

1. Start a round on the test server and observe as a ghost, far from Lavaland (the observer was on the station level, nowhere near any vent).
2. Open the Lua editor. Take an ore vent from `SSore_generation.possible_vents`.
3. Spawn a `/mob/living/basic/node_drone` at the vent, call `node:arrive(vent)`, and set `vent.node` to the drone.
4. Call `vent:start_wave_defense()`. This skips the `tgui_alert` and the other work done in `pre_wave_defense`.
5. Wait about 25-45 seconds, then read the state of every living mob within 12 tiles of the vent: its AI status and the drone's health.

Observed on master, at the vent at (156,186,3):

- Two brimdemons and three lava lobstrosities were present, and all five had their AI status off.
- The node drone's health was 530, the full amount, so nothing had attacked it.

Everything from the point of `start_wave_defense()` on is the same code the real scan and prompt reach. The one thing not exercised is `pre_wave_defense` itself (the tgui confirmation and the setup before the wave).

## Cause

`get_active_ai_status()` in `code/datums/ai/_ai_controller.dm:483-496` decides whether an AI controller runs:

```dm
if(istype(pawn_area, /area/station) || istype(pawn_area, /area/shuttle))
	return AI_STATUS_ON
if(has_nearby_client())
	return AI_STATUS_ON
if(ai_traits & RUN_WHILE_UNWATCHED)
	if(ai_traits & ALWAYS_HIGH_PRIORITY)
		return AI_STATUS_ON
	else
		return AI_STATUS_ON_LOW
return AI_STATUS_OFF
```

A pawn that is neither in a station or shuttle area nor near a client, and that lacks `RUN_WHILE_UNWATCHED`, gets `AI_STATUS_OFF`. Lavaland is off-station, so once the miner is out of range, any vent defender without the trait goes to sleep. A client arriving nearby wakes them again.

The vent defenders are goliaths, legions, watchers, lobstrosities, brimdemons and similar (see `defending_mobs` in `code/game/objects/structures/lavaland/vent_mining/ore_vent.dm`). In the code that was checked, only a few other mobs set the trait (carp, mooks, goldgrubs and some bots), so none of the wave defenders had it. The wave is created by the spawner component with `spawner_logic = SPAWN_BY_WAVE_BEHAVIOR` (`ore_vent.dm:298`), and the spawner component (`code/datums/components/spawner.dm:212`) has a wave-only branch for newly created mobs. That branch only adds a `heads_up` status effect and does nothing about the AI.

## Fix

One commit, "Fix issue 93715: ore vent wave mobs stop attacking when no player is nearby", changes `setup_spawned_mob` in `code/datums/components/spawner.dm`. In the `SPAWN_BY_WAVE_BEHAVIOR` branch, a spawned mob that has an `ai_controller` now gets:

```dm
created_mob.ai_controller.ai_traits |= (RUN_WHILE_UNWATCHED | ALWAYS_HIGH_PRIORITY)
created_mob.ai_controller.reset_ai_status()
```

`RUN_WHILE_UNWATCHED` stops the AI being turned off when unobserved. `ALWAYS_HIGH_PRIORITY` makes `get_active_ai_status()` return `AI_STATUS_ON` rather than `AI_STATUS_ON_LOW`, so the defenders plan at full rate. A vent can have up to 10 defenders alive at once (`max_spawned = 10`). `reset_ai_status()` applies the new traits straight away, since the controller has already computed its status by the time the spawner edits the traits.

The change is in the spawner component rather than in each mob type, because the wave branch is the one place all defenders pass through. Only the ore vent uses `SPAWN_BY_WAVE_BEHAVIOR`, so no other spawners are affected. I did not find another approach that was tried.

## Verification

After the fix, the same Lua-editor procedure was repeated, on a different vent (at (205,51,3)), again with the observer far away on the station level:

- The wave brimdemons had their AI on, with ai_traits 116 (= 20 | 32 | 64, which includes the two new flags). The watcher also had traits 116.
- The node drone's health went 530, then 362, then 324 while no player was nearby, so the defenders were attacking it.
- No new runtimes appeared in the runtime log, apart from an already-known empty Lua line.

Not checked or uncertain:

- The full player path (scanning the vent, answering the tgui prompt, the wave playing out to completion, and the vent finishing or failing) was not run. The wave was started by calling `start_wave_defense()` directly.
- A goliath and a lobstrosity in range showed traits 20 and were not wave spawns; they were ordinary mapgen mobs.
- One watcher showed `able_to_run` as 0 at the instant it was read. This was treated as transient and was not examined further.
- The node drone's own AI stays off when unwatched. It is passive, so this was considered irrelevant, but it was not tested further.
- No performance measurement was made.

## Notes

- Design cost: wave mobs now run their AI while nobody is near, which is exactly the cost the sleeping logic exists to avoid. It is limited to the ore vent's defenders, and only while a wave lasts, but a maintainer may prefer a lighter option. `ALWAYS_HIGH_PRIORITY` may be more than is needed; `RUN_WHILE_UNWATCHED` alone would give `AI_STATUS_ON_LOW` (a lower planning rate).
- Related issue: #94870, "Ore vent defense can be cheesed", is the same group of reports and was the source of the code lead.
- The fix does not change what happens if the node drone is simply left alone and the defenders never reach it for another reason (not examined).
