## Summary

Putting an integrated circuit into a shell charged the circuit's power cell once for every component in the circuit, because `set_shell()` triggers each component to refresh its outputs and every trigger costs energy. Any use of a rigged (plasma-filled) cell can set it off, so the circuit exploded in the player's hands as it was inserted (#63925, #65004). Separately, a cell destroyed inside a circuit stayed referenced, so the shell kept reporting the dead cell's old charge (#63922). The fix makes the refresh on shell attach free of energy cost and clears the circuit's cell reference when the cell is deleted. #76833 could not be reproduced.

## The bug

### #63925 and #65004 (duplicates)

A player puts a plasma-rigged battery into an integrated circuit as a booby trap, then inserts the circuit into a shell. The cell explodes at that moment, killing the player, instead of waiting until the device is actually used. #65004 describes the same thing ("it blew up on my face the moment I inserted it inside the shell"). A reply on #65004 pointed out that circuits are supposed to use energy only when components receive a signal. That is the intended design, and the problem is that the insertion itself counted as a signal.

Even without a rigged cell, every insertion drained a little power for no reason.

### #63922

When the rigged cell in a circuit exploded, the circuit shell still reported "The charge meter reads 100%", although the circuit no longer had a working cell and could not be used.

### #76833

The report says that after using a circuit in hand a few times, it "will start to drain power significantly faster for no reason". The author guessed the cost of modules such as speech was being added to a passive drain, then wrote "nvm something else causes this". It gives no steps and no component list.

## Reproduction

### #63925 / #65004

On master, using the Lua editor:

1. Spawn an `/obj/item/integrated_circuit/loaded` and add four `/obj/item/circuit_component/random` components to it.
2. Rig the circuit's cell with 5 units of plasma (a rigged cell).
3. Spawn a compact remote to act as the shell. Insert the circuit into it by calling `attach_circuit` on the shell's `/datum/component/shell`. This is the same proc the shell runs when a player inserts a circuit board, but it was called from Lua and not by hand.
4. Observed: at the moment of the call the admin log showed "triggered a rigged power cell explosion", with an explosion of heavy 1, light 2. Nothing had triggered a component except the attach itself.

### #63922

Same setup as above. After step 4, the circuit's `cell` variable still pointed at an object that Lua reported as destroyed ("destructed userdata" when converted to a string). Anything reading `cell.percent()` through it, such as the shell's examine text, still got the old charge. The shell was not examined after the explosion; the stale reference was observed directly on the circuit.

### #76833

A circuit with a remote component wired to a speech component was put into a compact remote. The remote was used in hand (`attack_self`) six times, with a wait between uses so the component could run on the following tick, and the cell's percentage was read before and after each use. The drain per use was 0.0100% of the cell every time (six readings of 0.0100). No growth in the drain appeared.

## Cause

### Charge on attach

`set_shell()` in `code/modules/wiremod/core/integrated_circuit.dm` (lines 194-204) turns the circuit on and then triggers every attached component once:

```dm
for(var/obj/item/circuit_component/attached_component as anything in attached_components)
	attached_component.register_shell(shell)
	// Their input ports may be updated with user values, but the outputs haven't updated
	// because on is FALSE
	attached_component.trigger_component()
```

The comment states the purpose: refresh the output ports after the circuit was switched off. But `trigger_component()` calls `should_receive_input()` (`code/modules/wiremod/core/component.dm:280`), which takes `energy_usage_per_input` from the circuit's cell (lines 290-294; the default is `0.001 * STANDARD_CELL_CHARGE`, line 54):

```dm
var/flags = SEND_SIGNAL(parent, COMSIG_CIRCUIT_PRE_POWER_USAGE, energy_usage_per_input)
if(!(flags & COMPONENT_OVERRIDE_POWER_USAGE))
	var/obj/item/stock_parts/power_store/cell = parent.get_cell()
	if(!cell?.use(energy_usage_per_input))
		return FALSE
```

So inserting a circuit with N components cost N times that amount. `power_store/use()` (`code/modules/power/power_store.dm:159-161`) calls `try_explode()` whenever it is asked for a positive amount, and a cell whose reagents react to the charge (plasma) explodes and is deleted. An ordinary use was also an energy cost, which #65004 questioned.

### Stale cell

`set_cell()` (`integrated_circuit.dm:137-139`) only assigned `cell = cell_to_set`. When `try_explode()` ends in `qdel(src)` (`power_store.dm`, end of `try_explode`), nothing told the circuit, so `cell` stayed a reference to a deleted cell. Code that reads it, such as the shell's `on_examine` (`code/datums/components/shell.dm:141`, `cell ? round(cell.percent(), 1) : 0`), saw a non-null cell and printed its last charge.

## Fix

Two commits on `fix/63925`.

**Fix issue 63922: circuits stop using a power cell that was destroyed inside them.** `set_cell()` now unregisters `COMSIG_QDELETING` from the old cell and registers it on the new one. The new `on_cell_qdeleting()` handler calls `set_cell(null)` if the deleted cell is still the circuit's cell. Going through `set_cell()` also sends `COMSIG_CIRCUIT_SET_CELL`, so module components that hold nested circuits get the cleared cell too.

**Fix issue 63925: attaching a circuit to a shell no longer uses power.** A new static variable `free_component_refresh` on `/obj/item/integrated_circuit` is set to TRUE around the `trigger_component()` call in `set_shell()`. In `should_receive_input()`, when it is set, the power-usage step is skipped as if a signal handler had returned `COMPONENT_OVERRIDE_POWER_USAGE`. The variable is static because a component inside a module runs against a different, nested circuit that shares the same cell. A per-circuit flag would not have covered those. Nothing else about the refresh changed: components still receive their input and update their outputs as before, and only the energy charge is skipped. The commit message also notes this covers #65004.

## Verification

Checked on a test server after rebuilding with both commits, through the Lua editor (the same direct `attach_circuit` call as in the reproduction, not by hand):

- Plain circuit: cell charge was 100 before and 100 after attach. Triggering a component for real (`trigger_component()` on the first component) then lowered it to 99.99, so normal use still costs energy.
- Rigged circuit: the cell survived the attach (`true`). Triggering a component afterwards made the cell explode, and the circuit's `cell` was `nil` afterwards, so examining the shell would show 0% and not the stale 100%.
- #76833: see Reproduction, six constant readings of 0.0100%.
- The runtime log of the test round showed no runtimes from this code. The one entry was from a mistake in the observer's own Lua.

Not checked:

- Inserting the circuit by hand in the player UI (item use on the shell), not just the proc call.
- The shell's examine text after the explosion, which was inferred from `cell == nil` and the `on_examine` code.
- Nested module circuits, with or without a cell, and the case where the shared flag should cover them. Only the reasoning in the Fix section supports this.
- Other shells or other power-use paths such as `COMSIG_CIRCUIT_PRE_POWER_USAGE` handlers, and circuits with `admin_only` set.

## Notes

- The one-time refresh still runs each component's real `input_received`. Only the energy is free. This is unchanged from before the fix.
- Another way to avoid the explosion would be to skip the refresh trigger or change which components are triggered. That was not tried, because the refresh is needed to set up outputs.
- The `free_component_refresh` flag is global. This is safe because `trigger_component()` must not sleep (it is marked `SHOULD_NOT_SLEEP`), so nothing else can run while it is set. Maintainers who prefer to avoid a static variable could pass the flag explicitly down to the trigger.
- #63922 is not exactly the report's scenario (a cell drained until it explodes). The reproduction reached the same state through the attach explosion and, after the fix, through a normal trigger. In both cases the stale reference is the same.
- #76833 may be caused by something specific that was not tried. Possible causes that came up during testing were components with unusually high costs (view sensor, remote camera, which has its own per-tick cost) or a shell drawing power from an APC when anchored. None of these were tested, and neither were module nesting or looping circuits. The author withdrew their own theory, so the report stays unreproduced and nothing was changed for it.
