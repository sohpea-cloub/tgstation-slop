## Summary
Hooded suits that use the `toggle_attached_clothing` component create their hood fresh each time it is first deployed, and nothing copies protections the suit gained afterwards (slime chill potion, pyre unmelting rite, darkblue regenerative core, hypernoblium crystal). So a fireproofed hooded suit has an unprotected hood. The fix adds `inherit_parent_modifications()` to the component, runs it on deploy and from the four modifier sites. For #93596 (a "fireproofed" MOD suit still burning), fireproofing individual MOD parts already worked, but the potion refused the control unit, so it was easy to miss a part. The potion now accepts the control unit and coats every part.

## #75980: hoods do not inherit protections

### The bug
Applying a modifier to a hooded suit, such as the pyre sect's unmelting ritual, does not apply it to the hood. The issue gives the Divine Archer robes as the main example: the hood cannot be detached or put on the altar, so the wearer can never become fully fireproof.

### Reproduction
On master, using the Lua editor and a test human:
1. Dress a human in `/obj/item/clothing/suit/hooded/chaplain_hoodie`.
2. Use a `slimepotion/fireproof` on the suit (`interact_with_atom(suit)`), then deploy the hood (`toggle_deployable()`).
3. Read the values. The suit had `max_heat_protection_temperature` 35000, the hood 0 with `heat_protection` 0, and `get_thermal_protection()` on the human returned 24500. That is below `FIRE_IMMUNITY_MAX_TEMP_PROTECT` (35000), so the human still takes fire damage (`code/datums/status_effects/debuffs/fire_stacks.dm`, around line 220).

The potion was used through its proc, not by a player click.

### Cause
`create_deployable()` in `code/datums/components/toggle_attached_clothing.dm:165` builds the hood with `new deployable_type(parent)`. Nothing later reapplies modifications that the parent received after its own creation. The four sources set flags only on the suit: the slime chill potion (`code/modules/research/xenobiology/xenobiology.dm`, `slimepotion/fireproof`), the darkblue regenerative core (`crossbreeding/regenerative.dm:131`), the pyre rite (`code/modules/religion/pyre/pyre_rites.dm:3`) and the hypernoblium crystal (`crystallizer_items.dm:11`).

The pyre rite also had its own defects: it set the hood's `heat_protection` to the *suit's* `body_parts_covered` (`pyre_rites.dm:6`, via `chosen_clothing`), and it only handled a hood that already existed in the suit's contents when the rite ran.

### Fix
Commit "Fix issue 75980: deployed hoods inherit fireproofing and pressure-proofing from their suit":
- adds `/datum/component/toggle_attached_clothing/proc/inherit_parent_modifications()`. It copies `FIRE_PROOF`, a raised `max_heat_protection_temperature` (and sets the hood's `heat_protection` to the hood's own covered parts), a changed `min_cold_protection_temperature` (with `cold_protection`), and `STOPSPRESSUREDAMAGE`. Each is copied only when the parent differs from its `initial()` value, so ordinary hooded suits are untouched.
- calls it when the hood is deployed, and from the potion, the regenerative core, the pyre rite and the hypernoblium crystal, so an already existing hood is updated too.
- makes the pyre helper use the item's own `body_parts_covered` instead of the suit's.

### Verification
On the test server with the same human:
- Potion on the suit before deploying the hood: hood `max_heat_protection_temperature` 35000, `FIRE_PROOF` set, human thermal protection 35000.
- Potion applied while the hood was already worn: the same values.
- No runtimes in the runtime log.

Not checked in game: hypernoblium and cold-protection inheritance (same code path as fireproofing, not exercised), the pyre rite and regenerative core call sites, and real burn damage over time; only `get_thermal_protection()`, the gate for fire damage, was read.

### Notes
- The inherit rules are heuristic ("differs from the initial value"). A parent whose initial protection is already high is not treated as modified.

## #93596: "fireproofed" MOD suit still burns

### The bug
A MOD suit and gas mask reported as fireproofed with all parts deployed still took burn damage in hot gas and while on fire.

### Reproduction and findings
Using a MOD suit (`pre_equipped`/standard) on a test human, deploying and sealing all four parts and using the potion on each part: thermal protection went 0 → 35000, and it survived unsealing and resealing (it reads 0 only while unsealed, which is intended) and retracting and redeploying. So fireproofing parts works as designed. Only the helmet and chestplate matter for `get_thermal_protection()` (`code/modules/mob/living/carbon/human/life.dm:149`). Hot-gas damage uses a separate per-bodypart `heat_protection` path that also counts boots and gloves.

The potion returned "can only be used on clothing" for the control unit, so "fireproofing the modsuit" meant coating each deployed piece, which is easy to get wrong. This matches the comments on the issue (missed parts such as shoes, and fire raising body temperature).

### Cause
No defect in the reported mechanism; a usability gap: `slimepotion/fireproof` rejects `/obj/item/mod/control`.

### Fix
Commit "Fix issue 93596: slime chill potion fireproofs every part of a MOD suit when used on its control unit" splits the potion into `fireproof_clothing()` and a new `fireproof_mod()`. On a control unit it coats every part not already fireproof for a single use, and keeps unsealed parts' `heat_protection` at its previous value until they are sealed. A second use says the suit is already fireproof and consumes nothing.

### Verification
Potion on the control unit with parts stowed: all parts `max_heat_protection_temperature` 35000 and `FIRE_PROOF`, one use consumed. Deployed unsealed protection was 0, sealed 35000. The second use used no charge. The hood case was rechecked after this refactor (35000). Not checked: damage in actual fire or hot gas.

### Notes
- This is a behaviour change, not a bug fix: a maintainer may prefer to leave the potion as is. The issue's thread suggested "improving something" to reduce confusion without prescribing it.
- The fixes for the two issues share the potion code and are in separate commits.
