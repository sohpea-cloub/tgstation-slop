# #94396: Build mode stays on after an admin loses their rights (plus #95855: Respawn Character randomizes felinid ears)

| | |
|---|---|
| Issues | [#94396](https://github.com/tgstation/tgstation/issues/94396): verified, fixed. [#95855](https://github.com/tgstation/tgstation/issues/95855): verified, fixed |
| Status | Both reproduced on master and fixed; fixes checked in game |
| Fix branch | [fix/94396](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/94396) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

The two issues are unrelated bugs that were worked in one unit. Each has its own commit.

## Summary

**#94396.** `/datum/admins/proc/disassociate()` removed the admin's verbs and holder but never quit an active build mode. After a deadmin (manual or automatic) the build mode buttons and click interception stayed on. The fix quits the build mode in `disassociate()` when the client's `click_intercept` is a `/datum/buildmode`.

**#95855.** `hardset_dna()` called `dna.generate_unique_features()` and discarded the returned string. The new mob kept its random `unique_features`, and `updateappearance()` then applied those blocks over the restored `dna.features`. Respawn Character therefore lost the felinid ears and tail. The fix assigns the result to `dna.unique_features`.

## The bug

### #94396

A build-mode admin who is deadminned, for example by taking a midround antagonist role that auto-deadmins, is no longer an admin. Their screen still shows the build mode buttons and build mode still intercepts their clicks. The issue is titled "Build mode remains on when you are automatically deadminned".

### #95855

Using the Respawn Character admin verb on a felinid gave the new body a different ear type from the one the player had. The ears and tail the player had chosen did not survive the respawn.

## Reproduction

### #94396

1. On a test server, as an admin with build mode rights, run Toggle-Build-Mode-Self. Four build mode buttons appeared on the screen: Toggle Mode, Buildmode Help, Change Dir and Quit Buildmode.
2. Run the DeAdmin verb. The verb list changed to show Readmin, so the deadmin had worked.
3. The four build mode buttons were still on the screen, and `click_intercept` was still the build mode datum.

The automatic deadmin could not be triggered directly. `auto_deadmin()` returns `FALSE` for a localhost client (`code/modules/admin/permissionedit.dm:574`), and the test client was a localhost guest. The manual DeAdmin verb was used instead. It calls the same `deactivate()` and `disassociate()` as the automatic path, so the code path under test is the same. A real midround antagonist role was not taken.

### #95855

This was reproduced with the Lua editor and the Respawn Character verb. It was not reproduced by a player dying and being respawned in a normal round.

1. With the Lua editor, spawn a human, set its `dna.features['ears']` to `Lynx`, and call `set_species` with the felinid species. Set the ears to `Lynx` again afterwards, since the species change can reset them.
2. Give the human a mind with the Assistant role and inject it into the manifest (`GLOB.manifest:inject(h)`), so that a locked character record exists. Have the test client possess it.
3. Make the client a ghost whose mind is not active: `ghostize(true)` and then set `mind.active = false`. (`ghostize(false)` drops the ghost's mind, so `respawn_character` finds no mind and no record, and takes the randomizing branch instead.)
4. Run Respawn-Character and enter the client's key.
5. Read `dna.features` on the new mob with the Lua editor.

Result on master: species `Felinid`, ear organ "the cat ears", but `dna.features['ears']` was `"None"` and `dna.features['tail_cat']` was `"None"`. The `Lynx` ears set in step 1 were lost.

Two earlier attempts with a different setup went through the verb's plain-randomize branch and did not exercise the bug.

## Cause

### #94396

`disassociate()` in `code/modules/admin/holder2.dm` (about line 170) removes the client from `GLOB.admins`, calls `owner.remove_admin_verbs()` and clears `owner.holder`. It never touches the build mode datum:

```dm
/datum/admins/proc/disassociate()
	...
	if(owner)
		GLOB.admins -= owner
		owner.remove_admin_verbs()
		owner.holder = null
		owner = null
```

Build mode lives in `code/modules/buildmode/buildmode.dm` and is stored in `client.click_intercept`. Its `quit()` (line 40) is what clears the click interception and the buttons. Nothing calls it when the holder goes away, so the UI stays. Both the manual DeAdmin verb and auto-deadmin end in `disassociate()`.

### #95855

`respawn_character` (`code/modules/admin/verbs/admingame.dm:249`) finds the locked character record for the ghost's mind and calls `hardset_dna` with the record's DNA (line 292), passing `found_dna.features`. In `hardset_dna` (`code/datums/dna/dna.dm:437`):

```dm
if(newfeatures)
	dna.features = newfeatures
	dna.generate_unique_features()
```

`generate_unique_features()` (line 191) returns the encoded feature string. Elsewhere its result is assigned (`unique_features = generate_unique_features()`, line 332). Here the return value was dropped, so `dna.unique_features` stayed as the fresh mob's own random values. `hardset_dna` is later followed by `updateappearance()` because `unique_identity` is passed. `updateappearance()` (line 481) applies each feature block from `dna.unique_features` to the mob (`block_to_apply.apply_to_mob(src, dna.unique_features)`) and also calls `organ.mutate_feature(dna.unique_features, src)`. That overwrote the restored `dna.features` with values decoded from the stale string.

## Fix

The branch has two commits.

- **Fix issue 94396: leave build mode when losing admin rights.** In `disassociate()`, before `owner.remove_admin_verbs()`, it checks `istype(owner.click_intercept, /datum/buildmode)` and calls `quit()` on it. Fixing it in `disassociate()` covers every way of losing the holder, including manual DeAdmin, auto-deadmin and forced deadmin, instead of patching each caller. Build mode needs `R_BUILD`, so it should not outlive the holder.
- **Fix issue 95855: respawned characters keep their DNA features.** One line in `hardset_dna`: `dna.unique_features = dna.generate_unique_features()`. This keeps `unique_features` in sync with the `features` that were just set, so `updateappearance()` re-applies the same values.

## Verification

### #94396

On the test server with the fix built, Toggle-Build-Mode-Self added the four build mode buttons. After DeAdmin, the chat showed "You are now a normal player." and the four buttons (Toggle Mode, Buildmode Help, Change Dir, Quit Buildmode) were removed from the screen.

Not checked: a real automatic deadmin from taking a midround role (not possible for a localhost client), and re-adminning afterwards.

### #95855

The same Lua setup was repeated on the fixed build and Respawn-Character was run through the record path. Afterwards `dna.features['ears']` was `Lynx`, the species was `Felinid`, the ear organ was the cat ears, and `dna.features['tail_cat']` was `Cat`.

Not checked: other species, a non-felinid respawn, the plain-randomize branch of the verb, a real death-and-respawn in a round, and the replica pod path.

## Notes

- `hardset_dna` has one other caller that passes `newfeatures`: `code/modules/hydroponics/grown/replicapod.dm:206`. It had the same stale `unique_features` problem and gets the same fix. Its behavior was not tested.
- On #95855 the issue says ears become "a random variant". In the reproduction the values came back as `None`, not a random ear type. Which one a player sees depends on what the fresh mob's random `unique_features` decode to, and that was not studied further.
- #94396 was reported with a Blood Worm test merge. The cause is in the admin holder code and does not depend on that merge.
- No upstream PR fixing either issue was looked up.
