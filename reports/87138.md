# #87138: Drones can lose their built-in tools (and carry guns)

| | |
|---|---|
| Issues | [#87138](https://github.com/tgstation/tgstation/issues/87138) (fixed for the built-in tools; the gun part is not a code bug), [#93919](https://github.com/tgstation/tgstation/issues/93919) (same cause, fixed) |
| Status | Reproduced, fixed and checked in game (built-in tools). No code change for guns. |
| Fix branch | [fix/87138](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/87138) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

A maintenance drone's built-in tools carry the `holderloving` component, which is supposed to keep them in the drone. It only blocks unequips and drops, so anything that moves the tool without going through the unequip check can take it out of the drone for good: wrapping it in a parcel (which can then go into a toolbox), `temporarilyRemoveItemFromInventory()` followed by `forceMove()`, or moving it from the drone's tool storage straight into another storage. The fix makes the component also react to the tool moving at all and put it back in the drone if it ended up anywhere else. Drones holding guns is not a code problem: nothing in the code prevents it, only the drone rules text does.

## The bug

#87138 says drones can take guns out of rechargers and shoot them, and that they can put their built-in tools into disposals, eject them and drag them around (dropping the tool in hand puts it back into the drone, so this is recoverable). It also says alt-click and ctrl-click on PDAs gets the ID and pen out. #93919 reports the same escape for an abandoned drone: the built-in tools can be put into toolboxes and left behind with the toolbox.

## Reproduction

On master `87b93338`, on a private test server, using admin tools:

1. Start a round, open the Lua editor and spawn: a recharger with an energy gun in it, a disabler on the floor, a mechanical toolbox, a disposal bin, a stack of package wrap and a drone (`/mob/living/basic/drone`). Take control of the drone (Assume Direct Control, or set the drone's ckey) and choose Maintenance Drone.
2. Guns: click the recharger with an empty hand. The energy gun went into the drone's left hand. The disabler on the floor was picked up the same way.
3. Built-in tool routes that were already blocked on master:
   - Clicking the toolbox with the built-in crowbar in hand: the crowbar stayed in the hand. The chat still printed "You put the built-in crowbar into the mechanical toolbox.", which is false (see Notes).
   - Clicking the disposal bin with the built-in wrench: blocked (the drone hit the bin instead).
   - Dragging a tool from the storage UI onto the toolbox: nothing happened.
   - Dumping the drone's storage: blocked by `/datum/storage/drone/dump_content_at`.
4. The route that worked: take the built-in wrench in one hand and the package wrap in the other, then click the wrench with the wrap. Chat: "Drone (35) wraps the built-in wrench." A small parcel appeared in the hand. Clicking the toolbox with the parcel printed "You put the small parcel into the mechanical toolbox." The Lua editor then showed the drone's built-in tools holding 9 tools (the wrench missing) and the toolbox holding a `/obj/item/delivery/small` with a `/obj/item/wrench/drone` inside. The wrench was left behind.

The disposals route from the report itself was not reproduced directly (the direct click was blocked); the parcel can go anywhere a normal item can, so it was only tested going into a toolbox. #93919 was reproduced with a normal (not abandoned) maintenance drone, and the screenshots in that issue do not show which route the reporter used, so wrapping is one working route, not necessarily the reporter's.

## Cause

`code/modules/mob/living/basic/drone/drone_tools.dm:28-29` gives every built-in tool `/datum/component/holderloving` with the drone as holder. The component (`code/datums/components/holderloving.dm:19-22`) registered only two signals: `COMSIG_ITEM_PRE_UNEQUIP` (`can_be_moved`, `:48-56`, blocks the unequip unless the destination is a turf or the holder or the holder's mob) and `COMSIG_ITEM_DROPPED` (`check_my_loc`, `:41-46`). Any move that does not pass through the unequip check is not seen:

- Package wrap (`code/game/objects/items/stacks/wrap.dm:140-151`): `dropItemToGround(item)` (allowed, the tool goes back to the drone), then `item.forceMove(parcel)` anyway, so the tool ends up inside a parcel the player holds.
- `temporarilyRemoveItemFromInventory()` (`code/modules/mob/inventory.dm:460`) defaults `newloc` to the mob, which the component accepts; a `forceMove()` afterwards is not seen. It has many callers (about 138 were counted).
- `attempt_insert()` from the built-in tools storage into another storage (`code/datums/storage/storage.dm:512-516`): the tool's location is the storage, not a mob, so it takes the plain `forceMove` branch with no unequip check.

For guns: `recharger` `attack_hand` simply calls `put_in_hands`, and nothing on drones prevents holding guns. The drone's flavour text (`code/modules/mob/living/basic/drone/_drone.dm:97`) forbids "Interacting with round critical objects (IDs, weapons, contraband, powersinks, bombs, etc.)", and `shy_update()` (`_drone.dm:293-299`) adds `TRAIT_PACIFISM` while the drone is shy, which only stops harmful shots. Whether drones should be physically prevented from holding weapons is a design decision.

## Fix

One commit on `fix/87138`: "Fix issues 87138, 93919: drone built-in tools return to the drone however they're moved".

- `holderloving` also registers `COMSIG_MOVABLE_MOVED` with a new `on_moved` handler (and unregisters it). If the tool lands anywhere that `is_valid_location` rejects (not the holder, not the holder's mob), it is `forceMove`d back into the holder. It does nothing if the tool or the holder is being deleted, so deleting the drone still deletes its tools.
- Two cases were added to `code/modules/unit_tests/holder_loving.dm`: moving the tool straight from its holder into another storage, and `temporarilyRemoveItemFromInventory()` followed by `forceMove()` into another storage; each asserts the tool ends up back in its holder.

This approach was chosen over adding more per-route blocks (a check in the wrap code, in storage insertion, and so on) because the escape is any move that skips the unequip check; one signal on the tool closes all of them, including ones nobody has found.

## Verification

Checked on a rebuilt server in a new round:

- On a second drone, via the Lua editor: moving a tool into another storage, holding it, `temporarilyRemoveItemFromInventory` plus `forceMove`, dropping it, and `forceMove` to a turf all ended with the tool in the drone's built-in tools, and the drone still had 10 tools. Taking a tool into the hand and dropping it still worked.
- The same clicks as step 4 above: "Drone (837) wraps the built-in wrench." The wrench reappeared in the built-in tools UI and was not in the parcel (checked in Lua: wrench in the built-in tools, 10 tools, the held small parcel empty).
- No runtimes in the server log or the round's runtime log.

Not checked: the new unit tests were not run (no unit-test run was done; the in-game Lua checks cover the same assertions). The disposals and PDA routes from the issue text were not tested individually. An abandoned drone specifically was not used.

## Notes

- After the fix, wrapping a built-in tool still uses one sheet of wrap and produces an empty parcel. A `can_be_package_wrapped()` override on the drone tools would refuse it up front; that was not done.
- `attempt_insert()` (`code/datums/storage/storage.dm:514`) ignores the return value of `transferItemToLoc`, so when the move is blocked it still prints "You put X into Y". This is a separate, cosmetic bug, not fixed here.
- Drones holding or shooting guns is a rules/design question. The code does not need a fix for it unless maintainers want drones to be unable to pick up weapons.
- The PDA ID and pen extraction mentioned in the body of #87138 was not looked into.
