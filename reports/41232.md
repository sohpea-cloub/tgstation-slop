# #41232: Timed actions (`do_after`) are not interrupted by movement for phased mobs, nor for voluntary steps in no gravity

| | |
|---|---|
| Issues | [#41232](https://github.com/tgstation/tgstation/issues/41232) - verified and fixed; [#93309](https://github.com/tgstation/tgstation/issues/93309) - verified and fixed (voluntary steps only, see Notes); [#49825](https://github.com/tgstation/tgstation/issues/49825) - not reproduced as described on current master (the voluntary-movement part is covered by the #93309 fix) |
| Status | Fix committed on a branch (two commits) and checked on a test server; not submitted upstream |
| Fix branch | [fix/41232](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/41232) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

`/datum/timed_action` (the object behind `do_after()`) cancels an action when the user moves, but it only listens to the user's own `COMSIG_MOVABLE_MOVED`. A mob jaunting inside an `/obj/effect/dummy/phased_mob` never changes `loc` (the dummy moves, not the mob), so the signal never fires and its timed actions keep running while it moves around (#41232). Separately, in no gravity every step creates a `drift_handler` before the moved signal is sent, and `on_user_moved()` treats "has a drift handler" as "is just drifting", so a jetpack or wing user who walks around keeps their action alive as long as the target stays adjacent (#93309, and the movement half of #49825). The fix registers a second moved-signal handler on the phased user's dummy container, and makes the drift exemption apply only to moves made by the drift loop itself (`inertia_moving`).

## The bug

### #41232: phased mobs

A mob in a phased form, such as a slaughter demon blood-crawling, can start a timed action (a `do_after()`) and then move around. The action's progress bar keeps filling and the action completes as though the mob had stood still. The issue author's diagnosis is that `do_after()` compares against `user.loc`, and a phased mob's `loc` is the dummy object, which stays the same. On current master the checking code has been rewritten (`/datum/timed_action` in `code/datums/timed_actions.dm`), but the cause is the same: nothing watches the thing that actually moves.

A comment on the issue notes that for some cases (resisting out of a locker) not being interrupted by "movement" of the container is correct. The fix leaves that alone (see Notes).

### #93309: wings (and other no-gravity movement)

The reporter had wings in a no-gravity area, started mining (with an armblade), moved "with kinetic force (not just WASD)", and the action bar kept filling and the rocks were destroyed. The issue says it is "very similar to #92583".

### #49825: pipes while drifting

A 2020 report: while drifting in space, a wrench or RPD action on a pipe is not cancelled, so a player can place or unwrench pipes from 2-4 tiles away. The reporter's steps were to hop between two lattices. The comment from the time points at the old `do_after` helpers, which skipped location checks while the user was drifting. That code no longer exists on master (see below).

## Reproduction

All steps below were done with admin tools on a test server running master `87b93338`. The timed action was **constructed directly** from the Lua editor (`SS13.new('/datum/timed_action', user, target, 1000)`, i.e. a 100-second action), and the user was moved by direct calls (`forceMove()`, `Move()`, `newtonian_move()`). I did not reproduce it with a real slaughter demon, pickaxe, wings or RPD, so the player-level path (blood-crawl entry, jetpack input, tool use) was not exercised; mining and pipework go through the same `do_after()` / `/datum/timed_action`.

### #41232 (phased user)

1. Open the Lua editor and spawn a human and an `/obj/effect/dummy/phased_mob` containing it: `SS13.new('/obj/effect/dummy/phased_mob', turf, human)`. The human's `loc` is now "the ethereal form".
2. Create a timed action for the human with no target: `SS13.new('/datum/timed_action', human, nil, 1000)`. Its `status` is `0` (`ACTION_WORKING`).
3. Move the dummy one tile north: `dummy:forceMove(get_step(dummy, NORTH))`. This is what `/obj/effect/dummy/phased_mob/relaymove()` does when the jaunter presses a movement key.
4. Read the action's `status` again.

Observed on master: `status` stayed `0` (action not cancelled), and the human's `loc` was still the dummy.

### #93309 (voluntary step in no gravity while a drift handler exists)

1. Mark an area as no-gravity (set the `NO_GRAVITY` bit in its `area_flags`); the test used the central primary hallway.
2. Spawn a human in it and give it `TRAIT_NOGRAV_ALWAYS_DRIFT` (`nograv_always_drift`; this trait is what makes `Process_Spacemove()` return false for a flying/jetpacking mover, so a drift handler is created and stays; godmode was also added to keep the test human alive). This stands in for a jetpack or wings user.
3. Create a timed action for the human whose target is a tile adjacent to the human (the tile directly north), 1000 ds long.
4. Make the human take a step east with `human:Move(east_turf, EAST)` (a plain voluntary step; the target stays adjacent diagonally).
5. Read `status`, `drift_handler`, and `inertia_moving`.

Observed on master: `status` `0` (not cancelled), `drift_handler` present (`/datum/drift_handler`), `inertia_moving` `0`, the human one tile east. As a control, an ordinary human without that trait that stepped in no gravity, in the positions tried, got no drift handler (it had something to push off from) and the action was cancelled (`status` `1`), which is why the trait was needed to model a jetpack/wing user.

### #49825 (pipes while drifting)

Not reproduced as described. With a drifting user (`TRAIT_NOGRAV_ALWAYS_DRIFT`, `newtonian_move(90)` along a wall) and a timed action targeting a wall tile that was diagonally adjacent at the start, the action stayed working while the user was still adjacent and was cancelled once they drifted out of adjacency (sampled every 0.1 s: x=109 working, x=110 working, x=111 working, x=112 cancelled). In an open hall with the target left behind, the action was cancelled when the user left adjacency. So the "unwrench from 3-4 tiles away" claim does not hold on master: the `Adjacent()` check in `on_user_moved()` ends the action. What is still true is that a drifting user keeps the action running as long as they are still adjacent to the target; see Cause and Notes.

## Cause

`code/datums/timed_actions.dm` (master).

### Phased users (#41232)

`register_signals()` (lines 71-75) only listens to the user:

```dm
if (!(timed_action_flags & IGNORE_USER_LOC_CHANGE))
	RegisterSignal(user, COMSIG_MOVABLE_MOVED, PROC_REF(on_user_moved))
```

A phased mob is moved by moving its dummy container: `/obj/effect/dummy/phased_mob/relaymove()` computes the destination and calls `forceMove(newloc)` on the dummy itself (`code/game/objects/effects/phased_mob.dm:88-95`). The jaunter's `loc` (the dummy) never changes, so `COMSIG_MOVABLE_MOVED` is never sent for the user and `on_user_moved()` never runs.

### Voluntary steps in no gravity (#93309)

`on_user_moved()` (lines 169-182):

```dm
if (user.loc == old_loc)
	return

if (isnull(user.drift_handler))
	cancel()
	return

for (var/atom/target as anything in targets)
	if (!target.Adjacent(user))
		cancel()
		return
```

The intent is that being carried by inertia should not cancel an action while the target is still within reach. But `drift_handler` is not specific to inertial movement. In `/atom/movable/Moved()` (`code/game/atoms_movable.dm:908-914`) a movement that is not diagonal-in-progress, not already inertial (`!inertia_moving`) and has `momentum_change` calls `newtonian_move()` **before** `COMSIG_MOVABLE_MOVED` is sent. `newtonian_move()` creates the `drift_handler` (`atoms_movable.dm:1333-1340`). So when someone who cannot push off anything (for example with a jetpack or wings) takes a deliberate step, they already have a drift handler by the time `on_user_moved()` runs, and the action is only checked against adjacency. The drift loop marks its own moves by setting `parent.inertia_moving = TRUE` around each move (`code/datums/drift_handler.dm:137-141`, reset at lines 133 and 150), so that flag is the right way to tell a loop move from a voluntary one.

### Pipes (#49825)

The 2020 comments cite `do_after`/`do_mob`/`do_atom` helpers that bypassed the location check while the user was drifting. They have since been replaced by `/datum/timed_action`, where the drift exemption still exists but is combined with the `Adjacent()` check shown above. The adjacency check is what limits the pipe range; the remaining issue is the same voluntary-step case as #93309.

## Fix

Branch: [fix/41232](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/41232), two commits, both in `code/datums/timed_actions.dm`.

1. **"Fix issue 41232: phased mobs' timed actions are interrupted when their dummy container moves".** Adds a `phased_container` variable (cleared in `Destroy()`). In `register_signals()`, inside the existing `!(timed_action_flags & IGNORE_USER_LOC_CHANGE)` branch, if the user's `loc` is an `/obj/effect/dummy/phased_mob`, the action remembers it and registers `COMSIG_MOVABLE_MOVED` on it with a new handler `on_phased_container_moved()`. That handler returns if the dummy's `loc` equals `old_loc` and otherwise calls `cancel()`.
   Why this approach: it keeps the check event-driven like the existing handler and needs no per-tick polling, it only affects users who are inside a `phased_mob` dummy, and it respects `IGNORE_USER_LOC_CHANGE`. Other containers (lockers, mechs, etc.) are not watched, so resisting out of a locker (the case mentioned in the issue comment) is unchanged. The dummy is captured once, when the action starts.

2. **"Fix issue 93309: voluntary movement cancels timed actions even while a drift handler exists".** In `on_user_moved()` the first check becomes `if (isnull(user.drift_handler) || !user.inertia_moving)` (with a comment). A move made by the drift loop (`inertia_moving` set) keeps the existing "stay running while still adjacent" behaviour; any other move cancels, as it already did for users without a drift handler.

An alternative would have been to remove the drift exemption altogether (any move cancels). That was not done because the existing exemption for pure inertia looks deliberate (the same exemption is used for moving targets in `on_target_moved()`).

## Verification

On the test server, after rebuilding with both commits, using the Lua editor to construct `/datum/timed_action` objects directly (status `0` = working, `1` = failed):

- Phased user, dummy moved north: `0` before the move, `1` after. Control: a second phased user whose dummy was not moved stayed `0`.
- Voluntary `Move()` east in a no-gravity area by a user with `TRAIT_NOGRAV_ALWAYS_DRIFT` (drift handler present, target adjacent): `1` (cancelled). On master the same test gave `0`.
- Pure inertia (`newtonian_move(90)`) along a wall with a diagonally adjacent wall target: working at x=109, 110 and 111, cancelled at x=112 when the user was no longer adjacent. This is the same behaviour as master, i.e. the inertial exemption was kept.
- Inertia away from an open-hall target: cancelled once the user left adjacency.
- No runtime errors in the runtime log of the round started after the rebuild (the earlier round's single runtime was a mistake in a test script).

Not checked:

- A real slaughter demon blood-crawling, or any other real jaunt, starting an actual `do_after` and moving with the movement keys. Only the dummy's `forceMove()` was exercised, not `relaymove()`.
- Real WASD input with a jetpack or wing organ, and real mining or RPD/wrench use; the voluntary step was a direct `Move()` call on a human with the always-drift trait.
- Cases involving being pushed, pulled, thrown or knocked back while a drift handler exists (see Notes).
- Other `do_after()` users with unusual flags, and the full unit test suite.

## Notes

- **#93309 remains partly open.** The reporter said they moved "with kinetic force (not just WASD)". A pure inertial drift (for example after a recoil or a throw) still does not cancel the action while the target remains adjacent, because the drift-loop exemption is kept on purpose. If that case is considered a bug too, the exemption would have to go or become narrower; the report does not say which source of movement they meant, so this is uncertain.
- **Behaviour change for non-voluntary, non-inertial moves.** With the second commit, any move that is not made by the drift loop, including being pulled or pushed while a drift handler exists, now cancels the action. That matches the behaviour for users without a drift handler, but maintainers may want to review whether a specific case (for example riding or being pulled) relies on the old behaviour.
- **#49825**: "drifting while still adjacent keeps the action going" is present and unchanged by the inertial rule; the long-range pipe interaction the reporter described is not reproducible on master because of the `Adjacent()` check. I suggest closing it as obsolete or merging it with #93309 if the maintainers agree.
- Issue labels and relationships: #93309 is described by its author as similar to #92583; it was not examined here.
- No upstream PR fixing these was identified from the available material.
