## Summary
#75472 (regal rats and other simple/basic mobs cannot toggle combat mode without a keybind) no longer applies: every living mob's HUD now has a combat mode toggle. #59166 had two complaints. The missing combat mode indicator is also already fixed. The other, a player-controlled MULEbot dragging a human onto itself and getting a useless view-only strip menu, still reproduced. The fix makes bots without `TRAIT_CAN_STRIP` skip that menu.

## #75472: regal rat combat mode toggle

### The bug
The report said combat mode controls regal rat licking, yet regal rats and other simple/basic mobs had no HUD button for combat mode, only the keybind.

### Reproduction
Not reproduced.
1. On the test server, observing, a regal rat was spawned with the Lua editor and the observer's ckey was set on it to take control.
2. The rat's screen contained a combat mode toggle ("toggle combat mode", at EAST-1:28,SOUTH:6).
3. Clicking it changed the state from combat off to combat on.

### Cause
Nothing wrong on master. `/datum/hud/living/initialize_screen_objects()` (`code/_onclick/hud/living.dm:1-4`) adds `/atom/movable/screen/combattoggle/flashy` at `ui_basic_combat_toggle` for every living mob that uses the living HUD.

### Fix
None.

### Verification
As above, in game. Not checked: other simple or basic mob types, apart from the MULEbot below.

## #59166: MULEbot drag onto self opens a strip menu

### The bug
Per the issue, a pAI-controlled MULEbot dragging someone onto itself buckled them and also opened their strip menu, even though nothing could be stripped. The issue also complained that combat mode state could not be seen.

### Reproduction
1. Spawned a `/mob/living/basic/bot/mulebot` and a human one tile east, using the Lua editor, and took control of the MULEbot.
2. Dragged the human onto the MULEbot.
3. On master a view-only `StripMenu` window opened. Clicking the MULEbot's combat toggle did nothing: the MULEbot has combat mode locked on (`TRAIT_COMBAT_MODE_LOCK`, `code/modules/mob/living/basic/bots/mulebot/mulebot.dm:77`), which is intended. The toggle icon showed "combat".

Buckling did not occur with default wiring (the MULEbot only made a "sighing buzz", `mulebot_delivery.dm:58`); it only happens on a hacked MULEbot. So only the strip menu half was seen.

### Cause
`mouse_drop_onto` in `code/datums/elements/strippable.dm:36` has a snowflake for cyborgs and bots (`strippable.dm:48-52`) that stops the menu only when the user is not in combat mode:

```dm
if(iscyborg(user) || isbot(user))
	var/mob/living/bot_user = user
	if (!bot_user.combat_mode)
		return
```
A MULEbot is always in combat mode, so it passes. No bot has `TRAIT_CAN_STRIP`, so the menu is always view-only (`ui_status`, `strippable.dm:521`).

### Fix
Commit "Fix issue 59166: bots that can't strip no longer open a useless view-only strip menu when dragging someone onto themselves" changes the check to `if (!bot_user.combat_mode || !HAS_TRAIT(bot_user, TRAIT_CAN_STRIP))`. Cyborgs have the trait, so they behave as before.

### Verification
After rebuilding, the same drag produced only "The MULEbot makes a sighing buzz" and no strip window. Not checked: a hacked MULEbot (buckling), cyborg behaviour after the change, or other bot types.

## Notes
- Non-bot simple mobs dragging someone still open the view-only strip menu. It was left alone, as arguably intended; the issue comments say all simple mobs do this.
- #59166's HUD indicator request was met by an earlier change: the MULEbot uses `/datum/hud/living/mulebot`, a subtype of the living HUD.
- The edited line in `strippable.dm` may also be touched by a fix for another issue (#89648) developed separately; a merge conflict is likely.
