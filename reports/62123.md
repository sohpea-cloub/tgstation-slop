# #62123: Forced latejoin ruleset is replaced by a random antagonist when the joiner is not a valid candidate

| Status | Verified; fix committed |

## Summary

When an admin queues ("forces") a latejoin ruleset in Dynamic and the next latejoiner is not a valid candidate for it (for example because they lack the matching antagonist preference), `on_latejoin()` logs that the queued ruleset "remains queued" but then continues into the normal random latejoin roll. The player can therefore be given a different antagonist than the one forced. The fix makes `on_latejoin()` return as soon as any queued ruleset has failed for this joiner, so the random roll is skipped and the queued ruleset stays queued for the next latejoiner.

## The bug

The report (2021, older Dynamic) says: the admin set the next latejoin to Syndicate Infiltrator, a player joined who had Infiltrator and Traitor enabled in preferences, and that player received a Latejoin Revolutionary head instead. The 2021 code is not what runs on master, but the current code produces the same symptom by a different path: an admin forces a latejoin ruleset, the joiner fails the forced ruleset's checks, and the joiner is handed a random latejoin antagonist anyway.

## Reproduction

Reproduced on the test server by setting the state up with the Lua editor, then performing a real latejoin through the lobby (the join itself was not simulated with proc calls).

1. Start the round (Start Now) and open the Lua editor.
2. For the joining player, set their antagonist preferences (`prefs.be_special`) to only "Syndicate Infiltrator". Master's Latejoin Traitor ruleset uses that preference; Latejoin Changeling uses "Stowaway Changeling", so this player is not a valid candidate for the changeling ruleset.
3. So that the random roll can pick Traitor with one player online, set `SSdynamic.dynamic_config` to `{["Latejoin Traitor"] = {min_pop = 0}}`. Set `SSdynamic.admin_forcing_next_latejoin = 1` (the admin "force next latejoin chance" toggle, which makes the latejoin chance 100%), and set `latejoin_ruleset_start` and `latejoin_cooldown` to 0.
4. Queue the "forced" ruleset: `SSdynamic:queue_ruleset(/datum/dynamic_ruleset/latejoin/changeling)`.
5. Latejoin from the lobby as an Assistant.

Observed on master:

- Chat: "You are the Assistant." followed by "You are the Traitor."
- `dynamic.log`:
  - `Latejoin (forced): Queued ruleset Latejoin Changeling failed to prepare! It remains queued for next latejoin.`
  - `Latejoin: <joiner> has been selected for Latejoin Traitor.`

The failure line appeared twice in that run because the changeling ruleset was in the queue twice (an earlier Lua attempt had failed part-way after queueing it, and the retry queued it again). The cause is not related to the duplicate.

## Cause

`on_latejoin()` in `code/controllers/subsystem/dynamic/dynamic.dm:452`. It first walks `queued_rulesets` (`:455`). If `prepare_execution()` fails for the joiner, it logs "failed to prepare ... remains queued" and does `continue` (`:459-461`). After the loop, the function does not remember that a queued ruleset failed, and falls through to:

```
if(COOLDOWN_FINISHED(src, latejoin_ruleset_start) && COOLDOWN_FINISHED(src, latejoin_cooldown))
	if(try_spawn_latejoin(latejoiner))
		return
```

(`:470-472`). `try_spawn_latejoin()` rolls `get_latejoin_chance()` and picks a random latejoin ruleset. With "force next latejoin chance" on (`admin_forcing_next_latejoin`, see `:590`) the chance is 100%, but it can also succeed by ordinary chance. The comment in `try_spawn_latejoin()` notes that no effort is made to pick a ruleset the player has opted into, so the random ruleset is applied to the same player the forced ruleset just rejected.

A forced ruleset fails for a joiner who lacks the ruleset's preference, among other `prepare_execution()` conditions (the commit message lists missing preference, ban and blacklisted job).

## Fix

One commit, "Fix issue 62123: forced latejoin ruleset no longer replaced by a random antag", changing `on_latejoin()` only:

- adds `var/queued_failed = FALSE` before the queue loop;
- sets it to `TRUE` in the failure branch, before the `continue`;
- after the loop, `if(queued_failed) return`, so the cooldown check and `try_spawn_latejoin()` are not reached.

The queued ruleset is not removed; it stays queued for the next latejoiner, and the existing "REMOVE FROM QUEUE" link in the admin message still works. Skipping the random roll only for that joiner was chosen over changing the queue behaviour (for example dequeuing on failure), because the existing log and message already document the "remains queued" intent.

## Verification

Same steps as above on the fixed build (the test server was rebuilt and restarted, the round restarted, the same Lua setup and a real lobby latejoin as Assistant):

- Chat: only "You are the Assistant."
- `dynamic.log`: only the `Latejoin (forced): Queued ruleset Latejoin Changeling failed to prepare! It remains queued for next latejoin.` line (once, as the queue held one copy this time); no "selected for" line.
- The queue still held the changeling ruleset after the join (a queue length of 1 was read before joining; the queue was not re-read afterwards, but the log message states it remains queued and the code path does not unqueue it).

Not checked: the positive path, where the queued ruleset has an eligible latejoiner and executes. That code was not changed and returns before the new check.

## Notes

- Behaviour change to weigh: while a latejoin ruleset that nobody can satisfy sits in the queue, no random latejoin antagonists roll at all, for any joiner, because every latejoin now fails the queued ruleset and returns early. Admins must dequeue it (the "REMOVE FROM QUEUE" link in the failure message) to restore random latejoin antagonists.
- The reporter's linked issue #31592 was said to be related; it was not examined.
- The reporter's exact symptom (forced Infiltrator giving a revhead) comes from an older Dynamic implementation and was not reproduced as such; the current-code equivalent is described above.
