# #85499: Polymorph belt re-rolls a magicarp's spell on every transformation

| | |
|---|---|

| Status | Fix committed and checked on the test server through admin tools; the real scan was not driven |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/85499 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The polymorph belt remembers only the mob type of what it scanned. A magicarp picks its spell (and with it its name and colour) at random in `Initialize`, so each transformation produced a magicarp with a new random spell instead of the scanned one. The fix makes the belt store the scanned magicarp's spell and apply it to the new form. Chaos magicarp, whose spell changes every cast, are unaffected.

## The bug

Scan a non-chaos magicarp with the belt and transform: you become a magicarp, but not necessarily one of the scanned kind. Scan something else, then the same carp again, and the belt turns you into a different type. The belt acts as though it only remembers "magicarp".

## Reproduction

1. On the test server, using the Lua editor, create a pre-activated polymorph belt (`/obj/item/polymorph_belt/functioning`) and set `stored_mob_type = /mob/living/basic/carp/magic`.
2. Call `update_transform_action()` on the belt.
3. Call `transform_action:create_shapeshift_mob()` five times.
4. Observed on master: the five forms were named "frigid", "vital", "grim", "blazing" and "quantum" magicarp, a different spell each time.

The real scan (the `do_after` on a living magicarp) was not driven; the stored mob type was set directly.

## Cause

`code/modules/clothing/belts/polymorph_belt.dm:13` holds only `stored_mob_type`, set on scan at `:91`. The transform action creates its form with `new shapeshift_type(loc)` (`create_shapeshift_mob`, `code/modules/spells/spell_types/shapeshift/_shapeshift.dm:194`). `/mob/living/basic/carp/magic/Initialize` (`code/modules/mob/living/basic/space_fauna/carp/magicarp.dm:78`) calls `assign_spell()` (`:81`), which picks a spell at random (`:93`, `pick(allowed_projectile_types)`). The "already scanned" check at `polymorph_belt.dm:80` also compares only the mob type.

## Fix

Commit "Fix issue 85499: Polymorph belt remembers the spell of a scanned magicarp":

- `polymorph_belt.dm`: new `stored_mob_spell`. A new `get_mob_spell()` returns the scanned magicarp's spell type (null for other mobs). It is stored on scan and passed to `update_type`.
- The "already scanned" check now compares the spell too, so scanning a magicarp of a different spell when another kind is stored is accepted.
- The belt's action gets `shapeshift_spell` and overrides `create_shapeshift_mob` to call the new `set_spell_type` on the resulting magicarp.
- `magicarp.dm`: new `get_spell_type()` (returns the spell's projectile type) and `set_spell_type()` (deletes the existing spell, resets the name, then calls `assign_spell`). `assign_spell` takes an optional spell type, defaulting to the random pick. `/chaos` returns null from `get_spell_type()` and its `assign_spell` accepts the new argument.

The alternative of storing a copy of the scanned mob was not tried. The chosen approach keeps the existing shapeshift code path.

## Verification

On the test server, with admin tools: `get_mob_spell` of a scanned carp returned `/obj/projectile/magic/door`. After the change, five forms created from the belt were all "unbarred magicarp", with the door spell and colour `#70ff25` (the same as the source), and the name was not doubled. `get_mob_spell` on a chaos magicarp returned null. The server log showed no runtimes.

Not checked: the actual scan by a player (progress bar and `do_after`), rescanning a different-spell magicarp in game, and the visual result of the colours.

## Notes

- The new comparison in the "already scanned" check means rescanning another spell of the same carp type now replaces the stored one, which seems to be what the report wants.
- Chaos magicarp are left alone because their spell changes on every cast.
