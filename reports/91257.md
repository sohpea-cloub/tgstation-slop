# #91257: Mechpads cannot send lifeforms even when the lifeform restriction is off

| | |
|---|---|
| Issues | [#91257](https://github.com/tgstation/tgstation/issues/91257): verified, fixed |
| Status | Fixed (verified in game through the console's `can_launch` and `try_launch` procs; the full console UI was not clicked through) |
| Fix branch | [fix/91257](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/91257) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The mechpad console refused to launch unless a mecha was standing on the pad ("detects no mecha on the pad"), whatever the state of the pads' lifeform restriction. Even past that check, the supply pod the pad spawns was set to carry mechs only, so a loose mob would not have been picked up. The fix lets the console launch when a living mob is on the pad and neither the source nor the destination pad is mech-only, and makes the pod accept mobs in that case.

## The bug

Mechpads have a "lifeform restriction wire" (toggled with wirecutters when the panel is open). The reporter cut it on two linked pads, stood on one, and tried to launch from the console. The console answered "No mecha detected on the pad" and nothing was sent. The pads could therefore never move a person, which is what the lifeform setting is meant to allow.

## Reproduction

On master, with admin tools, without clicking through the console UI:

1. Start a round and observe. In the Lua editor, create two `/obj/machinery/mechpad` on the same z-level a few tiles apart, and a `/obj/machinery/computer/mechpad` next to the first.
2. Call `connect_launchpad(pad1)` and `add_pad(pad2)` on the console.
3. Spawn a human on the first pad. No mech is present. Both pads have `mech_only = FALSE`, the default, which is the state the wire produces when cut.
4. Call `console.can_launch(human, pad2, TRUE)`.

Observed on master: it returns FALSE (the non-silent form prints "detects no mecha on the pad!"), so `try_launch` returns without doing anything. The reproduction used the procs directly; nobody used the console's UI.

## Cause

`/obj/machinery/computer/mechpad/proc/can_launch` (`code/game/machinery/computer/mechlaunchpad.dm:146`) looks for a `/obj/vehicle/sealed/mecha` on the source pad's turf and returns FALSE with the "no mecha" message if there is none (lines 163-166). The only lifeform check after that (line 168) concerns living things inside the mech. A lifeform standing alone on the pad could never pass.

Two further pieces would have failed even if that check were passed:

- `start_launch` (line 139) does `mech.setDir(SOUTH)` on the located mech without a null check, which would runtime with no mech.
- The pod used for mechpads (`code/game/machinery/mechlaunchpad.dm:68`, the mechpod's `reverse_option_list`) has `"Mobs"=FALSE`, so the pod does not pick up loose mobs. Only `"Mecha"=TRUE` is set.

The wire semantic itself was consistent with the examine text: `mech_only` is FALSE by default, which means lifeforms are allowed (`mechlaunchpad.dm:22` and `:46`).

## Fix

One commit, "Fix issue 91257: mechpads can send lifeforms standing on the pad", changes two files:

- In `can_launch`, when there is no mech, the console now looks for a `/mob/living` on the pad's turf. If there is none it fails with "detects no mecha or lifeforms on the pad!". If there is one but the source or destination pad is `mech_only`, it fails with "This pad does not allow lifeforms!" or "The target pad does not allow lifeforms!". Otherwise it allows the launch. The existing mech path is unchanged.
- `start_launch` uses `mech?.setDir(SOUTH)` and calls `connected_mechpad.launch(where, !connected_mechpad.mech_only && !where.mech_only)`.
- `/obj/machinery/mechpad/proc/launch` takes a new `with_lifeforms` argument (default FALSE) and passes `reverse_option_list` to `podspawn` with `"Mobs"` set from it, `"Mecha"=TRUE` and everything else FALSE.

The pod option is passed per launch instead of changing the mechpod's default, so a mech-only pad still never picks up mobs.

## Verification

On a rebuilt test server, using the same setup as above:

- Both pads allow lifeforms: `can_launch` returned TRUE.
- Destination pad `mech_only = TRUE`: FALSE. Source pad `mech_only = TRUE`: FALSE.
- `try_launch` with the human on the first pad: the launch animation and beep played, mortar and rocket-launch sounds were heard at the destination pad, and a look at the area afterwards showed the pods. The human had moved from the first pad to the other one.
- No new runtime appeared in the server log from this launch. The only runtime seen was an unrelated `area_beauty_updated` signal warning.

Not tested: a mech with a pilot, either with or without the destination restriction; the console UI itself; unpowered, broken, or open-panel pads (code unchanged); the actual wirecutter interaction on the pad.

## Notes

- Side effect to weigh: when both pads allow lifeforms, a launch with a mech now also takes loose mobs standing on the pad next to the mech, because the pod's mob option is on for that launch. Previously they were left behind. If that is not wanted, `with_lifeforms` could be limited to the no-mech case.
- Mobs sent this way travel in a supply pod; this uses the standard supply pod behavior and was not examined for other effects (for example on mobs buckled to something).
