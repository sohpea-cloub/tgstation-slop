## Summary

In 2023 a cyborg's RoboTact (the modular computer program shown from the cyborg's "Modular Interface" button) showed "NaN%" and "undefined" where charge and integrity should be, and the server logged `Cannot read null.stored` from RoboTact's `ui_data`. On master, `ui_data` no longer fails for a cyborg without a power cell, or for a cyborg whose AI was deleted: charge falls back to 0 out of 1, and an AI's destruction now unlinks its cyborgs first. The original round's exact scenario was not identified, so this is "not reproducible", not "proven fixed". No code was changed.

## The bug

The reporter was a cyborg, went through the gateway, came back and tried to charge in robotics. When they checked their integrity in RoboTact, the screen showed "NaN%" and "undefined" (the screenshot is only linked from the issue). A commenter pulled two runtime errors from the logs, both with the user being a `/mob/living/silicon/robot/nocell` (the type produced by building a cyborg from robot parts, which starts without a cell):

```
runtime error: Cannot read null.stored
proc name: ui data (/datum/computer_file/program/robotact/ui_data)
source file: code/modules/modular_computers/file_system/programs/robotact.dm,52
```

The commenter also noted the issue came after test merge #77307. When `ui_data` runtimes partway through, the UI receives an incomplete payload, which is the most likely way the interface ended up showing "undefined" and "NaN%" (this link is an inference, not something that was observed). The front end computes the charge bar as `charge / maxcharge` (`tgui/packages/tgui/interfaces/NtosRobotact.jsx`).

## Reproduction

Not reproduced. On master, on the test server, using the Lua editor and SDQL2:

1. Spawned a `/mob/living/silicon/robot/nocell`, found its RoboTact program in the modular interface's stored files and called `ui_data()` on it as that cyborg. The cyborg's `cell` was null, and its photo camera existed. `ui_data` returned `charge = 0`, `maxcharge = 1`, `integrity = 100`, `printerPictures = 0`. There is no NaN (0/1 is 0) and no runtime.
2. Turned a human into an AI (`AIize()`), spawned another cell-less cyborg, linked it to that AI by setting `connected_ai`, and called `ui_data()`. It returned normally (`printerPictures = 0`, one cyborg group).
3. Linked the cyborgs to the AI through `set_connected_ai()`, then deleted the AI with the SDQL2 query `DELETE /mob/living/silicon/ai`. The cyborgs' `connected_ai` was null afterwards, `ui_data()` still returned normally, and the runtime log contained nothing from RoboTact.

Not tested: opening RoboTact through the real button and looking at the rendered screen; the gateway or robotics-recharge sequence from the report; a cyborg whose `connected_ai` was set by a direct variable write and then had the AI deleted.

## Cause

The cause of the 2023 report was not confirmed. What master does now:

- Charge: `ui_data` (`code/modules/modular_computers/file_system/programs/robotact.dm:57-63`) starts with `charge = 0` and `maxcharge = 1` and only replaces them when `cyborg.cell` exists. A cell-less cyborg therefore reports 0/1 and the bar computes 0, not NaN. The reporting user was a `nocell` cyborg, and this guard is the likely answer to the "NaN%" half. Whether the 2023 code already had this guard was checked by the investigation and the answer was that it did, so the NaN in the screenshot probably came from the incomplete payload described above, not from a missing cell guard.
- Picture count: `robotact.dm:68` reads `cyborg.connected_ai ? cyborg.connected_ai.aicamera.stored.len : cyborg.aicamera.stored.len`. This is the line that would produce `Cannot read null.stored` if the AI's `aicamera` were already null. `/mob/living/silicon/Destroy()` does `QDEL_NULL(aicamera)` (`code/modules/mob/living/silicon/silicon.dm:87`), so a cyborg that still pointed at a destroyed AI would hit this. On master, `/mob/living/silicon/ai/Destroy()` (`code/modules/mob/living/silicon/ai/ai.dm:161-168`) now unlinks every cyborg in `connected_robots` with `set_connected_ai(null)` before the AI's resources are deleted, with the comment "Release linked cyborgs before deleting the resources they access through us". `set_connected_ai()` itself (`code/modules/mob/living/silicon/robot/robot.dm:994`) refuses to link to an AI that is already being deleted.
- That makes a dangling `connected_ai` the likely source of the 2023 runtime, since the reporter had been "in the gateway" with an AI around. The investigation could not confirm this against the original round, so it is a hypothesis.

Residual risk: line 68 has no null guard of its own (for example `connected_ai?.aicamera?.stored`). A cyborg whose `connected_ai` was written directly (bypassing `connected_robots`, so it is missed by the cleanup in `Destroy()`) could still produce the runtime. This is not reachable through normal play code that was found.

## Fix

None. No code was changed or committed.

## Verification

Nothing was fixed, so nothing to verify beyond the checks listed under Reproduction. The server's runtime log showed no RoboTact errors during those checks.

## Notes

- The issue is labelled "Needs Reproducing" and has had no new reports since 2023. It can reasonably be closed, or kept open only if someone wants the extra guard on `robotact.dm:68`.
- A defensive change (`cyborg.connected_ai?.aicamera?.stored?.len || cyborg.aicamera?.stored?.len`, or similar) would cost nothing and make the program robust against any other way a camera can be missing. It was not made because the failure could not be shown on master.
- Likewise `NtosRobotact.jsx` divides by `maxcharge`; the backend now always supplies at least 1, so it is only a problem if the payload is missing entirely.
