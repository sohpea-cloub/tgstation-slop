## Summary

None of the four reports reproduced as written on master: declining or timing out of a ghost role prompt gives the use back, an empty spawner leaves the ghost's mind alone, and an unready spider egg only prints a message. Testing the click flow did find a real bug that produces symptoms like #84859 and #76078: `attack_ghost()` reads `user.client` after the prompts, which sleep, so a ghost that is deleted or loses its client during the prompt (for example by re-entering its corpse) causes a runtime. The runtime leaves the spawner's use spent and the player's ckey stuck in the "trying to spawn" list, so the player can no longer use any spawner. The fix adds the missing checks and also changes the misleading "out of charges" message that other ghosts saw while a prompt held the use. A second, small change restores the ghost's mind if a spawner ever creates no mob (the cause suggested in #74041 and #90600).

## The bug

The four issues describe variations of "I clicked a ghost role spawner and something was lost":

- #84859: clicking a spawner and declining the prompt uses a charge; later the spawner says it is out of charges.
- #74041: after dying, clicking an out-of-charges spawner (blood spider eggs, carp portal) leaves the player unable to re-enter their body ("DNR'd"). A later comment suggests the mind is nulled in `create_from_ghost()` before `create()` runs, and `create()` can back out when a menu is closed, with nothing restoring the mind.
- #76078: if someone destroys the spider egg you are choosing from, you can no longer trigger any more eggs.
- #90600: clicking an unready spider egg as a ghost detaches the mind from the body (a log line "became a ." appears).

## Reproduction

All reproduction was done on master with admin tools. The Lua editor was used to create a human, give it the admin's ckey, kill it with `death()` and `ghostize(TRUE)` so that there is a ghost with a mind and a revivable corpse, and to spawn a one-use skeleton spawner (`/obj/effect/mob_spawn/ghost_role/human/skeleton`) and spider eggs (`/obj/effect/mob_spawn/ghost_role/spider/abnormal`, `ready = 1`). The ghost clicked the spawners through the normal click interface. The spider radial needs the ghost next to the egg (`require_near`).

### What did not reproduce

1. Click the one-use skeleton spawner and answer "No": `uses` went back to 1, the ghost's mind was kept.
2. Open the spider egg radial and pick "Close Menu": `uses` stayed 1, the mind was kept (#90600, #74041).
3. Click a spawner with `uses = 0`: only "This spawner is out of charges!" appeared; the mind and `can_reenter_corpse` were intact (#74041).
4. Click an egg that is not ready: only "... is not ready to hatch yet!" appeared; the mind was kept (#90600).
5. Delete an egg while the radial for it is open: nothing broke, and a second egg opened its radial normally afterwards (#76078 as written).

### What did reproduce

1. As above, make a ghost with a mind and a corpse. Have a one-use skeleton spawner next to it.
2. The ghost clicks the skeleton spawner. The prompt "Become a skeletal guardian? (Warning, You can no longer be revived!)" opens, and the spawner's `uses` drops to 0 while the prompt is open.
3. With the prompt still open, make the ghost re-enter its corpse from the Lua editor (`reenter_corpse()`), which deletes the ghost.
4. Observed: a runtime in the runtime log, `Cannot read null.prefs` in `attack_ghost` (`code/modules/mob_spawn/mob_spawn.dm:209`). The spawner's `uses` stayed 0 forever. Afterwards, clicking the skeleton spawner or an abnormal egg with that ckey did nothing at all, with no message, because the ckey was still in the static `ckeys_trying_to_spawn` list.
5. While a prompt is open the spawner's `uses` is 0, so by the code a second ghost clicking it is told "This spawner is out of charges!" (line 192), which is untrue. This is the closest match to #84859's "it says the spawner is out of charges". It was reasoned from the code and the `uses` value, not captured from a second player.

The ghost actually disconnecting was not tested; it goes through the same `user.client == null` path as the deleted ghost.

## Cause

`/obj/effect/mob_spawn/ghost_role/attack_ghost()` (`code/modules/mob_spawn/mob_spawn.dm:183`) is written so that the use is taken early and returned later if the spawn does not happen:

```dm
uses -= 1 // Remove a use EARLY to account for sleep / inputs
var/user_ckey = user.ckey
LAZYADD(ckeys_trying_to_spawn, user_ckey)
...
prompt_fail = tgui_alert(user, prompt, ..., timeout = 10 SECONDS) != "Yes"
var/species_pref = user.client.prefs.read_preference(...)   // line 209
...
if(prompt_fail || !can_ghost_take(user) || !create_from_ghost(user, apply_prefs, subtract_uses = FALSE))
	uses += 1
LAZYREMOVE(ckeys_trying_to_spawn, user_ckey)
```

`tgui_alert` sleeps. The code that follows assumes `user` still exists and still has a client. If the ghost was deleted or lost its client meanwhile, `user.client.prefs` runtimes. The proc is aborted, so `uses += 1` and `LAZYREMOVE(...)` never run: the use is lost for good and the ckey is stuck in the "already trying to spawn" list (`LAZYFIND(ckeys_trying_to_spawn, user.ckey)` at line 188 makes every later click return silently). That matches #76078's "can't actually trigger any more eggs" and #84859's lost charge. The other ghosts' "out of charges" message (line 192) is simply `uses <= 0` while a prompt is holding the use.

For #74041 and #90600: `create_from_ghost()` (line 256) sets `user.mind = null` before calling `create()` (lines 262-265), and nothing restores it when `create()` returns `CANCEL_SPAWN`. That could cut a ghost off from its body, but on master it cannot happen through the spider eggs any more: `pre_ghost_take()` (the spider radial, `code/modules/mob_spawn/ghost_roles/spider_roles.dm:201`) is called from `attack_ghost()` before `create_from_ghost()`, so the mind is not yet cleared when the radial is cancelled. Nothing in the tree currently returns `CANCEL_SPAWN`, so the missing restore is latent.

## Fix

Two commits.

**"Fix issue 84859: a ghost losing its client during a spawner prompt no longer burns the use or locks them out of spawners"** (`mob_spawn.dm`):

- After the first prompt, if `QDELETED(user)` or the user has no client, `prompt_fail` is set, so the species lookup (`user.client.prefs...`) is skipped and the normal path runs, which gives the use back and removes the ckey from `ckeys_trying_to_spawn`. The species preference defaults to human when the prompt failed.
- The same checks are added before `pre_ghost_take()` and before `create_from_ghost()`, since both can follow another sleep (the second prompt, the spider radial).
- A new variable `pending_takers` counts the ghosts currently answering a prompt for this spawner. It is incremented when a use is held and decremented at the end. While it is non-zero and the spawner has no uses left, the message is now "Someone else is deciding whether to take this spawner. Try again in a moment." instead of "This spawner is out of charges!".

The fix is deliberately local (guard after each sleep) and keeps the existing "reserve the use early" design, which exists to account for the sleeps in the prompts.

**"Fix issue 74041: restore the ghost's mind when a spawner creates no mob"** (`mob_spawn.dm`, `create_from_ghost()`): the ghost's previous mind is remembered, and if `create()` returned something that is not a mob (such as `CANCEL_SPAWN`) and the mind is still cleared on a ghost that still exists, the mind is put back. This addresses the cause proposed in the #74041 comment and is described in the commit as also covering #90600. It changes nothing for spawns that succeed.

## Verification

First commit (checked on the test server):

- The same sequence as the reproduction (prompt open, ghost re-enters its corpse): no runtime in the log. After the stale prompt timed out (10 seconds at most), the skeleton spawner's `uses` was back to 1, and a new ghost click opened the prompt again. Answering "Yes" spawned the skeleton normally ("By unknown powers, your skeletal remains have been reanimated!").
- The `pending_takers` counter was read through the Lua editor during these runs. The inputs do not record a second ghost actually seeing the new "Someone else is deciding" message, so that message is untested in game (listed below).
- Declining and Close Menu still return the use, as before.

Not verified:

- The second commit was not exercised in game. It only matters when `create()` returns `CANCEL_SPAWN` or another non-mob, and nothing on master does, so no scenario was available to trigger it.
- A ghost that actually disconnects during the prompt (assumed equivalent to the deleted-ghost test).
- The "Someone else is deciding whether to take this spawner" message, as seen by a second ghost while a prompt is open.
- Real egg destruction during selection combined with the fix (the combination of the stuck ckey and egg deletion was not tested together).

## Notes

- #84859 itself, and the other three, could not be reproduced as written on master. A maintainer's comment on #84859 also says it could not be reproduced. The fix is for the closest real bug found in the click flow, not for a confirmed instance of the reported report; it is reasonable to treat #84859 and #76078 as "possibly this" rather than certainly resolved.
- #90600 already has a reply from a maintainer that the "became a ." log line is a separate issue: spider eggs have no `prompt_name`, so the line is printed regardless. That was not changed.
- The change to the out-of-charges message is a small behaviour change that is separate from the bug: it only applies while a prompt holds the use.
- Other open work touching `special()` in the same file may conflict textually, but the hunks here are only in `attack_ghost()` and `create_from_ghost()`.
