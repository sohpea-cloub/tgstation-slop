## Summary

The issue (March 2022) says the linear sustain duration of a pAI's music synthesizer does not accept decimal values, the same as #64992. On master, a pAI opens the same tgui `InstrumentEditor` as every other instrument, and decimal durations (0.5, 1.5, 0.3, 0.2) were stored correctly, in deciseconds, when sent through the editor's `edit_sustain_mode` action. The one thing not tested was typing a value into the number box with a real browser client. A separate, minor display bug (the Linear mode's maximum is shown as 50 seconds while the real limit is 5 seconds) was noticed and is not specific to pAIs.

## The bug

As reported: in the pAI music synthesizer, setting "Linear Sustain Duration" to a decimal such as 0.5 did not work, so only whole seconds could be used. The reporter said it was "exactly the same issue" as #64992 (instrument linear sustain not playing nice with decimal numbers) and, after #65008 was meant to fix that, said the pAI still did not work and suspected "pAI code is different". The issue was later closed as a duplicate of #64992.

## Reproduction

I could not reproduce it. What was done, on a test server with admin tools:

1. Started a round and observed as a ghost.
2. In the Lua editor, created a pAI on the admin's tile (`SS13.new('/mob/living/silicon/pai', loc)`). It makes its own card. Gave it the synthesizer with `buy_software('Music Synthesizer')` (this creates the `piano_synth` instrument inside the pAI), then moved into the pAI by assigning the admin's ckey to it. The mob was `/mob/living/silicon/pai`, inside a "personal AI device".
3. As the pAI, pressed the "Software Interface" HUD button and then "Music Synthesizer" in the pAI Software Interface. This opened the `InstrumentEditor` window titled "synthesizer", for the song type `/datum/song/handheld`.
4. The editor opened in Linear mode showing a duration of 0.5 (the default `sustain_linear_duration` of 5 deciseconds), with minimum 0.1 and maximum 50.
5. Sent the editor's `edit_sustain_mode` action with `amount` set to 1.5, 0.3, 0.5 and 0.2 in turn. Each time the value shown by the window changed to exactly the value sent.
6. Read the stored value back with the Lua editor (`usr.instrument.song.sustain_linear_duration`): after sending 0.5 it was 5, and after sending 0.2 it was 2 (deciseconds). The 1.5 and 0.3 values were seen only in the window's data, not read back from the song.
7. Switched to Exponential mode with `set_sustain_mode` and sent 1.25 as the falloff factor; the window showed 1.25.

The runtime log had no instrument-, song- or pAI-related entries.

Limits of this test: the actions were sent to the window directly, not by typing in the number box, and the audible effect of the changed sustain was not checked. The stored value is what was checked.

## Cause

The old failure is no longer present, so no current defect was found. The code path on master is:

- `/datum/song/ui_interact()` opens `InstrumentEditor` for everyone (`code/modules/instruments/songs/editor.dm:1-5`). pAIs only differ in `ui_state()`, which returns `GLOB.always_state` for them (`editor.dm:10-12`), so the window stays usable although the pAI is inside its card.
- The pAI's synthesizer is an ordinary instrument: `var/obj/item/instrument/piano_synth/instrument` (`code/modules/pai/pai.dm:72`), created by the software purchase (`code/modules/pai/software.dm:121-122`) and opened with `instrument.interact(src)` (`software.dm:71-72`). `/obj/item/instrument/ui_interact()` just calls `song.ui_interact(user)` (`code/modules/instruments/items.dm:45-46`). There is no separate pAI input path left.
- `edit_sustain_mode` takes `params["amount"]`, checks that it is a number and passes it straight to `set_linear_falloff_duration()` (`editor.dm:185-193`).
- `set_linear_falloff_duration()` stores `clamp(round(duration * 10, world.tick_lag), world.tick_lag, INSTRUMENT_MAX_TOTAL_SUSTAIN)` (`code/modules/instruments/songs/_song.dm:399-401`). Decimals are kept and rounded only to the server tick (0.5 ds in the test; `world.tick_lag` read as 0.5).
- On the client side, the number box in `tgui/packages/tgui/interfaces/InstrumentEditor.tsx:212-222` uses `step={1}`. In the installed tgui-core (6.1.1), typed values are parsed with `parseFloat` and only clamped to the minimum and maximum; only dragging snaps to the step. So a typed decimal should be sent unrounded. This was read from the library source, not run in a browser.

Whatever broke the input in 2022 (the issue's thread points to #65008, "Fixes the inputs for the linear and exponential sustain settings") appears to have been removed when instruments moved to this single tgui editor. It is not known from these inputs why the reporter still saw the problem after #65008 in April 2022; they said they thought pAI code was different, which no longer applies to master.

## Fix

None needed for the reported symptom; no commits.

## Verification

Checked on master as described under Reproduction: decimal linear sustain values sent through the pAI's editor were accepted and stored (5 and 2 deciseconds read back for 0.5 and 0.2; the others were reflected in the window's data), and an exponential value of 1.25 was accepted.

Not checked: typing a value into the number box in a real client, dragging the value, and hearing the result. Also not checked on the BYOND version (514.1578) the reporter used.

## Notes

- Minor display bug, not pAI-specific and not part of this issue. In Linear mode, `ui_data()` sends the duration in seconds (`sustain_linear_duration / 10`) but sends `INSTRUMENT_MAX_TOTAL_SUSTAIN` unchanged as the maximum (`editor.dm:24-27`). That define is in deciseconds (`5 SECONDS` = 50, `code/__DEFINES/instruments.dm:12`), so the box is labelled "(in seconds)" with a maximum of 50 while the server clamps to 5 seconds. The window showed `sustain_mode_max` 50 in Linear mode (and 10 in Exponential mode) during the test. The effect on a typed value above 5 (it is accepted by the box, then clamped by the server) follows from the code and was not tried.
- Related: #64992 (the issue this duplicates), #65008 (the earlier fix), and the instrument settings group around #91554 and #81416.
- Suggested disposition: close as fixed/duplicate of #64992, and open or fold the max-sustain display mismatch into the instrument settings issue.
