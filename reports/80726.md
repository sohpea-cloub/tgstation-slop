# #80726: Gravity-negating mobs (cyborgs, drones, magboots) don't magnetize to a floor tile placed under them

| | |
|---|---|
| Issues | [#80726](https://github.com/tgstation/tgstation/issues/80726): verified, fixed. [#83071](https://github.com/tgstation/tgstation/issues/83071): duplicate of #80726 (same cause), fixed by the same commit |
| Status | Fixed and checked in game (with the limits listed under Verification) |
| Fix branch | [fix/80726](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/80726) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

A mob with `TRAIT_NEGATES_GRAVITY` (magboots, drones, the engineering and mining cyborg models, repair bots) only becomes "magnetized" to the ground when it moves, because the check that grants the magnetized state lives in `/mob/living/Moved()`. When a floor tile is built under a mob that is standing still on a lattice or in space, `ChangeTurf()` refreshes the mob's gravity but never re-evaluates that check, so the mob keeps floating until it steps off and back on. The fix moves the check into a new proc, `update_gravity_negation()`, called from `Moved()` and from the mob loop in `ChangeTurf()`, so it also runs when the turf under a stationary mob changes (in either direction).

## The bug

#80726: a cyborg floating over a lattice in space places a floor tile under itself and stays weightless. It has to step off the tile and back on before the game treats it as magnetized. The reporter expects magboots to behave the same way, and notes this can leave a player weightless on a surface of floor tiles with nothing to push off.

#83071 is the same defect seen with drones. A drone that covered a lattice with a floor tile while floating stayed stuck in the no-gravity state even though it was on a floor tile. Drones cannot throw anything to push themselves, so they cannot recover without help. The second remark in that issue (a drone moving onto a space tile next to a solid is still stuck) is ordinary space drift, not part of this bug.

What happens internally: whether a mob "ignores" gravity because it is magnetized is stored as `TRAIT_IGNORING_GRAVITY` with the source `IGNORING_GRAVITY_NEGATION`, and `mob_negates_gravity()` reads exactly that trait. The trait is added or removed only when the mob moves. If the turf under a stationary mob is replaced, the trait is stale.

## Reproduction

The reproduction was done with admin tools by calling the same proc the tile item calls, not by clicking a floor tile with a real cyborg (see Verification).

1. On a test server on master, as an observer, open the Lua editor.
2. Spawn two `/obj/structure/lattice` on open space tiles, side by side.
3. Spawn a `/mob/living/carbon/human` on one lattice and give it `TRAIT_NEGATES_GRAVITY` (a stand-in for magboots). Spawn a `/mob/living/basic/drone` (which has the trait innately) on the other.
4. Print each mob's `gravity_state` and `mob_negates_gravity()`. Both were `0` and `false`, as expected on a groundless turf.
5. Call `place_on_top(/turf/open/floor/plating)` on each turf. This is what `/obj/item/stack/tile/proc/place_tile()` does (`code/game/objects/items/stacks/tiles/tile_types.dm:85`) when a tile is built over a lattice.
6. Print the same values again.

Observed before the fix: both mobs stood on `/turf/open/floor/plating` with `gravity_state` 0 and `mob_negates_gravity()` false. Calling `forceMove` to move each mob off the tile and back onto it changed both to `gravity_state` 1 and `mob_negates_gravity()` true, which is the "step off and back on" behaviour from the issue.

## Cause

`code/modules/mob/living/living_movement.dm:4-8`, in `/mob/living/Moved()`, was the only place that set the trait:

```dm
if(HAS_TRAIT(src, TRAIT_NEGATES_GRAVITY))
	if(!isgroundlessturf(loc))
		ADD_TRAIT(src, TRAIT_IGNORING_GRAVITY, IGNORING_GRAVITY_NEGATION)
	else
		REMOVE_TRAIT(src, TRAIT_IGNORING_GRAVITY, IGNORING_GRAVITY_NEGATION)
```

The other place that handles this trait, `on_negate_gravity()` in `code/modules/mob/living/init_signals.dm:293`, runs only when `TRAIT_NEGATES_GRAVITY` itself is gained or lost, not when the turf changes.

When a turf is replaced, `ChangeTurf()` (`code/game/turfs/change_turf.dm:207-208`) loops over the living mobs on the new turf:

```dm
for(var/mob/living/target in new_turf.contents)
	target.refresh_gravity()
```

`refresh_gravity()` (`living_movement.dm:42`) recomputes `gravity_state` and nothing more. It does not touch `TRAIT_IGNORING_GRAVITY`, and no other code on this path re-runs the check from `Moved()`, so a mob that does not move keeps the stale trait. In the reproduction `gravity_state` and `mob_negates_gravity()` stayed at 0 and false after the tile was placed and changed to 1 and true after the mob was moved off and back on. The exact way `gravity_state` depends on the trait in this case was not traced; what was confirmed is that the trait going stale is the defect, because the fix makes both values correct without any movement.

## Fix

One commit on `fix/80726`, "Fix issue 80726: refresh gravity negation when the turf under a mob changes":

- `code/modules/mob/living/living_movement.dm`: the check from `Moved()` became a new proc, `/mob/living/proc/update_gravity_negation()`, which adds `TRAIT_IGNORING_GRAVITY` (source `IGNORING_GRAVITY_NEGATION`) if the mob has `TRAIT_NEGATES_GRAVITY` and is not on a groundless turf, and removes it otherwise. `Moved()` now calls it.
- `code/game/turfs/change_turf.dm`: the mob loop in `ChangeTurf()` calls `target.update_gravity_negation()` before `target.refresh_gravity()`. The trait is set first so that the refresh that follows sees the updated state.

This approach keeps a single definition of the rule and reuses the existing hook that already runs for every mob when a turf is created or destroyed. Patching only the tile-placing code (`place_tile()`) would have fixed the reported case, but any other code that replaces the turf under a mob would still leave the trait stale, and `ChangeTurf()` is where turf replacements pass through.

## Verification

After rebuilding with the fix, the same Lua editor setup was run: lattices on open space, a human with `TRAIT_NEGATES_GRAVITY`, a drone, then `place_on_top(/turf/open/floor/plating)` under each, then the floor replaced by open space again with `ChangeTurf`.

| Step | Human | Drone |
|---|---|---|
| On lattice over space | `gravity_state` 0, negates false | `gravity_state` 0, negates false |
| After the floor tile is placed | `gravity_state` 1, negates true | `gravity_state` 1, negates true |
| After the floor is replaced by space | `gravity_state` 0, negates false | `gravity_state` 0, negates false |

So both mobs magnetized immediately without moving, and released again when the ground was removed. No runtime errors appeared in the runtime log of the verification round.

Not checked:

- A real cyborg with the engineering or mining model. The trait and code path are the same as for the drone and the human, but no cyborg was spawned.
- Real magboots worn and toggled. A directly granted `TRAIT_NEGATES_GRAVITY` stood in for them.
- Placing the tile with an actual click. The attempts to call the item interaction and `build_with_floor_tiles` from the Lua editor did not place a tile, so `place_on_top()` was called directly, which is the call `place_tile()` makes.
- Other ways the turf can change under a mob (for example a floor destroyed by an explosion) were not tested separately; only the tile-placed and floor-replaced-by-space directions were.

## Notes

- `update_gravity_negation()` also removes the trait when the mob does not have `TRAIT_NEGATES_GRAVITY`, where the old code did nothing in that case. The removal is scoped to the `IGNORING_GRAVITY_NEGATION` source, so it cannot take away `TRAIT_IGNORING_GRAVITY` from other sources (for example the flight shoes in `code/datums/actions/items/flight.dm`). It is a no-op for mobs that never had the trait.
- `on_negate_gravity()` in `init_signals.dm` implements a similar rule for the gained/lost-trait case. It was left alone, but a maintainer could make it call the new proc to keep a single copy of the rule. Its handling differs slightly (it does nothing at all on a groundless turf), so this was not folded in here.
- One commenter on #80726 suggested the problem was about areas and lighting. Nothing observed pointed that way: the stale state was the trait, and it was fixed without touching areas.
- No upstream PR fixing this was identified in the inputs.
