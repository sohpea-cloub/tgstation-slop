## Summary

When something enters a bitrunning domain's send (goal) turf, the quantum server first looks for a byteforge with `oview()`, which needs line of sight, and then calls `pick()` on the result. If anything opaque is between the server and every forge, the list is empty, `pick()` runtimes, the cache's move is aborted and no reward is given until a later attempt. The fix looks for forges with `range()`, returns null when there are none, checks the arriving atom's type before searching, and shows an alert if no forge is linked. A second defect in the same handler was also fixed: the server's goal-turf signal registrations were never removed when a domain was unloaded, and from the second load of a domain on the wrong reservation was released.

## The bug

Players dragging or pushing the encrypted cache onto the "cache goal" marker see nothing happen, and have to try again (moving it onto and off the turf, or onto the other goal tile) until it works. The reporter's round logged `pick() from empty list` in `get_random_nearby_forge` (`code/modules/bitrunning/server/util.dm`, line 86) with the stack going from the cache's `Move` through `atom_entered` into `on_goal_turf_entered`. The runtime aborts the entering `Move`, so the cache stays on the turf. #85080 reports the same "not registered until I wiggled the cache" on an earlier version, plus a "ghost cache" that players could stand on after delivery.

## Reproduction

On master, on a station with a quantum server and byteforge, using the Lua editor as an observer:

1. Give the quantum server points and load the `clown_planet` domain (the test used `points = 100` and `cold_boot_map('clown_planet', 0)`).
2. Spawn a human in the domain's safehouse and give a player control of it. Spawn an encrypted cache (`/obj/structure/closet/crate/secure/bitrunning/encrypted`) and push it onto a goal turf with ordinary moves. This follows the same code path as the reporter's stack: `Move`, `Entered`, `atom_entered` signal, `on_goal_turf_entered`.
3. Control: with nothing in the way, the push delivered the reward (sparks, cache deleted).
4. Darkness is not the cause: with `luminosity` 0 on every turf within 6 tiles of the server and the byteforge moved 2, 3 and 4 tiles away, the forge was still in `oview` and still picked, both when called from Lua and with a real push.
5. Place opaque objects (`/obj/structure/fluff` with `opacity = 1`) on the tiles between the server and the forge. `oview(4, server)` then no longer contained the forge. Pushing the cache onto the goal turf left the cache there, gave no reward, and logged:

   ```
   RUNTIME: runtime error: pick() from empty list
    - proc name: get random nearby forge (/obj/machinery/quantum_server/proc/get_random_nearby_forge)
    -   source file: code/modules/bitrunning/server/util.dm,86
    - the quantum server: on goal turf entered(...)
    - the circuit floor: SendSignal("atom_entered", ...)
    - the encrypted cache: Move(...)
   ```

   This is the same stack as the issue's. Trying again after the view cleared worked, which fits "dragged it over both tiles a few times before it finally triggered".

The reported round was on Wawastation (server at 67,106 on z3; the issue's `src.loc` matches). Wawastation is no longer in the repo at the tested commit, so that room could not be tested, and what blocked the view in that round is unknown. Another thing that could not be shown is whether the second defect below played a part in that round.

For the second defect (the unloaded domain's handler staying on reused turfs): load `clown_planet`, reset the server, then inspect the old goal turfs' signal listeners (through the `_listen_lookup` var). After `reset()`, the released space turfs of the old goal tiles still had the server's `atom_entered` handler. A second server loading the same domain and being reset left its domain loaded and its handler on its goal turfs.

#85080's "ghost cache": after a pushed delivery on the tested master, the goal turf had no `TRAIT_ELEVATED_TURF` and the human standing on it had `pixel_z` 0, so the described ghost cache did not reproduce. Whether it needs a different map, multiple forges or something else was not determined.

## Cause

- `get_random_nearby_forge()` (`code/modules/bitrunning/server/util.dm:80-86`) collects forges with `oview(MAX_DISTANCE, src)` (distance 4). `oview` only returns what the server can see, so an opaque object between the server and the forge empties the list, and `pick(nearby_forges)` on an empty list is a runtime.
- `on_goal_turf_entered()` (`code/modules/bitrunning/server/signal_handlers.dm:34-37`) called `get_random_nearby_forge()` first, for every atom that enters a goal turf, and only afterwards checked what had entered (glitch mob, cache, curiosity lockbox). Any atom entering a goal turf could therefore trigger the runtime.
- `SIGNAL_HANDLER`s run inside `SendSignal`, and a runtime in one aborts the dispatch to the remaining listeners, including the `Entered` that finishes the move.
- `scrub_vdom()` (`code/modules/bitrunning/server/map_handling.dm:222-228`) released `generated_domain.reservations[1]`. That list belongs to the shared domain datum, keeps every past load of the domain by any server, and so does not necessarily contain the live reservation: from the second load onward the live one was not released. It also never unregistered `COMSIG_ATOM_ENTERED` / `COMSIG_ATOM_EXAMINE` from the goal turfs (registered in `load_map_items`, lines 150-152). `ChangeTurf` keeps signal registrations, so released turfs that later reservations reuse kept the old server's handler.

## Fix

Two commits.

**"Fix issue 93639: find byteforges without line of sight, no runtime when there are none"**
- `get_random_nearby_forge()` uses `range()` instead of `oview()` and returns null when no forge is found.
- `on_goal_turf_entered()` first checks the arrival's type (encrypted cache, encrypted curiosity lockbox, or an emagged-server glitch mob), returning immediately if it is none of them, and only then looks for a forge. If there is no forge it shows a "no byteforge linked!" balloon alert for the cache and lockbox cases.

`range()` was chosen so that line of sight (smoke, an opaque object) no longer decides delivery. The tradeoff: `range()` also finds a forge behind a wall within 4 tiles; this was judged acceptable.

**"Fix issue 93639: unregister goal turfs and release the server's own domain reservation"**
- New server vars `goal_turfs` and `domain_reservation` (set from the return value of `lazy_load()`; `goal_turfs` was previously a local variable of `load_map_items`).
- `scrub_vdom()` unregisters both signals on each goal turf, removes the server's own reservation from the shared list and deletes it (whose `Destroy` releases it).

## Verification

On a rebuilt test server, in a fresh round, with the same blockers in place (`forge in oview` was 0):

- Pushing the cache onto a goal turf delivered the reward: sparks, points went from 99 to 102, `domain_complete` was 1; no `pick()` runtime.
- After `reset()`: the goal turfs' `atom_entered` listener went from the quantum server to nothing, `goal_turfs` was empty, `domain_reservation` was null, and the domain had no reservations.
- Loading and resetting `clown_planet` two more times (it landed at different places each time): one reservation while loaded, none after reset, no listener left, and `SSmapping.turf_reservations` was back at its baseline of 1.
- The only other runtimes in the round were unrelated or caused by the test: null `moles` from delivery chutes in the safehouse templates, and "Mob with client has been deleted" for the possessed test human, which was wiped with the reservation.

Not checked: the glitch-mob (emagged server) and curiosity lockbox paths of the handler after the rewrite; the "no byteforge linked!" alert in game; maps with several forges; Wawastation or the actual round of the report; a real client dragging the crate (the push used a possessed mob's normal moves).

## Notes

- `code/modules/bitrunning/netpod/utils.dm:126` has the same pattern: `find_server()` uses `locate(/obj/machinery/quantum_server) in oview(4, src)` (line of sight again). Not changed.
- `quantum_server/Destroy` does `QDEL_NULL(generated_domain)` on a domain datum that is shared through the bitrunning subsystem; the lazy template refuses a non-forced qdel, which gives a stack trace. Not changed.
- No upstream PR for #93639, #85080 or `get_random_nearby_forge` was found.
- The "ghost cache" in #85080 may have been a version-specific issue, or may need a setup that was not tried.
