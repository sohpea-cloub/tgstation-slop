# #84233: Infrared emitter assemblies stop triggering after being picked up or moved

| | |
|---|---|
| Issues | [#84233](https://github.com/tgstation/tgstation/issues/84233): verified, fixed. [#96868](https://github.com/tgstation/tgstation/issues/96868): duplicate of #84233 for the attached case (confirmed, fixed); the standalone case it also describes did not reproduce |
| Status | Fixed on the branch, verified in game for infrared emitter + igniter holders and for a transfer valve with an infrared emitter |
| Fix branch | [fix/84233](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/84233) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

An infrared emitter that sits inside an assembly holder (emitter + igniter) or on a transfer valve only rebuilt its beam when its own direction changed. Picking the holder up, dropping it, or moving it left the beam stale or empty, so the emitter never saw anything cross it until someone rotated it. On a transfer valve there was a second problem: dropping the valve made the attached device's `dropped()` runtime, which aborted the beam rebuild as well. The fix rebuilds the beam whenever the holder moves, makes the assembly holder notify its assemblies when it moves, and passes the user through the transfer valve's `dropped()`.

## The bug

Both issues describe the same symptom. A player builds an infrared emitter + igniter assembly (or attaches an emitter to a transfer valve for a tank bomb), turns the emitter on, and it does not trigger. #84233 adds, in a comment, that the beam shows when the assembly is first created but misbehaves when dragged and stops working once the assembly is picked up, that alt-click rotating the assembly brings the beam back until the next pickup, and that throwing the assembly no longer makes the beam spin. #96868 says infrared assemblies "just don't trigger", standalone or attached to tanks or beakers, and a comment says they start working after being rotated.

What happens: the beam is drawn from the holder, not from the emitter, toward a fixed target turf. When the holder is carried somewhere else, nothing redraws it, so the beam either points at the old place or does not exist.

## Reproduction

All steps were done on master with the Lua editor on the test server; the humans were placed in the beam with `forceMove`, and "triggered" means the emitter's `next_activate` changed.

1. Standalone emitter (control): spawn an `/obj/item/assembly/infra`, set `secured = TRUE`, call `toggle_on()` (and `toggle_visible()`). Move a human into the beam. It triggered when fresh, after being picked up and dropped, and after being carried to another spot. Standalone emitters were therefore not broken, which does not match the standalone claim in #96868.
2. Emitter + igniter holder: spawn an infrared emitter and an igniter (both unsecured), combine them with `/obj/item/assembly_holder/assemble()`, and call `toggle_on()` on the emitter. The beam was built (6 elements) and a human walking into it triggered the emitter, so a freshly built holder works, as the issue says.
3. Put the holder in a mob's hands (`put_in_hands`), then drop it (`dropItemToGround`). The emitter's `active_beam` stayed in place with 0 elements, and a human moved into the line did not trigger it (`triggered = false`). Calling `setDir` on the holder (what alt-click rotation does) brought the beam back, which matches the comments in both issues.
4. Transfer valve: spawn a transfer valve and attach an infrared emitter with `try_attach_assembly`. Pick up and drop the valve. The drop produced a runtime, `Cannot read null._listen_lookup` at `code/game/objects/items.dm:713`.

Not reproduced: the standalone case in #96868, and the "throwing the emitter spins the beam" behaviour, which was not tested (see Verification).

## Cause

Three separate gaps combine.

1. `code/modules/assembly/infrared.dm:261`: the only code path that rebuilds the beam for a held emitter is `holder_movement()` (inherited from `code/modules/assembly/assembly.dm:70`), which just calls `setDir(holder.dir)`. `/obj/item/assembly/infra/setDir()` only calls `make_beam()` when the direction actually changed:

   ```dm
   /obj/item/assembly/infra/setDir(newdir)
   	var/prev_dir = dir
   	. = ..()
   	if(dir == prev_dir)
   		return
   	make_beam()
   ```

   So if the holder moves but keeps its direction, the beam is not rebuilt. The `Moved()` override on the emitter (line 250) fires when the emitter itself moves, not when its holder does, and the beam's origin is the holder (`var/atom/start_loc = holder || src`, line 91).

2. `code/modules/assembly/holder.dm`: `/obj/item/assembly_holder` calls `holder_movement()` on its assemblies from `setDir()` (line 131) and calls `dropped()` on them (line 136), but has no `Moved()`, so plain movement of the holder never reaches the emitter. (The transfer valve does forward `Move()`, `code/game/objects/items/devices/transfer_valve.dm:195`.)

3. `code/game/objects/items/devices/transfer_valve.dm:200`: `/obj/item/transfer_valve/dropped()` takes no arguments and calls `attached_device.dropped()` with no user. `/obj/item/dropped()` then runs `SEND_SIGNAL(user, COMSIG_MOB_DROPPED_ITEM, src)` (`code/game/objects/items.dm:713`) with `user` null, which runtimes ("Cannot read null._listen_lookup") before the emitter's own `dropped()` can run `holder_movement()`. For the transfer valve this means the beam was never rebuilt on drop.

## Fix

One commit, "Fix issue 84233: infrared assemblies stop working after being picked up or moved while attached", touching three files:

- `code/modules/assembly/infrared.dm`: new `/obj/item/assembly/infra/holder_movement()`. It calls the parent and, if the parent succeeded (there is a holder) and the direction did not change, calls `make_beam()`. If the direction did change, `setDir()` has already rebuilt the beam, so it is not rebuilt twice.
- `code/modules/assembly/holder.dm`: new `/obj/item/assembly_holder/Moved()` that calls `holder_movement()` on every assembly in the holder, so any movement of the holder (pickup, drop, throw, pulling) refreshes the beam.
- `code/game/objects/items/devices/transfer_valve.dm`: `dropped()` now takes `(mob/user, silent = FALSE)` and calls `attached_device.dropped(user, TRUE)`. Passing the user removes the runtime. `silent = TRUE` avoids a second drop sound for the attached device.

The alternative of overriding only the emitter's `dropped()` would not have covered dragging or throwing a holder, and would not have fixed the transfer valve runtime, so the fix goes through `holder_movement()`, which is the existing hook for this.

## Verification

Checked on the test server with the fix applied, using the same Lua editor method:

- Emitter + igniter holder, picked up and dropped: the beam had 6 elements after the drop and a human moved into it triggered the emitter (`triggered = true`).
- The same holder carried to a new spot: triggered.
- The holder moved step by step with `Move()`: triggered.
- Transfer valve + emitter: held, the beam had 0 elements; dropped, 6 elements; a human walking into the beam opened the valve (`triggered = true`). No runtime appeared in the runtime log.
- Standalone emitter after the fix: still works (also worked before the fix).

Not checked:

- Thrown assemblies. The old behaviour mentioned in #84233 (the emitter spinning when thrown) is not restored by this change; holders have `set_dir_on_move = FALSE`, so a thrown holder gets a rebuilt beam at its new position but does not spin.
- Beaker and grenade holders (the "attached to beakers" part of #96868); only the assembly holder and the transfer valve were tried.
- The beam glide animation for holders: when the holder moves, the beam now snaps to the new position instead of gliding as it does for a standalone emitter. The standalone glide code was not changed.
- Real player actions (clicking, alt-click, dragging with the mouse). Everything was done by calling the equivalent procs through the Lua editor.

## Notes

- #96868 is a duplicate for the attached case. Its "standalone assemblies" claim did not reproduce on master, before or after the fix (tested fresh, after pickup and drop, and after being carried elsewhere). If standalone failures exist, they likely come from a different path, for example a rotated or otherwise unusual starting state; this was not investigated.
- The Lua editor crashed the test server twice during testing ("Crashing due to an illegal operation" in `lua_state.dm`, `resume`), when a script waited (`SS13.wait`) around an igniter pulse, and after a runtime in a proc called from Lua. This looks unrelated to the bug (probably the Lua library or the patched BYOND in the test environment) and was avoided afterwards by using scripts that do not wait.
- The `silent = TRUE` in the transfer valve change only suppresses the attached device's drop sound; the valve's own drop sound still plays.
