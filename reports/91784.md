## Summary

All three issues come from the time stop field (`code/datums/proximity_monitor/fields/timestop.dm`). Frozen things get `move_resist = INFINITY`, so even a time-stop-immune wizard cannot pull them (#91784), and moving a frozen thing unfreezes it. Overlapping fields share one global record of frozen atoms, so when the first field ends it releases atoms the second field should still hold (#48939). A wizard who shapeshifts inside their own field is frozen because the new body enters the field before it receives the immunity (#49268). The fix lets immune pullers pull frozen things without unfreezing them, makes a surviving field take over atoms from an ended one, and releases a frozen atom when it gains time stop immunity.

## #91784: You can't grab people in stopped time

### The bug

After casting Time Stop, the wizard can attack frozen mobs but cannot grab or pull them, nor pull frozen objects such as lockers, so grab-based interactions are impossible. The issue thread disagrees on whether this is intended (one commenter held that frozen things should not be movable at all; the reporter held that the caster should be able to). The issue carries the "Consistency Issue" label rather than "Bug". The fix takes the reporter's side; a maintainer may want to confirm that is the intended design.

### Reproduction

On master, with the Lua editor:

1. Spawn a wizard-type human with the Time Stop spell (`/datum/action/cooldown/spell/timestop`), spell requirements disabled and a long `timestop_duration` (1200 was used, i.e. 120 s). Spawn a monkey and a locker next to it.
2. Trigger the spell.
3. Observed: the monkey's `move_resist` was `INFINITY`, and `wizard:start_pulling(monkey)` returned 0. Pulling the locker also failed.

This was done by calling `start_pulling` from Lua rather than through the in-game grab action.

### Cause

`freeze_atom` sets `A.move_resist = INFINITY` (`timestop.dm:121`). `can_be_pulled` refuses when `force < move_resist * MOVE_FORCE_PULL_RATIO` (`code/game/atoms_movable.dm:1739`), which can never hold for an infinite `move_resist`. Two more checks compare the raw value: `Move_Pulled` (`atoms_movable.dm:621`) and `Moving` (`atoms_movable.dm:657`) use `pulling.move_resist > move_force`, which would break an established pull on the first step. Finally, frozen atoms are registered with `COMSIG_MOVABLE_PRE_MOVE` -> `unfreeze_atom` (`timestop.dm:124`), so dragging one would unfreeze it.

### Fix

Commit "Fix issue 91784: immune wizards can pull things frozen by time stop" (one commit for all three issues, since they share `timestop.dm`):

- New `/atom/movable/proc/get_pull_resistance(puller)` in `atoms_movable.dm`. For a frozen atom (`move_resist == INFINITY` and held by a time stop field) whose puller is immune, it returns the pre-freeze `move_resist` that the field had saved in `frozen_things`; otherwise it returns `move_resist`. `can_be_pulled` and the two `pulling.move_resist > move_force` checks now use it.
- New `can_pull_frozen(puller)` on the field: true if the puller is in the field's `immune` list or has `TRAIT_TIME_STOP_IMMUNE`.
- The `PRE_MOVE` handler is now `frozen_atom_pre_move`, which does nothing when the atom's `pulledby` can pull frozen things, and unfreezes it otherwise. A pulled victim therefore stays frozen while dragged, including outside the field, until the field ends.

### Verification

On the test server, with the wizard possessed by an admin so it could move normally:

- `start_pulling(monkey)` returned 1. After the wizard moved south and then three steps west, the pulled monkey followed each time, and its `move_resist` stayed at the frozen value (`1e31`).
- A non-immune human calling `start_pulling` on the frozen monkey returned 0.
- Re-pulling after releasing returned 1, and a locker could be pulled.

Not checked: grab (aggressive grab) states and interactions that need them, and pulling frozen objects other than a locker.

## #48939: You can't keep someone frozen with chained Time Stops

### The bug

Casting Time Stop twice so that the fields overlap (the original report used Soul Tap to recharge the spell) unfreezes the victim when the first field ends, although the second is still running.

### Reproduction

1. With the Lua editor, create two time stop fields on the same victim, the first with a duration of 80 (8 s) and the second with 400 (40 s) triggered about 2 seconds later.
2. Wait for the first to end.
3. Observed on master: the victim's `move_resist` returned to 1000 (unfrozen) while the second field was still up.

### Cause

`freeze_atom` returned immediately if `global_frozen_atoms[A]` was set (`timestop.dm:92`). The atom was recorded under the first field only; the second field never recorded it, and `unfreeze_all` in the first field's `Destroy` released it.

### Fix

Part of the same commit. A field now has an `overlapped` list. When `freeze_atom` finds an atom already held by another field (after the immunity checks), it records it in `overlapped` instead of ignoring it. A static `active_fields` list tracks live fields. On `Destroy`, after `unfreeze_all`, `pass_on_overlapped()` goes through the other fields and re-freezes any atom of theirs that is now free, provided it is still in that field's turfs (field or edge). This keeps the existing single-field behaviour and handles partially overlapping fields of different sizes, a concern raised by XDTM in the issue. A trait-style stacking system (suggested in the comments) was not used.

### Verification

Victim V with field A (8 s) then field B (40 s, 2 s later): about 22 s after the start, when A had ended, V's `move_resist` was still `1e31`; after B ended it returned to 1000.

Not checked: fields with partially overlapping areas, fields of different sizes, three overlapping fields, and the case where the victim leaves field B's area before A ends.

## #49268: A wizard who shapeshifts inside their own time stop gets frozen

### The bug

The wizard's shapeshifted body is frozen if the wizard shapeshifts while inside their own field.

### Reproduction

Not reproduced before the fix. An early attempt used a shapeshift action without the right target, so the new form never received immunity, and was discarded as a valid repro. The cause below is from reading the code; it matches a comment in the issue.

### Cause

The new body is created inside the field and is frozen on entering it. The spell's `Grant` (`code/modules/spells/spell_types/self/stop_time.dm`) adds `TRAIT_TIME_STOP_IMMUNE` to the new body afterwards, but nothing re-checks the already frozen atom.

### Fix

Part of the same commit. A frozen atom now registers a handler for `SIGNAL_ADDTRAIT(TRAIT_TIME_STOP_IMMUNE)`. `frozen_atom_gained_immunity` unfreezes the atom and calls `freeze_atom` again, which now sees the immunity and only registers it as immune. The signal is unregistered in `unfreeze_atom`.

### Verification

With the Time Stop spell targeted at the wizard (so immunity transfers on shapeshift) and the shapeshift spell (wizard version) triggered inside a 60 s field, the new chaos magicarp had `move_resist` 1000 and moved from x=112 to 109 and then 106 inside the field. This was checked once after the fix and not before it.

## Notes

- The runtime log showed only errors from typos in the test scripts. The `spell_timestop` unit test and a full DM test run were not executed; the DM build had no errors.
- The combined commit touches shared timestop code; maintainers who want one PR per issue could split it (the changes for #91784, #48939, #49268 are mostly separable by function).
- `can_pull_frozen` treats anyone with `TRAIT_TIME_STOP_IMMUNE` as allowed, not only the caster. That includes other wizards immune to all time stop.
