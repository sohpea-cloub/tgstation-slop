# #83618: Gondola virtual domain loaded without mobs, with a "baseturf helper initialized multiple times" runtime

| | |
|---|---|

| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The report says the Gondola Asteroid virtual domain sometimes loads with no gondolas, and attaches a runtime saying the domain's baseturf helper was "initialized multiple times". On current master the domain loaded correctly with all 8 gondolas every time it was tried, and the warning never appeared. The warning matches a known race in `SSatoms.CreateAtoms` (an atom initialized by two initializers when one yields); master already contains the upstream fix for that (e9c4dc44c60, "Recheck atom initialization after map-load yields", #98162). No change was made. Whether the warning is actually why the gondolas were missing in the report is unproven.

## The bug

From the report: after setting the domain to Gondola Asteroid on the quantum console, the domain loaded but contained no mobs. The reporter attached a stack trace for `Warning: the virtual domain baseturf editor (/obj/effect/baseturf_helper/virtual_domain) initialized multiple times!`, raised from `lazy_load()` -> `InitializeAtoms` -> `CreateAtoms` -> `InitAtom`, and guessed that the setup might have bailed before mobs were populated. The reporter also wrote that this "apparently" happens regularly. The round also had two test merges (a TGS API revision-date change and a Lua logging change) whose relevance is unknown.

## Reproduction

Not reproduced. What was tried on the test server:

1. On a fresh round, a quantum server was set up with admin tools and the Gondola Asteroid domain was booted by calling `cold_boot_map` on the server through SDQL2 (names with quotes had to be set through the Lua editor, since quoted strings broke SDQL2 queries). The domain loaded in about 15 seconds. Counting with SDQL2 found 8 `/mob/living/basic/pet/gondola` on the domain's Z level, all alive (stat 0), and the runtime log had no "initialized multiple times" entry. The domain map (`_maps/virtual_domains/gondola_asteroid.dmm`) contains exactly 8 gondolas, and the domain has no mob-spawning modules, so the mobs come only from the map load.
2. The domain was reset (`reset(TRUE)`) and loaded again: same result, no warning.
3. To test the suspected race, the upstream recheck (the three lines at `code/controllers/subsystem/atoms.dm:113-115`) was temporarily removed from the test build, which was rebuilt and a new round started. Three quantum servers were then made to boot the Gondola domain at the same time (using the Lua editor to start three timers), so that the three `lazy_load` calls would interleave when they yield on tick checks. Still no "initialized multiple times" warning appeared. The only runtime was `Failed to find exit turfs on generated domain` from `code/modules/bitrunning/server/map_handling.dm:183`, after which the domain was scrubbed with an "initialization failed" result (see Cause, last paragraph). The temporary change was reverted afterwards.

Because the race was not actually triggered even with the fix removed, the warning's origin is established by reading the code, not by observing it.

## Cause

The warning comes from `atom/proc/Initialize` (`code/game/atom/atoms_initializing_EXPENSIVE.dm:119`), which calls `stack_trace` when `INITIALIZED_1` is already set on the atom. The stack in the report (`lazy_load` -> `InitializeAtoms` -> `CreateAtoms` -> `InitAtom`) goes through the loop in `SSatoms.CreateAtoms` (`code/controllers/subsystem/atoms.dm`, around lines 105-120). That loop checks `A.flags_1 & INITIALIZED_1`, and when the tick is over budget it calls `stoplag()`. Before the upstream fix it then initialized `A` without checking again, so if another initializer finished `A` while the loop was yielding, `A` was initialized twice. The four identical `Initialize(1)` lines in the report's trace are one call through the parent chain (virtual domain helper, baseturf helper, effect, obj, atom), so the report shows a single double-initialization of one helper.

Master already has the recheck:

```dm
// Another initializer may have completed this atom while we yielded.
if(A.flags_1 & INITIALIZED_1)
	continue
```

(`atoms.dm:113-115`). The upstream commit's own example is a suit storage unit with the same warning.

That warning does not abort the domain load: `stack_trace` only logs. So it is not an explanation, by itself, for the missing gondolas. Nothing in the inputs shows what else could have removed or prevented them in the reporter's round. One plausible contributor that was found while testing (unrelated to the logged warning): `load_map_items()` (`map_handling.dm:137-190`) iterates the global `GLOB.landmarks_list` (line 142) and deletes the landmarks it uses, so two domains being loaded at the same time (several quantum servers, as in a busy round) steal each other's landmarks. The load of the unlucky one then fails with `Failed to find exit turfs on generated domain.` (`map_handling.dm:183`) and the domain is scrubbed. This is a "domain does not come up" failure, which is not the same as "domain up, no mobs", so it is not shown to be the reported symptom.

## Fix

None. The warning is already addressed in master by upstream commit e9c4dc44c60 (#98162), and no other defect matching the report was found.

## Verification

Nothing to verify after a fix. The checks listed under Reproduction show that on master the domain loads with all 8 gondolas on a first load, after a reset, and (with the upstream recheck still in place) there was no warning in any load.

Not checked: loads on a long-running or busy round, loads while other lazy templates or map loads are running, other maps, and any scenario involving the test merges listed in the report.

## Notes

- The report is from 2024-06-01 and master has moved on; the upstream recheck is likely the reason the warning is not seen any more. The reporter's round is the only evidence for the symptom, and no round data was available.
- The `GLOB.landmarks_list` scan in `load_map_items()` makes concurrent domain loads unsafe. A possible direction (a suggestion, not tested) is to scan only the landmarks inside the new domain's bounds instead of the global list. It was not attempted, since it is not the issue's evidence. It looks related to #81672, but that was not examined here.
- A concurrent-load test as in step 3 of Reproduction may be a useful regression test for any change to either area.
