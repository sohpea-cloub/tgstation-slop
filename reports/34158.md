The three issues all concern implants but have different causes. Each is covered in its own subsection under each heading.

## Summary

- #34158: the internal radio implant opened its tgui window in a state that gives restrained users the view-only status, and the radio object also refused interaction from a restrained user. The fix adds a UI state that ignores restraints and marks the implant's radio as usable while restrained. A handcuffed human can now press Activate and toggle broadcasting.
- #42291: not reproduced. `can_equip()` already refuses to equip an item that is both held and `TRAIT_NODROP`, and the three equip paths tried all failed with the anti-drop implant active.
- #72834: gibbing a mob deletes its implants with `special = TRUE`, and the storage implant returns early in that case, so its contents were deleted with it. The fix spills the contents onto the implantee's location when the implantee is gibbed.

## The bug

### #34158

The implant's author intended that the radio implant could be switched on and off by any conscious wearer. When the wearer is handcuffed, pressing the implant's action button opens the Radio window, but it is view-only and its buttons do nothing.

### #42291

The report says that, with the anti-drop implant active, a held belt (or other equippable item) can be equipped through the UI slot or the equip hotkey, after which the implant stops working: items can be dropped and the action button still reports a deactivation. No reproduction was obtained on master (see below).

### #72834

When a monkey with a storage implant dies and is butchered, whatever was in the implant disappears instead of dropping.

## Reproduction

### #34158

Using the Lua editor on the test server as an observer, on master:

1. Spawn a human, create an internal radio implant (`/obj/item/implant/radio`) and implant it into the human (`implant(h, nil, TRUE, TRUE)`).
2. Create handcuffs, call `set_handcuffed()` with them and `update_handcuffed()`, so the human is restrained.
3. Give control of the human to the test player (`h.ckey = ...`).
4. Click the implant's "Activate" action button on the HUD. The "internal radio" Radio window opened.
5. Check the window's status and try the `broadcast` action.

Observed: the window's `config.status` was 1 (UI_UPDATE, view-only) and the `broadcast` action left `broadcasting` at 0.

### #42291

On master, in the Lua editor:

1. Spawn a human, create an anti-drop implant (`/obj/item/organ/cyberimp/brain/anti_drop`) and insert it with `Insert()`.
2. Spawn a utility belt and put it in the human's active hand.
3. Activate the implant with `ui_action_click()`.
4. Try to equip the belt: `equip_to_slot_if_possible(belt, ITEM_SLOT_BELT)`, `attack_ui(ITEM_SLOT_BELT)` (the call behind clicking a body slot in the inventory UI), and `equip_to_appropriate_slot(belt)`.

Observed: all three calls returned 0, the belt was not worn, and the implant stayed active. The issue was not reproduced. The equip hotkey itself was not pressed, and an actual click on the inventory slot was not tried (the same procs were called from Lua instead).

### #72834

On master, in the Lua editor:

1. Spawn a monkey (`/mob/living/carbon/human/species/monkey`), create a storage implant (`/obj/item/implant/storage`) and implant it with `implant(m, nil, TRUE, TRUE)`.
2. Place a pen in the implant's storage.
3. Call `death()` on the monkey, then `gib(3)` on it. The value 3 is `DROP_BRAIN | DROP_ORGANS`, the same flags the butchering component uses (`code/datums/components/butchering.dm:488`).
4. Check the pen.

Observed: the pen had been destroyed (using it from Lua gave a "destructed userdata" error). The reproduction called `gib()` directly rather than butchering a corpse with a knife, since that is what butchering calls.

## Cause

### #34158

Two layers each capped the window at view-only, and both had to change. A fix to the first layer alone still gave status 1 on a freshly opened window.

1. `/obj/item/implant/radio/activate()` (`code/game/objects/items/implants/implant_misc.dm:82-85`) opens the UI with `GLOB.deep_inventory_state`. That state (`code/modules/tgui/states/deep_inventory.dm:15-18`) returns `user.shared_ui_interaction(src_object)` after checking that the radio is in the user's contents. `shared_ui_interaction()` (`code/modules/tgui/states.dm:62-72`) returns `UI_UPDATE` for any conscious but incapacitated user, and a restrained user counts as incapacitated.
2. `/atom/ui_status()` (`code/_onclick/other_mobs.dm:120-124`) additionally caps the result at `UI_UPDATE` when `can_interact(user)` fails:

```dm
/atom/ui_status(mob/user, datum/ui_state/state)
	. = ..()
	//Check if both user and atom are at the same location
	if(!can_interact(user))
		. = min(., UI_UPDATE)
```

`can_interact()` (`other_mobs.dm:103-118`) fails for incapacitated users, and restraints are ignored only if the atom has `INTERACT_ATOM_IGNORE_RESTRAINED`. The implant's radio (`/obj/item/radio`) did not set that flag, so the radio's own `ui_status` stayed at 1 even when the state itself would have returned interactive.

### #42291

Not a defect on master. `/mob/living/carbon/human/can_equip()` (`code/modules/mob/living/carbon/human/inventory.dm:21-24`) returns FALSE with the message "[item] won't budge, it's impossible to put it on!" when `HAS_TRAIT(equip_target, TRAIT_NODROP) && is_holding(equip_target)`. That covers an item held with the anti-drop implant active. Which change introduced the check was not looked into.

### #72834

`gib()` (`code/modules/mob/living/death.dm`) ends with `SEND_SIGNAL(src, COMSIG_LIVING_GIBBED, drop_bitflags)` followed by `qdel(src)`. `/mob/living/carbon/Destroy()` then runs `QDEL_LIST(implants)` (`code/modules/mob/living/carbon/carbon.dm:23`). `/obj/item/implant/Destroy()` calls `removed(imp_in, silent = TRUE, special = TRUE)` (`code/game/objects/items/implants/implant.dm:142-145`). The storage implant's `removed()` (`code/game/objects/items/implants/implant_storage.dm:12-14`) starts with:

```dm
/obj/item/implant/storage/removed(source, silent = FALSE, special = FALSE)
	if(special)
		return ..()
```

so on this path it does not spill its contents (`atom_storage.remove_all()` is further down, only for a normal removal), and the contents are deleted with the implant. The implant's normal removal path (`removed()` with `special = FALSE`) does dump the contents and was not touched. `gib()` and the carbon `gib()` do not remove implants before the mob is deleted.

## Fix

Two commits on the branch, one per fixed issue.

### "Fix issue 34158: internal radio implant can be used while handcuffed"

In `code/game/objects/items/implants/implant_misc.dm`:

- A new UI state `GLOB.implant_radio_state` (`/datum/ui_state/implant_radio_state`). It keeps the "radio is in the user's contents" check, then calls `shared_ui_interaction()`, and if that returned `UI_UPDATE` but `INCAPACITATED_IGNORING(user, INCAPABLE_RESTRAINTS)` is zero (the only thing incapacitating the user is restraints), returns `UI_INTERACTIVE`. `activate()` opens the UI with this state instead of `GLOB.deep_inventory_state`.
- In `/obj/item/implant/radio/Initialize()`, `radio.interaction_flags_atom |= INTERACT_ATOM_IGNORE_RESTRAINED`, which fixes the second layer.

The commit message describes only the first layer; the second is in the diff. The reasoning is that the radio needs no hands, so restraints should not matter, while other incapacitation (stun, unconsciousness) should still block it. The shared deep-inventory state, and the global `/atom/ui_status()`, were left unchanged so other UIs are unaffected. The new state was also made specific to implants rather than changing `deep_inventory_state`, which other objects use.

### "Fix issue 72834: storage implant contents survive the implantee being gibbed"

In `code/game/objects/items/implants/implant_storage.dm`:

- `implant()` registers `COMSIG_LIVING_GIBBED` on the implantee (only if the parent `implant()` succeeds, i.e. the implant was actually placed), with the new handler `on_implantee_gibbed()`.
- The handler runs `atom_storage?.remove_all(source.drop_location())`, so the contents are put on the implantee's tile before the mob and implant are deleted. The signal is sent before `qdel(src)` in `gib()`, so the implant still exists at that point.
- `removed()` unregisters the signal.

Alternative considered and not taken: changing the `special` early-return in `removed()` so it also spills. `special = TRUE` is used by several callers that explicitly do not want side effects (for example the implant chair and the admin organ manipulation verb, found by grep), so a gib-specific hook is narrower.

## Verification

### #34158

On the fixed build, repeating the setup (Lua: cuffed human with the radio implant, click Activate, then the `broadcast` action): the Radio window opened with `config.status` 2, and `broadcast` changed `broadcasting` from 0 to 1. The Activate button was clicked through the HUD, not just called from Lua.

Not checked: the other radio controls (frequency, channels, volume, subspace), an uncuffed user (regression), a stunned or unconscious cuffed user (should stay view-only or closed), other implant types that use `deep_inventory_state`, and the Syndicate and mining radio implant subtypes.

### #42291

No fix. The negative result is described above.

### #72834

On the fixed build, with the same Lua setup (monkey, storage implant, a pen named TESTPEN in it, `death()`, `gib(3)`): the pen appeared on the floor at the monkey's location. The runtime log showed no runtime errors after the final run.

Not checked: butchering a real corpse with a tool (instead of calling `gib()`), gibbing a mob with other implants or several stacked storage implants, a gib with different drop flags, and removing the implant by surgery (the unchanged path).

## Notes

- #34158: the new state upgrades any `UI_UPDATE` result from `shared_ui_interaction()` when restraints are the only incapacitation. For a living mob, `shared_ui_interaction()` only applies the `MOBILITY_UI` check when the result would otherwise be `UI_INTERACTIVE`, so a restrained user who is also UI-blocked (the `TRAIT_UI_BLOCKED` mobility flag) would have the `UI_UPDATE` result upgraded to interactive. This comes from reading the code and was not tested. A maintainer might want the new state to re-check `MOBILITY_UI`.
- #34158: other implant-held items that use `deep_inventory_state` were not reviewed for the same problem.
- #42291: the issue's own comments note that, for example, picking up a NODROP helmet and putting it on made it impossible to remove. The check in `can_equip()` addresses the held-item equip case reported. If the behaviour is still seen in game, it may come from an equip path that does not go through `human/can_equip()`; none was found in testing.
- #72834: upstream PR #74120, referenced in the issue's notes, changed `removed()` to dump the contents when an implant is removed normally, so it does not cover the gib path.
