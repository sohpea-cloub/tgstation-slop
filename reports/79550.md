## Summary

This unit covers three radio problems. #79550: every broadcasting radio that hears a spoken message transmits it on its own, so a pile of radios repeats one message many times. The fix drops identical transmissions (same speaker, text, language, frequency) from the same tick after the first. #48267: free-range radios and intercoms could be tuned to the CentCom and capture the flag frequencies, and the fix makes them fall back to Common unless they have the CentCom special channel. #85482: the Communications Blackout event EMPed the Syndicate telecomms mainframe, which silenced the Syndicate channel, and the fix makes that mainframe EMP-immune.

## #79550: duplicate radio messages with more than one source

### The bug

With several radios on one tile, all set to broadcast, a player speaking was heard on the radio frequency several times, once per radio. The issue calls this an easy way to spam and lag the server, especially with tape recorders or holopads.

### Reproduction

Done on the test server with the Lua editor. The speech was produced by calling `say()` on a human, so the full player path from a keypress was not used.

1. Spawn a human and three `/obj/item/radio` on the same tile. Set each radio to broadcasting and not listening (`set_broadcasting(true)`, `set_listening(false)`). All were on the default Common frequency (1459).
2. Spawn a fourth radio about 10 tiles away, set to listening and not broadcasting, and register a Lua handler on its `radio_receive_message` signal that increments a counter. (The signal name is `radio_receive_message`; a first attempt with the `comsig_` name never counted.)
3. Make the human say "second test".

Observed on master: the counter read 3. Ghost chat showed the message once labelled `[Common]` and twice labelled `[145.9]`, i.e. three copies of one message.

### Cause

A broadcasting radio calls `talk_into()` from its own `Hear()` (`code/game/objects/items/devices/radio/radio.dm:427`), which runs `talk_into_impl()` (`radio.dm:310`). Nothing in that path knows another radio already transmitted the same speech, so each radio builds a virtual speaker and a signal and sends it. Three radios hearing the same speech send three signals.

### Fix

Commit "Fix issue 79550: radios hearing the same speech no longer all transmit it" adds `/obj/item/radio/proc/is_duplicate_transmission()` and calls it in `talk_into_impl()` after the existing checks (power, TX wire, jammer) and before the virtual speaker is created. It keeps a static list of signatures `"[REF(speaker)]|[freq]|[language]|[message]"` for the current `world.time` and clears it when the tick changes. The first radio to see a signature transmits; later radios hearing the same thing on the same tick return early.

The approach was chosen because the issue discussion agreed that "any exact replicas (same message, same radio frequency, etc) should be ignored". Same-tick comparison is cheap and avoids suppressing a player who legitimately repeats a sentence a moment later.

### Verification

On the rebuilt server the same setup (three broadcasting radios and a human on one tile, a listener radio 10 tiles away) produced a single `[Common]` chat line for "second test". The listener's counter was not read in that run (the script yielded and returned before the message arrived), so the evidence is the chat output, not the counter.

Not checked: a different-frequency pair of radios (two distinct frequencies should still each transmit once, which the code supports but which was not run), speech in different languages, radios in the speaker's hands versus on the floor, headsets, intercoms, and the tape recorder or holopad cases from the issue.

## #48267: free-range intercoms can speak on CentCom and CTF frequencies

### The bug

The AI satellite's free-range intercom could be tuned to the Syndicate (121.3), CTF red (121.5), CTF blue (121.7) and CentCom (133.7) frequencies, and then speak on them.

### Reproduction

1. On master, call `sanitize_frequency(f, TRUE, 0)` (the clamp used for a free-range radio without Syndicate access) for 1213, 1215, 1217, 1219, 1221, 1337 and 1243. Result: 1459, 1215, 1217, 1219, 1221, 1337, 1243. Only 1213 (Syndicate) is redirected; the CTF and CentCom frequencies pass through.
2. Spawn an `/obj/item/radio/intercom/freerange/ai_core`, set it to broadcasting and tune it to 1215 with that result. Spawn a plain radio on 1215, listening. Have a human beside the intercom say a line.

Observed on master: the intercom set its frequency to 1215, the line appeared in chat as a `[Red Team]` message, and the plain radio on 1215 received it. The Syndicate half of the report was already fixed on master, as shown by step 1.

### Cause

`sanitize_frequency()` (`code/__HELPERS/radio.dm:2`) only maps the Syndicate frequency back to Common (`if(. == FREQ_SYNDICATE && !syndie)`). Free-range radios clamp to 1201-1599, which includes the CTF (1215-1221) and CentCom (1337) frequencies, and nothing else stops them. Radios call it from `Initialize()` (`radio.dm:113`), the tuning handler in `ui_act()` (`radio.dm:518`), and the exosuit radio (`code/modules/vehicles/mecha/equipment/tools/radio.dm:40`).

Separately, `/obj/item/radio/intercom/can_receive()` has this at `code/game/objects/items/devices/radio/intercom.dm:152`:

```dm
if(!(special_channels &= RADIO_SPECIAL_SYNDIE))
```

`&=` assigns, so checking a Syndicate-frequency signal overwrites `special_channels` with only its Syndicate bit. This was almost certainly meant to be `&`.

### Fix

Commit "Fix issue 48267: free-range radios can't be tuned to CentCom or CTF frequencies":

- adds `/obj/item/radio/proc/sanitize_tuned_frequency()`, which calls `sanitize_frequency()` as before and then returns `FREQ_COMMON` if the result is the CentCom or any CTF frequency and the radio does not have `RADIO_SPECIAL_CENTCOM`;
- uses it in `Initialize()`, the `ui_act()` tuning handler and the exosuit radio;
- changes `&=` to `&` in the intercom's `can_receive()`.

### Verification

After the rebuild, `sanitize_tuned_frequency()` on an AI-core free-range intercom returned 1459 for 1215, 1217, 1337 and 1213, and 1355 stayed 1355 (Medical) and 1459 stayed 1459. The same intercom with `special_channels` set to the CentCom special channel kept 1337 and 1215. A non-free-range radio with the CentCom channel asked for 1337 got 1441 from the normal clamp.

Not checked: the real tuning UI (`ui_act`) and the exosuit radio path, whether the AI intercom can still be used for what its comment describes, and the `&` change in `intercom.dm` beyond reading the code.

### Notes

- Behaviour change to weigh: several descriptions say these devices tune to anything. The free-range intercom is described as "A special intercom that can be tuned to any frequency, bypassing encryption", the command intercom as tunable "to any frequency, granting you access to channels you're not supposed to be on", and the AI core one is for tuning "any encrypted frequency if comms are down". The fix keeps them able to reach every ordinary and secure channel but takes away CentCom and CTF. A maintainer may prefer to limit the change to the AI core intercom.
- The fix changes only what frequency a radio can be tuned to. It does not change what a radio hears.
- The issue comments mention related reports (#46337, #48250, #52698) that were not looked at.

## #85482: Syndicate comms stop working when telecomms are down

### The bug

The report says Syndicate radio does not work when comms are turned off. The steps are only "Turn comms off. Try to speak on syndi comms." The investigation took "comms off" to mean the Communications Blackout event, which EMPs every telecomms machine; other ways of turning comms off were only partly tested (see below).

### Reproduction

On the test server with the Lua editor:

1. Spawn a human, a Syndicate headset (`/obj/item/radio/headset/syndicate`) beside it and a second Syndicate headset about 10 tiles away with a receive counter. `GLOB.telecomm_machines` held 26 machines, one of them `/obj/machinery/telecomms/allinone/nuclear`.
2. Make the sender headset `talk_into()` the Syndicate channel. The message was delivered.
3. Switch off every telecomms machine except the `allinone/nuclear` one and send again. Syndicate headsets are subspace only, but the Syndicate mainframe still carried the message.
4. Call `emp_act(1)` (EMP_HEAVY, what the Communications Blackout event does in `code/modules/events/communications_blackout.dm:31-32`) on every machine in `GLOB.telecomm_machines`, wait a few seconds, then send a Syndicate message again.

Observed on master: after step 4 the Syndicate message was not delivered, while Common-channel radios still worked through their mundane (non-subspace) fallback. The event itself was not run; the EMP loop reproduces its effect on the telecomms machines.

### Cause

The Syndicate priority mainframe, `/obj/machinery/telecomms/allinone/nuclear` (`code/game/machinery/telecomms/machines/allinone.dm:58`), is placed on the always-loaded CentCom map (`_maps/map_files/generic/CentCom.dmm`) and is in `GLOB.telecomm_machines`. The base `/obj/machinery/telecomms/emp_act()` (`code/game/machinery/telecomms/telecomunications.dm:161`) sets the EMPed machine status on it like on any other machine, which turns it off for `300 SECONDS / severity`. Headsets can only use subspace transmission, so with this mainframe off a Syndicate headset has nothing to carry the message.

### Fix

Commit "Fix issue 85482: syndicate telecomms mainframe is immune to EMP" adds an `emp_act()` override on `/obj/machinery/telecomms/allinone/nuclear` that returns `EMP_PROTECT_SELF`, so it is never EMPed.

### Verification

On the rebuilt server, `emp_act(1)` was called on all 26 telecomms machines. 25 were off afterwards, the Syndicate mainframe was still on, and a Syndicate headset's message ("syndi test") appeared in chat as `[Syndicate] ... says`, so it was delivered. The Lua receive counter read 0 in that run, but it was read before delivery finished, so the chat line is the evidence.

Not checked: the real Communications Blackout event, other EMP sources (EMP grenades, ion storms), and a Syndicate message while the mainframe is switched off or unpowered some other way.

### Notes

- Design choice: the override makes the mainframe immune to all EMPs, not only the blackout event, and it returns without calling the parent `emp_act()`. A narrower fix would be to skip this machine in the event loop. The event description says it EMPs "all telecommunication machines", so the override at the machine was chosen.
- The report's "turn comms off" may also mean something other than the event (for example, a telecomms monitor or the machines being switched off). With every other machine off and only the Syndicate mainframe on, Syndicate messages were still delivered on master, so that reading was not reproduced.
