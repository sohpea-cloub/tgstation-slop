## Summary

Both issues say that a heretic's void cloak becomes invisible when the hood goes up (intended) and then stays invisible after the hood goes down (not intended). On master the cloak's sprite returned every time in the test, through three hood up/down cycles, after dropping and re-equipping the cloak with the hood up, and after dropping the hood item. Hood handling now goes through the generic `toggle_attached_clothing` component, which resets the cloak's icon state when the hood is removed, so the reported behavior was most likely fixed by that rewrite. No code was changed.

## The bug

### #78606

The reporter wore the void cloak (visible), flipped the hood up (the cloak turns invisible, which is how the item is meant to work: "Turns invisible with the hood up, lets you hide stuff"), then flipped the hood back down. The cloak stayed invisible: no worn sprite, though it still showed up on examine and still worked as a spell focus.

### #84287

Same symptom, reported in June 2024: "making the cloak invisible works but making it visible doesn't; the cloak can still be examined if the hood is down". The reporter wrote that they might have booted the game locally, and the issue carries a "Tested/Reproduced" label from that time. It is not known which build it was reproduced on.

## Reproduction

Not reproduced. On master, on the test server, using the Lua editor and the on-screen "Toggle Hood" button:

1. Put a character into the round and gave them the heretic antagonist datum. Before this, pressing "Toggle Hood" on the worn cloak gave the balloon text "can't get the hood up!" (the cloak refuses non-heretics through `can_create_hood()`).
2. Equipped a `/obj/item/clothing/suit/hooded/cultrobes/void` into the outer clothing slot.
3. Pressed Toggle Hood. Chat said "Light shifts around ..., making the cloak around them invisible!", the button's overlay changed from `void_cloak` to `void_cloak_t`, and a "void hood" item appeared on the head.
4. Pressed Toggle Hood again. Chat said "A kaleidoscope of colours collapses around ..., a cloak appearing suddenly around their person!", the button's overlay changed back to `void_cloak`, and the hood item was gone. Reading the cloak's variables with Lua and inspecting the mob showed `icon_state` back to `void_cloak`, `hood_up` 0, `alpha` 255, `invisibility` 0, and a `void_cloak` overlay on the character.
5. Repeated the up/down cycle three times with the same result.
6. With the hood up, dropped the cloak to the ground and equipped it again; then pressed Toggle Hood and checked the state. No stuck invisible state.
7. With the hood up, dropped the hood item itself from the head slot. The cloak was revealed again ("cloak revealed", the same chat message), and examining the cloak worked normally.

No runtime errors were seen. What was not done: the failing sequence from #84287 on a local-hosted build, a view of how the sprite looked to another player, and other ways of removing the hood (for example the hood being deleted or the wearer being stripped).

## Cause

No defect found. What the code does on master:

- Every `/obj/item/clothing/suit/hooded` gets a `toggle_attached_clothing` component (`code/modules/clothing/suits/toggles.dm`, `Initialize`). It is created with `parent_icon_state_suffix = hood_up_affix` (default `"_t"`), `destroy_on_removal = alternative_mode` (the void cloak sets `alternative_mode = TRUE`), and callbacks to `on_hood_created`, `on_hood_up` and `on_hood_down`.
- When the hood is deployed, the component sets the cloak's `icon_state` and `worn_icon_state` to `"[INITIAL_ICON_STATE]_t"` and refreshes the worn icon (`code/datums/components/toggle_attached_clothing.dm:143-146`). That is the transparent variant, which is what makes the cloak look invisible.
- When the hood is removed, `remove_deployable()` (`toggle_attached_clothing.dm:198-213`) sets both states back to `INITIAL_ICON_STATE(parent_gear)` and calls `update_slot_icon()`. It also runs when the hood item is dropped, deleted or moved to a different slot (`:180-195`). This is the step that restores the sprite.
- The void cloak's own code only toggles traits and messages. `make_invisible()` adds `TRAIT_NO_STRIP` and `TRAIT_EXAMINE_SKIP` and removes the cold and low-pressure resistances; `make_visible()` removes the traits and adds the resistances (`code/modules/antagonists/heretic/items/heretic_armor.dm:1235-1253`). On hood-down, `on_hood_down()` calls `make_visible()` (`:1216`).

The 2023 behavior is not in the inputs, so what the old code did wrong was not checked. It is a reasonable guess that the reported bug came from the pre-component hood code and went away with the rewrite; this was not verified against the history. Issue #84287 is from June 2024 and was labelled as reproduced then, so the fix, if it was a fix, landed after that or the reporter's local build differed.

## Fix

None. No code was changed or committed.

## Verification

Nothing was fixed, so the checks under Reproduction are the whole verification. Not checked: any server-side difference between the test setup and a live round, or other hooded suits.

## Notes

- Side finding, harmless as far as tested: `on_hood_down()` is defined twice on `/obj/item/clothing/suit/hooded/cultrobes/void` in `heretic_armor.dm` (`:1185`, which sets `hood_up = FALSE`, and `:1216`, which calls `make_visible()` and then `..()`). A reading of the duplicate definition suggests only one of them can take effect, which could leave `hood_up` set after the hood goes down. In the test, `hood_up` read 0 after lowering the hood, so the net effect was not seen; it is worth removing the duplicate so the intent is clear.
- Possibly inverted wording, read from the code and not tested: the void cloak's `examine()` (`heretic_armor.dm:1207-1214`) returns early when `!hood_up`, and otherwise adds "Allows you to cast heretic spells while the hood is down" and "Is space worthy as long as the hood is down". The comment says it is meant for the hood-down case, so the condition looks inverted.
- Both issues can be closed as no longer reproducible, unless someone can still produce the stuck state on current master; if so, a note of the exact steps (and whether a local-hosted server was involved) would help.
