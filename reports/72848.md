# #72848: Dead deadchat-controlled mobs (Birdboat) still obey deadchat commands

| Status | Verified on the test server; fix committed |

## Summary

A mob under deadchat control (the rare 5% "Birdboat" goose, or anything given the `deadchat_control` component) keeps carrying out commands typed by orbiting ghosts after it has died. The component's input handlers never check whether the parent mob is dead. The fix adds a `parent_is_dead()` check: dead parents no longer consume commands (the text goes out as ordinary deadchat), and the democracy loop discards votes and does not invoke actions for a corpse. The component stays attached, so a revived mob is controllable again.

## The bug

The issue reporter killed the deadchat-controlled goose, orbited the body and typed `honk`. The dead goose honked. Movement and barf commands also still worked. Two comments on the issue question whether this is a bug at all (one calls it "a ghost controlled goose, why can't it work when dead?", another "i thought this was an actual feature"). The issue carries the Oversight and Good First Issue labels and was treated as a bug.

## Reproduction

On master, as an admin observer:

1. Using the Lua editor, spawn `/mob/living/basic/goose/vomit` next to the observer, call `deadchat_plays()` on it (anarchy mode, 12 second cooldown), and make the observer orbit it. The game announced "Birdboat is now deadchat controllable!".
2. Type `honk` in deadchat. Result: "Birdboat yells, "HONK!!!"" and `"honk" input accepted. You are now on cooldown for 12 seconds.` (the expected behavior while alive).
3. Kill the goose by calling `death()` on it from the Lua editor. Its sprite changed to the dead goose.
4. Wait out the 12 second cooldown ("Your deadchat control inputs for Birdboat are no longer on cooldown.").
5. Type `up` in deadchat.

Observed: `"up" input accepted. You are now on cooldown for 12 seconds.` and the orbiting observer was carried from 107,144 to 107,145: the dead goose had stepped north.

Only anarchy mode was exercised in game. Honk after death was not retested before the fix in this run (the issue report shows it, and the unfixed `up` shows the same path); the movement result above is the first-hand evidence.

## Cause

`deadchat_react()` in `code/datums/components/deadchat_control.dm:66` handles ghost speech for the parent. After checking that the message is a known input (line 71) it goes straight to the anarchy branch (line 74), which starts the cooldown and calls `inputs[message].Invoke()` (line 83), or to the democracy branch (line 87), which records a vote. `democracy_loop()` (line 92) later counts votes and calls `inputs[result].Invoke()` (line 98). Neither path looks at the parent's `stat`.

Nothing else removes or gates the component on death: `goose.dm` only registers the component in `deadchat_plays()` (`code/modules/mob/living/basic/farm_animals/goose/goose.dm:161`), with a removal callback that is not tied to death. The same component is used by the corgi (`code/modules/mob/living/basic/pets/dog/corgi.dm`) and `simple_animal` (`code/modules/mob/living/simple_animal/simple_animal.dm`), so they had the same hole.

## Fix

One commit, "Fix issue 72848: dead mobs no longer obey deadchat control commands", changes only `code/datums/components/deadchat_control.dm`:

- New proc `parent_is_dead()`: TRUE when the parent is a `/mob/living` with `stat == DEAD`. Non-living parents (objects such as anomalies, rods, the singularity) are never considered dead.
- `deadchat_react()` returns early when the parent is dead, without returning `MOB_DEADSAY_SIGNAL_INTERCEPT`. The message is therefore spoken as ordinary deadchat and no cooldown or "input accepted" message is produced.
- `democracy_loop()` returns early when the parent is dead, after emptying `ckey_to_cooldown` (the stored votes), so votes cast for a corpse do not fire when it is revived.

The component is deliberately not removed on death, so reviving the mob makes it controllable again. The alternative (removing the component on death) would need a death signal hook per user and would lose the control on revival.

## Verification

On the test server after rebuilding with the fix: a new goose was set up as in the reproduction. Alive, `honk` still worked ("Birdboat yells, "HONK!!!"", input accepted). After killing the goose and waiting out the cooldown, `up` and `honk` each appeared only as plain `DEAD: <name> says, "..."` lines: no "input accepted" message, no honk, no movement.

Not checked: democracy mode (the vote-clearing branch of `democracy_loop()`), revival of a controlled mob, the corgi and `simple_animal` users, and non-living parents. No runtimes were looked for beyond observing normal behavior.

## Notes

- Design question: if maintainers consider a dead controlled mob a feature, the fix should be dropped; the issue comments are split on this.
- A dead mob's deadchat message now also bypasses cooldown messages, so ghosts can talk normally near a corpse.
