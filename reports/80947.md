| Status | Fixed; verified on the test server through the same `gib()` path, not with a physical singularity |

## Summary

Gibbing a mob that carries a disease aborted halfway: removing its organs tried to add the `infective` component to an organ that was already being deleted, which makes `_AddComponent` runtime. The runtime stopped `gib()` before its final `qdel(src)`, so the mob survived. The singularity consumes mobs through `gib()`, which is why it "failed to eat people". The fix skips adding the component when the organ is `QDELING`.

## The bug

The reporter saw a singularity not pulling in and gibbing mobs (two monkeys shown, plus a number of players who were later recovered) and posted a runtime from the same round: "Attempted to add a new component of type [/datum/component/infective] to a qdeleting parent of type [/obj/item/organ/internal/brain]". The call stack runs from the singularity's `Bumped` through `spill_organs` and the brain's `Destroy` and `Remove` to `AddComponent`.

## Reproduction

The singularity itself was not spawned; the test called the proc the singularity uses, so the physical bump path is untested. Using the Lua editor on the test server:

1. Start a round, spawn a human, and give it the flu with `ForceContractDisease(/datum/disease/flu)`.
2. Call `singularity_act(1, me)` on the human. This is `gib()` with drop flags `NONE`, which is what the singularity triggers when it bumps or consumes a mob.

Observed on master: a runtime "Attempted to add a new component of type [/datum/component/infective] to a qdeleting parent of type [/obj/item/organ/lungs]" at `_component.dm`, reached through `on_mob_remove`, `Remove`, `Destroy`, `qdel` and `spill_organs`. The human stayed alive and lying on the floor, the mob still present. (The lungs rather than the brain in this run; the stack is otherwise the same as the report's.)

## Cause

`gib()` calls `spill_organs(drop_bitflags)` and ends with `qdel(src)` (`code/modules/mob/living/death.dm:36`). When organs are not dropped they are deleted, and `Destroy` calls `Remove`, which ends in `on_mob_remove` (`code/modules/surgery/organs/organ_movement.dm`). If the owner has any diseases, that proc adds the `infective` component unconditionally:

```
if(LAZYLEN(diseases_to_add))
	AddComponent(/datum/component/infective, diseases_to_add)
```

(`organ_movement.dm:229-230`). `_AddComponent` raises a `CRASH` for a qdeleting parent (`code/datums/components/_component.dm:317`), which aborts the whole `gib()` before `qdel(src)` is reached. Only mobs with diseases hit this, which fits it being intermittent in the report.

## Fix

One commit, "Fix issue 80947: don't add infective component to an organ that is being deleted". It adds `&& !QDELING(src)` to the condition above, with a comment. An organ being deleted has no use for an infective component, so skipping it loses nothing.

## Verification

On the rebuilt test server, the same `singularity_act(1, me)` call on a flu-infected human gibbed it completely (no mob left), and the runtime log had no infective runtimes.

Not checked: a physical singularity consuming a diseased mob, other organ types and diseases besides flu, and other `gib()` callers.

## Notes

- The fix addresses only the `AddComponent` crash. Whether other causes of a singularity failing to consume mobs exist was not examined; the reporter's round may have had other factors.
- The report's own stack names the brain; the reproduction hit the lungs. Both go through the same `on_mob_remove` code.
