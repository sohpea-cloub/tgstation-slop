## Summary

**#61063:** `handle_charge()` on the ethereal stomach only threw the alert for the current charge range and never cleared the alert of the other kind, so the Blood Overcharge alert stayed on screen after the charge dropped and then appeared next to Low Blood Charge. The fix clears the opposite alert in every range case.

**#77215:** The ethereal glow light (`/obj/effect/dummy/lighting_obj/moblight/species`) was not marked `LIGHT_ATTACHED`, so its light holder was computed as null when the ethereal was inside a locker and was never recomputed when the ethereal came out. Marking the base `moblight` type `LIGHT_ATTACHED` makes the light follow the mob's own moves, and the holder is correct inside and outside containers.

## #61063: undercharge and overcharge alerts at the same time

### The bug

An ethereal who has been overcharged can end up with the "Blood Overcharge" alert and the "Low Blood Charge" alert on the HUD at the same time (the screenshot in the issue shows this). The two alerts are meant to be mutually exclusive: one is for too little charge, the other for too much.

### Reproduction

The charge values were set by calling procs directly through the Lua editor, not by playing through a natural overcharge and zap. The stomach's charge is in joules (`STANDARD_CELL_CHARGE` is 10 kJ, so for example `ETHEREAL_CHARGE_FULL` is 20000 and `ETHEREAL_CHARGE_DANGEROUS` is 30000).

1. On the test server, as an observer with the Lua editor open, spawn a human and make it an ethereal with `set_species`.
2. Get the human's stomach (`get_organ_slot('stomach')`, an `/obj/item/organ/stomach/ethereal`).
3. For a chosen value `v`, set the charge with `stomach:adjust_charge(v - stomach.cell:charge())`, call `stomach:handle_charge(human, 1)`, then read `human.alerts['ethereal_charge']` and `human.alerts['ethereal_overcharge']`.
4. Run it for 22000, then 5000, then 12000, then 5000 again.

Observed on master (low-charge alert / overcharge alert):

| Charge | Low-charge alert | Overcharge alert |
|---|---|---|
| 22000 | none | Blood Overcharge |
| 5000 | Low Blood Charge | Blood Overcharge (both showing) |
| 12000 | none | none |
| 5000 | Low Blood Charge | none |

The 12000 step clears both alerts only because 12000 falls in the one gap between cases (see Cause). Without passing through that gap, the overcharge alert survives, which is the bug.

### Cause

`handle_charge()` in `code/modules/surgery/organs/internal/stomach/stomach_ethereal.dm:89` is a `switch(cell.charge())` over charge ranges. Each case throws only the alert for its own range:

```dm
if(ETHEREAL_CHARGE_LOWPOWER to ETHEREAL_CHARGE_NORMAL)
	carbon.add_mood_event("charge", /datum/mood_event/lowpower)
	carbon.throw_alert(ALERT_ETHEREAL_CHARGE, /atom/movable/screen/alert/lowcell/ethereal, 2)
```

No case clears the alert of the other kind. The only place both alerts are cleared is the `else` branch (`:116-119`), and the cases cover everything except the span from `ETHEREAL_CHARGE_NORMAL` (10000) to `ETHEREAL_CHARGE_ALMOSTFULL` (15000), so `else` is reached only when the charge is in that span.

An ethereal at an overcharge level gets Blood Overcharge. If the charge then falls straight below `ETHEREAL_CHARGE_NORMAL`, for example after the overcharge zap in `discharge_process()` brings the charge down and it then drains, the overcharge alert is never cleared and the low-charge alert is added next to it. A charge of exactly `ETHEREAL_CHARGE_FULL` also leaves the overcharge alert standing, because the `ALMOSTFULL to FULL` case matches first and neither throws nor clears an alert. This matches the comment on the issue, which attributed it to the overcharge zap not updating the alerts. That was inferred from reading the code; the zap itself was not run.

### Fix

Commit "Fix issue 61063: Ethereal charge alerts no longer linger when the charge range changes" adds explicit `clear_alert()` calls to the cases:

- the three low-charge cases (`-INFINITY to NONE`, `NONE to LOWPOWER`, `LOWPOWER to NORMAL`) clear `ALERT_ETHEREAL_OVERCHARGE`;
- the `ALMOSTFULL to FULL` case clears both alerts;
- the two overcharge cases (`FULL to OVERLOAD`, `OVERLOAD to DANGEROUS`) clear `ALERT_ETHEREAL_CHARGE`.

The `else` branch is unchanged. Clearing in each case was chosen over restructuring the switch, to keep the diff small and each case self-describing. An alert that is not present is a no-op for `clear_alert()`.

### Verification

On the rebuilt test server, using the same Lua procedure, the alerts were (low-charge / overcharge): 22000 none/Blood Overcharge; 5000 Low Blood Charge/none; 12000 none/none; 27000 none/Blood Overcharge; 17000 none/none; 7000 Low Blood Charge/none; 1000 Low Blood Charge/none; 0 No Blood Charge/none. Both alerts were never present together.

Not checked: a natural overcharge that reaches the zap and then decays (charge was set directly, one `handle_charge()` call per value, not through the stomach's `on_life` ticking), the visual HUD, and the mood events and toxin damage in each case (those lines are untouched).

## #77215: ethereal glow missing when spawned in a locker

### The bug

An ethereal created inside a locker has no visible glow. Taking it out of the locker does not restore the glow, and admins had no way to give it back short of respawning the player (per the issue).

### Reproduction

Done through the Lua editor and the light component's internal state, not by looking at a rendered view.

1. On the test server, as an observer, spawn a `/obj/structure/closet` and spawn a human inside it (`SS13.new('/mob/living/carbon/human', locker)`).
2. Call `set_species` with `/datum/species/ethereal`.
3. Find the `/obj/effect/dummy/lighting_obj/moblight/species` in the human's contents and read `light_on` and the `current_holder` of the `overlay_lighting` component's `light` datum.
4. `forceMove` the human onto the floor and read the same values again.

Observed on master: in the locker, `light_on` was 1 and `current_holder` was nil. After moving to the floor, `light_on` was still 1 and `current_holder` was still nil. An overlay light with no holder shows nothing, so the glow stayed missing.

### Cause

The ethereal glow is created by `ethereal.mob_light(light_type = /obj/effect/dummy/lighting_obj/moblight/species)` (`code/modules/surgery/bodyparts/bodypart_effects/ethereal_glow.dm:31`). That light object lives inside the mob. The light's holder is decided by `/datum/light_overlay/proc/check_holder()` (`code/modules/lighting/light_overlay.dm:155-180`), which looks at the loc of `parent_attached_to` if set, otherwise of `parent`. Here `parent` is the light object, so `inside` is the mob; when the mob is in a locker, `inside.loc` is not a turf and the holder is set to null (the `!isturf(inside.loc)` branch).

`check_holder()` is re-run only when `parent` or `parent_attached_to` moves (`on_movable_moved`, `light_overlay.dm:188`). The light object never moves by itself when the mob leaves the locker, and `parent_attached_to` is only set when the light has `LIGHT_ATTACHED` (`code/datums/components/overlay_lighting.dm:64-66`). `/obj/effect/dummy/lighting_obj/moblight` (`code/game/objects/effects/lighting.dm:28`) did not set that flag, so nothing re-evaluated the holder.

### Fix

Commit "Fix issue 77215: Mob lights follow the mob into and out of containers" adds `light_flags = LIGHT_ATTACHED` to `/obj/effect/dummy/lighting_obj/moblight`. With the flag, the component sets `parent_attached_to` to the mob the light is inside, so the mob's moves re-run `check_holder()`. Inside a locker the holder is the locker; on the floor it is the mob. The flag was put on the base `moblight` type rather than only on `moblight/species`, so it applies to every mob light (including `moblight/fire` and the flash lighting FX that use the same base).

### Verification

On the rebuilt test server, with the same Lua procedure, an ethereal spawned in a locker had `light_on` 1 and holder = the closet; after leaving, holder = the mob; after moving into a second locker, holder = the closet; after leaving again, holder = the mob.

Not checked: the rendered glow on a client's screen (only the light component's holder state was read), the other users of the base type (fire, flash FX, jellyperson glow), and containers other than a closet (crates, pods).
