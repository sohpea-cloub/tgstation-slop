## Summary

These three issues were worked together because all concern species and DNA changes. #62385: random mutation of a mob's mutant color (radiation storm, mutation toxin, floral projectile, DNA scrambling, new random DNA) picks any six hex digits, so about 1.5% of results are near-black, a range the preferences menu refuses; the fix makes the mutant-color block pick only colors that pass the same darkness check. #71922: changing species on a mob without a head (the H.A.R.S. mutation) deletes its brain because the replacement brain belongs in the missing head; the fix keeps the brain's current zone in that case. #70176: changing species did not drop pocket or held items on master, in any of eight species tried.

The branch holds two commits, one per fixed issue.

## #62385: Lizards can turn pitch black

### The bug

The report (2021) says that a lizard whose mutant color is changed by a radiation storm, or by an envy knife stab, can end up with a pitch-black body color. A comment adds that this happens with all colors and with changeling transformations (changelings becoming copies with wrong skin colors) and that at least one pitch-black podperson was seen.

### Reproduction

Reproduced as a rate, not as a visible black lizard. Using the Lua editor on a test server:

1. Spawned a human, set its species to lizard, and called `random_mutate_unique_features()` repeatedly (the proc radiation storms, mutation toxin and floral projectiles call); after each call that changed the color, read `dna.features['mcolor']` and computed its HSL lightness.
2. Called `random_color()` (the helper that produced the value) 3000 times and counted results below 15% lightness.

Evidence: 44 of 3000 `random_color()` results (about 1.5%) were below 15% lightness, the darkest at about 4%. The preferences menu rejects any mutant color below 15% (`is_color_dark(value, 15)`, `code/modules/client/preferences/species_features/mutants.dm:28`). A literal `#000000` did not appear in 400 mutations; it needs all six hex digits to be near zero, so it is rare (the exact probability was not computed). The envy knife path was only read in code: it copies DNA from the stabbed mob rather than generating a color, so it was not a separate source. A pitch-black result from the changeling or podperson comments was not examined.

### Cause

`random_mutate_unique_features()` (`code/datums/dna/dna.dm:624`) writes a uniformly random hex string into whichever feature block it picks:

```dm
dna.unique_features = mutblock.modified_hash(dna.unique_features, random_string(mutblock.block_length, GLOB.hex_characters))
```

For the mutant color block, this can be any of 16,777,216 colors, including near-black ones. Callers include `code/datums/weather/weather_types/radiation_storm.dm:75`, `code/modules/reagents/chemistry/reagents/toxin_reagents.dm:63` and `code/modules/projectiles/projectile/special/floral.dm:49`. `scramble_dna()` (line 641) and `initialize_dna()` (line 352, `features[FEATURE_MUTANT_COLOR] = "#[random_color()]"`) use the same unrestricted source.

`scramble_dna()` has a second defect in the same code: its feature branch (`uf`) writes the new value into `M.dna.unique_identity` instead of `M.dna.unique_features` (line 660), so scrambling features modifies the wrong DNA hash.

### Fix

Commit "Fix issue 62385: random mutant colors can no longer be near-black":

- New helper `random_color_not_dark(threshold = 15)` in `code/__HELPERS/text.dm`: calls `random_color()` until `is_color_dark()` accepts the result.
- New `/datum/dna_block/proc/random_value()` in `code/datums/dna/dna_block.dm`, returning the old random hex string, so existing blocks behave as before.
- `/datum/dna_block/feature/mutant_color/random_value()` override in `code/datums/dna/blocks/dna_features_block.dm`, returning `random_color_not_dark()`.
- `random_mutate_unique_features()` and the feature branch of `scramble_dna()` now use `block.random_value()`; `initialize_dna()` uses `random_color_not_dark()`.
- The `scramble_dna()` feature branch now writes to `unique_features` instead of `unique_identity`.

The threshold of 15 is the same one the preferences menu uses for this color, so random mutation can no longer produce a color a player could not choose. Only the mutant-color block is restricted; other color blocks (for example tail or fish colors) still use fully random values.

### Verification

On the rebuilt fix, using the Lua editor: 1500 calls of the mutant-color block's `random_value()` gave 0 results below 15% lightness (darkest 15.29%); 1500 calls of `random_color_not_dark()` gave 0 dark results; 150 calls of `random_mutate_unique_features()` on a lizard produced 12 distinct mutant colors, none dark. The round's runtime log showed no new runtimes.

Not checked in game: a real radiation storm, mutation toxin or floral hit; the `scramble_dna()` feature branch after the `unique_features` correction (that change was made on reading the code); changeling and podperson color paths mentioned in the comment.

### Notes

- Nothing was changed for other species' DNA features, changelings, or podperson hair/skin color; the comments' reports on those were not tested.
- The `scramble_dna()` correction changes behavior for DNA scramblers: they previously overwrote part of the identity hash with feature data.

## #71922: Felinid mutation toxin "fixes" H.A.R.S.

### The bug

The report (2022): remove a non-felinid's limbs, give them the H.A.R.S. mutation (headless), then feed enough felinid mutation toxin to turn them into a felinid. The result can walk, talk and hear but has no arms, no head and cannot wear most clothes. A comment explains that `set_species` calls `regenerate_organs`, which resets the organs without checking for H.A.R.S., so a tongue, eyes, ears and a brain end up in a nonexistent head. Another comment asks not to break changelings walking without a head; a 2024 comment says it may already be fixed.

### Reproduction

Using the Lua editor on master:

1. Spawn a human and add the H.A.R.S. mutation with `dna:add_mutation(SS13.type('/datum/mutation/headless'), 'activated')`. The head is removed and the brain sits in the chest; the eyes, ears and tongue are gone (`brain=chest eyes=nil ears=nil tongue=nil`).
2. Dismember both arms.
3. Call `set_species` with `/datum/species/human/felinid`.

Evidence on master: the mob had no head and, as the report said, the arms stayed missing, but it also had no brain at all (`get_organ_slot('brain')` was nil). The floating head organs described in the report did not appear: the eyes, ears and tongue were not inserted because `regenerate_organs` only inserts an organ when the bodypart for its zone exists (`code/modules/mob/living/carbon/human/_species.dm:324`). The missing arms are not regenerated by a species change by design.

### Cause

Felinids have their own brain type (`mutantbrain = /obj/item/organ/brain/felinid`), so `regenerate_organs` (`_species.dm:288`) treats the brain as something to replace. It removes the existing chest brain (`_species.dm:313-323`) and then tries to insert the new one, whose zone is the head. With no head bodypart, the insertion condition (line 324) is false and the new brain is deleted at line 330. The mob ends up with no brain.

### Fix

Commit "Fix issue 71922: changing species no longer deletes the brain of a HARS mob", in `_species.dm`: just before the existing brain is removed, if the slot is the brain, the new brain's zone differs from the existing brain's zone, and the holder has no bodypart for the new brain's zone, then the new brain takes the old brain's zone (`new_organ.zone = existing_organ.zone`). The new brain is then inserted where the old one was, in the chest.

This keeps H.A.R.S. working and handles any headless mob with a species-specific brain, not only felinids. It leaves the head organs (eyes, ears, tongue) alone, since the existing bodypart check already prevents them from appearing.

### Verification

The same steps on the rebuilt fix: no head, brain present with zone "chest", `stat` 0 (not dead), species felinid. A control (normal human changed to felinid) still had a head and a brain in the head zone.

Not checked: removal of the H.A.R.S. mutation after the species change, and other species with their own brain types on a headless mob, changeling behavior (the comment's concern), and the exact report scenario (felinid mutation toxin instead of `set_species`; both reach the same `regenerate_organs` path in the code read, but the toxin was not used).

### Notes

- The report mentions inability to wear clothes and arms staying missing. Those are the same as for any limbless mob and were left as is.
- Related: #64122, linked by a commenter.

## #70176: Changing species drops your pocket contents

### The bug

The 2022 report says changing species (even to felinid) empties the pockets onto the floor; a comment says held items are affected too.

### Reproduction

Not reproduced. Using the Lua editor on master:

1. Spawned a human in a jumpsuit with a crowbar in the left pocket and a screwdriver in the right pocket and a wrench and wirecutters in the hands.
2. Called `set_species` one after another with felinid, lizard, moth, ethereal, skeleton, plasmaman, monkey and human, reading the pockets, uniform and hand contents after each change.

Evidence: after every change the pocket items, uniform and held items were all still in place. A species change only drops equipped items that no longer fit the new body through `worn_items_fit_body_check` (`_species.dm:332`, which calls `dropItemToGround` for items that `mob_can_equip` rejects).

### Notes

The bug was probably fixed some time after 2022. The test did not cover species with no pockets, mobs wearing backpacks or belts, or the exact way the original report changed species (an admin verb was not used, `set_species` was called directly).
