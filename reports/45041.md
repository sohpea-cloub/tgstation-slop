## Summary

All three issues concern portable turrets (`code/game/machinery/porta_turret/`). A lasertag turret built by hand worked on master, so #45041 was not reproduced: its small interface and team-only targeting are by design. For #46162, the turret's cover is a separate machine with its own health and no damage forwarding, so damaging the cover destroys only the cover and `process()` rebuilds it for free; cover damage now goes to the turret. For #53032, turrets without a cover (syndicate drop pod, shuttle) were left invisible and dense after being rebolted or switched off, until they next shot something; they are no longer hidden.

## The bug

### #45041: manually built tag-gun turret "doesn't work"

The reporter built a turret with a laser tag gun. It did not seem to activate, had no options list, and linking it to a turret control panel did nothing. A 2024 comment shows a screenshot of such a turret next to a regular laser turret, saying the tag-gun one has "no interface to shoot".

### #46162: turret covers regrow

The reporter broke AI upload turrets with a mech drill and they "self healed". A comment explains that the cover and the actual turret are two objects: hitting the cover makes it disappear for a second or two, then it reappears over the untouched turret.

### #53032: drop pod turrets look odd while unbolted and become invisible, unclickable barriers when rebolted

The reporter described syndicate drop pod turrets that look wrong while unbolted and, once rebolted, become invisible and unclickable (not even listed in the alt-click menu) but still block movement, until they shoot something or are shot out of action.

## Reproduction

All steps used the Lua editor to call procs directly on the test server, not player actions with tools in hand, unless stated.

### #45041 (not reproduced)

1. Using the Lua editor, run the turret's real construction steps: `wrench_act`, `item_interaction` with iron, a blue-tag gun, a proximity sensor (build step 5, `installed_gun` set).
2. Run the code of the final welding step by hand: create a `/obj/machinery/porta_turret/lasertag`, set `installation` to the gun's type and call `setup(gun)`. The welding itself was not performed by a player.
3. Observed: `team_color` was blue, the icon was the blue set, `on` was 1, `anchored` was 1, `machine_stat` 0, and a cover was created. The turret shot a human holding a red-tag gun ("hit by a laser tag beam").
4. The turret's interface opened (as a ghost, view-only as usual). It shows only the power button for lasertag turrets (`lasertag_turret` is passed to the UI at `code/game/machinery/porta_turret/portable_turret.dm:265`).

### #46162

1. Using the Lua editor, spawn a lasertag turret (integrity 160) whose cover has integrity 80.
2. Call `take_damage(200, "brute", "melee")` on the cover, which is what a drill or mech melee ends up doing.
3. Observed: the cover was deleted and the turret's integrity stayed at 160. A few seconds later `process()` created a new full-health cover (`portable_turret.dm:452-453`).

### #53032

1. Using the Lua editor, spawn a syndicate drop pod turret (`/obj/machinery/porta_turret/syndicate/pod`, no cover, always up). A fresh one had invisibility 0, icon `syndie_off`, `on` 1 and was in the process of popping up.
2. Call `toggle_on(FALSE)` so it pops down. Observed: invisibility 60, `dense` 1, anchored, icon `syndie_off`, no cover: an invisible dense barrier.
3. Call `wrench_act` to unbolt it (this needs the turret off and not raised). Observed: invisibility 0 but icon `turretCover`, which is the cover graphic and not suitable for a turret without a cover.
4. Call `wrench_act` again to rebolt. Observed: invisibility 60 again.

The first turret tried had been left in a muddled state by an earlier script, so the sequence was repeated on a fresh turret; it gave the same results (invisibility 60 and dense after toggling off, icon `turretCover` after unbolting, invisibility 60 after rebolting). The player wrench path was not used (see Verification).

## Cause

### #45041

No defect found. `/obj/machinery/porta_turret/lasertag` targets only the opposing team: `assess_perp` (`portable_turret.dm:1021`) scores a human 4 for a red/blue vest of the other team, 4 for holding a gun of the other team and 2 for one on the belt, and nothing else, so ordinary crew are never shot. `setup()` (`portable_turret.dm:1041`) takes `team_color` from the gun. The reported symptoms (no shooting at crew, only a power switch) match this design. The issue dates from 2019 and the code has changed since (`setup()` and `team_color` exist now).

### #46162

`/obj/machinery/porta_turret_cover` (`code/game/machinery/porta_turret/portable_turret_cover.dm:4`) is a separate machine with `max_integrity = 80`. Only some interactions are forwarded to `parent_turret` (the `attack_*`, `multitool_act`, `wrench_act` and `item_interaction` handlers); `take_damage` is not. A file comment says the same ("someone should just reroute these to the parent turret's procs"). Drills, mech weapons and similar damage the cover directly. When it breaks, `Destroy()` sets `parent_turret.cover = null`, and `process()` at `portable_turret.dm:452` ("if the turret has no cover and is anchored, give it a cover") creates a new one with full health.

### #53032

The turret type has `invisibility = INVISIBILITY_OBSERVER` (60) as its base value (`portable_turret.dm:32`: "the turret is invisible if it's inside its cover"). For a turret with `has_cover = FALSE` (`syndicate/pod`, `centcom_shuttle`: `portable_turret.dm:770` and `:924`) only `popUp()` (`:555`, `SetInvisibility(INVISIBILITY_NONE, id=type)`) makes it visible. Three code paths undid that:

- `wrench_act` at `:367` calls `RemoveInvisibility(id=type)` when rebolting, which drops back to the base value of 60.
- `finish_popdown()` (`:579-585`) always calls `SetInvisibility(2, id=type)`, even when there is no cover to show.
- `always_up` turrets only call `popUp()` when they shoot (`process()` at `:538` skips pop-down for them), so once hidden they stay hidden until they shoot.

The turret stays dense and anchored, so it is an unseen, unclickable barrier. Separately, `update_icon_state()` (`:190`) uses the `turretCover` icon whenever the turret is not anchored, even if it has no cover, which explains "look weird while unbolted".

## Fix

Two commits, in this order.

**"Fix issue 46162: damage to a turret's cover goes to the turret"**, in `portable_turret_cover.dm`:

- `take_damage` on the cover now forwards to `parent_turret?.take_damage(...)`.
- `ex_act` on the cover returns FALSE: the turret is on the same tile and takes the explosion itself, so the cover must not take it a second time.

**"Fix issue 53032: coverless turrets no longer vanish when rebolted or switched off"**, in `portable_turret.dm`:

- `finish_popdown()` hides the turret (`SetInvisibility(2, ...)`) only if `has_cover`.
- The anchoring branch of `wrench_act` calls `RemoveInvisibility` only if `has_cover` (a coverless turret keeps being visible).
- `update_icon_state()` uses `turretCover` only if `!anchored && has_cover`.
- `toggle_on(TRUE)` calls `popUp()` for `always_up` turrets, so they rise when switched on rather than only when shooting.
- `finish_popup()` calls `update_appearance()`, because a raised pod turret had still shown `syndie_off`.

No fix for #45041.

## Verification

### #46162

On a lasertag turret (integrity 160, cover 80) after a rebuild:

- `take_damage(50)` on the cover lowered the turret's integrity to 135; the cover was still the same object at 80.
- `take_damage(200)` broke the turret; its cover was removed by the turret's break handling (`atom_break`), as designed.
- A heavy explosion on a turret at 135 took it to 100, once, with the cover alive at 80.

No drill or mech was used; damage was dealt by calling `take_damage`. Not checked: whether the cover now reappears after the turret is repaired, and fire or other damage types.

### #53032

On a pod turret after the fix (all through Lua calls, not hand wrench): a fresh turret had invisibility 0 and, when raised, icon `syndie_lethal`. After toggling off: invisibility 0, icon `syndie_off`. After unbolting: invisibility 0, `syndie_off`, `anchored` 0. After rebolting: `anchored` 1, invisibility 0, `density` 1, `syndie_off`. After `toggle_on(TRUE)`: raised, `syndie_lethal`.

Regression check on a lasertag turret (with a cover): unbolting gave the `turretCover` icon, invisibility 0 and removed the cover; rebolting gave invisibility 60, a recreated cover and the `standard_off` icon. No new runtimes appeared.

Not checked: a real player wrenching a pod turret (the wrench path needs the turret off and not raised, which is rare for pod turrets; it would take something like a saboteur or EMP to disable one), the shuttle (`centcom_shuttle`) turret type specifically, and a turret control panel with the pod turret.

## Notes

- The two fixes are independent and touch different files.
- `porta_turret_cover` duplicates parts of the turret's logic, as the 2024 comment on #53032 complains; its `wrench_act` (`portable_turret_cover.dm:37-51`) has its own unbolting path which sets invisibility with a priority. It was not changed. The proper fix may be the rewrite that comment asks for rather than patches.
- A side finding, not changed: the cover's `Destroy()` (`portable_turret_cover.dm:16`) calls `parent_turret.RemoveInvisibility(type)` with the cover's own type, while the turret's visibility source id is the turret's type, so the call does nothing.
- #45041: the issue is from 2019 and likely already fixed or intended; the lasertag turret's UI shows only the power switch by design. If the reporter's turret still failed to fire, the likely explanation is that no one of the opposing team was wearing a vest or holding a gun, but this was not tested against the reporter's exact setup.
