## Summary

The HSL filter that `color_transition_filter()` builds for spraycans keeps the target's own lightness and only scales its saturation, so painting an object white desaturates it to grey instead of making it white, and an already grey object does not change at all. The first commit makes pale, low-saturation paint colors also pull the target's lightness toward the paint's, capped so shading stays visible. For #88879, the spraycan's "A color that dark on an object like this? Surely not..." check was based on the paint's lightness although the override mode no longer uses lightness; the second commit removes the check and the now unused `ALLOW_DARK_PAINTS_1` flag. The first change alters a shared helper that many other callers use; see Notes.

## The bug

### #67772

Painting things white with a spraycan (the issue also mentions chemicals) rarely seems to do anything. The result is a grey tint, or no change on an already grey object. The reporter saw white work only on a plastitanium table, which a commenter explained is a greyscale material atom that can take the color directly. The matrix cannot reach white for other sprites.

### #88879

A spraycan refuses to paint with very dark colors in override mode and prints "A color that dark on an object like this? Surely not...". Since #88201 override mode uses only the paint's hue and saturation, so a color's lightness has no effect on the result, yet the message is still triggered by it.

## Reproduction

On master, using the Lua editor on the test server (the round started with "Start Now"): spawn a human, an uncapped spraycan and emergency toolboxes. Set the can's `paint_color`, then call `use_on(toolbox, human, mods)` from Lua. A `nil` mods argument is a left click (multiply-saturation mode); `{right = 1}` is override mode. This calls the proc directly and does not go through the player's click.

1. Paint a red toolbox white with a left click. Result: the toolbox rendered grey (desaturated), not white.
2. Paint it white with an override. Result: the same as the left click. With saturation 0, both modes produce the same matrix.
3. Paint a toolbox black (`#000000`) in override mode. Result: `ITEM_INTERACT_BLOCKING` (2) and the "A color that dark..." message.
4. Same with `#200000`: blocked in the same way.
5. Paint with red (`#ff0000`) in override mode. Result: success (1). The override filter uses only hue and saturation, so this block was inconsistent with it.

## Cause

### #67772

`color_transition_filter` (`code/__HELPERS/colors.dm:162`) builds this matrix (starting around `:175`):

```
0, 0, 0,                          // ignore original hue
0, saturation, 0,                 // multiply the saturation by ours
0, 0, 1 - deducted_light,         // lightness: keep the target's, less a bit if saturated
hue, added_saturation, 0,         // apply our hue and some saturation
```

The lightness row has no constant term, so the target's own lightness is always kept. White has saturation 0, so the matrix only zeroes the target's saturation: a red toolbox becomes grey and a grey one is unchanged. White (lightness 1) can never be reached. The helper has many callers; the spraycan reaches it at `code/game/objects/items/crayons.dm:940` and `:986`.

### #88879

`crayons.dm:964` blocks the paint when `color_is_dark && saturation_mode == SATURATION_OVERRIDE && !(target.flags_1 & ALLOW_DARK_PAINTS_1)`, where `color_is_dark = is_color_dark(paint_color)` (`:953`). Override mode only uses hue and saturation, so the check refuses colors by a property the filter ignores.

## Fix

Commit "Fix issue 67772: spraycan white paint turned objects grey instead of white": `color_transition_filter` now also reads the paint's lightness. For paint with lightness above 0.5 it computes `added_light = min((lightness - 0.5) * 2 * (1 - saturation), MAX_COLOR_TRANSITION_LIGHTEN)`, with `MAX_COLOR_TRANSITION_LIGHTEN` defined as 0.75. The lightness row's multiplier becomes `(1 - deducted_light) * (1 - added_light)` and the row's constant term becomes `added_light`, so the target's lightness `L` becomes `L * (1 - added_light) + added_light`. Saturated colors have `(1 - saturation)` near 0, so they get little or no lightening; only pale, low-saturation colors such as white and silver are affected. The cap keeps the sprite's shading visible, so white paint results in near-white rather than flat white. An alternative would have been to special-case white in the spraycan code. That was not done, since the matrix is where the limit is, and other painting sources share it.

Commit "Fix issue 88879: spraycan "color that dark" check ignored what the paint does": removes the dark-color check from `crayons.dm`, and the `ALLOW_DARK_PAINTS_1` flag with its definition (`_flags.dm`), bitfield entry (`bitfields.dm`), and the two places that set it (`window.dm`, `decals/crayon.dm`). Windows still become opaque from the `COMSIG_OBJ_PAINTED` signal's `is_dark_color` argument, which is separate from the removed check.

## Verification

With the same Lua calls on a rebuilt server:

- White, with a left click or an override: the toolbox rendered near-white.
- Silver (`#c0c0c0`): light grey.
- Red: unchanged compared with before.
- Black in override mode: returned 1 (success, no message). The toolbox came out grey as before, not blocked.
- A full-tile window painted black stayed opaque (`color` `#000000`, `opaque` true).

Not checked: a real player click on the can, any other caller of `color_transition_filter` (see Notes), chemical white-paint sources, and painting mobs (`TRAIT_SPRAY_PAINTABLE`, which uses the same filter and should lighten as well). The unit tests were not run.

## Notes

- The lightening in `color_transition_filter` is a global change. Every caller with a pale, low-saturation color gets the new behavior. At master these include the fried-food element, dryable items, meat materials, paint cans (`paint.dm:124`), flashlights, the rainbow-type reagents in `other_reagents.dm`, xenobiology potions and crossbreeds, MODsuits, the crystallizer item coloring and eye coloring. None of these was individually checked. Reviewers should decide whether the helper itself is the right place, or whether the behavior should be opt-in through a parameter.
- The removal of `ALLOW_DARK_PAINTS_1` leaves bit 8 of `flags_1` unused (a gap).
- Black in override mode still gives a grey result, as before; the only change is that the message and block are gone.
- The `(1 - saturation)` factor and the 0.75 cap were chosen to keep shading visible; they are tuning values, not derived from anything in the code.
