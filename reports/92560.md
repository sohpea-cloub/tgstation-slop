# #92560: Genetic Makeup does not change TTS voice

| | |

| Status | Fixed on the branch and checked in game with a stand-in TTS server; the DNA console UI and unit tests were not run |

## Summary

Unique identity DNA had no block for the TTS voice, so transferring genetic makeup in the DNA console, or injecting a makeup injector, never changed the target's `voice`. The fix adds a voice block that stores an index into `SStts.available_speakers` and applies it with the rest of the identity. The block is kept in sync when a voice is first assigned on login or set with View Variables. Nothing is applied while TTS is disabled.

## The bug

The reporter saved Human 1's makeup in the DNA console, transferred it to Human 2 (and separately injected a full makeup injector into Human 3). Both took Human 1's appearance but kept their own TTS voice.

## Reproduction

TTS is off by default on the test server, so the voices had to be provided by a stand-in TTS HTTP service answering the voice list, configured through the server's dev overrides. Both were removed afterwards. The Lua editor cannot set `tts_enabled`.

The DNA console UI was not clicked. The same path was run from the Lua editor:

1. Spawn two humans, A and B, with different voices (A: "Echo Man", B: "Delta Woman").
2. Set `B.dna.unique_identity` to A's value and call `B:updateappearance()`. This is what the console transfer and the injectors do.
3. Read `B.voice`.

Observed before the fix: B's voice stayed "Delta Woman". The unique identity string was 57 characters long.

## Cause

`code/datums/dna/blocks/dna_identity_block.dm` defined identity blocks for gender, colors, height and so on, but none for `voice`. The console transfer and injectors write `unique_identity` and then call `updateappearance()` (`code/datums/dna/dna.dm:481`), which applies the identity blocks, so the voice was never read from or written to the DNA.

## Fix

Commit "Fix issue 92560: genetic makeup now carries the TTS voice":

- `code/datums/dna/blocks/dna_identity_block.dm`: new `/datum/dna_block/identity/voice`. `create_unique_block` stores the index of `target.voice` in `SStts.available_speakers` with `construct_block`. A mob without a valid voice gets a random index rather than the first speaker. If TTS has no speakers, a random hex string is stored. `apply_to_mob` sets `target.voice` from the block, and does nothing when TTS is disabled or there are no speakers.
- `code/modules/mob/living/carbon/human/login.dm:7`: after a human's voice is lazily assigned on `Login`, update the voice block.
- `code/game/atoms_movable.dm:1852`: the View Variables "Set TTS voice" action updates the block when the target is a human.

Since the block is part of unique identity, other users of it (changeling transformation, injectors) carry the voice too.

## Verification

With the stand-in TTS service, repeating the Lua steps above after the fix gave B the voice "Echo Man", and the unique identity string was 60 characters long. A human with no voice got a valid voice, and 30 calls to `random_mutate_unique_identity` never produced a voice outside the list. No runtimes appeared.

Not checked: the real DNA console UI, a real injector, pitch (it is not stored in DNA and was left alone), and the unit tests.

## Notes

- The unique identity string grows by 3 hex characters, so anything that assumes its length, or compares stored identities from before the change, should be considered. Only fingerprint-style uses of `unique_identity` were seen in the code and none were exercised.
- A human whose voice was set some other way after its DNA was generated (not through `Login` or View Variables) gets the stored voice back on any `updateappearance()`.
