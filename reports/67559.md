## Summary

`/obj/effect/turf_decal` applies itself to its turf as a `/datum/element/decal` overlay and then deletes itself, but it never passed its `pixel_x`/`pixel_y` to the element, so every mapped turf decal is drawn centered on the tile. The first commit adds offset parameters to the decal element and has `turf_decal` pass them, and keeps the offsets when decals are rotated, re-smoothed or moved with a shuttle. #76924 is a separate bug in the same area: each hit splatter landing on a full-tile window created a new `over_window` splatter in the window's `vis_contents` instead of merging. The second commit merges into the existing undried splatter.

## The bug

### #67559

A mapper can give a turf decal a pixel offset in the map editor, and the editor shows it offset. In game the decal is centered on the tile. The issue reporter noted this is not a map editor problem but a limitation of how decals work.

### #76924

When someone is hit repeatedly next to a full-tile window, every hit splatter that reaches the window adds another blood splatter on it, so the blood piles up. Splatters on walls do not behave like this.

## Reproduction

### #67559

No decal with a pixel offset exists in the repo's maps, so the "before" state was not observed in game. The cause was found by reading the code (see Cause). The fix was checked in game after the change (see Verification).

### #76924

On master:

1. Spawn a `/obj/structure/window/fulltile` on the tile east of a human, using the Lua editor.
2. From the Lua editor, call `spray_blood(4, 3)` on the human five times (direction 4 is east).
3. Run the SDQL2 query `SELECT /obj/effect/decal/cleanable/blood/splatter/over_window`.

Result: `9 objects selected`. Nothing else was bleeding in that round, so these were all splatters that had stacked on the window. This reproduces the bug by calling `spray_blood` directly, not by stabbing a mob. The count is above five because a single spray can send out more than one hit splatter.

## Cause

### #67559

`/obj/effect/turf_decal/Initialize` (`code/game/objects/effects/decals/decal.dm:82`) does:

```
T.AddElement(/datum/element/decal, icon, icon_state, dir, null, layer, alpha, color, null, FALSE, null)
```

and then returns `INITIALIZE_HINT_QDEL`. The mapped `pixel_x`/`pixel_y` are not among the arguments. `/datum/element/decal/Attach` (`code/datums/elements/decals/_decal.dm:68`) had no offset parameter, and `generate_appearance` (`:112`) never sets one, so the overlay's offset is always 0.

The same loss happens whenever the element is re-created from its stored appearance: `rotate_decals` (`:40`), `get_rotated_parameters` (the params list it builds), `shuttle_move_react` (`:172`) and `smooth_react` (`:194`) all rebuild the element from `pic.icon`, `pic.layer` and so on, without the offset.

### #76924

`/obj/effect/decal/cleanable/blood/hitsplatter/proc/land_on_window` (`code/game/objects/effects/decals/cleanable/blood.dm:925`) always creates a new splatter (`:934`) and adds it to the window's `vis_contents` (`:935`). The usual decal merging in `cleanable/Initialize` (`code/game/objects/effects/decals/cleanable.dm:28`) only looks at other decals on the same turf, and the new splatter's `loc` is the window, so nothing merges. A wall gets a single decal element, so it cannot stack.

## Fix

Commit "Fix issue 67559: keep pixel offsets on mapped turf decals":

- `/datum/element/decal/Attach` takes two trailing optional parameters, `_pixel_x` and `_pixel_y`, and applies them to the generated appearance when either is nonzero.
- `turf_decal` passes the offsets only when one is nonzero, and uses the old call otherwise. Ordinary decals therefore get the same element arguments as before, so they keep sharing one element instance. This applies also to the `RemoveElement` call in the `GLOB.running_create_and_destroy` (unit test) path of `Destroy`.
- Rotation, smoothing and shuttle re-adds pass `pic.pixel_x` and `pic.pixel_y` through, and the rotation params list now carries them.
- `/datum/element/decal/blood/Attach` (`code/datums/elements/decals/blood.dm`) called `..()` with its own argument list, which has extra trailing parameters (`_uses_filter`, `_emissive`). With the new parameters in the parent these would have landed in the pixel slots. It now forwards the parent's arguments explicitly.

Commit "Fix issue 76924: merge hit splatters landing on a window": `land_on_window` first looks through the window's `vis_contents` for an existing `over_window` splatter that is not deleted and not dried. If it finds one, it adds the blood DNA and bloodiness to it, calls `expire()` on the incoming splatter and returns TRUE. Otherwise it creates one as before.

## Verification

### #67559

A temporary `turf_decal` subtype (`icon_state = "bot"`, `pixel_x = 12`, `pixel_y = -9`) was added for the test only and not committed. It was spawned two tiles from the tester through the Lua editor, and the tile was rendered. The yellow "bot" box was shifted about 12 px right and about 9 px down from the tile center, matching the offsets.

Not checked: a real decal loaded from a map with an offset, shuttle rotation of an offset decal (this was only read through in the code), and the unit tests (not run).

### #76924

On a fresh round with the fix, the same Lua steps followed by the same SDQL2 query returned `1 objects selected`, and the splatter's examine text read as a pool of blood on the full-tile window. No new runtimes were seen.

Not checked: the "stab a mob" route from the issue, and whether a merged splatter's appearance (bloodiness, DNA) looks right beyond the single count.

## Notes

- The offset is preserved, not rotated, when a shuttle rotates, so an offset decal turns with the tile but its offset stays in the same screen direction. Rotating the offset too would be a design choice for a maintainer.
- Both fixes are in one branch because they were handled as one unit. The two changes are independent and can be split into separate PRs.
- Merging on windows only considers undried splatters, so once a splatter dries a new hit creates a fresh one.
- The first attempt at the `Attach` change set the offsets in an unconditional `else`, which would have written `null` offsets; it was changed to `else if(_pixel_x || _pixel_y)`.
