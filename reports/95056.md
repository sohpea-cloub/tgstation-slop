## Summary

The build mode map generator "Repair: Reload Block - Mass Delete - In Place" hung the server in an infinite loop when the selected region was not on a station z-level (CentCom, ruins, Lavaland, hyperspace). The region was never defined, the mass delete still ran, the map loader then loaded nothing, and its unset (infinite) bounds went into `block()`. The fix refuses to run on such regions, warns the admin, and stops using bounds from a load that placed nothing. A second commit makes build mode reject a second corner on a different z-level than the first, which is the plausible cause of #39164. #38053 was left unfixed.

## The bug

**#95056.** An admin in build mode picks the Map Gen mode, selects "Repair: Reload Block - Mass Delete - In Place", clicks two corners and confirms. On a station level it reloads the block from the map files. On a non-station level the server freezes for minutes (the reporter saw about two minutes, and an AFK/disconnected banner), and nothing visible happens. The reporter saw it on CentCom, a space ruin, Lavaland and hyperspace.

**#39164 (2018).** The reporter used "Full Mass Deletion" on a loaded space ruin and it deleted everything across z-levels. The comments could not reproduce it. One commenter asked whether the reporter had clicked a mirage (transition) border.

**#38053 (2018).** Turfs created by the build mode map generator keep the old turf's base turfs, so crowbarring a tile built over lava or space reveals lava or space.

## Reproduction

**#95056.** Reproduced with real build mode clicks on the test server, as an admin ghost:

1. Open build mode (F7), choose Map Gen, right-click the mode button and select "Repair: Reload Block - Mass Delete - In Place".
2. On z-level 1, click the two corners of a 5x5 area (x and y 98 to 102) and answer Yes to "Are you sure you want to run the map generator?".
3. The server process stayed at about 90% CPU for over five minutes. The admin tool call got no answer for more than 147 seconds, and no runtime was logged, which is consistent with an infinite loop.

The same steps on a station z-level reloaded normally.

**#39164.** Not reproduced on unfixed code. The cause was found by reading the code only.

**#38053.** Not tested in game. See Cause.

## Cause

**#95056.** `/datum/map_generator/repair/reload_station_map/defineRegion` (`code/modules/procedural_mapping/mapGenerators/repair.dm:108-116`) returns early when either corner is not on a station z-level:

```
if(!is_station_level(start.z) || !is_station_level(end.z))
	return
```

That leaves `x_low`, `y_low`, `x_high`, `y_high` and `z` at 0. Nothing then stops the run:

- `generate()` (`repair.dm:120`) still triggers the mass deletion of the selected block for the "Mass Delete" variants.
- The loader module (`repair.dm:19-55`) calls `load_map` with a crop region whose upper bounds are 0. The map reader skips every gridset, so nothing is placed and `bounds` stays at its initial infinite values (`code/modules/mapping/reader.dm`).
- `z_offset += bounds[MAP_MAXZ] - bounds[MAP_MINZ] + 1` then adds a nonsensical value, and `block(bounds[MAP_MINX], ..., z_offset - 1)` at `repair.dm:52-55` is given infinite coordinates, which never terminates.

No confirmation dialog or other check blocked a non-station region.

**#39164.** `handle_click` in `code/modules/buildmode/bm_mode.dm:77-88` stores corner B with no check of its z-level. `block(cornerA, cornerB)` covers every z-level between the two corners (used by the fill mode, `fill.dm:43`, and map generator `defineRegion`). If corner B is on another level, for example a space transition border turf, the whole range of levels is selected and mass deleted. This explains the report but was not demonstrated on the old code.

**#38053.** `place()` in `code/modules/procedural_mapping/mapGeneratorModule.dm:69` uses `T.ChangeTurf(turfPath)`, and `ChangeTurf` carries over the old turf's base turfs when none are passed (`code/game/turfs/change_turf.dm:118-121`). Fill mode uses `ChangeTurf` the same way (`fill.dm`, near line 63-66). So a floor generated over space or lava inherits those base turfs. This looks like replace-not-stack behaviour and was not tested.

## Fix

Two commits on the branch.

1. **"Fix issue 95056: reload block map generators hang the server outside the station z-levels."**
   - `defineRegion` now resets `z = 0` first and bails if the parent `defineRegion` failed or either corner is off-station.
   - `generate()` returns immediately when `z` is 0, so there is no mass delete and no load.
   - The loader module returns early if the parent `z` is unset. It also returns if `load_map` placed nothing (`bounds` null, or `bounds[MAP_MINZ] > bounds[MAP_MAXZ]`), after clearing `GLOB.reloading_map`. `GLOB.reloading_map` stays set during a hung run, which matches the reporter's note that a second reload was refused while the first was in progress.
   - In `code/modules/buildmode/submodes/mapgen.dm`, after `defineRegion`, a reload generator whose `z` is 0 prints "Reloading a block only works on the station's z-levels, and both corners must be on them!", deletes the generator and clears the selection. This is the warning the reporter asked for.
2. **"Fix issue 39164: build mode corner selection could span several z-levels."** `handle_click` rejects a second corner on another z-level than the first ("Both corners must be on the same z-level! Pick the second corner on z-level N.") and does not set corner B.

The commit message of the first fix also mentions "don't use bounds of a load that placed nothing" as a separate safety net, in case the region check is bypassed.

## Verification

Checked on a build with the fix, in game, with real build mode clicks:

- **#95056, non-station.** The same steps on z-level 1 now printed the warning above. There was no hang and the selection was cleared.
- **Station regression.** A "Reload Block - Mass Delete - In Place" run on a small region on z-level 2 (x 107 to 110, y 144 to 146) with Yes confirmed ran to completion, the server stayed responsive, and the region reloaded. The log only showed the usual pipe-stacking lines from reloading; no new runtime came from the map generator.
- **#39164.** Corner A was set on z-level 2, then the admin jumped to z-level 1 and clicked a turf. Chat showed "Both corners must be on the same z-level! Pick the second corner on z-level 2." and corner B was not set.

Not checked:

- The non-"In Place" "Reload Block - Mass Delete" variant was not run by hand. It shares `defineRegion` and `generate()` with the In Place variant, so the same guards apply.
- #39164's original symptom was not reproduced before the fix, so the commit hardens a plausible path rather than proving a fix.
- #38053 was not tested.

## Notes

- **#38053 is a design call.** Using `PlaceOnTop` instead of `ChangeTurf`, or passing base turfs per generator, would change behaviour for every existing use of the map generator. The issue is from 2018 and is vague, and the current behaviour is probably intended. It may be closed as intended, or a maintainer can choose.
- **Related existing bug.** On reconnecting in build mode, `code/modules/buildmode/buildmode.dm:63` (`post_login`) raised a runtime "Cannot read null.screen". It is unrelated to these commits, seen only when the test client reconnected, and was not investigated.
- **Reporter's remaining question.** The reporter was unsure if the plain (not In Place) variant also hung. By the code above it would, because it shares the same path, but this was not run.
- **Scope of the warning.** The new message appears when the region is chosen, before the confirmation dialog, so the admin never gets as far as confirming.
