# #90899: Spread kudzu loses its parent's mutation colour

| | |
|---|---|

| Status | Fixed, one-line change |
| Fix branch | [fix/90899](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/90899) |

## Summary

Kudzu is tinted by its mutations, but only the vine that receives a mutation keeps the tint. Every vine that spreads from it comes out in the default colour. `spawn_spacevine_piece()` copies the parent's colour with the wrong value: it passes the parent's whole `atom_colours` entry (a list of colour and colour type) to `add_atom_colour()` instead of the colour string. The fix indexes the entry with `ATOM_COLOR_VALUE_INDEX`.

## The bug

The report says kudzu changes colour when it develops a trait and then goes back to its default colour, which makes it hard to tell what a patch carries without examining every tile. Only the vine that gets the new mutation shows the mutation's hue. Each new vine that grows from it is built with an invalid colour, so it shows the default look and the hue never spreads.

## Reproduction

Reproduced by calling the relevant procs directly from the Lua editor, not by waiting for kudzu to spread in a round.

1. Start a round (or observe) on the test server and open the Lua editor as an admin.
2. Create a vine controller: `SS13.new('/datum/spacevine_controller', me.loc)`. Set its `mutativeness` to 0 so no random mutation is added to the child. Take the first vine from `ctl.vines` as the parent.
3. Take a mutation from `GLOB.vine_mutations_list` (here "Aggressive spreading", hue `#316b2f`) and call `add_mutation_to_vinepiece(parent)` on it.
4. Call `ctl:spawn_spacevine_piece(<adjacent turf>, parent, nil)` to create a child, and read `.color` of both.

Observed on master: parent `.color` was `"#316b2f"`; child `.color` was `nil`, so the child drew with the default look.

## Cause

`add_mutation_to_vinepiece()` tints a vine with `vine.add_atom_colour(hue, FIXED_COLOUR_PRIORITY)` (`code/modules/events/space_vines/vine_mutations.dm:17`). `atom_colours` stores, per priority slot, an entry of the form `list(colour, colour_type)`.

When a vine is spawned from a parent, `spawn_spacevine_piece()` copies the colour (`code/modules/events/space_vines/vine_controller.dm:87-88`):

```dm
var/parentcolor = parent.atom_colours[FIXED_COLOUR_PRIORITY]
vine.add_atom_colour(parentcolor, FIXED_COLOUR_PRIORITY)
```

`parentcolor` is the whole `list(colour, type)` entry, not the colour. `add_atom_colour()` then stores `list(list(colour, type), NORMAL)`, and the vine's resulting `color` is not a valid colour, so it falls back to the default. This matches the report: the colour appears on the vine that gets the mutation, and spread vines lose it.

## Fix

One commit, "Fix issue 90899: kudzu children keep the parent's colour". It changes line 87 to:

```dm
var/parentcolor = parent.atom_colours[FIXED_COLOUR_PRIORITY][ATOM_COLOR_VALUE_INDEX]
```

so the child receives the colour value, as the mutation code does. No alternative was tried.

## Verification

After rebuilding, the same procedure on the test server: parent, child, and a grandchild (spawned from the child) all had `.color` `"#316b2f"`.

Not checked: how the vines render in a real client (only colour values were read), natural spread during a round, and mutation combinations other than the single one used. The parent-with-no-colour case was not tried either: if a parent has no `FIXED_COLOUR_PRIORITY` entry, the new index would be applied to a null value. Whether that can happen was not examined.

## Notes

- The old code was unnoticed because the bad value is accepted silently; there is no runtime, only the default colour.
- The agents did not check for an upstream PR fixing this.
