| | |

## Summary
The reporter's screenshot shows the blocked tiles around a DNA vault offset by one to two tiles from its sprite. A DNA vault that is built normally has collision that matches its sprite exactly, so the report was not reproduced as such. The vault's collision comes from invisible filler objects placed once at `Initialize`. If the vault is moved afterwards, the fillers stay behind, which gives the kind of offset in the screenshot. The fix makes the fillers follow the vault when it moves. How the vault moved in the reporter's round is unknown.

## The bug
Players saw tiles they could walk through on the vault sprite's top corners, and blocked tiles extending below the sprite (red/green overlay in the issue's screenshot). The sprite is a 3x3 machine whose bottom middle tile is an open doorway.

## Reproduction
On master, with admin tools:

1. Using the Lua editor, spawned an `/obj/machinery/dna_vault` at one location (107,144 on the second z-level), and separately built one the normal way (a secured machine frame with the DNA vault board, then finished construction).
2. Inspected the vault with SDQL2/View Variables. It was anchored, facing south, with its sprite offset (pixel_x -32, pixel_y -64). It had six filler objects with density 1, at x±1 on the vault's row and on the two rows below it (x±1, y), (x±1, y-1), (x±1, y-2).
3. Checked the sprite: `icons/obj/machines/dna_vault.dmi` is 96x96. Per 32px tile, opacity was top row 100/100/100, middle row 100/34/100, bottom row 99/0/100, so the bottom middle tile is the open doorway. A render showed the sprite on x106..108, y142..144 sitting exactly over the fillers. So a vault built or spawned in place matches its collision; the layout in the code is correct. The sprite has not changed since 2016 according to the commit history.
4. Using a forced move of the vault from (107,144) to (107,146): the vault moved and the six fillers stayed at y142..144. This is the mismatch, and it looks like the screenshot (blocked columns away from the sprite).

The reproduction of the mismatch calls the move directly; no in-game player action that moves the vault was found (see Notes).

## Cause
`/obj/machinery/dna_vault/Initialize` (`code/modules/station_goals/dna_vault.dm:91-102`) computes the filler turfs relative to the vault once and creates the fillers there:

```
var/list/occupied = list()
for(var/direct in list(EAST,WEST,SOUTHEAST,SOUTHWEST))
	occupied += get_step(src,direct)
occupied += locate(x+1,y-2,z)
occupied += locate(x-1,y-2,z)
```

Nothing re-places the fillers later, and the vault has no `Moved` override, so any move after initialization leaves the collision behind while the sprite travels with the machine.

## Fix
One commit, "Fix issue 75532: DNA vault fillers follow the vault when it moves", in `code/modules/station_goals/dna_vault.dm`:

- The offset computation moved into a new proc `get_filler_turfs()` with the same offsets as before, used by `Initialize`.
- A new `Moved()` override recomputes those turfs (when the vault is on a turf) and `forceMove`s each existing filler to its new turf.

Re-placing existing fillers rather than recreating them keeps the `fillers` list and each filler's `parent` link intact.

## Verification
After rebuilding and starting a fresh round on the test server, a vault built at (107,144) had fillers at (108,144), (106,144), (108,143), (106,143), (108,142), (106,142). After a forced move to (107,146) the fillers were at (108,146), (106,146), (108,145), (106,145), (108,144), (106,144), so they followed the vault. The runtime log showed only a timer "qdeleted callback" runtime when the Lua editor finished the machine frame (the frame is deleted); it also occurred before the change and is unrelated.

Not checked: moving the vault by any in-game player action, turning or rotating it, and deconstruction or destruction after a move. The report's original round could not be examined.

## Notes
- The real trigger in the reporter's round is unknown. The vault is an anchored machine, and no wrench or pull path that moves it was found. If it was never moved, the cause is something that was not reproduced here (for example a client-side rendering offset).
- The change is defensive: it fixes a real failure mode but may not be what the reporter hit.
- Other multi-tile machines using the same filler pattern may have the same limitation; this was not checked.
