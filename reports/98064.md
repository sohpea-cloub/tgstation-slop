## Summary

The Cerulean species (the "fish" species of #98064) inherits `TRAIT_USES_SKINTONES` from `/datum/species/human`, so the preferences menu offers a skin tone that never shows, because a Cerulean's body is coloured by the fish tail colour. Clearing the species' `inherent_traits` hides the skin tone preference and removes the skin tone prompt from the mirror's race change. Separately, #75159 (hardcore random not applying on latejoin) was real: the latejoin spawn path never called `hardcore_random_setup`, which roundstart does. The branch adds that call. #36966 (random name/body when observing) no longer happens on master.

## #98064: skin tone offered to Ceruleans

### The bug

In character setup with the Cerulean species selected, a skin tone option is shown. Changing it has no visible effect on the character. The issue author suggested the option be hidden, and that the species should use mutant colour like lizards (referring to #98065).

### Reproduction

1. On the test server, spawn a Cerulean human and set its `skin_tone` to `african2` (via View Variables or SDQL2 / Lua).
2. Inspect its chest bodypart: `skin_tone` is `african2`, but `draw_color` is the fish tail colour (`#20e28e` in this run), not a skin tone colour. So the skin tone had no effect.
3. Read the species' `get_features()` for Cerulean: it contains `skin_tone`. This is why the preferences menu shows the option.

Done by setting variables on a spawned mob and reading the species data directly, not by clicking through the preferences UI on master. The in-game preferences screen before the fix was not captured separately; the issue's screenshot shows it.

### Cause

`/datum/species/human` sets `inherent_traits = list(TRAIT_USES_SKINTONES)` (`code/modules/mob/living/carbon/human/species_types/humans.dm:4`). `/datum/species/human/cerulean` (`species_types/cerulean.dm:1`) is a subtype and does not override it. The skin tone preference declares `relevant_inherent_trait = TRAIT_USES_SKINTONES` (`code/modules/client/preferences/skin_tone.dm:5`), so it counts as relevant to Ceruleans, and `species.dm:44` also sends `use_skintones` to the UI from the same trait.

The trait has no effect on Ceruleans' appearance because the fish organ set bonus puts a colour override on every non-robotic limb using the fish tail colour (`limb.add_color_override(carbon_owner.dna.features[FEATURE_TAIL_FISH_COLOR], LIMB_COLOR_FISH_INFUSION)`, `code/game/machinery/dna_infuser/organ_sets/fish_organs.dm:90`).

### Fix

Commit "Fix issue 98064: Ceruleans no longer offer a skin tone preference" adds `inherent_traits = list()` to `/datum/species/human/cerulean`, with a comment explaining why. Humans' only inherent trait is `TRAIT_USES_SKINTONES`, so nothing else is dropped. Other users of the trait also stop treating Ceruleans as skin-toned; for example the mirror's race change (`code/game/objects/structures/mirror.dm:221`) no longer prompts a Cerulean for a skin tone.

### Verification

On the test server after the fix: the `skin_tone` and mutant colour preferences report `has_relevant_feature` = 0 for the Cerulean, the fish tail colour preference reports 1, and a newly spawned Cerulean body still has the tail colour as `draw_color` (`#e5e75a` in this run).

Not checked: the actual preferences screen visually, and the mirror race-change prompt in play (the latter follows from the code only).

### Notes

- The issue also says the species should "use mutant color". That was interpreted as hiding skin tone, since the body already takes the fish tail colour (which has its own dark-colour restriction from PR 98067). The mutant colour preference is also not offered to Ceruleans after the fix (reported as not relevant), so the character setup shows only the fish tail colour. Whether that is the intended reading of "use mutant colour" is for a maintainer to decide.

## #36966: random name/body when observing

### Verdict

Not reproduced on master `87b93338`; no change.

### Reproduction attempt

Using admin tools, preferences were set to species lizard, gender female, real name "Fixedname Test", with Always Random Name and Always Random Body both enabled (values written as serialized preference values, e.g. species `lizard`). The character then observed. The resulting ghost was named "Jul-Lai", a random lizard-style name, not "Fixedname Test".

### Why it works now

When observing, `/mob/dead/observer/proc/set_ghost_appearance()` calls `client.prefs.apply_character_randomization_prefs()` (`code/modules/mob/dead/observer/observer.dm:833`) before `new_player.dm:102` reads `real_name` from the preferences to name the ghost. So the randomized name (which respects the species) is what gets used. The issue dates from 2018 and the code has since changed. Only the name/species case was tested; the gender and "it" pronoun symptoms from the issue (after transforming a ghost into a human with the Player Panel) were not.

## #75159: hardcore random not applied on latejoin

### The bug

With the Random Hardcore preference on, joining after roundstart leaves the chosen quirks untouched and gives no hardcore score at round end. (The report also describes name/looks being randomized; that is the separate always-random appearance path and was not investigated.)

### Reproduction

Established by reading the code rather than by a before-fix run. Roundstart spawning (`code/controllers/subsystem/ticker.dm:530-532`) does:

```
if(new_player_mob.client?.prefs?.should_be_random_hardcore(player_assigned_role, new_player_living.mind))
	new_player_mob.client.prefs.hardcore_random_setup(new_player_living)
SSquirks.AssignQuirks(new_player_living, new_player_mob.client)
```

The latejoin path in `code/modules/mob/dead/new_player/new_player.dm:247-250` called only `SSquirks.AssignQuirks(humanc, humanc.client)`.

### Cause

`hardcore_random_setup` (`code/modules/mob/dead/new_player/preferences_setup.dm:28`) picks the random quirk set into `all_quirks`, sets `hardcore_survival_score`, and logs the choice. Since latejoin never called it, `AssignQuirks` used the player's normal quirks and the score stayed unset.

### Fix

Commit "Fix issue 75159: hardcore random now applies on latejoin" adds the same two lines as roundstart before `AssignQuirks` in the latejoin path, inside the existing `JOB_ASSIGN_QUIRKS` and `roundstart_traits` checks.

### Verification

On a freshly started test server: in the lobby, the Random Hardcore preference was written through the Lua editor (read back as 1), the round was started, and the character joined as an Assistant. The game log contained "... started hardcore random with Pacifist, Food Allergy, Prosthetic Organ, Erratic, Touchy, All Nighter, Overconfident, Frail, Numb and Family Heirloom, for a score of 34." That line is only written by `hardcore_random_setup`. The spawned mob had the allergy, surplus liver and heirloom quirks.

Not checked: a run without the fix (no baseline), the end-of-round points payout, and whether `hardcore_survival_score` was set on the mob (the log line and quirks were used as evidence instead).

### Notes

`should_be_random_hardcore` still excludes heads of staff and team antagonists, so those latejoins are unchanged.
