# #82587: Admin combo HUD (antag HUD) stays on after ctrl+shift-click spawn or respawn

| | |
|---|---|

| Status | Fixed on a branch, verified in game for the ctrl+shift-click path |
| Fix branch | [fix/82587](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/82587) |

## Summary

An admin's "combo HUD" toggle keeps its state in `client.combo_hud_enabled`, but the HUD traits it adds live on the mob that was current when it was enabled. When the admin gets a new mob (ctrl+shift-click spawn from a ghost, respawn), the new mob has no HUD traits, yet the flag is still set, so `mob/Login()` re-shows the antagonist HUD while the medical/security/diagnostic HUDs are gone. The fix makes `Login()` turn the combo HUD off if the new mob does not carry the admin HUD traits.

## The bug

An admin ghost toggles the combo HUD, which shows the antag HUD, then spawns themself into a human with ctrl+shift-click on their own ghost (or respawns and joins normally). The other HUDs disappear as expected, but the antag HUD stays visible on the new body, which an admin playing a normal character should not have. The reporter notes this is not rare on downstreams that enable respawn.

## Reproduction

On master, with the test server and admin tools:

1. Start the round, and as an admin observer run the "Toggle Combo HUD" verb.
2. Using the Lua editor, spawn a human and give it a changeling antag datum (any antagonist works; the issue suggests the player panel).
3. Using the Lua editor, call `CtrlShiftClickOn(ghost)` on the admin's own ghost. This is the proc behind the ctrl+shift-click (`code/modules/mob/dead/observer/observer.dm:933`), which calls `change_mob_type(/mob/living/carbon/human, ...)`, replacing the ghost with a human.
4. On the new human mob, read `client.combo_hud_enabled` and count the antagonist alternate-appearance HUDs (`/datum/atom_hud/alternate_appearance/basic/antagonist_hud`) that list the changeling in `hud_users_all_z_levels`.

Observed before the fix: `client.combo_hud_enabled` was 1 and 2 antagonist HUDs were showing the changeling to the new mob, while the new mob had no admin HUD traits.

The respawn path was not run separately (see Verification).

## Cause

`/client/proc/enable_combo_hud()` (`code/modules/admin/verbs/admingame.dm:418`) sets `combo_hud_enabled = TRUE` on the client and adds the four HUD traits (security, medical, diagnostic, bot path) to `mob` with source `ADMIN_TRAIT`. `disable_combo_hud()` (`admingame.dm:433`) removes them from whatever `mob` is at that moment.

The antagonist HUD does not use traits. Its visibility check is

```dm
/datum/atom_hud/alternate_appearance/basic/antagonist_hud/mobShouldSee(mob/mob)
	return Master.current_runlevel >= RUNLEVEL_POSTGAME || (mob.client?.combo_hud_enabled && !isnull(mob.client?.holder))
```

(`code/modules/antagonists/_common/antag_hud.dm:61`), so it depends only on the client flag. When a client is given a new mob, `mob/Login()` reloads alternate appearances (`code/modules/mob/login.dm:99-100`, `alt_hud.check_hud(src)`), and `mobShouldSee` is true because the flag is still set. The traits stayed behind on the old mob, so the medical/security/diagnostic HUDs are gone but the antagonist HUD is on. Respawn goes through the same `Login()`, so it has the same cause.

## Fix

One commit, "Fix issue 82587: turn the admin combo HUD off when a client gets a new mob", adds to `mob/Login()` (`code/modules/mob/login.dm`), just before the alternate appearances are reloaded:

```dm
if(client.combo_hud_enabled && !HAS_TRAIT_FROM(src, TRAIT_SECURITY_HUD, ADMIN_TRAIT))
	client.disable_combo_hud()
```

If the flag is set but the new mob does not carry the admin HUD traits, the combo HUD is disabled, which also hides the antagonist HUD. The check keys off the traits (using `TRAIT_SECURITY_HUD` from `ADMIN_TRAIT` as a stand-in for all four) so that a mob that did get the traits kept the HUD. The alternative of moving the traits with the client was not tried.

## Verification

After rebuilding, the same ctrl+shift-click path was repeated: on the new human mob `client.combo_hud_enabled` was 0 and 0 antagonist HUDs showed the changeling.

Not checked: the respawn path (it goes through the same `Login()` but was not run); the HUD from the player's point of view in the client (counts were read from the server's HUD datums); whether other `Login()` paths where the mob keeps the traits behave sensibly (e.g. admin possession of a mob that was the one the HUD was enabled on); no unit test was added.

## Notes

- Side effect: an admin loses the combo HUD whenever they get a new mob (for example, after `aghost`) and must toggle it again. This is the same behaviour the other HUDs already have, since their traits stay on the old mob.
- A comment in the issue about a player keeping their traitor status after being sent to Thunderdome and appearing on the end-of-round manifest as surviving is a different problem and was not investigated.
