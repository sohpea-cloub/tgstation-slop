# #96589: The sign language toggle keybind does nothing

| | |
|---|---|
| Issues | [#96589](https://github.com/tgstation/tgstation/issues/96589): fixed (reproduced and verified by calling the key handler directly) |
| Status | Fixed |
| Fix branch | [fix/96589](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/96589) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

A key bound to the Sign Language action never toggled sign language. The action is created with `owner_has_control = FALSE`, so `Grant()` does not register the key-down signal handler, and the action's own `show_action()` later turned the flag on and gave the button but never registered the handler. The fix registers `COMSIG_MOB_KEYDOWN` in `show_action()` and unregisters it in `hide_action()`.

## The bug

The report says that setting a hotkey for the sign language toggle has no effect when the key is pressed. The button on the action bar presumably still worked (clicking it calls the same toggle); only the keybind did nothing.

## Reproduction

This was reproduced by calling the key handler from the Lua editor, not by pressing a physical key. The call is the one a client key press ends up making (`mob.focus.key_down`, which sends `COMSIG_MOB_KEYDOWN`).

1. Using the Lua editor on the test server, spawn a human and add `/datum/component/sign_language` with `_AddComponent`.
2. On the human's `/datum/action/innate/sign_language`, call `set_key('F')` to bind the key.
3. Call `key_down('f', client, 'F')` on the mob.
4. Observed on master: the action's `active` value was 0 before and still 0 afterwards. Nothing happened.

## Cause

`code/datums/actions/mobs/sign_language.dm:17` sets `owner_has_control = FALSE` on the action. In `/datum/action/proc/Grant` (`code/datums/actions/action.dm:121-123`) the key handler is only registered when that flag is set at grant time:

```dm
if(owner_has_control)
	RegisterSignal(grant_to, COMSIG_MOB_KEYDOWN, PROC_REF(keydown), override = TRUE)
	GiveAction(grant_to)
```

The sign language `Grant()` (`sign_language.dm:22`) calls the parent first, when the flag is still FALSE, and then calls `show_action()` for non-mute owners (line 36). `show_action()` (line 61) sets `owner_has_control = TRUE` and calls `GiveAction(owner)`, which only adds the button. Nothing registers `COMSIG_MOB_KEYDOWN`, so `datum/action/proc/keydown()` (`action.dm:454`), which compares the pressed key with the action's `full_key`, is never called for this action. The same happens when the action is shown again after a mute is removed (`on_unmuted`).

## Fix

One commit, "Fix issue 96589: sign language action keybind never fired", changing `sign_language.dm`:

- `show_action()` now calls `RegisterSignal(owner, COMSIG_MOB_KEYDOWN, PROC_REF(keydown), override = TRUE)`, the same call `Grant()` makes. `override = TRUE` avoids a duplicate-registration runtime if it was already registered.
- `hide_action()` now includes `COMSIG_MOB_KEYDOWN` in its `UnregisterSignal` list, so a muted owner (for whom the action is hidden) does not trigger the toggle by key.

The fix is local to this action. Changing the shared `Grant()` was not tried.

## Verification

After rebuilding and restarting the test server, with the same Lua setup (human with the sign language component, key `F` bound):

- Start: sign language off (0). After the key-down call: on (1).
- After adding the mute trait: on (1) (forced on by the mute handling).
- After removing the mute trait: still 1.
- Key-down again: off (0).

So the toggle works from a fresh grant and again after a mute/unmute cycle.

Not checked: a physical key press through a real client; setting the binding through the preferences menu (the test used `set_key`); a mute owner pressing the key while the action is hidden.

## Notes

- Other actions that set `owner_has_control` to TRUE after being granted may have the same flaw. This was not checked (a search for `owner_has_control = TRUE` would be the starting point).
