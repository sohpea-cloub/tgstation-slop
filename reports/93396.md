## Summary
The report said a newly created character keeps its randomised appearance only until the player switches slots or the server restarts, after which colours and other values are re-rolled. On current master this does not happen. The cause was that `randomise_appearance_prefs` kept the random values only in the in-memory cache because a brand-new slot had no savefile entry; upstream PR #97644 ("Fix randomise_appearance_prefs", commit `95ca80a0a`, 2026-08-29) creates the entry first. The fix is already in the tested master, and removing it reproduces the bug.

## The bug
When making a new character slot, whether or not the player edited it, switching to another slot and back (or a server restart) re-rolled the visuals: in the lizard screenshots, mutant colour, legs, spines and age (33 became 48) all changed. The report says it did not happen again for that character unless it was deleted.

## Reproduction
Not reproduced on unmodified master. To check this, and to confirm the cause, the test server was used with the character setup UI:
1. Unmodified master, fresh character data: open character setup on slot 1, change to slot 2 (a new slot), then change back to slot 1 and to slot 2 again. All values on return were identical (hair `#e1621d`, eye `#663300`, age 26, and so on). A lizard on a third new slot (mutant colour `#7fff7f`, short spines, digitigrade legs) also came back unchanged after a swap. After forcing a character and preferences save from the Lua editor, the saved preferences file matched the live values.
2. Old behaviour: the three-line block described under Cause was removed from `randomise_appearance_prefs`, the game rebuilt, and a fresh savefile used. Slot 1 had hair `#744729`, underwear `#ed8309`, skin tone indian, age 26. After changing to slot 2 and back to slot 1 it had hair `#a29a96`, underwear `#e60350`, skin tone latino, age 36. The scramble reproduced.
3. The block was restored and the game rebuilt. With a fresh savefile, slot 1 (hair `#fff2d6`, underwear `#d866cb`, skin tone mixed2, age 31) was identical after the same swap round-trip.

The screenshots' values could not be checked directly, only their symptoms.

## Cause
In the code the reporter was running, `randomise_appearance_prefs` (`code/modules/mob/dead/new_player/preferences_setup.dm:2`) wrote random values with `write_preference`, which writes into the savefile entry `character[slot]`. For a brand-new slot that entry did not exist, so the random values (colours, hair, age and so on) lived only in the preference value cache. `save_character` persists only recently updated keys (just the name here), so the first reload (a slot swap calling `load_character`, or a server restart) found nothing saved and re-rolled or defaulted the rest. Once loaded they were written to the savefile, which is why it "wouldn't happen again".

On master, lines 3-5 create the entry first:
```
var/tree_key = "character[default_slot]"
if(!(tree_key in savefile.get_entry()))
	savefile.set_entry(tree_key, list())
```

## Fix
None needed; PR #97644 already contains it.

## Verification
The round-trip comparison above on unmodified master, with the fix removed and with it restored. Not checked: an actual server restart (only slot swaps were tested), and live-server conditions the reporter mentioned (the reporter said it happened with a round time of 1 hour).

## Notes

- The issue can probably be closed as fixed by #97644.
