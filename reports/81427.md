## Summary

Click abilities with a custom cursor (pointed spells such as Mind Swap) put that cursor in `client.mouse_override_icon` and take it out again in their `unset_click_ability()` proc, which reaches the client through `on_who.client`. When the cast itself moves the client to another mob (Mind Swap) or the client leaves the mob first (the mob is deleted or ghosted), `on_who.client` is already null, the reset is skipped, and the cursor stays on the client. The fix adds a cleanup to `/mob/proc/become_uncliented()`, which runs when a client leaves a mob: if the mob's active click intercept is a cooldown or innate action whose `ranged_mousepointer` is the client's current override, the override is reset.

## The bug

Cast Mind Swap and you end up in the target's body with the spell's brain-shaped cursor still showing. The same leftover cursor is reported in #86745: a player used the Hallucination spell (a pointed spell) in a deathmatch, died, and kept the special red circle cursor through respawning and dying again. In both cases nothing in the new body will clear the cursor, because the ability that set it is no longer attached to the client's mob.

## Reproduction

All steps were done on master with the Lua editor (an admin tool), on a test server, with the tester first observing and then taking over a spawned human. The spell was activated by calling the same procs a click triggers, not by clicking in a client, so the player click path itself was not exercised.

#81427:

1. Using the Lua editor, spawn two humans, A and B, next to each other.
2. Create a `/datum/action/cooldown/spell/pointed/mind_transfer` for A, set its `target_requires_key` and `target_requires_mind` to false (so B, who has no player, is a valid target), and grant it to A.
3. Give A the client (`PossessByPlayer`), then call `set_click_ability(A)` on the spell. This is the "prepare to swap minds" state; the chat shows "You prepare to swap minds with a target...".
4. Call `InterceptClickOn(A, null, B)` on the spell, which is what a left click on B does. The cast succeeds and the client moves to B.
5. Read the client's cursor variables.

Observed on master after step 4:

- `client.mouse_override_icon` was `icons/effects/mouse_pointers/mindswap_target.dmi`.
- `client.mouse_pointer_icon` was the same file.
- A's `click_intercept` was nil, so the spell had been "unset" as far as the old mob was concerned.

The cursor is therefore stuck on the client, which is now in B's body, with nothing in the game that will reset it.

#86745: before the fix, I tried to reproduce it by setting the click ability and then deleting the client's mob from Lua. The outcome of that attempt on master is not recorded clearly; the only deletion attempt I have a record for (done on the fixed build) produced a runtime "Mob with client has been deleted" (`code/modules/mob/mob.dm`, in `Destroy()`) and left a destroyed mob holding the client, so it did not show a clean ghost/respawn transition. #86745 was therefore not reproduced separately on master. It is the same mechanism: Logout runs on the mob before anything unsets the click ability, so the client has already left when the reset runs.

## Cause

`unset_click_ability()` resets the cursor through the mob it is given (`code/datums/actions/cooldown_action.dm:321-329`):

```dm
on_who.click_intercept = null
if(ranged_mousepointer)
	on_who.client?.mouse_override_icon = initial(on_who.client?.mouse_override_icon)
	on_who.update_mouse_pointer()
```

The innate-action equivalent, `unset_ranged_ability()`, does the same at `code/datums/actions/innate_action.dm:70-76`.

For Mind Swap the order is wrong for this. `InterceptClickOn()` (`cooldown_action.dm:251-265`) calls `PreActivate(target)` first, which performs the swap and moves the client to the target. Only afterwards does it run

```dm
if(unset_after_click)
	unset_click_ability(clicker, refund_cooldown = FALSE)
```

so `clicker.client` is null and the `?.` silently skips the reset. When the mob is deleted or ghosted, `/mob/Logout()` (`code/modules/mob/logout.dm`) runs first, with the same effect.

`mouse_override_icon` is a var on the client (`code/modules/client/client_defines.dm:109`), not on the mob, so the stale value survives the change of body. The new mob's `Login()` calls `update_mouse_pointer()` (`code/modules/mob/login.dm:103`), and that proc copies `mouse_override_icon` into `mouse_pointer_icon` when it is set (`code/modules/mob/mob.dm`, `update_mouse_pointer`, around line 1304). So the new body actively re-applies the old spell's cursor.

## Fix

One commit, "Fix issues 81427, 86745: reset a ranged ability's cursor when the client leaves its mob". It adds to `become_uncliented()` in `code/modules/mob/mob.dm`, after the post-logout callbacks and before `canon_client` is cleared:

- If the mob's `click_intercept` is a `/datum/action/cooldown` or a `/datum/action/innate`, take its `ranged_mousepointer`.
- If that is set and equals `canon_client.mouse_override_icon`, reset the override to its initial value.

`become_uncliented()` is the shared cleanup that runs from `Logout()` and when the client is deleted, and `canon_client` is still set at that point, so the client can be reached even though `mob.client` is gone. The comparison against the ability's own cursor means the cleanup only removes the override the ability put there, and leaves an override set by something else (for example another mob's ability or a different system that uses `mouse_override_icon`) alone. The old mob keeps its `click_intercept`, as before.

The alternative of fixing it inside the ability procs was not taken: they only know the mob, and by the time they run the mob no longer has the client.

## Verification

Same steps as in the reproduction, on a server built with the fix:

- Mind Swap (#81427): with the click ability set, the client's `mouse_override_icon` and `mouse_pointer_icon` were both the mindswap cursor before the cast. After `InterceptClickOn(A, null, B)` the client was in B's body and both variables were nil, and A's `click_intercept` was nil.
- Death/removal path (#86745): the client possessed a human with the spell, `set_click_ability` set the override to the mindswap cursor, then the human was dusted. The client became a ghost and both the override and `mouse_pointer_icon` were nil. This is the path closest to the report (the caster stops being the client's mob).

Not checked:

- The actual cursor as drawn on a player's screen; only the server-side variable values were read.
- A real left click on a target in a client; the spell was triggered through its proc.
- The exact scenario of #86745 (the Hallucination spell in a deathmatch with respawn); the dust test used Mind Swap's pointer and has the same cause but is not that scenario.
- Dusting or deleting the mob on master, so there is no before/after pair for #86745.
- Other users of `mouse_override_icon` (for example the spawn panel and the pod launcher); they were not touched and were not tested.

## Notes

- The fix leaves the previous mob's `click_intercept` set to the spell after a logout. That was the behaviour before, and nothing here depends on it, but it means the old body (if it survives) still believes its ability is armed.
- Only the two action types that have `ranged_mousepointer` (`/datum/action/cooldown` and `/datum/action/innate`) are handled. A different click-intercept holder that sets `mouse_override_icon` would need its own handling.
- Side observation, not tested: in `unset_ranged_ability()` (`innate_action.dm:70-76`) the reset assigns `mouse_override_icon = initial(owner.client?.mouse_pointer_icon)`, i.e. it reads a different variable than the one it writes and goes through `owner` rather than `on_who`. This is harmless only if both initial values are null.
- No upstream pull request fixing this was looked for in the inputs.
