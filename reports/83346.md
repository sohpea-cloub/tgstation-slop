## Summary

The admin fax panel built its list of fax machines once, when the panel object was created, and kept it as weak references. `get_fax_by_name()` compares the name sent by the UI with each machine's current `fax_name`, so a fax that has been renamed (for example with a multitool), destroyed, or built after the panel was created is not found. The "send" action then calls `receive()` on null and runtimes, and the admin sees nothing. The fix looks the faxes up live every time and, when a name no longer resolves, tells the admin and refreshes the dropdown.

## The bug

An admin on Icebox tried to send a fax to the "Service Hallway" fax machine from the Admin Fax Panel. The send did nothing visible in game, and the runtime log showed:

```
runtime error: Cannot execute null.receive().
 - proc name: ui act (/datum/fax_panel_interface/ui_act)
 -   source file: code/modules/admin/admin_fax_panel.dm,130
```

Faxes the reporter had spawned themselves worked. The line number differs slightly from master (132), but the proc and the error are the same.

## Reproduction

Done on master with admin tools, as an observer. The test round was on MetaStation, not Icebox; it has a fax named "Service Hallway" as well, which was used as a stand-in, so the exact machine from the report was not tested. The reporter's cause is not known; this reproduction shows one way to get the same runtime.

1. Start a round and observe. Open the Fax Panel verb. Its fax list (17 entries on the test map) included "Service Hallway".
2. With the panel still open, use the Lua editor to rename that machine: set its `fax_name` to "Renamed Hallway". This does what the multitool rename does (`code/modules/paperwork/fax.dm:209-219`). An SDQL2 `UPDATE ... SET fax_name` was tried first, but it hit a parsing error and changed nothing; the Lua edit was what was used.
3. In the still-open panel, send a fax to "Service Hallway" (the old name, still in the dropdown). The send action was called directly with `faxName = "Service Hallway"`.

Observed on master: `runtime.log` contained "Cannot execute null.receive()" in `/datum/fax_panel_interface/ui_act`, at `code/modules/admin/admin_fax_panel.dm`, line 132, with the same call stack as in the report. The admin saw nothing happen.

## Cause

`/datum/fax_panel_interface/New()` (`code/modules/admin/admin_fax_panel.dm:20-25`) walks all fax machines once and stores a weak reference to each in `available_faxes`. The list is used in two places:

- `ui_static_data()` (`:62-76`) builds the dropdown from it. Static data is sent to the UI once when the panel opens and is not refreshed.
- `get_fax_by_name()` (`:42-51`) resolves the name sent by the UI by comparing it with each stored machine's current `fax_name`.

If a machine is renamed after the panel was created (a multitool rename, `fax.dm:209-219`), the dropdown still offers the old name, and `get_fax_by_name()` returns null because no machine has that name now. A machine that was destroyed fails the weak reference, and a machine built after the panel opened is not in the list at all. `ui_act()` does not check the result before using it, so the `"send"` branch runs `action_fax.receive(our_fax, sending_fax_name)` (`:132`) on null. The `"follow"` branch passes null to `admin_follow()` in the same situation.

Whether this is what happened on Icebox is a guess: someone may have renamed that fax, or the panel was opened before it changed. This was not tested on Icebox.

## Fix

One commit, "Fix issue 83346: admin fax panel looks faxes up live instead of from a stale snapshot":

- Removes `available_faxes` and the code in `New()` that filled it.
- Adds `get_available_faxes()`, which scans `SSmachines` for all `/obj/machinery/fax` machines each time and skips `/obj/machinery/fax/admin`, as the old code did.
- `get_fax_by_name()` and `ui_static_data()` use `get_available_faxes()`.
- In `ui_act()`, for the `follow` and `send` actions: if the name does not resolve to a fax, the admin gets the warning `No fax machine named "<name>" exists (it may have been renamed or destroyed). The fax list was refreshed.`, the static data is pushed again so the dropdown shows the current names, and the action returns without doing anything.

A live lookup was chosen over keeping the snapshot and refreshing it on events because there is no signal for a fax rename, and rebuilding the list is cheap compared with the cost of a stale entry. The guard also covers the case where the name was never valid.

## Verification

After rebuilding, the same steps were repeated on the test server (open the panel, rename "Service Hallway" with Lua, send to "Service Hallway").

- The admin received the chat warning above, and the panel's fax list changed from "Service Hallway" to "Renamed Hallway" without being reopened.
- There was no runtime: `runtime.log` had no fax entries.
- Sending to "Renamed Hallway" then worked and the admin log recorded "has sent a custom fax message to Service Fax Machine" (the machine's own `name` is unchanged by the rename).

Not checked: Icebox itself and the original "Service Hallway" machine; a destroyed or newly built fax with the panel open; the `follow` action with a stale name (covered by the same guard, but not run); a real multitool rename by a player (a Lua edit of `fax_name` was used instead); the fax panel UI's own behaviour when the dropdown contents change under a selected entry.

## Notes

- A `send` action with no `faxName` at all also gives a null `action_fax`, but the UI disables the button without a fax selected, so it is not reachable from the panel. The new guard only covers the case where a name was supplied. This case was left alone.
- The `createPaper` and `preview` actions do not use `action_fax`, so they were not changed.
- The report's testmerges (background checks station trait, cache lifespan) are not related to the cause found here.
