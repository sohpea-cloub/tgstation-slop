## Summary

`can_close_job()` in the Plexagon HR Core program tested the same population limit that is used for opening slots, so Close was only enabled for jobs that already had more slots than the cap allows. It should test whether the slot is unfilled. The fix restores that rule. A second commit replaces the full-table cooldown overlay in the tgui interface with a notice, so prioritizing is no longer blocked during the cooldown (#92187).

## The bug

**#65202:** In the Plexagon HR Core app, the "Close Job" button is greyed out regardless of how many slots are open, including slots the user just opened.

**#92187:** After opening a slot, the app goes on cooldown and an overlay covers the whole job table, so prioritizing jobs is impossible. Prioritizing has no cooldown on the server.

## Reproduction

### #65202

Reproduced on master `87b93338` by calling the program's procs from the Lua editor, not by clicking in the app. The player count on the test server was 1, so the population limit was emulated.

1. Start the round (`Start-Now`) and open the Lua editor.
2. Create a `/datum/computer_file/program/job_management` and read the Clown job: `total_positions` was 1, `current_positions` 0, and the cooldown had elapsed.
3. With one player, the limit is `players * max_relative_positions / 100` = 0.3. `can_close_job` returned 1 (1 > 0.3) and `can_open_job` returned 0.
4. Set `max_relative_positions = 1000` to emulate a populated station (limit 10). `can_open_job` returned 1 and `can_close_job` returned 0, although the Clown slot was open and unfilled.

The working estimate was that with the default 30% a job's close check fails once the slot count is no more than 30% of the player count (for example a single slot at 4 or more players). That was derived from the formula, not measured with a populated round.

### #92187

Not reproduced in a client. The cause is visible in the tgui source (see Cause). On the server side, `PRG_priority` was confirmed to work during the cooldown after the fix.

## Cause

### #65202

`code/modules/modular_computers/file_system/programs/jobmanagement.dm:48`:

```dm
/datum/computer_file/program/job_management/proc/can_close_job(datum/job/job)
	if(job.total_positions > length(GLOB.player_list) * (max_relative_positions / 100))
```

This is the mirror of `can_open_job()` (line 40), which allows opening only while `total_positions <= players * max_relative_positions / 100`. For closing, the condition was therefore true only for jobs above the opening cap, and the cooldown / instant-close branch (`opened_positions[job.title] > 0`) was nested inside it. The ID console's original rule was that a slot may be closed when `total_positions > current_positions`. The result is `status_close` (line 129) being false for nearly every job.

### #92187

`tgui/packages/tgui/interfaces/NtosJobManager.jsx` rendered a `<Dimmer>` ("On Cooldown: Ns") over the whole `<Section>` while `cooldown > 0`. Open and Close are already disabled server-side by `status_open` / `status_close` during the cooldown. `PRG_priority` has no cooldown. Instant closing of a slot that was opened earlier (`opened_positions > 0`) is also allowed during cooldown. The dimmer blocked all of these.

## Fix

Two commits.

- "Fix issue 65202: Plexagon HR Core can close unfilled job slots again": `can_close_job` now checks `job.total_positions > job.current_positions`, with a comment. The cooldown / instant-close logic is unchanged.
- "Fix issue 92187: Plexagon HR Core cooldown no longer blocks prioritizing": the `Dimmer` is replaced by a `NoticeBox` reading "Slot changes are on cooldown: Ns", and the unused `Box` and `Dimmer` imports are removed. The notice is shown above the table.

A notice was chosen over making individual buttons depend on the cooldown because the server-side status flags already disable Open and Close.

## Verification

On the rebuilt test server, with a Head of Personnel PDA holding a captain's spare ID, using the real `ui_act`:

- Close on a Clown slot with total 1 and 0 filled: allowed (`can_close_job` 1); `PRG_close_job` brought total to 0.
- Close on Mime during the cooldown: not allowed (0), so the cooldown is still enforced.
- `PRG_priority` during the cooldown: a job was prioritized.
- Reopening the closed slot worked (total went back to 1).
- A slot with 1 total and 1 filled could not be closed (0/0).

Not checked: the tgui change was built successfully but never viewed, because the test client does not run tgui JavaScript. The layout and text of the notice need a visual check with a real client. The population limit was emulated with `max_relative_positions = 1000`; a real populated round was not run.

## Notes

- #92187 is related to #65202 only through the same app; the server logic for the cooldown was already as the issue wants.
- The `can_open_job` population limit was not changed.
