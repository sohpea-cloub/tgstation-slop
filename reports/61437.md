| | |

## Summary

The Ollie action marks the skateboard with `BLOCK_Z_OUT_DOWN`, a flag that stops open space from dropping anything that carries it. The flag is supposed to be cleared when the ollie ends, but two paths never clear it correctly: the "too exhausted" early return clears the wrong flag (`CAN_BE_HIT`), and `grind()` resets the flags only after its final step, so a board that grinds off a table onto open space enters it still flagged and is never dropped afterwards. The fix adds a `land()` proc on the skateboard that clears the flag and immediately drops the board if it is over open space, and uses it on every path that ends an ollie or a grind.

## The bug

On a multi-z map a skateboard can be left hovering over open space indefinitely. The issue reporter describes ollieing next to a gap and then riding across open space as if it were floor; unbuckling and re-buckling does not help and the board stays immune to falling until it is picked up. A later comment (2024) says it still happens after grinding on a table or rail, while an unassisted ollie into the gap correctly drops the rider and board.

What is actually happening is that the board keeps `BLOCK_Z_OUT_DOWN` in its `obj_flags`. Open space checks that flag on everything in its contents before letting it fall, so a flagged board never falls.

## Reproduction

The flag defect was reproduced on the MultiZ Debug map (two station levels; the upper one has open space over a lower level). The player action was triggered through admin tools rather than by pressing the Ollie button.

1. Load the MultiZ Debug map and start a round.
2. Using the Lua editor, spawn a human and a `/obj/vehicle/ridden/scooter/skateboard` on a floor tile of the upper level next to open space (the test used x=124, y=135, z=3, with open space to the north), and buckle the human to the board.
3. Using Lua or View Variables, set the board's `instability` to 200, so the ollie's stamina cost (`instability * 0.75`) pushes the rider's stamina loss to 100 or more.
4. With SDQL2, trigger the ollie action: `CALL Trigger(owner, 0) ON /datum/action/vehicle/ridden/scooter/skateboard/ollie`.
5. Read the board's `obj_flags`.

Evidence on master (as recorded during testing): the board's `obj_flags` went from 2 (`CAN_BE_HIT`) to 32 (`BLOCK_Z_OUT_DOWN` only); the rider's stamina loss was 120 and the rider was unbuckled. `CAN_BE_HIT` was cleared and the hover flag left set, which matches the defect described below. The same procedure on the fixed build left `obj_flags` at 2.

Not reproduced: the literal steps of the issue (a successful ollie into a gap). At master, a successful ollie without a table at the landing tile clears the flag before the rider moves, so that path should not hover. The grind-off-a-table path from the 2024 comment was identified by reading the code and was not exercised in game.

## Cause

`code/modules/vehicles/vehicle_actions.dm:362` sets the flag at the start of every ollie:

```dm
vehicle.obj_flags |= BLOCK_Z_OUT_DOWN
```

and it is cleared only in the final `else` branch (`vehicle_actions.dm:383`, no table or tram rail on the landing tile). The other exits leave it set:

- The stamina failure branch (`vehicle_actions.dm:368-376`) runs `vehicle.obj_flags &= ~CAN_BE_HIT` (line 369). That is the wrong flag: it clears the flag that lets the board be hit and leaves `BLOCK_Z_OUT_DOWN` in place. The rider is unbuckled and thrown, and the board stays flagged.
- `grind()` (`code/modules/vehicles/scooter.dm:133`) calls `step(src, dir)` first and only then resets `obj_flags = CAN_BE_HIT` (lines 136 and 144). A board that steps off the end of a table onto open space therefore arrives while still flagged, and nothing re-triggers a fall after the flag is cleared.

The flag takes effect in `code/game/turfs/open/openspace.dm:103-110`:

```dm
/turf/open/openspace/zPassOut(direction)
	if(direction == DOWN)
		for(var/obj/contained_object in contents)
			if(contained_object.obj_flags & BLOCK_Z_OUT_DOWN)
				return FALSE
```

so a flagged board on open space never gets a downward move.

## Fix

One commit, "Fix issue 61437: skateboards stayed hovering over open space after a failed ollie or a grind", changing `scooter.dm` and `vehicle_actions.dm`:

- New `/obj/vehicle/ridden/scooter/skateboard/proc/land()` in `scooter.dm`: clears `BLOCK_Z_OUT_DOWN`, and if the board's location is an open space turf, calls that turf's `zFall(src)` so the board drops immediately.
- The ollie's non-table branch now calls `vehicle.land()` instead of clearing the flag by hand, so a plain ollie landing on open space also falls at once.
- The stamina-failure branch no longer clears `CAN_BE_HIT`; it calls `vehicle.land()` after unbuckling the rider.
- Both exits of `grind()` (the board lost its rider or left the table, and the rider lost their footing) call `land()` after resetting their state.

Re-checking the fall explicitly was chosen because clearing the flag alone is not enough: nothing else asks open space to reconsider a board that is already standing on it. A timer or a trait with a source could track the "in the air" state instead of the raw flag; neither was tried.

## Verification

Checked in game on the rebuilt fix: repeating the reproduction steps above left the board's `obj_flags` at 2 after the failed ollie.

Not checked:

- A board actually dropping a z-level. The open space on this map's upper level lies in an area with zero gravity (`has_gravity` returned 0), and `zFall` returned 0 for an unflagged board and for a board with `BLOCK_Z_OUT_DOWN` alike, so nothing falls there regardless of the flag. A test needs an area with gravity over open space (an attempt to set `default_gravity` on the area still showed `zFall` returning 0 and no change of z-level, so it was inconclusive).
- The grind path (ollie onto a table, grind off its end onto open space), before or after the fix.
- A successful ollie that lands on open space, before or after the fix.
- Normal play with the Ollie button; the action was triggered through SDQL2.
