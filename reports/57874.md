## Summary

The issue reports that a multi-line message sent to Central Command from a communications console is "censored" after the first line in the post-round logs. On current master the whole message is written to the game logs: the readable `game.log` keeps every line (continuation lines get a ` - ` prefix) and the `game.log.json` file keeps the full text with `\n` escapes. Nothing in the tgstation code truncates at a newline, so no fix was made. The most likely explanation is that the 2021 reporter was reading the logs through an external viewer that dropped the ` - ` continuation lines.

## The bug

As reported (March 2021): a player writes a message with line breaks in the communications console's "message CentCom" box and sends it. Admins see the message with its formatting. In the post-round logs, everything after the first line is missing, and the reporter's screenshot shows the logs saying the text was censored. The reporter also wondered whether this was intended.

## Reproduction

Attempted on master with admin tools; the bug did not appear.

1. Started a test round and joined as an observer.
2. Opened the Lua editor and, in a new Lua state, found the communications console on the CentCom Recovery Ship. Set its `authenticated` var to 1, its `authorize_access` to `{"captain"}` and `authorize_name` to a name. Spawned a human on the console's tile.
3. Gave the admin's own ckey to that human (so it was controlled by a real client), then clicked the console to open its tgui window.
4. Sent the console's `messageAssociates` action with the message `"FIRSTLINE hello\nSECONDLINE world\n\nTHIRDPARA end"`. The game replied "Message transmitted to Central Command." and the deadchat announcement showed the message with the line breaks flattened to spaces.

This exercises the real console action (`ui_act` through the tgui window), but the message text was injected as a tgui action parameter rather than typed into the console's text box. The text box's own behavior with the Enter key was not tested.

Evidence from the round's logs:

`game.log`:

```
GAME-SAY: testplayer/(...) (mob_3017) (message to CentCom) "FIRSTLINE hello
 - SECONDLINE world
 - 
 - THIRDPARA end" (CentCom Recovery Ship (110,44,1))
```

`game.log.json`:

```
"msg":"... (message to CentCom) \"FIRSTLINE hello\nSECONDLINE world\n\nTHIRDPARA end\" (CentCom Recovery Ship (110,44,1))"
```

All four lines of text are present in both files. (The guest name in the first line is the test client's ckey.)

## Cause

There is no defect that matches the report. The path the message takes:

- `code/game/machinery/computer/communications.dm:236-257`: the `messageAssociates` action sanitizes the text with `trim(html_encode(params["message"]), MAX_MESSAGE_LEN)`, calls `message_centcom()` (or `message_syndicate()` when emagged or on a Syndicate console), and then calls `user.log_talk(message, LOG_SAY, tag = "message to [associates]")` at line 257.
- `code/__HELPERS/logging/talk.dm:42`: `log_talk()` wraps the message in quotes and calls `log_message()`.
- `code/__HELPERS/logging/_logging.dm:98`: `log_message()` builds the log text and sends it to `log_say()` for `LOG_SAY`, which logs to the game-say category.
- `code/modules/logging/log_category.dm:66-70` and `code/modules/logging/log_entry.dm:119-125`: each entry is written twice, once as readable text and once as JSON (`write_entry_to_file`, line 116, uses `WRITE_LOG_NO_FORMAT`). For categories without `internal_formatting` (the default is FALSE, `log_category.dm:28`), the readable text is written with `WRITE_LOG` (line 125).
- `code/__DEFINES/logging.dm:196`: `WRITE_LOG` is `rustg_log_write(log, text, "true")`. With formatting on, rust-g indents every line after the first with ` - ` so that a multi-line entry is visibly one entry. That is where the ` - ` prefixes in `game.log` come from.

No step truncates the text at a newline. The text is intact in the plain-text log (with the ` - ` markers) and in the JSON log (with `\n`).

## Fix

None. The cause of the original report is not in this repository's code. A tool that reads `game.log` line by line and treats lines starting with ` - ` as noise or as separate non-entries would show only the first line, which matches the description. That was not confirmed, since the reporter's log viewer was not examined (the issue links to an external round-log site and a screenshot).

## Verification

Checked in game (see Reproduction): one multi-line message to CentCom produced complete entries in both `game.log` and `game.log.json`.

Not checked:

- The Syndicate and emagged-console branches (they share the same `log_talk` call at line 257 but were not run).
- A message typed in the real console UI with the Enter key (the text was injected as an action parameter).
- Any viewer or parser of the logs outside the game.
- Whether older rust-g or log-pipeline versions behaved differently in March 2021.

## Notes

- The continuation-line format is generic to every multi-line entry in every readable log category, so changing it is outside this issue's scope. The JSON twin of each log is lossless and is the better source for tools.
- The deadchat announcement of the same message (sent right after the log call, `communications.dm:258`) showed the line breaks flattened to spaces in the test. That is a different output from the log and was not part of the report; its cause was not investigated.
- The issue can probably be closed as obsolete or as an external log-viewer matter unless the reporter can show a current log file that is actually missing text.
