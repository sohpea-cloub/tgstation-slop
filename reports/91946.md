## Summary

Radio messages that do not pass through a working Common telecomms server carry no channel name, and `get_radio_name()` then falls back to formatting the raw frequency, so chat shows `[145.9]` instead of `[Common]`. Since channel names moved into the telecomms servers, only a server stamps the name. The fix adds a reverse lookup of the default radio channels (frequency to name) and makes `get_radio_name()` use it before the raw-frequency fallback. #88799 (radio sounds in hard crit) could not be reproduced: every radio sound is already gated on `TRAIT_DEAF`, which hard crit adds.

## The bug

### #91946

A player speaks into a station bounced radio and the chat line reads `[145.9] John Doe says, "..."` instead of `[Common] John Doe says, "..."`. The reporter suspected a recent radio rework. The issue lists a test merge of an unrelated UI helper PR and no round conditions, so whether a telecomms server was down in their round is unknown.

### #88799

The reporter said radio noise is heard while in hard crit, although hard crit is supposed to deafen.

## Reproduction

### #91946

Reproduced with admin tools; the speech was produced by the mob itself talking into the radio.

1. Spawned a human and gave it an `/obj/item/radio` (a station bounced radio) in hand. Using the Lua editor, turned broadcasting on with the `set_broadcasting(TRUE)` proc (setting the variable directly does not work).
2. With the telecomms servers on, had the mob speak: chat showed `[Common] ...`. This is the normal case.
3. Turned off the Common server: using the Lua editor, looped over `GLOB.telecomm_machines`, found the machine whose type contains `server/presets/common` and set `on = FALSE`.
4. Had the mob speak again. Chat showed `[145.9] <name> says, ...`, the symptom in the issue.

Not done: reproducing the report as written by a player on a live round with working telecomms. In the test, the raw frequency appeared only once the Common server was off, so whether the reporter's round had a down or bypassed server is an inference.

### #88799

1. Gave one human a station bounced radio, and a second human another radio. As a control at normal health, the second human talked on Common: chat showed `[Common] <name> says, "control test"` and `radio_receive.ogg` appeared in the sounds list at 100%.
2. Using the Lua editor, called `set_stat(3)` (hard crit) on the holder, with the radio moved back into the holder (hard crit makes a mob drop held items). The second human talked again: no `radio_receive.ogg` and no chat line.

## Cause

### #91946

Channel names are no longer a fixed table. They were moved into the telecomms servers, which stamp a name into the signal data; the Common server defines it in its `New()` (`code/game/machinery/telecomms/machines/server.dm`, the `server/presets/common` block, using `frequency_infos["[FREQ_COMMON]"]`). Chat composition calls `get_radio_name(radio_freq, radio_freq_name)` (`code/game/say.dm:166`):

```
/proc/get_radio_name(freq, freq_name)
	if(freq_name)
		return freq_name
	var/name = GLOB.reserved_radio_frequencies["[freq]"]
	if(name)
		return name
	return "[copytext_char("[freq]", 1, 4)].[copytext_char("[freq]", 4, 5)]"
```

(`code/game/say.dm:336-342`). Common is not in `reserved_radio_frequencies`, so a message with no `freq_name` ends in the last line and 1459 becomes `145.9`. A message gets no name when it bypasses a working Common server: the server is off or destroyed, or the mundane fallback `backup_transmission()` (`code/modules/…/radio.dm:391`, called from a 2 second timer at `:389`) delivers it.

### #88799

`/obj/item/radio/on_receive_message` returns early if `HAS_TRAIT(holder, TRAIT_DEAF)` (`radio.dm:457`). The talker's own radio click is gated on `!HAS_TRAIT(talking_living, TRAIT_DEAF)` (`radio.dm:374`). `set_stat()` adds `TRAIT_DEAF` when entering hard crit (`living.dm:2546` per the notes). So current code does not send radio sounds to a mob in hard crit.

## Fix

### #91946

One commit: "Fix issue 91946: name default radio channels when no telecomms server stamped a name".

- `code/game/communications.dm`: new `GLOB.default_radio_channel_names`, built by `init_default_radio_channel_names()`, the reverse of `GLOB.default_radio_channels` (frequency as text to channel name).
- `code/game/say.dm`: `get_radio_name()` now checks `reserved_radio_frequencies`, then `default_radio_channel_names`, and only then formats the raw frequency.

This keeps server-stamped names authoritative and only supplies a name where none existed, so unknown frequencies still show as numbers. Not tried: making the bypass paths stamp a name at the source.

### #88799

No change.

## Verification

#91946: after rebuilding, the same setup with the Common server off showed `[Common] <name> says, ...` in chat. The case with servers on was not changed by the fix and was not re-run.

Not checked: other default channels through the fallback (Security, Science and so on), the `backup_transmission` path separately from the server-off case, and AI private or other frequencies sharing the table.

#88799: checked only by `set_stat(3)`, which adds the deaf trait, and not by damaging a mob into real hard crit. The "no sound" result therefore rests on that trait being present. Other radio types (headsets, intercoms) were reviewed in code, not tested.

## Notes

- The earlier radio rework that moved channel names into telecomms servers is PR 91647 per the investigation notes; the issue cites no PR directly.
- The default-names table is derived from `default_radio_channels`, so adding a channel there updates it automatically. If two channels shared a frequency, the later one would win; none do in the inspected list, but this was not audited.
- #88799 was investigated in the same unit and has no fix branch content. It reads as already fixed at this master.
