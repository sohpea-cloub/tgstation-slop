# #53165: Rapidly applying gravitum multiple times causes runtimes

| | |
|---|---|
| Issues | [#53165](https://github.com/tgstation/tgstation/issues/53165): not reproduced (already fixed on master) |
| Status | Not reproduced; no fix needed |

| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The issue (opened 2020) reports that exposing the same object to gravitum several times in a row runtimes, because the `forced_gravity` element registers its `COMSIG_ATOM_HAS_GRAVITY` signal again on a target that already has it. On current master this does not happen: the element returns early when the target already carries the forced-gravity trait from that element instance, so the second registration is never attempted. Repeated gravitum exposure on the test server produced no runtimes, so no fix was written.

## The bug

As reported: a player (or a test setup, for example spamming "Clogged Vents: Catastrophic" so smoke carries a reagent onto objects) exposes an object to gravitum more than once. The first exposure makes the object weightless by adding the `forced_gravity` element. Each further exposure adds the element again, which tried to register the same signal handler a second time on the same object. The signal system treats registering an already-registered signal without `override` as an error, hence the runtimes.

## Reproduction

Not reproduced on master `87b93338`. The attempt, using admin tools on a running round (observer, Lua editor):

1. Spawned a pocket crowbar and a bare `/datum/reagent/gravitum` datum with its volume set to 10.
2. Called `expose_obj(crowbar, 10)` on the reagent five times in a row.
3. Checked the result: `crowbar.has_gravity()` returned 0 (the object is weightless, so the element works) and the `TRAIT_FORCED_GRAVITY` trait on the crowbar had a single source, not several.
4. Repeated with a more realistic path: spawned a beaker holding 20u of gravitum and called `reagents.expose(crowbar, 1, 1)` six times against a new crowbar. `has_gravity()` was again 0.
5. Read the round's `runtime.log`: apart from startup lines, it contained no runtime entries.

Caveats: this was done by calling the reagent's exposure procs directly from the Lua editor, not by triggering the clogged-vents event and letting smoke or foam deliver the reagent. One earlier Lua script failed on a mistake in the script itself (taking the length of a nil value); that was a script error, not a game runtime, and was corrected before the runs above. Only the first of the two paths above checked the trait source count; the beaker run checked gravity only and then the runtime log.

## Cause

Why it happened in 2020 and why it no longer does, from the current source:

`code/datums/elements/forced_gravity.dm:9-25`, the element's `Attach`:

```dm
var/our_ref = REF(src)
if(HAS_TRAIT_FROM(target, TRAIT_FORCED_GRAVITY, our_ref))
	return
...
RegisterSignal(target, COMSIG_ATOM_HAS_GRAVITY, PROC_REF(gravity_check), override = can_override)
...
ADD_TRAIT(target, TRAIT_FORCED_GRAVITY, our_ref)
```

- The element is `ELEMENT_BESPOKE` with `argument_hash_start_idx = 2` (`forced_gravity.dm:2-3`), so there is one element instance per distinct set of arguments; repeated `AddElement(/datum/element/forced_gravity, 0)` calls reach the same instance.
- On the first attach the instance registers the signal and adds the trait, keyed by its own `REF`. On any later attach to the same target, `HAS_TRAIT_FROM` is true and `Attach` returns before reaching `RegisterSignal` (`forced_gravity.dm:14-16`). `can_override` defaults to FALSE, so without this early return a second registration would be the duplicate-signal runtime described in the issue.
- The reagent side, `/datum/reagent/gravitum/expose_obj` (`code/modules/reagents/chemistry/reagents/other_reagents.dm:3149-3152`), adds the element and then schedules removal with `addtimer(..., TIMER_UNIQUE|TIMER_OVERRIDE)`, so repeated exposures also replace, rather than stack, the removal timer.

## Fix

None. The defect described in the issue is no longer present on master. I did not trace which upstream commit introduced the early return, so the exact fixing change is unidentified.

## Verification

Checked in game (see Reproduction): repeated exposure through direct `expose_obj` calls and through a beaker's `reagents.expose` left the object weightless, with one trait source on the first path, and the runtime log showed no runtimes.

Not checked:
- The actual clogged-vents or smoke/foam delivery path from the issue.
- Exposure of non-crowbar objects, or objects on turfs with forced no-gravity.
- Behaviour when the removal timer fires (the element being removed again afterwards).
- Mob metabolism (`on_mob_metabolize` / `on_mob_end_metabolize`), which is a separate path and was not part of this report.

## Notes

- Side observation, not part of this issue: `expose_obj` computes the removal delay from the reagent's `volume` rather than from the `reac_volume` argument it is passed (`other_reagents.dm:3152`). The duration of the weightlessness therefore depends on the reagent amount in the source holder rather than the amount applied to the object. This was left unchanged and has not been checked against the intent of the "1 minute per unit" comment.
- The issue can likely be closed as fixed on master.
