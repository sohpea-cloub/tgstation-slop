# #67013: Buckling a mob from an adjacent tile leaves it on its old tile

| | |
|---|---|
| Issues | [#67013](https://github.com/tgstation/tgstation/issues/67013): verified, fixed |
| Status | Fixed and checked in game (Lua-driven; see Verification) |
| Fix branch | [fix/67013](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/67013) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

When a player buckles another mob to a chair (or similar object) while standing on the chair's own tile, the mob is marked as buckled but stays on the tile it was on. The cause is that `buckle_mob()` assumes `M.Move(loc)` moves the mob onto the object, but the player standing on that tile blocks the move and the result is ignored. The fix checks afterwards whether the mob arrived and, if not, places it there with `doMove()`.

## The bug

The reporter's steps: stand on the tile of the object, buckle another mob to it, and the mob is buckled but is not moved onto the object. The mob does not become passable, but players can crawl under it. Any movement of the object, dragging the mob before releasing the grip, or unbuckling puts things right. The issue carries the "Tested/Reproduced" label, and a 2024 comment says it was still happening.

## Reproduction

I used the Lua editor to call the same proc a player action uses. `user_buckle_mob` calls `buckle_mob(M, force, check_loc)` after its delay, so this reproduces the player's situation but was not done through the click interface.

1. Spawned a human `user` and a chair on the same tile T, and a second human `v` on the tile directly east of T.
2. Called `chair:buckle_mob(v, false, true)`.
3. Result before the fix: the call returned 1 (success), `v.x` was 108, `chair.x` was 107, and `v.buckled` was the chair. The mob was buckled but not on the chair's tile.

A first attempt used a monkey as the target. It was confounded because monkey AI unbuckles itself. The chat showed "The monkey stands up from the chair", and the runtime log recorded an `unbuckle_mob()` runtime at `code/game/objects/buckling.dm:165` ("called unbuckle_mob() ... while having buckled as ."). Using a plain human removed this.

## Cause

In `buckle_mob()` the mob is first flagged as buckled (`M.set_buckled(src)`), then moved:

```
M.Move(loc)
if(buckle_dir == BUCKLE_MATCH_DIR)
```
(`code/game/objects/buckling.dm:119`)

`Move()` goes through `CanPass` checks. When `user` is a dense mob standing on the object's tile, that move is refused, and the return value is not checked. The only later check is `if(!M.buckled)` ("something has unbuckled us in reaction to the above movement"), which does not notice that `M` is on another tile. The result is a buckled mob that is not on the object. Moving the object, unbuckling, or the pull mechanics later fix up the position.

## Fix

One commit, "Fix issue 67013: buckling a mob from an adjacent tile moves it onto the object even if Move() is blocked", changes `code/game/objects/buckling.dm` by 3 lines. After `M.Move(loc)`:

```
// Move() can be blocked (e.g. by the dense user standing on our turf), which would leave M buckled to us from a different tile.
if(M.buckled == src && M.loc != loc)
	M.doMove(loc) // not forceMove(): that unbuckles living mobs
```

`doMove()` is used rather than `forceMove()` because `/mob/living/forceMove` unbuckles the mob. A first attempt with `forceMove` made `buckle_mob` return 0 for that reason. Using `doMove()` skips the blocked `Move()` path without that side effect.

## Verification

With the fix built and a plain human target:
- Buckling from the adjacent tile with `user` on the chair's tile returned 1, `v.x` was 107 and equal to `chair.x`, and the mob was still buckled (`lying_angle` 0).
- Buckling when no user is on the tile (the same-tile case) still worked (x 110 = 110).
- `unbuckle_mob` worked afterwards.
- The run logged no new runtime errors.

Not checked: pixel offsets and how it looks on a real client, buckling through the click and do_after interface rather than calling `buckle_mob`, and other callers of `buckle_mob` such as vehicles and beds with special movement rules.

## Notes

- The earlier monkey result (monkeys unbuckle themselves) is unrelated to this bug.
- Any caller that buckles with `check_loc = FALSE` from a tile that blocks the move could hit the same path. The fix is in `buckle_mob` itself, so it covers them.
