# #34317: open storage stays usable from afar after climbing into and out of a mech

| | |
|---|---|
| Issues | [#34317](https://github.com/tgstation/tgstation/issues/34317): verified, fixed |
| Status | Reproduced on master and fixed; fix checked in game |
| Fix branch | [fix/34317](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/34317) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

A mob's open storage window (for example a toolbox on the floor) is only closed when the mob walks out of reach, because the reach check lives in `/mob/living/Move()`. Entering and leaving a mech use `forceMove()`, which never calls `Move()`, so the storage stays the mob's `active_storage` however far the mech carried them. From the new position the player can still put items into the toolbox. The fix moves the check into `/mob/living/Moved()`, which runs for both `Move()` and `forceMove()`, so any relocation that leaves the storage out of reach closes it.

## The bug

From the issue: a player opened the storage window of a toolbox lying on the floor, climbed into a mech with the window still open, moved away, got out, and could still put things into the toolbox. A comment from 2018 adds that this only works one way: items can be inserted but not removed. Once the player takes a normal step after leaving the mech, the window closes.

What actually happens is that the mob's `active_storage` is never cleared, so the storage click handler keeps accepting clicks on the storage's cells. Nothing re-checks whether the player can still reach the container. This is not specific to mechs. Any `forceMove()` of the player (a teleport, for instance) has the same effect.

## Reproduction

Done on the test server (master `87b93338`) as an Assistant with admin tools, using the Lua editor and the player's own storage UI clicks.

1. Join the round as any job, open the Lua editor, and create a state.
2. In the Lua editor, spawn a mechanical toolbox on the player's tile, put a pocket crowbar in the player's active hand, and spawn a Ripley mech 4 tiles east of the player.
3. Open the toolbox's storage for the player (`toolbox.atom_storage:open_storage(me)`). The toolbox's storage window appeared on screen.
4. Enter the mech with `mech:moved_inside(me)`, then move the mech 5 tiles east with `mech:forceMove(...)`, then exit it with `mech:mob_exit(me, true)`.
5. Read `me.active_storage`. It returned `/datum/storage/toolbox` at all three points (inside the mech, after the mech was moved, after exiting). The player was at x=50 and the toolbox at x=45, so about 5 tiles apart.
6. Click one of the storage cells (the `storage` screen object) with the crowbar still in hand. The game answered "You put the pocket crowbar into the mechanical toolbox." from five tiles away. Removing items did not work, as the issue says.

The mech was relocated with a direct `forceMove()` call and the enter/exit procs were called directly, rather than by a player driving the mech and using the exit verb. Both the enter and the exit are `forceMove()`s in the real code paths (see Cause), so this exercises the same mechanism, but a full manual play-through was not done. The first attempts at this script failed on Lua errors in the script itself and were rerun; they are not part of the evidence.

## Cause

The reach check is in `/mob/living/Move()`, after the `..()` call (`code/modules/mob/living/living.dm:1069`):

```dm
if(active_storage)
	var/storage_is_important_recurisve = (active_storage.parent in important_recursive_contents?[RECURSIVE_CONTENTS_ACTIVE_STORAGE])
	var/can_reach_active_storage = active_storage.parent.IsReachableBy(src)
	if(!storage_is_important_recurisve && !can_reach_active_storage)
		active_storage.hide_contents(src)
```

Boarding a vehicle is a `forceMove`: `mob_enter()` calls `M.forceMove(src)` (`code/modules/vehicles/sealed.dm:85`) and mechs use `moved_inside()`, which calls `newoccupant.forceMove(src)` (`code/modules/vehicles/mecha/mecha_mob_interaction.dm:51`). Leaving is also a `forceMove`: `mob_exit()` calls `M.forceMove(exit_location(M))` (`sealed.dm:97`). `forceMove()` does not go through `Move()`, so the check above never runs for any of these.

The storage's own `close_distance` (`code/datums/storage/storage.dm:1019`) is only registered on `COMSIG_MOVABLE_MOVED` of the storage's parent, so it fires when the container moves, not when the viewer does.

The click handler does not compensate. `/atom/movable/screen/storage/Click()` refuses only if the player is incapacitated or `ismecha(usr.loc)` (`code/_onclick/hud/screen_objects/screen_objects.dm:672`); there is no reach check. The mech guard explains why the window is unusable while inside, and why it works again immediately after exiting.

## Fix

One commit, "Fix issue 34317: close unreachable active storage on any move, not only Move()".

It deletes the reach check from `/mob/living/Move()` in `code/modules/mob/living/living.dm` and adds it unchanged to the start of `/mob/living/Moved()` in `code/modules/mob/living/living_movement.dm`, right after `. = ..()`, with a comment explaining why. `Moved()` is called after both `Move()` and `forceMove()`, so a mech boarding, a mech exit, a teleport, and ordinary walking are all covered by the same check, and walking behaves as before.

No alternative was implemented. Adding a reach check to the storage click handler would also block the insert, but moving the check to `Moved()` also removes the stale open window itself.

## Verification

After rebuilding and restarting the test server, with Lua editor calls on a freshly spawned toolbox, Ripley and crowbar:

- Opened the toolbox, then `mech:moved_inside(me)`: `active_storage` was `nil` right after entering. (Before the fix this stayed open.) Moving the mech and exiting kept it `nil`.
- Opened the toolbox and `forceMove`d the player 1 tile west (still adjacent): `active_storage` stayed `/datum/storage/toolbox`.
- Then `forceMove`d the player 4 tiles south (out of reach): `active_storage` became `nil`.
- The round's `runtime.log` had no runtime errors from the new run (the earlier round on the same server had 3, from the failed Lua scripts mentioned above).

Not checked: the insert click after the fix (it was not needed since the storage is closed), a manual drive-and-exit play-through of the original issue scenario, storage opened inside a container held by the player or other `important_recursive_contents` cases, and other mob types or vehicles besides the Ripley.

## Notes

- Entering a mech now also closes a storage window that the player could still reach from the floor next to them. The cause is that `IsReachableBy()` is evaluated from the mech's contents after the `forceMove`, where the container is no longer reachable. This was noticed during testing and judged acceptable, since the player cannot use inventory from inside a mech anyway (`ismecha(usr.loc)` guard); a maintainer may prefer otherwise.
- The check now runs in `Moved()` rather than `Move()`, so it applies to every relocation of a living mob that has an active storage. The extra work is limited to mobs with `active_storage` set.
- The storage click path still has no reach check of its own; the fix relies on the window being closed. The existing `close_distance` signal, which handles the container being moved away, was not changed.
- No upstream PR that already fixes this is mentioned in the issue thread; none was checked for beyond that.
