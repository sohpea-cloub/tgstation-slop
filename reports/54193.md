| Status | Fix committed on a branch; one runtime problem after an infiltrator replace is unresolved |

## Summary

The issue lists four problems with loading and replacing shuttles through the Shuttle Manipulator. Two were reproduced and fixed. Replacing a shuttle that is in transit deleted the old shuttle's transit dock and then docked the replacement to the deleted dock, leaving it with no transit dock, no destination and an infinite timer. The infiltrator shuttle could not be replaced because its template id (`infiltrator`) does not match the mobile port's `shuttle_id` (`syndicate`), so the Manipulator never found the shuttle to replace. The fix gives the replacement a transit dock of its own, carries over the old destination and previous dock, and adds a `mobile_port_id` var to shuttle templates for the id mismatch. The half-loaded meteor was not reproduced, and the fourth point was not tested.

## The bug

The issue (filed in 2020 against an older revision) describes four symptoms:

1. Loading a new meteor shuttle with engines onto the transit docking port leaves about half of it missing; the reporter suspected `CHECK_TICK` in the shuttle movement code and the transit dock being wiped while the shuttle lands.
2. The infiltrator cannot be replaced; the reporter guessed at template naming.
3. Replacing a shuttle that is in transit places the new shuttle in "infinite transit"; the reporter suspected the transit dock being deleted with the old shuttle.
4. Shuttles in infinite transit try to fly to transit when sent somewhere, which stops the transit animation so the shuttle seems to stay in place.

## Reproduction

All steps used the Shuttle Manipulator's tgui actions (`select_template`, `load`, `replace`) and the Lua editor to read state. The Manipulator's interface does not list the infiltrator templates, so for point 2 the same actions were sent to the server directly.

**Point 1, meteor loaded to transit: not reproduced.**
Loading `emergency_meteor` through the Manipulator `load` action produced the shuttle `emergency_2` docked at transit with all 1513 turfs of its area, which matches the 1513 shuttle-area cells in the map file. Nothing was missing. `action_load` already sets the shuttle's mode to `SHUTTLE_PREARRIVAL` while it docks, with the comment "Transit dock get removed if shuttle moves too long" (`code/controllers/subsystem/shuttle.dm:961`), which appears to guard against the symptom described.

**Point 2, infiltrator not replaceable: reproduced.**
1. Load `infiltrator_basic` with the Manipulator. The shuttle appeared with `shuttle_id` `syndicate`.
2. Send `select_template` for `infiltrator_advanced`.
3. The Manipulator's `existing_shuttle` came back `null` instead of the loaded shuttle. In Lua, `getShuttle("infiltrator")` returned nil and `getShuttle("syndicate")` returned the shuttle.

**Point 3, replacing a shuttle in transit: reproduced.**
1. Early in a round, while the arrivals shuttle (`arrival`) is in transit ("called", heading to arrivals), send `select_template` and then `replace` for `arrival_box`.
2. Inspect the new `arrival` mobile port in Lua. On master it had no docked port (`get_docked()` nil), no `assigned_transit`, no `destination`, a timer of 1e31, mode "called", and sat on z-level 12; the old shuttle's transit dock was gone.

**Point 4: not tested directly.** It is probably a consequence of point 3 (a shuttle with no assigned transit dock), but this was not checked. From reading `enterTransit` (`code/modules/shuttle/mobile_port/mobile_port.dm:333`) and the docking code, a shuttle loaded straight onto a transit dock should behave normally; that was not exercised beyond the meteor load above.

## Cause

**Replacing in transit.** `action_load` (`code/controllers/subsystem/shuttle.dm:918`) takes the old shuttle's current dock as the destination for the replacement (`code/controllers/subsystem/shuttle.dm:937-940`):

```dm
else if(existing_shuttle && replace)
	timer = existing_shuttle.timer
	mode = existing_shuttle.mode
	dest_dock = existing_shuttle.get_docked()
```

When the old shuttle is in transit, that dock is the transit dock it owns. `action_load` then calls `existing_shuttle.jumpToNullSpace()` (`code/controllers/subsystem/shuttle.dm:955-956`), which ends in `qdel(src, force=TRUE)` (`code/modules/shuttle/mobile_port/mobile_port.dm:384`). The mobile port's `Destroy` deletes its `assigned_transit` (`mobile_port.dm:101-103`), and the transit dock's `Destroy` frees its turf reservation (`code/modules/shuttle/stationary_port/port_types.dm:53-65`). The replacement is then docked to a dock that no longer exists. It ends up in plain space with no `assigned_transit`, no `destination`, and the old timer and mode.

**Infiltrator lookup.** `select_template` finds the shuttle to replace with `getShuttle(S.port_id)` (`code/controllers/subsystem/shuttle.dm:1131`). The infiltrator templates set `port_id = "infiltrator"` (`code/datums/shuttles/infiltrator.dm:2`), but the mobile docking port in the map is `/obj/docking_port/mobile/infiltrator` with `shuttle_id = "syndicate"` (`code/modules/shuttle/mobile_port/variants/infiltrator.dm:4`). The two never match, so `existing_shuttle` is always null.

## Fix

One commit, "Fix issue 54193: shuttle manipulator replace of infiltrators and shuttles in transit", changes four files:

- `code/controllers/subsystem/shuttle.dm`, `action_load`: if the old shuttle's dock is a `/obj/docking_port/stationary/transit`, the destination dock is set to null so that `generate_transit_dock()` makes a new transit dock for the replacement before the old shuttle (and its dock) is destroyed. The old shuttle's `destination` and `previous` are remembered and put on the replacement after docking, unless they have been deleted in the meantime. The existing code already carried over `timer` and `mode`.
- `code/controllers/subsystem/shuttle.dm`, `select_template`: looks up `S.mobile_port_id || S.port_id`.
- `code/datums/shuttles/_shuttle.dm`: new var `mobile_port_id`, documented as the `shuttle_id` of the mobile port in the map when it differs from `port_id`.
- `code/datums/shuttles/infiltrator.dm`: `mobile_port_id = "syndicate"`.

A new template var was added rather than changing the infiltrator's `port_id` or `shuttle_id`; the reasoning for that choice was not recorded, and no other approach was recorded as having been tried. The same mismatch exists in several other templates (see Notes), which a per-template var can cover one by one.

## Verification

On the test server with the fix built:

- **Point 3, verified.** With the arrival shuttle in transit, `select_template` then `replace` for `arrival_box` gave a new `arrival` shuttle docked at a `/obj/docking_port/stationary/transit` ("Transit for arrival/arrivals shuttle", z-level 12), with `assigned_transit` set, `destination` and `previous` both "the arrivals", mode "called" and the carried-over timer (1e31, which is the arrivals shuttle's normal waiting timer). `SSshuttle.transit_docking_ports` contained exactly one entry (the old one had been removed). Before the fix there was no transit dock, no assigned transit and no destination.
- **Point 2, partly verified.** `load` of `infiltrator_basic` worked. `select_template` for `infiltrator_advanced` now returned the existing `syndicate` shuttle (it returned `null` before). `replace` ran without a CRASH and the admin log read "load/replaced the syndicate infiltrator". It was not confirmed afterwards that only one `syndicate` shuttle remained: the check ran before the replace had taken effect and showed one shuttle, 306 turfs, idle, on z-level 12. This needs a re-check.
- The log line "A transit dock was destroyed while something was docked to it." (`port_types.dm:56`) appeared when the old transit dock was destroyed. It is probably harmless (the old shuttle is still referenced as docked at that point), but it was not checked whether it also appears before the fix.

Not checked:

- That the replacement shuttle then moves on to its destination or arrives. The arrivals shuttle uses its own movement logic, so calling `request()` on it does nothing and could not be used for this.
- Transit parallax on the replacement.
- Point 4 (shuttle in infinite transit sent elsewhere), and any replace of a shuttle that is not the arrivals shuttle or the infiltrator.

## Notes

**Unresolved runtimes.** After the infiltrator replace the runtime log contained:

- 51 "list index out of bounds" runtimes at `code/modules/mapping/space_management/space_reservation.dm:218`, coming from `turf_reservation/calculate_turf_bounds_information` through `get_turf_above`/`get_turf_below`, called by SSair's adjacency rebuild on `/turf/open/space/transit` turfs (one at 163,38,12). The likely explanation is turfs of the destroyed old transit reservation still waiting in SSair's queue. They did not appear after the arrivals replace. It was not established whether the fix causes them; the old transit reservation is also destroyed on master when an infiltrator in transit is replaced.
- 5 "Cannot read null.air" runtimes at `code/modules/atmospherics/machinery/components/binary_devices/pump.dm:64` (the "Connector to Ship" pump) right after loading the infiltrator and before the replace. These are probably unrelated to the fix and pre-existing for infiltrators loaded this way, but this was not confirmed.

**Same mismatch elsewhere (not fixed).** Other templates have the same kind of `port_id` / mobile `shuttle_id` mismatch, so replacing them through the Manipulator likely fails the same way. The ids below come from the templates and the shuttle map files; replacing them was not tried. `mobile_port_id` could be set on each of them in the same way.

| Template `port_id` | Mobile port `shuttle_id` in the map |
|---|---|
| `labour` | `laborcamp` |
| `aux_base` | `colony_drop` |
| `hunter` | `huntership` |
| `assault_pod` | `steel_rain` |

**Review points.** The change touches core shuttle code and adds a template var. A maintainer may prefer to make the lookup match on either id automatically instead of a per-template var.
