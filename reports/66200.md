# #66200: Infinite Ash Exploit (dug volcanic ash does not regenerate when a lattice is built and cut)

| | |
|---|---|
| Issues | [#66200](https://github.com/tgstation/tgstation/issues/66200) not reproduced |
| Status | Not reproduced on master. No code change. |
| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The 2022 report says that on Lavaland a tile dug with a shovel gets its ash back after you build a lattice on it with a rod and cut the lattice, so the dig could be repeated forever. On current master that does not happen: the dug state is stored on the turf itself, and building or cutting a lattice never touches it. The tile stays "already excavated!" until an ash storm refills it, which is intended. The original cause was probably lattice or turf code that no longer exists, but that was not verified.

## The bug

As reported: dig "ash" (the item is "volcanic ash", dropped by digging a Lavaland basalt floor) with a shovel, use a rod to make a lattice on the same tile, and the tile can be dug again. Cutting the lattice and repeating gives unlimited ash. The reporter and the commenters agree that ash is easy to get anyway (ash storms refill dug tiles), so the severity is low. A 2025 comment says it matters in a multi-z Lavaland where only the surface level gets ash storms.

## Reproduction

I could not reproduce it. The sequence was run on the test server from the Lua editor, which calls the same procs the player actions call; no real shovel, rods or wirecutters were clicked through a human character.

1. Started the round, observed, and opened the Lua editor.
2. On Lavaland (z-level 3) picked a basalt tile, `/turf/open/misc/asteroid/basalt/lava_land_surface` at 60,61: `dug = 0`, `broken = 0`.
3. Called `getDug()` on it, which is what a shovel does after its dig delay: `dug = 1`, `broken = 1`, `can_dig() = 0`.
4. Spawned `/obj/item/stack/rods` and called `build_with_rods(rods, mob)` on the tile (chat: "You construct a lattice."): still `dug = 1`, `broken = 1`, `can_dig() = 0`.
5. Called `deconstruct()` on the lattice, which is what cutting it with wirecutters does (`wirecutter_act`): still `dug = 1`, `broken = 1`, `can_dig() = 0`, with the same single overlay (the dug-state overlay) on the tile.

Result: the tile could not be dug again. No runtimes were checked beyond the Lua calls returning normally.

Not done: digging with a real shovel held by a human mob (the `item_interaction` path, including its 4 second delay), and any ash storm.

## Cause

There is no defect on current master; this is why the reported sequence cannot work.

- The dug state belongs to the turf. `/turf/open/misc/asteroid` has a `dug` var (`code/game/turfs/open/asteroid.dm`), `break_tile()` sets it (`:74`), and `getDug()` calls `break_tile()` before dropping the ore (`:132-139`). `/turf/open` also has a `broken` var (`code/game/turfs/open/_open.dm:15`). A shovel dig goes through `item_interaction()` (`asteroid.dm:100`), which refuses unless `can_dig()` is true:

  ```dm
  /turf/open/misc/asteroid/proc/can_dig(mob/user)
  	if(!dug && !broken)
  		return TRUE
  	if(user)
  		balloon_alert(user, "already excavated!")
  	return FALSE
  ```
  (`asteroid.dm:141-147`)
- The only code that clears `dug` and `broken` is `refill_dug()` (`asteroid.dm:149`). Its callers are the end of an ash storm (`code/datums/weather/weather_types/ash_storm.dm:121-124`, which walks `GLOB.dug_up_basalt` for tiles in the storm's areas and z-levels), snow packing on snow tiles (`asteroid.dm:468` onward), and the basalt overrides themselves.
- A lattice is just an object on the tile. `build_with_rods()` (`_open.dm:645`) only creates the lattice (and, when one is already there, upgrades it to a catwalk); it does not replace the turf or call anything on it. Cutting the lattice (`code/game/objects/structures/lattice.dm:73-78`) deconstructs the object and drops rods; it does not touch the turf either.

So nothing in the build, cut or dig chain resets the dig state. Refilling by ash storm is deliberate (the `GLOB.dug_up_basalt` list exists "to replenish basalt tiles that have been dug up").

Why it may have worked in 2022: the likely explanation is that the lattice or turf code of that time replaced or reset the tile. This is an inference from the report; the 2022 code was not examined.

## Fix

None. No commits were made.

## Verification

Nothing to verify. The negative result above is the verification: after dig, lattice, and cut, the tile stays undiggable.

Not checked: a real shovel click, other diggable Lavaland floors (the test used a basalt `lava_land_surface` tile only), ash tiles of type `/turf/open/misc/ashplanet`, which are not dug by the same code (`ashplanet.dm` makes `break_tile()` a no-op), and the multi-z Lavaland scenario from the 2025 comment.

## Notes

- #66200 can probably be closed as already fixed or no longer reproducible.
- The 2025 comment is about ash storms not reaching the lower level of a multi-z Lavaland. That is a question about where storms apply, not about this exploit, and was not investigated. `ash_storm.dm:121-124` only refills tiles whose area is in `impacted_areas` and whose z-level is in `impacted_z_levels`, so tiles outside the storm's areas stay dug.
- The comment linking #66140 was not checked.
