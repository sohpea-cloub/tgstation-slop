# #84138: Swapping minds back and forth logs "living_death overridden" runtimes

| | |
|---|---|
| Issues | [#84138](https://github.com/tgstation/tgstation/issues/84138): verified, fixed |
| Status | Fixed (one commit), verified in game |
| Fix branch | [fix/84138](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/84138) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

`/datum/mind/proc/transfer_to()` registered `COMSIG_LIVING_DEATH` on the new body, but the registration was only removed again when the mind itself left that body through `transfer_to()`. A mind that was displaced from a body by `set_current(null)` (because another mind was transferred into the same body) kept its registration on that body, so when it moved back there, `RegisterSignal` found the old one and logged a "signal overridden" runtime. The fix moves the register and unregister of the death signal into `set_current()`, which every change of `current` goes through.

## The bug

Swapping the minds of two mobs and then swapping them back (any use of `transfer_to()`) makes the runtime log fill with `runtime error: living_death overridden. Use override = TRUE ...`, naming `set_death_time` as both the existing and the new proc. A single swap does not trigger it. The reporter diagnosed it as the signal being handled in `transfer_to()` instead of `set_current()`. The visible harm is runtime noise; in addition, a stale registration is a latent leak, since the mind keeps listening to a body it no longer occupies.

## Reproduction

1. On the test server, start a round, join as an observer and open the Lua editor as an admin.
2. In the Lua editor, create two humans `a` and `b` and call `mind_initialize()` on each, which gives each a mind, `ma` and `mb`.
3. Repeat three times, in this order: `ma:transfer_to(b)`, `mb:transfer_to(a)`, `ma:transfer_to(a)`, `mb:transfer_to(b)`.
4. Read the runtime log.

Observed on unmodified master: four runtimes of the form `runtime error: living_death overridden. Use override = TRUE ... Target: <human> (/mob/living/carbon/human) Existing Proc: set_death_time New Proc: set_death_time`. One round of the swap (the first two calls) did not produce one; the second round did, matching the report. This was done by calling `transfer_to()` directly from Lua, not through a game mechanic that swaps minds (for example a mind-swap spell), so which in-game actions hit it was not checked.

## Cause

In `code/datums/mind/_mind.dm`, `transfer_to()` did the following (line numbers at master):

- line 177: `UnregisterSignal(current, COMSIG_LIVING_DEATH)`, only on the transferring mind's own previous body;
- line 186-187: if the target body already has a mind, `new_character.mind.set_current(null)` is called on that other mind;
- line 215: `RegisterSignal(new_character, COMSIG_LIVING_DEATH, PROC_REF(set_death_time))`.

`set_current()` (line 160) only handled `COMSIG_QDELETING` on the mind. So when another mind was displaced from the body by `set_current(null)` at line 187, its death-signal registration on that body was never removed. Following the calls by hand for the sequence above: the first `ma:transfer_to(b)` displaces `mb` from `b`, leaving `mb`'s registration on `b`. After `mb` moves to `a` and `ma` to `a` again, `mb` has `current == null`, so its next `mb:transfer_to(b)` has nothing to unregister and registers on `b` a second time, which is the override.

## Fix

Commit **"Fix issue 84138: register mind's COMSIG_LIVING_DEATH in set_current, not transfer_to"**, in `code/datums/mind/_mind.dm`:

- `set_current()` now calls `UnregisterSignal(current, COMSIG_LIVING_DEATH)` for the old `current` and `RegisterSignal(current, COMSIG_LIVING_DEATH, PROC_REF(set_death_time))` for the new one.
- The unregister in `transfer_to()` (line 177) and the register (line 215) were removed.

Putting it in `set_current()` means the registration always follows the `current` variable, including when a mind is displaced (`set_current(null)`), when its mob is deleted (`clear_current` calls `set_current(null)`), and for other callers of `set_current()` (the report names `mind_initialize`, `temporary_body` and `avatar_connection`). Unregistering and then registering again for the same body is safe, so transferring a mind into the body it is already in does not override.

## Verification

Checked in game: after rebuilding with the fix and running the same Lua script, there were 0 "overridden" runtimes and no new runtimes of any kind. Death-time tracking still worked: after `b:death()` then `a:death()`, `last_death` on both minds was 873.5 (it was 0 before).

Not checked:
- Any game mechanic that swaps minds (the spell, the device, cyborgification, and so on); only direct `transfer_to()` calls were made.
- The other `set_current()` callers (`mind_initialize`, `temporary_body`, `avatar_connection`) were not exercised individually after the change.
- Behavior with a player-controlled mind (the test used admin-created humans).

## Notes

- A side effect of the new placement is that minds attached through other `set_current()` callers (for example `mind_initialize`) now also track death time, which the old code did only for minds that went through `transfer_to()`. This looks like what the issue wants, but a maintainer may want to confirm it.
- `set_current()` unregisters `COMSIG_QDELETING` on `src` (the mind itself) rather than on `current`, which looks odd, since the registration is also on `src`. It was left unchanged.
