# #88540: Observer with Admin AI Interact can place private cargo orders

| | |
|---|---|
| Issues | [#88540](https://github.com/tgstation/tgstation/issues/88540): verified, fixed |
| Status | Fixed (one commit), verified on the test server |
| Fix branch | [fix/88540](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/88540) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

`/obj/machinery/computer/cargo/proc/add_item()` only looks up an ID card and bank account, and only runs the "Buy Privately" checks, when the user is a `/mob/living`. An admin ghost with Admin AI Interact is not living, so a private order skipped every check, was created with a null `paying_account` (billed to the cargo budget), and then runtimed on `account.account_holder` when the console announced it. The fix refuses a private order from any non-living user with "No ID card detected.", the same message a living user without an ID gets. As the issue's commenter noted, only admins can reach this path, so it is a robustness fix, not a player exploit.

## The bug

With Admin AI Interact switched on, a ghost can use machines as an AI would. Opening a supply console as such an observer, ticking "Buy Privately" and ordering a pack gave:

- a runtime, `Cannot read null.account_holder` in `add_item()`, and
- an order that still went through: it was added to the shopping cart and charged to the general cargo budget instead of failing for lack of a bank account.

## Reproduction

On master `87b93338`:

1. Start a round as an admin and observe (become a ghost).
2. Run the "Toggle Admin AI Interact" admin verb.
3. Open the Lua editor and move the ghost next to a supply console, then open its UI as the ghost. In a Lua state the console was found through `SSmachines.machines_by_type` for `/obj/machinery/computer/cargo`, the ghost was moved with `forceMove` to the console's location, and `ui_interact(ghost)` was called on the console.
4. In the console UI, run the `toggleprivate` action (the "Buy Privately" checkbox), then the `add` action with the pack `/datum/supply_pack/vending/snack`.

Observed before the fix:

- The cart gained an order, billed to the cargo budget.
- `runtime.log` contained `Cannot read null.account_holder` from `code/modules/cargo/orderconsole.dm` in `add_item`, with the observer as `usr`. This matches the issue's runtime, except for the line number (275 in the issue's older revision, 340 on master).

The console UI was opened through a proc call from the Lua editor, but the `toggleprivate` and `add` actions were sent through the normal UI path.

## Cause

In `code/modules/cargo/orderconsole.dm`, `add_item()` declares `var/datum/bank_account/account` (line 243) and only assigns it inside `if(isliving(user))` (line 245). That block also holds all of the private-purchase checks (`if(self_paid)` at line 254): an ID card must be present, it must not be a departmental card, it needs a valid bank account, and it must have the access the pack requires. For a non-living user none of this executes, so with `self_paid` set the function carried on with `account == null`.

Later, `if(!self_paid)` (line 315) is the only place `account` is overwritten (with the personal department), so for a private order it stays null. The `/datum/supply_order` is created with `paying_account = account` (line 334), i.e. null, which the shuttle treats as a purchase from the cargo budget. Finally line 339-340 announces:

```dm
if(self_paid)
	say("Order processed. The price will be charged to [account.account_holder]'s bank account on delivery.")
```

which dereferences the null account and runtimes after the order has already been queued.


## Fix

One commit, "Fix issue 88540: Refuse private cargo orders from non-living users". Immediately after `var/datum/bank_account/account` is declared, it adds:

```dm
if(self_paid && !isliving(user)) // Observers/AI-interacting ghosts have no ID card or bank account to charge
	say("No ID card detected.")
	return
```

This reuses the message a living user without an ID card already receives, so the console's behavior is the same whether there is no ID card or no body to hold one. Non-private orders by non-living users (AIs, cyborgs, ghosts) are unchanged. An alternative would have been to make the later code null-safe and still let a private order proceed with no account, but then the order would still be billed to the wrong budget, so refusing it is the better outcome.

## Verification

After rebuilding the test server with the change, the same steps were repeated in a fresh round: the cart stayed empty, the console said "No ID card detected.", and `runtime.log` had no `orderconsole` runtime.

Not checked:
- Private orders by living players with and without an ID card (the existing path is untouched by the diff, but it was not re-run).
- Cyborgs and AIs ordering privately. They are `/mob/living`, so by reading the code they still go through the existing ID card lookup, but this was not tested.
- Request-only consoles and non-private orders by a ghost.

## Notes

- The commenter on the issue is right that this takes an admin using Admin AI Interact (`code/modules/admin/admin_verbs.dm:555`); no ordinary player can trigger it. The guard is harmless but low priority.
- For a ghost with a private order, a different outcome might be preferred, for example charging nothing or the admin's own account. The patch takes the simplest behavior that matches the existing message.
