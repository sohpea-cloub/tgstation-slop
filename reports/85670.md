# #85670: Transfer valve (TTV) icon does not change when some assemblies are attached

| | |
|---|---|
| Issues | [#85670](https://github.com/tgstation/tgstation/issues/85670): verified, fixed |
| Status | Fixed (one commit), checked in game by calling the attach proc directly, not through the player click |
| Fix branch | [fix/85670](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/85670) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Attaching a health sensor, igniter, voice analyzer or shock kit to a tank transfer valve leaves the valve on its empty "valve_1" icon state, so the device is not drawn on it. The valve only gets redrawn if the assembly itself passes an icon update on to its holder, and only some assembly types do that. The fix calls `update_appearance()` on the valve at the end of `try_attach_assembly()`, so the icon no longer depends on the assembly type.

## The bug

The issue reporter listed which devices show the green square on a TTV after being attached and which do not. Proximity sensor, timer, infrared emitter, remote signaling device and mousetrap show it; health sensor, "electrohelmet assembly" (shock kit), flash, igniter and "condenser" do not. The devices still work; only the icon is missing. What actually happens is that the valve keeps the sprite it has when nothing is attached (`valve_1`), so the attached device is not visible on the valve at all.

## Reproduction

On master, in a round, using the Lua editor as an admin:

1. For each assembly type (`health`, `igniter`, `flash`, `prox_sensor`, `timer`, `infra`, `signaler`, `mousetrap`, `voice`, `shock_kit`), spawn an `/obj/item/transfer_valve` and the matching `/obj/item/assembly/<type>`, and spawn a human to act as the user.
2. Call `try_attach_assembly(assembly, human)` on the valve and read `icon_state` before and after.

Notes on the setup: assemblies spawn with `secured = TRUE`, and `try_attach_assembly()` refuses secured assemblies, so the first attempt returned FALSE for all ten and changed nothing. After setting `secured = false` on each assembly, the attach succeeded for all ten.

Observed on unmodified master (`icon_state` before > after):

- health sensor, igniter, voice analyzer, shock kit: `valve_1` > `valve_1` (bug)
- flash, proximity sensor, timer, infrared emitter, signaler, mousetrap: `valve_1` > `valve` (icon updated)

This was reproduced by calling `try_attach_assembly()` from the Lua editor, not by a player attaching the item with a click. Flash, which the issue lists as broken, already updated the icon on this master; the flash `update_appearance` override propagates to the holder (see below). The "condenser" from the issue was not tested, and it is unclear which item that refers to.

## Cause

`try_attach_assembly()` (`code/game/objects/items/devices/transfer_valve.dm:176`) sets `attached_device`, then relies on `A.toggle_secure()` to refresh the valve's icon, as its comment says (`:187`):

```dm
A.toggle_secure() //this calls update_icon(), which calls update_icon() on the holder (i.e. the bomb).
```

The base `/obj/item/assembly/proc/toggle_secure()` (`code/modules/assembly/assembly.dm:111`) only flips `secured` and calls `update_appearance()` on the assembly itself:

```dm
/obj/item/assembly/proc/toggle_secure()
	secured = !secured
	update_appearance()
	return secured
```

Whether that reaches the holder depends on the individual assembly's `update_appearance`/`update_icon` override. The timer, proximity sensor, infrared emitter, signaler, mousetrap and flash overrides call `holder?.update_appearance()`; the health sensor, igniter, voice analyzer and shock kit do not. The valve's icon depends on `attached_device`:

```dm
/obj/item/transfer_valve/update_icon_state()
	icon_state = "[base_icon_state][(!tank_one && !tank_two && !attached_device) ? "_1" : null]"
```

(`transfer_valve.dm:226`). With no valve update after attaching, the state stays at `valve_1`, the "nothing attached" sprite.

## Fix

One commit, "Fix issue 85670: update transfer valve icon when an assembly is attached". In `try_attach_assembly()` it removes the misleading comment on `toggle_secure()` and adds `update_appearance()` on the valve after the device is attached and logged, with a comment explaining that not every assembly updates its holder.

This was chosen over changing each assembly (or the base `toggle_secure()`) to update its holder, because the valve owns the state that changed (`attached_device`) and a single call there covers every current and future assembly type. `tank_one`/`tank_two` attachment already calls `update_appearance()` on the valve in the same way.

## Verification

After rebuilding with the fix and restarting the test server, the same Lua script was run again (assemblies unsecured first). All ten assembly types, including health sensor, igniter, voice analyzer and shock kit, went from `valve_1` to `valve`.

Not checked: attaching by a player through the normal in-game click (only the proc was called directly); that the icon actually renders correctly on screen (only `icon_state` was read); detaching a device and the icon returning to `valve_1` (noted as a thing to check, but no result was recorded); a TTV that already has tanks; the "condenser" item from the issue.

## Notes

- The reporter's question "why can a player place some of them there at all?" is a design question rather than a bug; the valve accepts any `/obj/item/assembly` that is unsecured.
- A more thorough fix could make the base assembly `update_appearance` always notify the holder, but that would affect every holder type and was not attempted.
