## Summary

The issue reports a consistent runtime in `/datum/heretic_knowledge/limited_amount/proc/blades_limit_check`. That proc does not exist on master: a search of `code/` for `blades_limit_check` and `limit_check` finds nothing. The equivalent limit logic now lives in `recipe_snowflake_check` and `on_finished_recipe` of `/datum/heretic_knowledge/limited_amount`, and when exercised on the test server it ran without a runtime. The original runtime text is not recoverable (see below), so the old failure itself could not be confirmed or explained.

## The bug

The issue gives only two screenshots (of the runtime, presumably), which could not be read when the issue was triaged, and a comment suggesting a blade counter that refuses a new blade at the limit. No description of the runtime's message exists in the issue text, so what exactly failed in `blades_limit_check` is unknown.

## Reproduction

Attempted on master with the Lua editor, SDQL2 and the runtime log:

1. Spawned a human, gave it the heretic antagonist datum, and gave it the blade path's starting knowledge (`/datum/heretic_knowledge/limited_amount/starting/base_blade`, "The Cutting Edge", limit 4).
2. Called the knowledge's `recipe_snowflake_check` followed by `on_finished_recipe` six times in a row.
3. Deleted three of the created blades and called the check again. Also set the heretic's `unlimited_blades` and called it again.
4. Read the runtime log.

Observed:
- Calls 1-4 passed and each created a blade (four in total).
- Calls 5 and 6 returned false and showed the balloon alert "ritual failed, at limit!".
- After three blades were deleted, the check passed again.
- With `unlimited_blades` set, the check passed.
- No runtime appeared in the runtime log from any of this.

Limits of this test: the real transmutation rune was not driven with a knife and silver. The same procs the rune calls (`recipe_snowflake_check` is called at `code/modules/antagonists/heretic/transmutation_rune.dm:143`) were called directly. Two runtimes did appear, both caused by the test method and not real: `heretic_knowledge.dm:470` "bad index" from calling `gain_knowledge` directly, which skipped the knowledge tree's researched-knowledge entry, and a bad-proc runtime from misuse of a Lua argument list.

## Cause

None found, since the proc is gone. The current logic is in `code/modules/antagonists/heretic/heretic_knowledge.dm`:

- `recipe_snowflake_check` (line 415): returns TRUE early for sickly blade results when the heretic has `unlimited_blades`; otherwise removes destroyed weakrefs from `created_items` and refuses with a balloon alert when `LAZYLEN(created_items) >= limit`.
- `on_finished_recipe` (line 433): creates each result, adds a weakref to `created_items`, and tracks it for the living heart if `trackable_items`.

It is likely that the issue was fixed by the heretic knowledge rework since the issue was filed (2024), but the git history available in the test checkout is shallow and this was not confirmed.
