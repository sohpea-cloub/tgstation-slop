## Summary

The four issues were grouped as one "proximity sensor stops detecting after being moved or contained" problem. Only half of that holds on current master. An armed proximity sensor dropped on its own tile detects normally (#73342), and a sensor on an airlock "Open" wire opens the door when someone walks into range (#50645). What does not work is any sensor whose location is another movable, such as a closet, a box or a satchel (#40024, #96869), because `/obj/item/assembly/prox_sensor` builds its proximity monitor so that the monitor ignores everything while the host is not directly on a turf. The fix builds the monitor with `_ignore_if_not_on_turf = FALSE` and makes `HasProximity` ignore whatever carries or contains the sensor, so an armed sensor in hand does not trigger on its own carrier.

## The bug

### #73342: armed sensor dropped on the player's own tile

The report says that arming a sensor and dropping it on your own tile leaves it dead, and that it only works after being thrown at least one tile away. It blames the `get_turf(new loc) == get_turf(old loc)` early return in `connect_range`. That check no longer exists on master (see Cause), and a dropped sensor detects normally.

### #50645: sensor on an airlock "Open" wire

The report says a sensor attached to an airlock's "Open" wire (with the ID Scan wire cut) opens the door inconsistently. On master it opened the door whenever a mob was in range and did not when the mob was out of range.

### #40024 and #96869: sensors in containers

An armed sensor, or a sensor plus signaler assembly, placed in a closed locker, a box on the floor or a satchel on the floor never fires when a mob walks next to it or onto its tile. #40024 (2018) asks whether this is intended. #96869 (2026) describes the "sensor in a smuggler satchel under a floor tile" trap and notes that sensors still work in lockers, bodies and other items; that last claim was not borne out in testing, where a closed locker was dead too.

## Reproduction

All steps were done on a running test server with the Lua editor from an observer. Detection was measured through the sensor's `next_activate` variable: it was set to 0 beforehand, and `sense()` sets it nonzero when the sensor fires. Mobs were moved into range with `forceMove` rather than walked, so the movement was done by admin calls, not by a player walking.

### #73342 (not reproduced)

1. Spawn two humans and an `/obj/item/assembly/prox_sensor`, put the sensor in the first human's hands, set `sensitivity = 1` and call `toggle_scan(true)`.
2. Drop it with `dropItemToGround` on the human's own tile. Its location changed from the human to the floor.
3. Reset `next_activate` to 0 and `forceMove` the second human onto the sensor's tile. The sensor fired (`next_activate` nonzero). Reset it and `forceMove` the human to an adjacent tile. It fired again. The sensor's monitor range was 1.

A sensor dropped on its own tile therefore detects on master. The same holds in the original report's form of "activate, drop it under you".

### #50645 (not reproduced)

1. Spawn an airlock, cut its "ID Scan" wire, and attach a sensor (set to `sensitivity = 1` and armed) to its "Open" wire with the wire datum's `attach_assembly`. The sensor's monitor host became the airlock.
2. Spawn a human outside range and `forceMove` it to two tiles from the airlock: the door stayed closed.
3. `forceMove` the human one tile from the door. The door went from closed and idle (density 1, operating 0) to opening (1/1) and then open (0/0).

The result was the same with the fix applied, and also with the sensor attached while held in a mob's hand. Two caveats: an early attempt with the ID Scan wire not cut did not open the door, which is expected since the airlock then still wants an ID; and only the opening was checked, not the door's behaviour afterwards. The "inconsistent" behaviour in the report could not be reproduced.

### #40024 and #96869 (reproduced)

On unmodified master, with an armed sensor (`sensitivity = 1`):

1. Put the sensor in a closed `/obj/structure/closet`, then `forceMove` a human onto or next to the locker's tile: no detection (`next_activate` stayed 0).
2. Put the sensor in an `/obj/item/storage/box` on the floor and move a human next to it: no detection.
3. Assemble a sensor and a signaler in an `/obj/item/assembly_holder`, arm the sensor and put the holder in a box or a locker: no detection. The same holder lying on the floor did detect (in the final run).

A satchel was only tried after the fix. Before the fix the box on the floor stands in for it: both are containers whose `loc` is the turf, which is why #96869 is attributed to the same cause. This is an inference, not a measurement.

## Cause

`proximity_monitor.dm` creates its `connect_range` component with `works_in_containers` set to the inverse of `ignore_if_not_on_turf`:

```dm
AddComponent(/datum/component/connect_range, host, loc_connections, range, !ignore_if_not_on_turf)
```
(`code/datums/proximity_monitor/proximity_monitor.dm:59`)

`ignore_if_not_on_turf` defaults to `TRUE` (`proximity_monitor.dm:17`), and the sensor creates its monitor with that default:

```dm
proximity_monitor = new(src, 0)
```
(`code/modules/assembly/proximity.dm:19`)

So for a proximity sensor `works_in_containers` is FALSE. In `connect_range`, `update_signals` then does this whenever the tracked host's `loc` is another movable:

```dm
if(loc_is_movable)
	if(!works_in_containers)
		unregister_signals(old_loc, turfs)
		turfs = list()
		return
```
(`code/datums/components/connect_range.dm:82-86`)

The component drops every range-turf subscription, so nothing calls `HasProximity` on the sensor while it sits in a locker, a box or a satchel. This is by design for `connect_range` (and is used by `reflection.dm` and `plasticflaps.dm` deliberately), but the sensor never opts out of it. Only a sensor inside a grenade opts in, via `sensor.proximity_monitor.set_ignore_if_not_on_turf(FALSE)` in `code/datums/wires/explosive.dm:59`.

The cause the #73342 report names does not exist on master. `update_signals` carries the comment `Reconcile subscriptions even on the same turf: the container may have changed.` (`connect_range.dm:88`) and has no same-turf early return, so a sensor moved without leaving its tile is re-registered. Which upstream change removed that early return was not established; the history in the test checkout was shallow.

## Fix

One commit: "Fix issue 40024: active proximity sensors work inside containers (lockers, boxes, satchels under the floor; fixes issue 96869 too)". It changes `code/modules/assembly/proximity.dm` in two places.

1. The sensor's monitor is now created as `new(src, 0, _ignore_if_not_on_turf = FALSE)`, which gives the connect_range component `works_in_containers = TRUE`. The sensor's range turfs stay registered when its host is in a locker, a box or a satchel, and `connect_range` also follows the containers' movement (for example a locker pushed to another tile).
2. `HasProximity` returns early if the arriving atom is in `get_nested_locs()` of the monitor's host:

```dm
var/atom/monitored = proximity_monitor?.host
if(ismovable(monitored) && (AM in get_nested_locs(monitored)))
	return
```

The second change is needed because the first one alone would make an armed sensor trigger on its own carrier: the mob holding it, or the locker it is in, moves through the range turfs and registers as a detection. `get_nested_locs` returns everything the host is nested in, up to but not including the turf.

Alternatives were not documented beyond this: no change to `connect_range` or to the shared proximity monitor was made, so other users of the component are unaffected.

## Verification

Checked on a rebuilt test server (same Lua-editor method as above):

- Armed sensor dropped on its own tile: fired.
- Armed sensor in a closed locker, human moved next to or onto it: fired. The locker was then moved to another tile: no detection at the old tile, detection at the new tile.
- Sensor in a box on the floor: fired. Sensor in a flat satchel on the floor: fired.
- Sensor plus signaler holder in a locker and on the floor: both fired.
- Sensor armed in a human's hands, and in a carrier's inventory, while the carrier was moved around: did not fire. Another human moved next to the carrier: fired.
- The airlock "Open" wire case still opened the door.
- The runtime log showed nothing beyond the empty Lua-runtime lines that appear in this environment.

Not checked:

- A real satchel under the floor on plating with a floor tile on top (#96869's exact setup). The satchel's `loc` is still the turf and the hiding is cosmetic, so it should behave like the floor box, but it was not built that way.
- Sensors moved by a human actually walking, picking up or dropping; every movement was an admin `forceMove`.
- A sensor inside a grenade, mobs in a locker with the sensor, mechs, or other nesting depths (a sensor in a bag in a backpack on a mob).
- The unit tests and the CI compile of the whole tree.

## Notes

- This is a behaviour change. After the fix an armed sensor in a bag, locker or on a person detects passers-by. Both #40024 and #96869 ask for that, but #40024 also asks whether the restriction was intentional, and a maintainer may prefer to keep sensors from working through containers, in which case #40024 and #96869 would be closed as intended. Hiding armed sensors in lockers and on people becomes a stronger trap.
- A held armed sensor ignores its own carrier but not other mobs that walk next to the carrier.
- Code reading, untested: `set_ignore_if_not_on_turf` re-adds the component with `ignore_if_not_on_turf` where the constructor path passes `!ignore_if_not_on_turf` (`proximity_monitor.dm:75` versus `:59`). The argument looks inverted: a call `set_ignore_if_not_on_turf(FALSE)`, as `explosive.dm:59` makes for a grenade landmine, would pass `works_in_containers = FALSE`. With the sensor's monitor now created with `FALSE`, that call is a no-op for sensors (it returns at the equality check), so the fix hides the problem rather than touching it. The helper itself was left alone.
- The #73342 report mentions that moving a sensor from one movable to another can register signals when it should not. Nothing like this was seen: after the fix, moving the locker away left the old tile at no detection.
- The group's "same-cause" label for #50645 did not hold: the airlock case works without any change, and no common loc-change bug was found.
