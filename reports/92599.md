# #92599: Decal painter UI shows the wrong things

## Summary

The report says the floor (decal) painter's UI shows designs that do not match what gets painted. On master the preview sprite keys the UI asks for, the sprites in the generated sheet and the decals actually painted are consistent, so nothing was changed. A visual check in a real client was not possible, and the generated sprite sheet is 76928 px wide, which a client might mishandle. That risk is unverified.

## The bug

From the report (client 516.1667, August 2025): spawn a decal painter, select a design, paint it, and the painted decal does not match the design in the UI ("it's all messed up"). The report has no screenshots of the decal painter and no further detail.

## Reproduction

Not reproduced. What was checked on the test server, using the Lua editor and the extra decal painter admin spawn:

1. For every category (6), decal, direction (all 4 for directional decals, south for non-directional ones) and color, built the sprite key the same way `DecalPainter.tsx` does (`<state>_<dir>_<color without #>`) and looked it up in the sprites of `/datum/asset/spritesheet_batched/decals`. All 2404 keys were found, none were missing, and the sheet holds exactly 2404 sprites, so there are no collisions between categories.
2. Decoded the generated sheet, which is 76928 x 32 pixels (ImageMagick refused to open it because of its width limit, so it was decoded by hand), and cropped sprites from across it, including positions beyond x = 65535 px. They showed the correct floor decal shapes and colors, with "custom" as a rainbow and alpha tiles faint.
3. Spawned a decal painter, drove its UI actions (`select_category`, `select_decal`, `select_color`, then `paint_floor`) on 10 turfs, covering neutral alpha tiles, 8-direction trimlines, red warning stripes, and colored and plating sidings. The icon state, direction, color and alpha of each painted decal, taken from `get_decal_info`, are the same values the preview generator uses (`generate_colored_decal_spritesheet_icon` calls the same proc), so the preview matches the painted decal by construction.
4. No runtimes and no asset errors appeared in the round logs.

What could not be done: comparing the painted decals visually. The tool used to look at the game could not decode the `decals.dmi` overlays, which is a limit of that tool and not a game bug. The painter's UI itself was never viewed in a real client.

## Cause

None found. The relevant code on master is `paintable_decals.dm` (preview generation and `get_decal_info`) and `decal_painter.dm` (`paint_floor`), both under `code/game/objects/items/tools/engineering/painter/`, together with `tgui/packages/tgui/interfaces/DecalPainter.tsx`.

## Fix

None.

## Verification

Nothing to verify, since there was no change. The checks above are the whole result.

## Notes

- The issue is from 2025-08-16 and its test merges are unrelated to decals. Later changes to this area include upstream PR #93227 ("Decal painter now correctly paints alpha for neutral decals") and the move to batched spritesheets. The tested master includes them, so the bug may already have been fixed by one of them. That is an inference from dates, not something that was tested against the older code.
- The other possibility is a client-side problem at the time of the report. The sheet is 76928 px wide, above 65535 px. If a client mishandles very wide images, previews past that position would show the wrong sprites. Splitting the sheet by category would avoid that. It was not done because there is no confirmation that a real client has the problem.
- If the report still reproduces for someone, a screenshot of the UI next to the painted floor, plus the client version, would show whether it is the sheet width or something else.
