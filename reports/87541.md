## Summary

Ctrl+Shift+left-click on a mob is meant to offer your held item to that mob only. For ordinary items it does. For the hand items (kiss, high five, handshake) the target is lost on the way down, and the offer goes to every eligible mob next to you. `give()` called `on_offered()` without the clicked mob, and the hand items then applied the offering status effect without it, so the effect fell back to "everyone within one tile". The fix passes the target through `on_offered()`, the `COMSIG_ITEM_OFFERING` signal, the high-five handler and the status-effect calls.

## The bug

The issue says that offering with Ctrl+Shift+LMB on a person next to a second person offers the item to everyone around, and the second person can take it. Testing on the test server showed this happens for the hand items, not for normal items such as a crowbar.

## Reproduction

1. On master, in a started round, spawn four humans in a row near you: A (the offerer) and B, C, D, all within one tile of A's reach for `orange(1, A)` (the test used spawn spots a few tiles apart along a line, with A's neighbours inside range). Using the Lua editor this was done with `SS13.new('/mob/living/carbon/human', loc)`.
2. Put a `/obj/item/hand_item/kisser` in A's active hand.
3. Make A Ctrl+Shift+left-click B. The click was issued with the Lua editor as `A:ClickOn(B, 'shift=1;ctrl=1;left=1')`; a real client click was not used.
4. Count the "give" alerts on B, C and D.

Observed on master:

- Kisser aimed at B: alerts on B, C and D (1, 1, 1). A clean run, done after clearing leftover state, gave exactly this. An earlier run, in which the other hand items had been tried first in the same session, showed only B getting an alert; leftover state from the earlier attempts is the likely reason, but this was not confirmed.
- Crowbar aimed at B: alert on B only, so ordinary items are unaffected.
- The slapper (high five) and the handshake hand were not cleanly measured on unfixed master. They go through the same code path (see Cause).

## Cause

`click_ctrl_shift()` on a living mob calls `living_user.give(src)` (`code/modules/mob/living/living_item_handling.dm:218`), so `give()` knows the target as `offered`. But at `code/modules/mob/living/living_item_handling.dm:172` it calls:

```dm
if(offered_item.on_offered(src)) // see if the item interrupts with its own behavior
```

without `offered`. `on_offered()` (`code/game/objects/items.dm:1478`) and the hand items that override it then work as if the offer were general:

- `/obj/item/proc/on_offered` sends `COMSIG_ITEM_OFFERING` with only the offerer (`code/game/objects/items.dm:1484`), and the high-five element's handler `on_offer` (`code/datums/elements/high_fiver.dm:21`) applies `/datum/status_effect/offering/no_item_received/high_five` without a target (`:29`).
- `/obj/item/hand_item/hand/on_offered` applies `/datum/status_effect/offering/no_item_received` without a target for the plain handshake (`code/game/objects/items/hand_items.dm:397`; the lying-down branch at `:391` already passes `offered`).
- `/obj/item/hand_item/kisser/on_offered` does the same (`code/game/objects/items/hand_items.dm:512`).

`/datum/status_effect/offering/on_creation` (`code/datums/status_effects/neutral.dm:222`) takes `offered` as its fourth argument. Without it, it takes the `else` branch at `:232` and registers every eligible mob in `orange(1, owner)`.

Ordinary items do not apply the status effect from `on_offered()`. `give()` applies it later with the target, which is why the crowbar worked.

## Fix

One commit, "Fix issue 87541: ctrl+shift click offer ignores the chosen target for hand items", which passes the target along:

- `give()` calls `on_offered(src, offered)`.
- `/obj/item/proc/on_offered` and `/obj/item/borg/cleaner_box/on_offered` send `COMSIG_ITEM_OFFERING` with `offerer, offered`. The signal's doc comment in `signals_object.dm` was updated to match.
- `/datum/element/high_fiver/proc/on_offer` accepts `offered` and passes it to the high-five status effect.
- The handshake and the kiss pass `offered` to `apply_status_effect(...)`. The kiss passes `null` for the alert override, then `offered`.

This keeps the existing `offered` parameter of `on_offered()` and `/datum/status_effect/offering` as the single route for the target, rather than adding a new check in the status effect.

## Verification

After rebuilding and restarting the test server, with four spawned humans and `ClickOn` with Ctrl+Shift+left:

- Kisser click-targeted at B: alerts B=1, C=0, D=0.
- Through `give(target)` directly: slapper (high five) to B only, hand to C only, crowbar to D only.
- General `give()` with no target (the G key path): kisser and crowbar still offered to everyone (1, 1, 1).

Not checked: the repo's high-five unit test was not run; no real client Ctrl+Shift click was made (only `ClickOn` with modifier flags); the slapper and hand were verified through `give(target)` rather than through the click path, though the click path ends in the same `give()` call; borg `cleaner_box` was changed for signal-signature consistency but not exercised.

## Notes

- Any other `COMSIG_ITEM_OFFERING` handler would now receive an extra `offered` argument. The only handler found in the source is the high-five element.
- A comment on the issue asks why #82504 was closed; this was not investigated.
