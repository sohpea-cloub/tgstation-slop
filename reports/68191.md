## Summary

The issue (filed in 2022) reported that a player who connected right after a server start had no `Login` line in the game log before their mob login. On master, a connection made while the server was still initializing did get its `Login` line in `game.log`. The current logging system queues log calls made before logging is set up and replays them once it is. The queue path itself was not exercised: the test connection was made after logging was already set up. No change was made.

## The bug

As reported, in round 185990 a player (`Antorp`) had no `Login` line in `game.txt` before the line showing them logged into a mob. The reporter asked whether such early logins could be captured or whether the gap was intended.

## Reproduction

Not reproduced. On a test server at master, a client connected during startup:

1. The server was started and the client connected while subsystem initialization was still running (Lighting had finished, later subsystems were pending, and the client was shown the "round hasn't started" startup message).
2. The newest round's `game.log` was then read.
3. It contained a `GAME-ACCESS: Login: ... from <local address>-... || BYOND v516.1688` line, followed by a `Mob Login: ... was assigned to a /mob/dead/new_player` line. The Login line was present.

Not exercised: a connection made before `SetupLogs()` runs. That window is earlier than the one tested (it is before the round id step, in `world.ConfigLoaded`), and the client could not be connected that early. The test server also had no database.

## Cause

The original 2022 cause was not reproduced and is inferred from the code, not observed. Early in startup, `log_access` wrote to a log file path that was not set up yet when a client connected, for example while `SSdbcore.InitializeRound()` (`code/game/world.dm:157`) was still sleeping ahead of `SetupLogs()` (`world.dm:159`). The line was lost.

Master no longer works that way:

- The `Login` line is written by `log_access(...)` in `/client/New` (`code/modules/client/client_procs.dm:311`), which calls `logger.Log(LOG_CATEGORY_GAME_ACCESS, ...)` (`code/__HELPERS/logging/game.dm`).
- `/datum/log_holder/proc/Log` checks `initialized`; if logging is not set up yet, it stores the call and returns (`code/modules/logging/log_holder.dm:297-299`: `waiting_log_calls += list(list(category, message, data))`).
- `init_logging()`, called from `world.SetupLogs()` (`world.dm:249`), sets `initialized = TRUE` and replays the stored calls (`log_holder.dm:146-149`).

So a login before logging setup should be kept and written once setup completes. This is from reading the code only.

## Fix

None. The fix, if one was needed, already exists on master as part of the logging rewrite. The issue's own question ("is it possible to capture these logins?") is answered by the queue.

## Verification

Checked: a mid-startup connection (after logging setup) produced a `Login` line and a `Mob Login` line in `game.log`.

Not checked: a connection before `SetupLogs()`, which is the path the queue is meant to cover; whether the replayed line lands in the right category file after replay; whether the original 2022 cause was what the inference above says.

## Notes

- The queue replays calls in order, but only once `init_logging()` runs. If a round-start failure prevented it, the queued lines would not be written. That was not examined.
- The issue is likely closable. Anyone wanting certainty could test with a connection attempt held in the window around `SSdbcore.InitializeRound()` on a server with a database.
