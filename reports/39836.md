## Summary

When a map template that contains atmospherics pipes or components is loaded onto a running station and touches an existing station pipe, `SSair.setup_template_machinery()` only calls `atmos_init()` on the template's own machines. The template side therefore links to the station machine, but the station machine never links back. Building the template's pipenet then walks into the station pipes while they still belong to a live pipenet. This steals every member of that pipenet (the `build_pipeline(): ... added to a pipenet while still having one` warning from the issue) and leaves the old pipenet alive in `SSair.networks`. If the station side is a component such as a vent, it instead runtimes with `list index out of bounds` in `set_pipenet()`. The fix re-runs `atmos_init()` on the station machines that the template connects to, tears down their pipenet on the template's side, and rebuilds it at once with the template's machines included.

## The bug

### #39836

The reporter loaded a room next to existing pipes on Box station and got a series of `build_pipeline(): <pipe type> added to a pipenet while still having one. (pipes leading to the same spot stacking in one turf)` warnings, one for every pipe along the connected run. They were certain there were no stacked pipes. The title says "runtime", but the reporter later conceded that these are warnings from `build_pipeline()` and not runtimes.

What actually happens is that the station's pipenet is split into two live copies. The template's new pipenet takes over all the station pipes, but the old pipenet object stays in `SSair.networks` and keeps its member list, its air and the airs of the machines attached to it. Both keep processing. In the reproduction, three template loads left 6 stale pipenets (the station distribution and waste networks, each superseded several times) holding 13764 members whose `parent` was a different pipenet.

When the station side of the connection is a component rather than a pipe, there is a runtime as well (see Reproduction).

### #28991

The 2017 report was about loading `emergency_airless.dmm` onto the station and getting a flood of runtimes. The pasted ones were `null.copy from()` in `/turf/open/proc/Assimilate_Air` and `copy_air_with_tile`, from shuttle docking and turf air copying. A 2022 comment says the same happens with a new shuttle ruin that has vents on airless tiles, with "atmos runtimes and dividing by zero", and links it to #39836.

Those turf-air runtimes did not occur on current master (see Reproduction). The pipenet corruption that remains is the one in #39836.

### #82297

The reporter described a specific load order of pipes around a filter (south, south-east, west, the filter, then east) that causes `components_base.dm`'s `pipeline_expansion()` to index out of bounds on initialize. The layout is a filter whose two output ports sit on the same pipe loop. This is related to #39836 only in that it also involves pipenet building when machines connect in an unusual order.

## Reproduction

All steps used the Map Template - Place admin verb on MetaStation after the round had started. The template files were two small custom maps (see below), registered in `SSmapping.map_templates` through the Lua editor, so that the real verb could place them and runtime messages would keep their text. (A runtime inside a call that starts in Lua only logs an empty `uncaught runtime error:`.)

Templates:
- `pipes1`: a 1x1 map with plating carrying a `smart/manifold4w/scrubbers/hidden/layer2` and a `smart/manifold4w/supply/hidden/layer4`.
- `vent2`: a 1x2 map. Pipes on the bottom tile; a `vent_pump/on/layer4` and a `vent_scrubber/on/layer2` facing south on the top tile, on airless plating.

### #39836, pipe next to a station pipe run

1. Place `pipes1` at 132,122, directly next to the straight station pipe run at 132,121 (centering: No, confirm: Yes). No pipes were stacked.
2. With View Variables / Lua: the template pipe's `nodes` contained the station pipe, but the station pipe's `nodes` did not contain the template pipe (back-index 0).
3. The template's new pipenet contained all 2055 station scrubber pipes. The old pipenet was still in `SSair.networks` with 2055 members and had not been deleted.
4. The server log showed `build_pipeline(): /obj/machinery/atmospherics/pipe/smart/manifold4w/scrubbers/hidden/layer2 added to a pipenet while still having one. (pipes leading to the same spot stacking in one turf) around ...`, the warning from the issue.
5. After three such loads, an audit of `SSair.networks` counted 6 stale pipenets holding 13764 members that belonged to another pipenet.

### #39836, pipe next to a station component

1. Spawn an unconnected `vent_pump/on/layer4` at 60,20 facing east and set it up through `SSair.setup_template_machinery`.
2. Place `pipes1` at 61,20 with the verb.
3. `runtime.log` showed:
   ```
   runtime error: list index out of bounds
   proc name: set pipenet (/obj/machinery/atmospherics/components/set_pipenet)
   source file: code/modules/atmospherics/machinery/components/components_base.dm,221
   ... build pipeline blocking ... setup template machinery ... initTemplateBounds ... Map Template - Place
   ```
   followed by `addMachineryMember: Nonexistent (empty list) or null machinery gasmix added to pipeline datum from Space omni air vent ...`.
4. Afterwards the vent still had `nodes[1] = null` and its own pipenet, while the template's pipenet listed the vent as a machine.

### #28991

Place `vent2` at 88,128 (on the station run at 88,127). The same one-sided node links occurred as above. No turf-air or divide-by-zero runtimes appeared, so the 2017 `Assimilate_Air` / `copy_air_with_tile` runtimes do not reproduce on current master. The test notes say those came from shuttle and LINDA code that has since been rewritten (not independently checked). Shuttle docking itself was not tested.

### #82297

In Lua, at 30,20 and 40,20, the issue's layout was built through `SSair.setup_template_machinery`: a flipped filter facing east (input east, filtered output south, remaining output west), a loop of green `manifold4w` pipes to the south, south-east and east, and a yellow pipe to the west. It was built in the order given in the issue and again with the filter first. Both times, parents 1 and 2 of the filter shared the loop's pipenet, port 3 had its own pipenet, and there was no runtime.

Note that this was built by calling the template machinery setup directly from Lua, not by laying the pipes in the map editor and loading a station with that map.

## Cause

`SSair.setup_template_machinery()` (`code/controllers/subsystem/air.dm:741`) runs in two passes: `atmos_init()` on every machine in the template, then `build_pipeline_blocking()` for each machine that needs a pipenet. Only the template's machines are touched in the first pass:

```dm
for(var/A in 1 to atmos_machines.len)
    AM = atmos_machines[A]
    AM.atmos_init()
    CHECK_TICK
```

`atmos_init()` fills in a machine's `nodes` from whatever is adjacent. A template pipe next to a station pipe therefore gets the station pipe as a node. The station pipe was initialized before the template existed, so its `nodes` do not include the template pipe, and nothing re-initializes it. In normal construction the neighbours are re-initialized: `on_construction()` (`code/modules/atmospherics/machinery/atmosmachinery.dm:544`) calls `atmos_init()` on the machine and then on each of its `pipeline_expansion()` nodes. Template loading has no equivalent.

`build_pipeline_blocking()` (`code/modules/atmospherics/machinery/datum_pipeline.dm:81`) then expands through the template pipe into the station pipe. That pipe still has a `parent`, so the code logs the warning at `datum_pipeline.dm:113`, adds the pipe to the new pipenet and calls `replace_pipenet(item.parent, src)`. It does that for every pipe it reaches, which is the whole connected station network. The old pipenet datum is not told that it lost its members and is not deleted.

For a component, expansion calls `considered_device.set_pipenet(src, borderline)`, which is `parents[nodes.Find(target_component)] = reference` (`code/modules/atmospherics/machinery/components/components_base.dm:220-221`). The component's `nodes` does not contain the template pipe (same one-sided link), so `nodes.Find()` returns 0 and the write is out of bounds.

## Fix

One commit, "Fix issue 39836: connect map templates' pipes back to the pipenets they join", changing only `setup_template_machinery()` in `code/controllers/subsystem/air.dm`:

1. After the template machines' `atmos_init()`, it collects the border machines: nodes of the template's machines that are not themselves in the template.
2. It calls `atmos_init()` on them, so the link now goes both ways.
3. It tears down each border machine's pipenet on the template's side. For a pipe, that is `destroy_network()` on its parent (skipping pipenets already rebuilt in this pass). For a component, it takes the pipenet on the port facing the template and `qdel`s it if it has pipe members, or calls `nullify_pipenet()` if it has none.
4. It rebuilds each border machine's pipenet immediately with `build_pipeline_blocking()`, which now includes the template's machines.
5. It then builds the template's own pipenets as before, which is now a no-op for machines already included.

There is deliberately no `CHECK_TICK` between the teardown and the rebuild, so SSair's incremental rebuild cannot pick up a half-torn-down pipenet.

The test notes do not record other approaches that were considered. The teardown and rebuild is needed in addition to the second `atmos_init()`, because without it the old pipenet would still hold the members that the template's pipenet steals.

## Verification

Checked on a fixed build in a new round, repeating the reproductions:

- Baseline audit before loading anything: 330 pipenets, 0 stale.
- `pipes1` at 132,122: the station pipe at 132,121 now had the template pipe as a node and vice versa. Both were in the same pipenet (the notes record "2535/2055 members" without saying what each number is). 0 stale pipenets.
- `pipes1` next to the spawned vent at 61,20: the vent's node was the template pipe and both shared one pipenet. The vent's pipe underlay changed from exposed to intact. No `set_pipenet` runtime and no `addMachineryMember` trace.
- `vent2` at 88,128: station pipes, template pipes and both vents ended up in the station's pipenets with mutual nodes. 0 stale pipenets.
- The #82297 layout (filter first): correct parents, no runtime.
- After starting the round, the rebuild queue (4593 entries from the torn-down pipenets) drained to 0 with no new pipenets (333 total, 0 stale).
- `build_pipeline()` warnings in the server log: 0. `runtime.log` contained no atmos runtimes.

Not checked:
- Shuttle docking, which moves machines through a different path (relevant to the 2017 #28991 report).
- Multi-z adapters on a template edge.
- Layer manifolds as border machines. Their `atmos_init()` is `find_all_connections()`, which is expected to be fine, but was not tried.
- Templates loaded before `SSair` initializes. These go through `SSair`'s normal init and were never affected; the fix does not touch that path.
- Pipenet behaviour over a longer period, or gas flow across the merged networks. Only structure (nodes, members, parents, queue drain) was inspected.

## Notes

- The issue's wording "pipes leading to the same spot stacking in one turf" also covers a template placed over tiles that already hold pipes (`should_place_on_top = TRUE` keeps the old pipes). That is genuine stacking, and the warning there is correct. It is not what this fix addresses.
- The fix is in `setup_template_machinery()`, which is also called from `code/datums/lazy_template.dm:124`, `code/modules/mapping/map_template.dm:98` and `code/modules/procedural_mapping/mapGenerators/repair.dm:70`, so all three paths get the behaviour. Only the admin verb path was exercised.
- #82297: upstream PR #97822 ("Fixes some pipenet race conditions", 2026-09-19) is in this tree. Before it, every port's pipeline was allocated up front, leaving one orphaned and making `parents.Find()` return 0, so `nodes[0]` was read. The current `pipeline_expansion()` (`components_base.dm:208`) handles a missing port explicitly. The report's claim about the old behaviour comes from reading the PR; the old code was not run.
- No upstream PR was found for #39836 or #28991.
- Side finding, not investigated: placing a template onto a space turf logged `a lighting object was assigned to a turf that already had a lighting object!` (via `initTemplateBounds` / `InitializeAtoms`), on both unfixed and fixed builds.
- The test objects and templates existed only for the one test round and were not committed.
