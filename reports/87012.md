## Summary

The symptoms in #87012 (a whole stack going out one side, and infinite "0 sheet" stacks from single sheets) did not occur on this master: the router code was rewritten since the 2024 report and splits stacks one sheet at a time. Reading the code and testing found three real bugs in the same machines, all fixed in three commits. (1) A sheet split off a stack was lost in nullspace if every router output was blocked. (2) A router turned itself to face its last input, which is the "router changes direction by itself" part of #94925. (3) A crusher kept re-sending sheets it had already sent, and its capacity check was inverted. All three live in `code/modules/manufactorio/machines/`.

## #87012: stacks through a router

### The bug (as reported)

A router fed a stack of iron sends the whole stack to one side. A single sheet makes endless stacks that say "0 sheets".

### Reproduction attempt

On the test server, an observer with the Lua editor and SDQL2 built a conveyor line running east into a router, with conveyors leaving it north, south and east. A 10-sheet stack of iron was put on the line. Result on unmodified master:

- The stack was split one sheet at a time across the three outputs (4, 3 and 3 sheets).
- A single sheet was sent on whole.
- An SDQL2 query of all iron stacks showed no stack with 0 sheets; amounts were all 3 or more.

So the reported symptoms were not reproduced.

### The related bug that was found

`receive_resource` (`router.dm:41`) replaced its `receiving` variable with the piece returned by `handle_stack` (line 50). `handle_stack` calls `split_stack(1)`, and the piece it returns has no location (nullspace). If `send_resource` then failed for every output, the function returned `MANUFACTURING_FAIL` but the one-sheet piece was gone, so the original stack shrank by one sheet on each failed attempt.

This was found by reading the code. It was not reproduced on the old build; the all-outputs-blocked test was run only after the fix. In an earlier test on master with two of three outputs blocked, all 10 sheets went to the free output and none were lost.

## #94925: router and crusher

### Router turns itself

Reproduced on master: with a router at its default direction (south, dir 2), items arriving from the west left it at dir 8 (west). `router.dm:52` does `dir = receive_dir` on every successful receive, which turns the router (and its input/output overlays) to face whichever side the last item came from. The reporter's "turn it before wrenching, wait a while" is explained by this: the first received item resets it.

### Crusher problems

Found by reading the code. The crusher half of the report ("not crushing or taking in items after some time") was not reproduced on the old build; the pull-back described below was judged from the code.

- **Sent sheets are re-sent.** `process()` (`crusher.dm:43`) returns early while `withholding` is set and `send_resource(withholding, dir)` fails, but never clears `withholding` after a success. `withholding` is only cleared by `Exited()` when the item leaves the crusher's contents. For stacks made from held sub-sheet materials, `withholding = new material(null, new_amount)` (line 51) creates the stack in nullspace, so `Exited()` never fires. Every later tick therefore calls `send_resource` on the same stack again, pulling the already-sent sheets back onto the output turf, or re-sending a stack a downstream machine has already consumed or merged.
- **Inverted capacity check.** `crusher.dm:31`: `if(length(contents - circuit) >= capacity && may_merge_in_contents_and_do_so(receiving))` returns FAIL when the stack was merged (a success) and never rejects an unmergeable item when full. The storage box (`storagebox.dm:18`) and smelter (`smelter.dm:20`) use `&& !may_merge_in_contents_and_do_so(receiving)`.

## Fix

Three commits, in this order:

1. "Fix issue 87012: manufacturing router no longer loses sheets split off a stack when an output is blocked". In `receive_resource`, the split piece goes in a separate `to_send` variable instead of overwriting `receiving`. If the send fails, the piece is merged back into the original stack. The unused `direction` argument was dropped from `handle_stack`, and the helper got a doc comment.
2. "Fix issue 94925: manufacturing router no longer turns itself to face the last input". Removes `dir = receive_dir` and the `update_appearance` call that followed it.
3. "Fix issue 94925: manufacturing crusher no longer pulls back sheets it already sent and now refuses input when full". `process()` sets `withholding = null` after a successful send, and the capacity check gets the missing `!`.

## Verification

After rebuilding, with direct calls to `receive_resource` from the Lua editor and SDQL2 checks:

- **Blocked outputs.** A router with crates on all four sides received a 10-stack six times, alternating input directions. Every call returned FAIL, the stack stayed at 10, and the router's `dir` was unchanged.
- **Free outputs.** A second router with free sides, over three calls (returning success, success, fail), took the stack from 10 to 8, with 1-sheet stacks found on two adjacent tiles (8 + 1 + 1 = 10). The sheets were conserved and `dir` was unchanged.
- **Crusher.** A crusher with a zero crush cost, facing east, received two 1-rod stacks. One iron sheet appeared on the output tile. Afterwards `withholding` was null, `held_mats` was empty and the crusher's contents were only its circuit. A sheet moved away from the output tile stayed away over 10 seconds of ticks.
- The runtime log showed one runtime, from a malformed SDQL query by the tester, and none from the game code.

Not checked: the crusher's full-capacity rejection (verified by reading only); the crusher pull-back before the fix; a full conveyor setup with the fixed build (all post-fix checks called the procs directly); a crusher on a cable, which #94925 specifically mentions; and the reporter's wrench-then-wait router sequence, though the `dir` change was seen directly.

## Notes

- The suggestion in #87012's comment to "send it like a normal item" for single-sheet stacks matches what `handle_stack` already does.
- `may_merge_in_contents_and_do_so` has a side effect (it merges), so the crusher check evaluates it only when the machine is at capacity.
- #94925 as written might include other causes for crushers "on a wire" breaking; only the two above were found.
