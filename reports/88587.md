## #88587: Paintings Manager will not open a second time

### The bug

An admin opens the Paintings Manager (verb "Paintings-Manager"), closes it, and opens it again. The reporter saw the window flash open and immediately close, with no runtime in the log.

### Reproduction

On master, as an admin on the test server:

1. Run the Paintings Manager verb. The paintings admin panel opened in a tgui window.
2. Close the window.
3. Run the verb again.

Observed: it opened again (the same window slot was reused) and stayed open. Opening it twice at the same time gave two windows; closing both and reopening also worked. Only the server side was checked: the test client did not run the tgui JavaScript, so the page itself was not seen rendering.

### Cause (of the original bug)

According to the description of upstream PR 97619, the verb used one static datum that was deleted when its UI closed and never recreated, so the second open used a deleted datum. On master the verb is

```
ADMIN_VERB(painting_manager, R_ADMIN, "Paintings Manager", ...)
	var/datum/paintings_manager/tgui = new()
	tgui.ui_interact(user.mob)
```

(`code/modules/admin/painting_manager.dm:1-3`), so each call makes a new datum. The old code was not examined on this checkout; the cause comes from the PR text and the current code.

### Fix

None needed. The PR also touched similar admin UIs such as the trophy manager; that was not checked.

### Verification

See Reproduction. Not checked: the browser side of the window, and the old behavior on a build before the PR.

## #59183: library portraits give no do_after and no moodlet

### The bug

Examining an employee photo in a frame starts "You start appraising", takes a few seconds and gives a mood bonus. Examining a painting, including library portraits, did neither.

### Reproduction

Using the Lua editor on the test server:

1. Spawn a human and two wall paintings (`/obj/structure/sign/painting`), each with a canvas, one with `credit_value` 0 and one with 400. Call `add_art_element()` on both.
2. Examine each painting as the human.

Observed: exactly one appraisal message, "... stops and looks intently at Painting", from the 400-credit painting. The 0-credit painting produced nothing.

### Cause

`add_art_element()` adds `/datum/element/art` only if `get_art_value()` of the painting's patronage is nonzero (`code/modules/art/paintings.dm:746-750`). `get_art_value()` (`:756-764`) returns a value only from `PATRONAGE_NICE_FRAME` upward (375 credits); below that it returns 0, so no element is added. The element is what provides the 2 second `do_after` and the mood event (`code/datums/elements/art.dm:45-62`). Photo frames always add the element with a fixed `art_value` (`code/modules/photography/photos/frame.dm:79`), which is the difference the reporter noticed. Library portraits loaded from the saved JSON go through `load_persistent` (`paintings.dm:742`) and get the element only if their saved `credit_value` is high enough.

### Fix

None. This looks like intended behavior: a painting's art value depends on patronage.

### Notes

Uncertain: whether unpatronized paintings should give a small art value. That would be a design change (for example a bad-art fallback in `get_art_value()`); it was left alone.
