# #62267: Ore satchel shows a stale ore total after ore is merged into a stored stack

| | |
|---|---|
| Issues | [#62267](https://github.com/tgstation/tgstation/issues/62267): verified (a closely related stale-display case, not the exact steps in the issue) |
| Status | verified, fixed on branch |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/62267 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Storages with `numerical_stacking` (the mining satchel) draw one number per item type on the first matching stack: the total of all stacks of that type. That number is only recomputed when the storage refreshes its views, but `/obj/item/stack/update_name` also overwrites the stack's own maptext with its own amount, and changing the amount of a stack that is already inside the bag never triggered a refresh. The displayed total therefore went stale. The fix makes `update_name` refresh the storage views when the stack is in a numerically stacking storage.

## The bug

The issue reporter filled a satchel, merged ore in hand, put the larger stack back and saw the satchel display the old number, with the extra ore only reappearing after it was taken out again. In the reproduction on the test server the visible symptom was the same: the satchel held more ore than the number drawn on it.

## Reproduction

The exact sequence from the issue (merging stacks in hand and clicking the bag with an oversized stack) was not reproduced. The agents found that a plain click-insert usually ends with the right number, because a change in `w_class` triggers a refresh, and that stacks held in hand merge automatically. The stale display was instead reproduced through the walk-over pickup path (`pickup_ore`), which merges floor ore into a stack already stored in the bag. The pickup was triggered by calling the proc from the Lua editor, not by walking over the ore.

On master:

1. Open the Lua editor. Spawn a human and an `/obj/item/storage/bag/ore`. Insert an iron ore stack of 50 and one of 35 into the bag's storage, put the bag in the human's hand and give the human the admin's ckey.
2. Alt-click the satchel to open its storage UI. The first iron ore stack shows "85".
3. From Lua, call `pickup_ore` on the bag with a new iron ore stack of 5 on the floor.

Observed: the bag then held 50 + 40 = 90 iron ore, and the 40 stack's own maptext changed to "40", but the number drawn on the first stack stayed at "85".

## Cause

- `code/datums/storage/storage_interface.dm:121-122`: for numerically stacking storage, the displayed item's `maptext` is set to the computed total (`storage_contents[item]`). This only runs when the storage refreshes (`refresh_views`, `code/datums/storage/storage.dm:1048`), so the number is only as fresh as the last refresh.
- `code/game/objects/items/stacks/stack.dm:122`: `update_name` sets the stack's maptext to its own `get_amount()` when it is in a mob or in a storage. Adding to or using a stack calls this, so a stack inside the bag has its displayed number replaced with its own amount.
- Nothing refreshed the storage after a stored stack changed amount; the existing refresh on insert is tied to `w_class` changes, which merging into a stored stack does not cause. So the first stack kept a total that no longer matched the contents.

## Fix

One commit, "Fix issue 62267: refresh numeric storage display when a stored stack changes amount", in `code/game/objects/items/stacks/stack.dm`. After `update_name` sets the maptext, it now does:

```dm
var/datum/storage/loc_storage = loc?.atom_storage
...
if(loc_storage?.numerical_stacking && !loc_storage.block_insert_remove_updates)
	loc_storage.refresh_views()
```

The check for `block_insert_remove_updates` leaves the mass pickup and mass empty paths alone, because they set that flag and already refresh once at the end. The refresh is a loop over the mobs currently viewing the storage, so with no one viewing it, it does nothing.

## Verification

After rebuilding, the same setup was run on the test server with the satchel UI open:

- `pickup_ore` with an iron stack of 5: the first stack's number changed from "85" to "90" immediately, and the second stack's from "35" to "40".
- After a server restart, 20 single iron ore piles were picked up with `pickup_ore`: the first stack's number went from "85" to "105" (the real total), and the second stack's from "35" to "50". The 20 calls took about 10 ms in total.
- The runtime log of the test rounds after the fix had no new runtime errors; the earlier round's log had two runtime errors, which were not examined here.

Not checked: the exact steps from the issue (merging in hand, inserting an oversized stack), actually walking over ore, and other numerically stacking storages besides the ore satchel.

## Notes

- `pickup_ore` does not set `block_insert_remove_updates`, so walking over a pile of N ores does N refreshes, but only while someone has the UI open. This is the same cost as the existing refresh on insert.
- Reading `bag.contents` from Lua crashed the test server once while testing; it is unrelated to this fix and was avoided afterwards.
