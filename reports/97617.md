## Summary

A directional window crafted from titanium glass ("directional shuttle window") is created unanchored but already in the fully secured construction state, so a screwdriver cannot anchor it and it looks anchored to a player. The cause is that `/obj/structure/window/reinforced/titanium/unanchored` sets `anchored = FALSE` but inherits `state = RWINDOW_SECURE`. The fix sets the state to `WINDOW_OUT_OF_FRAME`, like the other unanchored reinforced windows. A second fix lets plastitanium window fillings be placed on a grille, which the grille's entry check rejected.

## The bug

### #97617

The report says a directional plastitanium window "claims to be anchored but is actually freely movable" and can only be anchored after going through the deconstruction steps; a comment adds that directional titanium glass/shuttle windows are affected too. In testing, only the titanium recipe was broken. The directional plastitanium recipe was not affected.

### #97618

The report says plastitanium windows turn into "window filling" when deconstructed, that the filling can be placed on girders but not on grilles, and asks for a tooltip if this is intended. The triage title ("build as pod windows") is somewhat misleading. What was found:

- The directional plastitanium recipe builds a window named "pod window" (a `survival_pod` type with the plastitanium icon). This is a naming matter and was left as is.
- A fulltile "pod window" deconstructs into a plastitanium window filling (`/obj/item/stack/wall_filling/plastitaniumglass/pod`). This looks intentional.
- The real defect: the grille never accepted a window filling, although the code further down already handled one.

## Reproduction

Everything below was done with admin tools (the Lua editor) on the test server, by spawning objects and calling item-use procs directly. The player action itself (opening the crafting menu and crafting) was not driven; the recipe's result types were read from `code/game/objects/items/stacks/sheets/glass.dm`.

### #97617

1. Spawn `/obj/structure/window/reinforced/titanium/unanchored`, which is what the "directional shuttle window" recipe builds (`glass.dm:238`).
2. Read its `anchored` and `state` variables. On master: `anchored` 0, `state` 8 (`RWINDOW_SECURE`).
3. For comparison, `/obj/structure/window/reinforced/unanchored` and `/obj/structure/window/reinforced/survival_pod/unanchored` (the directional plastitanium recipe, `glass.dm:272`) showed `anchored` 0, `state` 0. A screwdriver anchored the plastitanium one (`anchored` 1).

### #97618

1. Hold a plastitanium window filling in hand and use it on an anchored grille.
2. On master the grille's `item_interaction` rejects it (see Cause), so no window is placed.

## Cause

### #97617

`code/game/objects/structures/window.dm:494` defines `/obj/structure/window/reinforced` with `state = RWINDOW_SECURE` (line 504). The unanchored variants that are meant to be built by hand override it, e.g. `/obj/structure/window/reinforced/unanchored` sets `anchored = FALSE` and `state = WINDOW_OUT_OF_FRAME`. `/obj/structure/window/reinforced/titanium/unanchored` (`window.dm:913`) only set `anchored = FALSE`, so it kept the secure state. The window's screwdriver handling then treats it as already screwed to a frame, so it cannot be anchored without first being taken through the deconstruction steps. The type was also defined twice (`window.dm:913` and `window.dm:918`).

### #97618

In `code/game/objects/structures/grille.dm:247` the window-placing branch began with:

```dm
if(!broken && (is_glass_sheet(tool) || istype(tool, /obj/item/stack/sheet/bronze)))
```

Further down (lines 284-287) the same branch already built `plastitanium/windowfill` from `/obj/item/stack/wall_filling/plastitaniumglass/basic` and `shuttle/survival_pod` from `.../pod`, but fillings could never reach that code because they failed the entry check. Girders accept them, so they worked there.

## Fix

Two commits on the branch.

- **"Fix issue 97617: directional titanium windows start in the secure state while unanchored"** sets `state = WINDOW_OUT_OF_FRAME` on `/obj/structure/window/reinforced/titanium/unanchored` and removes the duplicate definition.
- **"Fix issue 97618: plastitanium window fillings can be placed on grilles"** adds `/obj/item/stack/wall_filling/plastitaniumglass` to the grille's entry check. A filling costs one item rather than two sheets, and the "not enough" message is adjusted to match.

## Verification

On the rebuilt test server, via the Lua editor:

- A spawned `titanium/unanchored` window had `anchored` 0 and `state` 0 (it was 0 / 8 before). Using a screwdriver on it set `anchored` to 1.
- Two anchored grilles with a person beside them: a `.../plastitaniumglass/pod` filling on one produced a "pod window" (`shuttle/survival_pod`) on the tile with the grille; a `.../plastitaniumglass/basic` filling on the other produced a "plastitanium window" (`windowfill`). Both were rejected before the fix.
- No new runtimes appeared in the round's runtime log.

Not checked: crafting through the crafting menu (including the direction check), and the placement time and message wording of the new grille path beyond what the result showed. Placement of a filling on a girder was not retested. An SDQL query with MAP and comparisons failed with a parsing error and was not pursued.

## Notes

- Naming ("pod window" for the directional plastitanium recipe, window fillings from deconstruction) was left as design; a tooltip or rename is a separate decision for maintainers.
- The grille fix accepts any `/obj/item/stack/wall_filling/plastitaniumglass` subtype; unknown subtypes would fall through to the default branch and build a plain window, so new subtypes need a matching branch.
