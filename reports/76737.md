# #76737: Emergency shuttle announces departure and counts down while still docked, never entering transit

## Summary

The emergency shuttle can reach the end of its launch countdown on a tick where no transit dock is ready. `SHUTTLE_IGNITING` resets the timer for that case, but it had already read `time_left`, so the same tick launched anyway. `enterTransit()` then only logged a warning, and the shuttle was marked as escaping, announced as departed and given an escape timer while still docked. When that timer ended it was moved to CentCom and the round ended as normal, which is what both issues describe. The fix refreshes `time_left` after the reset, makes `enterTransit()` report failure, and keeps the shuttle igniting (retrying in 2 seconds) instead of announcing a departure when it cannot enter transit.

## The bug

#76737 (round with a blob as hostile environment, shuttle launched early with an emag): the shuttle never entered hyperspace after the IGN countdown, but the ESC timer still ran and the shuttle arrived at CentCom as usual. A commenter adds that the shuttle manipulator believed the shuttle was moving, so it could not be flown manually, and that it "has been happening for a while". Another round (212007) was said to show the same.

#82464 reports the same symptom: the emergency shuttle does not leave the station when it should and lands at CentCom without a transit phase when the round ends. A comment suspects it is a repeat of an older issue.

## Reproduction

The issue's own conditions (a hostile environment such as a blob, then an early launch) did not produce the bug in testing. The mechanism was reproduced by forcing the timing. Setup: Metastation, admin tools on a test server.

Baseline checks on the unfixed build (all behaved correctly):
- Calling the shuttle with the Lua editor (`request(nil)`, `setTimer(30)`) and emagging the shuttle consoles (SDQL2: `UPDATE /obj/machinery/computer/emergency_shuttle SET obj_flags = obj_flags | 1`) made the shuttle go through IGN, enter transit (z=12) and reach ESC normally. This was also checked on Kilo Station.
- The hostile-environment flow: registering a hostile environment while docked and emagging gave STRANDED ("Departure postponed"). Clearing it returned the shuttle to DOCKED for 3 minutes, and a second emag gave IGN, transit and ESC as normal.
- The first transit dock generation is slow (over 10 seconds), during which the IGN timer keeps being reset. With no assigned transit for a while, IGN is normal.

Forced reproduction on the unfixed build:
1. Call the shuttle and set a short timer (`e:request(nil); e:setTimer(30)`). Wait until it is docked.
2. In the Lua editor, set `e.mode = "igniting"` and `e:setTimer(0)`. This models the IGN timer expiring in a tick where no transit dock is ready.
3. Observed: `runtime.log` showed `WARNING: shuttle "emergency" could not enter transit space. S0=emergency_home S1=null ...` (`mobile_port.dm`, in `enterTransit()`; also logged for the escape pods). The station was then told "The emergency shuttle has left the station. Estimate 2 minutes ...", while the shuttle was still at z=2 with mode ESCAPE and no assigned transit.

This is a forced race, not a naturally occurring one. A runtime logged as `CRASH("Emergency shuttle did not move to transit z-level!")` follows in the same branch on master (it is raised after the state has already been committed).

## Cause

In `code/modules/shuttle/mobile_port/variants/emergency/emergency.dm`, `check()` reads `var/time_left = timeLeft(1)` once at the top (line 149). The `SHUTTLE_IGNITING` branch (starts at line 197) then checks that every relevant port has its transit zone ready:

```dm
if(!success)
	setTimer(ENGINE_START_TIME)

if(time_left <= 50 && !sound_played)
	...
if(time_left <= 0 && !SSshuttle.emergency_no_escape)
```

When the transit is not ready (`success` false) the timer is pushed back, but the stale `time_left` is used for the launch test just below, at line 218. If the timer ran out in that very tick, the shuttle launches anyway. In that branch, pods get `on_emergency_launch()`, the launch sound plays, and `enterTransit()` is called (line 229). In `code/modules/shuttle/mobile_port/mobile_port.dm`, `enterTransit()` (line 333) does not report failure. If there is no `assigned_transit`, or `initiate_docking` fails, it only calls `WARNING(...)`. On lockdown or `!canMove()` it sets the mode to idle. The caller ignores the result and continues to set `mode = SHUTTLE_ESCAPE`, `launch_status = ENDGAME_LAUNCHED`, start the escape timer and announce the departure. The shuttle stays docked and, when the ESC timer ends, is moved to `emergency_away` (CentCom).

The conditions that make the timer run out in a tick with no ready transit were not identified in the logs of the original rounds. The investigation notes that `SSshuttle` runs once per second, and that lag making the subsystem fire late, or a lockdown or `canMove()` failure, can produce the same outcome. This is reasoning from the code, not something observed.

## Fix

One commit, "Fix issue 76737: emergency shuttle no longer launches (and counts down ESC) without entering transit". It touches two files.

- `emergency.dm`: after the `setTimer(ENGINE_START_TIME)` reset, `time_left = timeLeft(1)` is refreshed, so a timer pushed back in this tick no longer launches. Also, the call `enterTransit()` is now `if(!enterTransit())`. On failure the shuttle stays in `SHUTTLE_IGNITING`, sets a 2-second timer and returns before events, the ESC mode change and the departure announcement. The trailing `CRASH("Emergency shuttle did not move to transit z-level!")` was removed, since it only fired after the bad state had been committed.
- `mobile_port.dm`: `enterTransit()` now returns TRUE when the shuttle is in transit and FALSE when it could not leave (lockdown or `!canMove()`, failed docking, or no assigned transit). The `WARNING` calls are kept. The other callers of `enterTransit()` (in `mobile_port.dm`) do not use the return value.

Alternatives considered: only refreshing `time_left` would fix the observed forced race but would leave `enterTransit()` silently failing for other reasons (lockdown, `canMove`, a failing `initiate_docking`), which lead to the same visible symptom. Making failure visible and retrying handles all of them.

## Verification

After the fix was built, the same forced steps were repeated on the test server. No departure was announced while no transit existed. About 35 seconds later the transit dock was generated and the shuttle entered transit: mode `escape`, z=12, about 92 seconds left, and the departure announcement came at that point. No `WARNING` or `CRASH` appeared in `runtime.log`. The baseline emag flow was also confirmed to still work.

Not checked:
- The issue's real trigger (a long lag period, or a blob hostile environment before an early launch) was not reproduced, in either the unfixed or the fixed build.
- #82464 was not run separately; it has no steps, and it is treated as the same symptom and code path.
- The `transit_failure()` path was not exercised (see Notes).
- A failed `enterTransit()` from lockdown or `canMove()` rather than a missing transit dock was not tested.

## Notes

- Known minor side effect: when `enterTransit()` keeps failing, the retry loop plays the hyperspace launch sound every 2 seconds, because the sound and pod launch code runs before `enterTransit()` in each retry. Only the sound repeat was recorded.
- A second route to the same symptom exists and was left alone: `transit_failure()` in `emergency.dm` (line 297, called from `code/controllers/subsystem/shuttle.dm` around lines 245-249 after `MAX_TRANSIT_REQUEST_RETRIES` = 10 failed transit-dock generations). It sets ESCAPE and moves directly to the CentCom dock on purpose ("to prevent deadlock") and announces a "direct jump". `transit_request_failures` is never reset. This was read in the code but not tested.
- #76737's comment suggests a hostile environment that is never removed. The STRANDED branch of `check()` that calls `checkHostileEnvironment()` looks unreachable, because `check()` returns early when `timer` is 0 while stranded. A hostile source that is deleted without `clearHostileEnvironment` could therefore strand the shuttle forever. This was noted from the code, not tested, and is a separate issue from the one fixed here.
- The shuttle was not found to be stuck after the bug. The "shuttle manipulator thinks it is moving" comment fits the shuttle being in mode ESCAPE.
