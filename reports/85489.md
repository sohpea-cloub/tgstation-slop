## Summary

`/turf/open/floor/holofloor/item_interaction()` returned `ITEM_INTERACT_BLOCKING` for every item. Because that proc runs before the held item's own `interact_with_atom()`, paint cans (#85489) and spraycans (#91445) never got to act on holodeck floors such as the Photobooth's white floor. The fix keeps the block only for floor tiles and sheets and otherwise defers to the normal floor handling. #98032 (wrenches stop working on the holodeck floor after a program has been run) looked like the same bug but is not: the offline template's floor is a different turf type, which has no `wrench_act`.

## The bug

In the Holodeck's "Photobooth" program, which has a plain white floor so that players can paint it, adaptive paint does nothing when used on the floor. It still works on walls and on non-holodeck floors. #91445 reports the same for spraycans on that floor. The paint can's paint count does not go down and the floor does not change; there is no message.

## Reproduction

### #85489 and #91445

On master, using admin tools:

1. Using the Lua editor, called `load_program('holodeck_photobooth', true, false)` on the holodeck console. The floor at the test tile became `/turf/open/floor/holofloor/pure_white` ("white floor"). Before the call it was `/turf/open/floor/engine`.
2. Spawned a human next to a Photobooth floor tile, gave it an `/obj/item/paint/red` (200 units of paint), and called `ClickOn()` on that floor tile with the paint in hand. This calls the same click handling a player click goes through, but was not a physical mouse click.
3. Result: the paint count stayed at 200.
4. Control: the same steps on an ordinary `/turf/open/floor/iron` tile in the station gave a paint count of 199 after one click.

The turf's `color` var read `nil` in both cases, so the paint count was used as the signal. A spraycan was spawned and set to paint mode but, for the reason given under Verification, it was not clicked in game; the paint can stands in for it.

### #98032

Not reproduced as a before and after in game; analysis is from the code, plus one in-game observation:

- Before any program is loaded, the holodeck floor tile was `/turf/open/floor/engine`. `/turf/open/floor/engine/wrench_act()` (`code/game/turfs/open/floor/reinforced_floor.dm:44`) removes its rods, which matches the "floor can be wrenched at roundstart" part of the report.
- The report's steps (load a program, switch back to the offline program, try the wrench again) were not run in game.

## Cause

### #85489 and #91445

`code/modules/holodeck/turfs.dm:11-12` on master:

```dm
/turf/open/floor/holofloor/item_interaction(mob/living/user, obj/item/tool, list/modifiers)
	return ITEM_INTERACT_BLOCKING // Fuck you
```

`base_item_interaction()` (`code/game/atom/atom_tool_acts.dm:8`) runs in this order: `tool_act()` (only when combat mode is off, so wrenches and other tools with a `*_act` are unaffected), the interaction signals, then the target's `item_interaction()`, and only after that the held item's `interact_with_atom()`. When the target's `item_interaction()` returns a non-zero value the chain stops. The holofloor returned a blocker for every item, so `/obj/item/paint/interact_with_atom()` (`code/game/objects/items/paint.dm:115`) and `/obj/item/toy/crayon/interact_with_atom()` (`code/game/objects/items/crayons.dm:601`), which also handles spraycans, were never reached.

The override's intent seems to be that holograms cannot be built on or replaced. The real floor `item_interaction()` (`code/game/turfs/open/floor.dm:128`) handles replacing a floor tile with a tile stack and, in combat mode, sheets.

### #98032

The roundstart holodeck floor is the mapped `/turf/open/floor/engine`. When the console initializes it calls `load_program(offline_program, TRUE)`, but `program` already equals the offline program, so `load_program()` returns at its first check (`code/modules/holodeck/computer.dm:197`) and the mapped floor is left alone. Once any other program is loaded and the holodeck goes back offline, `_maps/templates/holodeck_offline.dmm` is loaded, and that template is made of `/turf/open/floor/holofloor/plating`. That type has no `wrench_act` (only `engine` defines one among floor turfs), and its parent `item_interaction()` is the blocking override above. So after the first program the floor can no longer be wrenched, for a reason separate from the paint problem. The fix described below does not change this.

## Fix

One commit, "Fix issue 85489: let paint, spraycans and other non-tile items interact with holofloors", changes `holofloor/item_interaction()` in `code/modules/holodeck/turfs.dm` to:

```dm
	// Holograms can't be built on or replaced, but everything else (paint, spraycans, ...) should still work
	if(istype(tool, /obj/item/stack/tile) || istype(tool, /obj/item/stack/sheet))
		return ITEM_INTERACT_BLOCKING
	return ..()
```

Floor tiles and sheets are still refused, which keeps the original purpose of the override (nobody can replace or build on a hologram). Everything else falls through to the parent floor handling and then to the item's own `interact_with_atom()`.

The commit does not touch the offline template, so #98032 is unchanged.

## Verification

After rebuilding and restarting the test server, with the same steps as above (Photobooth loaded, human, `/obj/item/paint/red`, `ClickOn()` on a Photobooth floor tile):

- The paint count dropped from 200 to 199, as on an ordinary iron floor, so the paint was used on the holofloor.
- Calling `item_interaction()` directly on the holofloor with an iron floor tile stack and with an iron sheet stack still returned `ITEM_INTERACT_BLOCKING`.

Not checked:

- The spraycan (#91445). Its `do_after` delay cannot be driven from the Lua editor, so it was not clicked. Both items go through the same `interact_with_atom()` path that the override was blocking, but that is inferred.
- That the floor's colour visibly changed. Only the paint count was read.
- Any player-driven click with a mouse; clicks were sent with `ClickOn()` from the Lua editor.
- Whether other items now interact with holofloors in ways nobody wants (see Notes).
- The #98032 sequence in game.

## Notes

- **Other items on holofloors.** Before the change, no item's `interact_with_atom()` could act on a holofloor. Now every item except tile and sheet stacks reaches the parent floor's `item_interaction()` and then its own `interact_with_atom()`. Nobody went through which other items might be unwanted on a hologram.
- **#98032 needs an owner decision.** The offline template could use `/turf/open/floor/engine` so the floor stays wrenchable after a program, but that changes what the holodeck rebuilds after every program. Alternatively `holofloor/plating` could get a `wrench_act`. I did not change either. The group's title ("holofloor blocks all item interactions (paint, spraycan, wrench)") covers #98032 only loosely: wrench interactions go through `tool_act()`, which runs before the blocking override, so the override never stopped wrenches.
- The `attackby()` override on the holofloor (`turfs.dm:8`) also returns early for everything; it is legacy and was not changed.
