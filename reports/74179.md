## Summary

Three reports describe an overlay that disappears when something moves to a z-level with a different plane offset: the slime mood face (#74179), the walking mushroom's cap (#84562) and the assembly on a rigged welding tank (#70968). The first two share one cause. `cut_overlays()` clears `overlays` but leaves the old `managed_overlays` list behind. On a z-layer change `update_icon()` compares the lengths of the two lists, decides it "fully controls" the overlays, and nulls them, wiping the overlay that was added by hand since. The fix makes `cut_overlays()` also clear `managed_overlays`. #70968 has a different mechanism: the tank stored a frozen copy of the holder as an overlay, which kept the wrong plane after a z change; it is now built in `update_overlays()` so it is rebuilt at the right plane.

## The bug

- **#74179.** A slime from a pyro anomaly loses its face when it goes up or down a z-level on a multi-z map (Icebox, Tramstation in the report).
- **#84562.** A walking mushroom loses its cap going up or down stairs, and it does not return when taking the mushroom back. The reporter's follow-up says it regained the cap when it was killed, which fits `update_mushroomcap()` being called from `death()`.
- **#70968.** A welding tank rigged with an igniter and signaler assembly shows the assembly on the tank. After going up or down a ladder or stairs the assembly is no longer visible, although the tank still is, so nobody can tell the tank is a bomb.

## Reproduction

All steps used the Lua editor on a test round using the multi-z debug map, with an observer admin. The mobs were spawned in the Lua editor and moved across z-levels with `forceMove` rather than walked through stairs or a ladder. The slime was an ordinary slime given a mood and not a player-controlled one; the overlay logic involved does not depend on a player controlling it.

### #74179 and #84562

1. Spawn `/mob/living/basic/slime`, set `current_mood = ':3'` and call `regenerate_icons()`. Inspecting the slime showed the mood face overlay (`aslime-pout`).
2. `forceMove` the slime to the same x,y on the z-level above (the move changed its plane from -218 to -111; `same_z_layer` was FALSE).
3. Inspect it again: the face overlay was gone. Moving it back did not restore it.
4. Spawn `/mob/living/basic/mushroom` and move it the same way: its `mushroom_cap` overlay was gone as well.

### #70968

1. Spawn a `/obj/structure/reagent_dispensers/fueltank` and an `/obj/item/assembly_holder` inside it, set it as the tank's `rig`, and put the holder's overlay on the tank by hand the way `item_interaction` does (`add_overlay(holder)`).
2. Move the tank to another z-level. The tank still had an "Assembly" overlay entry, but as a snapshot of the holder from the moment it was added: the holder's own `plane` had been updated to the new offset (-218) while the overlay copy did not follow.

Limits: the plane of an individual overlay could not be read through the available client tooling, so the actual invisibility of the assembly in #70968 was not seen. The snapshot with a stale plane is what was observed; that it renders as invisible follows from how BYOND planes work, not from a screenshot.

## Cause

### #74179 and #84562

Every movable with a generic emissive blocker gets a flattened blocker overlay in `Initialize()`, added both to `overlays` and to `managed_overlays` (`code/game/atoms_movable.dm:174-203`). `managed_overlays` is the list of overlays that `update_icon()` believes it put there itself.

Slimes and mushrooms rebuild their look by hand:

- `/mob/living/basic/slime/regenerate_icons()` calls `cut_overlays()` and then `add_overlay("aslime-[current_mood]")` (`code/modules/mob/living/basic/slime/slime.dm:198-209`).
- `/mob/living/basic/mushroom/update_mushroomcap()` does `cut_overlays()` then `add_overlay(cap_living)` (`code/modules/mob/living/basic/space_fauna/mushroom.dm:117-124`).

`cut_overlays()` only does `overlays = null` and a bookkeeping call (`code/controllers/subsystem/overlays.dm:62-68`), so `managed_overlays` still lists the emissive blocker that is no longer there. The atom then has one overlay (the face or cap) while `managed_overlays` still has one entry (the stale blocker).

When the atom changes z-layer, `on_changed_z_level()` calls `update_appearance()` to recalculate planes (`atoms_movable.dm:1264-1273`), which reaches `update_icon()`. There:

```dm
if(managed_overlays)
	full_control = length(overlays) == (islist(managed_overlays) ? length(managed_overlays) : 1)
	if(full_control)
		overlays = null
```
(`code/game/atom/atom_appearance.dm:82-86`)

The lengths happen to match (1 and 1), so `update_icon()` takes "full control" and clears `overlays`, deleting the hand-added face or cap. Nothing puts it back until something recalculates it (for the mushroom, death does).

### #70968

`/obj/structure/reagent_dispensers/item_interaction()` does this when rigging a tank (`code/modules/reagents/reagent_dispenser.dm:104-107`):

```dm
assembliesoverlay = holder
assembliesoverlay.pixel_w += 6
assembliesoverlay.pixel_z += 1
add_overlay(assembliesoverlay)
```

`assembliesoverlay` is declared as a `mutable_appearance` (line 33) but is assigned the holder object itself, so the pixel offsets are applied to the real holder, and `add_overlay()` takes a snapshot of its appearance at that moment. On a z-layer change the holder's plane is recalculated but the snapshot in the tank's `overlays` is not, because it is not part of `managed_overlays`, so it keeps the old plane. The detach path calls `cut_overlays(assembliesoverlay)` (line 151), but `cut_overlays()` takes no argument, so it clears all of the tank's overlays.

## Fix

Two commits.

1. **"Fix issue 74179: cut_overlays() also forgets managed_overlays"** (`code/controllers/subsystem/overlays.dm`). `/atom/proc/cut_overlays()` now also sets `managed_overlays = null`, with a comment explaining the stale-list problem. After a `cut_overlays()` followed by hand `add_overlay()`, `managed_overlays` is empty, so `update_icon()` no longer thinks it controls the overlay list and leaves the hand-added overlay alone. This fixes #74179 and #84562 together, and every other atom that rebuilds overlays by hand after `cut_overlays()`. It was chosen over changing the slime and mushroom code individually because the stale bookkeeping is wrong for any caller: once all overlays are gone, nothing is managed.
2. **"Fix issue 70968: rig overlay on reagent dispensers is rebuilt in update_overlays()"** (`code/modules/reagents/reagent_dispenser.dm`). The `assembliesoverlay` variable is removed. A new `update_overlays()` override builds a fresh `mutable_appearance` from `rig` with `plane = FLOAT_PLANE` and `layer = FLOAT_LAYER` and the same +6 / +1 pixel offsets, and attaching, detaching or losing the rig (`Exited`) just calls `update_appearance(UPDATE_OVERLAYS)`. A floating-plane overlay follows its parent's plane, and since it is part of the managed overlays it is rebuilt on a z change. It also stops changing the holder's own pixel offsets and removes the bad `cut_overlays(assembliesoverlay)` call.

## Verification

On a rebuilt test server, same Lua-editor approach:

- Slime with a mood face and a walking mushroom: both overlays persisted after moving to the z-level above and after coming back.
- Fuel tank with a rig: the rig overlay was present after the z move, and was removed when the holder was taken out (detached) in a later step. Attach, detach and a z round trip worked. The runtime log had no new errors.

Not checked:

- #70968 visually: whether the assembly shows at the right plane in a real client (the plane of overlays could not be read), so that fix rests on the code, not on a before/after screenshot.
- Rigging a tank through the real item interaction (the 2-second attach and detach with hands); the rig was assigned from the Lua editor and `update_appearance` was called directly.
- Real stairs or ladders; all moves were `forceMove` to the same x,y on another z.
- A player-controlled slime (the report says "sentient").
- Any other of the roughly 70 `cut_overlays()` callers in the tree for regressions, and the unit tests.

## Notes

- The first commit changes a core proc used everywhere, so a maintainer should weigh it. Code reading turned up one caller that relied on the old behaviour: `/mob/living/carbon/alien/adult/update_icons()` calls `cut_overlays()` and then loops over `managed_overlays` to re-add them (`code/modules/mob/living/carbon/alien/adult/adult_update_icons.dm:1-6`). With the fix `managed_overlays` is empty at that point, so that loop adds nothing; the aliens' emissive blocker would be missing from their `overlays` until the next full `update_appearance()`. That was not tested and is probably cosmetic, but it should be checked.
- `RTD.dm:268` reads `floor.managed_overlays` to copy floor designs. The fix only changes it for floors that had `cut_overlays()` called on them and not rebuilt.
- An alternative would be to leave `cut_overlays()` as it is and have slimes, mushrooms and other hand-rebuilding callers call `update_appearance()` instead of `add_overlay()`, which is a much larger change.
- The walking mushroom's follow-up in #84562 (cap came back when it was killed) is consistent with the cause: `death()` calls `update_mushroomcap()`, which re-adds it.
- The #70968 title says the overlay disappears; the real overlay survived on the tank but at a stale plane. The old code also left the holder with permanently shifted pixel offsets, which is gone with the second commit.
