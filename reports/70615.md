# #70615: Contextual screentips don't update when the held item changes

| | |
|---|---|
| Issues | [#70615](https://github.com/tgstation/tgstation/issues/70615): verified, fixed |
| Status | Fixed on a branch and checked in game; not merged |
| Fix branch | [fix/70615](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/70615) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

A contextual screentip is built once, when the mouse enters an atom, and is never rebuilt. It depends on the item in the player's active hand, so if that item is dropped, taken or swapped away while the cursor stays still, the tip keeps describing a tool the player no longer holds. The fix remembers the atom the client last hovered and, when the mob equips an item, unequips one or swaps hands, queues that atom through the existing mouse-entered subsystem so the tip is rebuilt on the next tick.

## The bug

The issue reporter hovered the cursor over a table while holding a wrench, then dropped the wrench with the hotkey. The screentip kept offering the wrench action ("right click to disassemble") although their hands were empty. Commenters noted that this is general: the tip only changes once the cursor re-enters an atom. Atom-internal state changes (for example inserting a pen or ID into a PDA) have the same stale-tip problem.

## Reproduction

On master, with admin tools:

1. Join the round as an Assistant.
2. With the Lua editor, spawn a `/obj/structure/table` next to the character and put a wrench in the active hand (`put_in_active_hand`).
3. Hover the mouse over the table. The screentip text changed from empty to `table / [RMB] Deconstruct`.
4. Without moving the mouse, press the drop key (Q).

Observed: the screentip text stayed `table / [RMB] Deconstruct` with empty hands, and no further update was sent for the screentip. The bug reproduced as reported, through the real player actions (hover, drop key).

## Cause

`/atom/MouseEntered` only stores the atom in `SSmouse_entered.hovers[usr.client]` (`code/game/atom/_atom.dm:865`). The subsystem's `fire()` (`code/controllers/subsystem/mouse_entered.dm:12`) calls `on_mouse_enter()` for each stored atom and then clears the entry. `atom/proc/on_mouse_enter` (`code/game/atom/_atom.dm:871`) builds the screentip text, including a lookup of `user.get_active_held_item()` for the context. Nothing calls it again when the held item changes, so the text is only recomputed on the next mouse-enter.

## Fix

One commit, "Fix issue 70615: contextual screentips refresh when held items change" (5 files, 17 added lines):

- `code/_onclick/hud/hud.dm`: new `last_hovered_atom` weakref var on `/datum/hud`.
- `code/game/atom/_atom.dm`: `on_mouse_enter` sets `active_hud.last_hovered_atom = WEAKREF(src)` once the HUD is known to exist.
- `code/modules/mob/mob.dm`: new `/mob/proc/refresh_screentip()`. If the mob has a client and HUD, and no newer hover is already pending for that client this tick, it resolves `last_hovered_atom` and puts it back into `SSmouse_entered.hovers[client]`. The existing deferred `on_mouse_enter` then reruns on the next tick, so all the screentip logic stays in one place. It is called from `swap_hand`, after `COMSIG_MOB_SWAP_HANDS`.
- `code/game/objects/items.dm`: `equipped()` calls `user.refresh_screentip()` after `COMSIG_MOB_EQUIPPED_ITEM`.
- `code/modules/mob/inventory.dm`: the unequip path calls `refresh_screentip()` after `COMSIG_MOB_UNEQUIPPED_ITEM`.

This reuses the hover queue instead of rebuilding the tip directly, and it covers exactly the held-item cases in the issue title. Registering signals on each hovered object, or polling, was discussed in the issue but not implemented.

## Verification

On the test server with the fix built, same setup as the reproduction (table, wrench, cursor resting on the table):

- Drop (Q): the screentip changed from `table / [RMB] Deconstruct` to `table / [RMB] Flip`.
- Picking a wrench up again (Lua `put_in_active_hand`, which goes through `equipped()`): back to `Deconstruct`.
- Swap hands to the empty right hand (X): `Flip`.
- No new runtimes appeared in `runtime.log`.

Not checked: other item types or screentip contexts, ghost/AI/overmind viewers, losing the item by other means (someone else taking it, item deleted), and screentips disabled in preferences.

## Notes

- Atom-internal state changes (PDA pen/ID insertion, and similar) still do not refresh the tip. The issue discussion considered a general update signal or polling and the maintainers disagreed on the approach; this fix does not address that part.
- `last_hovered_atom` is not cleared when the cursor leaves the map onto non-atom space, so a later refresh rebuilds the tip for the old atom. This gives the same text as before and was not seen as a regression, but a maintainer may want to clear it.
- The refresh is skipped if a hover is already queued for the client in the same tick, so a fresh hover is never overwritten by the old atom.
