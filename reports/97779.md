# #97779: Dragging a worn item onto a hand slot never calls its `mouse_drop_dragged`

## Summary

Dragging an equipped item onto one of the HUD hand slots never reached the item's `mouse_drop_dragged()`. The base drag handler requires both the dragged atom and the drop target to be "reachable" by the user. A HUD hand slot is a screen object with no `loc`, so `IsReachableBy()` is always false for it, and the handler returns before calling either `mouse_drop_dragged()` or `mouse_drop_receive()`. The fix treats screen objects as reachable in that one check. The dragged atom is still checked normally.

## The bug

Some items override `mouse_drop_dragged()` to react when the wearer drags them. The tinfoil hat uses it to warn "Why would you want to take this off?" when dragged off the head, and the orange sneakers use it to refuse removal while cuffed. Dragging a worn tinfoil hat onto a hand slot printed nothing, and the override (and any breakpoint in it) never ran. Clicking the hat did show the message, as the reporter noted.

The hat stayed on the head regardless. Only items that hook `COMSIG_MOUSEDROP_ONTO` (storage items such as backpacks, and items with the `drag_pickup` element) come off by dragging onto a hand. That signal is sent before the reachability check, so they work. Every other `mouse_drop_dragged()` override on a worn item was effectively dead code for drags to the hands.

## Reproduction

1. On the test server, join the round as an Assistant.
2. Using the Lua editor, spawn a `/obj/item/clothing/head/costume/foilhat` and call `equip_to_slot_if_possible(hat, 64)` to put it on the head (slot 64 is `ITEM_SLOT_HEAD`).
3. Open the inventory (the "toggle" button) so the head slot and hand slots are visible.
4. Drag the hat from the head slot onto the left hand slot.

Observed on master: no chat message, and the hat stayed on the head. The expected message ("Why would you want to take this off? Do you want them to get into your mind?!") never appeared. This was done with the real drag action through the client, not by calling procs directly.

## Cause

`base_mouse_drop_handler()` in `code/_onclick/drag_drop.dm:26` sends `COMSIG_MOUSEDROP_ONTO` and `COMSIG_MOUSEDROPPED_ONTO` first, then does the checks:

```dm
var/combined_atom_flags = interaction_flags_atom | over.interaction_flags_atom
if(!(combined_atom_flags & INTERACT_ATOM_MOUSEDROP_IGNORE_CHECKS))
	//Check for adjacency
	if(!(combined_atom_flags & INTERACT_ATOM_MOUSEDROP_IGNORE_ADJACENT) && (!IsReachableBy(user) || !over.IsReachableBy(user)))
		return // should stop you from dragging through windows
```

(`code/_onclick/drag_drop.dm:39-43`). Screen objects normally set `INTERACT_ATOM_MOUSEDROP_IGNORE_CHECKS` (`code/_onclick/hud/screen_objects/screen_objects.dm:19`), but the hand slot deliberately resets `interaction_flags_atom = NONE` (`screen_objects.dm:269`) "so dragging objects into hands icon don't skip adjacency & other checks". So for a drop on a hand slot the adjacency check does run. `over.IsReachableBy(user)` (`code/_onclick/click.dm:217`) then fails: the slot is not in `direct_access`, is not a turf, and has a null `loc`, so it returns FALSE at `if(isnull(loc) || isarea(loc))`. The handler returns, and `mouse_drop_dragged()` and `mouse_drop_receive()` are never called.

The tinfoil hat's override is at `code/modules/clothing/head/tinfoilhat.dm:49`. The orange sneakers override (`code/modules/clothing/shoes/sneakers.dm:172`) is affected the same way.

## Fix

One commit, "Fix issue 97779: dragging worn items onto a hand slot never reached mouse_drop_dragged", changes the adjacency condition in `code/_onclick/drag_drop.dm`:

```dm
(!IsReachableBy(user) || !(istype(over, /atom/movable/screen) || over.IsReachableBy(user)))
```

A `/atom/movable/screen` target is treated as reachable; the dragged atom (`src`) must still be reachable. The check was changed rather than the hand slot's flags because the comment at `screen_objects.dm:269` shows the other checks (usability) are meant to stay active for hand-slot drops. The inputs don't record whether other approaches were considered.

## Verification

On the test server with the fix built:

- Dragging the worn tinfoil hat from the head slot to the left hand slot now prints "Why would you want to take this off? Do you want them to get into your mind?!", and the hat stays on the head.
- Regression check: dragging the equipped backpack onto the right hand slot still works (it goes through the storage signal path).

Not checked: the unit tests (`dm-test`) were not run. Drags of other item types onto hand slots, and drags to screen objects other than hand slots, were not exercised in game, and the orange sneakers path was not tested.

## Notes

- The hat could never be removed by dragging in the first place, since there is no unequip path for non-storage items; the report's "it doesn't get unequipped" is existing behaviour. After the fix only the message appears.
- Side effect: items lying on the floor (or otherwise reachable) that are dragged onto a hand slot now also get `mouse_drop_dragged(over = hand)` called. The existing overrides check for specific `over` types, and no effect was seen, but maintainers may want to look through the `mouse_drop_dragged` overrides for any that act on any `over`. The headset override (`user == over`) is an example of the kind that checks `over`.
- Other worn items with `mouse_drop_dragged` overrides (such as the headset's `attack_self` on self-drag) are not affected by drags to hands in any new way beyond the above.
