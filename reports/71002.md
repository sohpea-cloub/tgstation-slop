# #71002: Obsessed "photo in your bag" objective reported as failing with the photo in MODsuit storage

## Summary
The issue (filed in 2022 against client 514.1585) says the Obsessed objective "Take a photo of [name] while they're alive, and keep it in your bag" is not completed when the photo is kept in a MODsuit's storage. On current master the objective completes with the photo in MOD storage. The check searches everything the owner carries, recursively, and that includes the contents of an installed MOD storage module. No fix was needed or committed.

## The bug
As reported, an Obsessed player took the required photo and kept it in a MODsuit's storage, but the objective still showed as failed even though every other requirement was met. A comment on the issue from 2022 said the problem was in the Obsessed code, not in the MODsuit.

## Reproduction
Not reproduced. The test below used admin tools, with a hand-built objective rather than a real Obsessed round, and the photo was inserted by calling the storage procs directly.

1. Using the Lua editor, spawned two humans with minds: A (the owner) and B (the target).
2. Created a `/datum/objective/polaroid` with `owner` = A's mind, `target` = B's mind and `obsession_weakref` = `WEAKREF(B)`, the same way `code/modules/antagonists/obsessed/obsessed.dm:117-120` does.
3. Created a `/datum/picture` whose `mobs_seen` held B's weakref and whose `dead_seen` was empty, and a `/obj/item/photo` using that picture.
4. Equipped A with a `/obj/item/mod/control/pre_equipped/standard` on the back slot. Its compact storage module provides the MOD's storage, and the storage's real location is that module.
5. Called `check_completion()` in several states:
   - Photo on the floor: returned 0 (control).
   - Photo inserted into the MOD storage with `atom_storage:attempt_insert`: returned 1.
   - Photo removed with `attempt_remove`: returned 0.
   - Photo inserted again: returned 1.

Completion followed the photo's presence in the MOD storage exactly as it would for an ordinary bag. A photo held in A's hands was also expected to return 1; the report does not record that result separately.

Harness note: the first attempts returned 0 only because B's `weak_reference` is created lazily and was still nil in the test setup until `WEAKREF(B)` was called. The real Obsessed code calls `WEAKREF()`, so this was a test artefact, not a game bug.

## Cause
There is no defect on master. The check is:

```dm
/datum/objective/polaroid/check_completion()
	for(var/obj/item/photo/photo in owner.current?.get_all_contents())
		if((obsession_weakref in photo.picture?.mobs_seen) && !(obsession_weakref in photo.picture?.dead_seen))
			return TRUE
	return FALSE
```
(`code/modules/antagonists/obsessed/obsessed.dm:271-275`)

`get_all_contents()` (`code/__HELPERS/atoms.dm:2`) walks `.contents` recursively. A worn MOD control unit is in the mob's contents, the installed storage module is in the control unit, and items in the MOD's storage are in the module's contents because the storage's real location is set to the module (`code/modules/mod/modules/modules_general.dm:21-27`, `set_real_location(src)`). The photo is therefore found.

The 2022 comment that this was "an obsessed issue" does not match the current code. The reported failure was most likely fixed by the later MOD and storage rework, but the inputs do not identify which change did it.

## Fix
None. No commit was made.

## Verification
Not applicable, since nothing was changed. The behaviour on master was checked as described under Reproduction.

## Notes
- The objective text says "your bag", but any container whose contents are reachable through `get_all_contents()` satisfies the check, MOD storage included.
- Suggested disposition: close #71002 as already fixed on current master.
