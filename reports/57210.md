## Summary

The 2021 report says the Derelict's vault controller only updates on the first tick it is powered. On current master, a vault controller placed on a powernet with surplus power siphoned steadily and its doors cycled correctly. The report came from a round with an unmerged laser-hitscan test merge and an older power implementation, so the problem is probably already gone. Two small code defects were noticed but not changed.

## The bug

The issue, filed with a round ID and a test merge (#57080), only says: "Try to power vault controller. Find out that it only updates on first tick when its powered." No more detail was given.

## Reproduction

Not reproduced. What was tried on the test server, using the Lua editor and SDQL2:

1. Spawned a `/obj/machinery/computer/vaultcontroller` on a station cable. Its `siphoned_power` grew steadily: 0, then 832k, then 2.49M over about 45 seconds (about 100k per tick). It was not limited to the first tick.
2. Spawned two `/obj/machinery/door/airlock/vault/derelict` doors, set the controller's `siphoned_power` to `1e7` (the maximum), and ran `CALL activate_lock() ON /obj/machinery/computer/vaultcontroller` twice. The first call opened and bolted both doors and set `locked` to 0; the second closed and bolted them with all `density` 1 and `locked` set to 1. The runtime log showed no runtimes.

Not tested: the real ruin (`russian_derelict.dmm`) with its own power source (SMES, solars). Whether that power network gives a surplus to the controller was not checked. The controller was only tried on a station powernet.

## Cause

No defect behind the reported symptom was found. The siphon logic in `code/modules/mapfluff/ruins/spaceruin_code/TheDerelict.dm:68-96` (`process()`, `update_cable()`, `attempt_siphon()`) takes `attached_cable.surplus()` each tick and adds it as load, which works with the powernet's per-tick `avail`/`load` accounting.

One untested possibility for the original report: `attempt_siphon()` adds the surplus as load, so an SMES on the same net sees no excess and stops recharging; if the ruin's SMES starts empty, the controller could appear to get power only briefly. This was an inference from reading the code and was not observed.

Two code defects were seen while reading:

1. `TheDerelict.dm:63-65` declares `/obj/machinery/computer/monitor/examine` inside the vault controller's section; it was probably meant to be `/obj/machinery/computer/vaultcontroller/examine`. As written, the line "It appears to be powered via a cable connector." is added to the examine text of power monitors, and the vault controller gets none. Whether `computer/monitor` already defines its own `examine` was not checked.
2. `lock_vault()` (`TheDerelict.dm:117`) and `unlock_vault()` (`:126`) read `door1.density` and `door2.density` without null checks, although the lines before them use `door1 &&` and `door1?.`. If `find_airlocks()` finds fewer than two matching doors (for example if the ruin's doors were deleted), these raise a runtime.

## Fix

None. A fix for the two defects above was planned but not made, because the report was closed as not reproduced.

## Verification

Only the behaviour on master described under Reproduction was checked. Not checked: the real ruin's power supply, the tgui interface, and examine on the controller or on a power monitor.

## Notes

- The issue is probably closable as no longer reproducible.
- Optional hardening if a maintainer wants it: move the `examine` override to the vault controller, and null-check the doors in `lock_vault()`/`unlock_vault()`.
- `process()` calls `update_cable()` (a `locate` on the turf) every tick; this is only a minor inefficiency.
