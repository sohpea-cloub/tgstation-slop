## Summary

When a ghost orbits something that is held or contained (the nuclear disk in someone's hand, a spectral blade, a player inside a stealth box, closet or mech), the orbiter component's `move_react()` can lose the race against itself under server load: a "stale" run keeps moving orbiters to a turf the target has already left, which ends their orbit. The check meant to cancel a stale run compared `master.loc`, which does not change when a carried object's carrier walks away. The fix compares turfs instead and also adds a missing `return`. #62589 and #84764 are the same bug in different clothes. #69795 is a separate oversight (orbit radius is set once and never updated when the orbited mob changes or grows) and got its own commit.

## The bug

**#88572**: orbiting the nuclear disk as a ghost (during war ops) frequently "drops" the ghost: it is left standing where it was while the disk moves on. The reporter suspected it happens for anything contained by something else, such as a player in a mech. A commenter said the same happens with the spectral blade.

**#62589**: ghosts orbiting a spectral blade occasionally stop orbiting without any input. Several people confirmed it between 2021 and 2024.

**#84764**: spectating someone with the stealth (box) implant, the ghost sometimes gets kicked out of orbit when they go in or out of the box.

**#69795**: ghosts orbiting a xenomorph larva or drone keep their old, very close orbit radius when it grows into a queen, until they re-orbit. A comment says the same applies to a loose singularity. (One reply questioned whether this is a bug.)

## Reproduction

### Orbit drops (#88572, #62589, #84764)

Plain movement did not reproduce the bug. On master `87b93338`, with a human holding `/obj/item/disk/nuclear` and six observers orbiting the disk, repeated `forceMove` calls on the human did not drop anyone, nor did moving the human in and out of an agent box (`/obj/structure/closet/cardboard/agent`) or deploying a real stealth implant and toggling its box action with one observer orbiting. The race needs the orbiter-moving loop to be interrupted by a tick check, so it was forced:

1. Start a round, observe, open the Lua editor.
2. Spawn a human holding the nuclear disk, and spawn five extra observers. With the user's own ghost that makes six, all orbiting the disk (`orbit(disk)`).
3. Occupy the rest of the tick with a busy loop (about 0.15 seconds of `os.clock()` spinning) so that `CHECK_TICK` in `move_react()` sleeps, then move the human twice in a row (`forceMove` to a turf two tiles away, then two further), then burn time again.
4. Count how many ghosts still have `orbiting` set.

Before the fix the count was 1 of 6, and the other ghosts were left standing on the last turf. After the fix the same script left 6 of 6 orbiting, all on the human's final turf. The script is artificial: it creates the load that, in a real round, would come from a busy server, many orbiters (war ops) or many moves in a short time. How often this happens in practice was not measured.

The spectral blade (#62589) and the stealth box (#84764) were not reproduced in the failing state:
- Blade: only tested after the fix (see Verification).
- Stealth implant: with a real implant and the real box action, sync tests never dropped the orbit before the fix, so #84764 is accepted as the same cause by mechanism (a box is a container: the carried target's `loc` stays the box while the box moves), not by observing the report's symptom. A cardboard-box case with the same tick burn was run only on the fixed build.

### Orbit radius (#69795)

1. Spawn an alien larva and a queen, make a ghost follow the larva (`ManualFollow`), and read the ghost's stored orbit radius from the orbiter component (`orbiter_params`): 24.
2. Call `larva.transfer_observers_to(queen)`, which is what happens when a mind moves to a new body.
3. Read the radius again.

By reading the code, the stored value stays 24 on master, because it is only written in `begin_orbit()`. This was not run on the unfixed build; the before-state rests on that reading. After the fix the radius is 48.

## Cause

### Dropped orbit

`code/datums/components/orbiter.dm:178-196`, `move_react()`, is called by a movement tracker whenever the orbited thing, or anything holding it, moves. It moves each orbiter to the master's turf in a loop, calling `CHECK_TICK` between orbiters. If the master moves again while the loop sleeps, the loop is supposed to stop because a newer call will take over:

```dm
var/turf/newturf = get_turf(master)
if(!newturf)
	qdel(src)

var/atom/curloc = master.loc
for(var/atom/movable/movable_orbiter as anything in orbiter_list)
	...
	movable_orbiter.abstract_move(newturf)
	if(CHECK_TICK && master.loc != curloc)
		// We moved again during the checktick, cancel current operation
		break
```

The staleness test compares `master.loc`. For a loose item or a mob walking on a turf, `loc` is the turf and does change. For a held item (loc is the holder), an item in a bag, or a mob in a box, closet or mech, `loc` stays the same while the carrier walks. The old loop therefore does not stop. After its sleep it moves the remaining orbiters to `newturf`, a turf the master has already left. Each orbiter's `orbiter_move_react()` (line 198) then sees `orbiter.loc != get_turf(parent)` and calls `end_orbit()`. Orbiters handled earlier, by the newer call, end up on the right turf, which would explain why only some ghosts are dropped.

A second defect in the same function: `if(!newturf) qdel(src)` had no `return`, so the code continued after queueing the component's deletion.

### Orbit radius

`/mob/dead/observer/proc/ManualFollow()` (`code/modules/mob/dead/observer/observer.dm:632-653`) computes the radius from the target's icon dimensions (lines 636-637) and passes it to `orbit()`. Nothing recomputes it later. When orbiters are handed to a new parent (`InheritComponent` at `orbiter.dm:58` onward, through `transfer_observers_to()` at line 233, used by mind transfers and xeno evolution), and when a singularity changes stage (`/obj/singularity/proc/expand()`), the stored radius and the ghost's transform keep the old value.

## Fix

Two commits.

**"Fix issue 88572: Orbiters are dropped when what they orbit is held or contained and moves repeatedly"** (`code/datums/components/orbiter.dm`). The stale-loop check now compares `get_turf(master)` with the `newturf` this call started from, instead of `master.loc` with a saved `curloc` (which is removed). Added `return` after `qdel(src)` when there is no turf. Orbiters only ever follow the master's turf, so whether the master's turf changed is the question the check needs to answer. This also covers #62589 and #84764.

**"Fix issue 69795: Orbit radius follows the size of the orbited thing"**:
- New `atom/movable/proc/get_orbit_radius(atom/target)`, returning null by default (keep the radius given when the orbit started). `/mob/dead/observer` overrides it with the icon-size formula that was inline in `ManualFollow()`, which now calls it.
- New `refresh_orbit_radii()` on the orbiter component asks every orbiter for its radius and, if there is one that differs, `set_orbit_radius()` updates the stored parameter and rebuilds the orbiter's transform and spin animation without ending the orbit.
- It is called when the component is registered after a transfer (`RegisterWithParent`), after orbiters are inherited from another component (`InheritComponent`), and from `expand()` in `code/modules/power/singularity/singularity.dm`, so singularity stage changes also resize the orbit.

No alternative was tried for the first fix. For the second, a design that restarted the orbit was avoided, so ghosts are not moved or reset when the radius changes.

## Verification

All checked in game on the fixed build, using the Lua editor to set things up:

- Forced-race script (see Reproduction): 6 of 6 ghosts still orbiting at the final turf. The same script with the human inside a cardboard box that was moved twice under the same tick burn: 6 of 6.
- Spectral blade (#62589): a human holding `/obj/item/melee/ghost_sword`, six ghosts orbiting it, eight moves of the human over about 8 seconds (so the blade's own processing ran in between): all 6 were still orbiting at the end, with no related runtimes. This was not run before the fix, and without the tick burn it would not be expected to fail anyway.
- Stealth implant (#84764): real implant, real box action toggled, box moved: orbit kept (before the fix too, see above).
- Radius (#69795): larva to queen via `transfer_observers_to()`: 24 to 48. Singularity: `expand(3)` took the radius from 24 to 72, `expand(1)` back to 24.

Not checked:
- The real-world frequency of the drop, or a real round with war ops and a moving disk carrier. The failing state was only produced by artificially burning tick time.
- The report's exact scenario for #84764 (a client orbiting a stealth-implant user during real play), and the mech case mentioned in #88572.
- A pre-fix run of the radius change, and pre-fix runs of the blade and box cases.
- The two commits were tested together on one working tree, then split into two commits; each was not separately built.
- Radius changes from other causes (an orbited thing changing icon without transferring and without being a singularity) are not handled.
- No full unit-test run.

## Notes

- `get_turf(master) != newturf` still lets one stale loop do a few extra `abstract_move`s to the current turf before it notices; that is harmless since orbiters already on `newturf` are skipped.
- The radius commit adds a small API (`get_orbit_radius`, `refresh_orbit_radii`) that other orbitable types can use; only ghosts and the singularity use it now. A comment on #69795 doubts the behaviour is a bug at all; the fix treats it as one because a freshly started orbit already uses the new size.
- #69795 was grouped with the others only because it is about orbiting; its cause is unrelated to the dropped-orbit race.
