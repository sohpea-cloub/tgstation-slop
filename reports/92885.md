## Summary

A modular computer UI could be left showing the NtOS main menu (`NtosMain`) while the server sent it a program's data. `NtosMain` reads `proposed_login.IDInserted`, which only the main menu's data contains, so tgui showed its fatal-error screen. `update_tablet_open_uis` returned right after opening the UI for a new viewer, so the other viewers' windows were never switched to the program's interface. The fix removes the early return and skips only the just-opened UI in the loop.

## The bug

The reporter saw the engineering cargo interfacing console open a small window with the tgui crash screen: `TypeError: Cannot read properties of undefined (reading 'IDInserted')`, interface `NtosMain`. The report mentions an emagged-looking round, a bitrunning "unregistered mechanical entity" announcement, air alarm errors and blinking APCs, and a commenter guessed the console had been emagged. Two test-merged PRs were also listed.

Those details turned out not to matter: any second viewer of the same computer is enough.

## Reproduction

The engineering console is `/obj/machinery/modular_computer/preset/cargochat/engineering`. It starts with the department orders program (`dept_order`) as its active program and with its processor switched off at round start.

1. In a running round, open the Lua editor as an observer.
2. Find the console in `SSmachines.machines_by_type`, turn its processor on, and background the active program (`active_program` becomes null).
3. Move to the console and open its UI as the observer. A window opened with interface `NtosMain`, title "NtOS Main Menu".
4. Spawn a human with no client and call `open_program` on the computer for that human with the `dept_order` program.
5. Read the observer's window. Before the fix its interface was still `NtosMain`, but it received the department orders data (`no_link`, `id_inside`, `can_override`, `PC_showexitprogram`). A real client rendering `NtosMain` with that data reads `proposed_login.IDInserted` on data that lacks `proposed_login`, which is the reported error.

The trigger was a Lua proc call, and only the interface name and data on the server side were inspected. No client rendered the crash screen. An earlier attempt to open the UI also produced a few runtimes from mistakes in the Lua calls (a bad `get_turf` call, a nonexistent `use_power` var); they are unrelated to the bug.

## Cause

`code/modules/modular_computers/computers/item/computer_ui.dm:13-32`, `update_tablet_open_uis(user)`:

```
if(user)
	var/datum/tgui/active_ui = SStgui.get_open_ui(user, src)
	if(!active_ui)
		... create the UI for the active program, or NtosMain
		return active_ui.open()

for (var/datum/tgui/window as anything in open_uis)
	window.interface = active_program.tgui_id   // or "NtosMain"
	...
```

When a user without an open UI triggers the call, the proc opens a UI for them and returns at line 22. The loop at lines 24-31, which sets `window.interface` and `window.title` for every open window, is skipped. Other viewers keep their old interface (here `NtosMain`) while the program's `ui_interact` and the computer's data updates now send them the program's data.

## Fix

Commit "Fix issue 92885: update other open modular computer UIs when a new viewer opens a program": a `new_ui` variable remembers the UI just opened; the `return` is removed (the UI is still opened); and the loop does `continue` for `new_ui`, since it was already created with the right interface. Every other open window now gets its interface, title and assets updated.

## Verification

Same steps on the fixed build: the observer's window switched to interface `NtosDeptOrder`, title "Department Orders", when the second viewer opened the program. A runtime log check showed only the earlier Lua mistakes.

Not checked: a real client rendering the window, an emagged console, opening a program from the tablet's own UI, and other modular computer types (laptops, tablets, preset consoles other than engineering).

## Notes

- The emag, the bitrunning alert and the APC and air alarm observations in the issue were not involved. Any computer with two viewers where one of them opens a program can hit this.
- This is core modular computer UI code, so a maintainer should check the other callers of `update_tablet_open_uis`.
- The loop calls `active_program.ui_interact` for every open window, as before; the fix changes only which windows are included.
