# #64879: Abductor recall implant and pad retrieval ignore NOTELEPORT areas

| | |
|---|---|
| Issues | [#64879](https://github.com/tgstation/tgstation/issues/64879): verified, fixed |
| Status | Fixed on a branch; design question open (see Notes) |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/64879 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The abductor recall implant ("emergency teleport") and the abductor console's gizmo retrieve both pull a target to the abductor pad with a plain `forceMove`. They never check whether the target stands in a `NOTELEPORT` area, although the console refuses to *send* anyone to such areas. The fix makes `Retrieve()` refuse when the target's area is `NOTELEPORT` (the abductor ship excepted) or the target has `TRAIT_NO_TELEPORT`, and the implant starts its cooldown only when the retrieval happened. Whether the bypass is intended is unsettled: the last maintainer-side comment on the issue leaned towards "feature".

## The bug

An abductor agent carrying a recall implant can activate it inside an area where teleporting is forbidden (the issue names the armory and the AI satellite) and still be pulled back to the pad. The console's own teleport destination picker refuses `NOTELEPORT` areas and AI-monitored areas, so the restriction exists for *sending* people but not for *retrieving* them.

## Reproduction

Reproduced by calling the implant directly from the Lua editor, not through a real abductor team or the abductor ship. The test humans had no mind.

1. On the test server, start a round and observe, then open the Lua editor.
2. Spawn an abductor pad (`/obj/machinery/abductor/pad`) at a hallway tile, and a human on a tile in a different area (here Central Primary Hallway for the pad, Fore Primary Hallway for the human).
3. Spawn a `/obj/item/implant/abductor` inside the human, implant it, and set its `home` to the pad.
4. Set the `NOTELEPORT` bit (4) on the human's area's `area_flags` (Luau has no `|`; `bit32.bor` was used).
5. Call `activate()` on the implant.

Observed on master: the human moved from the hallway tile to the pad's tile and the implant's cooldown timer was set, so the retrieval succeeded from a `NOTELEPORT` area. (A `has_antag_datum` runtime on a null mind appeared during setup; it comes from the mindless test human and is unrelated.)

## Cause

`/obj/machinery/abductor/pad/proc/Warp()` (`code/modules/antagonists/abductor/machinery/pad.dm:15`) moves the target with `forceMove(get_turf(src))` and `Retrieve()` (`pad.dm:29`) calls it with no area or trait check. `Retrieve()` is reached from the recall implant (`code/game/objects/items/implants/implant_abductor.dm:20`) and from the console's `TeleporterRetrieve()` for gizmo-marked targets (`code/modules/antagonists/abductor/machinery/console.dm:173`).

The checks that exist are on the sending side only, in `code/modules/antagonists/abductor/machinery/camera.dm:65` and `:109`:

```dm
if((target_area.area_flags & NOTELEPORT) && !istype(target_area, /area/centcom/abductor_ship))
```

## Fix

One commit, "Fix issue 64879: abductor recall implant and retrieval no longer bypass NOTELEPORT areas":

- `Retrieve()` now looks at the target's area. If it has `NOTELEPORT` and is not `/area/centcom/abductor_ship` (the same exception the camera checks make, since the ship is itself `NOTELEPORT`), or the target has `TRAIT_NO_TELEPORT`, it tells the target "The area's shielding blocks the warp!" and returns `FALSE`. Otherwise it behaves as before and returns `TRUE`.
- The recall implant now returns early if `Retrieve()` fails, so the 60 second cooldown starts only after a successful retrieval and the player can retry elsewhere.

The console's gizmo retrieve goes through the same proc and is blocked in the same way. The check lives in `Retrieve()` rather than in each caller so that both paths share it.

## Verification

In the Lua editor on a rebuilt test server:

- Two humans, each with a recall implant linked to a pad, stood in areas flagged `NOTELEPORT`. After `activate()` both stayed on their tiles and `on_cooldown` was still nil.
- Control: a human in an unflagged area was moved to the pad's tile and the cooldown was set.

Not checked: a real abductor team, the abductor ship exception, the console's gizmo retrieve path, `TRAIT_NO_TELEPORT`, and the message shown to the target. The test used mindless humans and a hand-linked pad.

## Notes

- Intent is unclear. The last comment on the issue says the implant being a "cure-it-all retrieval option" may be a feature. If maintainers want it kept, this fix should not be merged as is.
- The fix also applies to the console's gizmo retrieve, which the issue does not mention.
- The issue also notes the armory and AI satellite behave differently; only the `NOTELEPORT` flag is handled here, not the `ai_monitored` check the console performs when sending.
