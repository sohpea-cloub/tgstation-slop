# #70309: First open of Character Preferences freezes the server

| | |
|---|---|
| Issues | [#70309](https://github.com/tgstation/tgstation/issues/70309): not reproduced (already fixed on master) |
| Status | Not reproduced |
| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary
In 2022 the first opening of the character preferences UI after a fresh asset cache stalled the server for around 10 seconds and left a blank window, which then runtimed if the player had already joined and changed mob. On master, the preference spritesheets are built during initialization as early assets, and the menu refuses to open until that is done. With the cache deleted, the menu opened immediately after boot with no freeze and no runtimes.

## The bug
From the report: on a fresh server, opening Character Preferences lagged the whole server for roughly 10 seconds and the window stayed blank. If the player readied or joined in the meantime, the window later produced runtimes because it tried to reach the client of the old lobby mob. Later opens were fast. A maintainer attributed the first-open cost to building the lazily generated assets when the cache was invalid.

## Reproduction
Not reproduced. On master:

1. The server was started and character setup was opened in the lobby with a warm cache. The PreferencesMenu opened at once.
2. The server was stopped and the spritesheet cache (`data/spritesheets/`, including `smart_cache`) was deleted, to imitate the first-time case. The server was restarted.
3. Right after connecting (about 2 seconds, with the lobby countdown at 116 s), character setup was opened, and the round was started and the lobby mob replaced almost immediately.

Observed: "Initialized Early Assets subsystem within 2.15 seconds" on the cold cache (1.92 s warm); the preference, species and antagonist spritesheets were regenerated during init. The preferences UI opened in the same call with its character preview map, with no freeze. The round started normally, and the round's `runtime.log` held no runtimes beyond startup messages.

## Cause
The behaviour was changed since the report; the current code is:

- The preferences spritesheet (`code/modules/client/preferences/assets.dm:4`), the species spritesheet (`code/modules/client/preferences/middleware/species.dm:11`) and the antagonist spritesheet (`.../middleware/antags.dm:141`) set `early = TRUE`. They are built by the Early Assets subsystem (`code/controllers/subsystem/early_assets.dm`) during initialization.
- `/datum/preferences/ui_interact` (`code/modules/client/preferences.dm:154`) returns without opening if `SSearly_assets.initialized != INITIALIZATION_INNEW_REGULAR`.
- `/datum/preferences/ui_status` returns `UI_CLOSE` when `user.client != parent`, which covers a stale lobby mob whose client has moved on.

## Fix
None needed; no commit.

## Verification
Only the checks listed under Reproduction. Not checked: the runtime screenshot from the issue was not available, and the stale-mob case was only exercised on the fast path, since the UI now opens synchronously and there is no delayed open to race with a mob change. A slow machine or a very large cache rebuild was not tried.

## Notes
- The original stall has moved to initialization (about 2 seconds for Early Assets on the test server).
- Likely closable as fixed upstream.
