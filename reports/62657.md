## Summary

A circuit drone (`/mob/living/circuit_drone`) driven by a brain in the circuit's MMI component never has a key of its own. `key_name()` only looks at the mob's own key, so every attack the drone makes is logged as `*no key*/(drone)`, with nothing to show which player was behind it. The fix adds a signal that `key_name()` sends for keyless mobs; the MMI circuit component answers with its occupant, and the log line gains ` (controlled by KEY/(brain name))`.

## The bug

An admin reading `attack.log` for a drone that a player controlled through a posibrain (or MMI) sees `*no key*/(drone)` as the attacker. The report describes a player who put a posibrain in a circuit drone, wired it to move, and later saw the drone's mulebot fight a nuclear operative. The attack log showed no key for either the drone or the mulebot. The occupying player cannot be identified from the log.

The brain's mob does have a key. It controls the drone remotely through the circuit, so the drone mob stays keyless.

## Reproduction

The attack was triggered by calling `log_combat` directly, not by a player clicking. This is the same call the combat code makes when logging an attack. No real client controlled the brain mob; it was given a fake key.

On master:

1. Using the Lua editor, spawn a positronic brain processor (`/obj/item/brain_processor/positronic`), a `/mob/living/brain` with the key `FakeBrainKey` and the name "Test Posi", and a `/mob/living/circuit_drone`.
2. Create an `/obj/item/integrated_circuit` holding an `/obj/item/circuit_component/mmi`, and attach it to the drone's shell component with `attach_circuit`.
3. Set the component's `brain` variable to the brain processor and call `set_occupant` with the brain mob.
4. Confirm with View Variables or Lua that the component's `occupant` is the keyed brain mob.
5. Call `log_combat(drone, human, "attacked")` against any human and read `attack.log`.

Observed on master:

- `key_name(drone)` returned `*no key*/(drone)`, even though the occupant had a key.
- The attack log line was `ATTACK: *no key*/(drone) (mob_2910) attacked *no key*/(London Kelley)`.

## Cause

`key_name()` (`code/__HELPERS/logging/_logging.dm`, the key/no-key branch at about line 230) builds the name from the mob's own `key`:

```dm
	else
		. += "*no key*"
```

A circuit drone never gets a key. When a brain or AI is set as the occupant of the MMI circuit component, `set_occupant` (`code/modules/wiremod/components/action/mmi.dm:234`) sets `new_occupant.remote_control = src` and the occupant acts through the shell. Nothing in `key_name()` considers a remote controller, so the log has no way to name the player.

## Fix

One commit, "Fix issue 62657: log who controls a circuit drone through an MMI/posibrain". It does four things:

- **New signal.** `COMSIG_MOB_GET_REMOTE_CONTROLLERS` in `signals_mob_main.dm`, sent from `key_name()` with a list argument.
- **`key_name()`.** For a mob that has no key, it sends the signal with an empty list. For each mob that comes back (other than the mob itself), it appends ` (controlled by <key_name(controller)>)`, passing the same `include_link` and `include_name` values.
- **MMI component.** `register_shell` registers a handler for the signal when the shell is a mob. `unregister_shell` removes it. The handler adds the current `occupant` to the list if there is one.
- **Why a signal.** `key_name()` is generic logging code and should not depend on wiremod. A signal keeps that dependency out of core, and any other kind of remote control can answer the same way later. The alternatives (a new variable on every mob, or having `key_name()` read `remote_control` directly) were not tried, and the notes do not say whether they were considered.

Because the handler is on the MMI component and registers for any mob shell, it also covers an AI occupant (the "boris" AI upgrade) and shells other than the drone.

## Verification

After rebuilding, the same setup was run on the test server:

- `attack.log` showed `ATTACK: *no key*/(drone) (controlled by FakeBrainKey[DC]/(Test Posi)) (mob_2924) attacked *no key*/(Sorrel Seidner)`. The `[DC]` shows the fake key had no connected client.
- After calling `remove_occupant()` on the component, a new attack logged as plain `*no key*/(drone)` again.
- No runtimes appeared in the runtime log.

Not checked:

- A real client controlling the brain and attacking by clicking. The brain mob had a fake key and no client, and the log was written by a direct `log_combat` call. The log path is the same, but the click path was not exercised.
- An AI occupant, other shells, and the mulebot case from the report.
- The existing unit tests and any other `key_name()` callers.

## Notes

- `key_name()` is core logging code called from many places. The fix sends one signal per keyless mob per call, creating a list each time. A maintainer may want to weigh that cost, for example against caching or a cheaper check such as testing `remote_control` first.
- The log text lists every controller the signal returns. Only the MMI component answers today, so there is at most one.
- The mulebot part of the report (a drone loaded onto a mulebot controlling it) is tracked as #56586 and was not changed. The issue's comment says the same thing and notes that every drone in the logs showed `*no key*`.
