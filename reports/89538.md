# #89538: Admin proc calls are blocked while an earlier one is sleeping

| | |
|---|---|
| Issues | [#89538](https://github.com/tgstation/tgstation/issues/89538): verified (reproduced in part; see Reproduction) |
| Status | Cause found; no fix committed (needs a maintainer's decision) |
| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Advanced ProcCall marks "an admin proc call is running" with a global (`GLOB.AdminProcCaller`) that stays set for the whole call. If the called proc sleeps, the flag stays set, so the same admin's other admin verbs are refused as a "PERMISSION ELEVATION" and other admins' proc calls are refused. A draft fix that replaced the global with a walk up the call stack worked for the blocking, but it stopped procs started with `INVOKE_ASYNC` inside an admin-called proc from counting as admin proc calls, which weakens the guard. It was not committed.

## The bug

The issue (screenshots only, plus a description) says proc calling is treated as a blocking event when it is not. While one admin's proc call sleeps, calls by others are blocked, and the calling admin could be switched around. The reporter warns this could cause trouble on a live server if an admin breaks something, and says admins should not be locked out of actions because a proc call of theirs is sleeping.

## Reproduction

Only the same-admin part was reproduced in game; only one admin could be connected.

1. On the test server, as an admin, open Advanced ProcCall and call the global proc `/proc/tgui_alert` with a mob reference and some text ("sleeping proc"). The alert stays open, so the call is sleeping.
2. While it is open, open Advanced ProcCall again.
3. Observed in the admin log: `PERMISSION ELEVATION: <admin> attempted to dynamically invoke admin verb '/datum/admin_verb/advanced_proc_call'`. The verb did not run.

The other-admin block (a second admin's call being refused with "Another set of admin called procs are still running. Try again later.") was established only by reading the code.

## Cause

In `code/modules/admin/callproc/callproc.dm`, `WrapAdminProcCall()` (about lines 180 to 215):

- It sets `GLOB.AdminProcCaller = user_identifier` and increments `GLOB.AdminProcCallCount` before running the proc, and clears them only after the proc returns (`callproc.dm:208-214`).
- If another admin's ckey is already in `GLOB.AdminProcCaller`, it refuses with the "Another set of admin called procs are still running" message (`callproc.dm:201`).
- `IsAdminAdvancedProcCall()` returns true when `GLOB.AdminProcCaller` equals the ckey of `usr` (`callproc.dm:230`).

A sleeping proc keeps the global set, so any check of `IsAdminAdvancedProcCall()` by the same admin returns true even for the admin's own, separate verb use. Admin verbs call it (for example `code/controllers/subsystem/admin_verbs.dm:99-100`), hence the PERMISSION ELEVATION message. Other admins are refused by the check above. The flag is global state, not tied to one call's stack.

## Fix

None committed. A draft was written and tested but dropped:

- Remove `GLOB.AdminProcCaller`, `AdminProcCallCount` and the cross-admin block; make `IsAdminAdvancedProcCall()` true when `usr` is the proc call handler, or when walking the `caller` chain finds a frame of `/world/proc/WrapAdminProcCall`. Also change `code/modules/wiremod/components/admin/sdql.dm:23` from `if(GLOB.AdminProcCaller)` to `if(IsAdminAdvancedProcCall())`.
- In tests: a plain admin-called proc saw true; a proc that slept still saw true after sleeping (the stack survives the sleep); a normal Advanced ProcCall opened without being blocked while an `INVOKE_ASYNC` proc was sleeping.
- Problem: a proc started with `INVOKE_ASYNC` inside an admin-called proc saw `IsAdminAdvancedProcCall()` as false, because the stack is cut at the async boundary. The old code returned true in that first synchronous window. So the draft would let async children of admin calls bypass the guard.

The draft author thought the loophole minor, since admins with debug rights can already do worse, but did not want to weaken a privilege-escalation guard without a maintainer's choice of how async children should inherit the flag (for example a per-ckey counter consulted only for such cases).

## Verification

The blocking was reproduced on unmodified master (steps above). For the draft, the stack-walk behaviour above was observed, but the end-to-end check was not finished: leaving a `tgui_alert` open and then calling again or using other verbs without a PERMISSION ELEVATION message, answering the alert and confirming the first call completes, and confirming that protected actions inside an admin call are still refused. The draft was not committed.

## Notes

- Decision needed: how procs started asynchronously from an admin-called proc should be treated.
- The reporter notes that fully decoupling admin actions from a sleeping call would be "deeply annoying"; the draft only addresses the global flag.
