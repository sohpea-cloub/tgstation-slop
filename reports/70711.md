## Summary

Three unrelated HUD bugs were worked together. In #70711 the suit storage slot was the only inventory slot whose "filled" icon was the full-size `template` box, so the Retro style, which draws nothing for `template_small`, showed one big box on that slot alone; the slot now uses `template_small`. In #91409 the resist keybinding set the button's "on" icon after `resist()` returned, which can be long after the key was released, so the button could stay lit; the icon is now set before `resist()` runs. In #72619 the disabled-hand marker is drawn under opaque Operative active-hand art; no fix was made.

## #70711: suit storage slot shows a box in Retro HUD

### The bug
With the Retro HUD style, putting an item in the suit storage slot makes the slot show a large filled box. No other slot (belt, ID, pockets, back) does this, and the reporter considered the box unintended.

### Reproduction
1. Join as a human and set the HUD style to Retro with the Lua editor (`update_ui_style(ui_style2icon('Retro'))` on the mob's `hud_used`), with the inventory expanded.
2. Put a disabler in the suit storage slot.
3. Observed on master: the slot's screen object had icon state `template` and rendered as a full 32px blue box. Belt, ID, pocket and back slots holding items showed no box.

### Cause
`/datum/inventory_slot/human/suit_storage` sets `icon_full = "template"` (`code/_onclick/hud/human.dm`, the datum starts at line 146). Every other slot uses `template_small`. Retro's icon file has no visible art for `template_small` (so filled slots look unboxed there), but it does draw `template`. In Midnight, `template_small` is a slightly smaller box, the same one belt uses.

### Fix
Commit "Fix issue 70711: Use template_small for the suit storage slot's filled icon" changes `icon_full` to `"template_small"`, matching the other slots. It is a one-line change; no new art was needed.

### Verification
After rebuilding, in Retro with the inventory expanded, the screen object list showed suit storage holding the disabler with icon state `template_small`, the same as belt, ID, pockets and back. Not checked: other HUD styles after the change beyond what the icon state implies, and a real client's rendering of the slot.

## #91409: resist button stuck in its active sprite

### The bug
Using the resist hotkey leaves the resist button in the glowing "on" sprite. Clicking the button with the mouse does not.

### Reproduction
This was not reproduced on master. Only the cause was found from the code, and the stuck state was never seen before the fix.

### Cause
`/datum/keybinding/living/resist/down` (`code/datums/keybinding/living.dm`, around line 14) called `owner.resist()` first and set the button's icon state to `<base>_on` afterwards. `resist()` can sleep (the `do_after` for handcuffs, buckles or being on fire). While it sleeps, the key is released and `resist/up` resets the icon to the base state. When `resist()` finally returns, `down` resumes and sets the `_on` state, which nothing resets.

### Fix
Commit "Fix issue 91409: Light the resist button before resist() can sleep" moves the icon assignment above the `owner.resist()` call, so a later `up` always wins.

### Verification
On the fixed build the mob was handcuffed with the Lua editor and the resist key was held for 800 ms. The answer showed the unbuckle/uncuff attempt starting (a one-minute `do_after`) and the button going from `act_resist_on` back to `act_resist`; it did not change back to `_on` during the ongoing `do_after`. The unfixed build was not run, so the original stuck state was not observed; the fix rests on the code analysis above.

## #72619: Operative HUD, disabled-hand marker and gloves on a missing arm

### Glove part: already fixed
The reporter saw gloves on both hands with one arm missing. On master, `code/modules/mob/living/carbon/human/human_update_icons.dm` (about lines 196-206) masks the glove overlay of the missing hand with alpha (the agents attributed this to upstream PR 98038, which was not checked here). With a dismembered arm and gloves worn, the gloves stay equipped but the missing hand's glove is masked. Not a bug on this commit.

### Marker part: reproduced, not fixed
**Reproduction.** Join as a human, dismember the left arm, switch to the Operative style with the Lua editor, and make the missing hand active. The "blocked" marker is only faintly visible in a rendered view of the HUD. The reporter's screenshot shows it fully hidden in the real client, which could not be checked here.

**Cause.** `/atom/movable/screen/inventory/hand/update_overlays` (`code/_onclick/hud/screen_objects/screen_objects.dm:271`) adds the `lhandactive`/`rhandactive` overlay (line 286), then `blocked_overlay` (line 299, `screen_gen.dmi` "blocked", translucent) on the same layer. In the Operative file (`icons/hud/screen_operative.dmi`) the active states are fully opaque hand art, so they cover the marker.

**No fix, options.**
1. Skip the active glyph when `!has_hand_for_held_index`. The marker would be clearly visible, but the dead hand would lose its "active" hint.
2. Give `blocked_overlay` a higher layer (for example `FLOAT_LAYER + 1`) so it draws over the active art. This seemed less invasive but was not tried.

This is a sprite/UI decision that needs a look in a real client.

## Notes

- All three commits touch different files and can be taken independently.
- Retro/Operative are styles whose icon files lack some template states; other slots using `template_small` are why only suit storage stood out.
