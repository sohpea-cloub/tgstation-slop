## Summary

Two of the three issues no longer occur on master: the microwave "ding" on z-level changes (#96145) most likely went away when sound tokens became one-shot for finishing sounds, and the mushroom bowl keeps its sprite after the soup is removed (#80182). The third (#79107) is real: food on a plate or oven tray lives in the plate's `vis_contents` and inherits the plate's color. The branch sets `RESET_COLOR` on plated food. The flag is set correctly in game, but the test render still showed the food tinted, so the fix is unconfirmed.

## #96145: microwaves ding when you change z-level or jump near them

### The bug

The reporter, during a test merge of the "Sound Tokens" PR (#96018), heard a microwave ding repeatedly when going up and down the kitchen stairs on Catwalk (or the right-most research stairs on Tram), as a ghost or a living mob.

### Reproduction

Not reproduced. What was done on the test server (a MetaStation-like multi-z map, as a ghost, round running):

1. Using SDQL2, listed all microwaves with their `soundloop` state; at round start none had a sound token or was playing.
2. Using SDQL2, ran `wzhzhzh()` and then `after_finish_loop()` on the kitchen microwave. The start, middle and end sounds were all heard.
3. Afterwards an SDQL2 `SELECT /datum/sound_token` returned 11 tokens (moisture traps, gravity generator, supermatter, bonfires, firelocks) and none belonged to a microwave.
4. Using the Lua editor, moved the ghost with `forceMove` between z=2 and z=3 next to microwaves (idle ones, and the one that had just finished). No ding was heard; the only sound changes were the supermatter loop being muted and unmuted.

Not tested: actual stair movement on Catwalk or Tram. The test map had no stairs to walk, so z-changes were done with `forceMove`, which goes through the same listener update path.

### Cause (as far as can be told)

The microwave loop is `/datum/looping_sound/microwave` (`code/datums/looping_sounds/machinery_sounds.dm:88`, `use_sound_tokens = TRUE`, with an end sound). On master the end sound is played from `on_stop` in `code/datums/looping_sounds/_looping_sound.dm` through `playsoundtoken(..., delete_when_finished = TRUE)` (`code/game/sound/sound.dm:229`), and the token deletes itself once the sound's duration has passed (`update_sound` in `code/datums/sound_token.dm`). A token that is not deleted would be re-sent to listeners whenever their position or z-level changed, which matches the report. The reporter's round only had the original token PR test-merged; the one-shot token change (PR 96519, 2026-06-16) and later sound-token fixes (96638, 96903) landed after. That ordering is the inference; no run on the old code was done to prove it.

### Fix

None needed on current master.

### Verification

The checks above are the verification. Uncertain: whether any other microwave sound (for example a ding played outside the loop) behaves differently under real stair movement.

## #79107: recolored oven tray recolors food on it

### The bug

When an oven tray (or plate) is recolored, for example by its materials, any food placed on it is drawn in the same color.

### Reproduction

1. Using the Lua editor, spawned `/obj/item/plate/oven_tray`, spawned `/obj/item/food/pie/plain`, called `tray:AddToPlate(pie)`, then set `tray.color = '#ff0000'`.
2. Rendered the tray: the whole tray including the pie was red. Green gave the same result.
3. With View Variables-style inspection of the pie, `appearance_flags` was 769 while plated, with no `RESET_COLOR` (2).

### Cause

`/obj/item/plate/proc/AddToPlate` (`code/modules/food_and_drinks/equipment/plate.dm:64`) shows the food by adding it to the plate's `vis_contents`. Atoms in `vis_contents` inherit the parent's color unless they have `RESET_COLOR`. This confirms the comment on the issue that the food inherits the plate's color.

### Fix

Commit "Fix issue 79107: food on a recolored plate/oven tray no longer inherits its color" changes `plate.dm`:

- `AddToPlate` now sets `item_to_plate.appearance_flags |= RESET_COLOR` before `vis_contents += item_to_plate`.
- `ItemRemovedFromPlate` clears the flag (`&= ~RESET_COLOR`) when the food is taken off.

Alternative noted but not tried: draw the food as an overlay with `RESET_COLOR` instead of through `vis_contents`.

### Verification

Verified: on the test server the pie's `appearance_flags` were 771 while plated and back to 769 after removal. Setting the flag before or after the `vis_contents` add made no difference to the render.

Not verified: after the fix (built twice, flag set after and before the `vis_contents` add) the test client's render still showed the pie red. That renderer is not the real BYOND client and may not carry per-member flags, or the BYOND client may not apply `RESET_COLOR` to `vis_contents` members. So it is unknown whether the fix works in a real client. A check in Dream Seeker is needed; if it fails, the overlay approach above is the next thing to try.

## #80182: mushroom bowl becomes invisible after the soup is gone

### The bug

The 2023 report (from a Skyrat-TG fork, confirmed on an offline server) says a mushroom bowl filled with soup shows the soup sprite, then goes invisible when the soup is finished.

### Reproduction

Not reproduced. Using the Lua editor, spawned `/obj/item/reagent_containers/cup/bowl/mushroom_bowl` and added `/datum/reagent/consumable/nutriment/soup/mushroom`:

- Initially: `ash_flora.dmi` / `mushroom_bowl`.
- Filled with 20u: `soupsalad.dmi` / `mushroomsoup` ("Chantrelle Soup").
- After removing 5u: still `mushroomsoup`.
- After `remove_all`: back to `ash_flora.dmi` / `mushroom_bowl` ("mushroom bowl"). Refilling gave `mushroomsoup` again.
- A render of the emptied bowl showed a visible dark bowl.

`clear_reagents` and `remove_reagent` also left the icon intact. An early attempt hit a runtime from a wrong reagent type path; that was the test's mistake, not the game's.

### Cause (as far as can be told)

On master the bowl (`code/modules/food_and_drinks/food/salad.dm`, subtype at `code/modules/mining/lavaland/ash_flora.dm:729`) uses the `takes_reagent_appearance` component. It stores the original icon at Initialize (`code/datums/components/takes_reagent_appearance.dm:38-39`) and restores it when the reagent style resets (lines 62-63, 138-139). The bowl's `on_cup_reset` restores `fill_icon_thresholds`. The `fullbowl0` and `mushroom_bowl` states exist in `ash_flora.dmi`. The original bug probably came from older code in the fork; this refactor is the likely reason it is gone, but that was not checked against older code.

### Fix

None needed.
