## Summary

In 2021 the reporter price-tagged a custom vendor refill, loaded it into a custom vendor, and then got a runtime when trying to buy it back; a later commenter said that vending the refill made the vendor explode. On current master, a price-tagged refill loads and vends normally, the vendor stays intact, and no runtime is logged. The custom vendor's `vend()` and its product-list code both skip `component_parts`, so the refill installed inside the machine can no longer be picked as a product, which was the cause suggested in the issue thread.

## The bug

As reported: price-tag a custom vendor refill (sales tagger), put it into a custom vendor, and two messages appear at once when clicking the vendor with it. Trying to buy it back out then caused a runtime (the reporter's screenshot, with no full runtime text). A 2024 comment says it no longer runtimes, but that trying to vend the refill "explodes the vendor".

The "two messages" are expected, not part of the bug. `/obj/machinery/vending/proc/item_interaction` (`code/modules/vending/vendor/interaction.dm:107-110`) warns "You should probably unscrew the service panel first!" when the panel is closed, but because it only sets a failure return and does not return, the code falls through to the owner's stocking branch (`:128-140`), which loads the item as a product.

## Reproduction

The explosion could not be reproduced. What was run on master:

1. In the Lua editor, spawn a human with an assistant outfit and an ID with a bank account, and spawn a `/obj/machinery/vending/custom` linked to that ID as its owner.
2. Spawn a `/obj/item/vending_refill/custom`, set `custom_price = 50` on it (what the sales tagger does), and put it in the human's hand.
3. As the possessed human, click the vendor with the refill with the panel closed. The panel warning appeared and the refill was loaded as a product.
4. Open the vending UI. It listed "Custom Vendor restocking unit" as a free item (the human is the owner) with 1 in stock. Vend it through the UI's `vend` action.
5. Observed: the refill came back into the human's hand and the stock dropped to zero. The vendor did not explode and no runtime was logged. The game log had no explosion lines and the runtime log had nothing from `custom.dm` (only noise from the tester's own Lua misuse).
6. Variant, by calling `vend()` directly: set the same `custom_price` of 50 on the refill installed inside the vendor (so it has the same product hash as a second loaded refill), load the second refill, and call `vend` with that hash. It returned `TRUE`, the loaded refill came out, the installed one stayed in the machine, and the vendor was intact.

Not tested: a paying (non-owner) buyer, and swapping parts with an RPED or part replacer.

## Cause

Why the old bug happened (as the issue thread suggested): the vendor's products and its installed refill both live in its `contents`, and a price-tagged refill hashes like a stocked product. If `vend()` selected the installed component refill and moved it out, `/obj/machinery/Exited` (`code/game/machinery/_machinery.dm:1020-1023`) treats a component part leaving as the machine being destroyed:

```dm
if((gone in component_parts) && !QDELETED(src))
	component_parts -= gone
	// It would be unusual for a component_part to be qdel'd ordinarily.
	deconstruct(FALSE)
```

For a custom vendor with a linked account, `on_deconstruction` (`code/modules/vending/custom.dm:23-34`) deletes the refill and runs a self-destruct explosion (`explosion(get_turf(src), devastation_range = -1, light_impact_range = 3)`). That is the explosion path from the 2024 comment.

Why it does not happen now: `collect_records_for_static_data` (`code/modules/vending/custom.dm:231`) and `vend` (`:274`) both iterate `contents - component_parts`, so the installed refill is never offered or picked.

I could not tell which commit introduced the `contents - component_parts` exclusion. The repository checkout used was shallow and the only history hit was an unrelated changelog commit.

## Fix

None. No change was made.

## Verification

The behavior above was observed on the test server on unmodified master (see Reproduction). The real click path was used for loading, and the UI `vend` action for buying.

## Notes

- A related weakness remains but is not this issue: in `vend` (`code/modules/vending/custom.dm:273-277`), `dispensed_item` stays the text key from `params["ref"]` if no product matches (for example a stale ref), and later lines treat it as an item (for example `dispensed_item.custom_price`), so a stale ref would still runtime. It was not exercised.
- The issue could be closed as fixed by the `component_parts` exclusion.
