# #46775: Nuclear operative cyborgs made through the antag panel don't get the Syndicate faction

| | |
|---|---|
| Issues | [#46775](https://github.com/tgstation/tgstation/issues/46775): verified, fixed |
| Status | Fixed on a branch, verified in game on the test server |
| Fix branch | [fix/46775](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/46775) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

A cyborg that is given the nuclear operative antagonist datum (for example by an admin through the antag panel) never receives the `Syndicate` faction, so Syndicate turrets stay hostile to it. The faction is only added by the operative outfit's `post_equip()`, and `equip_op()` returns early for anything that is not a human, so the outfit is never applied to cyborgs. The fix adds the faction for silicons in `equip_op()` and removes it again in a new `on_removal()`, leaving Syndicate-model cyborgs alone because they have the faction innately.

## The bug

An admin turned a player into a cyborg, unlinked it from its AI, scrambled its lawset, and then made it a nuclear operative through the antag panel. The cyborg was then shot at by its own team's turrets. The only cyborgs that are friendly to Syndicate turrets are the Syndicate-model ones (assault, medical, saboteur), which are defined with the faction. Any other cyborg that is made an operative stays in the `silicon` faction only.

## Reproduction

Reproduced on master with admin tools. The faction was given to a cyborg by adding the antag datum directly, not through the antag panel UI; both end up in `add_antag_datum`. This was tested with the cyborg's mind and faction, not with real turrets (see Verification).

1. On the test server, started a round and opened the Lua editor.
2. Spawned a `/mob/living/silicon/robot` and gave it a new `/datum/mind`. The mind was moved into the cyborg with `mind:transfer_to(borg)`.
3. Called `mind:add_antag_datum(/datum/antagonist/nukeop)`.
4. Checked the factions. The `faction` var is protected and cannot be read from Lua, so `borg:has_faction("Syndicate")` and `borg:has_faction("silicon")` were used.

Observed on master: `Syndicate` was false and `silicon` was true for the cyborg after receiving the nuclear operative datum. That means a Syndicate turret would still treat it as hostile.

## Cause

`code/modules/antagonists/nukeop/datums/operative.dm:45-76` (`on_gain()`) calls `equip_op()`, which starts with

```dm
/datum/antagonist/nukeop/proc/equip_op()
	if(!ishuman(owner.current))
		return
```

(`operative.dm:132-134`). Everything that follows, including the outfit, is human-only. The faction is not set anywhere in the antag datum. The outfit does it: `code/modules/antagonists/nukeop/outfits.dm:76`, in `/datum/outfit/syndicate/post_equip()` (line 56), has `nukie.add_faction(ROLE_SYNDICATE)`. Cyborgs never go through an outfit.

The Syndicate-model cyborgs get the faction a different way: `faction = list(ROLE_SYNDICATE)` on `/mob/living/silicon/robot/model/syndicate` (`code/modules/mob/living/silicon/robot/robot_defines.dm:184`). That is why the problem only affects the other cyborg models. This matches the explanation in the issue's comment.

## Fix

One commit, "Fix issue 46775: nuclear operative cyborgs now get the Syndicate faction", changing `code/modules/antagonists/nukeop/datums/operative.dm`:

- `equip_op()` now begins with `if(issilicon(owner.current)) owner.current.add_faction(ROLE_SYNDICATE)` before the existing human-only return. The human path is unchanged.
- A new `/datum/antagonist/nukeop/on_removal()` removes `ROLE_SYNDICATE` from silicons that are not `/mob/living/silicon/robot/model/syndicate`, then calls `..()`. The exception exists because the Syndicate model has the faction innately and removing the datum should not take it away.

Putting the faction into the antag datum, rather than only into the outfit, was chosen because the outfit cannot be applied to a cyborg, and this keeps the faction tied to the antag datum's lifetime. The only alternative looked at was to add the faction to the outfit path, which does not help silicons. `silicon` is not touched.

## Verification

Checked in game after rebuilding with the fix, using the Lua editor and `has_faction("Syndicate")`:

- A standard cyborg: false before, true after `add_antag_datum(/datum/antagonist/nukeop)`, false again after `remove_antag_datum`.
- A `/mob/living/silicon/robot/model/syndicate` cyborg: true before the datum, true after, and still true after removal.
- No runtimes in the round's runtime log after the rebuild.

Not checked:

- Real Syndicate turrets shooting or ignoring the cyborg. Only the faction was inspected.
- The antag panel's own buttons; the datum was added by calling `add_antag_datum` directly.
- Other nuclear operative subtypes (leader, lone operative, reinforcement) on cyborgs. The new code is in the base `nukeop` type, so the subtypes are expected to behave the same but were not individually tested.

## Notes

- Nuclear operative cyborgs keep the `silicon` faction. The Syndicate cyborg model removes it itself (`code/modules/mob/living/silicon/robot/robot_model.dm:936`, in `rebuild_modules()`, so AI turrets are not hostile to them either way) and restores it when the module is removed (line 944). This fix does not change that, since the issue is about the Syndicate faction only. A standard cyborg made an operative will be friendly to Syndicate turrets after this fix, but the AI turrets will probably still treat it as a friend as well.
- The same file (`operative.dm`) is touched by another fix on a different issue from this batch, so the two branches may conflict textually when merged.
