# #94914: Deleting the vent of a vent clog event makes the event runtime forever

| | |
|---|---|

| Status | Fixed on the fix branch; 1 commit |

## Summary

When the vent used by a "Ventilation Clog" event is deleted, the event looks for a replacement vent. The search still counts the vent that is being deleted as valid, so it can pick it again. The event then keeps ticking on a vent that has lost its location and logs a `has no loc, aborting mobspawn` runtime on every spawn tick until the event ends. The fix makes the vent search skip any vent that is already being deleted.

## The bug

A vent clog event spawns small mobs out of a chosen vent. If that vent is deleted (the reporter used build mode's delete while mobs were coming out), the event is supposed to move to another vent and announce "Lifesign readings have moved to a new location". Instead the reporter got a stream of runtimes for the next few minutes:

`Runtime in code/modules/events/vent_clog.dm,149:  has no loc, aborting mobspawn`

The event never spawned another mob and never recovered.

## Reproduction

The report's trigger was build mode's delete. It was reproduced here with the Lua editor deleting the vent (`qdel`), which goes through the same deletion path.

1. Start a "Ventilation Clog: Minor" event: with the Lua editor, call `run_event` on that event's control datum.
2. Weld every other vent shut so the event's own vent is the only valid one. (With other valid vents the failure only happens when the search happens to pick the dying vent again; with only one valid vent it always does.)
3. Delete (`qdel`) the vent the event is using.
4. Result on master: the round's `runtime.log` got `Bar Lounge omni air vent ... has no loc, aborting mobspawn` from `produce_mob()` called by `tick()`, repeating on each spawn tick. The event was still in the running-events list, holding a vent whose `loc` was null.

## Cause

`clog_vent()` registers `vent_move()` on the vent's `COMSIG_QDELETING` (`code/modules/events/vent_clog.dm:198`). `qdel()` sends that signal before it calls `Destroy()`, so when `vent_move()` runs the vent is flagged as being deleted but is otherwise intact: it is still in the machine list, still has a turf, and is still unwelded.

`vent_move()` clears its `vent` reference and calls `get_vent()` (`vent_clog.dm:128-131`). `get_vent()` (`vent_clog.dm:94-106`) builds its candidate list from all vents that are on a station level, unwelded, in a station area and on an unblocked turf (line 99). It does not check whether the vent is being deleted, so the dying vent passes and `pick(vent_list)` can return it. That is certain when it is the only valid vent and 1-in-N otherwise.

The event then calls `clog_vent()` on the dying vent, which spawns one mob there and registers the signals again. After `Destroy()` finishes, the vent's `loc` is null, but the event still holds it as its `vent`. Every later call to `produce_mob()` (`vent_clog.dm:146-149`) finds `get_turf(vent)` is null and ends in:

```dm
var/turf/vent_loc = get_turf(vent)
if (isnull(vent_loc))
	CRASH("[vent] has no loc, aborting mobspawn")
```

This repeats until the event's `end_when`.

## Fix

One commit, **Fix issue 94914: vent clog event no longer re-picks the vent being deleted**. It adds `!QDELETED(vent)` to the condition in `get_vent()`, with a comment explaining that the old vent is still intact when `COMSIG_QDELETING` fires. `QDELETED()` is already true at that point, because the deletion flag is set before the signal is sent.

The fix is in `get_vent()` rather than in `vent_move()` so that any caller of the search is protected. The reporter suggested an early return when no vents remain; that case is already handled by `get_vent()` itself: with an empty candidate list it calls `kill()` and `CRASH("Unable to find suitable vent.")`, which ends the event. With the fix, deleting the last valid vent now reaches that existing path instead of looping on the dying vent.

## Verification

After rebuilding with the fix, on the test server and with the Lua editor:

- Deleting the event's vent while another valid vent existed: the event moved ("Lifesign ... moved to a new location") and no `has no loc` runtime was logged.
- Deleting the last valid vent: one `Unable to find suitable vent.` runtime from `get_vent()` appeared, and the event ended through `kill()`. This is the existing handling for "no vents left". Zero `has no loc` runtimes followed.

Not checked:

- The deletion was done with the Lua editor, not with build mode's delete tool as in the report.
- Other ways the event's vent can disappear (explosions, other deletion sources) were not tried, though they use the same `qdel()` path.
- The major vent clog event and its subtypes were not run separately; they share `get_vent()` and `vent_move()`.

## Notes

- The `Unable to find suitable vent.` runtime when the last valid vent is deleted is existing, deliberate behaviour (a `CRASH` after `kill()`). It is not caused by this change, and was left as is.
- The fix only filters candidates. The old vent still has the event's signals registered while it is being deleted, which is harmless because it is going away.
