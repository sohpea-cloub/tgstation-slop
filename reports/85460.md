# #85460: Dragging a mob onto a staked bonfire does nothing (restraint requirement, no feedback)

| | |

| Issues | [#85460](https://github.com/tgstation/tgstation/issues/85460): verified (reproduced; behaviour is intended, only the missing feedback is a defect) |
| Status | Reproduced, no code change made |
| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Dragging a mob onto a bonfire that has a stake does nothing. This is caused by the stake setting `buckle_requires_restraints`: an unrestrained mob cannot be buckled, and the refusal gives no message of any kind. A handcuffed mob buckles normally. No fix was committed, because the restraint requirement looks intentional and adding a message is a UX decision that affects every atom with that flag.

## The bug

The report says "nothing happens when you drag a mob onto it". On the test server that is exactly what happened with an uncuffed target: no chat message, no progress bar, no buckling. The reporter most likely dragged an unrestrained mob. The stake is meant for restrained victims, but nothing tells the player that.

## Reproduction

1. On the test server, using the Lua editor, spawn a `/obj/structure/bonfire` at (109,144) on z2 and set `can_buckle = TRUE` and `buckle_requires_restraints = TRUE`. These are the two values the "Stake" choice sets when rods are added to a bonfire.
2. Place a player-controlled human next to the bonfire and a second human (the victim) on the other side. The player stepped onto the bonfire's tile so that it was adjacent to the victim.
3. Drag the uncuffed victim onto the bonfire. Observed: no chat message and no progress bar. The victim was not buckled.
4. Handcuff the victim (`set_handcuffed` followed by `update_handcuffed`) and repeat the drag. Observed: "starts buckling Victim to the bonfire!" with a progress bar, and after it finished `Victim.buckled` was the bonfire.

The stake was set up by assigning the variables directly rather than by building it with rods through the construction dialog; the dialog itself was not used.

## Cause

`code/game/objects/structures/bonfire.dm:50-52`: choosing "Stake" sets `can_buckle = TRUE` and `buckle_requires_restraints = TRUE`.

The drag goes through `mouse_drop_receive` (`code/game/objects/buckling.dm:49`) to `mouse_buckle_handling` (`:59`) to `user_buckle_mob` (`:314`) to `is_user_buckle_possible` (`:286`) to `is_buckle_possible` (`:226`). At `:267`:

```dm
if(buckle_requires_restraints && !HAS_TRAIT(target, TRAIT_RESTRAINED))
```

returns `FALSE`. Nothing in that chain sends a message on a `FALSE`, so the player sees nothing.

## Fix

None committed. A possible change would be a `balloon_alert` or `to_chat` such as "[target] must be restrained!" in `user_buckle_mob` when `buckle_requires_restraints` blocks the buckle.

## Verification

Not applicable, since no code was changed. The two outcomes above (uncuffed: nothing; cuffed: buckles) were observed on unmodified master.

## Notes

- The restraint requirement itself looks intentional (a "salem style" stake for restrained victims), so the report may be closed as working as designed, with the missing hint as the only improvement.
- A message in `user_buckle_mob` would apply to every atom using `buckle_requires_restraints`, which is why it was left as a design decision rather than done here.
