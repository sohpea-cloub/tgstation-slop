## Summary

The 2021 report said that when the tram starts moving, a mob you are grabbing is released, fireman carries end, and buckled mobs are unbuckled. None of this happened on current master. Passive and neck grabs, chair buckles and fireman carries all survived full tram trips, including the whole line and the return trip. The cause of the old behaviour was that riders were moved with `forceMove`, which drops grabs and buckles. The current tram code moves riders in a way that never reaches that code, and also marks riders as unable to be unbuckled. There is no fix and no commit. The issue looks closable as fixed upstream.

## The bug

As reported (client 514.1561, September 2021): once the tram begins moving, the player's grab on another mob is broken. Commenters added that fireman carrying breaks too and that everything buckled on the tram is unbuckled (the unbuckling was already tracked in #60375). The report predates the current transport module: the tram then used an older lift implementation, and the code the report was written against is no longer in the tree.

## Reproduction

I tried to reproduce it on master with admin tools on the Tramstation map. The bug did not occur.

1. Started the test server with Tramstation as the map. The tram controller was `SStransport.transports_by_type['icts_tram']` (`tram_1`), one multitile module at 120,117,3 with 144 entries in `transport_contents`.
2. Using the Lua editor, spawned humans on the tram's tiles and set up four situations:
   - Mob A grabbing mob B with a passive grab (`start_pulling`), later raised to a neck grab (`setGrabState(2)`).
   - Mob C buckled to a spawned chair.
   - Mob E fireman-carrying a knocked-down mob D (`buckle_mob(D, TRUE, TRUE, CARRIER_NEEDS_ARM)`).
   - The `never_wounded` trait was added to the spawned humans so that damage would not interfere.
3. Moved the tram in two ways.
   - Directly: `tc:move_transport_horizontally(4)` three times. The module moved from x 120 to 123 and mob A from x 124 to 127, and the grab was intact afterwards. Further direct `travel()` calls then returned nil without moving the module, and I did not find out why; the dispatch trips below are the real test.
   - Through the normal dispatch path: `calculate_route` followed by `SStransport:dispatch_transport` to another platform. The module moved 56 tiles (x 123 to 67), and then back to Central Dock (x 67 to about 124). The second trip was made with mob A controlled by a connected player client.
4. After the first full trip, every relationship was intact: `A.pulling` was B, `B.pulledby` was A, C was still buckled to the chair, D was still buckled to E, and E still had a buckled mob. After the return trip the neck grab was still there (`grab_state` 2) along with the buckle and the carry.
5. The runtime log showed no runtimes from the tram code. The only Lua errors were my own script mistakes.

The one case that was not exercised is a real player actively walking while the tram moves. Nothing in the code suggests it would differ, but it was not run.

## Cause

These are the lines that explain why the old behaviour is gone, at master `87b93338`.

Riders are moved by `group_move` in `code/modules/transport/transport_module.dm:492`. Its header comment says it is "like calling forceMove() on everything in movers" but without `Entered`/`Exited` on the movers. Each rider is moved with a direct location assignment and a manual `Moved()` call (`transport_module.dm:532-543`):

```
mover.loc = (mover_new_loc = get_step(mover, movement_direction))
...
mover.Moved(mover_old_loc, movement_direction, TRUE, null, FALSE)
```

`forceMove` is never called on riders. The code that breaks grabs and buckles on a forced move is `/mob/living/forceMove` (`code/modules/mob/living/living.dm:1967`), which calls `stop_pulling()`, unbuckles the mob unless it has `TRAIT_CANNOT_BE_UNBUCKLED`, and unbuckles anything buckled to it. Riders do not go through it. It is the most likely mechanism of the original report, but I could not confirm that against the pre-rewrite code, which is not in the tested tree.

Riders also get a second protection. When the module registers a mob as a rider, `add_item_on_transport` adds `TRAIT_CANNOT_BE_UNBUCKLED` (`transport_module.dm:145-146`). It is removed again when the mob leaves the tram (`remove_item_from_transport`, `transport_module.dm:129-130`). So even code that did reach `forceMove` would not unbuckle a rider.

A grab can still be broken in one legitimate case: the grabbed mob is off the tram, for example standing in a destination tile. The tram's collision code (about `transport_module.dm:399-460`) damages and throws mobs in those tiles, so a throw (or the grabber's own movement) then ends the grab. That is intended behaviour, not this bug.

## Fix

None. No code was changed and nothing was committed.

## Verification

Only the checks listed under Reproduction were done: passive and neck grabs, a chair buckle and a fireman carry across a full trip of 56 tiles and back, the return trip with a player-controlled grabber, and a clean runtime log. Not checked: a real player walking around while the tram is moving, other trams or maps, the Birdshot and other tram variants, or the elevator and other transport types.

## Notes

- The issue is from 2021 and was written against the older lift code. The transport (ICTS) rewrite replaced the movement code, so closing it as fixed upstream looks justified. I did not identify the specific upstream PR.
- The related report #60375 (everything buckled on the tram gets unbuckled) is covered by the same finding. I did not test it separately, but the chair-buckle check above is the same situation.
- For follow-up testing by script, dispatch with `calculate_route` and `dispatch_transport`; direct `travel()` calls stopped moving the module after the first few tiles here.
