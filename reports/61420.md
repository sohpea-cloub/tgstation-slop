## Summary

All three issues are about the anomaly refinery (`/obj/machinery/research/anomaly_refinery`, `code/modules/research/anomaly/anomaly_refinery.dm`), the machine that compresses raw anomaly cores with a transfer-valve bomb. The 2021 report of "failure and success" being shown together (#61420) no longer happens, because the machine was rewritten since. Two real bugs remain in the same file. Under SSobj lag the refinery gave up after a fixed amount of world time and ejected a live, opened bomb that then went off outside (#61502). And when a raw core of an exhausted type was inserted, the machine said it could not be compressed but kept the core inside (#70248). Both are fixed in separate commits.

## The bugs

**#61420** (2021): a player used the compressor on a core and saw both an error line and a success line in chat, and got a refined core. A commenter explained, for the code of the time, that the test result was only reported after a fixed delay and that the machine was probably being re-run on an already refined core. The reporter suggested giving the success line earlier and adding a note that the core will be dispensed after a few seconds.

**#61502** (2021): during a meteor event (a heavy-lag situation) a player put a good bomb in a core compressor with a core loaded. After a while the machine said it failed, ejected the transfer valve with the valve open, and the bomb went off outside the machine. A commenter suspected the object-processing subsystem had been slowed down until it took longer than the compressor's timeout to handle the bomb; another suggested basing the timeout on times fired instead of a fixed delay.

**#70248** (2022): after the per-type hard limit of cores had been reached, the machine says "Unfortunately, due to diminishing supplies of condensed anomalous matter ... no longer of a sufficient quality level to be compressed into a working core." The reporter claimed that inserting the core and imploding it anyway still produced a core, and proposed removing the limit. Discussion in the issue concluded the hard cap is a deliberate balance decision (and that only the message/behaviour consistency is at stake); the maintainers' stated position was that removing the limit would not be accepted.

## Reproduction

All steps were done on the test server with admin tools (the Lua editor). The machine and bomb were assembled by script and the machine's `start_test()` was called directly, as the UI button does; the player-facing UI itself was not clicked.

### #61420 (not reproduced)

1. Open the Lua editor, spawn an anomaly refinery, and set up a transfer valve holding two tanks: one tank with about 507 mol of oxygen at 43 K, the other with about 1.45 mol of plasma at 15000 K (the recipe from #70248), the oxygen tank as the target.
2. Put a raw bluespace core and the bomb into the machine and call `start_test()`.

Observed: one chat line only, from the machine, at the end of the test: "Success. Resultant detonation has theoretical range of 18. Required radius was 4. Core production complete." A bluespace core and the valve were ejected.

Other cases tried:

- A scripted pair of internal blasts (14, then 3 against a required radius of 9): only "Success ... range of 14. Required radius was 9", no failure line, one core.
- A dud bomb (not enough to explode): only "Transfer valve resulted in negligible explosive power. Items ejected."

The success text is only said when the test ends (the timeout), which can be up to about 10 seconds after the bang. This is the only part of the original complaint that still applies and was treated as a design choice and left unchanged.

### #61502 (reproduced)

1. Set up the same bomb, core and machine as above (create the objects in one Lua run, call `start_test()` in the next; doing both in a single run failed with "Missing equipment").
2. Call `start_test()`, then immediately set `SSobj.can_fire = 0` and re-enable it with a timer 13 seconds later (SSobj runs the tanks, so this stands in for lag).

Observed on master: at about 10 seconds the machine said "Transfer valve resulted in negligible explosive power. Items ejected." and then the ejected bomb went off, causing a large explosion that wrecked the surrounding room (several thousand map changes were recorded).

### #70248 (reproduced, but as a different bug)

1. Spawn an anomaly refinery, raise the bluespace core count to its hard limit (3) using `SSresearch.increment_existing_anomaly_cores` until `is_core_available` is no longer true.
2. Give a human a raw bluespace core in hand and call the refinery's `item_interaction(human, core, null)`.

Observed on master: the call returned the blocking result and the machine said the "diminishing supplies" line, so the "keeps imploding" claim in the issue is out of date. However the core was no longer in the human's hand; it was in the machine's contents, with `inserted_core` unset, so it could not be taken back out through the machine's own eject.

## Cause

**#61420**: the machine was rewritten since 2021. A compression test result is stored in `test_status` by `check_test()` (`anomaly_refinery.dm:213-241`) and said once by `end_test()` (`:196`), called from `timeout_test()` (`:246`). Later internal blasts cannot overwrite a success: after a success `inserted_core` is the finished core, whose `anomaly_type` makes `get_required_radius()` (`:62`) return null, and after a failure `if(test_status)` (`:237`) cancels later explosions. So there is no combination that says both lines.

**#61502**: the test is armed in `start_test()` (`:173`) and in `error_test()` (`:188`, the emag path) with

```dm
timeout_timer = addtimer(CALLBACK(src, PROC_REF(timeout_test)), COMPRESSION_TEST_TIME, ...)
```

where `COMPRESSION_TEST_TIME` is `(SSOBJ_DT SECONDS * 5)` (`:4`), i.e. 10 seconds of world time. The tanks of the bomb only rupture when SSobj runs the tank's processing (the pressure tolerance check). When SSobj falls more than 10 seconds behind, `timeout_test()` fires first, finds no result in `test_status`, sets "negligible explosive power", and `end_test()` ejects the valve, which is now open. The bomb then goes off outside the machine when SSobj catches up.

**#70248**: in `item_interaction()` (`:76`), the raw-core branch (`:81-97`) did the following in order:

```dm
if(!user.transferItemToLoc(tool, src)) ...      // :86  core moves into the machine
var/obj/item/raw_anomaly_core/raw_core = tool
if(!get_required_radius(raw_core.anomaly_type)) // :91  exhausted type?
	say("Unfortunately, ...")
	return ITEM_INTERACT_BLOCKING                 // :93  returns, but the core is already inside
inserted_core = raw_core                          // :95
```

The exhausted-type check sat after the transfer, so the core was already inside the machine's contents when the check refused it, and `inserted_core` was never set. `eject_core()` only handles `inserted_core`, so the core cannot be taken out by the machine's controls.

## Fix

Two commits on the fix branch, both only in `code/modules/research/anomaly/anomaly_refinery.dm`.

**"Fix issue 70248: anomaly refinery no longer swallows a raw core of an exhausted type"**: the `get_required_radius()` check, with its message, now runs before `transferItemToLoc()`. A refused core stays in the player's hand. The hard cap itself is not touched (see Notes).

**"Fix issue 61502: anomaly refinery waits for SSobj before giving up on a bomb"**: the timeout is counted in SSobj runs, as suggested in the issue's comments.

- `COMPRESSION_TEST_TIME` is replaced by `COMPRESSION_TEST_FIRES` (5).
- A new variable `timeout_at_fire` and helper `start_timeout()` record `SSobj.times_fired + COMPRESSION_TEST_FIRES` and arm the same 10-second timer; `start_test()` and `error_test()` both use it.
- `timeout_test()` now checks `SSobj.times_fired < timeout_at_fire` first and, if SSobj has not run enough times, re-arms itself for another SSobj interval instead of ending the test.

In normal operation the behaviour is as before (about 10 seconds); under lag the machine waits for the tanks to be processed so the bomb goes off inside the machine and gets reported.

## Verification

- **#61502**: in a rebuilt test server, the same lag script (bomb as above, SSobj paused for 13 seconds) was run after the fix. The bomb went off once SSobj resumed; the machine said "Success. Resultant detonation has theoretical range of 18. Required radius was 4. Core production complete." and ejected a core. A dud bomb still ended with the "negligible explosive power" message after about 10 seconds. No runtimes involving the refinery were logged.
- **#70248**: after the fix, the same steps left the raw bluespace core in the human's hand and the machine's contents held only its own board, with the "diminishing supplies" line still said once.
- **#61420**: no change, nothing to verify beyond the observations above.

Not checked: the emagged-machine path through `error_test()`, which uses the new `start_timeout()` helper but was not run; the real UI buttons and a real meteor-event lag (only an SSobj pause); the other core types and their hard limits (only bluespace was exercised); and whether a long SSobj stall leaves the machine active for an unusually long time (see Notes).

## Notes

- A reported upstream PR (#71244) to remove the hard cap exists, was closed without merging, and is at odds with the design stated in the issue thread. It was not used here and the cap was left in place.
- With the new timeout, if SSobj never runs again the test never times out and the machine stays active. Under a total SSobj stall the bomb could not explode either, so this seems the right way round, but a maintainer may prefer an upper bound in world time as well. Timing could also stretch by an SSobj interval or two in normal play if the timer happens to expire a run early; I did not measure this beyond the dud-bomb case ending after about 10 seconds.
- #61420's leftover request, speaking the success line earlier or noting that the core arrives after a delay, is not addressed. Delaying the report to the end of the test is how the machine works now, and the original reason (a bomb that never goes off must not lock the machine) is still valid.
- The "18 tiles" in #70248 is an old figure; on master the radius scale is `MIN_RADIUS_REQUIRED` 4 to `MAX_RADIUS_REQUIRED` 20 (`anomaly_refinery.dm:1-2`) and the per-type limit is defined in `code/__DEFINES/research/anomalies.dm` (for bluespace, 3).
