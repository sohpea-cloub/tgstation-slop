## Summary

An uplink implant bought from an existing uplink was built with that uplink's `uplink_handler`, so the implant and the old uplink drew from one telecrystal (TC) pool. The fix gives the implant a handler of its own (same uplink flag, 0 TC). Two related reports in the same code were fixed with separate commits: an uplink implant deleted itself when implanted a second time (#70852), and a new traitor could adopt an uplink they were only carrying (#77505).

## The bug

### #95147: shared TC pool

A traitor who bought "Uplink Implant" from their PDA uplink got an implant whose TC count was the same number as the PDA's. TC added to or spent from one showed up in the other, so TC could be moved between the two. The item description says the implant "has no telecrystals and must be charged by the use of physical telecrystals", which the behaviour contradicted.

### #70852: implant deletes itself on re-implanting

An uplink implant removed from a body (for example by surgery, into an implant case) and implanted again was destroyed.

### #77505: traitor adopts a carried uplink

A player who was carrying another traitor's unlocked PDA uplink and later became a traitor got a broken uplink: no objectives tabs, and the traitor panel said their uplink was the other player's PDA, with that PDA's code.

## Reproduction

All three were reproduced on an unmodified build through the Lua editor, as an observer. Procs were called directly on spawned mobs and items. The in-game player actions (buying through the TGUI, the surgery, the antagonist roll with the implant preference) were not performed.

### #95147

1. Spawned a human with a PDA uplink component (handler `U`, 20 TC, `U.owner` set to the human's mind).
2. Called `U.purchase_item(human, /datum/uplink_item/implants/uplink, pda)`.
3. `U.telecrystals` went from 20 to 16 (the implant costs 4 TC).
4. The implanter in the resulting box held an implant whose `uplink_handler` was the same datum as `U`.
5. After implanting it, adding TC to the implant's handler also changed the PDA's pool: there was a single handler.

### #70852

1. Implanted `/obj/item/implant/uplink/starting` into a human `h2`.
2. Called `removed(h2)` on it, then `implant(h3)` on another human.
3. The implant was deleted: the next access reported a destroyed object.
4. Calling `implant()` on an implant while another uplink implant was already in the same body also produced "Attempted to add a new component ... to a qdeleting parent" (a `CRASH` at `code/datums/components/_component.dm:318`).

The surgery removal path was not used; `removed()` was called directly.

### #77505

1. Spawned a human `B` with no uplink, carrying another mind's unlocked PDA uplink (handler owner set to that other mind).
2. Called `add_antag_datum` for the traitor antagonist on `B`.
3. The traitor datum's `uplink_ref` resolved to the carried PDA's uplink (`parent` was the other player's PDA), and `traitor.uplink_handler` was the other player's handler. That handler therefore received `B`'s objectives and callbacks. This matches the report's "uplink cunningly disguised as the HoP's PDA".

## Cause

### #95147

`code/modules/uplink/uplink_items/implant.dm:54-57`:

```dm
/datum/uplink_item/implants/uplink/spawn_item(spawn_path, mob/user, datum/uplink_handler/uplink_handler, atom/movable/source)
	var/obj/item/storage/box/syndie_kit/uplink_box = ..()
	uplink_box.name = "Uplink Implant Box"
	new /obj/item/implanter/uplink(uplink_box, uplink_handler)
```

The buyer's handler was passed to the implanter, which passed it to the implant (`code/game/objects/items/implants/implantuplink.dm:14-18, 50-51`). On implanting, the implant gave it to the uplink component as `uplink_handler_override` (`implantuplink.dm:23`; the override is applied at `code/datums/components/uplink.dm:79-85`), so the component used the buyer's handler instead of creating its own. The handler holds the TC, so the pool was shared.

There was a second problem: the implant's `uplink_flag` was never passed to the component, so a handler-less implant always fell back to the component's default flag.

### #70852

`implant()` in `implantuplink.dm` (line 23) called `AddComponent(/datum/component/uplink, ...)` on every implantation. The uplink component is `COMPONENT_DUPE_UNIQUE` (`code/datums/components/uplink.dm:11`), so when the implant already had one, the new duplicate was deleted (`_component.dm:346`). Deleting a component sends `COMSIG_COMPONENT_REMOVING` to its parent (`_component.dm:82`). The implant listens for that signal (`implantuplink.dm:19`), and `on_component_removing()` (`implantuplink.dm:37-44`) ends in `qdel(src)`. The deletion of the duplicate therefore deleted the implant itself. Separately, `implant()` carried on after the parent `implant()` had already deleted the implant (when the body already had an uplink implant).

### #77505

Two places:

- `get_uplink_location()` (`code/datums/mind/antag.dm:91`) picked the first PDA, radio or pen in the mob's contents, including one that already held another uplink.
- `datum/antagonist/traitor/on_gain()` (`code/modules/antagonists/traitor/datum_traitor.dm:55-58`) called `owner.give_uplink(...)`, ignored its return value, then used `owner.find_syndicate_uplink()`, which returns the first uplink component found on the mob. When the mob carried someone else's uplink, that was the one used.

## Fix

Three commits on `fix/95147`:

- **Fix issue 95147: purchased uplink implants no longer share the buyer's telecrystals.** The purchase now passes only the buyer's `uplink_flag` to the implanter (`new /obj/item/implanter/uplink(uplink_box, uplink_handler.uplink_flag)`). `/obj/item/implant/uplink` and `/obj/item/implanter/uplink` take a flag instead of a handler in `Initialize`, the `uplink_handler` var is removed, and the implant passes `uplink_flag` to the component. The component therefore creates a handler of its own, with the same uplink kind as the buyer's and 0 TC. The owner, role and species fields are now always set on it.
- **Fix issue 70852: uplink implant deleted itself when implanted again.** `implant()` returns early if the parent call deleted the implant, and reuses an existing uplink component instead of adding a second one. The implant keeps its uplink and TC across removal and re-implantation. `assigned_role` and `assigned_species` use null-safe lookups.
- **Fix issue 77505: traitors adopted an uplink they were only carrying.** `get_uplink_location()` skips items that already have an uplink component. `on_gain()` keeps the item that `give_uplink()` returns and uses its uplink component, falling back to `find_syndicate_uplink()` only if there is none.

## Verification

After rebuilding and restarting the test server, the same Lua scripts were run:

- **#95147:** TC after the purchase was 16. The implant's handler was not the PDA's handler; its TC was 0; its flag was the same as the PDA's; its owner was set. After adding 7 TC to the implant, the PDA had 16 and the implant 7.
- **#70852:** re-implanting returned 1 and the implant stayed alive, with `imp_in` set to the new body and its component being the syndicate uplink.
- **#77505:** the traitor's uplink was no longer the carried PDA's; it was in a pen. The traitor's handler was not the carried PDA's handler, had objectives, and its owner was the new traitor. The carried PDA's handler was untouched (owner not the new traitor, no objectives).
- No new runtimes appeared in the server log beyond the usual ones.

Not checked: purchases by nuclear operators or clown operators (the flag is copied from the buyer's handler; untested), the real surgery removal path, the TGUI, and the real player flow for #77505 (implant preference at antagonist roll).

## Notes

- **Behaviour change.** A purchased secondary uplink implant now has only the market tab, with no primary/secondary objectives tab, because it has its own handler. This is what the description ("no telecrystals") implies. The description text was already correct and was not changed.
- **#77505 is only partly fixed.** In the test, the new traitor's uplink ended up in a pen that sat inside the carried PDA, not in an implant as in the report. `get_uplink_location()` still counts the contents of a carried foreign PDA as the player's inventory, so a pen taken from it can still host the uplink (cosmetic). The implant path itself is covered by the #95147/#70852 checks and by `on_gain()` now using the uplink it was given.
- **Re-implanting keeps TC.** With the #70852 fix a re-implanted uplink implant keeps its existing handler and TC; only the owner, role and species are updated to the new host.
- The issue text of #70852 was filed in 2022 and #77505 in 2023; both reproduced on current master.
