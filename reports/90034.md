## Summary

A big manipulator's drop point only recognised `/obj/item/storage` as "storage", so smart fridges (slime extract, plant and food storage) never received items. With "drop on floor" enabled the item was dumped beside the fridge, and with it disabled the manipulator picked the item up and then hung holding it (#90034). A second commit makes the manipulator re-check power every cycle and stop dropping items on turfs they cannot rest on, such as full-tile windows (#86446). The other four reports (#86481, #92510, #93979, #95837) describe code that has since been refactored; they were checked by reading the current code only and were not tested in game.

## The bug

### #90034
Players building a manipulator between a slime extract source and a Smart Slime Extract Storage found that the manipulator never put extracts inside. With both drop priorities (storage and floor) enabled the item landed on top of or beside the fridge; with only storage enabled the manipulator failed to drop at all.

### #86446
Two reports in one: (a) a manipulator facing a window or airlock placed items on the same tile as the window or airlock; (b) a manipulator that was powered on kept working after the area lost power.

### #86481, #92510, #93979, #95837
- #86481: an item on an active conveyor moved diagonally when caught by a manipulator.
- #92510: switching a manipulator from Drop to Use and turning it off mid-operation made the held item vanish.
- #93979: a manipulator could teleport a target (a borg in the report) to itself if the target had been dropped manually and the manipulator later retriggered.
- #95837: attack messages for a monkey worker attacking with a toolbox named the victim as the subject ("voodoo" wording) although the attack log was correct.

## Reproduction

### #90034
Done on the test server with the Lua editor to build the setup (create a big manipulator, anchor it, add a pickup task on one side and a drop task on the other, turn it on, spawn items):

1. Place a manipulator with its pickup tile to the east and its drop tile to the west. Put a Smart Slime Extract Storage on the drop tile.
2. Spawn grey slime extracts on the pickup tile and start the manipulator, with default drop priorities (storage, then floor).
3. Observed on master: the three extracts ended on the floor of the drop tile next to the fridge, not in it.

The "storage only" hang described in the issue was found from the code (see Cause) and was not separately captured as a before-fix run.

### #86446
No clean before-fix reproduction was made. The new behaviour was checked after the fix (see Verification). The defect itself was identified in the code.

### Other members
Not reproduced in game. See Notes for what the code reading showed.

## Cause

### #90034
- `code/game/machinery/big_manipulator/manipulator_tasks.dm:143` (`find_type_priority`): the drop task's "in storage" priority matched items by `istype(thing, prio.atom_typepath)` with `/obj/item/storage`. Smart fridges are machinery with their own load logic, so they never matched.
- `code/game/machinery/big_manipulator/big_manipulator_interactions.dm:102` (`try_drop_thing`): when `find_type_priority` returned null it returned FALSE without calling `finish_manipulation()`. With floor drops off the manipulator therefore stayed stuck holding the item.

### #86446
- Power: `try_kickstart` (`big_manipulator_interactions.dm:38`, `use_energy` at line 42) paid for power once when the manipulator started. `step_tasks()` (line 19) never checked power again.
- Windows: the drop task's floor priority (`atom_typepath == /turf`, `manipulator_tasks.dm:182`) accepted any turf, including dense turfs and turfs holding a dense object such as a full-tile window.

## Fix

Two commits.

**"Fix issue 90034: big manipulators can't put items in storage"**
- Adds `can_store_in` and `find_drop_endpoint` to the drop task. For each active priority, in order, a container on the drop tile counts if it has a storage datum that would accept the item, or if it is a smart fridge that is working, has room and accepts the item; the floor counts for the floor priority.
- `can_accept` uses the endpoint: a drop point with nowhere to put the item refuses it, so the manipulator no longer picks the item up. Overflow rules, which concern piles on the floor, only apply when the endpoint is the turf.
- `try_drop_thing` inserts into the found endpoint (storage datum, `smartfridge.load()` with a UI and icon update, or the turf). If the endpoint has vanished or filled up since pickup, it calls `drop_held_atom()` instead of hanging. A missing held item finishes the manipulation.

**"Fix issue 86446: big manipulators ignore lost power and drop items under windows"**
- `step_tasks()` now checks `powered()` and `use_energy()` every cycle. On failure it shows a "not enough power!" balloon, drops the held item and stops the manipulator. The one-time check in `try_kickstart` was removed.
- Adds `turf_accepts_items()` to the drop task and uses it for the floor priority. It rejects dense turfs and turfs with a dense object that is not `ON_BORDER` and does not have `LETPASSTHROW` (full-tile windows, closed airlocks), so tables and similar surfaces still work.

The first fix was kept in the drop task rather than extending the type list, because a smart fridge has no storage datum and needs its own insertion path.

## Verification

- #90034: three grey slime extracts were picked up from the east tile and dropped into a Smart Slime Extract Storage on the west tile (the first extract's location was the fridge). With floor priority off and the fridge deleted, new extracts stayed on the pickup tile and the manipulator idled without holding anything.
- #86446 windows: with a full-tile window on the drop tile and default priorities, a pen spawned on the pickup tile stayed there and the manipulator waited without holding anything. After the window was deleted the pen was picked up and appeared on the drop tile.
- #86446 power: with the area's equipment power turned off, a new pen on the pickup tile produced the "not enough power!" balloon from the manipulator; afterwards the manipulator was off, held nothing, and the pen was still on the pickup tile. Power was then restored.
- Not checked: backpacks (storage datum path) as the drop target; the 90034 build was a slightly earlier one containing the same code as its commit, while the 86446 checks were on a build with both commits; any of #86481, #92510, #93979, #95837 in game.

## Notes

Code-only findings for the unfixed issues (current master at the tested commit):
- #86481: the manipulator now only `forceMove()`s items (no stepping or throwing), and conveyors move items with move loops, so the described diagonal drift is unlikely. Untested.
- #92510: "modes" no longer exist; tasks have fixed types (pickup, drop, throw, use, interact), and turning the manipulator off calls `drop_held_atom()`, which moves the item to the manipulator's turf. Looks obsolete. Untested.
- #93979: `try_dropoff` and `try_use_thing` guard on `held.loc != manipulator`, `drop_held_atom` clears `held_object`, and pickup scans only its own turf, so the reported teleport looks fixed. Untested.
- #95837: the spectator message in `carbon_defense.dm` (around `send_item_attack_message`) uses "[user] ..." only if `user in viewers(src, null)`, otherwise it names the victim as subject. The monkey worker is now moved adjacent to its target before attacking (`big_manipulator_interactions.dm`, around lines 241-245), which should put it in `viewers()`. If the target tile is a closed-turf neighbour the worker is not moved and the message could still be wrong. Untested.
