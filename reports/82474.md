## Summary

The issue says that a photo taken as an AI does not load when it is sent to someone by PDA message. The photo, its asset registration and the sent message were all correct on the server, so the failure was not reproduced; whether an image actually displays could not be observed with the tools used. Reading the code found a possible defect that is not specific to AI photos: the messenger does not send a chat's photo assets to a user who opens that chat, and the sender's own copy is sent before their view switches to the chat. A commit on the fix branch addresses both. It compiled with no errors, but it was not tested for the symptom, so it should be treated as a hypothesis.

## The bug

As reported: an AI takes a picture with its camera, sends it to another person through the PDA messenger, and the image appears broken. The reporter only tried PDA and suspected other routes were affected as well.

## Reproduction

Not reproduced. What was done on the test server, using admin tools:

1. An AI was made from a human with the Lua editor. The AI took two pictures (the AI photo camera listed "Image 0" and "Image 1", taken by AI) and a PDA was imprinted for a recipient (a janitor).
2. The AI's PDA messenger was opened. "Image 1" was selected with the messenger's photo picker, and a message "look at this" was sent to the recipient.
3. Observed on the sender side: the messenger's `selected_photo_path` became `asset.bff2b055049c6dbaedc70ee3e8270604.png`, and the sent message in the chat data had the same `photo_path`. The runtime log had no errors.
4. With Lua, both stored pictures had a valid 96x96 icon as `picture_image`. The asset cache held both `ntos_messenger[...]_temp_image.png` and `ntos_picture_0.png`, with the same hash as the path above and a `.png` extension.

So the server side looked right. What was not observed: whether a recipient's client receives and displays the image bytes, since the images in the PDA window could not be rendered. A recipient with a real client, opening the chat in the PDA, was not tested. Re-selecting a second photo (which would re-register the same temporary asset name) was not tested either.

## Cause

Not confirmed. The photo flow in `code/modules/modular_computers/file_system/programs/messenger/messenger_program.dm`:

- For a silicon, `PDA_siliconSelectPhoto` registers the picture under a fixed temporary name, `TEMP_IMAGE_PATH(REF(src))` (the `#define` is at line 2; the register call is around lines 326-332), and `send_message` re-registers the same resource under a permanent `ntos_picture_N.png` key around lines 484-489.
- `get_picture_assets()` (line 113) lists the assets the UI needs: stored image files, the photos of the chat currently being viewed (`viewing_messages_of`), and the selected image.
- `update_pictures_for_all()` (line 132) sends that list to everyone with the program's UI open.
- On the recipient side, assets are sent when the UI is opened (`ui_interact`) and when a message is received to those who have it open.

The candidate defect has two parts:

1. The `PDA_viewMessages` action changes `viewing_messages_of` to another chat, but does not send that chat's photo assets. A photo that arrived while another screen was open might never reach the viewer.
2. In `send_message` (around lines 552-560 on master), `update_pictures_for_all()` runs before `viewing_messages_of` is switched to the chat just written to. `get_picture_assets()` then lists the photos of the previously viewed chat, and the new photo is not in the list.

If correct, both affect every PDA photo, not only AI photos. Whether they explain what the reporter saw is not established.

## Fix

One commit, "Fix issue 82474: send chat photo assets when opening a PDA chat and after the sender's chat switch", in `messenger_program.dm` (+6/-4):

- In `PDA_viewMessages`, after `selected_image = null`, the new chat's assets are sent with `SSassets.transport.send_assets(usr, get_picture_assets())`.
- In `send_message`, the `update_pictures_for_all()` call for a new photo was moved after the chat switch, so the sent photo is part of the chat then being viewed.

The commit does not touch `Topic()`/`ui_act` handlers other than that one action.

## Verification

None for the fix. The change compiled with 0 errors. It was not run in game against the symptom: no recipient client opened a chat, and no image display was observed before or after.

## Notes

- The issue cannot be closed on this evidence. The next step is a check with a real client as the recipient and the sender, with a photo from an AI and a photo from a normal PDA camera.
- If photos from normal cameras display fine, the cause is AI specific and the candidate fix is probably not the answer. A possible second suspect is the temporary name: choosing a second photo registers the same `ntos_messenger[...]_temp_image.png` name with a different hash, which was expected to trigger a "same name as another asset" `stack_trace` in the asset transport. It was not tested, and the recipient's message points to the permanent key anyway.
- The triage note suggested the problem might be asset delivery; the candidate fix follows that guess.
