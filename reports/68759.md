## Summary

`SSatoms` kept the list of atoms created by a map-template load in one global variable, `created_atoms`, shared by every `InitializeAtoms` call. If a holodeck program load yielded part-way through and another map load (a shuttle, for example) finished first, that other call merged and cleared the shared list, so the holodeck lost the rest of its atoms. Those atoms never got the hologram flag and were never deleted when the program changed. The fix gives each call its own list. It changes core atom initialization, and the failure itself was not reproduced before the fix, so it rests on code reading plus a no-regression run.

## The bug

Per the reports: while the holodeck was loading a program, another map load (the reporter used a large shuttle bought via the shuttle manipulator; the other report mentions a shuttle launching) caused lag. Some objects of the holodeck program then lacked the holographic flag and were not deleted when the program changed, or when moved out of the holodeck. #81064 describes the "Microwave Paradise" objects staying through different programs and a shutdown, at a time when the shuttle also launched. A comment on #68759 points at the logged runtime "We started maploading while we were already maploading" and notes that the template code isn't designed for simultaneous loads.

## Reproduction

The failure before the fix was not reproduced. The triggering order (another template load finishing while the holodeck's load is yielded) could not be obtained: in the one attempt, the second load stalled instead of finishing.

What was done instead (on the fixed code, see Verification) used the Lua editor to start two overlapping loads. A real reproduction would be to change a holodeck program while a shuttle is called or docks (or any other template load runs) during a lag spike.

An earlier attempt on the unfixed code loaded the thunderdome template and then the `holodeck_lounge` program. The holodeck ended up wedged (`spawning_simulation` 1, no `spawned` atoms, `Master.map_loading` 1). A later run with the fix, loading the thunderdome at the station hallway, wedged the same way, so that wedge is not this bug. It appeared to be the other load never finishing (thunderdome loaded over occupied station turfs, with atmos and turf runtimes). It was not investigated further and may be an artifact of starting the loads from Lua.

## Cause

Read from the code on master:

- `SSatoms.created_atoms` was a single global list (`code/controllers/subsystem/atoms.dm:24`).
- `CreateAtoms` created it with `LAZYINITLIST(created_atoms)` whenever it was given an `atoms_to_return` list (`atoms.dm:91`).
- `InitAtom` (`code/game/atom/atoms_initializing_EXPENSIVE.dm:52-53`) added each template movable's `get_all_contents()` to that global list.
- At the end of `InitializeAtoms`, the global was merged into that call's `atoms_to_return` and set to null (`atoms.dm:74-76`).

A holodeck load passes `template.created_atoms` as the list to fill (`map_template.dm:92`) and yields inside `CreateAtoms` (tick checks). If another `InitializeAtoms` call (a shuttle, ruin, lazy template, another template) reaches its end in that window, it merges and nulls the shared list. The holodeck's later atoms are then never added to its list, or are added to a list that was already merged elsewhere. The holodeck takes `spawned = template.created_atoms` (`code/modules/holodeck/computer.dm:234`), so:

- the missing atoms never get `HOLOGRAM_1` (`finalize_spawned`, `computer.dm:281`);
- `clear_projection()` (`computer.dm:257-259`) derezzes only atoms in `spawned`, so the missing ones are never removed.

The reverse is also possible: while both loads run, the other load's atoms can land in the holodeck's list. The match with the logged "started maploading while already maploading" runtime is consistent but was not observed.

## Fix

One commit, "Fix issue 68759: keep map template created atoms per InitializeAtoms call":

- `code/controllers/subsystem/atoms.dm`: removed the `created_atoms` variable, the `LAZYINITLIST` in `CreateAtoms`, and the merge-and-null block at the end of `InitializeAtoms`. `CreateAtoms` now calls `InitAtom(A, TRUE, mapload_arg, atoms_to_return)`.
- `code/game/atom/atoms_initializing_EXPENSIVE.dm`: `InitAtom` gained a fourth parameter, `template_created_atoms`, and appends to it directly instead of to the global.

Every call therefore fills only its own caller's list. Callers were audited by grep. The only one passing a list is `code/modules/mapping/map_template.dm:92` (`returns_created_atoms ? created_atoms : null`), used by the holodeck templates and the heretic tier-three code. The other `InitializeAtoms` callers pass none (the initial init, `mapping.dm`, lazy templates, shuttles, `repair.dm`). `InitAtom` callers outside `CreateAtoms` use only the first three arguments. No other user of `SSatoms.created_atoms` existed.

One behavior change: the caller's list is now filled as atoms initialize, not all at once at the end of `InitializeAtoms`. The `map_template.dm:92` callers read it after `InitializeAtoms` returns, so they still see everything.

## Verification

With the fix built (0 errors), on the test server, as an admin observer, using the Lua editor: the thunderdome template was loaded through an async callback and, while it was still loading, the holodeck program `holodeck_microwave` was loaded through another.

- The holodeck finished with `spawning_simulation` 0 and 249 `spawned` atoms, all with `HOLOGRAM_1` set. `SSatoms.active_initializations` was 1 at that moment, so the other load was still initializing: the overlap did happen.
- 53 of the 249 had x below 100; these were machine contents (x=0, inside microwaves), not thunderdome atoms.
- After switching to the offline program, an SDQL2 query found 11 microwaves on that z-level, none in the holodeck area and none flagged: the derez cleaned up.

Not checked: the failing behavior on unfixed code in the intended order; a shuttle load overlapping a holodeck load; the heretic tier-three user of the list; the unit tests; and #81064 itself.

## Notes

- #81064 (Microwave Paradise objects persisting after card battle/microwave use, with a shuttle launching) fits the same cause, but this was by code reading only and not run. An alternative not ruled out: objects moved out of the holodeck by players are not derezzed (see the special-location handling in `computer.dm`). The shuttle detail favors the shared list.
- Separate observation, not changed: `map_template.created_atoms` is not cleared between loads of the same template, so `spawned` can accumulate stale entries. This looked harmless for derez and was not tested.
- This is a core `SSatoms` change; review it as such.
