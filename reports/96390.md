# #96390: Goliath eating a bait worm runtimes in `sig_remove_from_blackboard` (list index out of bounds)

## Summary

The reported runtime came from `/datum/ai_controller/proc/sig_remove_from_blackboard` indexing a plain (non-associative) blackboard list by a numeric element, which is out of bounds whenever the number is larger than the list. Merged PR #96477 ("Fixes bug where sig_remove_from_blackboard would try to numerically index a regular list", 2026-06-14) added a guard for exactly this, and master `87b93338` contains it. The runtime could not be triggered on master, and no code was changed. The issue can probably be closed as fixed by #96477.

## The bug

The issue (opened 2026-06-08) reports a recurring, apparently random runtime near goliaths:

```
Runtime in code/datums/ai/_ai_controller.dm, line 938: list index out of bounds
proc name: sig remove from blackboard (/datum/ai_controller/proc/sig_remove_from_blackboard)
src: /datum/ai_controller/basic_controller/goliath
```

The call stack shows the goliath's AI behaviour (`interact_with_target/eat_food`) making the goliath unarmed-attack a bait worm, `basic_eating` consuming it and `qdel`ing it, and the worm's `parent_qdeleting` signal then reaching the controller's `sig_remove_from_blackboard`, where the runtime was raised. Players would see nothing; it was a log-only runtime. The reporter first suspected the tendril rework because it happened next to a tendril.

## Reproduction

Not reproduced on master. What was tried, using the Lua editor and the runtime log on the test server, after a normal round start:

1. Spawned a goliath and a bait worm (`/obj/item/food/bait/worm`) a few tiles away. The goliath did not walk to the worm on its own during the observation window. It pushed against a nearby window instead, so the natural "AI finds food and eats it" path was not exercised.
2. Put a worm on the goliath's own tile and set the goliath's `BB_TARGET_FOOD` blackboard key to it, then made the goliath call `UnarmedAttack` on the worm. This goes through the same `basic_eating` path as in the issue's stack. Result: "The goliath chews the worm.", the worm was deleted, and the runtime log had no new entry.
3. Set `BB_TARGET_FOOD` to a worm and `qdel`ed the worm. The key was cleared from the blackboard, with no runtime.
4. To exercise the old failure mode directly, put a plain list containing the worm and several numbers (`{worm, 7, "x", 9, 3, 1}`) into the goliath's blackboard under a test key and called `sig_remove_from_blackboard(worm)` on the controller. Result: no runtime. On the pre-fix code, a numeric element such as 7 or 9 in this 6-element list would have been used as an index into it and gone out of bounds. This step was a direct proc call, not a player action. It was not checked whether the worm was removed from that list in this step. The question was only whether the proc runtimed.

The only entries in the runtime log came from the admin's own Lua mistakes (reading `current_behaviors` and `can_idle`, which are not variables of the controller on master, and calling `set_blackboard_key` with a list).

Note that the stack in the issue comes from the older AI behaviour implementation (`ai_behavior/interact_with_target/eat_food`). Master now uses behaviour trees (the goliath uses `move_to_and_eat`), so the surrounding calls are different, but `sig_remove_from_blackboard` is the same proc.

## Cause

`sig_remove_from_blackboard` is registered on `COMSIG_QDELETING` for every datum added to a controller's blackboard (`code/datums/ai/_ai_controller.dm:744`, in the `TRACK_AI_DATUM_TARGET` macro). When a tracked datum is deleted, the proc walks the blackboard and any nested lists breadth-first (`_ai_controller.dm:1007`). For each element it looks for the deleted datum, and it also tries to treat the list as associative by reading `next_to_clear[inner_value]`.

In a non-associative list that contains numbers, `next_to_clear[7]` is a positional index, not a key lookup. When the number is greater than the list length, DM raises "list index out of bounds". Goliath blackboards hold lists like this, which is why the runtime showed up when a goliath ate (and so deleted) a tracked worm. The same failure was possible for any tracked datum on any AI controller whose blackboard held a plain list with numbers in it.

On master the associative lookup is now preceded by a guard:

```dm
//if this is the case stop here. This means the list isn't associative (because an assoc list couldnt have a key for a number!)
if(isnum(inner_value))
	continue

var/associated_value = next_to_clear[inner_value]
```

(`_ai_controller.dm:1025-1028`). An associative list cannot have a numeric key in this context, so a numeric element means the list is plain and must not be indexed.

## Fix

None committed. The fix is the upstream change in PR #96477, which adds the `isnum(inner_value)` guard above. The tested tree already contains it.

## Verification

Checked on master `87b93338` (steps 2-4 under Reproduction): the goliath eating a worm, deleting a worm that was a food target, and the direct call with numbers in a plain blackboard list all completed with no runtime.

Not checked:
- A goliath autonomously finding, walking to and eating a worm through the behaviour tree. The goliath in the test did not go for the worm by itself, so the eat was triggered by setting the target key and calling `UnarmedAttack`.
- The pre-fix code was not run for comparison. That the old code fails on such a list follows from reading the code and from the PR title, not from a run.
- Other blackboard shapes (nested lists of lists, associative lists with datum values) were not tested beyond a short trial that did not report a runtime.

## Notes

- Issue #96390 is still open on GitHub even though PR #96477 merged on 2026-06-14. It looks safe to close.
- The pre-existing loop in `sig_remove_from_blackboard` removes elements from a list (`next_to_clear -= inner_value`) while iterating over it. That was not investigated further here and nothing in the testing pointed to a problem with it.
