# #42567: Scopes and binoculars offset the view of an advanced camera console

| | |
|---|---|
| Issues | [#42567](https://github.com/tgstation/tgstation/issues/42567) (verified, fixed on the fix branch); [#34262](https://github.com/tgstation/tgstation/issues/34262) (verified, same cause, fixed by the same commit) |
| Status | Reproduced on master, fixed, fix checked in game |
| Fix branch | [fix/42567](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/42567) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The scope component (`/datum/component/scope`, used by binoculars, the sniper rifle and several other items) zooms by animating `client.pixel_x`/`pixel_y`. That offset moves whatever the client's eye is, so a player looking through an advanced camera console gets the camera view shifted by up to roughly 38 x 30 tiles. The component never checked that the eye was the player's own mob, and nothing stopped a zoom that was already running when the eye changed. The fix refuses to start a zoom while `client.eye` is not the user, and stops an active zoom as soon as the eye changes. Both reports are the same defect.

## The bug

### #42567 (binoculars)

A player who is looking through an advanced camera console and then wields binoculars sees the camera view move away from the camera, as if the binoculars were being used from the camera's tile. Moving the mouse over the scope overlay moves the view further. The reporter also noted that this ignores camera range, and that other scopes might do the same.

A later comment on the issue says binoculars do not zoom out (change the view size) on advanced consoles but do offset the view, and that static is respected. Basic camera consoles are not affected.

### #34262 (sniper rifle)

Same effect with the sniper rifle's scope. The old report talked about a larger view range. A 2023 comment points out that the view-size part was already fixed by tgstation PR #51208 and that only the offset of the view remained. The test agrees: the client view stayed `19x15` throughout, and only the pixel offset moved the camera view.

### What is really happening

`client.pixel_x`/`pixel_y` shift the client's whole viewport relative to its eye. For a normal scope the eye is the player's own mob, so the player sees further in the chosen direction. When the eye is a remote camera eye, the same offset moves the camera's view instead. The cap on the offset is `range_modifier` times half the view size, so with `range_modifier = 4` and a 19x15 view that is up to 1216 px by 960 px (38 x 30 tiles).

## Reproduction

On master `87b93338`, in a running round, as a player character:

1. Using the Lua editor (admin tools), spawn an `/obj/machinery/computer/camera_advanced` one tile from the character and put an `/obj/item/binoculars` in a hand.
2. Click the console with an empty hand. The client's eye becomes the console's camera eye (the view moves to the camera, the eye mob is named "Camera Eye (<player name>)").
3. Swap to the binoculars and use them in hand (this wields them). The message "You hold the binoculars up to your eyes" appears and the scope overlay is shown.
4. Move the mouse over the scope overlay. In one run the mouse was at about px 500, py 470 of the overlay.
5. Read the client with the Lua editor (or View Variables). Observed: `client.eye` is still the Camera Eye, `client.pixel_x = 862`, `client.pixel_y = 960`, `TRAIT_USER_SCOPED` is set, and the player's own mob had not moved. The camera view was therefore displaced by about 27 tiles horizontally and 30 vertically from the camera.
6. For the sniper rifle (#34262), swap the binoculars for `/obj/item/gun/ballistic/rifle/sniper_rifle`, and while still in the camera view right-click a turf to scope in. With the mouse near px 10, py 470, the eye was still the Camera Eye, `client.pixel_x = -1216`, `client.pixel_y = 960` (the cap), and the client view size read `19x15`.

This was reproduced through the player actions (clicking the console, wielding, right-clicking), with admin tools used for spawning and for reading the values. The offset depends on where the mouse is over the overlay, so the exact numbers vary with the mouse position.

Basic camera consoles were not tested in game. They draw the cameras into a separate tgui map rather than setting `client.eye`, so the component's offset would not apply to them.

## Cause

In `code/datums/components/scope.dm` on master:

- `process()` (`:59`) runs every tick while zoomed and applies the offset at `:68`:

  ```dm
  animate(user_client, world.tick_lag, pixel_x = tracker.given_x, pixel_y = tracker.given_y)
  ```

  The offset moves whatever `client.eye` is.
- `zoom()` (`:161`) checks only that the user has a client and is not already scoped. It does not look at what the client's eye is, so a zoom can start while the player is looking through a remote eye.
- Nothing stops an already running zoom when the eye changes. Opening an advanced console assigns the eye through `mob/eye/camera/remote/assign_user`, which calls `new_user.reset_perspective(src)` (`code/modules/mob/eye/camera/remote.dm:69`). The scope's stop conditions are only losing the client, swapping hands, deletion, entering a non-turf location, being stunned (worn items) and moving the item (`on_move`).
- `stop_zooming()` (`:206`) resets the offset to 0 when the zoom ends.

The same component is used by binoculars (`code/game/objects/items/binoculars.dm:16`, `range_modifier = 4`, wield), the sniper and other rifles in `code/modules/projectiles/guns/ballistic/rifle.dm` and `automatic.dm`, the beam rifle, the heretic hunter rifle, a CTF rifle and the moth goggles, so all of them are affected.

## Fix

One commit, "Fix issue 42567: scopes and binoculars no longer offset a remote (camera) view", changes `code/datums/components/scope.dm`:

- In `zoom()`, after the "already zoomed" check, if `user.client.eye != user` it shows the balloon alert "can't zoom right now!" and returns, so no scope overlay, sound, trait or processing is started.
- In `process()`, after the client check, if `user_client.eye != user_mob` it calls `stop_zooming(user_mob)` and returns. This catches a zoom that was started before the player opened a console, and any other later change of eye, within a tick.

Approach: the check is on `client.eye`, not on the console, so it covers every way of ending up with a remote eye (other remote-control consoles, direct `set_eye` calls) instead of listing them. The stop check is polled in `process()` because the component already processes while zoomed; a signal-based approach would need to hook every place that sets the eye. The commit message also names #34262.

## Verification

Checked on a rebuilt test server after the fix, with the same spawned items:

- Binoculars with no camera console: zoom still works. The eye is the player's own mob, `client.pixel_x = 730`, `pixel_y = 960`.
- Zoomed with binoculars first, then opened the advanced console (via the Lua editor calling the console's `attack_hand`): the eye became the Camera Eye, the zoom stopped (stop sound played), `client.pixel_x/y` went back to 0 and `TRAIT_USER_SCOPED` was cleared.
- Wielding the binoculars while in the camera view: the item is wielded, but "can't zoom right now!" is shown and no scope overlay appears.
- Sniper rifle, right-click in the camera view: "can't zoom right now!", `pixel_x/y` 0, trait not set.
- After using "End Camera View" on the console, the sniper rifle zooms normally again (`pixel_x = -1216`, `pixel_y = 960`).
- The round's `runtime.log` contained no new runtimes from this; the only entry was an empty "uncaught runtime error:" line from the Lua editor that was already known and unrelated.

Not checked: the other scope items (hunter rifle, beam rifle, CTF rifle, automatic rifle, moth goggles) were not tried in a camera view; they share the component but were not tested individually. Remote eyes other than the advanced camera console (for example other remote-control consoles) were not tested. Ending a zoom in other ways while in a camera view was only checked for the cases above.

## Notes

- Zoom is now refused whenever `client.eye != user`, not only for camera consoles. That also applies in other situations where the eye is not the mob, for example inside a locker or vehicle. The component already stopped zooming when the user entered a non-turf location (`on_enter_new_loc`), so this appears consistent with existing intent, but a maintainer may want to confirm no item relies on scoping through a different eye.
- The stop is checked once per `SSprojectiles` tick, not on a signal, so a very short window exists between the eye changing and the zoom stopping.
- The scope's target turf (`given_turf`) is computed relative to the owner mob, not the eye. No test checked what a scoped shot does in a camera view; the fix removes the case.
- An upstream search found no existing PR for either issue (searches for 42567, 34262 and "scope camera console"). The view-size part of #34262 was handled by tgstation PR #51208.
- #34262 could be closed as a duplicate of #42567 once the fix is merged; a comment on it from 2023 shows the maintainers had considered that.
