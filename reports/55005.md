# #55005: Unwelded disposal bin/outlet/chute constructs become invisible, but stay dense, under floor tiles

| | |
|---|---|
| Issues | [#55005](https://github.com/tgstation/tgstation/issues/55005): verified, fixed. [#79168](https://github.com/tgstation/tgstation/issues/79168): duplicate of #55005 (same cause), fixed by the same commit |
| Status | Fixed and checked in game for the bin and outlet constructs (see Verification for what was not checked) |
| Fix branch | [fix/55005](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/55005) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

An unwelded disposal bin, outlet or delivery chute is an `/obj/structure/disposalconstruct`. Every disposal construct gets the `undertile` element, which hides the object when a floor tile is placed over its turf. A construct that is anchored and is a bin, outlet or chute also becomes dense. So a wrenched-down, unwelded bin or outlet disappears under a new floor tile while still blocking movement, and #79168 is the same thing seen from the visual side. The fix adds the `undertile` element only to constructs of actual disposal pipes, so bin, outlet and chute constructs stay visible above the floor tile.

## The bug

#55005 (reported as "can block movement while under floor tiles"): following the build sequence trunk, wrench, weld, then bin/outlet/chute, wrench, floor tile, the unwelded machine construct is hidden by the tile but is still solid, so players cannot walk onto the tile and cannot see why.

#79168 (reported as "Disposals chute visibility"): an unwelded disposal chute placed on plating becomes invisible when a floor tile is placed over it. The expected behaviour is that it stays above the tile. The screenshot in that issue is not reproduced here; the description matches the behaviour found below.

Both issues carry maintainer comments calling this a "feature" (the hidden construct was used for a mime labyrinth) and saying the disposals code is hard to reason about. This write-up does not take a position on that; it records what the code does and the change that was tested.

## Reproduction

The bug was reproduced by setting up the state directly with the Lua editor and a procedure call that places a turf on top, rather than by building it with a wrench, welder and floor tile item. The relevant step, laying a floor tile over the turf, goes through `/turf/proc/levelupdate()` (`code/game/turfs/turf.dm:517`), which sends `COMSIG_OBJ_HIDE` to every initialized object on the turf, and the Lua call exercised that same path.

1. Start the test server on master `87b93338`, start the round, and open the Lua editor as an admin observer.
2. On a plating turf, spawn a disposal trunk (`/obj/structure/disposalpipe/trunk`).
3. On the same turf, spawn a `/obj/structure/disposalconstruct` whose `pipe_type` is the disposal bin (`/obj/machinery/disposal/bin`), and call `set_anchored(1)` on it. This is what wrenching it down does.
4. Check the construct: `density` is 1 (set because it is a bin and anchored, see Cause).
5. Call `place_on_top(/turf/open/floor/iron)` on the turf, which is what placing a floor tile does, and read the construct's variables again.

Observed on master, for the bin construct:

| | density | invisibility | alpha | anchored |
|---|---|---|---|---|
| before the tile | 1 | (not recorded) | (not recorded) | 1 |
| after the tile | 1 | 100 | 128 | 1 |

The construct was hidden (invisibility 100, alpha 128, which are the values the `undertile` element applies) but still dense. The outlet construct was not run on unfixed master; it goes through the same code path.

## Cause

`/obj/structure/disposalconstruct/Initialize()` adds the element unconditionally, whatever the construct is going to be:

```dm
// code/modules/recycling/disposal/construction.dm:36-37
AddElement(/datum/element/simple_rotation, post_rotation_proccall = PROC_REF(post_rotation))
AddElement(/datum/element/undertile, TRAIT_T_RAY_VISIBLE)
```

The element (`code/datums/elements/undertile.dm:38`) listens for `COMSIG_OBJ_HIDE`. When the turf's `underfloor_accessibility` is below `UNDERFLOOR_VISIBLE` (a floor tile is on it), it sets maximum invisibility and alpha 128 on the object (lines 41-43 and 69-71), moves it to the floor plane, and adds `TRAIT_UNDERFLOOR`.

That is right for pipe segments, which are never dense. But bins, outlets and chutes are also disposal constructs, and `set_anchored()` makes them solid:

```dm
// code/modules/recycling/disposal/construction.dm:16-20
/obj/structure/disposalconstruct/set_anchored(anchorvalue)
	. = ..()
	if(isnull(.))
		return
	set_density(anchorvalue ? initial(pipe_type.density) : FALSE)
```

`initial(pipe_type.density)` is TRUE for the bin (`bin.dm:11`), the outlet (`outlet.dm:21`) and the delivery chute (`bin.dm:707`). So an anchored machine construct is dense, and the element still hides it when a tile goes on top. The element is only gone once welding replaces the construct with the real machine (`welder_act`, line 163), which does not carry the element. This matches the issue author's note that "the undertile element is added, and density is set when anchored, but the element isn't removed until it's welded".

Anchoring a bin or outlet construct requires a trunk on the turf and the floor tile to be off (`wrench_act`, lines 113-141), so the sequence in the issue is: build while the plating is exposed, then put the tile back.

## Fix

One commit, "Fix issue 55005: unwelded disposal bin/outlet constructs no longer hide under floor tiles". It changes `Initialize()` in `code/modules/recycling/disposal/construction.dm` so the element is added only for pipe constructs:

```dm
// Only pipes go under the floor; bins, outlets and chutes are dense once anchored and must stay visible above tiles
if(is_pipe())
	AddElement(/datum/element/undertile, TRAIT_T_RAY_VISIBLE)
```

`is_pipe()` (line 170) is `ispath(pipe_type, /obj/structure/disposalpipe)`, the existing test the file already uses to separate pipe constructs from bin/outlet/chute constructs (for example in `update_icon()` and `can_place()`). The change is 3 added lines and 1 removed line. `pipe_type` is already set before the element is added, so the check sees the right type.

This removes the contradiction at its source: a construct that can become solid is no longer hideable. The inputs do not record any other approach being tried; see Notes for the alternative of keeping the element.

## Verification

After rebuilding the test server with the fix, the same Lua setup was run for four constructs, each on a fresh plating turf with a trunk, anchored, and then covered with an iron floor via `place_on_top`:

| Construct | density | invisibility | alpha |
|---|---|---|---|
| disposal bin | 1 | 0 | 255 |
| disposal outlet | 1 | 0 | 255 |
| disposal pipe segment | 0 | 100 | 128 |

(A third entry in that run was intended to be the delivery chute, but it used a type name that does not exist in this tree, `/obj/machinery/disposal/deliveryChute`; the real type is `/obj/machinery/disposal/delivery_chute`. That entry came out as a plain pipe-segment construct and is not evidence about the chute, so it is left out of the table.)

So bin and outlet constructs now stay visible and solid above the tile, and pipe segment constructs still hide under it as before. The run produced no new runtimes in the round's runtime log other than the usual startup lines.

Not checked:

- The delivery chute construct was not tested directly. It is expected to behave like the bin and outlet because the fix keys on `is_pipe()`, but that was not observed.
- The sequence was not performed with real tools: no wrench, welder, crowbar or floor tile item was used, and no one walked into the tile. The anchoring and tile placement were done by calling procs, so the player-facing interactions (including `welder_act`, which the fix does not touch) are untested.
- Welding the visible construct into a finished machine afterwards was not run.
- The #79168 screenshot scenario (placing a floor tile item on top of an unwelded chute on plating) was not repeated as such; it shares the code path above.
- The T-ray scanner interaction for bin/outlet constructs was not checked. These constructs no longer have `TRAIT_T_RAY_VISIBLE` applied by the element, since they are never hidden now.

## Notes

- The behaviour change is deliberate: unwelded bin, outlet and chute constructs can no longer be hidden under tiles. If maintainers want to keep the "hidden obstacle" trick from the comments, the alternative is to keep the element and make the construct non-dense while hidden; that would need a decision on whether a hidden, invisible object should be allowed to be solid at all.
- Related, not changed: when a finished disposal machine is deconstructed, `on_deconstruction()` (`bin.dm:351-352`) calls `set_anchored(FALSE)` and then `set_density(TRUE)`, so the resulting construct is dense even though it is unanchored. Before the fix such a construct could also be hidden under a tile. After the fix it is visible. Whether the explicit `set_density(TRUE)` there is intended was not investigated.
- No upstream pull request addressing this was found in the inputs.
