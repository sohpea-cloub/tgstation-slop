## Summary

The three issues are unrelated bugs in vehicles, handled as one unit. #58971: a mob buckled to an ATV is not protected from slipping on ice or lube, because `/turf/open/handle_slip` only spares buckled mobs for lubes that lack `GALOSHES_DONT_HELP`, and ice, permafrost and lube all carry that flag. The fix adds a `TRAIT_NO_SLIP_RIDERS` trait, gives it to ATVs and checks it in `handle_slip`. #93733: the golf cart is drawn as a wrongly scaled, overflowing composite in the "Buckled" alert, so the fix stops using the cart's icon in that alert. #95757: shuttle rotation rotated the speedwagon's centering pixel offsets, which left its sprite far from its tile, so the fix keeps the offsets fixed.

## #58971: ATVs don't properly go over all terrain

### The bug

The issue reporter described getting on an ATV that stood on a slippery tile (the Snowdin gateway was the example) and being slipped, and driving an ATV onto a slippery tile and being thrown off. ATVs are meant to be all-terrain, so the rider is expected to ignore the floor. In practice the rider slips, is knocked down and is unbuckled from the ATV.

### Reproduction

1. On the test server, open the Lua editor and spawn an ATV and a human on the same floor tile, then buckle the human to the ATV.
2. On the adjacent tile, call `MakeSlippery` with the permafrost wet type (`TURF_WET_PERMAFROST`, the type ice turfs use) and long durations.
3. Move the ATV onto that tile with `Move`.
4. Observed on master: the human ended up unbuckled and paralyzed, and slid one tile.

The reproduction moved the vehicle onto the tile with `Move` from the Lua editor. A player driving the ATV was not tested on master. Mounting an ATV that already stands on a slippery tile was not run before the fix, but the code path is the same (see Cause).

### Cause

`/turf/open/handle_slip` (`code/game/turfs/open/_open.dm:582-585`) decides what happens to a buckled mob:

```dm
if(slipper.buckled)
	if(!(lube & GALOSHES_DONT_HELP)) //can't slip while buckled unless it's lube.
		return FALSE
	buckled_obj = slipper.buckled
```

A buckled mob is spared only when the lube lacks `GALOSHES_DONT_HELP`. Ice turfs call `MakeSlippery(TURF_WET_PERMAFROST, ...)` (`code/game/turfs/open/ice.dm:30`), and the wet floor component gives ice, permafrost and superlube `GALOSHES_DONT_HELP` (`code/datums/components/wet_floor.dm:94-104`). So every slippery floor an ATV is likely to meet gets past the check, the rider slips, and `buckled_obj.unbuckle_mob(slipper)` (line 616-617) removes them from the vehicle.

Mounting is affected the same way: `buckle_mob` sets `M.buckled` (`code/game/objects/buckling.dm:108`) before it calls `M.Move(loc)` (line 119), so the rider is already counted as buckled when the ATV's tile is evaluated for slipping. `code/modules/vehicles/atv.dm` has no anti-slip handling.

The issue thread links #54901 (a bottled boat not working properly on icebox) as the same mechanism. The same check is responsible, but the boat was not changed here.

### Fix

Commit "Fix issue 58971: ATV riders no longer slip on ice or lube":

- Adds `TRAIT_NO_SLIP_RIDERS` (`code/__DEFINES/traits/declarations.dm`, next to `TRAIT_NO_SLIP_ALL`), listed under `/obj/vehicle` in `code/_globalvars/traits/_traits.dm`.
- `code/modules/vehicles/atv.dm` adds the trait in `Initialize` as an innate trait.
- `handle_slip` returns `FALSE` first thing in the buckled branch when the buckled object has the trait.

A trait on the vehicle was chosen over special-casing the ATV type in the turf code, so other all-terrain vehicles can opt in later, and over changing the `GALOSHES_DONT_HELP` rule, which would affect every buckleable object (chairs, beds) on lube.

### Verification

After rebuilding, on the test server:

- A human buckled to an ATV was moved with the ATV over two permafrost tiles and one lube tile (`MakeSlippery` with wet type 8). The human was still buckled at the end.
- A second human mounted an ATV standing on a permafrost tile and stayed buckled.
- The runtime log showed nothing tied to the change (one unrelated "list index out of bounds" at observer join).

Not checked: a player actually driving the ATV by keyboard over ice, other slip sources (banana peels, soap, wet floors with other flags), and other vehicles.

## #93733: Wacky golf cart preview in "buckled" alert

### The bug

When a mob is buckled to a golf cart, the "Buckled" alert shows a garbled cart image, as in the screenshot attached to the issue (the issue has no text beyond the screenshot).

### Reproduction

1. In the Lua editor, spawn a golf cart (`/obj/vehicle/ridden/golfcart`) and a human, buckle the human to it with `buckle_mob`, and give the human to your client (set its `ckey`).
2. Look at the "Buckled" alert on the screen (rendered with an icon-rendering tool on the alert object).
3. Observed on master: the whole two-tile golf cart (floor, roof and rear overlays at their pixel offsets) was drawn overflowing the alert's single tile.

### Cause

When someone is buckled, `buckle_mob` (`code/game/objects/buckling.dm:110-116`) decides whether to show the vehicle's icon in the alert by checking the dimensions of the icon file, and skips it if the file is larger than 32x32. The golf cart's icon file (`golfcart_split.dmi`) has 32x32 states, so it passes the check. But the cart's `update_overlays` (`code/modules/vehicles/cars/golfcart/golfcart.dm:573`) builds a two-tile-long cart out of overlays at offsets. The alert copies the whole appearance, so the overlays overflow the alert.

### Fix

Commit "Fix issue 93733: golf cart no longer drawn squashed in the Buckled alert":

- `code/game/objects/buckling.dm`: the inline size check became `/atom/movable/proc/show_in_buckled_alert()`, whose default does the same icon-dimension test, and `buckle_mob` uses it for the alert's `new_master`.
- `code/modules/vehicles/cars/golfcart/golfcart.dm`: the golf cart overrides it to return `FALSE`.

The alert then shows the plain "Buckled" icon for the cart. The override approach was chosen because the dimension check cannot see overlays; no attempt was made to detect overflowing overlays generically.

### Verification

On the test server, with a human buckled to a golf cart and controlled by the tester, the "Buckled" alert rendered as the plain alert with no cart in it (before the fix: the cart composite overflowing). Not checked: other vehicles built from overlays, and how the alert looks in a real client versus the icon renderer.

## #95757: speedwagon (admin spawn) flips itself

### The bug

The reporter, testing locally, said the admin-spawned speedwagon "flips its sprite" while not moving, even when unridden. A later comment said that after being carried by the mining shuttle, the speedwagon could not be moved at all and its sprite was "greatly misplaced".

### Reproduction

1. In the Lua editor, spawn a speedwagon (`/obj/vehicle/sealed/car/speedwagon`). Its pixel offsets are -48,-48, which center its 3x3 sprite on its one tile.
2. Call `shuttleRotate(90)` on it, as the shuttle code does when a shuttle rotates at docking.
3. Observed on master: the direction rotated from east to south, and the offsets became -48,+48, so the sprite was drawn far from its tile. Nothing resets them while the car is unridden. A ridden car re-applies its offsets when it moves.

This was reproduced by calling the rotate proc directly, not by flying a real shuttle.

### Cause

`/atom/proc/shuttleRotate` (`code/modules/shuttle/mobile_port/shuttle_rotate_callbacks.dm:9-30`) rotates `pixel_x`/`pixel_y` along with the direction when `ROTATE_OFFSET` is set, and the shuttle move code passes all parameters (`shuttle_move_callbacks.dm:82` and `:134`). That is right for atoms whose offsets are a position, but the speedwagon's -48,-48 are only centering offsets (`code/modules/vehicles/cars/speedwagon.dm`), so rotating them moves the sprite away from its tile.

### Fix

Commit "Fix issue 95757: shuttles no longer displace the speedwagon's centering pixel offsets": the speedwagon overrides `shuttleRotate` to clear `ROTATE_OFFSET` from the parameters and then calls the parent. Its direction and smoothing still rotate.

### Verification

After rebuilding, `shuttleRotate(90, 65535)` (all flags, as the shuttle code passes) was called twice on a speedwagon. The direction went 2 -> 8 -> 1 and the pixel offsets stayed at -48/-48.

Not reproduced: the "flips its sprite while stationary or unridden" report. The speedwagon icon has four directions and the car turns as it moves, and nothing in the code changes its direction on its own (`Moved()` only bumps things while occupied). It was seen facing east after one step with offsets unchanged. This may be intended behavior, or a quirk of the reporter's local setup.

Not investigated: "could not move it at all after the shuttle ride". Only the offsets part was checked. The likely explanation from reading the code is that an unridden car cannot be driven anyway and a ridden one re-applies its offsets on moving, but nothing was tested with a real mining shuttle.

## Notes

- #54901 (boats on icebox) shares the #58971 mechanism. A vehicle that wants the same protection can now add `TRAIT_NO_SLIP_RIDERS`; none other was changed.
- The `TRAIT_NO_SLIP_RIDERS` check runs after the gravity and non-touching-ground checks at the top of `handle_slip`, so those behave as before.
- The three fixes touch different files and can be taken separately.
