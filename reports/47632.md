## Summary

The 2019 report says that killing the vomiting goose (Birdboat, `/mob/living/basic/goose/vomit`) while it is still throwing up makes it come back to life. On current master the goose stays dead in every timing tried. The vomit status effect has an explicit `owner.stat != DEAD` guard in `on_remove()` and deletes itself when the owner dies, and no code under `goose/` revives the mob. No fix was committed.

## The bug

As reported: make the goose vomit, kill it while it is still vomiting, and it gets up again. The original 2019 cause, as far as can be inferred from the current code, was the end of the vomit effect resetting the goose's sprite and state to the living one after it had already died. Master no longer does this.

## Reproduction

The test was run on master with an observer and the Lua editor, calling the goose's own vomit ability directly. A player normally triggers it by feeding the goose, choking it on a non-food item, or deadchat control, so this does not go through those paths.

1. Using the Lua editor, spawn `/mob/living/basic/goose/vomit` and put six plain burgers (`/obj/item/food/burger/plain`) inside it, so it has something to vomit.
2. Trigger `vomit_action` on the goose.
3. Kill it with `death()`, at one of these moments:
   - (a) 0.5 s after triggering, during the 13-frame `vomit_start` wind-up (the goose's `vomit_action` sets `icon_state = "vomit"`, flicks `vomit_start` and only applies the status effect after 13 ticks);
   - (b) 3 s after triggering, while the `goose_vomit` status effect was running;
   - (c) 0.3 s after triggering, repeated with the state sampled at 0.6, 1, 1.5, 2.5, 4 and 6 s.
4. Read `stat`, `icon_state`, `health`, the number of contents and whether the status effect was present.

Observed:

- Cases (a) and (b), read 8 s after the kill: `stat=3` (DEAD), `icon_state=goose_dead`, `health=0`, no contents, no `goose_vomit` effect.
- Case (c): `stat=3` at every sample. The effect was not present at 0.6 s and 1 s, was present at 1.5 s, and was gone again by 2.5 s and afterwards. The goose never left the dead state.

## Cause

There is no live defect; these are the places that make the current behaviour correct.

- `code/modules/mob/living/basic/farm_animals/goose/goose_vomit.dm:83`: `on_remove()` only plays `vomit_end` and restores `icon_living` when `owner.stat != DEAD`. A dead goose therefore keeps its dead sprite when the effect ends.
- `goose_vomit.dm:76` and `:92`: `on_apply()` registers `COMSIG_LIVING_DEATH`, and `on_owner_died()` does `qdel(src)`, so the effect stops when the goose dies.
- `code/datums/elements/content_barfer.dm:14,20-28`: the goose carries the `content_barfer` element (`goose.dm:37`), which moves its contents out on death. With no contents left, `tick()` (`goose_vomit.dm:104-106`) deletes the effect.
- Nothing in `code/modules/mob/living/basic/farm_animals/goose/` revives the mob (grep for revive and related terms came back clean).

One side effect was seen. If the goose dies during the 13-frame wind-up, the delayed `start_vomiting()` (`goose_vomit.dm:50-53`) still applies `/datum/status_effect/goose_vomit` to the corpse, because the death signal is only registered later, in `on_apply()`. That is the "present at 1.5 s" sample in case (c). It is harmless here: the contents were already emptied on death, so the effect is deleted on its next tick, and `on_remove()` leaves the dead state alone.

## Fix

None. The issue appears to have been fixed some time after 2019.

## Verification

The no-revive result was checked on master in the three timings above. It was not checked with a real player-driven vomit (feeding or choking the goose, or deadchat control), with a goose that was not spawned through admin tools, or with other ways of dying (for example gibbing) during a vomit.

## Notes

- Optional hardening, not done and only cosmetic: skip applying the effect in `start_vomiting()` when the owner is already dead.
- Related to the issue's last comment: the commenter recalled a revive command for the goose when it is ghost-controlled. No revive code was found in the goose directory, so this was not investigated further.
