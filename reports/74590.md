# #74590: Movable machines that listen for COMSIG_ATOM_ENTERED on their own turf react to their own arrival (recycler eats itself)

| | |
|---|---|
| Issues | [#74590](https://github.com/tgstation/tgstation/issues/74590): verified (recycler reproduced in game; fix applied to four handlers) |
| Status | Fixed on the branch for the recycler, scanner gate, teambuilder and shower; the wider pattern was not audited exhaustively |
| Fix branch | [fix/74590](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/74590) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Machines that use the `connect_loc` element to hear `COMSIG_ATOM_ENTERED` on the turf they stand on also hear their own arrival whenever they are moved to a new turf. The recycler's handler then treats itself as something to eat, so an unanchored recycler that is moved destroys itself. The fix adds an `enterer == src` early return to the handlers of the recycler, scanner gate, teambuilder and shower. Other `connect_loc` handlers were reviewed from the code only and left unchanged.

## The bug

The issue reporter noticed it while adding `A.loc?.Entered(A)` to post-initialize, and named the recycler as an example: it "will eat itself if it moves". In game, an unanchored recycler that is moved to another turf is deleted. Other `connect_loc` users with similar handlers can react to themselves in the same way.

## Reproduction

On master, using admin tools:

1. Started a round and opened the Lua editor.
2. Spawned a `/obj/machinery/recycler` on a powered hallway turf, unanchored it with `set_anchored(false)`, and `forceMove`d it to a neighbouring turf.
3. Observed:
   - the Lua editor raised the error "a destructed callback or destructed userdata method was called" at the `forceMove` line, because the recycler had been deleted during the move;
   - the recycler's eating sound (`welder.ogg`) played at its turf;
   - an SDQL2 query found extra recyclers at turf `0,0,0`, one per attempt, i.e. the deleted ones.

This was triggered by moving the machine with `forceMove` rather than by a player pushing or pulling it. Only the recycler was reproduced in game.

## Cause

`/datum/element/connect_loc` (`code/datums/elements/connect_loc.dm`) registers the listed signals on the loc of the attached movable, and re-registers when that movable moves. When the movable arrives on a new turf, the turf's `Entered` fires `COMSIG_ATOM_ENTERED` with the movable itself as the arrived atom, and the movable has by then already registered on that turf. So the handler is called with `enterer == src`.

The recycler registers this in its `connect_loc` setup (`code/game/machinery/recycler.dm:45`) and its handler is:

```dm
/obj/machinery/recycler/proc/on_entered(datum/source, atom/movable/enterer, old_loc)
	SIGNAL_HANDLER

	if(can_butcher(enterer))
		return
	INVOKE_ASYNC(src, PROC_REF(eat), enterer)
```

(`code/game/machinery/recycler.dm:115-120`). It never checks whether `enterer` is the recycler, so `eat(src)` runs on the recycler itself, and `eat` only skips indestructible things and unpowered or safe-mode states (`recycler.dm:128-135`). The scanner gate, teambuilder and shower handlers have the same shape and no self check.

## Fix

One commit, "Fix issue 74590: movable listeners reacting to their own arrival on connect_loc turf signals". It adds an early return when the enterer is the listener in four `on_entered` handlers:

- `code/game/machinery/recycler.dm`
- `code/game/machinery/scanner_gate.dm`
- `code/game/machinery/teambuilder.dm`
- `code/game/objects/structures/shower.dm`

Each is `if(enterer == src) return` (with that handler's own variable name). The guard is a local change, and it leaves `connect_loc` itself alone, which other users may rely on.

## Verification

After the fix, on the test server, repeating the reproduction steps:

- The moved recycler survived: `machine_stat` was 0, it was still valid and was at the new turf, and no eating sound played.
- A crowbar `forceMove`d onto a recycler's turf was still eaten (`welder.ogg` played), so normal behaviour was intact.

Not checked in game: the scanner gate, teambuilder and shower changes (the same one-line guard, compile-checked only), and moving a recycler by a player action instead of `forceMove`.

## Notes

- The issue title says "most uses" of these hooks are affected. Only the four handlers above were changed. Other `connect_loc` `on_entered` handlers were read and judged not clearly self-affecting, because they act only on mobs, living things or specific items, or exclude effects and anchored objects: `mines.dm:82`, `pressureplates.dm:48`, `traps.dm:66`, `bonfire.dm:128`, `spiderwebs.dm:90`, the snap pop in `toys.dm:866`, and `tripwire.dm:258`. About 40 more files use `connect_loc` and were not reviewed. Only unanchored or otherwise movable listeners whose handler acts on any enterer can hit this.
- A more general fix could live in `connect_loc` (skipping the listener's own arrival), but that changes behaviour for every user of the element, so the per-handler guard was used. A maintainer may prefer the central change.
