## Summary

The issue reports that deathmatch items, with cluster grenades as the example, flood admins with messages. The cluster grenade spam was already fixed on master (PR 82090, referenced in the issue's comments). Two sources were still left: every explosion's "Explosion with size ..." admin message, and the explosive implant's "has activated their ... implant" message, neither of which checked whether the area is a quiet-log area such as a deathmatch arena. One commit makes both skip the admin message in `QUIET_LOGS` areas and keep the game log entry.

## The bug

Deathmatch arenas set the `QUIET_LOGS` area flag (`code/modules/deathmatch/deathmatch_mapping.dm:5`) so that actions inside them do not notify admins. The commenters say the admin chat was flooded for a whole day by deathmatch. Code that already honours the flag on master includes `log_bomber` (`code/__HELPERS/logging/attack.dm:82`), smoke and foam (`effects_smoke.dm:452,458`, `_fluid_spread.dm:160`), chemical recipe explosions (`others.dm:867`), and cluster grenades (cluster segments set a `type_cluster`, `clusterbuster.dm:97` and `_grenade.dm:147`). Two sources did not.

## Reproduction

Deathmatch needs several players, so a real match was not run. Using the Lua editor on the test server:

1. Started the round and observed. Chose a turf and its area.
2. In an ordinary (non-quiet) area: called `explosion(turf, 0, 0, 1)`, then spawned a human with `/obj/item/implant/explosive/deathmatch` (the implant deathmatch hands out, for example with the explode-on-death modifier) and called `death()` on it.
3. Counted new admin log lines. A microbomb death produced 3: the implant's activation message, the implant's own explosion, and a plain explosion message ("Explosion x2" plus "has activated their deathmatch microbomb implant").

That is a normal-area run plus reading the code; it shows the messages are sent regardless of area, not that they appear in a deathmatch. (The agent's first attempt set the flag on the wrong area, so it was not informative on its own.)

## Cause

- `code/controllers/subsystem/explosions.dm:363`: every explosion with `adminlog` sent `message_admins("Explosion with size ...")` regardless of the epicenter's area.
- `code/game/objects/items/implants/implant_explosive.dm:80`: activation sent `message_admins("... has activated their [name] ...")` regardless of area. Deathmatch uses these implants via its `explode_on_death` modifier and loadouts (`deathmatch_modifier.dm:290,361,427`).

## Fix

Commit "Fix issue 81865: stop explosions and microbomb activations in quiet-log areas (deathmatch) from spamming admins":

- `explosions.dm`: the `message_admins` call is skipped when the epicenter's area has `QUIET_LOGS`. The existing `log_game` line is unchanged and still runs.
- `implant_explosive.dm`: in a quiet-log area the admin message is replaced by a `log_game` entry (with `key_name` and `AREACOORD`); elsewhere the message is unchanged.

The area flag is checked at the source instead of filtering deathmatch's items individually, matching how the other already-fixed sources work.

## Verification

After rebuilding, with `QUIET_LOGS` set on the explosion's area through Lua (a stand-in for a deathmatch arena):

- Control run in a normal area: 3 admin lines, as before.
- Run with the flag on the area: no new admin lines at all.
- No runtimes from the changed files.

Not checked: a real deathmatch match with several players, and other deathmatch loadout items (for example mines) for other `message_admins` calls. They were not audited exhaustively, so more spam sources may remain.

## Notes

- Trade-off: admins no longer get explosion pings inside any `QUIET_LOGS` area, not only deathmatch. The explosions are still in the game log.
- The report on this issue suggested the cluster grenade was the main source; after PR 82090 the remaining ones found were explosions themselves and microbombs.
