## Summary

Three clothing display bugs were handled together, with one commit each. Uniforms ignored `worn_icon_state` because `update_worn_undersuit()` always passed `icon_state` as the sprite override. Rainbow bunch crowns kept the parent's `worn_icon_state = "garland"` whichever variant they rolled. Cowboy hats and the cakehat let hair show through, and a chameleon hat that changed look while worn left the wearer's hair masks wrong. The uniform change can alter how any uniform with a `worn_icon_state` is drawn, and the hair-mask choice is a sprite judgment; both are covered under Notes.

## The bugs

- **#72021:** a uniform with `worn_icon_state` set still drew its `icon_state` sprite on the mob. If `icon_state` is not a state in the worn icon file, nothing appears.
- **#78083:** a crafted rainbow bunch crown rolls one of four variants. The held and ground sprite matched the variant, but the worn sprite was always the plain garland.
- **#82632:** the cakehat and cowboy hats did not hide hair properly, so hair showed over the hat. The reporter also thought a chameleon hat changed into an EVA helmet showed the same problem; that case was not reproduced (see #82632 below).

## #72021: uniforms ignore worn_icon_state

### Reproduction

1. Spawn a human wearing a janitor uniform (state in `civilian.dmi`).
2. In the Lua editor, set the uniform's `worn_icon_state` to `"captain"` and call `update_worn_undersuit()` on the wearer.
3. Render the mob. It still showed the purple janitor suit, so `worn_icon_state` was ignored.

This was done by setting the variable and forcing an icon update, not through any normal player action.

### Cause

`update_worn_undersuit()` in `code/modules/mob/living/carbon/human/human_update_icons.dm:84` sets `var/target_overlay = uniform.icon_state`, and passes it as `override_state = target_overlay` to `build_worn_icon()` (line 121). `build_worn_icon()` uses `override_state` first (`var/t_state = override_state || (isinhands ? inhand_icon_state : worn_icon_state) || icon_state`, line 577), so `worn_icon_state` is never consulted. The check just before, `icon_exists(icon_file, RESOLVE_ICON_STATE(uniform))` at line 111, does use `worn_icon_state`, so the two disagreed about which state to draw. This is the explanation given in the issue thread.

### Fix

Commit "Fix issue 72021: uniforms ignored worn_icon_state": `target_overlay` is now `RESOLVE_ICON_STATE(uniform)`, which is `worn_icon_state || icon_state`. The `_d` suffix for adjusted uniforms is still appended afterwards. The thread's other suggestion, moving the logic into `build_worn_icon()`, was not done.

### Verification

After rebuilding, with the janitor uniform:

- `worn_icon_state = "captain"` (not a state in `civilian.dmi`): nothing was drawn, as expected for a state the file lacks.
- `worn_icon_state = "clown"` (a state in `civilian.dmi`): the red and white clown outfit was drawn.

The only uniform code found that sets `worn_icon_state` is in `color.dm` (`"jumpsuit"`, which equals the icon state after init), so no regression was expected from it. A full search of every uniform type was not recorded.

## #78083: rainbow bunch crown worn sprite

### Reproduction

1. Spawn rainbow bunch crowns (`/obj/item/clothing/head/costume/garland/rainbowbunch`) until one rolls a variant other than 1.
2. Read `icon_state` and `worn_icon_state` with View Variables or Lua.
3. On master, `icon_state` is `rainbow_bunch_crown_N` while `worn_icon_state` is `"garland"`, so the worn sprite is the garland's.

The `worn_icon_state` mismatch was read from variables. How the worn sprite looked on a mob before the fix was not recorded.

### Cause

`code/modules/clothing/head/garlands.dm` defines the garland parent with `worn_icon_state = "garland"`. The rainbowbunch subtype only changes `icon_state` in `Initialize()` (`rand(1,4)`), so it inherits `"garland"`. `costume.dmi` has `rainbow_bunch_crown_1` to `_4` worn states.

### Fix

Commit "Fix issue 78083: rainbow bunch crowns worn sprite ignored the rolled variant": the subtype sets `worn_icon_state = "rainbow_bunch_crown_1"` as its default and `Initialize()` sets `worn_icon_state = icon_state` after rolling.

### Verification

After rebuilding, spawned crowns showed `icon_state` such as `rainbow_bunch_crown_4` and `_2`, with `worn_icon_state` equal to them (it was `"garland"` before). Equipping a crown on a mob and viewing the worn sprite was not recorded.

## #82632: hats that should hide hair

### Findings

- Cowboy hats (`code/modules/clothing/head/hat.dm:112`) had no `hair_mask` and `flags_inv` 0, so tall hair (e.g. the Afro Large style) poked through.
- The cakehat inherits the hardhat's `hair_mask = /datum/hair_mask/standard_hat_middle` (`code/modules/clothing/head/hardhat.dm:16`), which was judged too high for the cakehat's large sprite.
- Chameleon hats have a separate bug. `update_item()` in `code/modules/clothing/chameleon/_chameleon_action.dm` (around line 177) copies the picked item's `hair_mask` to the hat, but the wearer's `hair_masks` list is only updated when the item is equipped or unequipped (`code/modules/mob/living/carbon/inventory.dm:104-117`). Changing look while worn therefore never added the new mask, and unequipping removed the new mask while the old one stayed.
- The issue's complaint of hair drawn over a sprite probably dates from before hair masks existed, when hats relied on `flags_inv` alone. This is an inference from the code, not something observed.

The chameleon hat to EVA helmet case was not tested.

### Fix

Commit "Fix issue 82632: cakehat and cowboy hats get a hair mask; chameleon hats swap it":

- The cakehat and the cowboy hat set `hair_mask = /datum/hair_mask/standard_hat_low`, which hides hair at the top, sides and rear (`code/datums/sprite_accessories/hair.dm:12`).
- `update_look()` in `_chameleon_action.dm` remembers the old `hair_mask`. If the new one differs and the item is worn in a slot it can occupy, it removes the old mask from the wearer's `hair_masks`, adds the new one, and calls `update_hair()`.

### Verification

Checked in the Lua editor:

- Wearers of the cakehat and a cowboy hat had `hair_masks` containing `standard_hat_low`.
- A worn chameleon hat went from no mask, to `standard_hat_middle` after changing to a hardhat, to no mask after changing to a welding helmet (which has none).

The rendered hair and hat sprites could not be judged because the renders were too small to read. No before and after screenshot was compared.

## Notes

- **#72021 can change many sprites.** Any uniform with a `worn_icon_state` that was previously ignored will now draw that state. A scan of all uniforms was not done, so unexpected visual changes are possible.
- **#82632 mask choice is a spriter's call.** `standard_hat_low` (also used by the helmet and fedora types) covers more of the head than `standard_hat_middle`; whether it suits these two sprites, or a per-hat mask would be better, was not judged. Berets and similar hats were not examined.
- The `iscarbon` and slot check in `update_look()` is there so the mask is only changed when the item is actually worn in its equip slot, not held.
