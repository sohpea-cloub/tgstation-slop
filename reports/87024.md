## Summary

A MODsuit disguised by its chameleon module, with a storage module installed, kept its disguise's icon file but had `icon_state` overwritten with the suit's own state (`standard-control`) whenever its appearance updated, for example when an item was put in or taken out. That state does not exist in the disguise's icon file, so the suit showed the ERROR sprite or nothing. The fix adds a `disguised` flag on the MOD control unit, set and cleared by the chameleon module, and `update_icon_state()` leaves `icon_state` alone while it is set. A chameleon mask (#94932) had a related but separate defect: its `update_icon_state()` rebuilds `icon_state` from `base_icon_state`, which chameleon disguises never set. A second commit makes the disguise set it.

## The bug

- **#87024, #71646, #80651:** adding or removing an item from a chameleon item with storage makes the item's icon disappear or turn into the ERROR sprite. #71646 describes a disguised Elite Syndicate MODsuit (disguised as an Engineering Industrial Satchel) whose sprite goes invisible when a tool is placed inside. #80651 describes a suit that turns invisible and later ERROR after using the module, and is marked a duplicate of #71646 in its thread. #87024 reports the same for "a chameleon satchel, or an infiltrator MODsuit with a chameleon module".
- **#94932:** spraying a disguised chameleon mask with a spray can makes it invisible, or reverts it to its original icon while keeping the paint colour.

## Reproduction

All steps on master, with the Lua editor to spawn and drive the items directly (no player clicking). The results are values of `icon_state` and `icon` read back from the items; no client render was looked at.

1. **Chameleon backpack and belt (the "satchel" case).** Spawned a chameleon backpack and a chameleon belt, disguised them as an engineering satchel and a security belt through the chameleon action's `update_look()`, then used the storage datum's `attempt_insert()` and `attempt_remove()` with a crowbar. Name, `icon_state` and `icon` did not change (they stayed `satchel-engineering` and `security`). The bug did **not** reproduce for these. Neither of these types overrides `update_icon_state()`.
2. **Chameleon mask (#94932).** Spawned a chameleon mask, disguised it as the clown mask (`icon_state` `clown`, icon file `icons/obj/clothing/masks.dmi`) and called `update_appearance()` on it. `icon_state` became `gas_alt` while `icon` stayed `masks.dmi`. This is what a spray can does, since applying paint ends in `update_atom_colour()`, which calls `update_appearance()`. The spray can itself was not used before the fix.
3. **Chameleon MODsuit (#71646, #80651, #87024).** Spawned a MOD control unit, installed a chameleon module and a storage module, disguised it as `/obj/item/storage/backpack/satchel/eng` (`icon_state` `satchel-engineering`, icon `backpack.dmi`), and called `attempt_insert()` with a crowbar. `icon_state` became `standard-control` while `icon` stayed `backpack.dmi`, a state that does not exist in that file: the ERROR or invisible sprite.

No runtimes were seen during these steps. #71646's comment mentions chameleon module runtimes (`null.update_clothing()` in `update_look`, and "bad index" in `on_install`/`on_use`); those were not reproduced and are not addressed here.

## Cause

### MODsuit (#87024, #71646, #80651)

`/obj/item/mod/control/update_icon_state()` (`code/modules/mod/mod_control.dm:405`) always writes:

```dm
icon_state = "[skin]-[base_icon_state][active ? "-sealed" : ""]"
```

The chameleon module's `update_look()` (`code/modules/mod/modules/modules_antag.dm:337`) disguises the suit by setting `mod.icon_state`, `mod.icon` and the worn and held icon vars directly. Nothing stops `update_icon_state()` from running afterwards. The storage module's `attempt_insert()` and `attempt_remove()` end in `parent.update_appearance()` (`code/datums/storage/storage.dm:199`, and similar lines for removal and other updates), so the first insert or removal replaces the disguise's `icon_state` with the suit's own one, on top of the disguise's `icon`. Any other `update_appearance()` would do the same, not only storage. `return_look()` restores the suit's own state, so the problem lasts only while disguised.

### Mask (#94932)

`/obj/item/clothing/mask/update_icon_state()` (`code/modules/clothing/masks/_masks.dm:76`) sets `icon_state = "[BASE_OR_INITIAL_ICON_STATE(src)][up ? "_up" : ""]"`, that is, from `base_icon_state`, or from the item's own initial `icon_state` if that is unset. The chameleon action's `update_item()` (`code/modules/clothing/chameleon/_chameleon_action.dm:142-148`) changes `icon_state` but never `base_icon_state`, so the next `update_appearance()` (for example from spray paint through `update_atom_colour()`) reset the icon state to the mask's own (`gas_alt` in the test) while the disguise's icon file stayed.

## Fix

Two commits, on the same branch.

**"Fix issues 87024, 71646, 80651: chameleon MODsuit disguise survives storage and other appearance updates"**
- Adds `var/disguised = FALSE` to `/obj/item/mod/control`.
- `update_look()` in the chameleon module sets `mod.disguised = TRUE`; `return_look()` sets it back to `FALSE`. `return_look()` is also what `on_uninstall()` calls when the module is removed while disguised, so the flag is cleared there as well.
- `update_icon_state()` returns `..()` immediately while `disguised` is set, leaving `icon_state` for the chameleon module to own.

This was chosen over resetting `icon_state` from the module after every update because the suit rebuilds its look in several places, and a flag leaves the disguise alone for all of them.

**"Fix issue 94932: chameleon items keep their disguised icon_state when their appearance updates"**
- In `update_item()`, also sets `atom_target.base_icon_state = picked_item::base_icon_state || INITIAL_ICON_STATE(picked_item)`. Items that rebuild `icon_state` from `base_icon_state` (the mask, as above) then follow the disguise.

The first commit contains the changes to `mod_control.dm` and `modules_antag.dm`; the second only touches `_chameleon_action.dm`.

## Verification

After rebuilding and restarting the test server, using the Lua editor as above:

- **Mask:** disguised as the clown mask and worn or held by a spawned human; a real spray can's `interact_with_atom()` on it, followed by a direct `update_appearance()`. In both cases `icon_state` stayed `clown`.
- **MODsuit:** disguised as the engineering satchel with the storage module installed: `icon_state` stayed `satchel-engineering` after a crowbar was inserted and after it was removed.
- **Return path:** after `return_look()` and an `update_appearance()`, the suit was back to `standard-control` with the MOD icon file.

Not checked:

- Anything on a real client: no render of the sprites, no in-hand or worn sprite, and no visual check of the spray-painted mask's colour.
- Chameleon backpack and belt, before and after the fix. They were fine before, so there was no failure to compare, and the `animate_parent` transform animation that storage plays (`code/datums/storage/storage.dm:1202`) was not seen to change `icon_state`. If the original #87024 reporter saw the satchel break, that may be another effect (for example only visible on a client), and it is not explained here.
- Other chameleon item types (jumpsuits, hats, shoes, and so on) after the `base_icon_state` change, other than the mask.
- Module runtimes mentioned in #71646.

## Notes

- #87024 says it happens with the chameleon satchel too, and #94932 is filed separately; the grouping puts them together because of their symptoms. Only the MODsuit case is a real storage-related failure on this master.
- The `base_icon_state` change affects every chameleon item, not only masks. It writes `picked_item::base_icon_state` (or the disguise's initial `icon_state`) on each disguise change. Items that never read `base_icon_state` are unaffected, but only the mask was tested.
- `disguised` is a separate flag rather than checking `current_disguise` on the module because `update_icon_state()` lives on the suit, which does not otherwise know about the module.
