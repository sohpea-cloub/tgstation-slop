# #88315: View Round Logs drops every log entry after the first 1000 per category

| | |

| Status | verified (fix committed and checked in game) |

## Summary

The admin "View Round Logs" window kept only the first 1000 entries of each log category and silently discarded every later one, so on a long round the recent lines were missing from the viewer although they were in the log files. The fix keeps the newest entries instead (trimming the list in batches) and sends only the newest 1000 to the UI. The viewer title now also says "showing newest N" when the list is truncated.

## The bug

The issue reports that View Round Logs omits log lines that are present in the files and in the `get-current-logs` output. The reporter attached only screenshots, which could not be viewed, so their exact case is inferred from the code. The viewer title showed the true total count for a category (`entry_count`), but the list below it stopped at the 1000th entry ever logged in that category. On a long round the most useful entries, the recent ones, were the ones missing.

## Reproduction

1. Start a round on master and observe, or otherwise get admin access.
2. Open the Lua editor and create a state. Run:
   `for i=1,1200 do dm.global_procs.log_game('TESTLINE '..i) end`
3. Open View Round Logs and read the data of the `game` category from the tgui window.

Observed on master:
- `entry_count` of `game` was 1297 (the 1200 test lines plus lines already logged).
- `entries.length` was 1000.
- The last entry's message was `TESTLINE 903`. `TESTLINE 904` to `TESTLINE 1200` were not in the viewer data, though they were logged.

The viewer data was read through the tgui window's data, not by looking at the rendered table.

## Cause

`/datum/log_category/proc/create_entry` caps the cache by refusing new entries once the total count passes the limit (`code/modules/logging/log_category.dm:52`):

```dm
entry_count += 1
if(entry_count <= CONFIG_MAX_CACHED_LOG_ENTRIES)
	entries += entry
```

`CONFIG_MAX_CACHED_LOG_ENTRIES` is 1000 (`code/__DEFINES/logging.dm:2`). The entries are always written to the file first (`write_entry`), so the file is complete, but the in-memory list that `cache_ui_data` (`code/modules/logging/log_holder.dm:74`) sends to the UI holds only the oldest 1000. `entry_count` keeps counting, which is why the title shows a larger number than the list.

## Fix

One commit, "Fix issue 88315: round log viewer keeps the newest log entries instead of the first ones":

- `log_category.dm`: `create_entry` now always appends the entry. When the list grows past twice the cap, it cuts the oldest entries so 1000 remain. Trimming in batches avoids shifting the whole list on every log call.
- `log_holder.dm`: `cache_ui_data` sends only the newest `CONFIG_MAX_CACHED_LOG_ENTRIES` entries, since a category may now hold up to twice that.
- `LogViewer.tsx`: when the list has fewer entries than `entry_count`, the title reads `name[total, showing newest N]`.
- `code/__DEFINES/logging.dm`: the comment on the define now says it is the number of newest entries shown.

The alternative of keeping an unbounded list was not used, because the define's comment warns about performance with large lists.

## Verification

After rebuilding and restarting the test server, with a fresh Lua state:

- After 1200 `log_game` lines: the last `game` entry was `TESTLINE 1200`, the first was `TESTLINE 201`, `entry_count` was 1303 and the list held 1000 entries.
- After 1500 more lines (`SECOND 1` to `SECOND 1500`), which pushed the list past the 2x trim threshold, and a refresh: the last entry was `SECOND 1500`, the list length was still 1000, and `entry_count` was 2803.

Not checked: the reporter's exact case (screenshots only); the tgui title change was built successfully but not looked at in a rendered window. Only the `game` category was tested.

## Notes

- Behaviour change: the viewer now shows the newest 1000 entries per category rather than the oldest 1000. Entries older than that are only available in the log files (and the title says so).
- A maintainer may prefer a different trim policy or cap, or a client-side "load more"; the fix only changes which 1000 are kept.
