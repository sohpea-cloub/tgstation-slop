# #73530: Honorbound Knights cannot target living mobs to sculpt

| | |
|---|---|
| Issues | [#73530](https://github.com/tgstation/tgstation/issues/73530): not reproduced |
| Status | Not reproduced on master; the report appears to be stale |
| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The issue says a chaplain with the Honorbound sect cannot pick a living mob as a sculpting target with a chisel, because the game treats the click as a dishonorable attack. On current master this does not happen: an honorbound human could target a cow, a monkey and another human, adjacent and at range, with combat mode on and off. The chisel now selects targets through item interaction, which returns before the attack code runs, so the honorbound attack check never sees the click. No fix was needed or committed. The issue can probably be closed.

## The bug

As reported (client 514, February 2023): as an honorbound chaplain, take a carving block and a chisel, start a sculpt, and try to target a living thing. Selecting a target works like an attack click without the harm, and honorbound blocked it.

## Reproduction

Attempted on master; the reported behaviour did not occur.

1. Using the Lua editor, spawn a human and give it the honorbound brain trauma (`gain_trauma(/datum/brain_trauma/special/honorbound)`). `has_trauma_type` confirmed it was present.
2. Give the human a chisel, take control of it, and spawn carving blocks, a cow, a monkey and a second human.
3. Click a carving block with the chisel ("select sculpt target"), then click a target.
4. Ranged, on the cow and the monkey: "sculpt target is cow" and "sculpt target is monkey".
5. Adjacent, combat mode off, on the cow and on the second human: "sculpt target is ...".
6. Adjacent, combat mode on (checked: `combat_mode` was 1): left click on the human and right click on the cow both gave "sculpt target is ...". The "no honor in attacking" message never appeared.
7. Finishing a sculpt of the cow produced a "statue of cow".

The monkey is a human subtype, so honorbound treats it as innocent. It therefore does not by itself show that attacks on innocents are bypassed. The cow was the main test of a living non-human target.

## Cause (why the report no longer applies)

Honorbound blocks held-item attacks in `attack_honor` (`code/modules/religion/honorbound/honorbound_trauma.dm:68`), registered at line 33 on `COMSIG_MOB_ITEM_ATTACK`. That signal is sent from `/obj/item/proc/attack` (`code/_onclick/item_attack.dm:228`).

The chisel now sets its target in `/obj/item/chisel/interact_with_atom` (`code/modules/art/statues.dm:356`, calling `set_target` at line 375) and `ranged_interact_with_atom` (line 385). In `melee_attack_chain`, `base_item_interaction` runs first and the chain returns on success:

```
var/item_interact_result = target.base_item_interaction(user, src, modifiers)
if(item_interact_result & ITEM_INTERACT_SUCCESS)
	return TRUE
```

(`code/_onclick/item_attack.dm:32-34`). `attack` is never called, so `attack_honor` never runs. The 2023 code was not checked; it is inferred that targeting then went through the attack path (before the item-interaction refactor), which would be why the check used to apply.

## Fix

None. No commit was made.

## Verification

The test server run described above is the whole verification: targeting worked on a cow, a monkey and a human in the cases listed, and a sculpt completed. Not checked: other mob types, other chisel-based sculpting paths, and whether a mob that honorbound treats as an enemy (for example a hostile or an antagonist) behaves differently. Nothing indicates it would, since the attack check is not reached.

## Notes

- Side finding: an SDQL2 `CALL forceMove(locate(x,y,z)) ON ...` did not move the cow during setup. This was not investigated. Creating the mob at the target turf from Lua worked.
- Suggested action: close #73530 as no longer reproducible, citing the item-interaction change to the chisel.
