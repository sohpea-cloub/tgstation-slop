# #73963: Same-named crewmembers share Medical/Security records in HUD examine, wanted HUD and threat checks

| | |
|---|---|
| Issues | [#73963](https://github.com/tgstation/tgstation/issues/73963): verified, fixed |
| Status | Fixed and checked in game for the HUD examine, threat assessment and record rename paths; ID and console name lookups unchanged |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/73963 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Crew records are looked up by name only, and the lookup returns the first record with that name. When two crewmembers share a name (for example a respawned character), the second one is shown with the first one's rank and criminal status by HUDs, and is treated as wanted by secbots, turrets and scanner gates. The fix stores a weak reference to the mob on each crew record and lets `find_record()` take an optional subject mob, so mob-aware callers get that mob's own record, falling back to the name match when the mob has no record of its own.

## The bug

With a Security or Medical HUD, examining a crewmember shows their rank and, for Security, their criminal status. If two crewmembers have the same name, both show the record of whichever was added first. In the issue's example, a Captain named Rita Starpattern is shown as "Assistant" because a dead Assistant with the same name came first, and a warrant on the Assistant also appears on the Captain. A later comment on the issue reports that this happens with different players too, and that a secbot arrested both of them after an arrest was placed on the Assistant. The same-ckey condition in the original report was therefore not required.

## Reproduction

This was reproduced by calling the relevant procs from the Lua editor on the test server, not by respawning through OOC or by a real secbot arrest.

1. With admin tools (Lua editor), spawn two humans both named "Rita Starpattern", one with a mind whose assigned role is Assistant and one with a mind whose role is Captain. Spawn a third human with the security and medical HUD traits as the viewer.
2. Inject both into the manifest so each has a crew record.
3. Set the Assistant's record `wanted_status` to Arrest.
4. For each of the two humans, call `get_hud_examine_info(viewer)` and `assess_threat(JUDGE_RECORDCHECK)` (the arrest-warrant check).

Observed on master:

- Assistant: "Rank: Assistant", criminal status Arrest, threat 5.
- Captain: "Rank: Assistant", criminal status Arrest, threat 5. The Captain showed the Assistant's rank and warrant.

## Cause

`find_record(name)` (`code/__HELPERS/_lists.dm:778`) walks `GLOB.manifest.general` and returns the first crew record whose name matches. Every consumer passes only a name taken from the face or ID, so same-named crew resolve to the same record:

- HUD examine: `code/modules/mob/living/carbon/examine.dm:499`
- HUD links in `Topic`: `code/modules/mob/living/carbon/human/human.dm:162` and `:282`
- Threat assessment (used by secbots): `human.dm:454`
- Wanted HUD: `code/game/data_huds.dm:314`
- Scanner gate warrant check: `code/game/machinery/scanner_gate.dm:206`
- Portable turret: `code/game/machinery/porta_turret/portable_turret.dm:617`
- Renaming a mob's records: `replace_records_name`, `human.dm:671`

This also explains the secbot behaviour in the issue: the threat check uses the same lookup, so both people appear to have the warrant.

## Fix

Commit "Fix issue 73963: crew records of same-named crewmembers no longer mix" (8 files):

- `code/datums/records/record.dm`: `/datum/record/crew` gets a `subject_ref` var, a weakref to the mob the record was made for.
- `code/datums/records/manifest.dm`: `inject()` sets `subject_ref` when it creates the crew record.
- `code/__HELPERS/_lists.dm`: `find_record()` takes an optional `mob/subject`. With a subject, it returns the crew record whose `subject_ref` resolves to that mob; if none does, it returns the first name match, as before. Without a subject the behaviour is unchanged.
- The callers listed under Cause that have a mob (HUD examine, the two `Topic` lookups, `assess_threat`, the wanted HUD, the scanner gate, the turret) now pass that mob as `subject`.
- `replace_records_name` finds the crew record for `src` and uses its `lock_ref` to rename the matching locked record, so renaming one mob no longer renames the first record carrying the old name (it falls back to the name lookup if there is no `lock_ref`).

The fallback to the name match was kept on purpose: someone impersonating another crewmember (wearing their ID or face) or a body without a record still gets the record of the name they present, as before.

## Verification

Same Lua setup as in Reproduction, after rebuilding and restarting the test server:

- Assistant: "Rank: Assistant", Arrest, threat 5 (unchanged).
- Captain: "Rank: Captain", criminal status None, threat 0.
- A body with the same name but no mind or record still fell back to the first name match (the Assistant's record, Arrest), so the impersonation behaviour is kept.
- `replace_records_name` on the Assistant renamed only that record; the records "Rita Renamed|Assistant" and "Rita Starpattern|Captain" remained.
- No new runtimes in the runtime log.

Not checked: a real respawn through the OOC commands, a real secbot arrest, the wanted HUD icon, the scanner gate and turret paths in play (these changed in the same way but were not exercised), and the HUD `Topic` links (photos, status changes).

## Notes

- **Merge risk.** `find_record()` is core record lookup and the change touches 8 files. The signature change is backwards compatible, but a reviewer may want to confirm every mob-aware caller was converted.
- **Not changed.** Lookups that go by name because they have no mob remain name-based: ID name lookups, `manifest.modify`/`remove`/change-pictures, the PDA and ID card consoles, mulligan, the labor stacker, `say.dm` and admin verbs. With two same-named records, editing through these can still hit the first one.
- Mobs created before the fix or records created by paths other than `manifest.inject()` have no `subject_ref` and use the name fallback.
