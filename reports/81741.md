## Summary

The Uplink tgui interface downloads the full item list (`uplink.json`) once, keeps it in a module-level variable, and then filtered that shared list in place for the uplink being opened. tgui windows are reused and keep their JavaScript loaded, so the next uplink opened in the same window filtered the already-filtered list, and a traitor uplink followed by a nuclear uplink ended up showing only the items both types allow. The fix filters into new local arrays and leaves the cached list untouched, and adds a bun test that opens a traitor, a nuclear and a traitor uplink in turn.

## The bug

Four reports describe one symptom from different angles:

- #81741: after opening a traitor uplink and a nukie uplink, almost nothing can be bought from either, because only items purchasable from both types are listed. The reporter notes that buying still works server side ("buying random items will still purchase items that you can't see").
- #93191: picking up (opening) a nuclear uplink makes every other uplink lose the items the nuclear uplink does not allow.
- #64142: a traitor uplink opened first makes a later nuclear uplink show the traitor market. The reporter says it does not work "reversely", i.e. nuclear first, then traitor, is fine.
- #65592: admin-spawned nuclear uplinks look like traitor uplinks and lack operative weapons and suits; the stock "occasionally" appears right, and a commenter observed that it seems to fix itself after refreshing tgui. The same report also says spawned uplinks could be locked regardless of the `lockable` variable.

The server side is correct throughout: each uplink sends the right `uplink_flag`. Only the list the client displays is wrong.

## Reproduction

The server side was checked in game; the client side was reproduced with a unit test, not in a running game client.

1. On the test server, with the Lua editor, spawned a human holding a `/obj/item/uplink` in one hand and a `/obj/item/uplink/nuclear` in the other, and took control of it. Used each in turn.
   - The first tgui window (traitor uplink) received `static_data.uplink_flag` = 1.
   - The second tgui window (nuclear uplink) received `static_data.uplink_flag` = 2.
   So the game sends each uplink the correct flag.
2. Using the Lua editor to iterate `SStraitor.uplink_items`, counted 369 items: 177 purchasable from traitor uplinks, 217 from nuclear uplinks, and only 85 from both. After the bug triggers, the second uplink can offer at most those 85.
3. Because the test server's connection does not run tgui's JavaScript, the display bug was reproduced with a new bun test, `tgui/packages/tgui/interfaces/Uplink/Uplink.test.tsx`. It mocks `uplink.json` with one traitor-only, one nukie-only and one shared item and renders the real `Uplink` component three times: a traitor uplink, a nuclear uplink, and a traitor uplink again.
4. On master code (before the fix) the test failed at the second step: the nuclear uplink offered `["shared"]` where `["nukie only", "shared"]` was expected.

The third step (traitor again) was not reached on the unfixed code, because the test failed at the second. That the reverse order breaks as well (contradicting #64142's remark) comes from reading the code, which filters the same shared list whichever type comes first, and is not a separate test result.

## Cause

`tgui/packages/tgui/interfaces/Uplink/index.tsx` caches the downloaded item list at module level (line 83: `let fetchServerData: Promise<ServerData> | undefined;`, filled at lines 100-103). `populateServerData()` then awaits that shared object and overwrites its fields:

```ts
const uplinkData = await fetchServerData;          // line 111
...
uplinkData.items = uplinkData.items.filter((value) => { ... });          // line 114
...
uplinkData.categories = uplinkData.categories.filter((value) => ...);    // line 141
this.setState({ allItems: uplinkData.items, allCategories: uplinkData.categories });  // lines 145-148
```

The filter keeps only items whose `purchasable_from` matches the current `uplink_flag` (and passes the role and species checks), and it writes the result back into the cached object. tgui windows are pooled and keep their JavaScript module state across UIs, so the next uplink opened in that window starts from the list already narrowed by the previous one. After a traitor uplink and a nuclear uplink the list is the intersection of both types, and it stays that way for the life of the window. This also fits #65592's observation that the full stock sometimes appears: that happens when the uplink opens in a freshly created window (or after a tgui refresh), which downloads the list again.

Because the narrowing is client side, the server is unaffected, matching the "buying still works" remark in #81741.

## Fix

One commit, "Fix issue 81741: uplinks of different types no longer share a filtered stock":

- `Uplink/index.tsx`: the filtered items and categories are built into new local `items` and `categories` arrays and passed to `setState`; the cached `uplinkData` is never assigned to. A comment explains why.
- `Uplink/Uplink.test.tsx` (new): the regression test described above, which opens a traitor, a nuclear and a traitor uplink in turn and checks each one's item names.

Alternatives such as re-fetching the list per uplink, or caching one filtered list per `uplink_flag`, were not considered in the inputs; filtering into locals is the smallest change and keeps the one-download cache that the original comment ("Cache response so it's only sent once") intended.

## Verification

- The new bun test failed on the unfixed code (the nuclear uplink got `["shared"]`) and passes with the fix. All the tgui bun tests passed after the change (26 of 26).
- tgui was rebuilt on the test server; the built `tgui.bundle.js` now filters `o.items` into locals and no longer assigns back to the cached object.
- The server half (correct `uplink_flag` per uplink) was checked in game before the fix, as described under Reproduction.

Not checked: the fix was not watched in a running game client, since the client used for testing does not run tgui's JavaScript. By eye, the check would be: open a traitor uplink, close it, open a nuclear uplink, and confirm the nuclear one shows the operative guns, MODsuits and the other nuke-ops items. The role and species filters were not tested separately.

## Notes

- #64142's claim that the problem does not occur in the reverse order is wrong by the code: both orders give the intersection.
- #65592's lockable complaint is already fixed on master: `/obj/item/uplink` passes `lockable_uplink = FALSE` as the component's `lockable`, the `"lock"` action returns early when `!lockable` (`code/datums/components/uplink.dm:259`), and the lock button is only shown when `lockable` is set. The ticket's other half (nuclear stock) is the bug fixed here. A commenter there also suggests the nuclear uplink checks that the user is a real nuke op; the inputs did not look into that, and what was observed was the client-side cache mutation described above.
- The same in-place filtering applied to the role and species restrictions, so two uplinks with different `assigned_role` or `assigned_species` in one window would also have narrowed each other. This follows from the code and was not tested.
- Frontend-only change; no DM code is touched.
