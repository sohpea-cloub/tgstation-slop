## Summary

When an AI tracks a crew member through the crew monitor, or double-clicks a mob, `track_mob()` hands the mob's `name` to a name-based lookup. Every mob whose name shows as "Unknown" (unknown-appearance, husked, and similar) has the same name, so the lookup returns the first one in the list no matter which one was chosen. The fix makes `track_mob()` track the mob it was given instead of looking it up by name. After the fix each Unknown tracked itself in the test.

## The bug

#58817: the AI opens the crew monitor, clicks Track on any entry listed as "Unknown", and the camera goes to one particular Unknown, always the same one, regardless of which entry was clicked. If that mob is removed or leaves camera coverage, tracking any other Unknown fails (the reporter says the crew monitor "can no longer find any target"). The reporter also saw clicks that did nothing.

#59723 is a report from an AI player who pressed Track on Unknown entries and ended up following monkeys. It was filed as a separate issue and a commenter linked it to #58817. Its symptom of landing on the wrong mob is the same bug; its second theme (monkeys and husks showing as "Unknown" at all) is discussed under Notes.

## Reproduction

All of this was done on the test server on master with the Lua editor, because the test setup could not click inside the crew monitor UI. The calls below are the ones the UI and the double-click handler make, so this reproduces the logic but not the click itself.

1. Start a round and open the Lua editor as an admin.
2. Spawn three humans on separate tiles, each wearing a grey jumpsuit with `sensor_mode = 3` (full coordinates), and give each the `unknown_appearance` trait (`TRAIT_UNKNOWN_APPEARANCE`). After calling `update_visible_name()` on each, all three have `name == "Unknown"` and different `real_name`s. In the first run they were Jamar Best, Tucker Jowers and Anne Lewis.
3. Spawn another human and call `AIize()` on it so there is an AI whose `ai_tracking_tool` can be used.
4. For each Unknown human `h`, call `ai.ai_tracking_tool:track_mob(ai, h)` and read `ai.ai_tracking_tool.tracked_mob`.

Observed on master: every call ended up tracking the same mob, "Jamar Best" (the first Unknown). The written record of the test counts this as 6 of 6 lookups wrong, which does not fit with the first Unknown being the one returned (that lookup would have been correct), and the raw output of that run was not available to me. What is solid is that every lookup returned the same single mob regardless of which mob was passed.

## Cause

`/datum/trackable` keeps the tracking state for an AI. Its name-based path works like this:

- `find_trackable_mobs()` (`code/game/machinery/camera/trackable.dm:39`) builds the list of trackable mobs keyed by name. When two mobs share a name it numbers the duplicates ("Unknown", "Unknown (2)", ...) using `namecounts`, so the keys are unique.
- `track_name()` (`trackable.dm:189`) rebuilds that list and looks up the requested name in `humans` / `others`.
- `track_mob()` (`trackable.dm:209`) is what both entry points use. On master it is:

```dm
/datum/trackable/proc/track_mob(mob/living/tracker, mob/living/tracked)
	if(!tracker || tracker.stat == DEAD)
		return
	// Need to make sure the tracked mob is in our list
	track_name(tracker, tracked.name)
```

The name it passes is always the plain `tracked.name`, i.e. "Unknown". The numbered keys ("Unknown (2)", ...) can never be produced from a mob's own name, so only the first Unknown can ever be found.

The two callers both hold the exact mob:

- the crew monitor's `select_person` action (`code/game/machinery/computer/crew.dm:302`) locates the target from a ref sent by the UI and then calls `track_mob(AI, target)`;
- `/mob/living/silicon/ai/DblClickOn()` (`code/_onclick/ai.dm:14`) calls `track_mob(src, A)` with the clicked mob.

The comment in `crew.dm` ("We need to do this because the ID might add an honorific and otherwise break tracking") shows the ref was already meant to avoid name matching, but `track_mob()` converted it back to a name.

## Fix

One commit, "Fix issue 58817: AI crew monitor and click tracking now follow the exact mob, not the first one with the same name", changes `track_mob()` in `code/game/machinery/camera/trackable.dm`. Instead of calling `track_name()` with the mob's name it:

1. rejects anything that is not a living mob, or that fails `can_track(tracker)`, with the same "Target is not on or near any active cameras. Tracking failed." message as before;
2. otherwise prints the same "Now tracking [name] on camera." message and calls `set_tracked_mob(tracked, tracker)` directly.

`can_track()` (`code/modules/mob/living/living.dm:1332`) is the same check `find_trackable_mobs()` applies when building the list, so the set of mobs that can be tracked is unchanged: cloaked mobs, mobs in containers, mobs on centcom or away levels, the Syndicate base case, mobs no camera can see, and the tracker itself are still refused. `track_name()` and `track_input()` (used by the `track` verb and by hrefs from `silicon.dm`) were left alone; they still go through the numbered list, which does disambiguate.

An alternative would have been to look up the mob's key in `humans`/`others` by reference, but that adds another rebuild of the list for no benefit when the caller already has the mob.

## Verification

In the test round after the fix:

- Four mobs were spawned: three humans with `unknown_appearance` and one monkey with the `husk` trait, each in a grey jumpsuit with `sensor_mode = 3`, all with `name == "Unknown"`.
- For each, `track_mob(ai, mob)` was called and `tracked_mob` was compared with the mob passed. All four tracked themselves ("Deangelo Kelley -> Deangelo Kelley OK", and likewise for the others, including "monkey (211)").
- Other mobs named "Unknown" that the cameras could not see were still refused (`tracked_mob` stayed nil), as before.
- The runtime log of the round held only two tgui errors about reopening a window (`code/modules/tgui/tgui.dm:124` and `:270`), unrelated to this change.

Not checked: the real click in the crew monitor UI (the test setup could not run the tgui JavaScript, so the `select_person` action was not exercised; only the `track_mob()` call it makes was), the AI double-click path, and a long-running track of a moving target after it was set. The sensor-based visibility of the Unknown entries in the crew monitor list itself was not examined.

## Notes

- #59723 mixes two things. The wrong-mob part is this bug and is fixed. The other part is that husked or slime-eaten monkeys and humans appear with the name "Unknown" in the camera track list. That is how the list is built (`find_trackable_mobs()` uses `mob.name`, adding "(2)" suffixes), and a commenter on #58817 says AIs being foolable by names is intended. That was not changed.
- `track_name()`, which still looks up by displayed name, was not changed and still behaves as designed.
- The change also makes `track_mob()` tolerate non-living arguments: `DblClickOn()` passes any mob (`ismob(A)`), and the new `isliving()` check turns a non-living mob into the normal "tracking failed" message instead of reading `.name` of it and looking it up.
