# #42588: RPG loot event gives fantasy to item stacks (and to items pooled in SSwardrobe)

| | |
|---|---|
| Issues | [#42588](https://github.com/tgstation/tgstation/issues/42588) (verified), [#91336](https://github.com/tgstation/tgstation/issues/91336) (verified, fixed) |
| Status | Fixed on the branch below; both issues reproduced on master and checked after the fix |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/42588 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

When the RPG Loot event starts, `handle_current_items()` gives the fantasy component to every initialized `/obj/item` in the world. It does not apply the exclusions that items created later get, so existing stacks become "fantastical", which blocks stack merging. It also reaches items pooled in nullspace by `SSwardrobe`, which never go through the after-init signal again. The fix adds one shared `can_be_fantastical()` check (stacks and `SKIP_FANTASY_ON_SPAWN` items are skipped), skips nullspace items when the event starts, strips fantasy when an item is stashed in the wardrobe, and applies it when the item is provided again while the event is active.

## The bug

### #42588: stacks

Players saw stacks with fantasy names and modifiers (for example "package wrapper of ... +7") that no longer merged with others of their kind. The reporter's case was xenobiology: with the event active, opening the extract storage was slow and the storage was full of single items instead of stacks. The issue title and body say the event should never apply to stackable items.

`SKIP_FANTASY_ON_SPAWN` is meant to prevent exactly this, but it is only checked for items created after the event starts. Items that already exist when the event starts are not checked.

### #91336: SSwardrobe

Items held in `SSwardrobe`'s pool sit in nullspace. When the event starts they got fantasy too. The issue author points out the consequence: a pooled item that carried a curse (for example polymorph) could affect someone when it is later spawned from the pool.

## Reproduction

On master, on a running round (the test character was an observer):

1. Open the Lua editor and start the event: `SS13.new('/datum/round_event/wizard/rpgloot'):start()`. (Creating `/datum/rpgloot_controller` directly also works, but leaves `GLOB.rpgloot_controller` null.) Wait about 40 seconds: `handle_current_items()` yields with `CHECK_TICK` while it walks the world.
2. In the SDQL2 console, run `SELECT /obj/item/stack WHERE GetComponent(/datum/component/fantasy)`. Result on master: 798 of 817 stacks had the fantasy component (for example a package wrapper named "package wrapper of ... +7").
3. To see the merge effect: `fantasy.dm`'s handler for `COMSIG_STACK_CAN_MERGE` returns `CANCEL_STACK_MERGE`, so `can_merge()` fails for such stacks.
4. For #91336, use the Lua editor to read `SSwardrobe.preloaded_stock` (index entries as `ps[ps[i]]`) before and after starting the event. Before: 0 of 5106 pooled items had fantasy. After: 390 or more did, in nullspace, for example "unsteady identification card () of awkwardness -11".

Both observations were made by starting the event and inspecting world state. No player action was needed beyond the event itself.

## Cause

`code/modules/events/wizard/rpgloot.dm:101` (`handle_current_items`) calls `AddComponent(/datum/component/fantasy)` on every initialized, non-deleted `/obj/item` in `world`, with no exclusions:

```dm
for(var/obj/item/fantasy_item in world)
	CHECK_TICK
	if(!(fantasy_item.flags_1 & INITIALIZED_1) || QDELETED(fantasy_item))
		continue
	fantasy_item.AddComponent(/datum/component/fantasy)
	if(isnull(fantasy_item.loc))
		continue
```

Items created after the event go through `on_new_item_in_existence` (`rpgloot.dm:79`), which does honour `SKIP_FANTASY_ON_SPAWN` (line 83). So the two paths disagree.

Two further points:

- `/obj/item/stack` sets `item_flags = SKIP_FANTASY_ON_SPAWN` (`code/game/objects/items/stacks/stack.dm:17`), but several stack subtypes assign `item_flags` again and lose the flag: `package_wrap` (`stacks/wrap.dm:92`), the medical wrap subtype that is sticky tape (`stacks/tape.dm:9`), and `/obj/item/stack/ducts` (`code/modules/plumbing/ducts.dm:270`). After a test fix that only checked the flag in `handle_current_items()`, 49 stacks still got fantasy. Checking `isstack()` is therefore needed in both paths.
- Items pooled by `SSwardrobe` were initialized long before the event, so they never receive `COMSIG_GLOB_ATOM_AFTER_POST_INIT` again. In `handle_current_items()` the `isnull(fantasy_item.loc)` check comes after `AddComponent`, so nullspace items were already fantasied by then. `stash_object()` and `provide_type()` in `code/controllers/subsystem/wardrobe.dm` (lines 232 and 271) know nothing about the component.

## Fix

Two commits on `fix/42588`.

**Fix issue 42588: RPG loot no longer makes existing item stacks fantasy.** Adds `/datum/rpgloot_controller/proc/can_be_fantastical(obj/item/checked)`, which returns `!isstack(checked) && !(checked.item_flags & SKIP_FANTASY_ON_SPAWN)`. `on_new_item_in_existence()` and `handle_current_items()` both use it. Checking `isstack()` as well as the flag covers the subtypes that overwrite `item_flags`.

**Fix issue 91336: RPG loot no longer affects items pooled in SSwardrobe.** Three changes:

- `handle_current_items()` moves the `isnull(loc)` check ahead of `AddComponent`, so nullspace (pooled) items are skipped when the event starts.
- `stash_object()` does `qdel(object.GetComponent(/datum/component/fantasy))` after moving the item to nullspace. Deleting the component runs `unmodify()`, which restores the name and stats.
- `provide_type()` calls `GLOB.rpgloot_controller?.on_new_item_in_existence(null, requested_object)` after taking an item from the pool, so a pooled item gets fantasy when handed out, as a freshly created item would.

## Verification

On the test server, after the fix, repeating the steps above:

- Stacks with the fantasy component: 0 of 792 (798 of 817 before).
- Pooled `SSwardrobe` items with fantasy after the event: 0 of 5102.
- With the event active, `provide_type` returned an identification card with fantasy applied ("enfeebled identification card () of draining -10"). Calling `stash_object` on it restored the name, removed the component and left `loc` null.
- Fresh spawns with the event active: iron sheets and a package wrapper had no component. A pocket crowbar still got fantasy ("superior pocket crowbar +1").

Not checked:

- The wardrobe provide and stash paths were exercised by calling `provide_type` and `stash_object` directly, not through normal gameplay spawns such as a player joining.
- The xenobiology scenario from #42588 was not played out.
- Merging after the fix was not tested separately. It follows from the stacks no longer carrying the component.

## Notes

- #42588 describes slime extracts. Extracts are not `/obj/item/stack`, so this fix does not stop them from getting fantasy. The sorting complaint in that issue (the thread discusses sorting by name versus type) is separate and was not changed.
- A comment on #91336 calls the behaviour a feature. The pooled-item case looks like an oversight, especially given the curse example in the issue.
- Alternative not taken: checking only `SKIP_FANTASY_ON_SPAWN` in `handle_current_items()`. It left 49 stacks fantasied because of the subtypes that overwrite `item_flags`. Fixing those subtypes' flags would also work, but the `isstack()` check cannot be bypassed by a new subtype making the same mistake.
- Pooled items are stripped on stash and re-applied on provide, so each provide rolls new fantasy. They do not keep earlier modifiers.
