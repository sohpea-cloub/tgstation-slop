## Summary

An AI that takes over a mech with an AI control beacon (`AI_MECH_HACK`) has several ways to end up inside the mech without being able to drive it or leave it. Three separate defects were found. `mob_exit()` strips an AI's mech control before it finds out the AI has no core to return to, so a core-less AI is left half-ejected (#87425). The beacon takeover never checks whether the mech is already occupied, so AIs pile into a mech whose only driver slot is taken (#55695, #85136). `/mob/living/silicon/ai/up()` and `down()` always move the AI's camera, even while it is controlling a mech (#93134). The branch has one small commit for each defect.

## The bug

**#87425.** An AI that controls a mech through a beacon gets a temporary empty core and a `linked_core` pointing at it, to return to when it leaves the mech. If that core is destroyed, the AI stays in the mech. Trying to eject then gives only "Inactive core destroyed. Unable to return." That message is intentional. But some other exit paths (below) go further: the AI stops piloting, loses access to the mech and its equipment, and remains an occupant.

**#55695.** A mech can end up with a pilot and an AI together. The first half of the report (AI can't use equipment) was already fixed according to a comment on the issue. Only the "pilot plus AI" half was examined here.

**#85136.** Two AIs took over one mech at once and both became stuck in it, unable to drive or return to their cores. The reporter's later comment says a single AI also couldn't control the mech. That part was not reproduced (see Reproduction).

**#93134.** In a multi-z map, pressing up or down while controlling a mech prints "you move upwards" or "you move down", but the mech does not move.

## Reproduction

All steps were done on MetaStation with the Lua editor. The takeover was triggered by calling `transfer_ai` directly, not by clicking the "take control" link in a real AI client. A real AI client, the `ai_take_control` href and the camera-visibility check were not exercised.

Setup: spawn a Durand (a Ripley is not AI-compatible) and attach `/obj/item/mecha_parts/mecha_tracking/ai_control` with `try_attach_part`. Create an AI by calling `AIize(nil, FALSE)` on a spawned human. Take control with `mech.transfer_ai(AI_MECH_HACK, ai, ai)` (value 3).

**#87425**
1. Take control of the Durand with the AI. A core is created and `ai.linked_core` is set.
2. `qdel(ai.linked_core)`. `on_core_destroyed` runs and calls `break_core_link`, so `linked_core` becomes null.
3. Make the AI eject with `container_resist_act`. It prints "Inactive core destroyed. Unable to return." and, since the AI has no shunt or hacked APCs, returns. This is the intentional message and the AI stays in the mech.
4. Call an unforced `mob_exit(ai)` instead. This is what generic code such as `dump_mobs` or `process_occupants` does. The runtime log shows `tried to resolve a core link with no core!!!!` from `resolve_core_link()` (`code/modules/mob/living/silicon/ai/ai.dm:1175`).
5. Check the state afterwards. `mob_exit` had already cleared `remote_control` and `controlled_equipment`, cleared `SILICON_PILOT` (`mecha_flags` went from 52340 to 52324) and moved the eye out of the mech. But `remove_occupant` never ran, so `occupants` was still 1. The AI was inside the mech and no longer controlling it, which matches "stops piloting the mech and will lose access to it" in the issue.

**#55695 and #85136**
1. Take a mech with a human pilot (`max_occupants` is 1) and two AIs holding a beacon.
2. Call `transfer_ai(AI_MECH_HACK, ...)` for both AIs.
3. `occupants` became 3. Both AIs had `linked_core` and `remote_control` set. Neither received a drive flag from `auto_assign_occupant_flags`, because the pilot held the only driver slot. So neither AI could control the mech, and neither could get back to a core. This matches the #85136 report.
4. Control group: a single AI in an empty Durand controlled it normally (one driver). The comment on #85136 saying that even a single AI couldn't control the mech was not reproduced.
5. Not reproduced here: the human pilot still getting in while the AI takes control (the first part of #55695's steps). `enter_checks` already guards that case inside the `do_after`.

**#93134**
1. Control the Durand as an AI.
2. Call `ai.up()`. The mech's `cooldown_vehicle_move` stayed at 0, so the mech never received `relaymove`.
3. This was a call to the proc, not a keypress. MetaStation has no z-levels above or below, so an actual move up or down was not seen.

## Cause

**#87425.** In `/obj/vehicle/sealed/mecha/mob_exit()` (`code/modules/vehicles/mecha/mecha_mob_interaction.dm:114`), the AI branch (line 124) clears state before it knows the exit can succeed:

```dm
AI.eyeobj?.forceMove(newloc) //kick the eye out as well
AI.controlled_equipment = null
AI.remote_control = null
if(forced)
    ...
mecha_flags &= ~SILICON_PILOT
AI.resolve_core_link()
```

The only guard for a missing `linked_core` is inside `if(forced)` (line 133), which gibs or shunts the AI. For an unforced exit there is no check. `resolve_core_link()` then hits `CRASH("tried to resolve a core link with no core!!!!")` (`ai.dm:1175`). The proc stops there, so the base `mob_exit` / `remove_occupant` never runs. `container_resist_act` (`mecha_mob_interaction.dm:201`) is not at fault. It checks `linked_core` first and refuses, but other callers of an unforced `mob_exit` do not.

**#55695 and #85136.** In `transfer_ai()`, the `AI_MECH_HACK` branch (`code/modules/vehicles/mecha/mecha_ai_interaction.dm:80`) has no occupancy check. The occupied-mech check at line 101 exists only for `AI_TRANS_FROM_CARD`. In the hack branch, only an AI with `can_dominate_mechs` (the malf mech takeover) does anything about occupants: it ejects them (lines 82-86). A beacon AI goes straight to `ai_enter_mech`, which calls `add_occupant()` whatever the occupancy. The branch also creates the core link (line 81) before anything else can fail. The `ai_take_control` Topic handler (`ai.dm:481`) does not check occupancy either, and `attack_ai` only hides the link.

**#93134.** `/mob/living/silicon/ai/up()` and `down()` (`ai.dm:1082` and `1086`) override `/mob/proc/up()` and `down()`. The base procs (`code/modules/mob/mob_movement.dm:534` and following) have a branch `if(remote_control) return remote_control.relaymove(src, UP)`. The AI overrides skip it and always call `eyeobj.zMove()`, so the camera moves instead of the mech.

## Fix

Three commits, one per defect:

- **Fix issue 87425: core-less AI ejecting from a mech is no longer half-ejected.** Adds an early return at the top of the AI branch of `mob_exit()`: `if(!forced && !AI.linked_core)` it sends the "Inactive core destroyed. Unable to return." message (unless `silent`) and returns FALSE, before changing any state. The AI keeps `remote_control`, `controlled_equipment`, `SILICON_PILOT` and its eye in the mech, so it stays a working occupant. Forced exits (mech destroyed, shunt) are unchanged. An alternative would be to let a core-less AI leave without a core (for example by killing it or moving it to a hacked APC). That would change the intended behaviour, so it was not done.
- **Fix issue 55695: AI beacon control no longer enters an occupied mech.** In the `AI_MECH_HACK` branch, before the core is created: `if(!AI.can_dominate_mechs && LAZYLEN(occupants) >= max_occupants)`, warn "Unable to take control of [mech]: it is currently occupied." and return. Malf AIs that can dominate mechs still eject the current occupants. The check is done before `create_core_link`, so a refused takeover leaves no stray core. The commit message says it also fixes #85136, and no separate change was needed.
- **Fix issue 93134: AI controlling a mech moves the mech up/down, not its camera.** `up()` and `down()` in `ai.dm` return `..()` when `remote_control` is set, which relays the move to the mech through the base procs. Without a mech the camera still moves.

## Verification

After rebuilding, on a fresh round on the test server (still using direct proc calls, as in Reproduction):

- Pilot inside the mech plus two beacon AIs: `occupants` stayed 1, the pilot was still inside, and neither AI had `remote_control` or `linked_core`.
- Empty mech, AI1 took control, AI2 tried: `occupants` 1, one driver, AI2 refused and given no core.
- `ai.up()` while controlling the Durand: `cooldown_vehicle_move` went from 0 to 674, meaning the mech received the move (a turn sound was heard).
- Core destroyed, then unforced `mob_exit(ai, silent)` and `container_resist_act`: `occupants` stayed 1, `remote_control`, `controlled_equipment` and `SILICON_PILOT` were kept, the eye was still in the mech, and `runtime.log` had no runtime.
- Normal exit with a core: the AI left the mech, ended up on the core's turf and the link was resolved. A forced exit of a core-less AI still gibbed it (robot debris), as before.
- No runtimes related to the changes appeared.

Not checked:
- #93134 on a real multi-z map. Only the cooldown on the mech was checked, not an actual z-move.
- The `ai_take_control` Topic path and the real "take control" link from an AI client. `transfer_ai` was called directly. The camera-visibility check is untouched.
- The #55695 scenario where a human is mid-entry when the AI takes control.
- Malf (`can_dominate_mechs`) takeover of an occupied mech after the change. The code path is unchanged.

## Notes

- For #87425, the player-visible behaviour after the fix is "core destroyed means the AI is trapped in the mech, with full control, until the mech is destroyed or the AI shunts". The old behaviour for callers that eject unforced was a broken half-state. The maintainers may prefer a different rule, such as destroying the empty core killing the AI, giving the AI a way to leave, or re-creating a core on ejection. That is a design decision this fix does not make.
- Generic callers of an unforced `mob_exit` (for example `dump_mobs`) now fail to remove a core-less AI, so any code that relies on emptying the mech will leave this AI inside. Before the change the same callers removed its control but also left it inside.
- The occupancy check is a plain length comparison on `occupants`. It blocks both an AI joining a piloted mech and a second AI joining an AI-occupied mech.
- The #85136 reporter's comment that intelicard extraction said "No AI detected in the mech's onboard computer" was not examined.
