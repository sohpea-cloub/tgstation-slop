| Issues | [#63890](https://github.com/tgstation/tgstation/issues/63890): not reproduced (already fixed on master by an earlier refactor of `dummy.dm`) |

## Summary

The issue (January 2022) says that deleting a human dummy called `dropped()` twice on each item it held: once from the dummy's own cleanup code and once from the item's `Destroy()`. This produced runtimes, for example from the ninja's energy katana, which removes its jaunt action in `dropped()`. On master the dummy's `Destroy()` no longer touches its equipment at all, and the equipment cleanup (`delete_equipment`) removes each item exactly once. In game, the drop signal fired once when a dummy was wiped and zero times when it was deleted, with no runtimes. No fix is needed.

## The bug

As reported against the code at commit `366ac218`: `dummy.dm` called `dropped()` on the dummy's items at two places a few lines apart, and `obj/item/Destroy()` also removes an item from its owner's inventory with `temporarilyRemoveItemFromInventory`, which ends in a third `dropped()` path. For most items a second call is harmless. For `/obj/item/energy_katana`, `dropped()` calls `jaunt.Remove(user)` if the jaunt action is not deleted (`code/modules/antagonists/space_ninja/equipment/energy_katana.dm:61-64`), so a second call after the action was already removed or deleted can runtime.

## Reproduction

The bug could not be reproduced on master. Test, using the Lua editor on the test server:

1. Spawned `/mob/living/carbon/human/dummy`, spawned an `/obj/item/energy_katana`, and put it in the dummy's hands.
2. Registered a Lua callback on the katana's `COMSIG_ITEM_DROPPED` (`item_drop`) signal to count how often `dropped()` ran.
3. Case 1: called `dummy.wipe_state()`, which runs `delete_equipment()`. The counter ended at 1.
4. Case 2: repeated with a fresh dummy and katana and called `qdel(dummy)`. The counter ended at 0.
5. Read the round's runtime log afterwards.

Observed: counts of 1 and 0 as above, and no runtime errors in the log (0 matches for "runtime error"). The ninja's jaunt action itself was not exercised, so the original symptom (the katana runtiming) was not tried directly.

## Cause

There is no defect on master. The code that the issue pointed at has changed:

- `/mob/living/carbon/human/dummy/Destroy()` (`code/modules/mob/living/carbon/human/dummy.dm:15-17`) only resets `in_use` and calls the parent. It no longer calls `dropped()` or removes equipment.
- `delete_equipment()` (`dummy.dm:47-72`) is used by `wipe_state()` and recycling. For each item that has nothing inside it, it calls `temporarilyRemoveItemFromInventory(checking, TRUE)` once if the item is on a mob (`dummy.dm:66-68`), which triggers `dropped()` once, then hands the item to `SSwardrobe.recycle_object` (`dummy.dm:69`), which either stashes it or deletes it. Items that contain other items are queued and `qdel`'d at the end (`dummy.dm:71-72`).
- After the first removal, the item's location is no longer a mob, so `obj/item/Destroy()` (`code/game/objects/items.dm:276-282`) does not call `temporarilyRemoveItemFromInventory` a second time.

When the dummy itself is deleted with `qdel`, the held katana did not receive a drop signal in the test (count 0). The reason was not traced; the observation is that no double call happens in either path.

## Fix

None. An earlier refactor of the dummy's equipment handling removed the problem. The exact upstream change that removed the double call was not identified. An upstream PR that mentions this issue (#65638) is closed and is not the reason the code is fixed now.

## Verification

Checked in game: the drop signal count (1 for `wipe_state()`, 0 for `qdel`) with an energy katana held by a dummy, and the absence of runtimes in the round's log.

Not checked:
- The ninja's jaunt action (granting, using and removing it) on a dummy.
- Other items whose `dropped()` is sensitive to being called twice.
- Dummies that hold items with contents, or that wear equipment in every slot.
- A direct comparison with the old code from January 2022.

## Notes

- The issue can be closed as already fixed.
- `delete_equipment()` still has a different shape from the old code (the comment at `dummy.dm:45-46` describes the wardrobe recycling), so any future double-call regression would need to come from a new call site, not from `Destroy()`.
