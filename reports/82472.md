The two issues were handled together because both are in the shuttle code and were tested with the same shuttle (the labor camp shuttle).

## Summary

**#82472:** When a shuttle that is controlled by a console is already in flight, sending it to the other destination calls `setTimer()` with the full flight time, so every swap restarts the trip. Repeating the swap keeps the shuttle in transit. The fix changes the destination without touching the timer. Only consoles that allow swapping the destination mid-flight are affected, which in practice means the labor camp shuttle console; the mining consoles already refuse the order.

**#72052:** Every time a shuttle leaves a transit dock, `initiate_docking()` created a new, empty "Hyperspace" area that nothing ever deleted, and destroyed transit docks also left their own Hyperspace area behind. The area list grew with every trip. The fix reuses the transit dock's area on departure, and a destroyed transit dock now deletes its area.

## #82472: Shuttle Transit Purgatory

### The bug

The reporter said that a shuttle driven by a console (they named the mining, public mining and gulag shuttles) can be kept in the middle of deep space, with its passengers, for as long as the depart button is pressed repeatedly after launch.

What happens is narrower. On consoles that allow it, pressing the button for the other destination while the shuttle is flying redirects the shuttle and resets its remaining flight time to the full value. Each press while in flight therefore pushes the arrival back.

### Reproduction

Done on master with admin tools, as an observer, using the Lua editor. The console's `send_shuttle()` proc was called from Lua in place of clicking the depart button in the UI, so the console's own checks ran but the tgui layer was not exercised.

1. Start a round and open the Lua editor.
2. Mining shuttle check: on the lavaland (common mining) console (`/obj/machinery/computer/shuttle/mining/common`), call `send_shuttle()` for the away dock. The shuttle went through `igniting` to `called`. Calling `send_shuttle()` again while it was in flight returned `intransit` and nothing changed. The mining consoles set `no_destination_swap = TRUE` (`code/modules/mining/mine_items.dm:98`), so this part of the report did not reproduce.
3. Labor shuttle check: take the labor shuttle console (`/obj/machinery/computer/shuttle/labor`, exactly that type), clear its `req_access` so the check passes, and send the shuttle to one of its two docks. Log `mode` and `timeLeft(1)` every tick with Lua timers. The shuttle spends about 5.5 s igniting (`ignitionTime` 55) and then 10 s in the `called` phase (`callTime` 100).
4. While the shuttle is in the `called` phase, call `send_shuttle()` again with the other labor camp dock (`laborcamp_home` / `laborcamp_away`).

Observed on master: the order was accepted (`success`) and the timer jumped back to 100 deciseconds: the log read `called/81`, then after the swap `called/100`, and again `called/100` after a second swap. A swap during the `igniting` phase is not possible, because the other dock is the one the shuttle is docked at and is not offered as a destination.

### Cause

`/obj/docking_port/mobile/proc/request()` in `code/modules/shuttle/mobile_port/mobile_port.dm:292` handles an order for a shuttle that is already in `SHUTTLE_CALL` mode (`:304`). If the order names the destination it already has, the timer is only raised if needed. If it names a different destination, the branch at `:308-310` does:

```dm
else
	destination = destination_port
	setTimer(callTime * engine_coeff)
```

so the whole trip starts over. The console lets this happen: `get_valid_destinations()` (`code/modules/shuttle/shuttle_consoles/shuttle_console.dm:~125`) only excludes the current destination, and `send_shuttle()` only blocks orders during flight when the console sets `no_destination_swap` (`shuttle_console.dm:159`). The mining and monastery consoles set that flag; the labor shuttle console (`code/modules/mining/laborcamp/laborshuttle.dm`) does not. The one-way prisoner console offers a single destination, so from the code it has no second destination to swap to (not tested).

### Fix

Commit "Fix issue 82472: swapping a console shuttle's destination mid-flight no longer restarts its trip" changes the different-destination branch in `request()`: it calls `remove_ripples()` and sets `destination = destination_port`, and no longer calls `setTimer()`. The shuttle therefore keeps its remaining flight time and lands at the new destination when the original timer runs out.

`remove_ripples()` is there because the landing ripples are drawn at the old destination once the shuttle is near the end of its flight; `check_effects()` makes new ones for the new destination.

Alternatives not taken: setting `no_destination_swap` on the labor console (this removes a feature on that console, and other consoles and shuttle controllers calling `request()` would still restart the timer), or refusing the order in `request()`. The `SHUTTLE_RECALL` branch was left alone, since it is only reachable through `cancel()`.

### Verification

On the test server with the fixed build, the same labor shuttle trip was repeated with two destination swaps. The remaining time in deciseconds went `called/93`, 83, 73, swap to `laborcamp_home` (success), 63, 53, 43, 33, swap to `laborcamp_away` (success), 23, 13, 3, `idle`. The timer kept counting down across both swaps and the shuttle arrived. Before the fix it was reset to 100 at each swap.

Not checked: the ripples at the new destination; a swap issued from the real console UI by a player; other callers of `request()` (shuttle calls from other code such as the emergency shuttle); whether the shuttle arrives at the swapped destination with passengers intact (it arrived, but no passengers were aboard).

## #72052: There are over 100 separate hyperspaces

### The bug

In a long round the reporter saw well over a hundred areas named "Hyperspace" in the area list (147 at the end of the round), and new ones kept appearing within a minute. They did not know whether this was intended. Commenters explained that transit space is created as shuttles move; one maintainer noted it was also true on master and had never been fixed.

Transit space is meant to be reused, with a handful of "Hyperspace" areas (one per shuttle that has a transit dock). The area count should therefore stay roughly constant, but it grew by one per trip.

### Reproduction

Done on master with admin tools and the Lua editor, as an observer, using the labor camp shuttle. Hyperspace areas were counted by iterating `GLOB.areas` and comparing names.

1. Start a round, open the Lua editor, and take the labor shuttle console as in the #82472 steps.
2. Count the areas named "Hyperspace", and list for each its type, whether a transit dock owns it (`assigned_area`) and how many turfs it holds.
3. After a trip, the list contained the arrivals shuttle's transit area (1734 turfs), the labor shuttle's transit area (1518 turfs) and a further `/area/shuttle/transit` with 0 turfs that no dock owns.
4. Send the shuttle on more trips. The count grew by one per trip. In a loop that sent the shuttle three times and destroyed the labor transit dock after each arrival, the count after each arrival was 3, 4 and 5, and after destroying the dock 2, 3 and 4. The extra empty areas were never removed.

This run was done with the first of the two fixes below already applied, which is why the dock's own area disappeared when the dock was destroyed (3 to 2, 4 to 3, 5 to 4); the empty area left behind by each arrival was still the leak that remained.

### Cause

There are two leaks.

1. **A new empty area on every departure from transit.** In `initiate_docking()` (`code/modules/shuttle/mobile_port/shuttle_move.dm`), the area used for shuttle turfs that have no area underneath is the dock's `area_type` when the shuttle is docked (`:21-24`): for a transit dock that is `/area/shuttle/transit` (`stationary_port.dm`: `area_type` taken from the dock's own area at creation). The code then looks it up in `GLOB.areas_by_type` and creates one if it is missing (`:36-40`). That list only holds areas flagged `UNIQUE_AREA` (`code/game/area/areas.dm:179`), and transit areas are not unique, so the lookup always fails and a new empty `/area/shuttle/transit` (named "Hyperspace") is created every time a shuttle leaves a transit dock. It is registered in `GLOB.areas`, is owned by no dock, and nothing deletes it.
2. **A transit dock's area is not deleted with the dock.** `SSshuttle.generate_transit_dock()` (`code/controllers/subsystem/shuttle.dm:~749`) creates the area together with the dock and stores it in `assigned_area`. `/obj/docking_port/stationary/transit/Destroy()` (`code/modules/shuttle/stationary_port/port_types.dm:~55`) qdels the turf reservation but leaves `assigned_area` alone, and the shuttle subsystem destroys idle transit docks (`shuttle.dm:~215`) and creates new ones the next time they are needed. Each such cycle leaves one more "Hyperspace" area.

### Fix

Two commits:

- "Fix issue 72052: a destroyed transit dock now deletes its Hyperspace area" adds `QDEL_NULL(assigned_area)` to the transit dock's `Destroy()` (inside the `force` branch, after the reservation is released).
- "Fix issue 72052: leaving a transit dock no longer makes a new empty Hyperspace area every trip" moves the fallback-area setup in `initiate_docking()` to just before the shuttle takes off. If the old dock is a transit dock and has a live `assigned_area`, that area is used as the fallback. Otherwise a new area is created as before, flagged as created by this call, and after `cleanup_runway()` it is deleted again if it ended up with no contents.

The two commits were meant to be one, but an attempt to squash them was blocked in the test environment, so they stay separate.

### Verification

The fixed build was started and the labor console was driven through four consecutive trips (home, away, home, away), after one earlier trip. The count of "Hyperspace" areas was 2 at the start and 2 after each of the four arrivals (the arrivals transit area and the labor transit area, created on first use). The two remaining areas had contents (1734 and 1518 turfs), and none was empty. The labor console's area after the trips was "Labor Camp Shuttle", so the shuttle's turfs were in the right area. Separately, qdel-ing a transit dock lowered the Hyperspace count by one. The runtime log showed one new runtime, caused by an invalid proc call made from the Lua test script itself, and none from the shuttle code.

Not checked: the emergency shuttle, escape pods, the cargo shuttle and other shuttles with transit docks; shuttles that use a shuttle-specific fallback area (for example those flying between docks inside a shuttle area); lighting or atmosphere effects of reusing the transit area as the underlying area; the unit tests (including `mapload_space_verification`, which refers to the transit area type); a whole-round count.

## Notes

- The #82472 report named the mining shuttle, but the mining consoles already return "in transit" when used mid-flight. In the tests, only the labor shuttle console allowed the restart. If the reporter really did this on a mining shuttle, it was either through a console without `no_destination_swap` or through a different path that was not found; this is unexplained.
- The labor console is normally locked to brig access; in the tests its `req_access` was cleared so the order could be sent by an observer.
- `request()` restarting the timer for a different destination is the only place found that does this for ordered redirects. The same file's `SHUTTLE_RECALL` branch (`:311-316`) also calls `setTimer(callTime * engine_coeff)` for a different destination; it is only reached from `cancel()` and was not changed or tested.
- The first #72052 fix (area deleted with the dock) is a smaller leak than the second; the second accounts for the "one more per trip" growth the reporter saw. The first is still a real leak whenever the shuttle subsystem reclaims an idle transit dock.
