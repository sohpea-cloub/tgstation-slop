# #94772: Runtime from being drunk if mood is config disabled

| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The report said that with `DISABLE_HUMAN_MOOD` enabled, humans have no mood datum and getting drunk spams runtimes from code that reads `mob_mood` without a null check. On the tested master that config option no longer exists, and every human gets a mood datum, so the failing condition cannot occur. The investigation found two upstream PRs, #97752 (removes the "disable mood" config) and #97753 (gives dummy humans a mood datum), that account for this. Their merge status came from a search by issue number and was not re-checked against the PRs themselves. Drinking a normal human and a dummy human to a high drunk level on the test server produced no runtimes.

## The bug

As reported: with the mood system disabled in `game_options.txt`, a character who gets drunk triggers a flood of runtimes because code reaches into a mood datum that was never created. The reporter noted that any place reading `mob_mood` without a `?.` or other guard could fail the same way, giving `code/modules/antagonists/wizard/equipment/artefact.dm` as an example, and described the configuration as "pretty unsupported".

## Reproduction

Not reproducible on this master, because there is no longer a way to turn mood off.

1. Searched the whole tree (code and config files) for `DISABLE_HUMAN_MOOD` and `disable_human_mood`: no hits in code or in `game_options.txt`.
2. On the test server, using the Lua editor, spawned a `/mob/living/carbon/human` and a `/mob/living/carbon/human/dummy` and called `set_drunk_effect(80)` on each.
3. Read back `mob_mood` on both: `/datum/mood` on the human and `/datum/mood/dummy` on the dummy. The human's mood level was 6.
4. Waited about 40 seconds. The drunk effects ran (the human vomited), and the round's `runtime.log` contained only boot-time lines: no mood-related runtime and no runtime at all from the drunk effect.

## Cause

Historic only. The config option let mob setup skip creating `mob_mood`, so any code that read `mob_mood` unguarded runtimed on a null value while drunk.

On master, `/mob/living/carbon/human/proc/setup_mood()` (`code/modules/mob/living/carbon/human/human.dm:43-44`) always does `mob_mood = new /datum/mood(src)`, and `/mob/living/carbon/human/dummy/setup_mood()` (`human.dm:49-50`) creates a `/datum/mood/dummy` (`code/datums/mood.dm:693`). `setup_mood()` is called unconditionally from human initialization (`human.dm:7`). Unguarded reads such as `jedi.mob_mood.sanity` in `artefact.dm:144` are therefore safe for humans.

## Fix

None was needed or made.

## Verification

- Confirmed in game on master `87b93338` that a normal human and a dummy human both have a mood datum and can be made drunk without any runtime (see Reproduction).
- Not checked: the exact contents of PRs #97752 and #97753 were not read here, so the claim that they are what removed the config and added the dummy mood datum rests on the PR search described above. The earlier state of the tree (with the config present) was not built or tested, so the original runtime was not observed.
- Not checked: non-human mobs that read `mob_mood`, or other code paths that read it.

## Notes

- The reporter's broader point (unguarded `mob_mood` reads) matters only if a mob type other than human can lack a mood datum. That was not examined.
- If a downstream codebase still has the `DISABLE_HUMAN_MOOD` config, this runtime can still occur there. The `?.` guards the reporter suggested would be the downstream mitigation.
