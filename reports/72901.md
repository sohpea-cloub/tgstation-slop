# #72901: Ventcrawl trait is not kept in sync when a mob is forcemoved into or out of pipes

| | |
|---|---|
| Issues | [#72901](https://github.com/tgstation/tgstation/issues/72901) fixed (verified in game); [#62448](https://github.com/tgstation/tgstation/issues/62448) fixed, same cause (verified in game) |
| Status | Fixed, one commit, verified on the test server |
| Fix branch | [fix/72901](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/72901) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

`TRAIT_MOVE_VENTCRAWLING` (which gives a mob the `VENTCRAWLING` movement type) is only added and removed by the ventcrawling procs themselves. Anything else that moves a mob into or out of a pipe (`forceMove`, teleporting, a shapeshift back to humanoid form) leaves the trait wrong: a mob teleported out of the pipes keeps it (#72901), and a mob forcemoved into a vent never gets it (#62448). The fix makes the pipe machinery itself add the trait when a mob enters crawlable atmos machinery and remove it when the mob leaves to anywhere that is not another pipe. It also fixes a null `hud_used` runtime in `update_pipe_vision` that the new removal path exposed.

## The bug

### #72901

A ventcrawling mob that is moved out of the pipes by anything other than leaving through a vent (the issue mentions wizards teleporting and bluespace crystals) keeps `TRAIT_MOVE_VENTCRAWLING` and the `VENTCRAWLING` movement type while standing on a normal floor.

### #62448

A mob that is moved into a vent with `forceMove` (the original case was a vampire turning from bat form back to human inside a vent) does not get the trait, so its movement type stays ground-based. Since the code for climbing out of a vent requires the trait, the mob is stuck inside the pipes. The 2021 comments debate whether shapeshifting into a form that cannot ventcrawl should gib the mob, but the reporter notes the missing movement type is the reason that does not happen.

## Reproduction

All of this was done with the Lua editor on the test server while observing; no one played the scenario with normal controls.

1. Start the round, open the Lua editor, and find a vent pump (`/obj/machinery/atmospherics/components/unary/vent_pump`).
2. Spawn a monkey (`/mob/living/carbon/human/species/monkey`) on the vent's tile.
3. Entering by `forceMove` (#62448): call `monkey:forceMove(vent)` and read the monkey's `TRAIT_MOVE_VENTCRAWLING` and `movement_type`. On master: trait absent, `movement_type` 1 (ground), while the monkey's loc is the vent pump.
4. Leaving by `forceMove` (#72901): spawn a second monkey, call `move_into_vent(vent)` (the proc used by the normal alt-click flow), then `forceMove` it back to the floor tile. On master: after `move_into_vent` the trait is present and `movement_type` is 5; after the `forceMove` out, the trait is still present and `movement_type` is still 5 on the floor.

The normal alt-click ventcrawl flow itself (it sleeps in `do_after`) could not be driven from Lua and was not exercised.

## Cause

`move_into_vent` (`code/modules/mob/living/ventcrawling.dm:121-124`) adds the trait with `ADD_TRAIT(src, TRAIT_MOVE_VENTCRAWLING, VENTCRAWLING_TRAIT)` after its `forceMove`, and `handle_ventcrawl` removes it when climbing out (`ventcrawling.dm:85-87`). Nothing else touches the trait. The pipe machinery only had an `Entered` handler (`code/modules/atmospherics/machinery/atmosmachinery.dm:566-570`), which sets `ventcrawl_layer` on the arriving mob, and had no `Exited` at all. So any movement into the pipes that does not go through `move_into_vent` produces no trait (#62448), and any movement out of them that does not go through `handle_ventcrawl` leaves the trait set (#72901). The movement type follows the trait through the `movement_type_trait_to_flag` mapping (`code/_globalvars/traits/_traits.dm:908`), so both symptoms show up as a wrong `movement_type`.

## Fix

One commit, "Fix issues 72901, 62448: sync ventcrawl trait when a mob enters or leaves pipes by any means":

- `/obj/machinery/atmospherics/Entered` now adds `TRAIT_MOVE_VENTCRAWLING` (source `VENTCRAWLING_TRAIT`) to a living arrival if the machinery has `VENTCRAWL_ALLOWED` in its `vent_movement`, and calls `update_pipe_vision()`. It is skipped if the trait from that source is already there. Machinery without that flag (for example thermomachines, whose `vent_movement` has no ventcrawl flags) does not give the trait, and cryo cells are not atmos machinery subtypes.
- A new `/obj/machinery/atmospherics/Exited` removes the trait (and calls `update_pipe_vision()`) from a living mob unless its new location is another `/obj/machinery/atmospherics`. Moving from pipe to pipe therefore keeps the trait; moving to a turf, a different container, or being qdeleted/gibbed removes it.
- `update_pipe_vision` now uses `hud_used?.get_true_plane_masters(...)` in the branch where there is nothing to show. This was found while testing: a mob gibbed inside a vent has no HUD, and the new `Exited` calls `update_pipe_vision`, which hit "Cannot execute null.get_true_plane_masters()" at `ventcrawling.dm:144`.

The existing explicit add/remove in `move_into_vent` and `handle_ventcrawl` were left alone; they are now redundant but harmless. Syncing the trait in the pipe machinery rather than patching each caller (teleport, shapeshift, etc.) was chosen because every caller goes through `Entered` and `Exited`.

## Verification

On the test server, with Lua, after the fix:

- `forceMove` into the vent: trait present, `movement_type` 5.
- `forceMove` back out to the floor: trait absent, `movement_type` 1.
- `move_into_vent`, then `forceMove` to another pipe (a hidden supply manifold in the same network): trait still present, `movement_type` 5, loc is the pipe; `forceMove` out of that: trait absent, `movement_type` 1.
- Gibbing a monkey inside a vent: no runtime. (The first fixed build, without the `hud_used?` change, did produce the runtime listed above.)
- A monkey controlled by the observing admin's client: `forceMove` into the vent gave 47 entries in `pipes_shown` and the trait; `forceMove` out gave 0 entries and no trait.

Not checked:

- The real alt-click flow with its `do_after` (its code is unchanged except for the now-redundant explicit calls).
- The vampire bat-form case from #62448, wizard teleporting, bluespace crystals, or shapeshifting. Only direct `forceMove` was used.
- A mob that cannot ventcrawl (it has neither `TRAIT_VENTCRAWLER_NUDE` nor `TRAIT_VENTCRAWLER_ALWAYS`) forcemoved into a vent: by reading the code it now gets the trait, but `handle_ventcrawl` still refuses to let it out because `can_enter_vent` requires one of those traits (`ventcrawling.dm:25`). This was not tested in game. Such a mob is still stuck, although it now has the correct movement type.

## Notes

- Any living mob entering crawlable machinery now gets the trait, not only creatures that normally ventcrawl. That is deliberate (a mob inside a pipe is ventcrawling whatever the cause), but a maintainer may prefer to restrict it.
- Code that relies on the trait, such as `code/datums/ai/basic_mobs/basic_ai_behaviors/ventcrawling.dm:150` (a `stack_trace` if a mob has left the vent and still has the trait), should benefit from the `Exited` cleanup. This was not tested.
- #62448 and #72901 are the same problem seen from the two directions, so one change fixes both.
