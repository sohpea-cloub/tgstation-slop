# #44349: Robot factory cyborgs are first linked to the wrong AI before being re-linked to the malf AI

| | |
|---|---|
| Issues | [#44349](https://github.com/tgstation/tgstation/issues/44349): verified (the wrong first link and the misleading notice); the final state the issue complains about was already correct on master and was not reproduced |
| Status | Fixed on the branch below |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/44349 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

A cyborg made by a robot factory placed by a malf AI is created with no master AI, so on creation it links to the AI with the fewest cyborgs, syncs its laws and photos to that AI, and the AI gets a "New cyborg connection detected" notice. Only afterwards does the factory re-link the cyborg to the malf AI. The final state is correct, but a second AI sees cyborgs appear in its list or hears about them, as the issue describes. The fix passes the factory's master AI into the cyborg's creation, so it links to the malf AI from the start.

## The bug

The reporter had a malf AI place a robot factory while a second AI was present. Some of the new cyborgs showed up as synced to the second AI and some to the malf AI, and the cyborgs that appeared synced to the second AI seemed to act as if they were. A 2019 comment on the issue found that all the cyborgs ended up with the malf AI as master (and the malf law 0), even when they showed in the other AI's status panel.

On master the panel problem is already gone: `set_connected_ai()` (`code/modules/mob/living/silicon/robot/robot.dm:994`) removes the cyborg from the old AI's `connected_robots` when it is re-linked. What is left is the transient link described below.

## Reproduction

The test used admin tools and did not use the malf AI's own factory ability (see Verification).

1. Using the Lua editor, create two AIs (by calling `AIize` on two spawned humans) and rename them, for example "AI-MALF" and "AI-OTHER".
2. Spawn an `/obj/machinery/transformer` (the robot factory), set its `master_ai` variable to AI-MALF and set `cooldown_duration` to 10 so it can be reused quickly.
3. Spawn a human in front of the factory and call `do_transform` on it. Repeat with fresh humans.
4. Read the silicon log. On master it showed:

   ```
   New cyborg (Default Cyborg-611) created with master AI: (AI)
   New cyborg (Default Cyborg-824) created with master AI: (AI-OTHER)
   (Default Cyborg-824) resynced to (AI-MALF)
   New cyborg (Default Cyborg-865) created with master AI: (AI-OTHER)
   (Default Cyborg-865) resynced to (AI-MALF)
   ```

   The first cyborg was created with the first AI as master, which in that run was the malf AI (a tie in cyborg count). Later cyborgs were created linked to AI-OTHER, which had fewer cyborgs, and then "resynced" to AI-MALF.
5. Afterwards AI-MALF had all the cyborgs and AI-OTHER had none, so the final state was consistent, as the 2019 comment reported. During creation, though, the cyborg was bound to AI-OTHER: its laws and camera photos were synced to that AI and AI-OTHER received the "New cyborg connection detected" notice.

## Cause

`Robotize()` (`code/modules/mob/transform_procs.dm:135`) creates the cyborg through `transform_into_mob(/mob/living/silicon/robot, delete_items)` without a master AI. The cyborg's `Initialize` then calls `try_connect_to_ai(master_ai)` with a null master (`robot.dm:48`), which falls back to `select_active_ai_with_fewest_borgs()` (`robot.dm:963-966`). That path syncs laws and photos to the chosen AI. Still inside `Robotize()`, `new_borg.notify_ai(AI_NOTIFICATION_NEW_BORG)` (`transform_procs.dm:150`) then notifies that AI.

Only after `Robotize()` returns does `/obj/machinery/transformer/proc/do_transform` (`code/game/machinery/transformer.dm:106-110`) notice that `connected_ai != master_ai` and call `set_connected_ai(master_ai)`, `lawsync()` and set `lawupdate`. By then the wrong AI has already been linked and notified. The malf AI sets the factory's `master_ai` in `code/modules/antagonists/malf_ai/malf_ai_modules.dm:685` (`conveyor.master_ai = owner`).

## Fix

One commit, "Fix issue 44349: robot factory cyborgs are created already linked to the placing malf AI":

- `Robotize()` takes an optional `master_ai`. If it is set and not qdeleted, it is passed to the new cyborg's `Initialize` as an extra argument (`list(null, master_ai)`: `innate_laws`, then `master_ai`, after the mapload/loc argument).
- `transform_into_mob()` takes an optional `extra_args` list, appended to the new mob's `Initialize` arguments via `arglist()`. Other callers are unchanged.
- The transformer calls `victim.Robotize(master_ai = master_ai)`.

The transformer's old re-link block was left in place as a harmless fallback, for example if the master AI is deleted. A qdeleted `master_ai` is ignored and the old behaviour applies. The other caller of `Robotize()` (the cyborg job code) was not changed.

## Verification

After the fix the game was rebuilt and the same setup repeated, with the second AI possessed so its chat could be read. The first cyborg was already on AI-MALF, so AI-OTHER had fewer cyborgs and would have been picked by the old logic. The new cyborg's log line read `created with master AI: (AI-MALF)`, with no "resynced" line, AI-OTHER received no cyborg notice, and the counts were AI-MALF 2, AI-OTHER 0. No new runtimes appeared.

Not checked: a real malf AI placing the factory through its module (the factory's `master_ai` was set directly through Lua), and any player-controlled creation of cyborgs other than via the factory.

## Notes

- `unlock_new_robot` (`transformer.dm:113-118`) still sends the master AI a second "new cyborg" notice about 8 seconds later. That duplicate was already there and was left alone.
- The reporter's belief that some cyborgs acted for the second AI was not reproduced: on master the cyborgs always ended up on the malf AI, which matches the 2019 test in the issue comments. The transient link to the other AI (laws and photos synced, notice sent) is the only observable effect found.
- Related issues named in the issue's triage, all closed: #51682, #53330, #37467. No upstream PR was found that changes this: the two PRs looked at (#72532 on logging and #69091 on shapeshifting) do not touch it.
