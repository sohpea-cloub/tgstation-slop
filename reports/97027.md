## Summary

When a shuttle rotates while moving, `/atom/movable/shuttleRotate` re-places multi-tile atoms with a guess based on the new `dir` instead of rotating their bounds and icon offsets. The guess is right only for some rotations, so the huge/large shuttle engines end up with bounds in one place and the icon drawn in another (#97027). The same generic code turns the portable BSA, which only has west and east sprites and firing lines, to north or south, so it draws off to the side and fires at its own tile (#92839). The fix rotates the bounds and icon rectangle of multi-tile atoms around their `loc` tile and gives the BSA its own `shuttleRotate`. #39347 (sink/shower/urinal offsets) could not be reproduced and appears to have been fixed upstream by PR #67672.

## The bug

#97027 (Lance emergency shuttle on Runtime station, fast travel with the shuttle manipulator): "The engines at the back should appear irregularly offset". The reporter notes it is mainly visible with huge engines, applies to heretic runes too, and points at `shuttle_rotate_callbacks.dm`. The report says multi-tile objects are bound and placed by their bottom-left corner and that this corner is itself rotated when the shuttle moves, so the rotation code must account for it.

#92839 (portable BSA on a custom shuttle, facing right, shuttle rotated 90 degrees clockwise, then fired): the BSA "does not rotate with the shuttle, leaving it to weirdly stray off to the side and clip through objects" and "shoots itself". A commenter notes the BSA has no north/south variant and that a 180 degree turn may break it too.

#39347 (2018): sinks, toilets, showers and urinals on rotated shuttles end up with pixel offsets that push them into walls or into the middle of the room.

## Reproduction

All with admin tools (Lua editor and SDQL2 style reads of variables) on the test server, using the emergency shuttle on MetaStation. The shuttle was sent between docks with `SSshuttle.emergency:initiate_docking(dock)`, and state was read a few seconds later. Docks with different facings were used: the emergency "away" dock (east), the "home" dock (south) and an extra test dock facing west that was created with Lua. A huge engine (`/obj/machinery/power/shuttle_engine/huge`, 3x3), nine pens placed on its 3x3 footprint as markers, a BSA facing west, and a `directional/north` sink, shower and urinal were put on the shuttle with admin tools.

Baseline (unmodified master):

1. Dock at the east dock, then at the south dock (a 90 degree turn, "E to S"). The engine ended with `bound_x/y = 0,-64` and `pixel_x/y = 0,-64`, and no pens were outside the engine's footprint. This rotation happened to work. The BSA ended with `dir = NORTH`, `pixel = -32,192`, and `get_front_turf()` returned the BSA's own turf, i.e. it fires at itself (#92839).
2. Dock at the east dock again (the south to east turn, a 270 degree turn, "S to E"). The engine's bounds were `0,-64` while its icon offset was `64,0`: bounds and icon disagreed, and 6 of the 9 pens were outside the footprint. This reproduces #97027.

## Cause

`afterShuttleMove` calls `shuttleRotate(rotation, params = ALL)` on every moved atom after it has been moved to its rotated tile (`code/modules/shuttle/mobile_port/shuttle_move_callbacks.dm:134`). The base proc rotates `pixel_x`/`pixel_y` as if the atom were one tile (`code/modules/shuttle/mobile_port/shuttle_rotate_callbacks.dm:9-25`). `/atom/movable/shuttleRotate` then overwrites that for multi-tile atoms (`shuttle_rotate_callbacks.dm:30-40`):

```dm
if(((bound_height != ICON_SIZE_Y) || (bound_width != ICON_SIZE_X)) && (bound_x == 0) && (bound_y == 0))
	pixel_x = dir & (NORTH|EAST) ? -bound_width+ICON_SIZE_X : 0
	pixel_y = dir & (NORTH|WEST) ? -bound_width+ICON_SIZE_X : 0 //?
	bound_x = pixel_x
	bound_y = pixel_y
```

This ignores how far the shuttle actually rotated and picks offsets from the new `dir` alone. It uses `-bound_width + 32` for both axes (so non-square footprints are wrong), only touches the bounds when `bound_x` and `bound_y` are both 0, never swaps `bound_width` and `bound_height` on quarter turns, and sets the icon offset and the bounds to the same value. It is correct for some turns (S to W in the issue's diagram, and E to S in the test above) and wrong for others, which is why the engines look "irregularly offset". The reporter's description of a multi-tile atom's footprint hanging off its loc corner is exactly what the code should have modelled: after the loc has been moved to the rotated tile, the whole rectangle (bounds and icon) has to be rotated around that tile.

For the BSA (#92839), `/obj/machinery/bsa/full` only has west and east icons, and `get_front_turf()`, `get_back_turf()` and `get_target_turf()` only handle `WEST` and `EAST` (`code/modules/station_goals/bsa.dm:174-196`); for any other direction they return the BSA's own turf. The generic code turned it to `NORTH`/`SOUTH` and rotated its large pixel offsets, so it was drawn off to the side and fired at itself. Its `bound_x` is non-zero (-192 or -128), so the guess in the base code also did not apply to it.

## Fix

Two commits on the fix branch.

**"Fix issue 97027: rotate the bounds and icon offsets of multi-tile atoms when a shuttle rotates"** (`shuttle_rotate_callbacks.dm`). For an atom that has `ROTATE_OFFSET` set and a bound size other than 32x32, `/atom/movable/shuttleRotate` now clears `ROTATE_OFFSET` for the parent call (so the single-tile pixel rotation does not run) and then rotates, clockwise around the centre of the `loc` tile, both the physical bounds rectangle (`bound_x`, `bound_y`, `bound_width`, `bound_height`) and the icon rectangle (`pixel_x`, `pixel_y`, with the icon's width and height taken from `get_icon_dimensions(icon)` since some icons, like the engines, differ from the bounds). It handles 90, 180 and 270 degrees and swaps the bound width and height on quarter turns. Mobs, the gateway and the gravity generator pass parameters without `ROTATE_OFFSET`, so they are unaffected, and single-tile atoms take the old path (the formula is identical to the old pixel rotation for 32x32 icons).

This was chosen over patching the old guess because the old code could not be made right without knowing the rotation; the rotation amount is available in `shuttleRotate`, and rotating the rectangle is a direct statement of what should happen.

**"Fix issue 92839: the BSA no longer turns north/south or fires at itself on a rotating shuttle"** (`code/modules/station_goals/bsa.dm`). New `/obj/machinery/bsa/full/shuttleRotate`: a quarter turn keeps the BSA's direction, bounds and offsets (it cannot be shown or fire vertically); a half turn swaps west and east, setting `cannon_east`/`cannon_west`, the known offsets (-128 / -192 for `pixel_x` and `bound_x`) and recomputing the top overlay. True north/south support would need new sprites and firing logic.

## Verification

On the test server, same setup as the baseline. After the fix:

- E to S (90 degrees): engine `bound 0,-64`, `pixel 0,-64`, 0 pens outside the footprint. The BSA kept `dir = WEST` and `get_front_turf()` returned a tile 7 tiles away, not its own. The sink, shower and urinal ended with `dir EAST` and pixel offsets `-14,0` / `-16,0` / `32,0`, the same as their mapped `directional/east` variants.
- S to E (270 degrees): engine `bound 0,0`, `pixel 0,0`, occupying x 206-208, y 69-71, 0 pens outside. The fixtures went back to their north offsets.
- E to W (180 degrees): engine `dir NORTH`, `bound -64,-64`, `pixel -64,-64`, occupying x 204-206, y 174-176, 0 pens outside. The BSA turned to `dir EAST` with `icon_state cannon_east`, `bound_x -128`, `pixel -128,-32`, and a front turf 7 tiles to its east. The fixtures went to `dir SOUTH` with offsets `0,14` / `0,16` / `0,-32`.
- No new runtimes were logged (only start-up noise).

Not checked:
- Nothing was looked at in a real game client; results are from variable values and from where the pens fell relative to the bounds. Whether the engine's icon looks right on screen was inferred from `pixel_x/y` matching the bounds, not seen.
- The exact Lance emergency shuttle from the issue was not used for the final runs (the MetaStation emergency shuttle with a spawned huge engine was). The large (2x2) engine and non-square multi-tile atoms were not tested separately.
- Heretic runes (mentioned in #97027) were not tested. They should take the same path if their bounds exceed 32 pixels.
- A BSA turned by a quarter turn still stays horizontal while the shuttle is rotated, so it can clip through objects in that orientation (it no longer fires at itself).
- The fix assumes a rotated icon rectangle based on the icon file's frame size; a non-square, 4-direction icon was not examined.

## Notes

- #39347 (sink/toilet/shower/urinal offsets) was not reproduced. The fixtures now use the symmetric `MAPPING_DIRECTIONAL_HELPERS` offsets (`code/__DEFINES/directional.dm:32`), which upstream PR #67672 introduced, and they came out consistent with their mapped `east`/`south` counterparts after a rotation. The test fixtures were only read with the fix applied; this part of the code is not changed by the fix, so the result would be the same without it.
- #92839 is tracked as "same cause" as #97027 but needed its own change because the BSA has no north/south sprites at all. If sprites for those are ever added, the BSA override and the `get_*_turf` procs would need to be extended together.
- The old comments in the removed code mention that it was written so that the BSA and the gateway (which have non-zero `bound_x`/`bound_y`) are not shifted. With the new code the gateway and gravity generator are unaffected because they do not pass `ROTATE_OFFSET`; the BSA now has its own override.
- No upstream PR covering this was found (the closed #97212 is the closest).
