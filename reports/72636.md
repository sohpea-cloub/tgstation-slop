## Summary

#72636 reports that the Buildmode Copy tool also copies an object's `cached_ref`, so copies cannot be edited with View Variables and share state with the original. That variable is not present anywhere in master's `code/`, and copies made with `duplicate_object` are distinct datums, so this part is already gone. While checking it, a real defect in `duplicate_object` showed up that matches #44804: copied cables get the original cable's `linked_dirs`, so they claim links to cables that are not there, and they never get a powernet. The fix stops copying the cable link state and gives a copied cable a new powernet, merged with its neighbours, through a new `on_duplicated` hook.

## The bug

### #72636

Copying a VV'd item with the Buildmode Copy tool is reported to create an item with the same ref as the original: VV windows always target the original, copied projectile weapons start their firing effects on the original, and when a copied energy weapon's charge runs out, the original (fully charged) cannot be fired.

### #44804

Smart wires placed with Buildmode Copy are described as placed inconsistently compared to hand-laid wire, produce a piece of wire on every cut without being removed, and cannot be admin-deleted. A commenter noted that Copy copies every var of the source object, including references that should belong to a single object, so it cannot work for such objects. Another said the delete problem was fixed in 2019 but "the copy logic itself" probably remained broken.

## Reproduction

### #72636 (`cached_ref`)

Checked on master with the Lua editor and by searching the source:

1. A search of `code/` for `cached_ref` finds nothing; `tag` is in `GLOB.duplicate_forbidden_vars` (`code/__HELPERS/duplicating.dm:31`), and the loop in `duplicate_object` skips any var whose value is a datum (lines 77-78).
2. Spawned a crowbar and copied it with `duplicate_object`. The copy was a different object from the original (`original == copy` was false).

So the "same ref" symptom could not be produced on master. I could not tell from the inputs when or how `cached_ref` was removed. The energy gun charge and firing-effect claims were not tested directly (see Verification).

### #44804 (cable copies)

Using the Lua editor on a running round, on the station level:

1. Spawn three cables in a row on adjacent tiles (call them c1, c2, c3, left to right).
2. Call `duplicate_object(c2, <a tile far from any cable>)`.
3. Read `linked_dirs` of the copy.

Result on master: the copy's `linked_dirs` was 12 (east and west), the same as c2, even though it was on an isolated tile with no neighbours. A copy made next to c3 also got 12. The copy also had no powernet; comparing powernets with c2's gave "equal" only because both were empty (`nil`).

This reproduces the data defect behind #44804 (links to cables that do not exist, one-sided links, no powernet). The Buildmode Copy click itself (`code/modules/buildmode/submodes/copy.dm:21` calls `duplicate_object`), cutting copied wire with a wirecutter, and the admin delete were not tried in game.

## Cause

`duplicate_object` (`code/__HELPERS/duplicating.dm:64`) creates a new object of the same type and then assigns every var of the original except those in `GLOB.duplicate_forbidden_vars`. For a cable (`code/modules/power/cable.dm`):

- `Initialize` (line 50) calls `connect_cable()` (line 83), which works out `linked_dirs` from the cables actually next to it (and updates the neighbours' `linked_dirs`).
- `duplicate_object` then overwrites `linked_dirs` with the original's value. The copy claims links in directions where there is no cable, so links are one-sided (the copy points at cables that do not point back).
- `is_fully_initialized` is also copied, which is not meaningful for a new object.
- A powernet is only created when cable is laid with a cable coil (`code/modules/power/cable.dm`, around line 711, which creates a `/datum/powernet`, adds the cable and merges with adjacent networks). Nothing does that for a copy, so a copied cable has no powernet. Cable removal (`Destroy` and `disconnect_cable`) reads `linked_dirs` and `powernet`, so a copy with stale links and no powernet is a plausible source of the cutting and deleting problems in #44804, though that was not traced in game.

## Fix

One commit, "Fix issue 72636: buildmode copy of cables kept the original's linked_dirs and had no powernet" (it also covers #44804):

- `code/__HELPERS/duplicating.dm`: added `/obj/structure/cable::linked_dirs` and `/obj/structure/cable::is_fully_initialized` to `GLOB.duplicate_forbidden_vars`, so `Initialize` keeps the values it computed for the copy's own position.
- `code/__HELPERS/duplicating.dm`: added an empty `/atom/proc/on_duplicated(atom/original)`, called at the end of `duplicate_object` once the vars have been transferred.
- `code/modules/power/cable.dm`: `/obj/structure/cable/on_duplicated` creates a new powernet, adds the cable to it and merges it with adjacent cables' networks (`mergeConnectedNetworks` in each cardinal direction and `mergeConnectedNetworksOnTurf`), exactly as the cable coil does.

A hook was chosen rather than special-casing cables inside `duplicate_object`, so that other object types that need more than a var copy can use it. Other users of `duplicate_object` (admin "mark and copy" in `topic.dm`, the supply pod launcher) get the hook call too, but only cables implement it.

## Verification

On the test server, rebuilt with the fix, using the Lua editor:

- An isolated copy of c2 had `linked_dirs` of 0 (before: 12) and its own powernet, different from c2's.
- A copy placed at the end of the row next to c3 shared c3's powernet. `deconstruct()` on that copy removed it, and c3's `linked_dirs` dropped from 12 to 8, which is correct (its link to the removed copy was cleared).
- No new runtimes appeared in the runtime log.

Not checked: the real Buildmode Copy click path; cutting a copied cable with wirecutters or admin-deleting it in game; cables on other layers or under machines; the energy gun charge and firing-effect claims of #72636 (cells are datums and are skipped by `duplicate_object`, so they were expected to be fine, but this was not tested); VV on copies.

## Notes

- The fix handles only cables. #44804's commenter noted that other objects can also suffer from copying all vars; the forbidden-vars list is a patchwork ("grandfathered in" entries are noted in the file) and was not audited.
- #72636 can probably be closed as already fixed for its own claim, since `cached_ref` no longer exists, but this was not traced to a specific upstream change. #44804 remains partly open in the sense that the Buildmode click path was not exercised.
- No upstream pull request was identified for either issue.
