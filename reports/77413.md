## Summary

Three MODsuit issues were examined together. #94544 (the MOD flashdark module does nothing) was reproduced and fixed: the module used a black light colour with positive power, and a positive-power light is drawn with additive blending, so black adds nothing. The fix makes it a white light with power -1, which subtracts light. #77413 (a Syndicate MODsuit shows "insufficient access" with an agent ID) could not be reproduced on current master: the suit unlocked for a wearer holding an agent ID. #63822 (chameleon mutation vs. MOD cloaking module) was confirmed by reading the code only; it is a known limitation and has no fix.

## #77413: Syndicate MODsuit does not unlock with an agent ID

### The bug
The reporter (2023) held a Syndicate MODsuit and an agent ID. They could activate the suit, but the MODsuit UI's ID lock said "Insufficient access". A commenter said it affected every ID-locked MODsuit, including nuclear operatives' suits, when the interface was used.

### Reproduction
Not reproduced. What was done on the test server, using admin tools:

1. Spawned a human in a jumpsuit wearing a `/obj/item/mod/control/pre_equipped/nuclear` suit (`req_access` Syndicate) on the back, and gave them an agent ID (`/obj/item/card/id/advanced/chameleon`). Took control of the human.
2. Checked `suit.allowed(H)` for the wearer: it returned 1.
3. Opened the "MODsuit Panel" from the suit's HUD button and pressed the lock toggle. The lock went locked → unlocked → locked, with "locked"/"unlocked" floating text each time. It also worked while the suit was active.

The "access insufficent!" message did not appear in any of these runs.

### Cause (of the message)
The message is produced only when the lock is on and `allowed()` fails (`code/modules/mod/mod_ui.dm:94-98`):

```dm
if("lock")
	if(!locked || allowed(ui.user))
		locked = !locked
		balloon_alert(ui.user, "[locked ? "locked" : "unlocked"]")
	else
		balloon_alert(ui.user, "access insufficent!")
```

The agent ID's chameleon trim carries `ACCESS_SYNDICATE` (`code/datums/id_trim/syndicate.dm:86`), so with an agent ID that has its default trim the check passes. The text "Insufficient access" does not appear in the MODsuit tgui interface (`MODsuit.tsx`) either.

### Verification / not checked
Because nothing could be reproduced, there is no fix. Two explanations are plausible and were not told apart: the bug was fixed after the 2023 report, or the reporter's ID lacked Syndicate access (an early commenter suggested this, though the reporter doubted it). Not tried: an ID without Syndicate access (for example a regular crew ID), a nuclear operative's or infiltrator's spawn ID, and the exact UI flow with a real client rather than the lock action sent through admin tools.

## #63822: Chameleon mutation vs. MOD cloaking module

### The bug
The reporter said the chameleon mutation takes priority over the MOD cloaking module, so with the mutation the cloak module has no visible effect. A maintainer replied on the issue that it is unfixable without something like vgstation's alpha handling system.

### Reproduction
Not reproduced in game. The finding is from reading the code only, and no fix was attempted. The suggested test would be: give a human the chameleon mutation, activate a MOD cloak module, and watch the human's `alpha` in View Variables.

### Cause
Both features write the mob's `alpha` directly, with no shared system to combine them:

- Chameleon mutation (`code/datums/mutations/chameleon.dm`): sets `owner.alpha = CHAMELEON_MUTATION_DEFAULT_TRANSPARENCY` on movement and on attacking/clicking (lines 16, 42, 58), and lowers it in `on_life` (line 21).
- Cloak module (`code/modules/mod/modules/modules_antag.dm`): `animate(mod.wearer, alpha = stealth_alpha, ...)` on activation (line 536, `stealth_alpha = 30` at line 484) and `animate(..., alpha = 255, ...)` on deactivation (line 525).

Whichever wrote last wins, and the chameleon code rewrites alpha repeatedly, so it overrides the cloak.

### Notes
A real fix needs a layered alpha mechanism (several sources contributing, the result computed from them). That is a larger change than this unit covered.

## #94544: MOD flashdark module does nothing

### The bug
Installing a flashdark module on a MODsuit, deploying the helmet and turning the module on produced no darkness.

### Reproduction
1. On the test server, spawned a human in a jumpsuit wearing `/obj/item/mod/control/pre_equipped/nuclear` and took control of them with the Lua editor.
2. Uninstalled the stock MOD flashlight module (it is incompatible with the flashdark module) and installed `/obj/item/mod/module/flashlight/darkness`.
3. Deployed the helmet and activated the module (the module's `on_select()` was called from Lua).
4. Read `get_lumcount()` of the wearer's turf before and after.

Observed on master: `light_on` = 1, `light_power` = 1, `light_range` = 2, and the turf's lumcount went from 0.88 to 1.0, that is, brighter, with no darkness.

### Cause
The flashdark subtype only set `light_color = COLOR_BLACK` and inherited the flashlight's `light_power = 1` (`code/modules/mod/modules/modules_general.dm:419-504`). With the overlay light system, `set_power` picks the blend mode from the sign of the power (`code/modules/lighting/light_overlay.dm:210-217`):

```dm
visible_mask.blend_mode = new_power > 0 ? BLEND_ADD : BLEND_SUBTRACT
```

Positive power means `BLEND_ADD`, and adding black adds nothing. To get darkness the light must have negative power (subtracting) and a colour that subtracts something, so black is the wrong colour there too.

### Fix
One commit, "Fix issue 94544: MOD flashdark module now subtracts light", in `code/modules/mod/modules/modules_general.dm`:

- The darkness module now has `light_color = COLOR_WHITE` and `light_power = -1`, so it is drawn with `BLEND_SUBTRACT` (the commit message says this matches the flashdark item).
- A new variable `worn_light_color` on the flashlight module lets a subtype choose the colour of the worn "light on" overlay; `generate_worn_overlay` uses `worn_light_color || light_color`. The darkness module sets it to black so the indicator on the helmet still looks dark.
- The darkness module still removes the colour option from its configuration, as before.

### Verification
On the test server with the fix built: a nuclear MODsuit worn by a spawned human, stock flashlight replaced by the flashdark module, module activated. The wearer's turf lumcount went from 0.883 to 0.383 (it had gone 0.88 → 1.0 with the old code). `light_on` = 1, `light_power` = -1, `light_range` = 2, and the worn overlay was `module_light_on` with colour `#000000`.

Not checked: only the module's activation proc was called directly, and the suit parts were not fully "active" in the test, so the normal path of activating the whole suit and then the module from the HUD was not exercised. No client-side screenshot was compared, and the module's range configuration (min/max range) was not tested after the change.

### Notes
- A Lua `install()` call with a force argument produced a `balloon_alert` runtime ("Cannot read 1.client") during testing; this came from how it was called from Lua, not from the game.
- A commenter on #94544 wondered whether a separate report (#92431) about darkness effects on mob lighting is related; that was not investigated.
