# #97231: do_afters that should hide their cogbar show it

| | |

| Issues | [#97231](https://github.com/tgstation/tgstation/issues/97231): verified |
| Status | Verified, fixed |
| Fix branch | [fix/97231](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/97231) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

PR #97018 replaced the `hidden` argument of `do_after()` with `cog_icon = null`. `do_after()` declares a default value for `cog_icon`, and DM substitutes the default when a caller passes an explicit `null` for an argument that has one. So the null never reached the check that suppresses the cogbar, and every do_after meant to be invisible displayed the cog. The fix adds a `COGBAR_HIDDEN` define (`FALSE`), uses it in all 49 `cog_icon = null` callers and in `start_unequip_mob()`, and makes the cogbar check test truthiness instead of `isnull()`.

## The bug

Actions that are meant to run without the cog over the user's head (the issue's example is shoving someone) show the cog anyway. The same applies to every other caller converted by #97018, for example resisting out of handcuffs.

## Reproduction

1. On the test server, start the round and join as an Assistant.
2. Using the Lua editor, create a pair of handcuffs and apply them to your own mob (`set_handcuffed`, then `update_handcuffed`).
3. Click the "Handcuffed" alert on the HUD. This runs the resist from `code/modules/mob/living/carbon/carbon.dm:219`, a one-minute `do_after(..., cog_icon = null, ...)`.
4. While the resist is in progress, run the SDQL2 query `SELECT /datum/cogbar WHERE user.client != null`.

Observed on master: one `/datum/cogbar` owned by the player's mob, so the cog is shown during a do_after that asks to hide it. This went through the player action (the alert click), not a direct proc call. The shove from the issue was not tried; the resist path uses the same mechanism.

## Cause

`do_after()` is declared at `code/datums/timed_actions.dm:211` with `cog_icon = 'icons/effects/progressbar.dmi'` as its default. In DM an argument passed as `null` is replaced by the parameter's default, even when `null` is passed explicitly. Callers writing `cog_icon = null` therefore always forwarded the progressbar icon to `/datum/timed_action/New()`. There, `code/datums/timed_actions.dm:40` creates the cogbar when `!isnull(cog_icon) && delay >= 1 SECONDS`, which was always true. `start_unequip_mob()` in `code/datums/elements/strippable.dm:313` used the same pattern (`hidden ? null : ...`) and was affected the same way.

## Fix

One commit, "Fix issue 97231: do_afters meant to hide their cogbar show it again":

- Adds `#define COGBAR_HIDDEN FALSE` to `code/__DEFINES/do_afters.dm`, with a comment explaining why it is not `null`.
- Replaces every `cog_icon = null` with `cog_icon = COGBAR_HIDDEN` (49 occurrences on master, 33 files changed in total), including `strippable.dm`.
- Changes the check in `/datum/timed_action/New()` to `if(cog_icon && delay >= 1 SECONDS)`. `FALSE` is not null, so it survives the call and now suppresses the cogbar. The default of `New()`'s own `cog_icon` is also set to `COGBAR_HIDDEN`, and the `do_after()` doc comment mentions the define.

A define was chosen over changing the default parameter of `do_after()` to `null`, which would have hidden the cog from every caller that relies on the default.

## Verification

After rebuilding, the same handcuff resist was repeated and the same SDQL2 query returned 0 cogbars (before: 1). Getting up from resting (`code/modules/mob/living/living.dm:723`) was also run and likewise showed no cogbar.

Not checked: that do_afters using the default still show their cog (the default parameter is unchanged, so this is expected); the shove from the issue; the other converted callers individually.

## Notes

- The diff touches 33 files, so it is likely to conflict with other changes to those lines. A maintainer may prefer to rebase it right before merging.
- Any new code passing `null` for a parameter that has a default hits the same DM behavior; the define is the workaround.
