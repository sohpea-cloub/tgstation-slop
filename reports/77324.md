## Summary

The issue lists three RPG loot points. (1) The item fortification scroll "sometimes just doesn't work": it does not check that the target can take the fantasy component, so on items that are innately fantastical (e.g. mythril-made items) the component is refused, nothing is shown, and the scroll is still used up. The fix makes the scroll refuse with a balloon alert and keep its use. (2) The summoning property failing to summon could not be reproduced; the code that picks the summoned creature has since changed. (3) "RPG loot is overwhelming" is a design opinion, not changed.

## The bug

1. Using a fortification scroll on some items appears to do nothing, with no message. The reporter suspected incompatible items, and asked for an error message and for such items not to get RPG descriptors.
2. An item with a summoning suffix did not summon the creature named in its name (the screenshot shows "Lizardperson").
3. A request to make RPG loot less overwhelming (descriptors only on items that interact with the system, a -5 to +5 range with a chance to evaporate above that, uncommon modifiers).

## Reproduction

All with admin tools on the test server, using the Lua editor to spawn a human "user", items and `/obj/item/upgradescroll`, and calling `scroll:melee_attack_chain(user, item)`.

**Point 1, reproduced.**
1. Spawn a crowbar, give it the `innately_fantastical_item` trait (the one mythril adds), put a scroll in the user's hand and use it on the crowbar.
2. Observed: the runtime log showed `Incompatible /datum/component/fantasy assigned to a /obj/item/crowbar! args: [1,null,null,1,1]` (`code/datums/components/_component.dm:50`), raised from the scroll's `pre_attack`. The item's name did not change. In real play (outside the debug call) `AddComponent` returns null in this case and the code goes on to use up the scroll, so the player sees nothing and loses the scroll; this last point was read from the code rather than seen in play.
3. For an item that already has the component and the trait (a mythril-style item), the component is re-inherited and the item's name and effects did not visibly change.
4. Using the scroll on a backpack just put the scroll in the bag. That is normal storage behaviour (item interaction is handled before `pre_attack`), not a failure of the scroll; it was left alone.

**Point 2, not reproduced.** A crowbar given the summoning affix at +6 was hit against a human; the chat showed "The viper spider appears out of nowhere!".

## Cause

- Point 1: `/obj/item/upgradescroll/pre_attack()` (`code/modules/events/wizard/rpgloot.dm:37-41`) calls `target.AddComponent(/datum/component/fantasy, ...)` and then unconditionally does `uses -= 1` (deleting the scroll when it reaches 0) and returns TRUE. `/datum/component/fantasy/Initialize()` (`code/datums/components/fantasy/_fantasy.dm:17`) returns `COMPONENT_INCOMPATIBLE` for non-items and for items with `TRAIT_INNATELY_FANTASTICAL_ITEM`, which is set for items made of the mythril material (`code/datums/materials/basemats.dm:543`). Neither the trait nor the result is checked.
- Point 2: the affix at `code/datums/components/fantasy/suffixes.dm:88-128` now only picks mob types (`valid_subtypesof` the basic/carbon/simple_animal lists, minus megafauna, elites and abstract types). "Lizardperson" is a species name, not a mob type, so the 2023 behavior is not reachable in this code. A comment near line 92 still refers to species. The summoning component fires only on `COMSIG_ITEM_AFTERATTACK` (`code/datums/components/summoning.dm:45`), so it does not trigger when the click is handled by item interaction (tools on doors and similar) or at range; this may explain "does not work" in some situations but was not tested.

## Fix

One commit, "Fix issue 77324: item fortification scroll no longer silently fails on innately fantastical items", changes `pre_attack()` in `rpgloot.dm`:

- If the target has `TRAIT_INNATELY_FANTASTICAL_ITEM`, show a balloon alert "already fortified!" and return TRUE without using the scroll.
- If `AddComponent()` returns null for any other reason, show "can't be fortified!" and return TRUE without using the scroll.
- Otherwise behavior is unchanged.

Returning TRUE makes the attack count as handled so the scroll is not applied as a normal hit. The reporter's other suggestion, that such items should not carry RPG descriptors at all, was not changed.

## Verification

After rebuilding, on the test server with the same Lua calls:

- Crowbar with only the trait: scroll kept (still valid), name unchanged, no runtime.
- Crowbar with the component and the trait: scroll kept, name unchanged, no runtime.
- Plain crowbar: became "true pocket crowbar +1", scroll used up.
- Crowbar already at +2: became +3, scroll used up.
- The runtime log had no fantasy/scroll entries.

Not checked: the balloon alert text as it appears on a client (only the code path was exercised), scrolls with several uses, the unlimited scroll, other incompatible targets (e.g. non-items), and the summoning point beyond the single case above.
