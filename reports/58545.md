## Summary

The three issues are unrelated bugs in materials and item handling that were worked together.

- #58545: crafting a glass shard from reinforced (or reinforced plasma) glass consumes the sheet, which contains an iron rod, and creates only the shard. The rod disappears. Stack recipes can now declare "byproducts", and the two shard recipes return one rod.
- #85497: a sheetifier ejects every material as a plain default sheet, so the mob-specific meat material of gibbed meat is lost. `retrieve_stack` now tells the new sheet which bespoke material it is made of, and no longer merges sheets of different materials.
- #64780: the item drop animation replaces the looping bobbing animation of flying items such as hauntium ones, and nothing restarts it. `movetype_handler` now restarts the bobbing when the drop animation is over.

## #58545: reinforced glass shard crafting removes the rod

### The bug

A reinforced glass sheet is built from a glass sheet and an iron rod. Using the sheet in hand to make a "glass shard" produces the shard but the rod is not returned: it is gone from the game. The issue's comments also mention that breaking a reinforced window should drop rods; a reply says breaking windows does so, and that was not looked at here.

### Reproduction

Reproduced by calling the crafting proc from the Lua editor rather than through the crafting menu (the recipe's build time was set to 0 so the proc would not wait on a `do_after`).

1. On the test server, open the Lua editor and spawn a human and a stack of 3 reinforced glass sheets on the same tile.
2. Find the recipe titled "glass shard" in `GLOB.reinforced_glass_recipes` and set its `time` to 0.
3. Call `make_item(human, recipe, 1)` on the sheet stack.
4. Result on unfixed master: the stack went from 3 to 2 sheets, the shard was placed in the human's hand, and no iron rod appeared anywhere.

### Cause

- `code/game/objects/items/stacks/stack.dm:425-519` (`/obj/item/stack/proc/make_item`) creates only `recipe.result_type` (lines 453-467) and then splits off and deletes `recipe.req_amount * multiplier` of the stack (lines 470 and 502). It has no way to create anything else.
- The shard recipes at `code/game/objects/items/stacks/sheets/glass.dm:158` ("glass shard") and `:200` ("plasma glass shard") are plain recipes with nothing to say that the rod inside the sheet should survive. The sheet's rod is therefore destroyed along with the sheet.

### Fix

Commit "Fix issue 58545: crafting a shard from reinforced glass returns the rod":

- `stack_recipe.dm`: new `byproducts` variable and constructor argument, an assoc list of stack path to amount per craft.
- `stack.dm` (`make_item`): after the crafting log entry, for each byproduct a stack of `amount * multiplier` is created at the builder's `drop_location()` and gets the builder's fingerprints.
- `glass.dm`: the "glass shard" and "plasma glass shard" recipes in the reinforced glass lists declare `byproducts = list(/obj/item/stack/rods = 1)`.

A generic recipe argument was chosen over special-casing the shard recipes in `make_item`, so that any other recipe that should return part of what it consumes can use it.

### Verification

On the test server with the fix built, the same Lua call as above: the floor of the human's tile then held 2 reinforced glass sheets and 1 iron rod (the rod was also seen appearing as an "iron rod" object from the client side). Not checked: the plasma reinforced glass shard recipe was given the same `byproducts` entry but was not run separately; crafting through the real crafting menu with its normal build time; crafting with a multiplier greater than 1; whether the rod should rather go into the builder's hands.

## #85497: sheetifier loses the mob's meat material

### The bug

Meat from a gibbed mob has a custom, per-mob material (for example "Rose Archibald's meat"). When that meat is put into a sheetifier, the resulting meat sheets are ordinary default meat sheets and the mob-specific material is lost.

### Reproduction

Only the fixed build was exercised in game for this issue; the unfixed behaviour was established by reading the code (the cause below), not by observing it on the test server. The gibber step of the issue was replaced by setting the custom material by hand, matching what the gibber does.

1. In the Lua editor, spawn a human, a sheetifier and two plain meat slabs.
2. Give one slab the custom material the gibber would give it, `SSmaterials:get_material(/datum/material/meat/mob_meat, human)`, with `set_custom_materials`.
3. Insert both into the sheetifier's material container (`materials:insert_item`), wait for it to finish processing, and list the `/obj/item/stack/sheet/meat` stacks on the tile with their `mats_per_unit`.

### Cause

- `code/modules/food_and_drinks/machinery/gibber.dm:277` sets the meat's materials to `SSmaterials.get_material(/datum/material/meat/mob_meat, victim)`. `/datum/material/meat/mob_meat` (`code/datums/materials/meat.dm:115`) has `MATERIAL_INIT_BESPOKE`, so it is a separate material datum per mob.
- `code/game/machinery/sheetifier.dm:55-58` calls `materials.retrieve_all()`, which calls `retrieve_stack` per material.
- `code/datums/materials/material_container/material_container.dm:711` creates the sheet with `new type_to_retrieve(target, amount, FALSE)` and no material override, so the sheet gets the default materials of its type. The mob-specific material is spent from the container but never put on the sheet.
- The merge loop at line 726 only compares types, so any new sheet merges into any existing stack of the same type.

### Fix

Commit "Fix issue 85497: sheetifier keeps the mob a meat sheet came from", in `retrieve_stack`:

- If the material has `MATERIAL_INIT_BESPOKE`, the new stack is created with `mat_override = list(material = SHEET_MATERIAL_AMOUNT)`, using the `mat_override` argument that `/obj/item/stack/Initialize` already has (`stack.dm:68`, `:87-88`).
- The merge loop additionally requires `new_stack.can_merge(item_stack)` (`stack.dm:660`, which compares `mats_per_unit` keys), so a sheet of one mob's meat does not merge into a stack with a different material.

### Verification

On the test server with the fix built, the sheetifier produced two separate stacks: `/obj/item/stack/sheet/meat` x4 with the default "meat" material and `/obj/item/stack/sheet/meat` x4 whose material was "Rose Archibald's meat". Not checked: an actual gibbed mob's meat through the gibber (the custom material was assigned by hand); other bespoke materials; other callers of `retrieve_stack`, which pass through the changed code but were not tested; the same-material merge path.

## #64780: hauntium items stop animating after being dropped

### The bug

The issue reports that a hauntium toolbox looks fine when held but after being dropped it stops being animated and is no longer see-through.

### Reproduction

Partly reproduced, and only by reading the state back with admin tools. The animation itself cannot be seen through the test client, so the loss of bobbing was inferred from the code, not observed.

1. In the Lua editor, spawn a human and a `/obj/item/storage/toolbox/haunted`, put it in the human's hands, and drop it with `dropItemToGround`.
2. Read back its state before and after the drop. On the unfixed build, the item kept `alpha` 39, the haunt glow filter and its AI controller after the drop, so it was still translucent. The "no longer see through" part of the report was therefore not reproduced; the translucency of hauntium is by design.
3. After the fix, the same steps gave `movement_type` 3 (flying), `alpha` 39 and no runtime in the runtime log.

### Cause

- Hauntium items get `make_haunted`, which adds `movetype_handler` and `TRAIT_MOVE_FLYING` (`code/datums/elements/haunted.dm:16-17`). `movetype_handler` makes flying movables bob with a looping `pixel_z` animation, `DO_FLOATING_ANIM` (`code/__HELPERS/visual_effects.dm:8-10`).
- `/obj/item/proc/do_drop_animation` (`code/game/objects/items.dm:1542-1583`) ends with a new `animate(src, alpha = ..., pixel_x = ..., pixel_y = ..., time = 3, ...)` at line 1583. The working conclusion was that starting a new animation on the object replaces the looping floating one, and nothing starts it again, so the item stops bobbing once dropped. That would match the "stops being animated" part of the report. This was not seen on a real client.
- The drop animation already announces itself: it sends `COMSIG_ATOM_TEMPORARY_ANIMATION_START` with the duration (3 deciseconds) at line 1581, and the fish code (`code/modules/fishing/fish/_fish.dm:1495-1497`) uses it to restart its flopping once the animation is over. `movetype_handler` did not listen for it.

### Fix

Commit "Fix issue 64780: flying items resume bobbing after the drop animation", in `code/datums/elements/movetype_handler.dm`:

- The element registers (and, on detach, unregisters) `COMSIG_ATOM_TEMPORARY_ANIMATION_START`.
- On the signal, if the duration is positive and the atom is floating or flying, a timer for that duration calls `restore_floating_anim`, which calls `DO_FLOATING_ANIM` again if the atom is still alive, still attached and still floating or flying without `TRAIT_NO_FLOATING_ANIM`.

This is the same approach the fish code already uses, applied in the one place that owns the floating animation, so that all flying movables are covered instead of only the hauntium ones.

### Verification

On the test server with the fix built, dropping the haunted toolbox raised no runtime. The bobbing itself, and its restoration, were not observed on a client; the fix is verified only at the level of the code path and the absence of runtimes. Other users of the same signal, and mobs that fly, were not checked.

## Notes

- All three fixes are small and independent; they share a branch only because the issues were worked together, and each is its own commit and can be taken separately.
- #58545: the fix returns exactly one rod per craft (per multiplier). The rod is dropped at the builder's feet rather than put in hand. Whether broken reinforced windows drop rods was not tested.
- #85497: the stack of a different mob's meat no longer merges with other meat sheets. Any other caller of `retrieve_stack` now also gets the `can_merge` check in the merge loop.
- #64780: the original screenshot's "not see through" cannot be explained from the tests: the hauntium alpha and filter persisted after a drop. It may refer to something that is only visible on a real client.
