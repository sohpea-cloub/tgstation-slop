## Summary

**#93892.** `animate_door()` in `closets.dm` creates visual clones of a closet's contents on the closet's turf. Only a timer owned by the closet deletes them. If the closet is deleted before the timer fires, the timer dies with it and the clones stay on the turf as immovable copies, with no head, of whatever was inside. `Destroy()` now deletes any clones still in the closet's `vis_contents`.

**#67715.** The defibrillator paddles' stunning shocks never called `check_block`, so MODsuit shield modules could not stop them. Both stunning paths (right-click "disarm" and combat-mode "harm") now call it.

**#62779.** Not reproduced.

The three issues were worked as one batch. They are unrelated and are covered separately below.

## #93892: leftover clones of body bag contents

### The bug

The reporter was kidnapped by another player and found a copy of their body left on the floor, headless and immovable. The screenshots show it. Other players testing it reported that the copies could be flung with telekinesis. One of them said the copies cause a lot of lag.

What is on the floor is not a body. It is an `/obj/effect/appearance_clone/closet_item`, a throw-away object that copies the appearance of a closet's contents so the door-closing animation has something to show.

### Reproduction

On current master the stock body bags do not show the bug: `bodybag.dm` sets `door_anim_time = 0` for every body bag (`code/game/objects/structures/crates_lockers/closets/bodybag.dm:22`), and `animate_door()` returns early when that is 0 (`closets.dm:310`). The mechanism was reproduced by turning the animation back on. The folding and deletion were done by calling procs from the Lua editor, not by the player action (right-click fold).

1. On the test server, spawn a `/obj/structure/closet/body_bag/bluespace` on a floor tile. In the Lua editor, set its `door_anim_time` to 2 (the default for ordinary closets) and call `open()`.
2. Put a human on the bag's tile and call `close()`. The human is taken into the bag. (Humans who stand on the bag's tile afterwards get taken too, so put the folder on a different tile.)
3. Put a second human on an adjacent tile. Call `perform_fold(<second human>)` on the bag, then `qdel` the bag straight away. The player action does both in one go: `attack_hand_secondary` calls `perform_fold(user)` and then `qdel(src)` (`bodybag.dm:73-74`).
4. Read the contents of the bag's turf.

Observed on master: the turf's contents included `/obj/effect/appearance_clone/closet_item <victim name>`, a leftover copy of the victim. The victim themself was inside the folded bag item.

### Cause

`animate_door(closing = TRUE)` builds a clone of every item in the closet (`closets.dm:316-323`):

```dm
for(var/content in src)
    var/obj/effect/appearance_clone/closet_item/clone = new(loc, content)
    ...
    vis_contents += clone
```

The clones are created at `loc`, so they exist on the turf, not only in the closet's `vis_contents`. The only code that deletes them is `end_door_animation()` (`closets.dm:357-360`), which runs from a timer set at `closets.dm:354` through `addtimer(CALLBACK(src, ...))`. A timer whose callback object is deleted is cancelled. A closet that is deleted before `door_anim_time` elapses therefore never runs the cleanup. `/obj/structure/closet/Destroy()` (`closets.dm:216`) did not remove them either.

A bluespace body bag is the easy way to hit this. It can be closed with contents and folded at once, which deletes the bag (`bodybag.dm:73-74`) while the closing animation is still running. Any other closet that is deleted while closing has the same problem.

### Fix

Commit "Fix issue 93892: closets leave their content clones behind when deleted mid door animation" adds a loop to `/obj/structure/closet/Destroy()` that deletes every `/obj/effect/appearance_clone/closet_item` found in the closet's `vis_contents`:

```dm
for(var/obj/effect/appearance_clone/closet_item/clone in vis_contents)
    qdel(clone)
```

This fixes it for every closet, not just body bags. It is also the narrowest change: it does not touch the animation or the timer. The other option would have been to stop the clones being placed on the turf at all, which would change how the animation is built. That was not tried.

### Verification

The same Lua steps as in Reproduction were run on a build with the fix. The turf's contents were only floor-level objects (a firelock, an airlock, a cable and the lighting object). There was no `appearance_clone`, and the victim was inside the folded bag item.

Not checked: a real player folding a bag by right-click, and closets other than the bluespace body bag. Neither was run on the unfixed build either, since stock body bags have the animation off.

### Notes

- Because stock body bags have `door_anim_time = 0` on this master, the exact report cannot happen with an unmodified body bag at this commit. The reporter's server was at a different commit (`4487f26e`) with test-merged PRs, including a blood refactor (#93854). It is not known whether `door_anim_time` was different there. The fix is still correct for any closet that animates, and it protects against the body bag animation being turned back on.
- The "lag" the reporter mentions is plausible if copies pile up, but that was not measured.

## #67715: emagged defibrillator stuns through shields

### The bug

An emagged defibrillator or combat defibrillator stunned someone wearing a MODsuit with an active shield module (the issue is about the nuclear operative and wizard MODsuits). The shield did not absorb or block the shock. A maintainer's comment on the issue said that blocking itself is not a bug but that the shield case should be fixed.

### Reproduction

The issue's steps (non-combat mode, aiming at the chest) do not stun anyone on this master. That path is `do_help()`, which only revives or restarts a heart. The paddles' stunning paths are:

- right-click: `do_disarm()` (`code/game/objects/items/tools/medical/defib.dm:530`), which applies 60 stamina damage and a 75 Knockdown
- combat mode and chest targeted: `do_harm()` (`defib.dm:546`), which applies 50 burn, a heart attack and Paralyze 100

Both are gated by `DEFIB_CAN_HURT` (`defib.dm:3`), i.e. combat paddles or a defibrillator with its safety off (emagged).

This was reproduced by calling `do_disarm()` from the Lua editor, not by a right-click. `do_harm()` uses `do_after` twice and was not exercised.

1. Spawn an `/obj/item/defibrillator/loaded` and emag it.
2. Put a `/datum/component/regenerative_shield` (threshold 100) on one human victim to stand in for a shield module. Leave a second human unshielded as a control.
3. Call `do_disarm(<victim>, <attacker>)` on the paddles for each victim.

Observed on master: nothing in `defib.dm` calls `check_block`, so the shield never gets a chance to react. The pre-fix output of this test was not recorded; the only measured results are the post-fix ones under Verification.

### Cause

Neither `do_disarm()` nor `do_harm()` calls `check_block` on the target, so the block and shield handling behind `check_block` never runs for these shocks.

### Fix

Commit "Fix issue 67715: defibrillator shocks that stun now go through check_block":

- `do_disarm()`: after `busy = TRUE`, call `M.check_block(src, 10, "\the [src]", MELEE_ATTACK, 0, BURN)`.
- `do_harm()`: after the target-dead check, immediately before the "shocks" message, call `H.check_block(src, 50, "\the [src]", MELEE_ATTACK, 0, BURN)`.

When a block succeeds in either path, the paddles play the failed sound and call `do_success()`, so the shock is still spent and the paddles recharge. The user cannot spam shocks at a shielded target. The alternative of calling `do_cancel()` would have refunded the charge. The damage values passed to `check_block` (10 and 50) were chosen by the fix's author, roughly in line with each path's severity; they are a judgement call.

### Verification

On a build with the fix, using the emagged defibrillator through `do_disarm()` (Lua editor):

| | Shielded victim | Unshielded control |
|---|---|---|
| Knockdown | none | yes |
| Stamina damage | 0 | 60 |
| Shield hits | 15 → 14 | n/a |
| Sounds | `tap.ogg` and `defib_failed.ogg` | `defib_zap.ogg` |

Not checked: `do_harm()` (the combat-mode path) was changed in the same way but never run, since it needs the `do_after` calls and two-handed wielding. An actual MODsuit shield module was not used; the stand-in was the shield component directly.

### Notes

- The new `check_block` calls also let other blockers react to the shocks, not just shields. Only the shield component was tested.

## #62779: pixel shift after roller bed and sleeper

### The bug

A 2021 report: after being buckled to a roller bed, moved into a sleeper, taken out and put back on the bed, then released, the reporter's sprite was pixel-shifted to the left of their tile. The reporter suspected the sleeper. The round ID in the report was invalid (one reply said round 45 does not exist), the issue is tagged "Needs Reproducing", and there are no test-merge details.

### Reproduction (not reproduced)

Using the Lua editor on current master, a human was buckled and unbuckled to a `/obj/structure/bed/medical/emergency`, put into an `/obj/machinery/sleeper` with `close_machine()` and taken out with `open_machine()`, rebuckled, and unbuckled again. `pixel_x`, `pixel_y` and `pixel_w` stayed at 0. The transform was only the resting rotation (lying angle 270; the human was never stood up, so it was never reset), with no horizontal shift.

These were single-tick checks. A shift that depends on timing, on an animation in progress, or on the exact player actions (interface moves rather than direct calls) was not excluded.

### Notes

No cause or fix. If the shift still occurs, the report needs a round ID or a step-by-step reproduction.
