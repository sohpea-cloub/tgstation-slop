# #38032: Admin broadcast links runtime with "No client for HrefToken()!" when `usr` has lost its client

| | |
|---|---|
| Issues | [#38032](https://github.com/tgstation/tgstation/issues/38032): verified, fixed |
| Status | Reproduced on master and fixed; the fix was checked in game |
| Fix branch | [fix/38032](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/38032) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

`RawHrefToken()` (`code/modules/admin/holder2.dm`) deliberately `CRASH`es when `usr` is a mob without a client, unless the caller passes `forceGlobal = TRUE`. Seven admin-facing messages, sent to every admin through `message_admins()` or `to_chat(GLOB.admins, ...)`, still called bare `HrefToken()`. If the proc that builds one runs with a clientless `usr`, which is what happens when a player aghosts (or disconnects) while a delayed proc is pending, it runtimes. The fix passes `forceGlobal = TRUE` at all of them, as the `ADMIN_*` macros already do. The runtime was reproduced on master and is gone after the change. The explosion/smoke path from the original 2018 report no longer calls `HrefToken()` at all, so the bug survives only in these other sites.

## The bug

The issue was reported in 2018. Dozens of weed control crates were dropped on the station at once, and the reporter aghosted before the resulting chain of grenade explosions and smoke reactions had finished. The runtime log showed `Runtime in holder2.dm, line 203: No client for HrefToken()!` with `usr` set to the human body the player had just left. In the stack the failing call was inside `smoke_spread/chem/set_up()`, reached from a chemical reaction triggered by an exploding grenade.

Players see nothing; the visible effect is a runtime in the log, and whatever the aborted proc was about to do (here, building and sending an admin message) does not happen. The same pattern, an admin message built with `HrefToken()` while `usr` has no client, exists in several other places today.

## Reproduction

Any one of the affected sites works. This is the one that was reproduced. It needs a way to make `usr` clientless in the middle of a proc, so it used a temporary debug verb (not part of the fix; see below).

1. Start a round on the test server and join as an observer. Use the Lua editor to spawn a human next to you and give it your ckey (`h.ckey = me.ckey`), so you control a normal living mob.
2. Add a temporary verb to the build. It prints a message, then `sleep(200)`, logs `usr` and `usr.client`, calls `SSshuttle.requestEvac(usr, "this is a long enough reason")`, spawns a `/obj/item/transfer_valve` with two oxygen tanks and a signaler attached, and calls `toggle_valve()` on it.
3. Run the verb as the human, and during the 20 second sleep use the `Ghost` verb and confirm. `usr` is now the old body, which has no client when the proc resumes. This matches the aghost-mid-proc situation in the issue.
4. Read the round's `runtime.log`.

Observed on master (`87b93338`):

```
RUNTIME: ZZREPRO usr=<human name> client=
RUNTIME: runtime error: No client for HrefToken()!
 - proc name: RawHrefToken (/proc/RawHrefToken)
 - source file: code/modules/admin/holder2.dm,509
 - usr: <human name> (/mob/living/carbon/human)
```

The stack was `RawHrefToken` <- `HrefToken` <- `toggle_valve` (transfer valve) <- the debug verb. `usr.client` was empty, as expected.

Limits of this reproduction:

- It reproduced the crash by calling the procs from a debug verb, not by performing the original player actions (crate drop, grenade chain, aghost). The smoke path in the issue no longer exists (see Cause).
- Only the transfer valve site was confirmed to crash in the unfixed build. `requestEvac()` was called first in the same verb, but the logs available did not show whether it reached its `message_admins` line (it has several early returns, for example when the shuttle cannot be called). The other sites (power sink, lag switch, slow query, shuttle console request) were not run; they are the same call pattern, found by reading the code.
- The Lua editor, SDQL2 and ProcCall could not reproduce it directly: `WrapAdminProcCall` runtimes first with "no ckey" when the calling admin has no client of their own, so a debug verb was needed.

## Cause

`code/modules/admin/holder2.dm:504-513`:

```dm
/proc/RawHrefToken(forceGlobal = FALSE)
	var/tok = GLOB.href_token
	if(!forceGlobal && usr)
		var/client/C = usr.client
		if(!C)
			CRASH("No client for HrefToken()!")
		var/datum/admins/holder = C.holder
		if(holder)
			tok = holder.href_token
	return tok
```

Without `forceGlobal`, the token is `usr`'s own per-admin token, and a `usr` with no client is treated as a bug. That is reasonable for an admin opening a panel (the link is for them), but wrong for a link broadcast to all admins, for two reasons:

1. `usr` in such code is whoever happened to cause the event, often a player mob, and can be clientless (aghosted, disconnected, or logged out) by the time the proc runs.
2. Even when it does not crash and `usr` is an admin, the link carries that admin's own token. `CheckAdminHref` (`code/modules/admin/topic.dm:1-4`) accepts either the clicking admin's own token or `GLOB.href_token`, so such a link is rejected for every admin except that one. Clicking it logs a "clicked an href with a bad authorization key" message.

The `ADMIN_*` macros in `code/__DEFINES/admin.dm` (for example `ADMIN_FLW`, `ADMIN_VV`, lines 48-57) already use `HrefToken(forceGlobal = TRUE)` for this reason. The 2018 smoke path does not call `HrefToken()` at all on current master (no match in `code/modules/reagents` or `code/game/objects/effects`), so that route is no longer a source. At master these sites still used the bare form for broadcast links:

- `code/game/objects/items/devices/transfer_valve.dm:318`: the "list signalers" link added to the admin message when a bomb with an attached signaler is opened.
- `code/game/objects/items/devices/powersink.dm:154` and `:191`: the cooled-down and overheat warnings.
- `code/controllers/subsystem/shuttle.dm:397`: "has called the shuttle", with the Centcom recall link (`requestEvac`, called from shuttle and communication consoles).
- `code/modules/shuttle/shuttle_consoles/shuttle_console.dm:228`: the "requesting to move or unlock the shuttle" message sent to `GLOB.admins`.
- `code/controllers/subsystem/lag_switch.dm:37`: the automatic lag switch warning with a CANCEL link.
- `code/controllers/subsystem/dbcore.dm:682`: the "database query timed out" message (two links).

## Fix

One commit, "Fix issue 38032: admin broadcast links no longer runtime on HrefToken() when usr has no client". It changes `HrefToken()` to `HrefToken(forceGlobal = TRUE)` at the sites listed above (seven changed lines, nine call expressions, because the slow query message and the shuttle console request each contain two links). No other logic changes.

Using the global token keeps the link usable by every admin who receives the message and removes the `usr.client` dependency, which is the same approach the `ADMIN_*` macros take. The alternative of making `RawHrefToken` return the global token instead of crashing when `usr` has no client was not pursued, because the `CRASH` is a useful guard for links that really are meant for one admin and silently falling back would hide mistakes at those sites.

## Verification

- With the fix built, the same temporary verb was run as above (spawn a human, give it the observer's ckey, run the verb, `Ghost` during the 20 second sleep). The log showed `ZZREPRO usr=<human name> client=` followed by `ZZREPRO done` and no `HrefToken` runtime.
- The temporary verb was removed before the commit; the fix branch contains only the seven call-site changes.

Not checked:

- Clicking the resulting links as an admin to confirm they are accepted with the global token. This was read from `CheckAdminHref`, not tested.
- The power sink, lag switch, slow query and shuttle console request sites were not exercised in game, only the transfer valve (and `requestEvac`, see the caveat above).
- The original crate-and-smoke scenario from the issue.

## Notes

- Other bare `HrefToken()` uses were intentionally left alone. They build HTML shown to the admin who opened it, and `usr` is that admin with a client: antag panels, View Variables and item/mob tweak HTML (`code/game/objects/items.dm`, `code/modules/mob/living/living.dm`, `code/game/atom/atom_vv.dm`), the error viewer (`code/modules/error_handler/error_viewer.dm`), the revolution and nuke op reports, and a few adminhelp lines. They would only break if called from a context with a clientless `usr`.
- The issue title ("Spamming buttons") describes how the reporter hit the condition: many delayed events pending when the player left their body. Any admin-broadcast link built after `usr` loses its client is affected, so a more general guard (for example a lint or a macro for "link to all admins") could prevent new sites from regressing; this was not attempted.
