## Summary

The direction buttons in the "spawn light" window of the light debug tool never changed anything: the window read its direction from a React context that had no Provider, so the buttons called the default no-op setter and every light was spawned facing north. The fix keeps the direction in `LightSpawn` state and wraps the content in the Provider. The spawn path was checked with a new bun test, which fails on master and passes with the fix. It was not tried in a real game client.

## The bug

In the light debug tool, the "spawn light" window shows a row of arrow buttons for the direction. Clicking them did not change the highlighted button or the direction of the spawned light.

The issue also has a second screenshot, and a commenter could not reproduce the problem. The reporter clarified that the problem is in the "spawn light" window, not in the "edit light" window the commenter tested. The second screenshot's content could not be determined from the inputs.

## Reproduction

The window could not be driven in game: the tools used for the test server do not run the tgui JavaScript. The bug was reproduced with a component test instead.

1. Add `tgui/packages/tgui/interfaces/LightSpawn.test.tsx` (included in the fix commit). It mocks `sendAct`, renders `LightSpawn` with a one-template data set (`bulb`), and clicks the wrench (spawn) button, then the left arrow, then spawn again.
2. Run `bun test packages/tgui/interfaces/LightSpawn.test.tsx` on master's `LightSpawn.tsx`.
3. Result on master: the test fails. After clicking the left arrow, `spawn_template` is sent with `dir: 1`, where `dir: 8` was expected.

So the click on the direction button has no effect on what the spawn action sends.

## Cause

`tgui/packages/tgui/interfaces/LightSpawn.tsx` defines `DirectionContext` with the default value `[North, () => {}]` (around line 259) and `useWorkingDirection()` (line 264) reads it. Both `DirectionButton` (line 224) and `LightInfo` (line 119) use the hook, but no `<DirectionContext.Provider>` was ever rendered anywhere. `setWorkingDir` was therefore always the default no-op and `workingDir` was always 1, so the spawn button always sent `dir: 1` (line 159).

A second small bug: `DirectionButton` marked a button as selected with `workingDir & dir`, a bitwise AND that yields a number rather than a boolean.

The backend is not at fault: `code/modules/admin/verbs/light_debug.dm` (the `spawn_template` handler, around line 418) passes `params["dir"]` to `light_template.create`, and `/datum/light_template/proc/create` (`code/_globalvars/lighting.dm`) calls `lad.setDir(direction)`.

## Fix

Commit "Fix issue 90839: Light Spawn direction buttons did nothing":

- `LightSpawn` now holds `const [workingDir, setWorkingDir] = useState<number>(Direction.North)` and wraps its content in `<DirectionContext.Provider value={[workingDir, setWorkingDir]}>`. Most of the diff is re-indentation of the existing content.
- `selected={workingDir & dir}` became `selected={workingDir === dir}`.
- It adds `LightSpawn.test.tsx`, which covers the north default, west and south.

Alternatives such as moving the state into `DirectionButton`/`LightInfo` would not work because the two components need to share it, which is what the context was for.

## Verification

With the fix, the same test passes: the spawn sends `dir` 1, then 8 after clicking the left arrow, then 2 after clicking the down arrow (1 test, 8 expectations).

Not checked: the window in a real client (visual state of the selected button), and an actual light spawned in the game with the chosen direction. The server was started but not used, since the backend is unchanged.
