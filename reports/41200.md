# #41200: Forcefield projector places fields on tiles the user cannot see

| | |
|---|---|
| Issues | [#41200](https://github.com/tgstation/tgstation/issues/41200): verified |
| Status | Verified, fix committed |
| Fix branch | [fix/41200](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/41200) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The forcefield projector lets the user place a field on any tile within 7 tiles, including tiles behind walls and other tiles they have no line of sight to. `ranged_interact_with_atom()` checks that the target tile is not dense, that it is in range and that it is not the projector's own tile, but it never checks visibility. The fix adds a `CAN_SEE_RANGED` check that refuses the target with "You can't see that location!". After the fix, a tile behind a wall is refused and a visible tile still works.

## The bug

A player holding a forcefield projector can click a tile they cannot see (the issue says "black tiles") and, after the short build time, a forcefield appears there. The issue was opened in 2018 and is labelled as tested and reproduced. A 2025 comment questioned whether it matters because the field is not instant. A reply said it was still an inconsistency.

## Reproduction

The bug was reproduced by calling the projector's interaction proc directly from the Lua editor. A real click was only used to verify the fix, so the unfixed behavior was not shown with a real click.

1. On the test server, open the Lua editor as an admin.
2. Pick a spot in a corridor. Using Lua, turn the turf one tile to the east into a wall (`ChangeTurf` to `/turf/closed/wall`). The target is the tile 3 tiles east, behind that wall.
3. Spawn a human and a `/obj/item/forcefield_projector`, put the projector in the human's hands and set its `creation_time` to 0 so there is no `do_after` delay.
4. Call `ranged_interact_with_atom(target_turf, human, ...)` on the projector for the tile behind the wall.
5. Observed on unfixed master: the chat showed "<name> projects a forcefield!" and a field was created behind the wall. The target tile was not dense, so the density check did not stop it.

## Cause

In `code/game/objects/items/devices/forcefieldprojector.dm`, `ranged_interact_with_atom()` (line 27 at master) validates the target in this order: an existing field on the tile (lines 36-40), `T.density` (41), `get_dist(T,src) > field_distance_limit` (43), and `get_turf(src) == T` (45). Then it checks the field count and the busy flag, and starts the `do_after`.

None of these checks is about whether the user can see the tile. The distance check is a plain tile distance and ignores walls. Clicks on tiles inside the view range but out of sight (dark tiles, tiles behind walls) still reach this proc. The test notes say that click handling allows clicking dark tiles in view range. The proc has no further check, so the field is placed. Adjacent targets are always treated as visible by the existing helper, so only ranged targets are affected.

## Fix

One commit, "Fix issue 41200: forcefield projector requires line of sight to the target tile", adds three lines after the "Target is too close" check:

```dm
if(!CAN_SEE_RANGED(T, user, field_distance_limit))
	to_chat(user, span_warning("You can't see that location!"))
	return ITEM_INTERACT_BLOCKING
```

`CAN_SEE_RANGED` is an existing macro in `code/__HELPERS/view.dm`: `((source in viewers(dist, target)) || in_range(target, source))`. It is used with the projector's own `field_distance_limit` (7) as the range, so the visibility range matches the placement range. It returns true for adjacent targets and for targets in the user's line of sight. This was chosen because it is the existing helper for this kind of check. The inputs do not mention other approaches.

## Verification

Checked on the test server after rebuilding with the fix:

- Calling `ranged_interact_with_atom()` from Lua on the tile behind the wall returned `ITEM_INTERACT_BLOCKING` and no field was created. A tile on the visible side of the user was not blocked by the new check. The test notes say it got a field, and the chat showed one "projects a forcefield!" message in that run. The returned values from that particular call were not read back, so this rests on the notes and the message.
- With a real player body holding a projector, a click on the tile behind the wall printed "You can't see that location!" in chat and nothing was started.
- A real click on a visible tile started the normal build progress bar. The click was not followed through to a finished field.

Not checked: a tile that is in view range but dark (rather than behind a wall), the effect of the check on other maps or lighting setups, a click through windows or other see-through obstacles, and behavior with the projector held by a non-human mob.

## Notes

- The check runs only once, before the `do_after`. If the user loses sight of the tile during the build, the existing `do_after(..., target = interacting_with)` check still applies (it covers the user or target moving). No new check was added at the end of the build.
- A reply from 2025 on the issue argued that the delay makes this less important. The fix does not change the delay.
- `CAN_SEE_RANGED` is built on `viewers()`. How it treats tiles that are in line of sight but dark was not tested.
