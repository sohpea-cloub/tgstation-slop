# #87032: Bots drop off the diagnostic HUD when their path is cleared

| | |
|---|---|
| Issues | [#87032](https://github.com/tgstation/tgstation/issues/87032): verified, fixed |
| Status | Fixed (verified at the level of HUD membership on the test server; not checked through a client) |
| Fix branch | [fix/87032](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/87032) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

`clear_path_hud()` on simple bots removed the bot from the whole diagnostic atom HUD, not only from the bot path HUD. Anything that calls it (`bot_reset()`, which runs when a bot is turned off, emagged or finishes a summon, plus `Destroy()` and a client logging in) therefore made the bot invisible to diagnostic HUDs until a new path happened to be generated. The fix removes the diagnostic HUD from the lists that `clear_path_hud()` and `generate_bot_path()` touch, so only the bot path HUD is added to or removed from.

## The bug

The issue reporter saw that a diagnostic HUD "sometimes shows" a bot's status icons, and that after interacting with or repairing a bot the icons could disappear. What happened underneath: the bot was taken out of the diagnostic HUD's list of tracked atoms, so none of its diagnostic icons (health, status, mode, battery) were sent to HUD users.

## Reproduction

The bug was reproduced on master by calling procs directly, not by the player actions in the report (repairing a bot, say). It was also not observed through a worn diagnostic HUD; the check was on the HUD datum's membership list.

1. On the test server, use the Lua editor to spawn a `/mob/living/basic/bot/cleanbot`.
2. Use SDQL2 (`SELECT /datum/atom_hud/data/diagnostic`) to get the diagnostic HUD datum.
3. Read `hud_atoms_all_z_levels[bot]` on it. Result: 1, so the bot is tracked.
4. Call `bot_reset()` on the bot and read the entry again. Result: 0.
5. Call `turn_off()` on the bot and read the entry again. Result: 0 (the report does not say whether the bot was re-added in between).

Observed on master: before = 1, after `bot_reset()` = 0, after `turn_off()` = 0.

## Cause

`code/modules/mob/living/basic/bots/bot_hud.dm:108` defines `clear_path_hud(remove_hud = TRUE)`. After fading out the path images, it builds a list of HUDs and removes the bot from each:

```dm
var/list/path_huds_watching_me = list(GLOB.huds[DATA_HUD_DIAGNOSTIC], GLOB.huds[DATA_HUD_BOT_PATH])
for(var/datum/atom_hud/hud as anything in path_huds_watching_me)
	hud.remove_atom_from_hud(src)
```

(`bot_hud.dm:118`.) The diagnostic HUD is the one that carries the bot's health, status, mode and battery icons, and the bot is added to it once in `Initialize()` (`_bots.dm:140-141`). Removing the bot from it here drops all of those icons, not just the path.

`clear_path_hud()` is called from `Destroy()` (`_bots.dm:221`), from `bot_reset()` (`_bots.dm:565`) and from the client-login handling (`_bots.dm:778`). `generate_bot_path()` builds the same two-HUD list at `bot_hud.dm:55` and re-adds the bot to both after drawing a path, which is why the icons came back after the bot next planned a route and "sometimes" showed.

The diagnostic HUD does not carry `DIAG_PATH_HUD`, so adding or removing the bot there for path purposes was never needed. (Only the bot path HUD displays path images.)

## Fix

One commit, "Fix issue 87032: bots no longer drop off the diagnostic hud when their path is cleared". In both places in `bot_hud.dm` (`generate_bot_path()` and `clear_path_hud()`), the list becomes `list(GLOB.huds[DATA_HUD_BOT_PATH])`. Clearing a path now removes the bot only from the path HUD, and generating a path no longer re-adds the bot to the diagnostic HUD (it never left). No other approach was recorded in the inputs.

## Verification

After rebuilding on the test server with the fix, the same check gave: before = 1, after `bot_reset()` = 1, after `turn_off()` = 1. So the bot stays in the diagnostic HUD.

Not checked:
- Rendering on a client wearing a diagnostic HUD; only the server-side HUD membership was read.
- Other bot types; they share this code, but only a cleanbot was tested.
- The path HUD itself (that path images still appear and disappear correctly for path HUD users).
- The exact repair scenario in the issue.

## Notes

- The other bot icons are set by `diag_hud_set_bothealth()`, `diag_hud_set_botstat()` and `diag_hud_set_botmode()`. These were not changed.
- The issue's repro ("mess with it or wait") fits any of the `bot_reset()` triggers, but which one the reporter hit is not known from the issue.
