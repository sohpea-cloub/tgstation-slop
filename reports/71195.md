# #71195: Ghosts can double-click jump across secret cordons

| | |
|---|---|
| Issues | [#71195](https://github.com/tgstation/tgstation/issues/71195): verified, fixed |
| Status | Fixed on a branch and checked in game; partial, because other teleport paths still cross a cordon |
| Fix branch | [fix/71195](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/71195) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary
A non-admin ghost cannot walk through a secret cordon, but it can double-click any turf on the far side and be moved there. `DblClickOn` calls `abstract_move()` on the clicked turf, and `abstract_move()` only refuses when the destination itself is a secret cordon or a secret z-level. The fix adds a check to the ghost double-click handler: a non-admin ghost's straight line to the target may not contain a secret cordon turf. Other ways for a ghost to relocate (the Teleport and Jump-to-Mob verbs, the Orbit menu, follow links) were not changed and still bypass the cordon.

## The bug
The issue was filed in 2022 while testing a away mission map (the "Caves" mission) that hides modular content behind a cordon. Mappers use cordons so that players cannot peek at content they should not see. A deadminned ghost is stopped by the cordon when it walks, but double-clicking a turf on the other side makes it jump across. The reporter shows a solid black line as the cordon and an X on the far side as the click target. A commenter asked why cordons matter when maps are open source. The reporter answered that the missions load many nested modules dynamically, so assembling them in a map editor is slow, whereas peeking in game is easy.

## Reproduction
Reproduced on master.

1. On the test server, as an observer, opened the Lua editor and changed the turfs at x=110, y=125..165 on the station z-level to `/turf/cordon/secret` (`ChangeTurf`). This makes a vertical wall of secret cordon.
2. Used the DeAdmin verb so the ghost counted as a normal player (the check in `abstract_move()` exempts clients with admin holder datums).
3. With the ghost at 107,144 on the west side of the line, double-clicked the floor turf at 114,144 on the east side.

Observed before the fix: the ghost moved from 107,144 to 114,144, straight across the cordon.

Walking was already blocked, because a ghost moves one tile at a time and the next tile is the cordon turf itself, which `abstract_move()` refuses.

## Cause
`/mob/dead/observer/DblClickOn` (`code/_onclick/observer.dm:1`) follows the clicked thing if it is a movable, and otherwise jumps:

```dm
	else if(A.loc)
		abstract_move(get_turf(A))
```

`/mob/abstract_move` (`code/modules/mob/mob_movement.dm:582-585`) is the only guard:

```dm
/mob/abstract_move(atom/destination)
	var/turf/new_turf = get_turf(destination)
	if(new_turf && (istype(new_turf, /turf/cordon/secret) || is_secret_level(new_turf.z)) && !client?.holder)
		return
```

It looks only at the destination turf. A destination that is beyond the cordon, but is not itself cordon, passes the check.

## Fix
One commit, "Fix issue 71195: ghosts can double-click jump across secret cordons", changes `code/_onclick/observer.dm`:

- Adds `/mob/dead/observer/proc/jump_crosses_secret_cordon(turf/destination)`. It returns FALSE for ghosts whose client has an admin holder, when there is no destination, and when the ghost and destination are on different z-levels. Otherwise it walks `get_line()` from the ghost's turf to the destination and returns TRUE if any turf on the line is a `/turf/cordon/secret`.
- `DblClickOn` calls it with `get_turf(A)` before anything else. If it returns TRUE, the ghost gets the warning "Something blocks the way." and nothing happens. Because the check runs before the movable test, double-clicking a mob or object beyond the cordon (which would start following it) is refused too.

Only `/turf/cordon/secret` is checked. The plain `/turf/cordon` type is documented as not blocking ghosts, so it was left alone. The line is a straight Bresenham line, which was the simplest test that matches "jumping over" the cordon; a pathfinding test would have been heavier for little gain.

## Verification
Checked in game after rebuilding, repeating the setup above (secret cordon at x=110, ghost deadminned at 107,144):

- Double-click on 114,144 (beyond the cordon): the chat showed "Something blocks the way." and the ghost did not move.
- Double-click on 104,144 (same side): the ghost jumped there as before.

Not checked:
- Teleport, Jump-to-Mob, Orbit and follow, which were identified as still crossing (see Notes) but not changed.
- Admin ghosts (the code path exempts them; no in-game test).
- Ghosts on a different z-level from the click target.
- The original Caves mission map, and the effect of the `SIDE_MAP` map format mentioned in the issue.

## Notes
- Remaining gaps, same hole through other paths: the Teleport and Jump-to-Mob verbs, the Orbit menu and follow links all use `abstract_move()` and can still put a ghost in an area or on a mob behind a cordon. A more complete fix would put the line-crossing test in a shared place, or in `abstract_move()` for ghost sources.
- Side effect: a ghost already inside a secret-cordon region cannot double-click out of it, because the straight line crosses the cordon. Such a ghost can still use Teleport or Orbit.
- Only `museum.dmm` uses `/turf/cordon/secret` among the in-repo maps at the tested commit, so the change affects few rounds today.
- The issue text says "a solid black line as a cordon". Plain `/turf/cordon` does not block ghosts by design, so the reported behaviour matches only the secret type for which a block is intended.
