## Summary

The mapping-debug verb "Check Plumbing" was reported to print "Unconnected multi deck pipe adapter" for adapters that were in fact working, because an adapter that only uses its up or only its down side always has an empty node slot. On master the pipe loop of the verb skips `/obj/machinery/atmospherics/pipe/multiz` entirely, and the adapters link to each other in both directions, so there is no false positive. Running the verb on IceBoxStation, which has 54 adapters, printed no adapter lines. The skip is coarse, though: it also hides adapters that really are unconnected. No fix was committed.

## The bug

A multi deck pipe adapter connects to the z-levels above and below, with one node slot for each direction. If a map only uses one side, the other slot stays null. The verb treated any null node as "unconnected", so every correctly used one-sided adapter was listed, burying real pipe problems in noise.

## Reproduction

The check was run on IceBoxStation, which has multi-z adapters, using the verb as an admin.

1. Boot the test server on IceBoxStation, start the round, and observe.
2. Run "Enable Mapping Verbs", then "Check Plumbing".
3. Read the admin chat lines starting with "Unconnected" or "One-way connection".
4. Using SDQL2, run `SELECT /obj/machinery/atmospherics/pipe/multiz` to count the adapters on the map.

Observed: SDQL2 selected 54 adapters. The verb printed 45 "Unconnected" lines: omni pressure tanks, omni air scrubbers, and two named pipes in abandoned areas. None mentioned a "multi deck pipe adapter". No "One-way connection" lines were printed at all.

This does not show that the pre-fix code produced false positives (the old behaviour was not run), and it does not show that every adapter on the map is actually connected. It only shows that the verb no longer reports adapters.

## Cause

There is no live false positive; why it does not occur on master:

- `code/modules/admin/verbs/atmosdebug.dm:6-8`: the first loop only checks `/obj/machinery/atmospherics/components`. Adapters are pipes (`/obj/machinery/atmospherics/pipe/multiz`), so they are not in it.
- `atmosdebug.dm:11-15`: the pipe loop explicitly skips them:

  ```
  if(istype(pipe, /obj/machinery/atmospherics/pipe/smart) || istype(pipe, /obj/machinery/atmospherics/pipe/layer_manifold) || istype(pipe, /obj/machinery/atmospherics/pipe/multiz))
  	continue
  ```

- `atmosdebug.dm:17-21`: the "One-way connection" check goes through every atmospherics machine's nodes. For adapters it finds none, because `pipeline_expansion()` in `code/modules/atmospherics/machinery/pipes/multiz.dm:49-60` sets both ends of a vertical link (`nodes[2] = above` and `above.nodes[3] = src`, and the below adapter re-runs the expansion so its link to us is set too).

## Fix

None needed. The history of when the `multiz` skip was added could not be checked: the available checkout is shallow, so no upstream commit or PR was identified.

## Verification

Checked once on IceBoxStation as described above. Not checked: other maps, an adapter placed with no neighbour on either side (to see what, if anything, would be reported), and a deliberately broken vertical link.

## Notes

- Side effect of the skip: an adapter whose horizontal node (`nodes[1]`) is genuinely missing, meaning it is attached to nothing, is no longer reported either. A finer check could keep the adapters in the loop but only require `nodes[1]` to be non-null, leaving the up and down slots optional. That would be an improvement to the verb, not a fix for the reported false positive.
- The reporter's "Needs Reproducing / Needs Pictures" labels were never resolved; the issue text is a single paragraph and gives no map or output.
