# #36382: Giving a player control of a bot doesn't clear the bot's pathfinding icons

| | |
|---|---|
| Issues | [#36382](https://github.com/tgstation/tgstation/issues/36382): not reproduced |
| Status | Not reproduced on master; no fix written |
| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The issue reports that when a player takes control of a bot that is following a path (for example a Beepsky), the path markers drawn on the floor stay visible and static. On current master this could not be reproduced: `/mob/living/basic/bot/Login()` calls `clear_path_hud()`, which empties the bot's path and removes it from the diagnostic and bot-path HUDs. In every test the bot's path was empty after a player was put into it. One narrow edge case, a path request that finishes after the player has already taken control, was not exercised.

## The bug

The original report (2018) says only "drag a player onto a moving beepsky". A 2024 comment adds screenshots and describes the symptom: when a player is given control of a Beepsky while it is following a path, the path stays printed on the ground for the player to see. It does not go away until the player ghosts, it does not move with the bot, and no new paths are drawn. The commenter says it only happens if the bot already had a path when the player was dragged in or spawned into it.

A bot's path is a set of `image`s (one per turf of the route) kept in `current_pathed_turfs` and in the bot's `active_hud_list[DIAG_PATH_HUD]`. They are shown only to clients whose mob has the diagnostic or bot-path HUD (ghosts, AIs, diagnostic HUD glasses and MOD visors). A bot's own player normally has the bot's data HUD (security, medical or diagnostic), not the bot-path HUD.

## Reproduction

Not reproduced. What was tried, on a test server running master:

1. Started a round and waited for roundstart bots to begin pathing (they walk their routes on their own after round start). Bots in `GLOB.bots_list` with more than three entries in `current_pathed_turfs` were used as test subjects.
2. Using the Lua editor, called `PossessByPlayer` on a secbot with a path of 10 turfs. Afterwards the bot had a client, `speed` was 2, its AI was off and `current_pathed_turfs` was empty. It was still empty 4 seconds later. A Beepsky with a path of 5 also went to 0.
3. Race test on a "dedbot": forced the JPS move loop to repath (`repath_cooldown = 0`, `recalculate_path()`; `is_pathing` read 1) and called `PossessByPlayer` in the same tick. After 4 seconds the path was empty and `speed` was 2. `generate_bot_path` did not draw anything in this test, because this bot had no beacon target and returned at the `BB_BEACON_TARGET` check.
4. The game log confirmed that `Login` runs for a bot taken this way (a "Mob Login ... was assigned to a /mob/living/basic/bot/cleanbot/autopatrol" line).

One early observation was inconsistent with the rest: a cleanbot on autopatrol (path of 15) was possessed, and 10 to 40 seconds later it read `current_pathed_turfs` still at 15 and `speed` 3, with its AI off. This could not be repeated. Later, that same cleanbot read a path of 0 with a client attached. The early reading may have come from a different bot or been taken before `Login` took effect; this was not resolved.

Possession was done by calling `PossessByPlayer` from the Lua editor, not by dragging a player onto a bot or by the bot's sapience interface, so the exact in-game action from the issue was not performed. An admin "Give Direct Control" route was considered but not used.

## Cause

There is no defect found for the reported scenario. The relevant code on master:

- `code/modules/mob/living/basic/bots/_bots.dm:770`, `/mob/living/basic/bot/Login()`, sets `speed = 2`, calls `diag_hud_set_botmode()` and then `clear_path_hud()`.
- `code/modules/mob/living/basic/bots/bot_hud.dm:108`, `clear_path_hud()`, fades every image in `current_pathed_turfs` to alpha 0, removes the entries, and (with the default `remove_hud = TRUE`) removes the bot from the diagnostic and bot-path HUDs so viewers' clients drop the images.
- `Logout()` (`_bots.dm:780`) calls `bot_reset()`, which also clears the path.
- When the player's mob changes, `code/modules/mob/login.dm:29` resets `client.images` and reloads HUDs, so images shown to the previous mob (a ghost or AI) are not carried into the bot.

The path images the commenter saw most likely came from the previous mob's client (ghost or AI) or from a path drawn after `Login`. This was not confirmed.

Two possible weaknesses were noted but produced no visible symptom:

- `generate_bot_path` (`bot_hud.dm:35`) has no client check. If a JPS path request is still in flight when a player takes control, the finished-pathing signal could still draw a path and re-add the bot to the HUDs after `Login` has cleared them. `handle_hud_path` (`bot_hud.dm:97`) returns early when `client` is set, so such a path would never be faded out as the bot moves. That would match the commenter's "static track" description. It needs a bot with a beacon target and a request mid-flight, and none was available in testing.
- `clear_path_hud()` empties `current_pathed_turfs` but not `active_hud_list[DIAG_PATH_HUD]`, so stale images stay in that list until the next path replaces it.

## Fix

None committed.

## Verification

No fix to verify. The "not reproduced" result covers the secbot, Beepsky and dedbot tests above, all started through `PossessByPlayer`. Not checked: possession by dragging a player onto a bot, possession through the bot's own sapience or an admin Give Direct Control verb, and a bot with a beacon target and a path request in flight at the moment of possession.

## Notes

- If the issue is to be closed as stale, the unchecked in-flight request case is the only plausible remaining route. A defensive `if(client) return` at the top of `generate_bot_path` would cover it.
- `clear_path_hud(remove_hud = TRUE)` removes the bot from the whole diagnostic HUD, not only the path part, so diagnostic HUD viewers lose the bot's status icons until something re-adds it. This was noted by reading the code, not tested.
