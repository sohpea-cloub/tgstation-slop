# #71941: Every escape pod area is named "Escape Pod One"

| | |
|---|---|
| Issues | [#71941](https://github.com/tgstation/tgstation/issues/71941): verified, fixed |
| Status | Fixed on the fix branch; verified on the test server (Metastation only) |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/71941 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Every escape pod shuttle is loaded from the same template, whose area is named "Escape Pod One", and nothing renames the area after loading. All pods on a station therefore report the same location, which makes the crew monitor and the player's location readout useless for finding a pod. The fix adds a `load_roundstart()` override on escape pod docking ports that numbers each pod in load order and appends the nearest station area, e.g. "Escape Pod 2 (Transfer Centre)".

## The bug

On Metastation there are four escape pods. A player standing in any of them sees their location as "Escape Pod One", and the crew monitor shows the same name for a body in any pod. The reporter looked for dead crew in "Escape Pod One", did not find them, and later found a body in a different pod. A maintainer commented that all stations behave this way.

## Reproduction

1. Start a round on Metastation (the only map tried).
2. As an admin, run this SDQL2 query: `SELECT /area/shuttle/pod_1 MAP [name, length(contents)]`.
3. The query selected 4 areas, and every one had the name "Escape Pod One".

The query reads area names directly; no pod was boarded or checked through the crew monitor.

## Cause

`/area/shuttle/pod_1` is defined with `name = "Escape Pod One"` (`code/game/area/areas/shuttles.dm:138-139`). Each escape pod docking port loads the same template at round start through `/obj/docking_port/stationary/proc/load_roundstart()` (`code/modules/shuttle/stationary_port/stationary_port.dm:89`), called from `setup_shuttles()` (`code/controllers/subsystem/shuttle.dm:203-205`). That makes a separate area instance for each pod, but each keeps the template's name. `load_roundstart()` also discards the loaded shuttle: it calls `SSshuttle.action_load(...)` as its last statement (line 103) and returns nothing, so callers cannot adjust the new pod.

## Fix

One commit, "Fix issue 71941: give each escape pod a unique area name":

- `stationary_port.dm`: `load_roundstart()` now returns the result of `SSshuttle.action_load(...)`, which is the loaded mobile port.
- `port_types.dm`: a new `/obj/docking_port/stationary/escape_pod/load_roundstart()` calls the parent, then names every area in the pod's `shuttle_areas` `"Escape Pod N (area)"`. N is a static counter, incremented in load order. The area is the `/area/station` area closest to the dock within 10 tiles, ignoring the escape pod hallway area (`/area/station/hallway/secondary/exit/escape_pod`). If none is found, the name is just "Escape Pod N".

The issue discussion asked for directional names (arrivals, holodeck, security). Deriving the location from the surrounding area gives that on every map without map edits or passing a name through the docking port. This works for the default, cramped and luxury templates, since they all load through the same override. The simpler option raised in the issue, dropping the designation, was rejected in the discussion.

## Verification

After rebuilding and restarting the test server on Metastation, the same SDQL2 query returned four areas:

- Escape Pod 1 (Arrival Shuttle Hallway)
- Escape Pod 2 (Transfer Centre)
- Escape Pod 3 (Recreation Area)
- Escape Pod 4 (Engineering Maintenance)

No runtimes appeared in the server log.

Not checked: other maps, the cramped and luxury pod templates, the crew monitor display, and the location readout while riding a pod.

## Notes

- The number is the load order, not tied to the old `pod_1`/`pod_2` type names, and not tied to a fixed physical pod, so numbering may differ between maps or if load order changes.
- Names come from a nearest-area heuristic and can be odd (such as "Engineering Maintenance"). A maintainer may prefer explicit per-dock names set in the map.
- The `/area/shuttle/pod_1` and `pod_2` types are still referenced elsewhere (for example in `code/datums/components/stationloving.dm`), and only their `name` changes at runtime.
