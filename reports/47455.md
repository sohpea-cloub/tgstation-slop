## Summary

The 2019 report says an AI cannot use an empty AI shell (cyborg with a B.O.R.I.S. module) that was built before the AI was created: "Deploy to Shell" answers "No usable AI shell beacons detected." On master the opposite happened in game: a shell created while no AI existed was deployable by an AI made afterwards. The code agrees: shells with no master AI are intended to be usable by any AI. No change was made. The one path not tested is hand assembly through the robot suit, though it passes the same arguments to the same constructor.

## The bug

As reported: after a player builds an AI shell and a different AI is made (for example a late-join AI), the AI's "Deploy to Shell" verb finds nothing and prints "No usable AI shell beacons detected." The reporter later clarified that the shell was empty, unused and not claimed by another AI. Commenters on the issue said that AIs are meant to be able to take unsynced shells, and that a shell synced to another AI would not be available, but the reporter stated that the shell was neither.

## Reproduction

The shell was created from the Lua editor, not assembled by hand, so the physical build was not exercised.

1. Start the round with no AI present.
2. In the Lua editor, spawn a `/mob/living/silicon/robot/shell` with the same constructor arguments the robot suit uses when a B.O.R.I.S. module is installed (location, no laws, no forced AI, `aisync` on, `lawsync` on).
3. Create an AI (a human turned into an AI with `AIize`) and take control of it.
4. Check the shell and use the AI's "Deploy-to-Shell" verb.

Observed on master:

- `GLOB.available_ai_shells` contained "Empty AI Shell-842" with `shell` = 1, `deployed` = 0, `stat` = 0 and `connected_ai` = null.
- The AI had `control_disabled` = 0 and was not incapacitated.
- The verb opened the "Direct Control: Which body to control?" list containing "Empty AI Shell-842". The "No usable AI shell beacons detected." message did not appear. The window was cancelled without deploying, so the actual transfer into the shell was not carried out.

## Cause

There is no defect on master for this scenario. What decides the outcome:

- `select_shell` (`code/modules/mob/living/silicon/ai/ai.dm:998-1013`) offers a shell if `R.shell && !R.deployed && (R.stat != DEAD) && (!R.connected_ai || (R.connected_ai == src))`. A shell with no master AI qualifies for any AI. "No usable AI shell beacons detected." (`ai.dm:1013`) is printed only when no shell passes this test (or if the AI is incapacitated or has its wireless network disabled, which give different messages).
- A shell is added to `GLOB.available_ai_shells` by `make_shell` (`code/modules/mob/living/silicon/robot/robot.dm:808-817`).
- A new cyborg tries to sync to an AI in its initialization (`robot.dm:48`, `try_connect_to_ai` at `robot.dm:963`). With no active AI, `select_active_ai_with_fewest_borgs` returns null and the cyborg stays unsynced (`connected_ai` null). If an AI does exist when the shell is built, the shell is synced to it. Such a shell is then unavailable to any other AI. This is intended.
- The robot suit creates the shell with `new(get_turf(src), null, forced_ai, aisync, lawsync)` (`code/game/objects/items/robot/robot_parts.dm:344`), the same arguments used in the test.

## Fix

None. No code was changed.

## Verification

Nothing to verify; see Reproduction for the evidence that the reported symptom does not occur on master in the tested path.

Not tested: building the shell physically (robot suit, MMI-less frame, B.O.R.I.S. module) instead of constructing it with the same arguments; shells built while another AI exists and then used by a second AI; AIs that were already on the round when the shell was built and were later wiped, destroyed or had wireless disabled; the actual transfer into the shell, which was not completed.

## Notes

- Likely explanations for the 2019 report, from reading the code and not tested: the code has changed since then; or the shell was built while another (possibly dead or unnoticed) AI existed and was synced to it, in which case other AIs correctly cannot use it; or the AI had wireless networking disabled or was incapacitated. The first reply on the issue and the maintainers' later comments point to the same intended rule.
- If the reporter's exact steps can be recovered (round setup, whether an AI existed at build time), they would help confirm whether anything beyond the above is involved.
