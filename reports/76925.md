## Summary

The Select Equipment admin panel builds one preview dummy per panel and reuses it for every outfit. Resetting the dummy only removes its equipment, so an outfit that changes the body (the psyker and echolocator outfits call `psykerize()`, which swaps the head and brain) leaves that change on the dummy for every later preview. The fix throws the dummy away and builds a fresh lookalike of the target each time a new preview is rendered. Of the three related issues in the group, none reproduced: one (#79080) was already fixed on master.

## #76925: psyker outfit preview changes all later previews

### The bug

After previewing a psyker outfit in the panel, every later preview of any other outfit shows a psyker head, until the panel is closed and reopened. A comment on the issue (Rhials) correctly identified that the dummy's head and brain become psyker versions and are not cleaned up when a new preview is made.

### Reproduction

The visual panel itself was not viewed. The dummy state and the preview data the panel receives were inspected with admin tools instead.

1. In the Lua editor, spawn a human (a moth was used) and create a `/datum/select_equipment` datum for an admin client and that human, then call its `ui_data()` once. The dummy's head was `/obj/item/bodypart/head/moth` and its brain `/obj/item/organ/brain`.
2. Set `selected_outfit` to `/datum/outfit/psyker` (and `selected_identifier` to match) and call `ui_data()` again. The dummy now had a psyker head and a psyker brain.
3. Set the outfit back to the plain `/datum/outfit` (naked) and call `ui_data()`.

Observed on master: after step 3 the dummy still had the psyker head and psyker brain, so the "naked" preview is rendered with them. This reproduces the report.

### Cause

`/datum/select_equipment/ui_data` (`code/modules/admin/verbs/selectequipment.dm:108-120`) creates the dummy once (`if(!dummy_key) init_dummy()`) and then renders every preview from that same dummy:

```dm
if(!dummy_key)
	init_dummy()

if(isnull(cached_dummy_icon) || cached_for_identifier != selected_identifier)
	cached_dummy_icon = get_flat_human_icon(null, dummy_key = dummy_key, ...
```

Each preview resets the dummy with `/mob/living/carbon/human/dummy/proc/wipe_state()` (`code/modules/mob/living/carbon/human/dummy.dm:87`), which only calls `delete_equipment()`, clears lips and cuts overlays and filters. Psyker outfits (and the echolocator outfit) call `psykerize()` (`code/modules/religion/burdened/psyker.dm:71`) in their post-equip step. That proc replaces the head with a psyker head and the brain with a psyker brain, and nothing in `wipe_state()` undoes it. The bitrunning outfits (`bitrunning/outfits.dm:16`) were also found to call it.

### Fix

One commit, "Fix issue 76925: Select Equipment previews keep the psyker head and brain". In `ui_data`, when a new preview needs rendering (no cached icon, or the selected identifier changed), the code now calls `clear_human_dummy(dummy_key)` if a dummy exists and then `init_dummy()`, so every preview starts from a fresh lookalike of the target. The old `if(!dummy_key) init_dummy()` is removed, since the new block covers the first preview too. Rebuilding the dummy was preferred over teaching `wipe_state()` to restore organs, because any outfit might change the body in other ways, and the preview should always start from the target's own appearance. The cost is a dummy rebuild per preview change, which only happens when an admin selects a different outfit.

### Verification

After rebuilding, the same sequence of a moth target (initial preview, psyker, then naked) was run. The naked preview's dummy had a moth head and the normal `/obj/item/organ/brain` again, and the moth wings (Oak Worm) were preserved.

Not checked: the actual tgui panel (the preview image was not looked at; only the dummy state and the `icon64` payload `ui_data` returns), the other psykerizing outfits, and any performance difference.

## #62914: respawning leaves a second, unselectable copy of you in the target list

Not reproduced.

The report (2021) said that after respawning, Select Equipment offered only a stale entry with the player's name instead of the current mob. The verb now takes its target from the context menu or a mob in the world (`ADMIN_VERB_ONLY_CONTEXT_MENU`, `code/modules/admin/verbs/selectequipment.dm:1`).

Steps tried: an admin ghosted and respawned (admin override) as a late-join Assistant. Using the Lua editor over the global mob list, exactly one mob had the new character's name, the human. The old observer is deleted: observer `Logout` (`code/modules/mob/dead/observer/logout.dm:12-14`) deletes a ghost whose key has moved to another mob. The panel's own target list also showed only the human. The stale entry the report describes no longer exists on master. It was not found which change removed it.

## #67466: wrong moth wings and antennae in the preview

Not reproduced.

Using the same setup as above, three random moths were spawned and the panel's datum created for each. In every case the dummy's wings and antennae (by sprite name) and the `dna.features` matched the target's. The issue text alone does not say what the mismatch was, so what the original report showed is unknown.

## #79080: detective preview shows every cigarette animation frame

Not reproduced; already fixed on master.

`ui_data` already calls `get_flat_human_icon` with `no_anim = TRUE` (`code/modules/admin/verbs/selectequipment.dm:118`),, which the test notes attributed to upstream PR 98038. Generating the detective outfit's icon directly gave a base64 string of 1176 characters with animation and 836 without; the wizard and naked outfits were identical both ways. The panel passes `no_anim = TRUE`, so the smaller image is what it uses. The PR number is from the test notes and was not checked against upstream here.

## Notes

- The fix touches only the Select Equipment panel's dummy. Other users of `wipe_state()` (the dummy used for preferences, for example) were not examined and are not changed; they may have the same stale-body problem with outfits that alter organs.
- #62914, #67466 and #79080 were checked in the same session and need no code change; they can likely be closed as no longer reproducible (or, for #79080, fixed upstream).
