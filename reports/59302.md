# #59302: Closing a crate swallows dense objects (such as canisters) that got onto its tile

| | |
|---|---|
| Issues | [#59302](https://github.com/tgstation/tgstation/issues/59302) - verified, fixed (reproduced with a stand-in for the fall, see Reproduction) |
| Status | Fixed; not tested with a real z-level fall or teleporter |
| Fix branch | https://github.com/sohpea-cloub/tgstation-slop/tree/fix/59302 |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

An open crate is dense, so dense objects such as gas canisters cannot normally be pushed onto its tile. Falling down a z-level or being teleported bypasses that check, and crates have `allow_dense = TRUE`, so when the crate is then closed `take_contents()` pulls the canister inside. The fix makes `close()` skip dense objects; the initial population of crates at mapload is unchanged.

## The bug

#59302: a canister is shoved down the stairs onto an open crate on the level below. The player can then close the crate, and the canister is inside it, which is not supposed to be possible (closets and crates are not meant to hold dense objects like that). The reporter's screenshots show the result. In the comments, one person suspected teleporters can do the same; another traced the code in a debugger and was confused because `AM.density` was true but the `if` appeared to be skipped, which they later put down to a debugger quirk (crates set `allow_dense`, which the debugger view did not show).

## Reproduction

The real route (shoving a canister down stairs onto an open crate, or a teleporter) was not tested: the test map is single-level, and the test used a stand-in that lands a dense object on the open crate's tile without going through the density check.

1. Start a round and open the Lua editor as an admin, standing on a floor tile.
2. Spawn a crate (`/obj/structure/closet/crate`) on the tile and call `open()` on it.
3. Spawn a canister (`/obj/machinery/portable_atmospherics/canister`) on the same tile. Spawning directly onto the tile avoids the movement check that stops a dense object being pushed onto an open crate, the same effect as a fall or teleport landing there.
4. Call `close()` on the crate.

Observed on master: the crate was closed and its contents were the canister. This result comes from the test's written record rather than a raw log I could inspect. An earlier attempt of the same script failed because of Lua indexing errors in the test script itself (not game runtimes) and was redone.

## Cause

`/obj/structure/closet/crate` sets `allow_dense = TRUE` and `dense_when_open = TRUE` (`code/game/objects/structures/crates_lockers/crates.dm:10-11`, defaults `FALSE` at `closets.dm:52-53`). `dense_when_open` makes an open crate dense (`closets.dm:548`), which is what normally keeps dense objects off its tile.

`close()` (`code/game/objects/structures/crates_lockers/closets.dm:612`) calls `take_contents()` (`:617`), which runs `insert()` on everything on the tile, and `insertion_allowed()` (`:575`) decides what is accepted. For objects:

```dm
else if(isobj(AM))
	if((!allow_dense && AM.density) || AM.anchored || AM.has_buckled_mobs() || ismecha(AM))
		return FALSE
```

With `allow_dense = TRUE` a dense, unanchored object passes. So anything dense that is on the open crate's tile when it is closed is taken in. Normally nothing dense can be there, but falling down a z-level and teleporting do not check density.

`allow_dense` itself has a purpose: crates are populated by `take_contents()` at mapload (`closets.dm:191`, via `LateInitialize`) and by the maintenance loot spawner (`code/game/objects/effects/spawners/random/maintenance.dm:72`), and dense objects are legitimately allowed there.

## Fix

One commit: "Fix issue 59302: closing a crate no longer swallows dense objects that got onto its tile", all in `code/game/objects/structures/crates_lockers/closets.dm`.

- `take_contents()`, `insert()` and `insertion_allowed()` get a new argument `dense_allowed = TRUE` (defaulting to the old behaviour), passed down through the three procs.
- In `insertion_allowed()` the density check becomes `AM.density && (!allow_dense || !dense_allowed)`.
- `close()` now calls `take_contents(dense_allowed = FALSE)`.

The mapload population and the maintenance spawner call `take_contents()` without the argument and so still accept dense objects. The alternative of removing `allow_dense` from crates would have broken those cases, and checking density in `close()` only would have duplicated the logic in `insertion_allowed()`. The other overrides of these procs (`supplypod` has its own `take_contents` and `insertion_allowed`, the mimic has its own procs of the same names on a different type) were left alone; the extra argument is simply not used by them.

## Verification

After the fix, the same script was run on a rebuilt test server with a pocket crowbar also spawned on the tile. After `close()` the crate was closed and contained only the crowbar; the canister was on the floor. No new runtimes were logged.

Not checked: a real fall down a z-level or a teleporter; the stair-push scenario; mapload crates that contain dense objects (the code path is unchanged because the default argument is TRUE, but it was not run); the supply pod, mimic crate and body bag module paths (the last also calls `take_contents()` and keeps the default); any other closet type than the standard crate. The closed crate remained dense on a tile that still holds the canister, which is the natural result and was not examined further.

## Notes

- The fix removes the symptom (the canister vanishing into the crate) but not the underlying overlap: a dense object that fell onto an open crate's tile still sits there, and closing the crate makes the crate dense on top of it. Preventing the fall or teleport from landing on a dense open crate would be a separate change.
- Closing a crate no longer takes any dense unanchored object from the tile. Normal play should not rely on this, since dense objects cannot be moved there by walking or pushing, but a maintainer should check whether anything else deliberately does so (for example placing a dense object with an admin tool, or a special crate type that allows it).
- A person in the issue guessed the teleporter case works as well; by the cause above it should, but it was not tested.
