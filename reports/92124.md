# #92124: Holograms and holodisk replays ignore the size of the person they copy

| | |
|---|---|
| Issues | [#92124](https://github.com/tgstation/tgstation/issues/92124): verified, fixed |
| Status | Fixed on the branch; checked by reading transform values, not visually |
| Fix branch | [fix/92124](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/92124) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Holopad projections and holodisk replays copy the caller's icon, icon state and overlays, but never their transform, so a mob enlarged by growth serum or gigantism appears at normal size as a hologram. The fix copies the scale: the replay hologram takes the recorded image's transform, and a live hologram gets a scale (plus the matching vertical offset) built from the caller's `current_size`. The lying-down rotation is deliberately not copied for live holograms. An issue comment argues the old behaviour may be intentional, to limit spam with huge looping holograms; the inputs show no code-level reason for it.

## The bug

A player with growth serum (the reporter also lists gigantism, or the Red Queen drink) records themselves on a holodisk, or calls from a holopad. The hologram appears normal sized, while a statue of the same player keeps the size. The reporter wanted giant holograms. Commenters disagreed on whether the omission is intentional: one guessed it prevents spam with large looping holograms; the reporter replied that the cost of getting growth serum is a fair price.

## Reproduction

Reproduced by calling procs and reading values with admin tools. No client view of the hologram was checked, and a real recording made with a camera or holopad recording was not used.

1. Using the Lua editor, spawned a human and called `update_transform(2)` on it. This is what growth serum does: `current_size` becomes 2 and the transform becomes scale 2 plus a translation of 16.
2. Spawned a holopad and a holodisk. Created a record, called `set_caller_image(human)` on it, put the disk in the pad (`pad.disk = disk`) and called `pad:replay_start()`.
3. Read the transforms.

Before the fix: `record.caller_image.transform.a` was 2, so the recorded image kept the size, but the replay hologram's `transform.a` was 1 and `f` was 0 (default).

## Cause

Both hologram creation paths copy appearance by hand and omit the transform:

- Live projection, `activate_holo()` (`code/game/machinery/hologram.dm:542`): sets `hologram.icon`, `icon_state` and calls `copy_overlays(work_off, TRUE)` (line 558), then `makeHologram()`. No transform.
- Replay, `setup_replay_holo()` (`code/game/machinery/hologram.dm:802`): the same three copies (lines 805-807), then `makeHologram()`. No transform.

Size on living mobs is applied through the mob's transform (`update_transform()` in `code/modules/mob/living/living_update_icons.dm:5`, with `get_transform_translation_size()` at `:68`), so it is lost with the copy. The image the replay copies from (`work_off`) is made with `image(user)`, so it already carries the transform; only the copy was missing.

## Fix

One commit: "Fix issue 92124: holograms now reflect the size of the person they are copied from", in `code/game/machinery/hologram.dm`.

- Replay (`setup_replay_holo()`): `hologram.transform = work_off.transform`.
- Live (`activate_holo()`): when the caller is a living mob, not an AI, and `current_size != RESIZE_DEFAULT_SIZE`, set
  `hologram.transform = matrix().Scale(current_size).Translate(0, get_transform_translation_size(current_size))`.

Live holograms get only the scale, not the caller's transform, on purpose. The hologram is made when the call starts and not refreshed, so copying the full transform would leave a hologram rotated if the caller was lying down at that moment and then stood up. Size-1 callers are untouched, so normal holograms are unchanged.

## Verification

After rebuilding:

- Replay of the disk made in the reproduction: the replay hologram had `a = 2`, `f = 16`.
- Live: `pad:activate_holo(giant)` produced a hologram named "<name> (Hologram)" with `a = 2`, `f = 16` (read with SDQL2). A normal-size human's hologram had `a = 1`, `f = 0`, unchanged.

Not checked: how it looks in a client (clipping, layering, lighting of oversized holograms), a disk recorded through the real camera or recording flow (the notes say the camera code at `camera.dm:443` uses the same `set_caller_image`, so it should work), AI holograms (excluded by the `!AI` condition), mobs smaller than size 1, and the preset holoimage path in `replay_entry()` (`hologram.dm:~915`), which builds its own image and was not changed.

## Notes

- Design: whether giant holograms are wanted is a maintainer decision. The only argument against in the issue is that large looping holograms could be used to block sight; no code limits or special-cases hologram size, and this was not tested for abuse. If it is a concern, a cap on the scale applied would be a small change in the same two places.
- The issue is labelled as a consistency issue, with the statue case already preserving size.
- Live holograms ignore rotation but replay holograms copy the whole recorded transform, so a replay of a recording made while the caller was lying down would show them lying down if the recorded image carried that. This was not tested.
