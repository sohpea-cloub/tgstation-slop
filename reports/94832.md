## Summary

If a player casts a fishing rod and drops it while the hook is still in the air, the hook still lands and hooks its target. The new fishing line is attached to the former holder, who no longer has the rod, and nothing ever removes it. The fix makes `/obj/projectile/fishing_cast/on_hit` do nothing unless the firer is still a mob that holds the rod. #91833 (a bear-trap hook that could not be removed from a space carp) was not reproduced, and its cause is unknown.

## #94832: the line persists after the rod is dropped

### The bug

As reported: cast the line, drop the rod while the hook is in the air, and a line stays tied to your mob. The reporter says it works as a marker that shows where you are anywhere on the Z map. The issue's title calls it "suit sensors set to maximum".

### Reproduction

Using the Lua editor on the test server (as an observer with admin tools):

1. Spawn a human, a fishing rod and a toolbox about 4 tiles away.
2. Call `rod:cast_line(toolbox, human)`, then immediately `human:dropItemToGround(rod)`, so the rod is dropped while the hook is still flying.
3. After the hook landed, inspected the rod.

Observed on master: the rod was on the floor, `rod.currently_hooked` was the toolbox, and `rod.fishing_line` was a `/datum/beam/held` whose origin was the human who had dropped the rod (the beam was drawn). The same happened with the jawed hook on a possessed space carp: the "Snagged By Jaws" alert appeared on the carp while the rod lay on the floor.

This reproduced the bug by calling the cast and drop procs directly, not by a player throwing and dropping the rod with clicks.

### Cause

`/obj/item/fishing_rod/dropped()` (`code/modules/fishing/fishing_rod.dm:328-330`) deletes the fishing line with `QDEL_NULL(fishing_line)`. A cast creates a projectile that is still in flight at that moment. When it hits, `/obj/projectile/fishing_cast/on_hit` (`fishing_rod.dm:870-876`) goes on to call:

```dm
owner.hook_hit(target, firer)
```

which reaches `hook_item` and `create_fishing_line(target, user)` although the rod is no longer held. The new beam has the former holder as its origin. `dropped()` has already run, so nothing deletes it, and its line-of-sight check uses the rod lying on the floor.

### Fix

One commit, "Fix issue 94832: don't hook anything if the fishing rod was dropped while the hook was still in the air". In `on_hit`, after the existing cleanup of the old beam and the `blocked >= 100` check, it returns before `hook_hit` unless the firer is still a mob that contains the rod:

```dm
if(!ismob(firer) || !firer.contains(owner))
	return
```

The cleanup (`QDEL_NULL(owner.fishing_line)`, `owner.casting = FALSE`) still runs before the check, so a dropped rod is left in its normal idle state.

### Verification

On the test server, after the fix, the same drop-in-flight sequence was run with a plain hook on the toolbox and with the jaws hook on a carp. In both cases `fishing_line` was nil, `currently_hooked` was nil, no hooked status effect was applied, and `casting` was 0. A normal cast while still holding the rod still hooked the toolbox, with `fishing_line` a `/datum/beam/held` and `currently_hooked` the toolbox.

Not checked: a player doing the throw-and-drop with the mouse, the case where another mob picks the rod up mid-flight, and a rod that is stored in a container instead of dropped (the new check uses `firer.contains(owner)`, so a rod put into a bag the firer carries would still count as held).

## #91833: bear-trap hook can't be removed from a space carp

### The bug

Reported on a test merge of PR 91290, on client 516.1663: a space carp hit by a bear-trap fishing hook can never remove it with the "remove" action, even after the progress bar completes and the "removed" message shows, or after going far away. The reporter suspects it needs the fisherman to fall down a Z level and drop the rod.

### Reproduction

Not reproduced. On the test server, with a possessed carp hooked by the jaws hook, the unhook worked: clicking the alert ran a 10 second bar and gave "hook removed". The same worked with the rod on the floor, with the rod dropped, and with the hooker moved to another Z level. No cause was found.

### Notes

- A possible explanation is that the report involved several hook sources on one status effect (unhooking removes only one random source). This is a guess; it was not reproduced.
- The stale line from the mid-flight drop (#94832) could have contributed, because a carp could be hooked by a line from a mob that no longer held the rod. That path is now closed, but nothing shows it was the cause here.
- The report was filed against a test merge, so the code may have differed from master.
