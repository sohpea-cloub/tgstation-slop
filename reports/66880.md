## Summary

The 2022 report says that spawning an Obsessed antagonist from the Game Mode Panel produced an error. The screenshot in the issue could not be read, and the panel and the code behind it have since been rewritten. On current master, forcing the Obsession ruleset from the Dynamic Panel produced no runtime. There is one related quirk: if no other player is a valid obsession target, the trauma is silently discarded while the dynamic log still says the candidate was selected. No fix was committed.

## The bug

The reporter, an admin, added an Obsessed antagonist through the Game Mode Panel so that it would pick a random person. An error was shown, and the reporter did not know whether they had done anything wrong. The issue text gives no error message. The round was running the Dynamic 2022 testmerge (#65997), so the error most likely came from that testmerge's code.

## Reproduction

I could not reproduce the error. What I did on master:

1. Started the round and joined as an Assistant, so a candidate with a mind and a client existed.
2. Opened the Dynamic Panel verb and ran the "Obsession" ruleset (`/datum/dynamic_ruleset/midround/from_living/obsesed`) with the panel's execute button.
3. The first attempt failed cleanly. `dynamic.log` said "preparation failed! Reason: Not enough eligible candidates. Have: 0, Need: 1". The admin's own preferences did not include the "Obsessed" role.
4. Using the Lua editor, I added "Obsessed" to that client's `prefs.be_special` and ran the ruleset again. `dynamic.log` then said the player "has been selected for Midround Obsessed", and the panel listed "Obsession" as an active ruleset.
5. `game.log` then showed the character losing `/datum/brain_trauma/special/obsessed`, and `runtime.log` contained 0 "runtime error" entries.
6. As a control, I tested the success path directly. With the Lua editor I spawned a second human with a mind, created an obsessed trauma with its `obsession` set to that human, and gave it to the first character's brain with `brain_gain_trauma`. The objectives were printed and no runtime occurred. This step called the procs directly and did not go through the panel.

Only one client was connected during the panel test, which is why the trauma was lost (see Cause).

## Cause

Nothing in current code produces an error on this path. The silent failure in step 5 works like this:

- `assign_role` for the ruleset calls `brain.brain_gain_trauma(/datum/brain_trauma/special/obsessed)` and ignores the result (`code/controllers/subsystem/dynamic/dynamic_ruleset_midround.dm:1271`).
- The trauma's `on_gain()` needs a target. If none was preset, it calls `find_obsession()` (`code/datums/brain_damage/creepy_trauma.dm:211`). That proc only accepts living humans who have a client and are not the owner (`creepy_trauma.dm:222`).
- If it finds nobody, `on_gain()` returns FALSE (`creepy_trauma.dm:25-31`), and `brain_gain_trauma` deletes the trauma and returns null (`code/modules/mob/living/brain/brain_item.dm:693`).

So with fewer than two clients the ruleset reports success but nothing happens.

## Fix

None was committed. A possible improvement, not implemented: make `is_valid_candidate` for the ruleset (`dynamic_ruleset_midround.dm:1264`) also require that `find_obsession()` can find a target. Dynamic would then not pick a candidate whose trauma is going to be discarded.

## Verification

Only the current-master behaviour described above was checked. I could not check the original 2022 error, since the code it came from is gone. A live round with several players was not tested.

## Notes

- The report was closed as not reproduced because the original error cannot be matched to any existing code, not because it was proven never to have happened.
- The silent no-op above is a minor usability gap for admins, not the reported bug.
