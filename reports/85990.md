# #85990: Admin combo HUD breaks after a mindswap

| | |
|---|---|
| Issues | [#85990](https://github.com/tgstation/tgstation/issues/85990): verified, fixed |
| Status | Fixed (one commit); checked on the HUD datums, not on a rendered client |
| Fix branch | [fix/85990](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/85990) |

## Summary

After a mindswap, the mind moved into the other participant's body did not get its antagonist (combo) HUD image, because `mind/transfer_to()` tried to add a HUD to a body that still held the previous occupant's one under the same key. The fix deletes the displaced mind's HUD before taking the body. I did not reproduce the exact symptom in the report ("both participants show a wizard HUD"); what I saw was a broken HUD on the swapped-in mind.

## The bug

The report says that with the admin combo HUD on, both parties of a mindswap are shown as wizards. In the test the antagonist HUD was wrong after a swap, but in a different way: the wizard's mind ended up with no HUD at all.

## Reproduction

On master, with the Lua editor:

1. Spawn two humans, W and B, and call `mind_initialize()` on both.
2. Give W's mind the wizard antagonist datum.
3. Call `swap_minds(W, B)` on the mind transfer spell (`/datum/action/cooldown/spell/pointed/mind_transfer`), the same code path mindswap uses. This was done by calling the spell proc directly, not by casting it as a player.
4. Read each mind's `antag_hud` (the alternate appearance datum) and the images it holds.

Observed on unmodified master after the swap: the wizard's `antag_hud` was `nil`, and the other mind's HUD held 0 images. The combo HUD on a real client was not viewed.

I did not see both minds showing a wizard HUD. The report is from August 2024 and the code may have changed since, so the failure may now appear differently, but the HUD was clearly broken after a swap.

This is not the same as #82587 (the notes say that concerns `Login` and `combo_hud_enabled`, a different path).

## Cause

`/datum/mind/proc/transfer_to()` (`code/datums/mind/_mind.dm`, around line 172) handles a body that already has a mind with:

```dm
if(new_character.mind) //disassociate any mind currently in our new body's mind variable
	new_character.mind.set_current(null)
```

That detaches the old mind from the body but does not touch its `antag_hud`, which is an alternate appearance with the key `"combo_hud"` still registered on the body. A little later the proc does:

```dm
QDEL_NULL(antag_hud)
new_character.mind = src
antag_hud = new_character.add_alt_appearance(/datum/atom_hud/alternate_appearance/basic/antagonist_hud, "combo_hud", src)
```

`add_alt_appearance()` does nothing if the atom already has an appearance with that key. In a swap, the target body still holds the previous occupant's `combo_hud`, so the incoming mind's call returns without adding anything and `antag_hud` is left null. The old mind's HUD also stays attached to a body that is no longer its own.

## Fix

One commit, "Fix issue 85990: free the combo hud slot of the mind a transferring mind replaces". In the block that disassociates the body's current mind, it adds `QDEL_NULL(new_character.mind.antag_hud)` before `set_current(null)`, with a comment explaining why. The slot is then free when the incoming mind adds its own HUD.

## Verification

After the fix, the same swap was repeated. Result: the wizard W's mind had its antag HUD (`wizard`, from `icons/mob/huds/antag_hud.dmi`, 1 image) on its new body; B's mind had no HUD (`nil`, 0 images) on its new body, as expected for a non-antagonist; and both bodies had a `combo_hud` alternate appearance.

Not checked: how the combo HUD looks on a real admin client (per-client HUD images could not be rendered in the test); a mindswap done through the real spell cast or through other `transfer_to()` callers (only the spell's `swap_minds()` was called); a second swap back.

## Notes

- The problem is not specific to wizards or to mindswap; any `transfer_to()` into a body that has a different mind with a HUD would hit it.
