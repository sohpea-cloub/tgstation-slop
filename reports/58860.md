## Summary

Both reports describe coloured carpet stacks (black, blue, red, ...) being turned into some other carpet through the tile "reskin" radial menu, with no way back, and merging with the wrong stacks. On master the coloured carpet subtypes explicitly set `tile_reskin_types = null` and each has its own `merge_type`, so the reskin menu is not offered on them and they do not merge with the plain carpet family. The behaviour could not be reproduced, and no code was changed.

## The bug

#58860 (2021): coloured carpet tile stacks (the reporter named black, blue and cyan, "basically any carpet that's a subtype of `/obj/item/stack/tile/carpet`") could be reskinned, by using the stack in hand, into the red carpet's pattern variants. There was no way to reskin back, and the resulting stack merged with real red carpet stacks. The reporter suggested making the plain/symbol/star carpets subtypes of the red carpet.

#73184 (2023) describes the same thing from the other side: re-patterning a coloured carpet stack yielded the plain carpet design, and the coloured stack ended up as normal carpet. Its numbered steps are short and do not say which colours or patterns were involved, so the match to #58860 is by symptom, not by exact steps.

The mechanism both rely on is the tile reskin radial in `code/game/objects/items/stacks/tiles/tile_reskinning.dm`: `attack_self()` opens a menu built from the stack's `tile_reskin_types` and, if one is chosen, `tile_reskin()` replaces the stack with a new stack of the chosen type and the same amount.

## Reproduction

Not reproduced. What was done on master:

1. Started a round and opened the Lua editor as an admin.
2. Spawned one stack each of `/obj/item/stack/tile/carpet`, `.../carpet/black`, `.../carpet/red`, `.../carpet/royalblue`, `.../carpet/symbol`, `.../carpet/star`, `.../carpet/neon` and `.../carpet/donk`, and read `tile_reskin_types`, `tile_rotate_dirs` and `merge_type` from each.
3. Observed (number is the length of the reskin list):

```
carpet            reskin=3  rot=false  merge=/obj/item/stack/tile/carpet
carpet/black      reskin=0  rot=false  merge=/obj/item/stack/tile/carpet/black
carpet/red        reskin=0  rot=false  merge=/obj/item/stack/tile/carpet/red
carpet/royalblue  reskin=0  rot=false  merge=/obj/item/stack/tile/carpet/royalblue
carpet/symbol     reskin=3  rot=true   merge=/obj/item/stack/tile/carpet/symbol
carpet/star       reskin=3
carpet/neon       reskin=0
carpet/donk       reskin=0
```

(The rotate and merge values for the star, neon and donk stacks were not recorded in the written results; for neon and donk only the empty reskin list was. Symbol and star each had 3 reskin options.)

The coloured carpets have no reskin list and no rotate directions, so `attack_self()` falls through to the parent `..()` and no radial opens. The test did not open the radial in the UI by hand, since there was nothing to click; the conclusion is from the variable values and the code path.

## Cause

Historically (the likely cause of the report, not shown on master): the coloured carpet types are subtypes of `/obj/item/stack/tile/carpet` and so inherited that parent's `tile_reskin_types` (plain carpet, symbol, star) and its `merge_type`. That fits #58860's description. The state of the code when the issue was filed was not inspected, and history in the test checkout is shallow, so the change that fixed it, and when, is unknown.

On master (`code/game/objects/items/stacks/tiles/tile_types.dm`):

- The base `/obj/item/stack/tile/carpet` (line 227) sets `merge_type = /obj/item/stack/tile/carpet` and `tile_reskin_types = list(carpet, carpet/symbol, carpet/star)`. `symbol` (line 243) and `star` (line 252) have their own `merge_type`; `symbol` also has `tile_rotate_dirs`.
- Every coloured subtype from `/obj/item/stack/tile/carpet/black` (line 260) to `/obj/item/stack/tile/carpet/human` (line 419-426) sets its own `merge_type` and `tile_reskin_types = null`, e.g.:

```dm
/obj/item/stack/tile/carpet/black
	...
	merge_type = /obj/item/stack/tile/carpet/black
	tile_reskin_types = null
```

`stack.dm` only merges stacks whose `merge_type` match (`code/game/objects/items/stacks/stack.dm:662`), so a coloured stack does not merge with the plain/symbol/star stacks or with other colours.

The other neon carpets (`carpet/neon`, line 476-477) also set `tile_reskin_types = null`; `carpet/neon/simple` and its colour variants (line 516 onward) deliberately offer a reskin among their own dotted/no-dot pair only.

## Fix

None. The reported behaviour is already gone on master.

## Verification

Checked only that the relevant variables have the values above on a live server and that `attack_self()` has no branch for a stack with neither a reskin list nor rotate directions. Not checked: actually using a coloured stack in hand and clicking, alternate ways of converting a coloured carpet stack (crafting, other tools), and every one of the roughly twenty coloured subtypes individually; the rest were read from source (all have `tile_reskin_types = null` and a unique `merge_type` in the file as listed above).

## Notes

- The conversion #73184 describes ("re-pattern a coloured carpet, get a plain/other carpet") cannot happen via the reskin menu any more for the same reason. If the reporter was using a specific variant (e.g. a coloured carpet that has a patterned subtype), the inputs do not say which; the neon carpets are the only coloured family on master with an intended reskin list.
- The feature the #58860 reporter hints at as a nicety, reskinning among a coloured family (e.g. red symbol/star), does not exist on master. Only the plain, symbol and star carpets and the simple neon carpets have reskin lists.
- Wood and bamboo tiles, which the reporter says reskin among themselves usefully, were not examined.
