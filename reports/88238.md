# #88238: Very sticky web overlay has a TOPDOWN_LAYER layer on a floating plane

| | |

| Status | Fixed (one commit), verified on the test server |

## Summary

`/obj/structure/spider/stickyweb/very_sticky/update_overlays()` builds its `sticky_overlay` mutable appearance with the default floating plane (`FLOAT_PLANE`) but with `layer = layer + 1`, and the web's own layer is a topdown layer (around 10000). The topdown sanity check forbids that combination and raises a runtime. The fix gives the overlay `FLOOR_PLANE`, the plane the web itself is on, plus `offset_spokesman = src` so the plane is offset correctly on multi-z maps. The check only runs in unit-test builds, so players never saw a runtime; rendering is unchanged.

## The bug

The issue was reported from a CI run. With the `topdown_filtering` focus test enabled, the two very sticky webs in the `garbagetruck4` ruin each produced a `/mutable_appearance is NOT ALLOWED to have a TOPDOWN_LAYER layer due to its plane, but it did!` runtime while icon smoothing initialised them. In a normal build nothing is visible: `mutable_appearance()` only calls the validity check when `PERFORM_ALL_TESTS(focus_only/topdown_filtering)` is true, and that macro is constant `FALSE` outside unit-test builds (`code/__DEFINES/unit_tests.dm`).

The underlying inconsistency is real, though: the overlay is a topdown-layer appearance that is not on a topdown plane.

## Reproduction

The normal player-visible action (spawn a very sticky web in a regular build) does not produce the runtime, because the check is compiled out. It was reproduced by running the same check by hand on the overlay the web generates. `check_topdown_validity` exists in normal builds, only its call from `mutable_appearance()` is gated.

1. Start a round on the test server (master `87b93338`) as an observer and open the Lua editor.
2. In a Lua state, spawn a very sticky web and fetch the overlay list it produces, then run the check on the last element (the `sticky_overlay` appearance):

   ```lua
   local SS13 = require('SS13')
   local me = SS13.get_runner_client().mob
   local w = SS13.new('/obj/structure/spider/stickyweb/very_sticky', me.loc)
   local l = w:update_overlays(0)
   local ma = l[#l]
   dm.global_procs.check_topdown_validity(ma)
   ```
3. Read the newest round's `runtime.log`.

Observed before the fix:

```
/mutable_appearance is NOT ALLOWED to have a TOPDOWN_LAYER layer due to its plane, but it did! layer: (10016) plane: (-32767)
```

The web itself was at layer 10015 on plane -6, which is `FLOOR_PLANE`. The overlay's plane, -32767, is `FLOAT_PLANE`, which is not in `GLOB.topdown_planes`. This is the same message and the same shape of values as in the issue's CI log (layer 10007 in the CI log, 10016 here).

The ruin-based steps in the issue (spawn `garbagetruck4` with `topdown_filtering` tests on) were not run; the manual check above exercises the same code path.

## Cause

`code/game/objects/effects/spiderwebs.dm:146-151`:

```dm
/obj/structure/spider/stickyweb/very_sticky/update_overlays()
	. = ..()
	var/mutable_appearance/web_overlay = mutable_appearance(icon = 'icons/effects/web.dmi', icon_state = "sticky_overlay", layer = layer + 1)
```

The call passes no `plane`, so it defaults to `FLOAT_PLANE`, which means the appearance inherits the plane of the atom it is drawn on. But `layer = layer + 1` copies the web's topdown layer. The rule documented in `code/__DEFINES/layers.dm` is "ANYTHING on the floor plane needs TOPDOWN_LAYER, and nothing that isn't on the floor plane can have it". `check_topdown_validity()` (`code/__HELPERS/_planes.dm:98-105`) enforces this by testing the appearance's plane against `GLOB.topdown_planes`, and `FLOAT_PLANE` is not in that list, so the layer is rejected.

## Fix

One commit, "Fix issue 88238: very sticky web overlay used a floating plane with a TOPDOWN_LAYER layer". In `very_sticky/update_overlays()` the `mutable_appearance()` call now passes `offset_spokesman = src, plane = FLOOR_PLANE`. `offset_spokesman` is required by `mutable_appearance()` whenever a non-floating plane is given, so the plane can be adjusted for the web's z-level offset.

The first attempt was `plane = plane` (reuse the web's plane). That was changed to the explicit `FLOOR_PLANE`, which matches how other floor-plane appearances are built in the codebase (for example `code/__HELPERS/icon_smoothing.dm:317`). The web's own plane is `FLOOR_PLANE`, so the result is the same.

## Verification

- Rebuilt the test server with the change, started a new round and repeated the Lua steps above. The newest `runtime.log` contained 0 `NOT ALLOWED` lines, where before it had the runtime.

## Notes

- The bug is invisible in normal builds; it only shows in unit-test builds with the topdown filtering check active, which is how it appeared in CI.
- Other `mutable_appearance()` calls that combine a topdown layer with the default plane would fail the same way; none were searched for here.
