# #81889: Returning to body removes the ghost role poll alert

| | |
|---|---|
| Issues | [#81889](https://github.com/tgstation/tgstation/issues/81889): verified, fixed |
| Status | Verified on the test server; fix committed |
| Fix branch | [fix/81889](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/81889) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Ghost role poll alerts (the "Looking for candidates" button used for ERT and other ghost roles) are thrown only on the ghost mob that was polled. If the player re-enters their body, that ghost is deleted and the alert goes with it. When they ghost again they get a new observer that nobody offers the still-running poll to, so they cannot sign up. The fix makes each poll remember who it was offered to, and re-offers it to that player when a new observer logs in.

## The bug

An admin summons an ERT (or any ghost poll starts). A dead player who accidentally goes back into their body before pressing "yes", and then ghosts out again, no longer has the poll button. The poll keeps running for everyone else, but that player cannot take part in it.

## Reproduction

On master, with admin tools:

1. Start the round, join as an Assistant, then use AGhost.
2. From the Lua editor, start a ghost poll. A direct call from Lua would sleep, so it was scheduled with a timer. The script was:
   `SS13.new('/datum/callback', SSpolling, 'poll_ghost_candidates', 'Test ERT poll?', nil, nil, 3000)` passed to `dm.global_procs._addtimer(cb, 1)`.
   The poll lasted 5 minutes. The ghost received the "Looking for candidates" alert.
3. Use Re-enter Corpse, then AGhost again.
4. Check the new ghost's screen.

Observed on master: the new ghost had no poll alert. It never came back, although the poll was still running. The poll was started by calling the polling proc from Lua, not through the ERT admin verb. The player actions (re-enter corpse, ghost again) were done as described.

## Cause

`SSpolling.poll_candidates` (`code/controllers/subsystem/polling.dm`, the loop over `group` starting around line 83) calls `throw_alert` on each polled mob only once, at the start of the poll. The alert is a screen object on that mob. Re-entering the body deletes the ghost, and its alert is deleted with it (the poll's `clear_alert_ref` handler on `COMSIG_QDELETING` just drops the reference). `ghostize()` (`code/modules/mob/dead/observer/observer.dm:264`) then creates a new observer. Nothing in the poll knows about that new mob. The poll's `signed_up` list (`code/datums/candidate_poll.dm`) also holds the old, dead ghost.

## Fix

One commit, "Fix issue 81889: restore running poll alerts when a polled player becomes a ghost again":

- `code/datums/candidate_poll.dm`: the poll now stores the arguments needed to offer itself again (`check_role`, `check_jobban`, `alert_pic`, `chat_text_border_icon`, `start_signed_up`) and `polled_ckeys`, the ckeys of everyone it was offered to. `alert_pic` and `chat_text_border_icon` are cleared in `Destroy()`.
- `code/controllers/subsystem/polling.dm`: the per-candidate body of `poll_candidates` (eligibility checks, alert, overlays, chat message, sound) moved unchanged in intent into a new `SSpolling.offer_poll(mob, poll, flash_window, restored)`. `poll_candidates` now calls it for each mob. A new `SSpolling.restore_poll_alerts(ghost)` goes through the running polls and re-offers each one whose `polled_ckeys` contains the ghost's ckey. Restored offers do not flash the window or play the sound, and are skipped if the mob already has that poll's alert, so a reconnect does not duplicate it.
- `code/modules/mob/dead/observer/login.dm`: `/mob/dead/observer/Login()` calls `SSpolling.restore_poll_alerts(src)`.

Hooking observer `Login()` was chosen because it covers every way a player becomes a ghost again (re-entering and re-ghosting, reconnecting), without touching each ghostize path.

## Verification

Same steps as above, after the fix: the new ghost's screen listed the "Looking for candidates" alert again, and clicking it signed the player up ("You have signed up for !"). The empty role name is not caused by the fix: the test poll was started with no `role_name_text`. No runtimes came from the change; the only runtime seen was from a mistaken Lua call (`addtimer` instead of `_addtimer`) during the test.

Not checked: the chat message and sound on restore, the ERT admin verb itself, polls with `start_signed_up`, several polls running at once, a poll expiring after a restore, the Teleport / Never For This Round links, reconnecting while a poll runs, and polls with a real role name.

## Notes

- An earlier sign-up is not carried over. If the player had signed up before re-entering the body, they must sign up again (polls with `start_signed_up` re-sign them automatically).
- Possible defect in the fix, found by reading the diff and not tested. In `offer_poll`, the "Sign up inheritance and stacking" loop uses `return` where the original code used `continue`. `new_poll` is itself in `currently_polling`, so the loop can reach its `new_poll == other_poll` check and return before the alert image, the chat message and `START_PROCESSING` run. The alert is already thrown by then, which fits the observed result (the alert was present and could be clicked), but the alert's image, the chat message and the timer updates may be skipped, for the original offer as well as restored ones. This should be changed back to `continue` and re-tested before upstreaming.
- The issue was filed against client 515.1633; this was tested on 516.
