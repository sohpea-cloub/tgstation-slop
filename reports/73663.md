## Summary

A pet told to follow its owner (Ian, or any corgi) walks up to a closed door and stops, because its movement loop uses `get_step_to()`, which routes around dense atoms and never bumps the door. The fix switches the follow command's `move_to_target` node to the JPS movement type, so the pet paths through doors it can pass, and makes the corgi's `get_access()` null-safe, since JPS calls it and it runtimed for corgis without an ID card. #73664 (following across z-levels) is a missing feature: nothing in the follow behaviour handles a target on another z-level. It was checked in the code only and not changed.

## The bug

### #73663
A player befriends or commands a corgi to follow, walks through a door and closes it behind them. The corgi comes to the door and stays there. It does not open the door, even when the door needs no access. The issue's reporter also gave the corgi an ID, with the same result.

The follow behaviour never bumps the door at all. A mob normally opens a door by walking into it (`Bumped`), but the follow movement steps around dense things, so the bump never happens.

### #73664
A corgi following its owner stops when the owner changes z-level (stairs), and resumes only when the owner comes back.

## Reproduction

### #73663
1. On the test server, round started, build a sealed test box with admin tools (Lua editor): walls forming a room from x110 to x118 and y141 to y147, with a wall column at x114 and plating inside.
2. Place an airlock with no access requirement in that column at 114,144.
3. Spawn a human at 116,144 (east of the door) and a corgi at 112,144 (west).
4. Call `befriend` on the corgi with the human. The dog follow command has `activate_on_befriend`, so the corgi starts following at once, with the human as `BB_current_pet_target`. (This starts the follow through the proc call rather than a player radial-menu or "follow" speech command, but it runs the same follow behaviour.)
5. Sample the corgi's x coordinate every 0.5 s for 15 s.

Observed on master: the corgi walked to 113,144, directly in front of the door, and stayed there for the whole 15 s. The airlock stayed closed.

### #73664
Not reproduced in game. Only the code was checked (see Cause).

## Cause

### #73663
The follow command's behaviour tree (`code/datums/ai/basic_mobs/pet_commands/pet_command_follow.bt.json`) has a `move_to_target` node with no movement type of its own, so it uses the controller's default. Dogs use `/datum/ai_movement/basic_avoidance` (`code/datums/ai/dog/dog_controller.dm:7`). That movement type drives a `move_to` move loop (`code/controllers/subsystem/movement/movement_types.dm:613-620`):

```dm
/datum/move_loop/has_target/dist_bound/move_to/move()
	. = ..()
	...
	var/turf/next = get_step_to(moving, target)
	moving.Move(next, get_dir(moving, next), FALSE, ...)
```

`get_step_to()` picks a step that avoids dense atoms. A closed airlock is dense, so the pet never moves into it, `/obj/machinery/door/Bumped` (`code/game/machinery/doors/door.dm:254`) never runs, and the door never opens. There is no fallback when the only route is through the door, so the pet just stays beside it.

A second defect only shows once JPS is used. `/datum/ai_controller/basic_controller/dog/corgi/get_access()` (`code/datums/ai/dog/dog_controller.dm:33`) does `corgi_pawn.access_card.GetAccess()`, and `access_card` is null by default. JPS asks the controller for its access list, so every repath produced a "Cannot execute null.GetAccess()" runtime, about four per second per following corgi.

### #73664
`move_to_target` (`code/datums/ai/generic_behaviors/move_to_target.dm`), the follow tree and both movement types have no handling for a target on a different z-level. `get_dist()` across z-levels returns 127, which is never within the required distance, and neither movement loop crosses stairs or ladders. So following across z-levels was never supported.

## Fix

Commit "Fix issue 73663: Pet follow command uses JPS pathing so pets can open doors" (the only commit) changes three files:

- `code/datums/ai/basic_mobs/pet_commands/pet_command_follow.bt.json`: adds `"movement_type": "/datum/ai_movement/jps"` to the `move_to_target` node's vars. `move_to_target` already supports this variable (it swaps in the given movement type for the duration of the behaviour and restores the original when it finishes), and other behaviour trees use it, for example `monkey_find_weapon.bt.json`. JPS paths through doors the pet is allowed to pass, so the pet walks into the door and bumps it.
- `build/behavior_trees/.../pet_command_follow.bt.compiled.json`: the regenerated compiled form of the same tree, committed alongside.
- `code/datums/ai/dog/dog_controller.dm:33`: `corgi_pawn.access_card?.GetAccess()`, so a corgi without an ID card returns no access instead of runtiming.

The alternative suggested in the issue comments (changing dogs and other mobs to JPS instead of basic avoidance) is the same idea; this change applies it only to the follow command, not to the dog controller's default movement.

## Verification

### #73663
After rebuilding, the same box was rebuilt on the test server with the same setup (human at 116,144, corgi at 112,144, `befriend`):

- The corgi went through the access-free door and reached 115,144, adjacent to the human, within about 12 s. The airlock opening and closing sounds were heard at 114,144.
- The runtime log showed no runtimes.
- A second box had an airlock at 114,154 requiring engineering access. A corgi with no ID stayed at 112,155 and the door stayed closed. A corgi given an engineering ID card also stayed outside (at 113,154).

Not checked: other pet types that share this follow tree; follow behaviour in open rooms with many followers or in crowded areas; frame or pathfinding cost with several followers; the player-facing way of issuing the command (radial menu, speech "follow"/"heel"/"walkies"); the original reporter's ID-carrying case on an access-free door beyond the above.

## Notes

- **Behaviour and performance change.** The edit is in the shared follow tree, so every pet that uses the follow command now follows with JPS instead of `basic_avoidance`. JPS computes paths (through the pathfinder subsystem, re-pathing about every 0.5 s) instead of calling the cheap `get_step_to()`, so many simultaneous followers will cost more. A maintainer may prefer a narrower change.
- **Locked doors are still not opened by a corgi's ID.** `door.Bumped` returns early for mobs with `TRAIT_HANDS_BLOCKED` unless `check_access(null)` passes (`code/game/machinery/doors/door.dm`, around line 267), so a corgi only opens doors that need no access. The ID in `access_card` is not honoured for bumping. This is existing behaviour and was not changed; the reporter's "even if they have access" expectation is therefore only met for access-free doors.
- **#73664 would need new behaviour**, for example pathing to stairs or a z-move when the leader changes z-level; the issue's comments suggest listening for the target's z-level change. It looks like a feature request rather than a small bug, and it is related to #73663 only by being part of the same follow behaviour.
