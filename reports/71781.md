# #71781: Luxury shuttle scanner loses partial payments

| | |
|---|---|
| Issues | [#71781](https://github.com/tgstation/tgstation/issues/71781): verified, fixed |
| Status | Fixed (one commit) |
| Fix branch | [fix/71781](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/71781) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The luxury shuttle's scanner gate takes the whole bank balance of anyone who cannot cover the entry fee in one go, so they can pay in instalments. It zeroed the account first and then added the account's balance to the running total, which was by then 0. The payer lost the money and got no credit for it. The fix reads the balance into a variable before the account is zeroed.

## The bug

A player with less than the entry fee (500 credits) in their ID's bank account walks into the scanner and finds their account at 0, with nothing counted towards the fee. Later payments are counted from zero again, so a player can pay more than the fee in total and still be refused. The issue reporter lost money this way twice, and says the partial-payment chat messages did not show.

## Reproduction

Using the Lua editor on the test server:

1. Spawn a human with an ID card that has a bank account at 60 credits, and spawn an `/obj/machinery/scanner_gate/luxury_shuttle` on the same tile.
2. Call `Bumped(human)` on the gate directly. Walking into a gate on a landed shuttle was not done; the same `Bumped` proc is what the walk-in calls.
3. Result: the account went from 60 to 0, and the gate's `payees` entry for the human was 0.
4. Set the balance to 400 and bump again: 400 went to 0, and `payees` was still 0. The money vanished, as the issue describes.

This was a direct call on a script-spawned mob and gate. It reproduces the account and `payees` arithmetic, not the walk-in or the chat messages.

## Cause

`code/modules/shuttle/misc/special.dm:293-295`, in the luxury shuttle gate's `Bumped()`:

```dm
if(account.account_balance < threshold - payees[AM])
	account.adjust_money(-account.account_balance, "Scanner Gate: Entry Fee")
	payees[AM] += account.account_balance
```

`adjust_money()` takes the whole balance out of the account, so the next line reads `account.account_balance` as 0 and adds nothing to `payees[AM]`. The `else` branch (`special.dm:296-299`) is correct: it stores `money_owed` in a variable and uses that for both lines.

The reporter also tried a second payment with a credit chip and the account went to 0 again. That follows from the same defect: nothing was ever credited, so each bump tried again to take the whole balance.

## Fix

One commit, "Fix issue 71781: luxury shuttle scanner credited 0 for partial payments". It stores the balance in `amount_paid` before the account is adjusted, and uses that for both the deduction and the credit:

```dm
var/amount_paid = account.account_balance
account.adjust_money(-amount_paid, "Scanner Gate: Entry Fee")
payees[AM] += amount_paid
```

Nothing else in the proc changes. The sibling `else` branch already used a variable in this way.

## Verification

Checked on the test server with the same direct `Bumped` calls:

- Balance 60: the account went to 0 and `payees` became 60.
- Balance set to 400 and bumped again: the account went to 0 and `payees` became 460.
- Balance set to 100 with 460 already paid: only 40 was taken (balance 60 remained), the gate said "Welcome to first class", and `payees` returned to 0. So the overpayment and change handling is right.

Not checked: a real walk-in through the gate on the landed shuttle, the chat messages the reporter said were missing, and payments by credit chip or cash combined with the account balance.

## Notes

- Upstream PR 73226 also addressed this issue and was closed without merging, so master still had the bug.
- One commenter on the issue guessed that the scanner adds your money to a running payment, which is the intended design (the payees list). The bug is only that the instalment was recorded as 0.
- The issue also complains that the partial-payment feedback is a `to_chat`. That was not changed.
