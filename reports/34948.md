# #34948: Slamming someone onto a table does not interrupt the slammer's strip in progress

| | |
|---|---|
| Issues | [#34948](https://github.com/tgstation/tgstation/issues/34948): verified, fixed |
| Status | Reproduced on master and fixed; the fix was checked on the test server |
| Fix branch | [fix/34948](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/34948) (one commit) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

A timed action (`do_after`) is only cancelled by movement of the user or the target, by the user becoming incapacitated, or by the user changing held items. Slamming a mob onto a table that it is already standing or lying on moves nobody, so a strip that was started earlier carries on while the victim is knocked down again and again. The fix registers the two table-slam signals on the user of every timed action, so any slam cancels the slammer's pending timed actions, including the strip.

## The bug

The issue reporter describes a "greytide" tactic: grab an officer, slam them onto a table, queue up stripping through the strip menu, then slam them again on the same table. Switching intents, picking up items, grabbing other people and similar actions cancel the strip, but the repeated slam does not. The stripper can keep the victim knocked down and take their equipment.

The issue is from 2018. A 2021 comment says shove stunning and table slamming have changed a great deal since then. This investigation found that the behaviour still exists on current master.

## Reproduction

The setup was done with the Lua editor from an observer. The strip, grab and slam themselves were done by a player-controlled mob through the real strip menu and normal clicks.

1. Using the Lua editor, spawn an `/obj/structure/table`. Spawn a human "Greytider" on the tile next to it and a second human "Victim" on the table's own tile, lying down (`set_resting(TRUE, TRUE)`). Equip the victim with a jumpsuit, shoes, gloves and helmet. Raise `strip_delay` on each of those items to 300, so the strip lasts long enough to interrupt. (With the default delay of about 4 seconds, the strip finished before the slam could be tried and the slam had nothing to interrupt.) Give both humans the `never_wounded` trait, and give control of Greytider to the observer's client.
2. As Greytider, drag the victim onto yourself to open the strip menu and use the victim's shoes slot. Chat shows "You try to remove Victim's black shoes..." and a progress bar starts.
3. While the bar runs, ctrl-click the victim twice. Chat shows "You grab Victim aggressively!". The progress bar kept running (it was at 25% at that point).
4. Turn on combat mode and click the table.
5. Observed on master: chat showed "Greytider slams Victim onto the table!" and the strip's progress bar kept running (it was at 15% in the first run on master). The strip was not cancelled.

The aggressive grab itself did not cancel the strip either. The strip menu only opens when the grab is not aggressive: with an aggressive grab, a drag onto yourself starts a fireman carry (`mouse_buckle_handling`, `code/modules/mob/living/carbon/human/human.dm:870`). So the strip has to be started before the grab is upgraded, as above.

## Cause

`/datum/timed_action/proc/register_signals()` (`code/datums/timed_actions.dm:71`) subscribes a timed action to a short list of events:

- the user moving (line 75), unless `IGNORE_USER_LOC_CHANGE` is set;
- the user becoming incapacitated (line 78);
- the user's next-move changing (line 81, only with `DO_AFTER_CHECK_NEXT_MOVE`);
- the user equipping, unequipping or swapping held items (lines 84-86);
- the user or a target being deleted (lines 72 and 91);
- a target moving (line 93), unless `IGNORE_TARGET_LOC_CHANGE` is set.

A strip is started through `start_unequip_mob()` in `code/datums/elements/strippable.dm:312`. It calls `do_after(user, strip_delay || item.strip_delay, source, interaction_key = REF(item), ...)` (line 313) with the victim as the target.

When a victim who is not on the table is slammed, `tablepush()` (`code/datums/elements/table_smash.dm:140`) does `pushed_mob.Move(table.loc)` (line 151). The victim moves, the target-moved signal fires, and the strip is cancelled. This is why the first slam of someone who has been dragged next to a table does interrupt stripping. When the victim is already on the table tile, `Move(table.loc)` moves them nowhere, no movement signal is sent, and nothing else the slam does is observed by the timed action. The slam does send `COMSIG_LIVING_TABLE_SLAMMING` to the user (line 161; `COMSIG_LIVING_TABLE_LIMB_SLAMMING` for the head slam at line 178), but timed actions did not listen to it.

## Fix

**Fix issue 34948: slamming someone onto a table now interrupts the slammer's timed actions.**

In `code/datums/timed_actions.dm`, `register_signals()` now also registers the user (when it is a `/mob/living`) for `COMSIG_LIVING_TABLE_SLAMMING` and `COMSIG_LIVING_TABLE_LIMB_SLAMMING`, with a new handler, `on_user_table_slam()`, which calls `cancel()`.

I chose to put this in the timed action core rather than in the strip code. The strip is one of many timed actions, and the same loophole applies to any that the slammer has running against a target that does not move. The signals are only sent after a slam succeeded (after the pacifism and blocked-movement early returns in `tablepush`), so a failed slam attempt does not cancel anything. The alternative of adding the signal to the strip code alone was not tried.

## Verification

On the test server with the fixed build, the same setup and steps as in the reproduction were used (a fresh strip of Victim's shoes through the strip menu, an aggressive grab with two ctrl-clicks, combat mode on, a click on the table):

- Chat showed "Greytider slams Victim onto the table!".
- The timed action was reported as interrupted (its progress bar failed), and Victim's shoes stayed on.
- Control: the same strip was restarted with no slam and left to run for 32 seconds. It completed: the shoes came off and a "black shoes" item appeared on the floor. A normal strip is unaffected.
- The round's runtime log held only the known boot-time entries; none mentioned `timed_action` or `strippable`.

Not checked:
- The gentle table place (combat mode off, `tableplace`), which sends no slam signal and so should not cancel anything, was not tried.
- The head slam (`tablelimbsmash`) was not tried; it relies on the same handler but was not exercised.
- Only the strip was tested as the interrupted action. No other timed action was tried.
- Slamming an unrelated victim while the slammer has a different action running was not tried.
- No unit test was added or run.

## Notes

- **Wider effect, to review.** The fix is in core timed action code. Any successful table slam or head slam now cancels all of the slammer's running timed actions, not only strips. That seems right for something as disruptive as slamming, but it is a behavioural change for any `do_after` the user has open at the time.
- **Martial arts.** `code/datums/martial/_martial.dm:399` already listens to the same two signals on its holder to trigger its own table smash behaviour. The new handler is separate from it and does not change that listener.
- **Grabbing.** The issue title also mentions grabbing. Upgrading to an aggressive grab did not cancel the strip in the test, and the fix does not change that. It was not examined whether that should cancel anything; the issue's reproduction needs the table slam.
- The strip must outlast the slam for any of this to matter. With the default strip delay (about 4 seconds) the strip finished before the slam. As the 2021 comment says, it matters mostly when a victim has too little stamina left to break free during the grab and slam.
