# #70889: Shredded clothing runtimes when it takes damage at 0 integrity

| | |

| Status | Fixed on the fix branch, verified in game |
| Fix branch | [fix/70889](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/70889) |

## Summary

Clothing destroyed by ordinary damage (brute, laser and so on) is not deleted. It is "shredded" and left on the floor or worn with 0 integrity. Any later damage to it, such as fire exposure, reaches `/atom/proc/take_damage`, which deliberately `CRASH`es for atoms at or below 0 integrity, producing the runtime in the issue. The fix adds a `take_damage` override on `/obj/item/clothing` that does nothing, and returns 0, when the clothing is already at 0 integrity.

## The bug

Clothing has its own damage handling. When an item reaches 0 integrity through anything other than fire, acid, bombs or being consumed, it is made useless (no coverage, no slot flags, renamed "shredded ...") but remains in the world. Shredded items then keep being hit by effects that damage objects, for example fire, and each hit logs a runtime. The issue's log shows shredded prescription glasses lying on a reinforced floor being burned.

## Reproduction

On master, using the Lua editor on a running round (the effect was triggered by calling procs directly, not through an actual fire):

1. Spawn `/obj/item/clothing/glasses/regular`.
2. Call `take_damage(1000, "brute", "melee")` on it. The glasses became "shredded prescription glasses" with integrity 0 and `damaged_clothes` set to shredded. The item was not deleted.
3. Call `fire_act(10000, 100)` on the shredded glasses.

Result: a runtime in the runtime log, `code/game/atom/atom_defense.dm:23`, "The shredded prescription glasses taking damage while having <= 0 integrity", with the stack `take_damage(20, "burn", "fire", 0)` called from `fire_act(...)`. This matches the issue's log (which was taken on an older version, where the line was 9).

## Cause

`/atom/proc/take_damage` (`code/game/atom/atom_defense.dm:15-23`) refuses to run on a destroyed atom:

```dm
if(QDELETED(src))
	CRASH("[src] taking damage after deletion")
if(atom_integrity <= 0)
	CRASH("[src] taking damage while having <= 0 integrity")
```

This is fine for ordinary objects, which are deleted at 0 integrity. `/obj/item/clothing/atom_destruction` (`code/modules/clothing/clothing.dm:609`) only calls the parent for acid and fire; for bombs and being consumed it deconstructs the item; for every other damage flag it shreds the item (clears `body_parts_covered` and `slot_flags`, sets the shredded state, renames it, drops it from the wearer) and keeps it alive at 0 integrity.

Other code does not know about this and keeps damaging the item. `/obj/fire_act` (`code/game/objects/obj_defense.dm:125`) calls `take_damage(clamp(potential_damage, 0, 20), BURN, FIRE, 0)` on any non-fireproof object, and acid, `take_damage_zone` and other callers go through the same proc.

## Fix

One commit, "Fix issue 70889: shredded clothing no longer runtimes when damaged at 0 integrity", adds to `code/modules/clothing/clothing.dm`:

```dm
/obj/item/clothing/take_damage(damage_amount, damage_type = BRUTE, damage_flag = "", sound_effect = TRUE, attack_dir, armour_penetration = 0)
	if(!QDELETED(src) && get_integrity() <= 0)
		return 0
	return ..()
```

The override sits next to `atom_destruction`, which is where the "alive at 0 integrity" state is created. It returns 0 (no damage dealt) for a shredded item, and otherwise defers to the normal proc. The `QDELETED` guard means an item that has actually been deleted still reaches the parent and its "taking damage after deletion" check, so that real error is not hidden. Returning 0 also keeps `take_damage_zone` sane, since it multiplies the return value.

The alternative of making `atom_destruction` delete the clothing would change gameplay (shredded clothing is meant to remain, and can be repaired), so it was not pursued. The alternative of guarding each caller (fire, acid, etc.) would miss other callers.

## Verification

On the test server after rebuilding with the fix, using the Lua editor:

- Shredded glasses: `take_damage(20, "burn", "fire", 0)` returned 0 and `fire_act(10000, 100)` ran without error.
- A worn grey jumpsuit was shredded; it fell off the wearer with the usual message, and `fire_act` and `take_damage_zone` on it ran without error.
- Intact glasses still took damage normally: 5 burn damage was applied, leaving 195 integrity.
- The round's runtime log contained no integrity-related runtimes.

Not checked: real fire, acid or explosion exposure of shredded clothing in a live scenario (only direct proc calls), moth consumption, repair of shredded clothing, and other clothing subtypes beyond glasses and a jumpsuit.

## Notes

- `take_damage_zone` (`code/modules/clothing/clothing.dm:183`) calls `take_damage(damage_amount * 0.1, damage_type, armour_penetration, FALSE)`. The third parameter of `take_damage` is `damage_flag`, so `armour_penetration` is passed in the wrong position. This looks like a separate, pre-existing mistake; it was not touched and its effect was not investigated.
- A commenter on the issue said they had tried to find a clean solution locally; the issue has no linked fix.
