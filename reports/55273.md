## Summary

The 2020 report showed `/datum/reagents` objects failing to garbage-collect because a `/datum/component/plumbing/simple_demand` still held them in its `reagents` variable. On current master the plumbing component clears that variable in `Destroy()`, and the subtypes that create their own reagent holders delete them. Spawning and deleting a set of plumbing machines, and deleting the roundstart plumbing machine, produced no hard deletes or garbage-collection failures. No fix was needed or committed; some deletion paths were not tested.

## The bug

The issue shows a testing log from a round where a `/datum/reagents` failed to be garbage-collected ("was unable to be GC'd") and the reference finder located it in the `reagents` variable of a `/datum/component/plumbing/simple_demand`, reachable from `World`. The title says this happens at roundstart. In the comments, a maintainer asked whether the reagents came from the ruin with the holy water and blood synthesizers; the reporter did not know, and said they had not deleted anything there.

## Reproduction

An attempt was made on master with admin tools on the test server:

1. Started a round and observed. An SDQL2 query (`SELECT /obj/machinery/plumbing MAP [type, z]`) showed that exactly one `/obj/machinery/plumbing` existed at roundstart: a synthesizer on Z-level 2.
2. Using the Spawn panel, spawned three each of `/obj/machinery/plumbing/reaction_chamber`, `/obj/machinery/iv_drip/plumbing`, `/obj/machinery/plumbing/acclimator`, `/obj/machinery/plumbing/disposer`, `/obj/machinery/hydroponics/constructable` and `/obj/machinery/plumbing/synthesizer`, on one tile.
3. Deleted them with SDQL2: `DELETE /obj/machinery WHERE x == 107 and y == 144 and z == 2` (the spawn tile), then `DELETE /obj/machinery/plumbing`. The second query reported 13 objects selected by type path and deleted, which includes the roundstart synthesizer. It is not known how many of the spawned machines the first query had already removed.
4. Waited about six minutes, which is longer than the garbage collector's delay before it reports a failed deletion, and checked the round's `qdel.log`, the server log and `runtime.log`.

Result: `qdel.log` contained only its header line, the server log had no "unable to be GC'd" line, and `runtime.log` had no plumbing or reagent runtimes (only the admin SDQL notices). The log from roundstart also had no entries.

Not done: no objects were handled from the Lua editor, since Lua would hold references and could mask a leak. The holy water and blood synthesizer ruin was not loaded, and machines were not deconstructed by hand.

## Cause

The reference named in the issue was the plumbing component's `reagents` variable. The component sets it in `Initialize` to the parent's reagents (`code/datums/components/plumbing/_plumbing.dm:36`). On master it is released in the component's destructor (`_plumbing.dm:73-77`):

```dm
/datum/component/plumbing/Destroy()
	disable()
	ducts.Cut()
	reagents = null
	return ..()
```

Subtypes that create their own `/datum/reagents` delete them in their own `Destroy()`: the buffered component deletes `buffer` (`code/datums/components/plumbing/reaction_chamber.dm:80`, which is the `/datum/component/plumbing/buffered` destructor), the automated IV component deletes `holder` (`automated_iv.dm:16`), and the hydroponics component deletes `water_reagents` (`hydroponics.dm:20`).

The commit that added `reagents = null` was not identified, so it is unknown when this was fixed.

## Fix

None. No commit was made.

## Verification

Not applicable as a fix. The negative result above (no failed or hard deletes after deleting 13 plumbing machines and the roundstart one) is the only in-game evidence.

## Notes

- The generic `Destroy()` should cover every deletion path of the component, but paths such as machine deconstruction and the holy water and blood synthesizer ruin from the comments were not individually exercised.
- A hard delete caused by something other than the component's `reagents` variable would not have been ruled out by the reference in the issue; none appeared in this run.
- Suggested status: the issue can probably be closed as already fixed, unless someone can produce a current `qdel.log` entry.
