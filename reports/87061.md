## Summary

All three issues are in the cargo code and were worked on together. The Express Supply console starts locked and could only be unlocked by swiping a suitable ID, which cyborgs cannot do, and its UI offered no button; the fix adds a silicon-only `lock` action and an Unlock button shown to silicons. Private mining orders came in plain grey crates because the custom supply pack had no `crate_type` of its own; the fix sets it to the mining crate. The decal report (#62041) could not be reproduced on master.

## #87061: Borgs can't unlock the Express Supply console

### The bug

The Express Supply console is locked by default. A cyborg who opens it sees only the text "Swipe a Cargo Technician-level ID card to unlock this interface." and no button, so there is no way for them to use it. A maintainer comment on the issue says they reproduced it and that it was not intended.

### Reproduction

1. On the test server, use the Lua editor to spawn a `/mob/living/silicon/robot` and possess it.
2. Spawn an Express Supply console and open its UI as the cyborg.
3. Observed: the UI data had `locked = 1` and `siliconUser = 1`, and the interface showed only the swipe-an-ID message, with no control.

This was reproduced by opening the console as a cyborg; unlocking was not attempted on unfixed code since no UI control or action exists for it.

### Cause

- `code/modules/cargo/expressconsole.dm:44-47`: `item_interaction()` toggles `locked` only when the tool is an ID that passes `allowed(user)`. Cyborgs cannot swipe an ID on it.
- `code/modules/cargo/expressconsole.dm:119`: `ui_act()` had no action that changed `locked`.
- `tgui/packages/tgui/interfaces/CargoExpress.tsx`: the locked screen shows only the text.

`ui_data()` already sent `siliconUser` (`expressconsole.dm:95`), but nothing used it.

### Fix

Commit "Fix issue 87061: silicons can unlock the Express Supply console":
- `expressconsole.dm`: new `lock` action in `ui_act()`. It returns unless `HAS_SILICON_ACCESS(user)` and otherwise toggles `locked`.
- `CargoExpress.tsx`: adds `siliconUser` to the `Data` type and shows an "Unlock" button on the locked screen when it is set, which calls `act('lock')`.

The action is a toggle and the button is only on the locked screen, so in practice it only unlocks from the UI; the action itself would also re-lock if called. Silicons were given a direct toggle because they cannot swipe an ID; no other approach is recorded.

### Verification

- As the possessed cyborg, calling the `lock` UI action took `locked` from 1 to 0.
- Non-silicon users are rejected by the `HAS_SILICON_ACCESS` check (read from the code; no non-silicon call was recorded).
- The tgui bundle built successfully with the new button.

Not checked: the Unlock button was not seen rendered or clicked in a client (the test tooling does not run the tgui JavaScript); the action was called directly.

## #62041: Decals can't be permanently placed on the cargo shuttle

### Result

Not reproduced on master. The issue (from 2021) says decals sprayed on the cargo shuttle are destroyed when the shuttle returns, assumed to be "sold".

### Steps tried

1. On the test server, a `/obj/effect/turf_decal` was placed on a cargo shuttle floor tile.
2. `sell()` was called on the supply shuttle.
3. The shuttle was moved from the cargo dock to home and then away (selling runs on docking at the away location).
4. After each step the decal's overlay was still on the turf (the turf's overlay count stayed at 1).

### Explanation

Decals are now a `/datum/element/decal` on the turf. The `turf_decal` objects that apply them are anchored and then deleted, and `sell()` skips anchored objects, so there is nothing for it to sell. The decal refactor probably fixed the original report. Removing or replacing the floor tile still erases decals, and the decal painter's description documents this ("Decals break when the floor tiles are removed"). The reporter mentions the shuttle having been damaged and repaired, which would be consistent with that. This was not reproduced with a decal sprayer by a player, only by placing the decal object.

## #97738: Mining orders do not come in mining crates

### The bug

Private orders placed by a shaft miner through the cargo console arrive in a plain grey crate rather than a mining crate. A commenter on the issue attributes it to PR #97348, which removed the black default crate that private orders used, and is unsure whether it counts as a bug.

### Reproduction

Reproduced by calling the pack directly, not by placing a real order through the console:
1. On the test server, create a `/datum/supply_pack/custom` (the pack behind mining orders) and call `generate()` on it.
2. Observed on master: the crate was a plain `/obj/structure/closet/crate`.

### Cause

`code/modules/cargo/packs/_packs.dm:49-54` defines `/datum/supply_pack/custom` with a name and `crate_name = "shaft mining delivery crate"` but no `crate_type`, so it uses the base default `crate_type = /obj/structure/closet/crate` (`_packs.dm:23`). The sibling `/datum/supply_pack/custom/minerals` (`_packs.dm:62-65`) sets `crate_type = /obj/structure/closet/crate/cargo/mining`, which is why materials orders look right. Orders reach the pack through `/datum/supply_order/proc/generate()` (`code/modules/cargo/order.dm:185`).

### Fix

Commit "Fix issue 97738: mining orders arrive in mining crates": adds `crate_type = /obj/structure/closet/crate/cargo/mining` to `/datum/supply_pack/custom`, matching the `minerals` subtype.

### Verification

After the fix, `generate()` on the pack produced a crate named "shaft mining delivery crate" with icon state `mining` (type `/obj/structure/closet/crate/cargo/mining`).

Not checked: a full order through the vendor or cargo console and shuttle delivery. The report states the order path ends in the same `generate()` call but did not exercise it.

## Notes

- Whether the grey crate was a deliberate result of #97348 is a maintainer call. The fix assumes mining orders should use the mining crate like materials orders.
- The Unlock button was only checked for building, not for appearance.
