# #55275: Merged pipelines keep stale references to components with two ports on the same pipeline (hard deletes, leaked gas mixtures)

| Status | Fixed on the fix branch; fix checked in game |
| Fix branch | [fix/55275](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/55275) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

When two pipelines are merged, `/obj/machinery/atmospherics/components/replace_pipenet()` repoints only the first port of a component that points at the old pipeline. A component with two ports on the same pipeline (for example a pump whose output pipe loops back to its input) is left with one port pointing at the merged, deleted pipeline. That pipeline then hard deletes, still holding the component's gas mixtures, and when the component is later removed one of its gas mixtures stays in the surviving pipeline's `other_airs`. The fix makes `replace_pipenet()` replace every matching port and makes `merge()` also empty the merged pipeline's `other_airs`.

## The bug

Players do not see anything directly. The effect is on the server: a `/datum/pipeline` that was merged into another one and `qdel`ed is never garbage collected, because a component's `parents` list still points at it. In addition, the gas mixture of the component's second port stays registered in the live pipeline after the component is deleted, so the pipeline keeps a dead machine's mixture and its volume (200 L for the pump used in the test) when it reconciles air.

Both issues were opened in 2020 with GC failure output of the form "Found /datum/gas_mixture in list World -> /datum/pipeline -> list" (#55275) and "Found /obj/machinery/atmospherics/components/unary/vent_scrubber/on/layer2 in list World -> /datum/pipeline -> list" (#55276). Both name a `/datum/pipeline` list as the holder of the leaked object.

## Reproduction

The test server used MetaStation and was compiled with `-DREFERENCE_TRACKING_STANDARD`, so that GC failures are searched for and written to `harddels.log`. The pieces were built with the Lua editor, because spawned `/obj/item/pipe` fittings were broken on the test server (their `Initialize` set `pipe_type` to null). Each piece was built with `SS13.new(path, locate(x, y, 2))` followed by `:on_construction(nil, '#00ff00', 1)` (piping layer 1, on empty space tiles near the station), one call per piece so that SSair processed the rebuild between them.

1. Built a `/obj/machinery/atmospherics/components/binary/pump` at 32,143 (facing south, so its ports are north and south).
2. Built smart pipes at 32,144; 33,144; 33,143; 33,142 and 32,142, forming a loop from the pump's output back to its input. With SDQL2, `SELECT` on that pump with `MAP parents` showed the same pipeline in both entries, `[0x21048b77] /datum/pipeline, [0x21048b77] /datum/pipeline` (call this pipeline P): `parents` is `[P, P]`, as expected.
3. Built a smart pipe at 33,146 on its own (its own pipeline Q), then a smart pipe at 33,145 between it (its north node) and the loop (its south node). This made Q add a member that touched P, so `Q.merge(P)` ran.
4. Observed after the merge: the pump's `parents` was `[Q, P]` (`[0x21048c83], [0x21048b77]`). In View Variables, P showed as "Deleted" (it had a `gc_destroyed` value), with `other_airs` still holding 2 entries and `members` empty.
5. After the GC check interval, `harddels.log` contained:
   `Found /datum/pipeline [0x21048b77] in list World -> /obj/machinery/atmospherics/components/binary/pump [0x20285a1] -> parents (list).`
6. Deleted the pump with SDQL2 (`DELETE /obj/machinery/atmospherics/components/binary/pump` restricted to its coordinates and layer). In View Variables, the live pipeline Q then had `other_atmos_machines = /list (0)` but `other_airs = /list (1)` containing `/datum/gas_mixture [0x21048b7c]`: the gas mixture of a deleted machine, reachable as `World -> /datum/pipeline -> list`.

The Lua state itself held the pump, so the pump failing to GC in these rounds is noise and is not the bug. Only the pipeline's hard delete and the leftover `other_airs` entry are attributed to this defect.

## Cause

`replace_pipenet()` on components, `code/modules/atmospherics/machinery/components/components_base.dm:226` at master:

```dm
/obj/machinery/atmospherics/components/replace_pipenet(datum/pipeline/Old, datum/pipeline/New)
	parents[parents.Find(Old)] = New
```

`parents.Find(Old)` returns only the first index. The proc is called only from `/datum/pipeline/merge()` (`code/modules/atmospherics/machinery/datum_pipeline.dm:179`), once per component in the old pipeline's `other_atmos_machines`. A component with several ports on the same pipeline has that pipeline in `parents` more than once, so after the merge only the first entry points at the new pipeline.

Consequences, in the order they were observed:

- The old pipeline P is `qdel`ed at the end of `merge()` (`datum_pipeline.dm:188`), but the pump's `parents[2]` still references it, so it hard deletes. `merge()` cuts P's `members`, `other_atmos_machines` and `require_custom_reconcilation` (`datum_pipeline.dm:184-186`) but not `other_airs`, so P also keeps the pump's gas mixtures alive through that list.
- `other_airs |= parent_pipeline.other_airs` (`datum_pipeline.dm:183`) gave Q both of the pump's gas mixtures. When the pump is deleted, `/obj/machinery/atmospherics/Destroy()` calls `nullify_node()` for each port (`atmosmachinery.dm:109`), which calls `nullify_pipenet()` (`components_base.dm:174`) with the pipeline in that port's `parents` entry. Only entry 1 holds Q, so only `airs[1]` is removed from Q's `other_airs`; `airs[2]` stays there. This is the leftover seen in step 6.
- Until the pump is deleted, its second port points at a dead pipeline that is no longer in `SSair.networks`. This was read from the code, not tested: other code that goes through that port (`components/add_member()` calling `return_pipenet()`, for example) would get the dead pipeline and could move a live network into it.

## Fix

One commit, "Fix issue 55275: components replace every port on a merged pipeline", with two changes:

- `replace_pipenet()` in `components_base.dm` now loops over every entry of `parents` and replaces each one equal to `Old`:
  ```dm
  for(var/i in 1 to length(parents))
  	if(parents[i] == Old)
  		parents[i] = New
  ```
- `merge()` in `datum_pipeline.dm` now also calls `parent_pipeline.other_airs.Cut()`, next to the existing cuts of `members`, `other_atmos_machines` and `require_custom_reconcilation`, so a merged-away pipeline no longer keeps gas mixtures.

The first change removes the stale reference and the second is the matching cleanup. Pipe `replace_pipenet()` (the pipe version in `pipes.dm`) was not touched.

## Verification

The same steps were repeated on a build of the fix branch, again with reference tracking, on MetaStation:

- After step 3, the pump's `parents` was `[0x2101b06b], [0x2101b06b]`: both ports pointed at the same pipeline, which was also the parent of the pipe at 33,145. The merge had happened and both ports were moved.
- After deleting the pump, the surviving pipeline had `other_airs = /list (0)` and `other_atmos_machines = /list (0)`.
- No `/datum/pipeline` GC failure appeared in `harddels.log` after more than 5 minutes. The merged pipeline had been `qdel`ed about 10:50:50 and the GC queue had passed items queued later, up to 10:56:13. The only reference search in the log was for an `/obj/effect/statclick/SDQL2_delete` created by the SDQL2 query, which is noise. No runtimes were logged other than the empty-line Lua runtimes also seen on the unfixed build.

Not checked: any layout other than the one pump loop (other components with two ports on one pipeline, such as a multi-port component, or a pipeline merged several times); the GC behaviour with the original 2020 symptom (a `gas_mixture` hard delete); the unit tests or a full round on a normal map; the "dead pipeline" follow-on effects described under Cause.

## Notes

- The 2020 reports show `/datum/gas_mixture` GC failures. On master gas mixtures are not `qdel`ed, so the same reference chain appears as a leaked mixture and a stale volume in the pipeline rather than as a GC failure. The old gas-mixture report was therefore not reproduced as written; what was reproduced is the path it names (`World -> /datum/pipeline -> other_airs`) and the pipeline hard delete.
- #55276 (a `vent_scrubber` found in a pipeline list) is listed in this group as the same cause. That link was not demonstrated in game: bulk deletion of vents and scrubbers, and manual unwrench-and-rebuild sequences on vents and the manifold under them, left no hard deletes in two attempts (see the separate write-up for #55276). The code path from this bug to a machine staying in a pipeline's list needs a dead pipeline to be reused through one of the "overwrite a port that already has a live pipeline" paths (`add_member()` at `datum_pipeline.dm:153`, `expand_pipeline` in `air.dm:447`, `build_pipeline_blocking` at `datum_pipeline.dm:104`), and that chain was only read, not run.
- Possible hardening that was not done: have components' `get_rebuild_target()` treat a `QDELETED` parent like a missing one (pipes already do, `pipes.dm:72`), and make `set_pipenet()` detach the component from a previous live pipeline before overwriting.
- The upstream PR #56202 (nodes of components are nullified properly) is already in master; it does not cover this case.
