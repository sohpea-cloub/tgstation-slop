## Summary

The report says a module removed from a MODsuit while the wearer is under space drugs does not get the rainbow ("high") overlay, and a commenter suspected the module was left on the HUD plane. On current master this did not happen: every removed module ended up on `GAME_PLANE` (-4), the same as a freshly spawned one. The most likely reason is the fallback in `/obj/item/doMove`, which resets the plane for items that are moved while still flagged `IN_INVENTORY`. The git history was not checked, so which change fixed it is unconfirmed. No fix was written.

## The bug

The issue (reported on client 515.1630, March 2024) says that after taking space drugs and removing a module (the security suit's storage module in the screenshot), the module did not show the drug tint. The comment on the issue says: "Plane not being set correctly? Looks like it's still on HUD plane." The "high" effect is a fullscreen overlay on the lighting plane, so it only affects things on the game plane. An item left on a HUD plane would draw above it, untinted.

## Reproduction

I could not reproduce it. What was done on master:

1. Spawned a human wearing `/obj/item/mod/control/pre_equipped/security` and took control of it with the Lua editor.
2. Applied `/datum/status_effect/drugginess`. The client showed the "druggy" fullscreen object and the "High" alert.
3. Removed modules the way the crowbar does it, by calling `uninstall(module)` and then `module.forceMove(drop_location())`. The crowbar's input list was not used, so this exercised the same procs but not the player's action.
   - A pre-installed module (magnetic harness): plane -4 before and after removal.
   - A module first picked up into a hand (plane 41, `ABOVE_HUD_PLANE`; `appearance_flags` 769), then installed, then removed: -4 right after install and -4 after removal.
   - The storage module with a crowbar inside the open suit storage: the module was -4, and the crowbar went from plane 41 in storage to -4 on removal.
4. Ran the SDQL2 query `SELECT /obj/item/mod/module WHERE plane != -4`. It checked 298 modules and matched none. The held-then-installed module's `appearance_flags` (769) matched a fresh module's.

## Cause

There is no live defect to point at. The symptom the commenter described can only occur if an item keeps `ABOVE_HUD_PLANE` after it leaves an inventory. `put_in_hand` sets that plane (`code/modules/mob/inventory.dm:249`, and equipping does at `:613`), and `doUnEquip` is the normal place that resets it (`:502`). Installing a module does `new_module.forceMove(src)` (`code/modules/mod/mod_control.dm:650`), which would bypass `doUnEquip` for a module taken from a hand.

On master that case is covered by the fallback in `/obj/item/doMove` (`code/game/objects/items.dm:1319`). For any item with `IN_INVENTORY`, it routes the move through `transferItemToLoc`, which goes through `doUnEquip` and resets the plane. That is probably what fixed the report after 2024. I did not check the history (the clone is shallow), so this is an inference.
