# #40247: Spawn Object-Mob fails when a non-default mob type is picked (ranged mimics)

| | |
|---|---|
| Issues | [#40247](https://github.com/tgstation/tgstation/issues/40247): verified, fixed |
| Status | Verified on master, fixed and checked in game |
| Fix branch | [fix/40247](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/40247) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

The admin verb Spawn Object-Mob cannot spawn a ranged mimic (or any base mob type other than the default) because it calls `text2path()` on a value that is already a typepath. The result is `null`, the verb prints "Mob or object path invalid" and then carries on to `new null`, which runtimes, so no mob is created. The fix accepts either a typepath or text, returns after the "invalid" message, and also refuses a ranged mimic for a non-gun object, since such a mimic would runtime when it tried to fire.

## The bug

The issue (2018) consists of two screenshots and the title "Spawn object-mob can't spawn ranged mimics". In game, an admin picks an object in Spawn Object-Mob, opens the "Customize mob" window, changes "Base mob type" to the ranged mimic and presses Ok. The chat says "Mob or object path invalid" and nothing is spawned except the stray copy of the object (a laser carbine in the test). The runtime log shows `Cannot create objects of type null.`

The problem is not specific to ranged mimics: it happens for any value picked through the "Base mob type" link, and for the "Base obj type" link as well.

## Reproduction

On master, with admin rights:

1. Start a round (observing is enough) and run the Spawn Object-Mob verb (Debug category).
2. Choose a gun type as the object, for example the laser carbine (`/obj/item/gun/energy/laser/carbine`).
3. In the "Customize mob" window, click the "Base mob type" link and pick the ranged mimic (`/mob/living/basic/mimic/copy/ranged`) from the type list.
4. Press Ok.

Observed:

- Chat: "Mob or object path invalid".
- `runtime.log`: `Cannot create objects of type null.` at `code/modules/admin/verbs/spawnobjasmob.dm:80`.
- Only the object itself (the carbine) appeared on the floor; no mob was created.

This was reproduced through the real admin UI (the verb and its picker window), not by calling procs directly.

## Cause

`code/modules/admin/verbs/spawnobjasmob.dm:74-76` reads the picker results with `text2path()`:

```dm
chosen_obj = text2path(mainsettings["objtype"]["value"])

basemob = text2path(mainsettings["mobtype"]["value"])
if (!ispath(basemob, /mob/living/basic/mimic/copy) || !ispath(chosen_obj, /obj))
	to_chat(user.mob, "Mob or object path invalid", confidential = TRUE)

basemob = new basemob(...)
```

The settings list is built in the same file with string values (`"value" = "/mob/living/basic/mimic/copy"`, `"value" = "[chosen]"`). When the admin clicks a "datum" setting, the picker's `Topic()` in `code/datums/browser.dm:409-419` stores the result of `pick_closest_path()` straight into `setting["value"]`. `pick_closest_path()` returns a typepath, not text. So after any change to the mob or object type, the value is a path, and `text2path(path)` returns `null`. Only values left at the default are still strings, which is why the default `/mob/living/basic/mimic/copy` always worked.

The "invalid" branch at line 78 also had no `return`, so execution continued to line 80 and evaluated `new basemob(...)` with `basemob == null`. The argument `new chosen_obj(...)` is evaluated before the failing `new null`, which is why the stray object stays on the floor while no mob appears.

## Fix

One commit, "Fix issue 40247: Spawn Object-Mob can pick ranged mimics", changes `spawnobjasmob.dm`:

- `chosen_obj` and `basemob` are taken from the picker as they are, and only passed through `text2path()` if they are not already paths (`if (!ispath(x)) x = text2path(x)`), so both the default text values and picked paths work.
- The "Mob or object path invalid" branch now returns.
- A new check refuses a ranged mimic base type when the chosen object is not an `/obj/item/gun`, with the message "Ranged mimics can only copy guns".

The last check was added because `/mob/living/basic/mimic/copy/ranged/proc/fire_gun()` (`code/modules/mob/living/basic/ruin_defender/mimic/mimic.dm:384-386`) does `locate() in contents` as `/obj/item/gun` and calls `gun.can_shoot()` without a null check. A ranged mimic holding a non-gun (a toolbox was tried, made via the Lua editor) runtimes with `null.can_shoot()` when it tries to fire. Fixing the picker would otherwise have made that state easy for an admin to reach. An alternative would be to make `fire_gun()` null-safe; the fix limits itself to the admin verb.

## Verification

After rebuilding with the fix, the same steps (laser carbine, ranged mimic, Ok) spawned a mob named "Bob", a ranged mimic showing the laser carbine, with no runtimes. `admin.log` recorded "spawned a sentient object-mob Bob from /obj/item/gun/energy/laser/carbine".

Before the fix, a sentient ranged mimic holding a laser gun was also created through the Lua editor to check that the mob itself works. It fired normally (clicking a target gave "You fire the Type 5 laser gun!"), so the bug was confined to the verb.

Not checked in game: the new "Ranged mimics can only copy guns" refusal message, and changing the object type through the picker's "Base obj type" link (the code path is the same, but only the mob type was exercised).

## Notes

- The same pattern (picker values assumed to be text) may exist in other users of `present_pref_like_picker`; none were audited.
- The non-gun ranged mimic runtime in `fire_gun()` remains reachable by other means (it was reproduced via the Lua editor); a null check there would be a separate change.
- In the original verb, `var/obj/chosen_obj = text2path(chosen)` at line 10 also runs `text2path()` on a typepath and yields `null`, but the value is overwritten after the picker closes, so it has no effect.
