## Summary

Repairbots could not be picked up into their `carried_repairbot` box form because bots default to `status_flags = NONE`, and `grabbedby()` refuses to upgrade a grab on a mob without `CANPUSH`; the `can_be_held` element needs that aggressive grab. The fix gives repairbots `CANPUSH`. Two related issues in the same code were also fixed: the repairbot girder ability had no range check (#89554), and a repairbot inside its box form had no way out of a disposal unit (#89756).

## The bug

### #97552

Grabbing a repairbot and dragging it onto yourself is supposed to collapse it into a box for transport. It did nothing. The player sees "The Repairbot can't be grabbed more aggressively!" when trying to upgrade the grab.

### #89554

The repairbot's "Build Girder" ability (it uses no materials from the player and no power) was meant to work only on adjacent tiles. The reporter found it worked on any tile they could target, including through a window, and that when the bot was being carried the construction timer was never interrupted because the bot itself never moves, so a carrier could run away while the bot built a girder behind them.

### #89756

A carried repairbot (the blue toolbox form) put into a disposal chute stayed there: attempting to move gave "can't move while buckled!" and there was no other way out.

## Reproduction

All steps used the test server with admin tools; the Lua editor was used to spawn objects and call procs.

### #97552

1. Spawned a repairbot and a human.
2. As the human, ctrl-clicked the repairbot twice to upgrade the grab.
3. Result on master: "The Repairbot can't be grabbed more aggressively!". Dragging the bot onto the human therefore never picked it up.
4. Control: with the grab bypassed by calling `mob_try_pickup(human, TRUE)` from the Lua editor, picking up worked and dropping it to the floor ("plops down") worked. So the pickup code itself is fine; the aggressive grab is what is missing.

### #89554

1. Possessed a repairbot (Lua `PossessByPlayer`) and used the Build Girder ability on a distant turf.
2. Result on master: a girder was placed 5 tiles away with the bot on the floor, and 4 tiles away while the bot was carried by a human. The `do_after` was not interrupted because the bot never moved.
3. The bot's own AI only builds at distance 1 (`maximum_distance = 1`, `repairbot_ai.dm:201`), which is the intended range.

### #89756

1. Had a human pick up a repairbot (`mob_try_pickup`), spawned a disposal bin, and called `place_item_in_disposal` with the carried box.
2. Result on master: when the bot tried to move it got "can't move while buckled!"; there was no way to leave.

The disposal-unit insertion was done by calling procs rather than by the player action.

## Cause

- **#97552**: `code/modules/mob/living/basic/bots/_bots.dm:28` sets `status_flags = NONE //no default canpush`. `grabbedby()` (`code/modules/mob/living/living_defense.dm:393`) returns FALSE with "can't be grabbed more aggressively!" for any target without `CANPUSH`. The `can_be_held` element (`code/datums/elements/can_be_held.dm:20`, `trying_to_hold_mob`) only allows pickup at `GRAB_AGGRESSIVE`, so a repairbot could never be picked up by the intended route.
- **#89554**: `Activate()` in `code/modules/mob/living/basic/bots/repairbot/repairbot_abilities.dm` checks that the target is an open turf and not blocked, but has no distance or location check, so the target can be anywhere the player can click, and the owner can be inside a box.
- **#89756**: `/obj/item/carried_repairbot` (`repairbot.dm`) had no `relaymove` or `container_resist_act`. The default `atom/relaymove` (`code/game/atom/_atom.dm:506`) only prints the "can't move while buckled" message. (Mob holders have their own handling for this; the repairbot box did not.)

## Fix

Three commits on the branch:

1. **"Fix issue 97552: repairbots can be grabbed aggressively again so they can be scooped into box form"**: adds `status_flags = CANPUSH` to `/mob/living/basic/bot/repairbot`. This is set on the repairbot only, not on all bots, since only repairbots use the box form.
2. **"Fix issue 89554: repairbot girder ability needs the repairbot adjacent to the target turf, on a turf itself"**: at the start of `Activate()`, if the bot is not on a turf or is not `Adjacent` to the target, it shows a "too far!" balloon alert and returns. This also blocks building while carried, because the bot's `loc` is then the box.
3. **"Fix issue 89756: a carried repairbot can wriggle out of its box form"**: adds `relaymove` and `container_resist_act` to the box, both calling a new `wriggle_free()` (drops the box if it is held and releases the bot; if the box is in a bin or locker the bot simply pops out where it is). `Destroy()` now releases the bot before calling the parent, which would otherwise delete the box's contents first. For a bot with no client, `container_resist_act` does nothing while the box is held by a mob (see Notes).

## Verification

On a fixed build in a running round:

- **#97552**: ctrl-click twice gave "You grab the Repairbot aggressively!"; dragging the bot onto the player's own mob gave "You start trying to scoop up the Repairbot..." then "scoops up the Repairbot!" with the box in hand. Done twice, in two rounds.
- **#89554**: possessing the bot and using Build Girder on a turf 4 tiles away showed "too far!". On an adjacent turf, the construction effect appeared and the girder was built after about 3 seconds.
- **#89756**: a bot (AI-controlled) in a human's hand stayed there for more than 5 seconds after the final change (see Notes). After `place_item_in_disposal`, the message "You place the Repairbot into the disposal unit." appeared and, a few seconds later, the bot was on the bin's turf and no longer buckled. The runtime log showed only start-up noise and one error caused by the tester's own bad Lua call.

Not checked in game on the final build: the girder ability while carried by a human (covered by the `isturf(owner.loc)` check, reviewed in code only); a player-controlled bot moving out of a bin (`relaymove` to `wriggle_free()`, reviewed in code only); a player-controlled bot wriggling out of a hand.

## Notes

- The first version of the #89756 fix made the bot's AI wriggle out of the carrier's hand immediately after being scooped up ("The Repairbot wriggles free!"). The bot AI's escape logic resists whenever its pawn is inside an object, and `container_resist_act` now worked. The commit was amended so that clientless bots do not resist while the box is held by a mob. The consequence is that an AI repairbot is never able to get out of a held box by itself, only out of containers. In the disposal test it got out through the AI's own resisting, since the box was no longer in a hand.
- #89554 also has a claim that the ability works through walls; the adjacency check covers that, but through-window range was not separately tested after the fix beyond the 4-tile case.
- The reports are from rounds with test merges, so some behaviour may depend on them. Nothing found on master suggested it did.
