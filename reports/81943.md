# #81943: Spacetime Distortion causes sprite displacement (not reproduced on current master)

| | |
|---|---|
| Issues | [#81943](https://github.com/tgstation/tgstation/issues/81943): not reproduced; [#80868](https://github.com/tgstation/tgstation/issues/80868): duplicate of #81943, not reproduced |
| Status | Not reproduced; no fix needed on master as tested |
| Fix branch | none |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

Both reports say that walking through the wizard's Spacetime Distortion (especially onto tables caught in it) leaves a mob's sprite permanently displaced, and that repeating it adds more displacement. On current master this could not be reproduced: table elevation is applied as a named offset per source (`add_offsets` / `remove_offsets`), and entering the same elevation source twice returns early, so offsets cannot stack. Repeated walks through linked distortions and several hundred randomised moves over floor, table and distortion tiles left every tested mob at the expected pixel values. The old bug is most likely gone because elevation was rewritten onto the offsets system, but that is inferred from the code, not confirmed from history.

## The bug

As reported, a mob that passes through a Spacetime Distortion ends up with a visibly shifted sprite, and each further pass shifts it more. #81943 (a revenant who went through many times) shows it as an upward displacement; a commenter there says the shift is added each time a mob "walks into" a table that the distortion has teleported it onto, without climbing. #80868 describes a "permanent positive offset" after tables adjacent to the affected area were climbed on or deconstructed, and a commenter suggests the mob does not get un-offset if the tile it steps onto also offsets it.

Both are issues filed in early 2024 (January and March). The sprite offsets in question are the vertical lift that tables give to a mob standing on them.

## Reproduction

Not reproduced. What was tried, on master, using the Lua editor on the test server (an observer with the Lua editor, without casting the real spell):

1. Built a row of floor tiles in the central hallway, placed tables on four of them, and spawned pairs of `/obj/effect/cross_action/spacetime_dist` effects (the objects the spell creates) with `linked_dist` set both ways: floor to table, and table to table.
2. Spawned human mobs (not player-controlled) and moved them with `Move()` and `forceMove()`.
3. Floor to distortion to table loop, repeated four times (move into the distortion, step back, repeat): `pixel_z` was 12 on the table tile and 0 off it every time, with `pixel_x` and `pixel_y` at 0 throughout.
4. 150 random `Move()` / `forceMove()` steps over a mix of floor, table and distortion tiles: 0 mismatches against the expected value (12 on a table tile, 0 elsewhere).
5. 200 random steps with a human whose `TRAIT_IGNORE_ELEVATION` was toggled at random: 0 mismatches. 200 steps with a lying human (after `Knockdown`): 0 mismatches.
6. A revenant (which ignores elevation by design) kept `pixel_z`, `pixel_x` and `pixel_y` at 0. An early run showed 36 mismatches for this case, but that was a wrong expected value in the check, not a game problem.
7. Flipped, unflipped and deleted a table with a mob on its tile: `pixel_z` went 12, 0, 12, 0 with no residue. In one run `pixel_z` stayed at 0 after unflipping a table with mobs standing there; this did not recur in a clean run, and it is an under-shift rather than the reported over-shift (nothing accumulates).
8. The runtime log showed no runtimes other than startup lines.

## Cause

There is no live defect on master. The relevant current code:

- Elevation from tables is applied by `/datum/element/elevation_core` in `code/datums/elements/elevation.dm`. `elevate_mob()` (line 187) returns early if `target.has_offset(source = ELEVATION_SOURCE(src))`, then calls `target.add_offsets(ELEVATION_SOURCE(src), z_add = pixel_shift, ...)` (line 207); `deelevate_mob()` (line 211) calls `target.remove_offsets(ELEVATION_SOURCE(src), ...)`.
- `add_offsets()` and `remove_offsets()` (`code/modules/mob/living/living_update_icons.dm:81` and `:99`) store offsets in a per-source associative list (`LAZYSET(offsets[PIXEL_Z_OFFSET], source, z_add)`), so adding the same source again overwrites its own value instead of adding to it.
- `on_entered()` (line 148) only registers and elevates a mob if it did not come from a tile with the same elevation source, and `on_exited()` (line 162) only de-elevates when it is not moving to such a tile.

The older mechanism (relative animation shifts on the mob) is not in this tree and the tree is a shallow clone, so what the previous implementation did is an inference from the reports: a `forceMove` inside `Entered` (as the distortion's `get_walker()` does, `code/modules/spells/spell_types/self/spacetime_distortion.dm:130-135`) causes a nested move, and a relative shift could be applied twice or its undo skipped. With keyed offsets that cannot happen.

## Fix

None. Nothing was changed.

## Verification

Only the reproduction attempts above. Not checked:

- The real wizard spell was not cast. The test used the same effect objects it creates; the spell itself only adds photograph overlays on top of this.
- No real client's glide movement was tried, only server-side `Move()` / `forceMove()` calls (the same path the client movement uses).
- Climbing a table with the climb action, and deconstructing a table while mobs are on or near it, were not tried, except for the flip, unflip and delete cases in step 7.
- The "pixel_z stays 0 after unflipping with leftover mobs" case was seen once and not reproduced; it was not investigated further.

## Notes

- Both issues were filed in 2024-01 and 2024-03, before the elevation rewrite onto `add_offsets` / `remove_offsets` in current master; that is the most likely reason they no longer reproduce. This was not confirmed from history.
- #80868 is a duplicate of #81943 (same mechanism, equally not reproducible), though it also carries the `Tested/Reproduced` label from when it was filed.
- If a maintainer still sees displacement on a current build, the likely thing to look at is a mob whose offsets list gets out of sync with `TRAIT_MOB_ELEVATED`, for example after a table is flipped with mobs on it (the single under-shift seen in step 7), rather than a stacking bug.
