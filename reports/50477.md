## Summary

The issue (opened April 2020) reported that a player welded into a locker queued one breakout `do_after` for every movement keypress, reaching dozens at once. On master `87b93338` this does not happen. The locker's breakout proc returns early if the mob is already breaking out of that locker, and `do_after` itself refuses a second action under the same interaction key. About 40 movement attempts inside a welded locker on the test server produced one breakout message, one progress bar and one entry in the mob's `do_afters` list. No code change is needed.

## The bug

As reported, a mob stuck in a welded (not locked) locker who tried to move out started a breakout attempt on every movement attempt. Holding an arrow key queued dozens of breakouts. The reporter's screenshot, taken from the chat log, showed about 69 of them.

## Reproduction

I tried to reproduce it on master and could not; the bug no longer exists. The steps below show how the check was done and what was observed.

1. On the test server, start the round and open the Lua editor as an admin.
2. In the Lua editor, spawn a `/mob/living/carbon/human` and a `/obj/structure/closet`, `forceMove` the human into the closet, set `closet.welded = TRUE` and `closet.breakout_time = 600` (one minute), then give the human a player by setting its `ckey` to the admin's.
3. As that player, try to move north once, then 10 more times, then 30 more times (about 40 attempts in total). Each attempt is a `relaymove` from inside the closet.
4. Observe the chat log, the progress bars, and the mob's `do_afters` list. The list was read with an SDQL2 query (`SELECT /mob/living/carbon/human WHERE client MAP [do_afters, length(do_afters)]`) and a Lua expression on the mob (`#mob.do_afters`).

Evidence observed:

- Only one "You lean on the back of the closet and start pushing the door open... (this will take about 1 minute.)" message appeared, on the first move.
- Exactly one progress bar was shown, on the closet. It advanced from 10% to 70% over about 45 seconds while the movement attempts continued.
- After the roughly 40 movement attempts, the mob's `do_afters` list had length 1.
- No stacked breakout attempts appeared at any point.

The test was run through the player's real movement attempts, not by calling procs directly. The breakout was not left to finish (the run stopped at about 70%), so the final break-out message was not observed.

## Cause

The old defect (no guard against re-entering the breakout) has been closed in two places:

- `code/game/objects/structures/crates_lockers/closets.dm:1024` `relaymove` calls `container_resist_act(user)` for every movement attempt from inside the closet, unless the closet is locked or the user is unconscious or in crit. This is the entry point the issue describes.
- `code/game/objects/structures/crates_lockers/closets.dm:1085` `container_resist_act` returns early when the user is already breaking out of this closet:

  ```dm
  if(DOING_INTERACTION_WITH_TARGET(user, src))
  	return
  ```
  (line 1097), before the shake message, the timer and the `do_after(user, breakout_time, target = src)` call at line 1107.
- `code/datums/timed_actions.dm:211` `do_after` also caps concurrent actions. When no `interaction_key` is given it defaults to the target, `max_interact_count` defaults to 1, and `code/datums/timed_actions.dm:235-238` returns without starting an action if the mob's `do_afters` entry for that key is already at the cap.

Either check alone would stop the stacking; the early return in `container_resist_act` also avoids repeating the "begins to shake violently" and "start pushing the door open" messages.

## Fix

None. No commit was made.

## Verification

Confirmed in game on master as described under Reproduction: with a welded closet and roughly 40 movement attempts, one breakout was queued.

Not checked: a locked (rather than welded) locker, which `relaymove` handles separately with a "door won't budge" message; a closet inside another container (the `relay_container_resist_act` path); the breakout completing; and other mob types (for example monkeys, cyborgs or simple animals) inside the locker.
