## Summary
When paper is bound into a book, each piece of text is wrapped in `<font ...>` and `<b>` tags that are glued directly to the text. The book viewer renders its content as markdown, so those tags count as inline HTML. A fenced code block directly after the opening tag is mangled and a stray `</font>` is left behind. The fix puts the wrapper tags on their own lines, with blank lines around the text, so the renderer treats them as standalone HTML blocks and still parses the markdown between them.

## The bug
A code block written on paper looks right in the paper UI. After the paper goes through a book binder, the book shows the text with the formatting broken and a stray `/font` at the end. The reporter suspected the monospace font handling, which is close: the problem is the font wrapper tag.

## Reproduction
Done on the test server with admin tools. The binding was driven through the book data procs, not by writing the text on paper by hand; a real book binder was also run on a paper and printed a book without errors.

1. With the Lua editor, spawn an `/obj/item/paper` and add one text input with `add_raw_text("Hello\n```\nlike this\n  indented\n```\nafter", "Courier New", "#000000", ...)`.
2. Spawn an `/obj/item/book`, call `book_data.set_content_using_paper(paper)` on it, then read `book_data.get_content()`.
3. The stored content was `<font color='#000000' face='Courier New'>Hello\n```\nlike this\n  indented\n```\nafter</font>`. The HTML is shown unescaped here; the game stores it HTML-encoded.
4. Books display their content with tgui's `MarkdownViewer`, which uses `marked`. The content was rendered with the copy of `marked` in tgui's `node_modules`, in Node. The output was `<p><font ...>Hello</p><pre><code>like this\n  indented\n</code></pre><p>after</font></p>`.

The first line is pulled into a paragraph together with the inline `<font>` tag, and the closing `</font>` ends up inside the last paragraph. This matches the stray `/font` in the issue's screenshot.

## Cause
`/datum/paper_input/proc/to_raw_html()` (`code/modules/paperwork/paper.dm:856`) wraps the raw markdown text inline:

```
final = "<font[" color='[colour]'"][" face='[font]'"]>[final]</font>"
...
final = "<b>[final]</b>"
```

`/datum/book_info/proc/set_content_using_paper()` (`code/modules/library/book_info.dm:44`) builds the book content from these strings. The paper UI parses markdown first and applies font and bold afterwards. A book does the reverse: it wraps the text first and lets the book viewer parse markdown on the result. With the tag on the same line as the text, markdown sees inline HTML followed by text, so the code fence is not recognised as starting a block in the way it is when the text stands alone. `to_raw_html()` is only called from `book_info.dm`.

## Fix
One commit, "Fix issue 98174: keep markdown code blocks intact when binding paper into books", changes `to_raw_html()` to emit `<font ...>\n\n[text]\n\n</font>` and `<b>\n\n[text]\n\n</b>`. A tag alone on its line, followed by a blank line, is a CommonMark HTML block, so the markdown between the tags is parsed normally. A comment in the code explains this. Only the two wrapper strings changed.

## Verification
- Lua on the test server, same paper as in the reproduction: the content became `<b>\n\n<font ...>\n\nHello\n```...```\nafter\n\n</font>\n\n</b>`.
- Rendered with `marked`, this gave `<font><p>Hello</p><pre><code>like this\n  indented\n</code></pre><p>after</p></font>`, correctly nested and with no stray tags.
- No new runtimes appeared.
- Not checked: the rendering in the actual game client (the tgui book window was not seen). The check was done with the same `marked` library in Node. Papers with several inputs, stamps or other bold or font combinations were not tested individually.

## Notes
- Paper text in a book now gets extra blank lines (paragraph breaks) around each input. This is harmless in markdown, but books whose text relied on tight inline spacing between inputs will have slightly more vertical space.
- A single-line input wrapped this way now renders as a paragraph inside the `<font>` block rather than inline; visual spacing may differ slightly from before.
