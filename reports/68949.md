## Summary

The circuit "Get ID" component (`/obj/item/circuit_component/id_getter`) only reads the ID of a target within 1 tile. That is the coded and advertised limit (`max_range = 1`, shown in the component's UI as "Maximum Range: 1 tiles."), so a gun shell cannot read IDs of targets at range. Raising it is a design and balance decision, so no change was committed. For #79494, circuit capacity is enforced by total size per shell and an empty module component costs 3 plus whatever is inside it; this matches the code, so the "can't fit more than 2 modules" report is probably down to the shell's capacity or an outdated wiki table.

## #68949: ID getter range

### The bug
The report says the ID reader only works when standing directly next to a person, which stops a gun shell from reading IDs at range. The gun shell's projectile range is 7 tiles (`code/modules/wiremod/shell/gun.dm`, `range = 7`), hence the consistency complaint.

### Reproduction
1. On the test server, with the Lua editor, spawn a human holding an ID card (put it in their hands), 3 tiles away from the test setup.
2. Spawn a compact remote shell, attach an integrated circuit to it, and add an `/obj/item/circuit_component/id_getter` to the circuit.
3. Set the component's `target` input to the human and call `input_received(nil)`.

Observed: with the human 3 tiles away the `ID` output was null. After moving the human to 1 tile away the output was the ID card. This was done by calling the component directly with a set target, not by firing a real gun shell.

### Cause
`code/modules/wiremod/components/id/getter.dm:17` declares `var/max_range = 1`, and `input_received` (`:31`) clears the output when the target is farther away:

```dm
if(!istype(target_mob) || get_dist(current_turf, target_mob) > max_range || current_turf.z != target_mob.z)
	id_port.set_output(null)
```

The limit is on purpose: `get_ui_notices` displays it, and two sibling components (`access_reader.dm:14` and `info_reader.dm:20`) use the same value. Other circuit components use larger ranges (5 for health and the material scanner, 7 for the pinpointer and tostring), so the choice of 1 for ID reading is a balance decision (remote reading of IDs) and not an obvious oversight.

### Fix
None committed. If maintainers want longer range, changing `max_range` in `getter.dm:17` is enough, because the check already uses the variable; the same could be done for the access and info readers.

### Verification
Only the before state was checked (range 1 works, range 3 does not). No change was tested.

## #79494: shell capacity and module circuits

### The bug
The reporter could not fit "16 circuits" into a shell, or 14 components plus 2 modules, and could not fit more than 2 module components. They suspected the wiki is out of date.

### Reproduction
Using the Lua editor:
1. An integrated circuit with 14 arithmetic components had `current_size` 14.
2. An empty `/obj/item/circuit_component/module` had a `circuit_size` of 3 (the component itself plus its input and output components), and its inner circuit had `current_size` 2. Adding two modules to the circuit brought the total to 20.
3. A compact remote shell (`SHELL_CAPACITY_SMALL` = 25, `code/__DEFINES/wiremod.dm:104`) accepted 25 arithmetic components. The 26th component and a module were refused with "it won't fit!".

### Cause
No bug found. Capacity is the sum of component sizes against the shell's limit (tiny 12, small 25, medium 50, large 100, very large 500). A module costs 3 plus every component placed inside it, so a few modules fill a small shell quickly. Which shell the reporter used is unknown, so the reported counts cannot be matched exactly; the wiki table may be stale.

### Side finding (not part of the report)
In the module component's `add_component` (`code/modules/wiremod/components/abstract/module.dm`), adding a component to a module's inner circuit grows the module component's `circuit_size` without updating the `current_size` of a circuit that already contains that module. `set_circuit_size` in `component.dm` does update it. The effect is that a circuit can be pushed past a shell's capacity; it does not explain the reported symptom. This was read in code, not tested.

### Fix
None.
