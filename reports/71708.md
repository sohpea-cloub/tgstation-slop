## Summary

The report (2022, Icebox) says a rod got stuck, with a screenshot and no settings. Rods thrown by the immovable rod event no longer stick on Icebox on current master: they cross the multi-z station and are deleted at the map border, which an earlier upstream change added. One stuck case still reproduces: a rod created with no destination, as an admin Spawn does, never moves on any map, because `move_towards()` is called on null. The optional fix makes such a rod fly in the direction it faces. Whether this is the rod in the report is a guess.

## The bug

The reporter wrote "play shitbox, spawn rod" and attached a screenshot that was not available to us. A comment on the issue says all things that spawn as "flung" objects behave this way on Icebox, probably because of how the z-levels work. The report names testmerge #71527 and round 195614, and a client version from late 2022. From the text alone it is unclear whether the rod was event-spawned, admin-spawned, or something else.

## Reproduction

### Event-style rods on Icebox (not reproduced)

1. Run Icebox as the test server's map. The station z-levels were 2, 3 and 4, with a map width of 255.
2. Using the Lua editor, replay what the immovable rod event's `start()` does by hand. For each z in 2..4 and for each of the four start sides, take a start turf with `spaceDebrisStartLoc`, an end turf with `get_edge_target_turf` toward the opposite side, and create `/obj/effect/immovablerod` with the start turf, the end turf, no special target and `force_looping` false.
3. Check after 20 to 45 seconds. All 15 rods had crossed the map and been deleted (the Lua references to them were destructed). None stayed stuck.

This replays the event's logic by hand; the actual event was not triggered.

### Rod with no destination (reproduced)

1. In the Lua editor create a rod on a turf with no further arguments, which is what an admin Spawn effectively does: `SS13.new('/obj/effect/immovablerod', turf)`.
2. Wait. After two minutes the rod was still on its starting turf (113,141, z 4 on Icebox). It never moved.

This was checked it on Icebox only. By the code below it is not specific to Icebox.

## Cause

`code/modules/events/immovable_rod/immovable_rod.dm:34-53`, `Initialize()`:

```dm
var/turf/real_destination = get_turf(target_atom)
destination_turf = real_destination
...
if(special_target)
	GLOB.move_manager.home_onto(src, special_target)
else
	GLOB.move_manager.move_towards(src, real_destination)
```

With no `target_atom`, `real_destination` is null, and `move_towards(src, null)` starts no movement loop, so the rod sits where it was created. Nothing about this depends on the map.

The event-rod border problem that Icebox's layout caused was handled upstream: `Moved()` in the same file (`immovable_rod.dm:120-141`) deletes the rod when it has reached its destination or when it is parallel to the destination at the world border (`y == world.maxy`, `x == 1`, and so on). The comment there names Icebox. This is upstream PR 90810 ("Icebox rods delete themselves at the world border"). The 15-rod test above exercised that code.

## Fix

One commit, "Fix issue 71708: immovable rods spawned without a destination fly off instead of sitting still". In `Initialize()`:

```dm
else if(real_destination)
	GLOB.move_manager.move_towards(src, real_destination)
else
	// Spawned with no destination at all ...: fly the way we face.
	walk_in_direction(dir)
```

A destination-less rod now moves in the direction it faces (SOUTH by default) using the existing `walk_in_direction()`. The event path and the wizard rod-form path (which passes a target) are unchanged. The fix is labelled optional because it addresses a case that may not be the reported one.

## Verification

Checked on the test server after a rebuild:

- A bare rod placed at 60,150 on z 4 moved to 60,112 within seconds and was then gone. No runtimes appeared in the round's runtime log.

Not checked:

- Why the rod was deleted. The border check in `Moved()` sits inside `if(destination_turf)`, and a bare rod has no destination turf, so the deletion cannot be credited to that block. It may be an effect of leaving the z-level; this was not traced.
- Event-spawned rods and the wizard rod-form path after the fix (they are unchanged in code).
- Rods created with `force_looping`. On Icebox they are deleted at the border too, which upstream chose on purpose.
- Any other map, or a non-default facing.

## Notes

- Uncertain: the original rod (round 195614, with a testmerge that reverted part of #70431) may have been a different stuck state from 2022 that upstream has since fixed. Only the border case and the no-destination case were tested. A closing comment could ask the reporter for the rod's settings.
- Maintainers who prefer that destination-less rods stay inert could skip this commit; nothing else depends on it.
