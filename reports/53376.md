# #53376: tgui "suspend" and "close" messages are handled twice, so windows are suspended twice

| | |
|---|---|
| Issues | [#53376](https://github.com/tgstation/tgstation/issues/53376): verified |
| Status | Fixed on a branch (duplicate handling removed and checked in the server log; the zombie-window symptom itself was not reproduced) |
| Fix branch | [fix/53376](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/53376) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

When the tgui client sends a `suspend` or `close` message for a window that is locked by a `/datum/tgui`, the message is handled twice: once by the `/datum/tgui` and once more by the `/datum/tgui_window` it belongs to. The `/datum/tgui` handler closes the window but does not tell the window that the message was consumed, so the window runs its own `suspend`/`close` case and calls `close()` a second time. The fix returns `TRUE` (prevent default) from the `suspend` and `close` cases in `/datum/tgui/proc/on_message`, so each message is processed once.

## The bug

The issue reports that tgui windows get suspended twice, which interferes with window pooling "in a very subtle way" and might be the cause of "zombie windows": a window that opens in game code but never appears on the client, leaves the machine apparently stuck for about 10 seconds, and is then killed by the subsystem with `Error: Zombie window detected, closing.`

What actually happens is visible without any client symptom. Every `suspend` message from the client produces two `close (suspending)` entries in the tgui log, and the server sends a second `suspend` message to the client. A plain `close` message likewise closes the window twice.

## Reproduction

On master, with admin tools:

1. Connect as an admin on the test server and run the `Spawn` verb. This opens the `SpawnSearch` tgui interface in a pooled window (`tgui-window-1`).
2. Send that window a `suspend` message from the client side. This is the message the tgui JavaScript sends when a window is closed by the user (it comes from the suspense handler in the tgui client). It was sent here by injecting the message through the client's tgui message interface rather than by closing a rendered window.
3. Read `href.log` in the round's log directory.

Observed before the fix, two identical lines in the same millisecond:

```
[04:56:18.875] HREF-TGUI: <ckey> in tgui-window-1/close (suspending)
[04:56:18.875] HREF-TGUI: <ckey> in tgui-window-1/close (suspending)
```

Only the message path was exercised. The behaviour was reproduced by delivering the client's own tgui message to the server, not through a graphical window being closed with the mouse. The zombie-window symptom was not reproduced (see Verification).

## Cause

Incoming tgui messages reach `/datum/tgui_window/proc/on_message` (`code/modules/tgui/tgui_window.dm:333`). If the window is locked by a UI, the message is first passed to that UI's handler (`code/modules/tgui/tgui_window.dm:348-350`):

```dm
if(locked && locked_by)
	var/prevent_default = locked_by.on_message(type, payload, href_list)
	if(prevent_default)
		return
```

Only if the handler returns a true value does the window stop processing. Otherwise the window continues to its own `switch(type)`, which also has `suspend` and `close` cases (`code/modules/tgui/tgui_window.dm:368-371`):

```dm
if("suspend")
	close(can_be_suspended = TRUE)
if("close")
	close(can_be_suspended = FALSE)
```

`/datum/tgui/proc/on_message` (`code/modules/tgui/tgui.dm:348`) handles the same two message types (`code/modules/tgui/tgui.dm:366-369`) by calling `close()` on itself, and returns nothing:

```dm
if("suspend")
	close(can_be_suspended = TRUE)
if("close")
	close(can_be_suspended = FALSE)
```

`/datum/tgui/proc/close` (`code/modules/tgui/tgui.dm:133`) releases the window lock and calls `window.close(can_be_suspended)` (`code/modules/tgui/tgui.dm:143-144`). `/datum/tgui_window/proc/close` (`code/modules/tgui/tgui_window.dm:213`) logs `close (suspending)`, marks the window ready and sends a `suspend` message to the client. Because `/datum/tgui/proc/on_message` returned nothing, the window then runs its own `suspend`/`close` case and calls `close()` again: a second log line, a second `suspend` message to the client, or a second close.

The `closing` guard at the top of `/datum/tgui/proc/close` does not help, because the second call goes straight to `/datum/tgui_window/proc/close`, not through the UI.

## Fix

One commit, "Fix issue 53376: tgui windows no longer suspend twice", changes `code/modules/tgui/tgui.dm` (+4 lines). In `/datum/tgui/proc/on_message`, the `suspend` and `close` cases now `return TRUE` after calling `close()`, with a comment explaining why. Returning `TRUE` is the existing "prevent default" convention, so the window's own handler is skipped.

No alternative was recorded. Removing the window's own `suspend`/`close` cases would not have worked as a simple fix, since the window handler is also what processes these messages when no UI holds the lock.

## Verification

On the test server, after rebuilding with the fix:

- Opened the `Spawn` window and sent a `suspend` message: one `close (suspending)` line in `href.log`, where master produced two.
- Sent a `close` message to a freshly opened window: one `close` line.
- Reopened `Spawn` after the suspend: the pooled window `tgui-window-1` was reused.

Not checked:

- The zombie-window symptom (window open in game code but not visible, 10-second stall, `Zombie window detected, closing.`). That needs a graphical client and was not tried. It is not known whether this bug is its only cause.
- The JavaScript side of tgui was not changed or tested.
- Windows not locked by a `/datum/tgui` (those that go through the window's own handler only) were not tested.
- No real client closed a window; the messages were injected.

## Notes

- The fix touches core tgui code, so it deserves a careful review from the tgui maintainers.
- A secondary hazard of the duplicate handling: the first `close()` releases the window lock, and a UI's `ui_close()` handler may re-acquire the same window for another UI before the second `close()` runs. The second call could then suspend or close a window that a different UI now owns. This is how the issue's zombie windows could come about. It was derived from reading the code and was not demonstrated.
