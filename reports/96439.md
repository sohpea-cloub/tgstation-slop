# #96439: A glitch inside a locker can be carried into the bitrunner safehouse

## Summary

Virtual entities (bitrunning glitches and similar) are stopped from entering the bitrunner safehouse by a pre-move check that is registered only on the entity itself. When the entity is inside a locker, the locker is what moves, so the check never runs and the locker, with the entity in it, can be pushed into the safehouse. The fix also registers the same check on every container the entity is inside, using `connect_containers`.

## The bug

On a virtual domain with many glitch spawns (the beach domain in the report), a glitch can climb into a locker and have another player push the locker into the bitrunners' safehouse. Once inside, the glitch can leave the locker and is then in the safe area it should never be able to reach (the report says it is "stuck in place there").

## Reproduction

The reproduction used the Lua editor on the test server and moved the locker by calling the movement subsystem directly. It was not a push by a second player. The tester also did not use the beach domain: the safehouse was imitated, because the check only depends on the destination area's flags.

1. Using the Lua editor, create a `/area/virtual_domain/safehouse` and assign one turf to it (the target turf, at x=110) with `change_area`.
2. Create a quantum server and a human, and give the human the component: `_AddComponent({_text2path('/datum/component/virtual_entity'), server})`.
3. `forceMove` the human into a closet on the turf directly west of the safehouse turf (x=109).
4. Push the closet east with `dm.global_vars.GLOB.move_manager:move(closet, 4, 1, 10)`. Calling `closet:Move()` or `step` from Lua did not work (`Move` always returned 0), so the movement subsystem was used instead.
5. Observed on master: the closet moved onto the safehouse-area turf with the human still inside it.

## Cause

`/datum/component/virtual_entity/Initialize` (`code/modules/bitrunning/components/virtual_entity.dm:7`) registers the restriction only on the parent:

```dm
RegisterSignal(parent, COMSIG_MOVABLE_PRE_MOVE, PROC_REF(on_parent_pre_move))
```
(line 12). `on_parent_pre_move` (line 33) blocks the move if the destination area has `VIRTUAL_SAFE_AREA` (line 41). `COMSIG_MOVABLE_PRE_MOVE` is sent by the atom that is being moved. A mob inside a locker does not move when the locker is pushed; the locker does, so the mob's signal never fires and the safe-area check is skipped. The safehouse area (`code/modules/bitrunning/areas.dm:31`) has `VIRTUAL_SAFE_AREA` set, so nothing else stops the locker.

## Fix

One commit, "Fix issue 96439: virtual entities can no longer be carried into the bitrunner safehouse", changing only `virtual_entity.dm`:

- `Initialize` now also adds a `/datum/component/connect_containers` on the parent, with a static list that maps `COMSIG_MOVABLE_PRE_MOVE` to the same `on_parent_pre_move`. The check therefore also runs for each container the entity is in (locker, mech, bag, and so on).
- `on_parent_pre_move`'s `source` may now be the container, so the "out of bounds!" balloon alert is shown by the entity (`parent`) instead of `source`, so the entity sees it.

`connect_containers` was chosen because it follows the container chain as it changes, without adding code to lockers or other containers.

## Verification

On the test server with the fix built, using the same Lua setup, two closets were pushed east toward a safehouse-area turf at x=110 for the 10 s push loop:

- Virtual entity in a closet (y=145): the closet stayed at x=109 and the human was still inside.
- Control, a plain human with no component (y=143): the closet crossed x=110 and ended at x=127.

The runtime log for the verifying round showed no runtimes (apart from a known empty-line Lua message). A first attempt moved nothing because the second row's turf at x=110 was a wall and the loop timeout was too short; that was corrected by using floor rows and a longer timeout.

Not checked: the "out of bounds!" balloon alert (the test had no client-controlled body, so only positions were checked); an actual player pushing a locker; the real beach domain or the real safehouse; other containers such as mechs or bags; a human leaving a locker normally in a non-restricted area.

## Notes

- `connect_containers` adds a component and a few signal registrations per virtual entity; a maintainer may weigh that against handling it in the locker code.
- The 2-second `OOB_cooldown` is started but not read by this proc (the block runs on every attempt); this was not changed.
