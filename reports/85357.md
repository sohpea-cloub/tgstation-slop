## Summary

An immovable rod sent at a chosen target (the admin "aim" option) does not home in on it. The rod uses the `move_towards` movement loop, whose per-axis "ticker" is snapped with `FLOOR(ticker + rate, rate)`. Floating-point error can leave that value just under the next multiple of the rate, so the ticker stops advancing and the loop never moves along its minor axis again. The fix accumulates the tickers directly (`ticker += rate`) and also corrects a typo that reduced `y_ticker` from `x_ticker`. The change is in a core movement loop and therefore affects every `move_towards` user. #84651 (False Alarm picking Aurora Caelus) could not be reproduced: master already returns from the fake announcement before touching space lighting.

## The bug

### #85357

An admin triggered the Immovable Rod event, aimed it at telecomms and set it to loop. The rod did not pass through telecomms and did not loop. Comments on the issue added that the rod sometimes veers straight up or down when it reaches the target, and that it can loop even when looping was not chosen.

What was actually happening:

- **Aiming:** the admin setup code was correct. The chosen turf was passed to the rod as `special_target`, and the rod took the homing branch. The movement loop then stopped correcting its course, so the rod flew in a straight line along one axis and missed the target.
- **Looping:** `force_looping` was passed through correctly and a forced rod did loop on a self-looping z-level. A rod also loops on a self-looping z-level without the option, which is intended according to the comment on `loopy_rod`. This matches the comment that the rod "can also loop even if you choose not to". No separate defect was found there.

### #84651

The issue reports that when False Alarm picks Aurora Caelus, space turns green and stays green. This is not reproducible on master (see Reproduction).

## Reproduction

### #85357

The rod was created by a Lua editor script calling the same constructor the event uses, not by firing the event through the admin panel. The event's setup code was read and found correct, so this exercises the movement path directly.

1. On the test server, with a round running, open the Lua editor.
2. Create a rod with a start turf, an end turf and a special target on another row: `SS13.new('/obj/effect/immovablerod', locate(235,100,2), locate(1,100,2), locate(107,144,2), false)`. The rod starts at (235,100) on z2, its end point is (1,100) and the target turf is (107,144).
3. Log the rod's position each second.
4. Observed on master: after the first few steps the rod stopped changing y and travelled along y=113 for the rest of its flight, passing x=107 nowhere near the target's y of 144. Positions per second: `226,103`, `216,106`, `206,109`, `196,113`, then y stayed at 113 while x kept decreasing.
5. A per-step debug line added temporarily inside the movement loop (and removed afterwards) showed the cause: `from=195,113 want=194,113 xt=0 yt=0.688889 xr=1 yr=0.344444`, and `yt` stayed at 0.688889 on every following step.
6. Before arriving at the cause, an earlier run with only the `y_ticker` typo fixed (see Cause) still showed y stuck, so the typo alone does not explain the behaviour.

Whether the stall occurs depends on the movement rate. In this run it began after about 40 steps.

### #84651

1. Using the Lua editor, create a `/datum/round_event/falsealarm`, set its `forced_type` to the Aurora Caelus event control, and run its announcement.
2. Read the starlight colour for 60 seconds.
3. Observed: starlight stayed at `#8589fa/2`, the base value, throughout.
4. For comparison, a real `round_event/aurora_caelus` with `end_when` set to 30 was run. Space colours cycled through green and blue, and returned to `#8589fa/2` after the end announcement and stayed there.

The leftover green patches on kitchen floors mentioned in a comment on the issue (seen on Wawastation) were not checked.

## Cause

### #85357

`code/controllers/subsystem/movement/movement_types.dm:737` is `/datum/move_loop/has_target/move_towards/move()`. At master it advances its tickers with:

```dm
if(x_rate) //Did you know that rounding by 0 throws a divide by 0 error?
	x_ticker = FLOOR(x_ticker + x_rate, x_rate)
if(y_rate)
	y_ticker = FLOOR(y_ticker + y_rate, y_rate)
```

(`code/modules/events/immovable_rod/immovable_rod.dm:51` starts this loop via `home_onto` when a special target is set.)

`FLOOR(x, y)` is defined in `code/__DEFINES/maths.dm:45` as `( round((x) / (y)) * (y) )`, and BYOND's one-argument `round()` floors. So the ticker becomes `floor((ticker + rate) / rate) * rate`. When the ratio is mathematically a whole number but is computed a hair below it in floating point, it floors to the previous integer, and the ticker snaps back to the previous multiple of the rate. In the observed run, `(0.688889 + 0.344444) / 0.344444` is mathematically 3 but computed just under 3. It floors to 2, so the ticker was reset to 2 * rate on every step, and the y axis never moved again.

A second, separate typo is at `movement_types.dm:753`: `y_ticker = MODULUS(x_ticker, 1)` reduces `y_ticker` using `x_ticker`.

The suspicion that `update_slope` resets the tickers was checked and ruled out: the cause is the snapping.

### #84651

`round_event/aurora_caelus/announce(fake)` (`code/modules/events/aurora_caelus.dm:20`) returns right after the priority announcement when `fake` is set (`:24`), before the sound and before fading space and the kitchen floors. A False Alarm therefore does not change lighting on master, so the "green forever" state described in the issue cannot arise this way.

## Fix

Commit "Fix issue 85357: homing move_towards loops no longer stall on float error" changes `move_towards/move()` in `code/controllers/subsystem/movement/movement_types.dm`:

- `x_ticker = FLOOR(x_ticker + x_rate, x_rate)` became `x_ticker += x_rate`, and likewise for y. The remainder is still reduced with `MODULUS(..., 1)` once a ticker reaches 1, so the tickers keep tracking the fractional remainder as the comment says they should.
- `y_ticker = MODULUS(x_ticker, 1)` became `y_ticker = MODULUS(y_ticker, 1)`.
- The `if(x_rate)` / `if(y_rate)` guards remain (they were there to avoid dividing by zero in `FLOOR`; plain addition does not need them, but they were left in place).

No alternative was tried: plain accumulation is the simplest change and no longer divides by the rate.

## Verification

#85357: after the change the test server was rebuilt and the same rod was sent from (235,100) at the target (107,144) on z2. Positions per second were `235,100`, `226,103`, `216,106`, `206,109`, `196,113`, `186,116` ... `116,140`, `106,144` (the special target was still set up to here), then `106,154` ... `106,244`, then the rod was gone. The rod reached the target, `complete_trajectory` ran, the rod then continued straight and was deleted at the edge of the map.

#84651: confirmed unchanged lighting for a False Alarm and normal restoration after a real event, as under Reproduction.

Not checked:

- Other `move_towards` users (any caller of `move_towards` or `home_onto`) were not tested; the change affects them all.
- The admin panel dialog itself was not driven to fire the event; the rod was created directly with the same arguments.
- The reported rods that turn straight up or down on reaching the target.
- A forced-loop rod on a non-self-looping z-level.

## Notes

- Because `move_towards` is a core movement loop, a maintainer should look at this change as affecting every user, whether homing or not; the stall could occur for other rates too.
- Side finding, not fixed: a rod with a special target on another z-level, whose path crosses the edge of a z-level, reaches the "phases out of reality" branch in `immovable_rod.dm` `Moved()` (`:108`), where `get_step_multiz` can return null and `do_teleport(src, null)` then runtime-errors (`code/game/atoms/movable/teleport.dm:68`, as reported by the runtime log). Real events spawn several tiles inside the edge, so this is rare.
- Looping: a forced rod on z2 looped as expected, and a non-forced rod on a self-looping z-level also loops, which is intended by the code. No change was made to looping.
- #84651 appears to have been fixed upstream before master `87b93338`; no code change was needed.
