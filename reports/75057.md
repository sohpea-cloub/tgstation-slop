## Summary

All five issues report the green "genturf" marker turf showing up in the world, usually after a ruin floor is destroyed (RCD, explosion, singularity). Genturfs are placeholders that terrain generation is supposed to replace. They used to survive under ruins because ruins were loaded before terrain generation. Master now loads ruins after terrain generation (upstream PR #97083, as identified in the investigation). On master no genturfs were found on IceBox or lavaland, including after ScrapeAway and explosions at the locations named in the issues. Nothing was changed.

## The bug

Players see bright green turfs (`/turf/open/genturf`, a mapping marker) either at roundstart outside a station or ruin, or after something removes the floor of a ruin and exposes what is underneath. The five reports are:

- #75057: on IceBox, deconstructing the snowed-over plating outside the Engineering Outpost ruin with an RCD exposed genturf.
- #57449: on lavaland, the Syndicate base self-destruct (or a potassium-water bomb) left genturf behind. Comments report the same for the seed vault and the icebox village ruin.
- #91103: a genturf just outside the station on IceBox (the reporter did not know the cause; a maintainer suggested a duplicate of #57449).
- #94048: IceBox, blowing up a welding fuel tank next to the Thing ruin's keycard blast doors exposed genturf.
- #94987: IceBox, a singularity left genturfs behind where it consumed terrain.

The explanation given in #57449 (a comment by LemonInTheDark) is that genturfs are markers for area terrain generation and are normally replaced when the area's map generator runs. Ruins were loaded before that step and placed their turfs on top of the unreplaced genturfs, so the genturf became the baseturf under the ruin floor, ready to be exposed.

## Reproduction

The original ordering was not re-run, so the bug itself was not reproduced. The following was checked on master instead, using admin tools on a test server:

1. IceBox, roundstart: SDQL2 `SELECT /turf/open/genturf` returned 0 objects.
2. IceBox, Engineering Outpost (#75057): at 126,29,4 the "snowed-over plating" outside the outpost was `/turf/open/floor/plating/snowed/smoothed/icemoon`, with baseturfs `[openspace/icemoon, misc/asteroid/snow/icemoon]`. `ScrapeAway(1)` on it produced `/turf/open/misc/asteroid/snow/icemoon`. An explosion at 122,31,4 (devastation 3, heavy 6, light 10) left 0 genturf in a 24 by 21 area around it.
3. IceBox, Asteroid Site ruin: the ruin's map contains a mapped genturf, but in the test round its turfs had been generated (basalt, `lava_land_surface`), with lava baseturfs and no genturf.
4. IceBox, the Thing / Outpost 31 region (#94048) on z3, x 110 to 150, y 30 to 60: 0 genturf turfs and 0 genturf in baseturfs.
5. IceBox, singularity (#94987): no singularity was run. Instead, turf destruction (`ScrapeAway` and explosions) was done and exposed snow asteroid, never genturf. This does not exactly match the issue's scenario.
6. IceBox, roundstart (#91103): 0 genturf at roundstart; the genturfs mapped in `IceBoxStation.dmm` are replaced by terrain generation.
7. Lavaland (Metastation): 32 ruins, with an explosion (devastation 6, heavy 10, light 14) at each, then about 20000 turfs scanned: 0 genturf types and 0 genturf in baseturfs.
8. Lavaland Syndicate Lava Base (#57449): it was not rolled naturally, so it was placed through the Map Template Place verb. 2304 turfs were scanned after 4 large explosions (8, 12, 16): 0 genturf. Its baseturfs start with `lava_land_surface` (a baseturf helper from upstream PR #60419).

Turf checks used the Lua editor (`dm.global_procs._locate(x, y, z)` for turf access, `baseturfs` list for baseturfs) and SDQL2.

## Cause

Not applicable on master; the historical cause is described above and is consistent with the code now. In `code/controllers/subsystem/mapping.dm` (around lines 163-170):

```dm
// Run map generation after ruin space is reserved, since this space is used for the cave gen.
run_map_terrain_generation()
// Generate our rivers, we do this here so the map doesn't load on top of them
setup_rivers()
// Now that terrain generation is done, actually load the ruin maps in.
load_reserved_ruins()
```

Ruin space is reserved first (`setup_ruins()`), terrain generation runs on the rest, and the ruin maps are then loaded on top (`load_reserved_ruins()` at line 282, `load_ruin_now()` at line 294). This is the order LemonInTheDark's comment on #57449 said was needed. The inputs attribute the change to upstream PR #97083 ("Refactors ruin load order to make sure they spawn after map generation", merged 2026-07-21). The PR number and date come from the investigation, and the local checkout (shallow) does not contain the PR's own commit, so they could not be confirmed here.

## Fix

None. No change was made.

## Verification

What was checked is listed under Reproduction. In short: no genturf at roundstart, after targeted `ScrapeAway` and explosions on IceBox and on lavaland, and in every ruin checked.

Not checked:
- The old load order was not restored, so the original failure was not reproduced and the claim that PR #97083 fixed it rests on the code order and on the absence of genturfs on master.
- No singularity was run for #94987, and the welding-tank explosion from #94048 was not repeated exactly; large explosions at the same locations were used instead.
- Only a few rounds were run, so a rare placement that still leaves a genturf is not excluded.
- Away missions and other map types were not checked.

## Notes

- A unit test already guards this: `code/modules/unit_tests/orphaned_genturf.dm` (a map test) fails if any `/turf/open/genturf` exists after generation.
- Related, not part of this work: #75057, #57449, #91103, #94048 and #94987 can probably be closed as fixed by the upstream ruin load order change, if a maintainer agrees. #91103 is the least certain, because its report does not say how the genturf appeared or where.
- Reports that predate the change (most of the comments on #57449, including the icebox village ruin and seed vault) are consistent with the old ordering. #94048 and #94987 were opened in late 2025 and early 2026, before the merge date given above.
