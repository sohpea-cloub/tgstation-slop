# #67901: Custom radio emotes bypass telecomms garbling

| | |
|---|---|
| Issues | [#67901](https://github.com/tgstation/tgstation/issues/67901): verified, fixed for the compressed-signal case (the "no telecomms at all" case was not tested, see Verification) |
| Status | Fixed; checked in game on the test server |
| Fix branch | [fix/67901](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/67901) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

When telecomms garbles a radio transmission (a compressed signal, as with an overloaded or compressing processor), only the spoken message is garbled. A custom say emote sent over the radio (`; slaps his mic and mutters. Damn Radio is out.*`) is stored separately from the message and arrived intact. The fix garbles the emote text too, with the same rules as the message, when the signal is compressed.

## The bug

Players can write a radio message of the form `;<emote text>*<spoken text>`, i.e. a custom say emote on the radio. During a telecomms problem that garbles radio speech, a normal radio line such as `;The radio is out.` arrives as noise, but the same information written as the emote part (`; slaps his mic and mutters. "Damn Radio is out."*`) arrived clear. This lets players communicate over a broken radio network. Comments on the issue suggest that it may be treated as a rule matter ("ban people who abuse it"); this write-up only covers the code.

## Reproduction

On master, on the test server with admin tools:

1. Observe, and open the Lua editor.
2. Set every `/obj/machinery/telecomms/processor` to `compressing = 1` (this makes every transmission pass through with a compression of 100).
3. Spawn a human wearing a `/obj/item/radio/headset`.
4. Make the human say `;Hello this is a normal message` on the common channel.
5. Make the human say `; slaps his mic and mutters. Damn Radio is out.*`.

Observed:

- The normal message arrived garbled: `[Common] ... says, "$*elo&*t*#is $> a *o*@*l *ssag"`.
- The emote arrived clear: `[Common] Ulyssa Sidower slaps his mic and mutters. Damn Radio is out.`

The plain "slaps his mic..." lines that also show up in the chat are the speaker's own local (non-radio) hearing and are expected.

This reproduces the processor "compression" garbling case from the issue's title. The "Exospheric outage" case (see Verification) was not tested.

## Cause

A radio transmission is wrapped in a `/datum/signal/subspace/vocal`. Its `data["message"]` holds the spoken text, and `data["mods"]` holds the message modifiers, which include the custom emote text under `MODE_CUSTOM_SAY_EMOTE` (copied across in `code/game/objects/items/devices/radio/radio.dm:414-415`).

When telecomms processors compress the signal (`code/game/machinery/telecomms/machines/processor.dm:27-28`), `data["compression"]` goes above zero. In `/datum/signal/subspace/vocal/broadcast()` (`code/game/machinery/telecomms/broadcasting.dm:117-119`) only the message is garbled:

```dm
var/compression = data["compression"]
if(compression > 0)
	message = Gibberish(message, compression >= COMPRESSION_REPLACE_CHARACTER_THRESHOLD)
```

But when the message is rendered, `generate_messagepart` (`code/game/say.dm:237-244`) shows the emote text instead of the message: for a pure emote (`MODE_CUSTOM_SAY_ERASE_INPUT`) it returns only the emote, otherwise it uses the emote as the "says" verb. The emote text in `message_mods` was never garbled, so it reached every listener intact.

## Fix

One commit: "Fix issue 67901: garble custom say emotes sent over radio when the signal is compressed". In `broadcast()` (`code/game/machinery/telecomms/broadcasting.dm`), after `message_mods` is read from the signal data, if `compression > 0` and the mods hold a custom say emote, the list is copied and the emote is passed through `Gibberish` with the same replace-character threshold as the message:

```dm
if(compression > 0 && LAZYACCESS(message_mods, MODE_CUSTOM_SAY_EMOTE))
	message_mods = message_mods.Copy() // the list is shared with the original signal and its copies
	message_mods[MODE_CUSTOM_SAY_EMOTE] = Gibberish(message_mods[MODE_CUSTOM_SAY_EMOTE], compression >= COMPRESSION_REPLACE_CHARACTER_THRESHOLD)
```

The copy is needed because the `mods` list is shared with the original signal and its `copy()` instances; modifying it in place would change the other copies. The change is placed in `broadcast()`, next to where the message is garbled, rather than in the radio code, so all signals that pass through telecomms get the same treatment.

## Verification

On the fixed build, with the same setup (all processors compressing, compression 100):

- `; slaps his mic and mutters. Damn Radio is out.*` arrived as `[Common] Jamie Byers &%laps h$@* &#ca***mutt*%;s** ;&*$ Radois *t`.
- A second emote, `;*waves...`, arrived as `W@v& h*llo t/<@;ev@***yne`.
- The normal message was still garbled as before.
- With compression 0 (processors set back to decompressing), the emote path was unchanged: no garbling.

Not tested:

- The exact "Exospheric radio outage" case from the title, where there are no working telecomms at all. Without a working broadcaster, headsets receive nothing, and non-subspace radios send with compression 0 through `backup_transmission` (`radio.dm:391`, and `signal.data["compression"] = 0` at `broadcasting.dm:365,397`), which is presumably by design. Whether an emote can bypass such an outage was not checked.
- Non-headset radios, intercoms, and other signal types.
- The unit tests were not run.

## Notes

- Because only the signal type with compression is changed, anything that treats an emote as free text in a compressed transmission (for example, admin or logging output) is not affected; the speaker's own log of the emote is unchanged (`code/__HELPERS/logging/talk.dm`).
- A maintainer comment on the issue suggested "wontfix, just ban people who abuse it". This fix is the code-side alternative.
