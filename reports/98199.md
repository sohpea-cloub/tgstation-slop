## Summary

When a ghost accepts the possessed blade's poll, `spirit_holding` hands the ghost's mind to the new shade, but a ghost's mind is not active, so the player's client is never moved. The shade has no client, its name prompt returns null, `sanitize_name` shows "Invalid name." and `custom_name` calls itself again with `iteration++`, which never raises the retry counter, so the prompts never stop. Ghosts that never had a body (lobby observers) have no mind at all, which causes a runtime that leaves the blade half-bound: it examines as "alive" but a bible does nothing. The fix creates a mind when needed, moves the key by force, treats a cancelled or missing name prompt as "keep the default name" and passes `iteration + 1` to the retry.

## The bug

Players who chose the possessed blade as a null rod form and used it in hand to request a spirit saw this:

- A ghost signed up and was "selected", but the blade never talked and the candidate could not speak or interact (#98199).
- The awakener, and in some reports the candidate, were buried in "Invalid name." alerts; closing one produced another (#96805 reports the game slowing to a crawl until the sword was destroyed).
- Examining the blade said it was alive, but a chaplain's bible did nothing, so the spirit could not be exorcised (#98199).

#85087 (2024) is the same report. A commenter there says that after a follow-up PR (#85090) ghosts could take the blade but the error spam continued for a few minutes; the loop is still present on master `87b93338`.

## Reproduction

Using the Lua editor on the test server (the real use-in-hand path was exercised through `attack_self`):

1. Start the round with an observer connected from the lobby (the character has no mind) and open the Lua editor.
2. Spawn a human and a `/obj/item/nullrod/claymore/talking` (the possessed blade), put the blade in the human's hand and call `attack_self(human)` on it. This starts the ghost poll.
3. Sign up for the poll from the observer through the poll's "Sign Up" link and wait about 20 seconds.
4. Observed on master:
   - The runtime log shows `Cannot execute null.transfer to()` at `spirit_holding.dm:108`, with call stack `bind_the_soule` from `affix_spirit` from the poll callback, and the observer as `usr`.
   - An endless chain of "Invalid name." alerts follows; answering one produced a new one each time.
5. Second case, a ghost that had a body before (it has a mind, but an inactive one): no runtime, but the player stayed a ghost and still received the endless "Invalid name." alerts.

The bible symptom was matched by code reading: when `bind_the_soule` runtime-fails halfway, `bound_spirit` is already set (so the blade looks "alive") but the `COMSIG_BIBLE_SMACKED` registration at line 114 is never reached.

## Cause

All in `code/datums/components/spirit_holding.dm` unless noted.

1. Line 95, in `affix_spirit`: `bind_the_soule(ghost.mind, awakener)`. `bind_the_soule` then calls `chosen_spirit.transfer_to(bound_spirit)` (line 108). `/datum/mind/transfer_to` only moves the client when `active || force_key_move` (`code/datums/mind/_mind.dm:216`), and a ghost's mind is not active. The shade therefore never gets the key.
2. For lobby observers `ghost.mind` is null (`/mob/dead/observer/sync_mind()` does nothing, `_mind.dm:537`), so line 108 runtimes with `null.transfer_to()`. The remaining lines of `bind_the_soule`, including the bible registration, do not run.
3. `custom_name` (lines 122-129):

   ```dm
   var/chosen_name = sanitize_name(tgui_input_text(bound_spirit, "What are you named?", ...))
   if(!chosen_name)
   	to_chat(awakener, span_warning("Your blade did not select a valid name! ..."))
   	return custom_name(awakener, iteration++)
   ```

   With no client on the shade, `tgui_input_text` returns null. `sanitize_name(null)` (`code/__HELPERS/text.dm:25-33`) fails `reject_bad_name`, pops `tgui_alert(usr, "Invalid name.")` and returns an empty string, so the code retries. `iteration++` passes the old value and increments the local copy afterwards, so the `iteration > 5` cap at line 123 can never trigger.

## Fix

One commit, "Fix issue 98199: possessed blade spirit never got the ghost's client and looped on invalid-name prompts", in `spirit_holding.dm`:

- `affix_spirit`: if the ghost has no mind, a new `/datum/mind` is created for the ghost's key (with the ghost's real name and added to `SSticker.minds`). The mind is set `active = TRUE` and `bind_the_soule` is called with `force_key_move = TRUE`.
- `bind_the_soule`: takes a new `force_key_move` argument and passes it to `transfer_to`.
- `custom_name`: if the input is null (cancelled, or the spirit has no client) it returns null, so the spirit keeps the default name instead of being nagged; otherwise the retry uses `iteration + 1`, so the cap of five tries works.

The approach keeps the existing flow and only fixes the hand-over and the loop. It does not change `sanitize_name`.

## Verification

On the test server after rebuilding, in a new round:

- Lobby observer (no mind): the poll chose the observer ("Possessed Blade Poll: ... was selected"), the observer's view became the blade's shade, the "Spectral Nomenclature" input window opened for them and there was no runtime. Submitting an invalid name ("1234") brought the prompt back once (bounded retries); cancelling it produced no further prompts.
- Bible exorcism: with a human whose mind had `holy_role` set, calling the bible's `interact_with_atom` on the blade printed "You were exorcised!", then "... exorcises the possessed blade!" and the spirit went back to being a ghost. The bible signal is now registered.
- Second poll with the ghost that now had a mind (inactive): it again became the shade, got the name prompt, and there was no loop.

Not checked:

- Entering a valid name end to end (the prompt appears; the `fully_replace_character_name` call after it was not changed).
- A ghost whose mind is attached to a real previous character and who returns to it afterwards.
- Other users of `spirit_holding` (other possessable weapons) beyond the possessed blade null rod.

## Notes

- The "Invalid name." alert from `sanitize_name` is shown to `usr`, which is not necessarily the spirit. This explains why the awakener sees prompts in the reports; it was left as it is.
- The new mind is created with the ghost's key and given the ghost's real name only; a maintainer may prefer to create it elsewhere, or with a shared helper if one exists.
- #85087 was reported in 2024; PR #85090 did not fix it, since the loop is still present on master.
