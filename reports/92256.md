## Summary

**#92256:** Bumping a depowered external airlock from inside a mech starts the "unlocking the airlock safety mechanism" action. After 15 seconds the door is forced open, though a mech occupant has no free hands. The cause is that `/obj/machinery/door/airlock/external/try_safety_unlock()` has no hands check in its unpowered branch, and vehicles reach it through `/obj/vehicle/sealed/Bump()`. The fix refuses when the user has `TRAIT_HANDS_BLOCKED`.

**#71505:** The mech typing-indicator report (a stuck indicator on an empty mech) could not be reproduced. Code reading found no path that leaves one, but the in-game check was inconclusive.

## #92256: depowered airlocks open from inside a mech

### The bug

The reporter walked a mech into a depowered airlock (they thought the ones at evac or arrivals) and it opened. This is inconsistent with a person on foot with blocked hands, and with ordinary depowered airlocks, which do not open on bump.

### Reproduction

On master, using the Lua editor to set up the scene:

1. Start a round and observe.
2. Spawn a human and an `/obj/vehicle/sealed/mecha/ripley`, and put the human in the mech (`mob_try_enter`).
3. Spawn an `/obj/machinery/door/airlock/external` with `space_dir = 1`, cut all its wires, and unbolt it so it is unpowered and closed.
4. Move the mech into the door and call `Bump` on it.

Observed: the occupant got "You begin unlocking the airlock safety mechanism...". About 15 seconds later the forced-open sound played and the door opened. A plain (non-external) depowered airlock did not open on bump (`bumpopen` needs power).

The mech movement and bump were driven with Lua `Move`/`Bump` calls rather than by a player steering into the door.

### Cause

`/obj/vehicle/sealed/Bump()` (`code/modules/vehicles/sealed.dm:41-46`) calls `conditionalwall.try_safety_unlock(occupant)` for every occupant. For an external airlock, `try_safety_unlock()` (`code/game/machinery/doors/airlock.dm:2334`) takes the unpowered branch, runs a 15-second `do_after`, and calls `try_to_crowbar()`. That branch never checks whether the user has hands. The normal mob path through `door.dm` `Bumped` does check `TRAIT_HANDS_BLOCKED`, but the vehicle path does not go through it. Every vehicle occupant gets `TRAIT_HANDS_BLOCKED` in `after_add_occupant()` (`sealed.dm:49-51`), and the mech `add_occupant` override calls the parent, so mech drivers have it.

### Fix

One commit, "Fix issue 92256: no forcing depowered external airlocks open from inside a vehicle". In the unpowered branch of `try_safety_unlock()` it adds `if(HAS_TRAIT(user, TRAIT_HANDS_BLOCKED)) return FALSE` before the message and `do_after`. It is placed in the airlock rather than in `Bump()` so that other vehicle-bump paths cannot force the door either.

### Verification

After a rebuild, with the same setup:

- Bumping the closed unpowered door from the mech twice and waiting 23 seconds left it closed.
- Control: a free-handed human on foot, calling `Bumped` on the same kind of door, saw it open after about 19 seconds. So the on-foot path still works.

The "begin unlocking" message goes to the occupant's client, and the mob had no client in this test, so the evidence is the door staying closed, not the absence of a chat line. Not checked: a real player driving a mech into the door, other vehicle types, and powered external airlocks.

## #71505: stuck mech chat indicator

### Not reproduced

The report says a speech or typing indicator stays on a mech after the occupant stops talking, even when the mech is empty. The report is from 2022.

Code reading on master:

- The mech speech bubble (`code/modules/vehicles/sealed/mecha/_mecha.dm`, `display_speech_bubble`) goes through `flick_overlay_global` (`code/__HELPERS/game.dm:101`), a client image removed on a 3-second client-time timer, so it should not stick.
- The typing and thinking indicators (`tgui_input/say_modal/typing.dm`) are overlays on the speaking mob, removed by `stop_typing` and `remove_all_indicators` (also on stat change and Logout). Nothing in the mech code copies occupant overlays onto the mech.

An in-game attempt called `display_speech_bubble` from Lua with only an observer client in range. No client was a recipient (client image count 0 before and after), so the test is inconclusive. The speech bubble code appears to have been rewritten since the report, so this was possibly fixed incidentally. No change was made.

## Notes

- #71505 would need a test with a real player in a mech typing and speaking, exiting, then checking the mech's overlays from a second client.
- Because the `try_safety_unlock` check is on the user, a mob with hands blocked for another reason (for example restrained) is also refused. This seems consistent with the intent but was not tested.
- Another upstream approach, putting the check in `Bump()`, was not tried.
