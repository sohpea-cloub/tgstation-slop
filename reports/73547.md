# #73547: The IC word filter can be bypassed by gluing a word to a radio prefix

| | |
|---|---|
| Issues | [#73547](https://github.com/tgstation/tgstation/issues/73547): verified, fixed |
| Status | Fixed on the fix branch; verified in game |
| Fix branch | [fix/73547](https://github.com/sohpea-cloub/tgstation-slop/tree/fix/73547) |
| Tested on | tgstation master `87b93338`, 2026-10-23 |

## Summary

A word on the IC filter list could be said by writing it directly after a radio or mode prefix, for example `:hword` or `.hword`. The filter checked the raw text, where the word has no word boundary in front of it, but the prefix was then stripped and the bare word was spoken. The fix moves the filter into a reusable `passes_ic_filter` proc and runs it a second time on the prefix-stripped message.

## The bug

The report (round 200412) says that saying a blocked word as the first word of a message on a department channel, using a department prefix, got through. The prefix part was blocked but the radio message was not. A comment notes that the same words were blocked with the `;` prefix or when they were not the first word. A later comment gives `.h<blockedterm>` as a working example.

## Reproduction

1. On a local test server, add a word to the `[ic]` section of `config/word_filter.toml`. The test word was `blockedinic`.
2. Join as an Assistant and de-admin. Admins skip the filter through `CAN_BYPASS_FILTER` (`code/__DEFINES/chat_filter.dm:12`), so an admin cannot reproduce this.
3. Say each of the following:
   - `blockedinic`, `;blockedinic` and `:h blockedinic` (note the space) were blocked.
   - `:hblockedinic` was spoken on the common channel as `Sheri Wilson says, "Blockedinic"` (the filter was bypassed).
   - `.hblockedinic` also went through.

## Cause

In `/mob/living/say` (`code/modules/mob/living/living_say.dm`), the original text is saved at line 117 and `get_message_mods` strips the prefix from `message` at line 118. The filter is applied at line 164 by `try_speak(original_message, ...)`, which calls `is_ic_filtered` on the raw text in `/mob/try_speak` (`code/modules/mob/mob_say.dm:49`, filter call at line 54).

The filter regex uses word boundaries. In `:hblockedinic` there is no boundary between `h` and `blockedinic`, so the raw text does not match. After `:h` is stripped, however, the message that is actually spoken is `blockedinic`. With `:h blockedinic` the space supplies the boundary, which is why that form was already blocked.

## Fix

One commit, "Fix issue 73547: IC word filter now also checks the message after radio prefixes are stripped".

- The filter logic was moved out of `/mob/try_speak` into a new `/mob/proc/passes_ic_filter(message, check_soft = TRUE)` in `code/modules/mob/mob_say.dm`. It runs the hard filter (blocks and warns) and the soft filter (asks the speaker to confirm). `try_speak` now calls it unless the speech is forced or filterproof.
- In `living_say.dm`, after `try_speak`, the stripped `message` is checked too when it differs from `original_message` and the speech is not forced or filterproof. The soft check is skipped there if the raw text already hit the soft filter, so the speaker is prompted only once.

Moving the check into a shared proc seemed less invasive than changing the filter regex to match inside prefixes; no other approach is described in the notes.

## Verification

Tested in game on a build with dmfast, as a de-admined player:

- `:hblockedinic`, `.hblockedinic` and `#blockedinic` were blocked with "That message contained a word prohibited in IC chat".
- `:h hello there friend` was spoken normally.
- A soft-filter word glued to a prefix (`:htestsoftblocks`) gave one prompt, and answering Yes sent the message.

Not checked: other filter-bearing paths (whispers, emotes, other languages), prefix forms beyond the ones listed, and a stock BYOND build. No unit test was added.

## Notes

- Upstream PR 76483 (emotes) does not cover this, and the bug was still present on master `87b93338`.
- Admins bypass the filter by design, so this affects only non-admin players.
